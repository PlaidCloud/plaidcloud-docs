# PlaidCloud Documentation — Project Notes

Astro Starlight docs site at [docs.plaidcloud.com](https://docs.plaidcloud.com), deployed via Cloudflare Workers Static Assets.

## Stack and constraints

- **Astro + Starlight** for the framework; Pagefind for search; no other docs plugins beyond `@astrojs/sitemap` and `starlight-llms-txt`.
- **Cloudflare Workers Static Assets** (free plan) for hosting. Hard cap: **100 MB total upload size, 20,000 files max**. The current build sits at ~125 MB and ~2,800 files — close to the limit. Any change that meaningfully grows per-page size needs to be evaluated against the cap.
- **Node 22+** required for Astro 6.

## Sidebar architecture (read before touching `astro.config.mjs`)

Starlight inlines the **full sidebar tree** into every page's HTML at build time. With 1,400+ pages and ~1,400 reference entries (workflow steps + expression functions), a fully autogenerated sidebar produced 363 KB per page (~493 MB total) — well over the 100 MB cap.

The current sidebar is split:

| Section | Sidebar mode | Why |
|---|---|---|
| `get-started/` | Hand-curated entries | Small, deliberate ordering |
| `guides/` | Hand-curated top, autogenerate at leaf | Friendly labels for the ~13 sub-guide groups |
| `reference/` | **Top-level only** (5 link entries) | Full tree would inline 1,400+ entries × 1,400 pages = breach the cap |
| `integrations/` | Hand-curated | Friendly labels |
| `administration/` | Hand-curated | Friendly labels |
| `releases/` | Single link | Timeline lives on the index page |

**Implication for reference content navigation:** users reach `/reference/connectors/databases/postgres/` via landing-page link lists, not the sidebar. So every reference category and sub-category index page **must** explicitly list its children. If you add a new connector, workflow step, or expression function, update the relevant category's `index.md` to link to it. Same applies to anything under `reference/cli/`.

## Content conventions

### File layout

```
src/content/docs/
├── get-started/    Quickstart, concepts, tutorials
├── guides/         Task-oriented how-to content (autogenerated sidebar)
├── reference/      Lookup content; sidebar is curated
│   ├── connectors/        Provider-specific reference (~50 pages)
│   ├── workflow-steps/    Every step type (~190 pages, 14 categories)
│   ├── expressions/       SQL function reference (~1,000+ pages, v1 + v2)
│   ├── cli/               PlaidLink, PlaidXL, Jupyter CLI
│   └── glossary.mdx       Single canonical terms page
├── integrations/   External tools (AI agents, PySpark)
├── administration/ Access management, scheduled events
└── releases/       Monthly summaries (Phase E content)
```

### Front matter

Required: `title`, `description`. Optional: `sidebar.label`, `sidebar.order`, `template: splash` (for landing-style pages).

Description bounds are intentionally permissive (any length); the original Zod schema with `.min(20).max(160)` was relaxed during migration so existing pages wouldn't fail the build. Tightening is a future cleanup item.

### House style

- **Title Case** for every H2-H6 heading. Run `python3 scripts/title-case-headings.py` if you change a batch of headings; the script handles acronyms (SQL, API, OAuth, etc.) and product names correctly.
- **Front matter `title:` is also Title Case.**
- **Sidebar `label:` is also Title Case.**
- **Voice**: second person ("you can do X"). PlaidCloud company voice ("we recommend") is fine where it reflects an explicit recommendation. Avoid third-person "the user" except when referring to external system accounts (AWS IAM users, SAML user attributes, etc.).
- **Don't restate the obvious**. A step called "Compress PDF" doesn't need a description saying "This step compresses a PDF" — go straight to inputs, outputs, and when to use it.

### Page patterns

- **Reference pages**: short description → Configuration / Inputs / Outputs / Common Uses / Related links
- **Workflow step pages**: `## Description` (2-3 sentences with use case context) → step-specific sections (Load Parameters, etc.)
- **Guide pages**: prerequisites if any → numbered steps → notes → next steps
- **Landing/index pages**: 1-2 sentence intro → categorized link list (CardGrid or plain `## H2` + bullet list)

## Build and deploy

```bash
npm install
npm run dev          # local dev at http://localhost:4321
npm run build        # production build to dist/
```

Pushed commits to the `astro-migration` branch trigger CF Workers Builds:

- Build command: `npm ci && npm run build`
- Deploy command: `npx wrangler deploy`
- Wrangler config: `wrangler.jsonc` at repo root (assets: `./dist`, 404 handling: `404-page`)

**Don't push casually.** Each push runs through CF's build minutes (3,000/month free). Stage changes locally with `npm run build` first.

## Adding content

### A new guide page

1. Drop the `.md` or `.mdx` in the right `src/content/docs/guides/<section>/` folder
2. Front matter: `title`, `description`, optional `sidebar.order`
3. That's it — the autogenerated sidebar picks it up

### A new connector reference page

1. Drop `.md` in `src/content/docs/reference/connectors/<category>/`
2. Front matter with `title`, `description`, `sidebar.order` if needed
3. **Update the category's `index.md`** to add a link entry — sidebar won't surface the new page on its own
4. **Update `reference/connectors/index.md`** if the new connector should be listed there too

### A new workflow step reference page

1. Drop in `src/content/docs/reference/workflow-steps/<category>/`
2. **Update the category's `index.md`** — same constraint as connectors
3. Step pages typically follow: Description → step-specific Load Parameters / Configuration → Examples (or "No examples yet.")

### A new monthly release page

The PR template (`.github/pull_request_template.md`) has a "User-facing change?" checkbox and a customer summary field. Future monthly notes should be writable directly from the squash-merge commit body — no excavation needed.

For the current corpus, monthly pages were generated from `plaid-tenant-infrastructure` tag history via:

- `scripts/release-harvest.py` — walks tenant-v* tags, buckets by month, outputs JSON to `/tmp/release-bundles/`
- `scripts/release-filter.py` — classifies extracted PR titles as signal/neutral/noise (for review before writing)

These scripts are retained as documentation of the approach and can re-run when a future month's notes need help.

## Custom components

Three custom Starlight overrides:

- **`src/components/PageTitle.astro`** — adds a breadcrumb trail above the H1 on any page 2+ levels deep. Walks the slug, looks up each ancestor's `index` page in the docs collection to get a friendly title, and renders a clickable trail.
- **`src/components/Head.astro`** — extends Starlight's default `<head>` with:
  - **JSON-LD `TechArticle` structured data** for SEO rich results
  - **Per-page OG image meta tags** pointing at the image generated by `src/pages/open-graph/[...slug].ts`
- **`src/snippets/`** (not a component, but related) — reusable MDX fragments imported by docs pages, replacing Hugo's `{{< include >}}` shortcode. Imported via the `@snippets/*` TypeScript path alias.

No SwaggerUI component — interactive API docs are served per-tenant inside each instance, not centrally on this site.

### OG image generation

`src/pages/open-graph/[...slug].ts` uses `astro-og-canvas` to generate per-page social-card PNGs at build time. To keep the build under the Workers Assets size cap, it **skips deep reference pages** (workflow-step pages and expression-function pages) — they share a single `/open-graph/_default.png`. Top-level pages and category landings get bespoke per-page images.

If you add a new section that should get per-page OG images, update the `shouldGenerate()` filter in both `open-graph/[...slug].ts` and `components/Head.astro` (they must stay in sync).

## Don't touch

- **Hugo files are gone** (deleted in Phase 7 cleanup). Don't re-introduce `content/en/`, `static/`, `themes/`, `layouts/`, `config.toml`, or related infrastructure. The current source of truth is `src/content/docs/`.
- **`public/_redirects`** has ~1,400 entries mapping legacy Hugo URLs to current Astro URLs. Don't delete entries — they protect inbound links from the old site.
- **`public/images/`** holds shared image assets at stable paths. New page-specific images can go alongside the page for `astro:assets` optimization, but shared images should stay where they are so existing references work.
- **`scripts/migrate.py`** is a one-shot migration tool retained for reference. Don't re-run it; it's idempotent but would no-op or duplicate work depending on current state.

## CI checks

`.github/workflows/docs-checks.yaml` runs on every PR:

- **Lychee link check** — scans built `dist/` HTML for broken links. Excludes `docs.plaidcloud.com` (self-references resolve only post-deploy), `mailto:`, and loopback. Report uploaded as artifact.
- **Vale prose lint** — Google style pack + PlaidCloud vocab (`styles/Vocab/PlaidCloud/accept.txt`). `.vale.ini` disables `Google.Headings` (our own Title Case script owns this), `Google.We` (company voice OK), `Google.Contractions` (matches voice). Fenced code blocks are token-ignored.

If a check fails, fix it before merge — don't disable the rule unless there's an explicit reason captured here.

## Open items

- **PR preview deployments**: Cloudflare Workers Builds supports per-PR previews via the CF dashboard (toggle "Preview branches" → All non-production branches). Currently disabled to conserve build minutes; enable when team review of doc PRs becomes a bottleneck.
- **Feedback widget**: a "was this helpful?" widget at page bottom would feed signal on content quality. Requires GitHub PAT + Turnstile to keep it spam-free. Deferred until we have bandwidth to triage feedback.
- **Search analytics**: Plausible or similar event tracking on Pagefind queries would surface what users search for but don't find. Deferred — install when we want to drive content priorities from real search misses.
- **Description Zod schema tightening**: relaxed during migration; could re-enable `.min(20).max(160)` after a description audit pass on the corpus. Many pages have no description or one that's too short for SEO meta-description quality.
- **Forward release notes process**: rely on PR template + commit conventions; future monthly summary should be a 30-minute editorial pass, not an excavation. First "real" test is the next month after merge to production.
- **The 100 MB Workers cap**: if the corpus grows substantially (more reference content, more guide subsections), reassess. Options if we breach it: drop `lastUpdated`, drop `pagination`, paid CF plan, or split reference into a separate Astro project.
