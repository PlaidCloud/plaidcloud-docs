*~15 minutes · copier ou importer un projet, puis le faire vôtre*

La victoire la plus rapide du premier jour dans PlaidCloud n'est pas de construire à partir de rien, mais de partir de quelque chose qui fonctionne déjà. Choisissez un projet qui importe déjà des données, les transforme et produit un résultat, obtenez-en votre propre copie et modifiez les parties qui vous concernent.

Il n'existe pas de galerie de modèles à parcourir. Vous disposez en revanche de deux façons concrètes de démarrer à partir d'un projet qui fonctionne :

- **Copier un projet** qui existe déjà dans votre espace de travail vers un tout nouveau projet qui vous appartient : [Copier un projet](/fr/guides/projects/managing-projects/#copie-dun-projet).
- **Exécuter un bundle portable** : un projet que quelqu'un a exporté sous forme de package autonome au [format portable](/fr/guides/projects/export-to-portable-format/), qui s'exécute seul en dehors de PlaidCloud.

Le choix dépend de votre destination.

| Vous voulez… | Utilisez | Résultat |
|---|---|---|
| Construire sur un projet dans PlaidCloud et continuer à itérer | **Copier le projet** | Un nouveau projet qui vous appartient, prêt à être modifié et exécuté |
| Exécuter la logique d'un projet hors ligne, ou la remettre à quelqu'un qui n'a pas de compte PlaidCloud | **Exporter au format portable** | Un package autonome Python + DuckDB |

## Prérequis

- Un espace de travail PlaidCloud ([démarrez un essai gratuit](https://app.plaidcloud.com) si vous n'en avez pas).
- Pour la **voie A** : un projet existant visible dans l'onglet **Projets** : l'un des vôtres, un exemple partagé ou tout projet auquel un collègue vous a donné accès.
- Pour la **voie B** : un `.zip` au format portable exporté par quelqu'un, ou un projet à vous à exporter.

> **Vous ne savez pas ce qu'est un projet ?** Un projet est l'unité de travail dans PlaidCloud : il possède ses propres données, workflows, dimensions et historique, et ne partage aucun état avec un autre projet. Lisez d'abord [Projets](/fr/guides/projects/) si c'est nouveau pour vous.

## Voie A : copier un projet existant

La copie crée un duplicata complet et modifiable, entier ou limité aux parties que vous choisissez, dans un tout nouveau projet qui est entièrement à vous.

1. Ouvrez **Analyser** et sélectionnez l'onglet **Projets**.
2. Sélectionnez le projet dont vous voulez partir.
3. Cliquez sur le bouton **Actions** et choisissez **Copier le projet**.
4. Choisissez **a new project** comme cible. Donnez-lui un nom et un **ID**.
5. Laissez l'arborescence de sélection entièrement cochée pour reprendre tout le projet, puis cliquez sur **Copier le projet**.

> **L'ID est définitif.** L'ID que vous donnez au nouveau projet devient le nom de son schéma et ne peut plus être modifié ensuite. Choisissez quelque chose avec lequel vous êtes à l'aise : le nom peut être changé à tout moment, l'ID non.

La copie s'exécute en arrière-plan ; vous êtes averti lorsqu'elle se termine. Consultez [Copier un projet](/fr/guides/projects/managing-projects/#copie-dun-projet) pour la boîte de dialogue complète.

### Reprendre uniquement les parties souhaitées

Vous n'êtes pas obligé de tout copier. L'arborescence de sélection liste le contenu du projet par type (workflows, étapes, tables, dimensions, éditeurs de données, fonctions définies par l'utilisateur) et vous pouvez cocher uniquement les parties voulues. Tout ce que vous cochez emporte automatiquement ses dépendances : les tables qu'une étape lit et écrit, les dimensions sur lesquelles elle charge, les fonctions qu'elle appelle et tout sous-workflow qu'elle invoque. Vous n'avez jamais à déterminer ces dépendances vous-même.

> **Gardez les références pointées vers votre copie.** Laissez **Mettre à jour les références** activé (valeur par défaut). Cette option réécrit les étapes copiées pour qu'elles pointent vers les tables et objets de votre nouveau projet plutôt que vers l'original, ce qui est presque toujours ce que vous voulez. Désactivez-la uniquement si vous souhaitez délibérément que la copie continue de lire les objets du projet source.

## Voie B : partir d'un bundle portable

Un bundle portable est un projet empaqueté sous forme de programme Python autonome qui s'exécute sur [DuckDB](https://duckdb.org) sans aucune connexion à PlaidCloud. C'est la façon de partir d'un projet qui fonctionne lorsque vous voulez qu'il s'exécute *hors de la plateforme* : sur votre ordinateur portable, dans une tâche de CI, ou entre les mains de quelqu'un qui n'a pas de compte PlaidCloud.

Si un collègue vous a déjà remis un bundle, passez à [Exécuter](#exécuter). Pour en créer un vous-même :

1. Ouvrez **Analyser** et sélectionnez l'onglet **Projets**.
2. Sélectionnez un seul projet.
3. Ouvrez le menu **Actions** et choisissez **Exporter au format portable**.
4. Définissez le **Compte de documents** et le **Chemin du dossier** dans lesquels le package est écrit, laissez **Include data** coché pour qu'il s'exécute sans aucune source externe, puis cliquez sur **Exporter**.

Le résultat est un `.zip` contenant un script Python par workflow, les instantanés de données Parquet, un `requirements.txt` listant les paquets Python dont les scripts ont besoin, ainsi que `README.md`, `COVERAGE.md` et `RUN_ORDER.md`. Consultez [Exporter au format portable](/fr/guides/projects/export-to-portable-format/) pour le rôle de chaque fichier.

> **Un bundle portable est un instantané à sens unique, pas une réimportation.** Il s'exécute *en dehors* de PlaidCloud et ne se synchronise pas en retour : les modifications apportées au package ne reviennent pas dans le projet, et un nouvel export après modifications produit un package neuf. Pour continuer à travailler dans PlaidCloud, utilisez plutôt la **voie A**. Pour continuer à itérer dans PlaidCloud *et* distribuer une copie exécutable, faites les deux.

> **La fidélité est assurée au mieux.** Les étapes de transformation SQL sont reproduites à l'identique. Les étapes propriétaires ou à effets de bord (allocations, chargements de dimensions, notifications, étapes de documents et de rapports, scripts) sont exportées sous forme de stubs qui ne se réexécutent pas ; leur dernier résultat matérialisé est alors inclus sous forme d'instantané. La fidélité de chaque étape est consignée dans `COVERAGE.md`. Pour obtenir des résultats entièrement recalculés, exécutez le projet dans PlaidCloud.

### Exécuter

Décompressez le package, créez un environnement Python et exécutez chaque script de workflow dans l'ordre indiqué par `RUN_ORDER.md` :

```bash
python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
python pipeline_<workflow>.py
```

Chaque script construit ses tables dans une base DuckDB locale. Les étapes SQL sont recalculées en direct ; les étapes remplacées par des stubs laissent en place leur résultat sous forme d'instantané.

## Faites-le vôtre

Quelle que soit la façon dont vous avez commencé, la copie est maintenant à vous : c'est là que la victoire du premier jour porte ses fruits. Quelques premières actions :

| Faites ceci | Où |
|---|---|
| Faire pointer les importations vers *vos* données plutôt que celles de l'exemple | Les étapes d'importation de chaque workflow ; consultez [Charger, transformer et publier des données](/fr/get-started/tutorials/load-and-transform-data/) |
| Renommer le projet ou ajuster qui peut l'ouvrir | [Gérer les projets](/fr/guides/projects/managing-projects/) → Contrôle d'accès |
| Définir des variables de projet pour les valeurs qui reviennent d'un workflow à l'autre | [Gérer les variables du projet](/fr/guides/projects/managing-projects/#gestion-des-variables-du-projet) |
| Vérifier que l'ensemble s'exécute toujours de bout en bout | Cliquez sur **Exécuter** sur chaque workflow et suivez le journal |

Comme chaque modification est suivie, vous pouvez expérimenter librement : le [suivi automatique des modifications](/fr/guides/projects/managing-projects/#historique-des-versions) vous permet de récupérer n'importe quel état antérieur à un instant donné si une modification tourne mal.
