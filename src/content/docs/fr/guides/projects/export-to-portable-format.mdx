**Exporter au format portable** empaquette les workflows d'un projet sous la forme d'un programme Python autonome qui s'exécute sur [DuckDB](https://duckdb.org) sans aucune connexion à PlaidCloud. Il produit une copie portable de la logique et des données du projet, qui s'exécute hors ligne, de manière indépendante.

C'est une exportation à sens unique. Le package généré est un instantané à un instant donné ; il ne se synchronise pas en retour, et une nouvelle exportation après des modifications produit un nouveau package.

<Aside type="caution" title="Fidélité au mieux">
L'exportation reproduit exactement les étapes de transformation basées sur SQL. Les opérations propriétaires ou à effets de bord — allocations, chargements de dimensions, notifications, étapes de documents et de rapports, scripts — sont exportées sous forme de **stubs** : leur configuration d'origine est conservée et, lorsque la table de sortie a été matérialisée, ses données sont incluses sous forme d'instantané, mais l'étape elle-même ne se réexécute pas. La fidélité de chaque étape est consignée dans `COVERAGE.md` à l'intérieur du package. Pour obtenir des résultats garantis et entièrement recalculés, exécutez le projet dans PlaidCloud.
</Aside>

## Exporter un projet

1. Ouvrez **Analyze** et sélectionnez l'onglet **Projets**.
2. Sélectionnez un seul projet.
3. Ouvrez le menu **Actions** (ou faites un clic droit sur le projet) et choisissez **Exporter au format portable** — il se trouve à côté de **Exporter le projet**.
4. Dans la boîte de dialogue :
   - **Compte de documents** — le compte de documents dans lequel le package est écrit.
   - **Chemin du dossier** — le dossier de ce compte, par exemple `/exports`.
   - **Inclure les données** — lorsque cette case est cochée (par défaut), les tables source et d'instantané sont incluses au format Parquet afin que le package s'exécute sans aucune donnée externe. Décochez-la pour ne livrer que le code et les contrats de schéma, que vous alimentez ensuite vous-même.
5. Cliquez sur **Exporter**. Une fois l'opération terminée, un message confirme où le package a été écrit et combien de tables ont été capturées en instantané.

L'action nécessite l'accès au projet et à la lecture de ses tables — le même niveau d'accès que celui requis aujourd'hui pour exporter les données de table.

## Contenu du package

L'exportation est un fichier `.zip` contenant :

- `pipeline_<workflow>.py` — un script par workflow, avec les étapes dans l'ordre d'exécution.
- `config.py` — la sélection du moteur (DuckDB par défaut) et le nom de schéma du projet.
- `_runtime.py` — une petite couche d'adaptation au moteur ; la seule dépendance en plus de DuckDB.
- `stubs.py` — des fonctions sans effet pour les opérations non portables, chacune portant la configuration d'origine de l'étape.
- `data/` — des instantanés Parquet des tables sources et figées (lorsque **Inclure les données** était coché).
- `requirements.txt` — les dépendances Python (uniquement `duckdb`).
- `README.md`, `COVERAGE.md`, `RUN_ORDER.md` — comment l'exécuter, la fidélité de chaque étape, et l'ordre d'exécution des scripts de workflow.

## Exécuter le package

1. Décompressez le package et créez un environnement Python :

   ```bash
   python -m venv .venv && source .venv/bin/activate
   pip install -r requirements.txt
   ```

2. Exécutez chaque script de workflow, dans l'ordre indiqué dans `RUN_ORDER.md` :

   ```bash
   python pipeline_<workflow>.py
   ```

Chaque script génère ses tables dans une base DuckDB locale (`export.duckdb` par défaut). Les étapes de transformation SQL sont recalculées en direct ; les étapes remplacées par des stubs affichent un avis et laissent en place leur sortie capturée en instantané. Pour pointer le package vers votre propre entrepôt au lieu de DuckDB, définissez `ENGINE` dans `config.py`.
