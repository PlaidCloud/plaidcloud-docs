Les données tabulaires et les informations de PlaidCloud sont stockées dans des entrepôts de données Greenplum. Cela offre une évolutivité et des performances considérables tout en s'appuyant sur une technologie éprouvée et bien connue, afin de réduire au minimum le risque de perte ou de corruption des données.

De plus, l'utilisation d'un entrepôt de données qui fonctionne avec une syntaxe commune permet à des outils tiers de se connecter et d'explorer directement les données. En pratique, cela rend l'écosystème de données de PlaidCloud ouvert et explorable, tout en garantissant une sécurité et des contrôles d'accès de premier plan.

## Tables

Les tables contiennent les données tabulaires physiques dans l'ensemble de PlaidCloud. Une table peut contenir plusieurs téraoctets de données si nécessaire. Les données sont stockées sur de nombreux serveurs physiques et sont automatiquement mises en miroir pour garantir leur intégrité et leur haute disponibilité.

Les tables se composent de colonnes de différents types de données. Utiliser un type de données approprié peut améliorer les performances et, surtout, réduire la taille de stockage de vos données. PlaidCloud peut aussi mieux compresser les données lorsqu'elles utilisent le type le plus approprié. Ce type est généralement deviné par PlaidCloud, mais il est également possible de le modifier à l'aide des mappeurs de colonnes dans les étapes de workflow.

Vous pouvez rechercher des tables par le workflow qui les utilise, par nom de colonne ou par valeur qu'elles contiennent, et voir à quand remonte la dernière lecture d'une table. Consultez [Gérer les tables et les vues](/fr/guides/projects/managing-tables-and-views/#recherche-de-tables).

## Vues

Les vues se comportent comme des tables, mais ne contiennent aucune donnée physique. Ce sont des représentations logiques de tables, obtenues par une requête. L'utilisation de vues peut réduire l'espace de stockage.

L'utilisation des vues comporte toutefois certaines limites. Gardez à l'esprit les points suivants :

 * Performances de l'empilement de vues : l'empilement de vues (une vue d'une vue d'une vue, etc.) peut nuire aux performances sur de très grandes tables ou pour des calculs complexes. Il peut être nécessaire de créer des tables intermédiaires pour améliorer les performances.
 * Performances des tableaux de bord : publier une vue pour un tableau de bord ne pose aucun problème, mais pour de très grandes tables, il peut être préférable de publier une table plutôt qu'une vue afin d'offrir la meilleure expérience aux utilisateurs.
 * Données dynamiques : les données d'une vue changent lorsque les données de la table référencée changent. Cela peut être un avantage (tout se met à jour automatiquement) ou une source de désagréments inattendus si vous souhaitiez un jeu de données statique.

<Aside>L'utilisation de vues peut accélérer les workflows, car aucun déplacement de données n'est nécessaire au moment de l'exécution du workflow.</Aside>

<Aside>Comme les vues ne contiennent aucune donnée, vous constaterez qu'elles ne peuvent pas servir de cible pour des importations. Il faut alors utiliser une table.</Aside>
