Une **connexion** est une configuration enregistrée qui permet à PlaidCloud d'atteindre un système externe : base de données, lac de données, ERP, API REST, service cloud ou fournisseur Git. Les étapes de workflow référencent la connexion par son nom ; les détails du point de terminaison et les identifiants sont ainsi regroupés en un seul endroit et réutilisés dans chaque étape et chaque projet qui en a besoin.

Les connexions se gèrent depuis **Tools > Connections**.

## Créer une connexion

1. Ouvrez **Tools > Connections**
2. Cliquez sur `New Connection` dans la barre d'outils et choisissez dans le menu le système auquel vous souhaitez vous connecter
3. Renseignez le formulaire de connexion (les onglets et les champs varient selon le type ; consultez [Formulaire de connexion](#formulaire-de-connexion) ci-dessous)
4. Cliquez sur `Create` pour enregistrer

La nouvelle connexion apparaît dans la liste, avec vous comme propriétaire.

<Aside type="note">La liste des types de connexion et les champs requis pour chacun sont répertoriés dans la [référence des connecteurs](/fr/reference/connectors/). Pour un service sans connecteur dédié, utilisez la [connexion REST générique](/fr/reference/connectors/rest/generic-rest/).</Aside>

## Formulaire de connexion

La plupart des connexions ouvrent un formulaire à plusieurs onglets. Les onglets exacts dépendent du type, mais vous verrez généralement :

- **Configuration de la connexion** (ou **Détails de la connexion** pour REST) : le `Name` de la connexion, un `Memo` facultatif, l'hôte, le port et la base de données (ou l'hôte et le type d'authentification pour REST), le commutateur `Usage` (`Active`) et le `Security Model`. Pour une connexion de base de données, les identifiants se trouvent ici, dans un groupe **Identifiants d'authentification** ; pour une connexion REST, ils ont leur propre onglet **Authentification**.
- **Configuration SSL** : `Use SSL`, ainsi que le mode SSL et les certificats client/racine facultatifs pour une connexion chiffrée.
- **Configuration SSH** : `Use SSH`, ainsi que l'hôte bastion, le port, l'utilisateur et la clé permettant de faire transiter la connexion par un hôte de rebond SSH.

Les champs de mot de passe, de jeton et autres identifiants sont en écriture seule : ils apparaissent vides lorsque vous rouvrez une connexion enregistrée, et les laisser vides à l'enregistrement conserve le secret stocké. Ressaisissez une valeur uniquement si vous voulez la modifier. Cela concerne la clé d'API, le secret client OAuth et le jeton d'actualisation OAuth d'une connexion REST. Les identifiants multilignes (certificat privé NetSuite, certificat et clé privée Anaplan, clé d'API Postman, URL de webhook entrant Slack ou Teams) sont également en écriture seule et sont masqués pendant que vous les saisissez ou les collez. Une valeur de remplacement composée uniquement d'espaces est refusée au lieu d'écraser l'identifiant stocké ; videz le champ pour conserver la valeur enregistrée. La clé client SSL et la clé privée SSH d'une connexion SQL ou Git sont aussi en écriture seule, mais restent visibles pendant la saisie. Tous les autres champs affichent leur valeur réellement enregistrée partout où la connexion est présentée, dans l'éditeur comme via l'API, y compris les champs dont le nom semble sensible (l'indicateur de lecture seule d'une base de données, un identifiant de compte, un schéma, un nom d'hôte) : seul un véritable identifiant est masqué ou caché.

Via l'API REST et MCP, un champ d'identifiant suit la même règle que l'éditeur : envoyez une chaîne vide et PlaidCloud conserve la valeur stockée ; envoyez `null` pour l'effacer. Tout champ qui n'est pas un identifiant s'efface toujours lorsque vous l'envoyez vide.

Les champs obligatoires sont validés à l'enregistrement ; s'il en manque un, le formulaire bascule vers l'onglet contenant le premier champ invalide et le signale.

## Modèle de sécurité

Le `Security Model` d'une connexion détermine qui, dans l'espace de travail, peut l'utiliser :

| Option | Qui peut utiliser la connexion |
|---|---|
| Privé (propriétaires uniquement) | Uniquement les propriétaires. |
| Membres spécifiques uniquement | Les propriétaires, plus une liste explicite de membres. |
| Groupes de sécurité spécifiques uniquement | Les propriétaires, plus les membres de groupes de sécurité désignés. |
| Tous les membres de l'espace de travail | Tous les membres de l'espace de travail. |

Lorsque vous choisissez `Specific Members Only` ou `Specific Security Groups Only`, accordez l'accès depuis le menu `Actions` de la liste : `Members` pour `Specific Members Only` ou `Groups` pour `Specific Security Groups Only`, ainsi que `Agents` et `Owners`, ouvrent chacun une liste de cases à cocher filtrable où vous cochez les personnes qui ont accès (consultez [Attribution avec le sélecteur](/fr/administration/access/managing-security-groups-and-assignments/#attribution-avec-le-sélecteur)). Seul un propriétaire de la connexion ou un administrateur de l'espace de travail peut y modifier l'accès. Toute autre personne qui peut modifier des connexions peut les ouvrir pour voir qui a accès, dans une liste en lecture seule des personnes déjà affectées. Un administrateur de l'espace de travail peut modifier l'accès à une connexion dont il n'est pas propriétaire, afin de la transmettre lorsque ses propriétaires sont partis.

## Qui voit les identifiants d'une connexion

Toute personne qui peut utiliser une connexion peut l'ouvrir et consulter ses paramètres, ainsi que parcourir les dépôts, les branches et les fichiers d'une connexion Git. Les mots de passe, jetons et clés d'une connexion ne sont renvoyés qu'aux membres qui peuvent modifier des connexions ou des workflows. Via l'API REST et MCP, tous les autres les reçoivent masqués.

Lorsque vous parcourez une connexion Git avec une URL de serveur différente de celle qui est enregistrée, saisissez un jeton pour ce serveur.

## Environnements

Une connexion peut contenir une configuration différente par **environnement** (par exemple un hôte de développement et un hôte de production sous un même nom de connexion). Le sélecteur d'environnement de la barre d'outils choisit l'environnement dont vous consultez et modifiez la configuration.

- `New Environment` : ajouter un environnement de connexion
- `Edit Environment` : renommer l'environnement sélectionné
- `Delete Environment` : supprimer l'environnement sélectionné, une fois qu'aucun projet ne l'utilise, qu'aucune étape ne l'a comme [environnement fixe](/fr/guides/projects/managing-projects/#fixer-une-étape-à-un-environnement) et qu'aucun agent ne le dessert. Sinon, le message indique ce qui l'utilise encore. L'environnement par défaut ne peut pas être supprimé.

La colonne `Available` de la liste indique si la connexion sélectionnée est configurée pour l'environnement choisi.

<Aside type="note">L'enregistrement d'une configuration est fusionné avec celle qui est stockée pour cet environnement ; les secrets en écriture seule laissés vides ne sont donc jamais écrasés par des valeurs vides.</Aside>

Les environnements sont partagés avec les agents PlaidLink : l'environnement d'un projet peut donc changer l'agent qui exécute ses étapes distantes ainsi que les connexions qu'il lit. Consultez [Environnements des agents](/fr/reference/cli/plaidlink/agents/#environnements-des-agents).

## Modifier une connexion

1. Sélectionnez la connexion dans la liste
2. Cliquez sur `Edit` dans la barre d'outils (ou faites un clic droit sur la ligne)
3. Modifiez les champs puis cliquez sur `Update`

## Tester une connexion

La façon de tester dépend du type :

- Les **connexions de base de données** (Databricks, Snowflake, PostgreSQL et Redshift) disposent d'un bouton **Tester la connexion** dans l'éditeur. Il ouvre la connexion avec les identifiants que vous avez saisis et signale la réussite (avec la version du serveur atteint) ou la cause de l'échec, sans fermer l'éditeur, afin que vous puissiez corriger et réessayer sur place.
- Les connexions de base de données avec SSH exposent également un test du tunnel SSH dans l'onglet `SSH Config`.
- La [connexion REST générique](/fr/reference/connectors/rest/generic-rest/) dispose d'un onglet `Testing` qui envoie une requête ad hoc via la connexion enregistrée.

Enregistrez la connexion avant de la tester : les tests s'exécutent sur la configuration stockée.

<Aside type="note">**Tester la connexion** apparaît pour un type de connexion dès que son éditeur le propose, actuellement les types de base de données ci-dessus, ainsi que [TM1](/fr/guides/connections/tm1/), [Oracle Essbase](/fr/guides/connections/essbase/), [HFM/FCCS](/fr/guides/connections/hfm-fccs/), Salesforce et Anaplan. Les autres connexions REST, comme NetSuite, ne l'ont pas encore ; testez-les en envoyant une petite requête depuis une étape de workflow (pour NetSuite, consultez [Se connecter à NetSuite](/fr/guides/connections/netsuite/#tester-le-bon-fonctionnement-de-la-connexion)).</Aside>

## Adresses qu'une connexion ne peut pas atteindre

Une connexion ne peut pas pointer vers une adresse de bouclage, une adresse link-local ou une adresse de métadonnées cloud. PlaidCloud vérifie l'adresse à laquelle un nom d'hôte se résout lorsque vous testez la connexion et lorsqu'une étape l'utilise ; une adresse non admise échoue avec une erreur qui nomme l'hôte et l'adresse obtenue. Les adresses de votre réseau privé ne sont pas concernées.

## Cloner, supprimer et tracer l'utilisation

- **Cloner** : dupliquer la configuration d'une connexion pour en créer une nouvelle. Consultez [Cloner une connexion](/fr/guides/connections/clone-connection/).
- **Supprimer** : supprimer la connexion sélectionnée depuis la barre d'outils (une confirmation vous est demandée).
- **Où utilisé…** : lister les étapes de workflow qui référencent la connexion, afin de mesurer l'impact avant de la modifier ou de la supprimer.

<Aside type="caution">`Edit`, `Clone` et `Delete` ne sont disponibles que sur les connexions dont vous êtes propriétaire. Si ces actions sont grisées pour la ligne sélectionnée, vous n'êtes pas propriétaire : demandez à un propriétaire d'effectuer la modification ou de vous ajouter via `Owners`.</Aside>

Il en va de même via l'API REST, JSON-RPC et l'assistant IA ou MCP : modifier les paramètres d'une connexion exige d'en être l'un des propriétaires, ou administrateur de l'espace de travail pour une connexion sans propriétaire. Activer, désactiver, verrouiller et déverrouiller une connexion exige d'être propriétaire ou administrateur de l'espace de travail. Une requête portant sur plusieurs connexions ne s'applique que si vous pouvez modifier chacune d'elles.
