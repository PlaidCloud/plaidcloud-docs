*~45 minutes · a live NetSuite connection, a landed general ledger, a monthly P&L, an A/R aging, and a scheduled refresh*

This is the day-one path for a controller or FP&A analyst: by the end you'll have pulled your **general ledger** straight from NetSuite, turned it into a **monthly Profit & Loss** you can read like a statement, built an **accounts-receivable aging**, put both on a dashboard, and set the whole thing to refresh on its own. No spreadsheet export, no manual re-keying — the numbers come from NetSuite and stay current.

You'll connect once, pull once, and then do the part that actually matters: shaping raw GL rows into the summaries a business person reads on Monday morning.

## Prerequisites

- A PlaidCloud workspace and a project to work in ([start a trial](https://app.plaidcloud.com) if you need one).
- **A working NetSuite connection.** Follow [Connect to NetSuite](/guides/connections/netsuite/) first — you need OAuth 2.0 and REST Web Services enabled in NetSuite, the integration's client id, a certificate id, your account id, and the private-key PEM. Confirm **Send Test Request** is green before you start here.
- A little SuiteQL is helpful but not required — every query is provided. Keep [NetSuite SuiteQL Query Examples](/guides/connections/netsuite-financial-queries/) open in a tab; this tutorial draws from it.

<Aside type="note">
Two different SQL dialects appear below, and it's worth knowing which is which. The **pull** query is **SuiteQL**, which runs *inside NetSuite*. The **shaping** query is ordinary PlaidCloud warehouse SQL, which runs *in PlaidCloud* over the table you already landed. They look similar but have different functions available.
</Aside>

## Step 1: Create a Workflow

The workflow is the pipeline that pulls and shapes the data.

<Steps>

1. Open your project and switch to the **Workflows** tab.
2. Click **New Workflow**, name it something like `NetSuite Financials`, and open it.

</Steps>

## Step 2: Pull the General Ledger

One SuiteQL query gives you a year of posting activity — every account, every month — which is enough to build both a P&L and, later, other statements.

<Steps>

1. Add a [REST Request step](/guides/workflows/rest-request-step/). On the **Request** tab set **Connection** to your NetSuite connection, **Method** to `POST`, and **Endpoint** to `/services/rest/query/v1/suiteql`.

2. In the **Body**, put this SuiteQL wrapped as `{"q": "…"}`:

   ```sql
   SELECT
       TO_CHAR(t.trandate, 'YYYY-MM')  AS period,
       a.accttype                      AS account_type,
       a.acctnumber                    AS account_number,
       BUILTIN.DF(a.id)                AS account_name,
       tal.amount                      AS amount
   FROM transactionaccountingline tal
       JOIN transaction t ON t.id = tal.transaction
       JOIN account a     ON a.id = tal.account
   WHERE tal.posting = 'T'
       AND tal.accountingbook = 1
       AND t.trandate BETWEEN TO_DATE('2026-01-01', 'YYYY-MM-DD')
                          AND TO_DATE('2026-12-31', 'YYYY-MM-DD')
   ORDER BY period, a.acctnumber
   ```

3. On the **Response** tab, set the destination to **Table** — call it `netsuite_gl` — and set the column types: `amount` → **Currency**, everything else → **Text**. (SuiteQL returns numbers and dates as text; the type is what lets `amount` add up.)

4. Click **Send Test Request** to confirm it runs, then run the step. You now have a `netsuite_gl` table: one row per account per month, with a signed posting amount.

</Steps>

<Aside type="note">
`amount` is **debit-positive, credit-negative** — NetSuite's GL convention. That's the raw truth; the next step turns it into a readable statement. If your books span more than one subsidiary or currency, filter to one subsidiary (`t.subsidiary = <id>`) — see the multi-currency caution in the [query examples](/guides/connections/netsuite-financial-queries/#conventions-used-in-every-recipe).
</Aside>

## Step 3: Shape the GL Into a P&L

Now the analysis. A P&L is just the GL rolled up: income and expense accounts, grouped into a few lines, with the sign flipped so revenue reads positive. One PlaidCloud SQL transform does it.

<Steps>

1. Add a table transform step that reads from `netsuite_gl` and writes to a new table `netsuite_pnl`. Open its **SQL editor** and enter:

   ```sql
   SELECT
       period,
       CASE
           WHEN account_type IN ('Income', 'OthIncome')  THEN '1 - Revenue'
           WHEN account_type = 'COGS'                     THEN '2 - Cost of Goods Sold'
           WHEN account_type IN ('Expense', 'OthExpense') THEN '3 - Operating Expenses'
       END                             AS pnl_line,
       SUM(-1 * amount)                AS amount
   FROM netsuite_gl
   WHERE account_type IN ('Income', 'OthIncome', 'COGS', 'Expense', 'OthExpense')
   GROUP BY
       period,
       CASE
           WHEN account_type IN ('Income', 'OthIncome')  THEN '1 - Revenue'
           WHEN account_type = 'COGS'                     THEN '2 - Cost of Goods Sold'
           WHEN account_type IN ('Expense', 'OthExpense') THEN '3 - Operating Expenses'
       END
   ORDER BY period, pnl_line
   ```

2. Run the step.

</Steps>

The `SUM(-1 * amount)` is the one accounting move: negating the debit-positive amount makes **revenue positive and costs negative**, so each month's three lines *add up to net income*. This is ordinary PlaidCloud SQL, not SuiteQL — the [v1 / v2 function reference](/get-started/tutorials/transform-with-sql/) covers what's available, and **Prettify** keeps it readable.

<Aside type="tip">
Grouping several dozen accounts into three lines is deliberately coarse for a first pass. To break Operating Expenses into departments, add `department` (via `BUILTIN.DF(tl.department)`, joining `transactionline`) to the Step 2 pull and to this grouping.
</Aside>

## Step 4: Read It Like a Finance Person

Open the `netsuite_pnl` table. For each month you have three numbers:

| period | pnl_line | amount |
|---|---|---|
| 2026-01 | 1 - Revenue | 486,200.00 |
| 2026-01 | 2 - Cost of Goods Sold | -190,540.00 |
| 2026-01 | 3 - Operating Expenses | -212,880.00 |

Read straight off it:

- **Gross profit** = Revenue + Cost of Goods Sold (COGS is already negative) → `486,200 − 190,540 = 295,660`.
- **Net income** = the three lines summed → `82,780`.
- **Gross margin %** = gross profit ÷ revenue → ~61%.

The first thing to do is **tie it out**: run NetSuite's own Income Statement for the same month and confirm revenue and net income match. If they don't, it's almost always a scope difference — a subsidiary/currency filter, or posting-period vs transaction-date alignment (see the [note on periods](/guides/connections/netsuite-financial-queries/#trial-balance)). Trust the pipeline only once it ties.

<Aside type="tip">
Want the classic month-across-the-top layout? Add one more SQL transform that pivots `period` into columns — one column per month, one row per P&L line — using a `CASE`-per-month `SUM`, or the [pivot approach in Transform Data With SQL](/get-started/tutorials/transform-with-sql/). That gives you month-over-month at a glance.
</Aside>

## Step 5: Build an A/R Aging

The second day-one win, and it follows the same connect-pull-shape shape. Start from the open-receivables recipe, then bucket it by how overdue each invoice is.

<Steps>

1. Add another **REST Request** step (same connection, `POST`, the suiteql endpoint) with this body:

   ```sql
   SELECT
       t.tranid                            AS invoice_number,
       BUILTIN.DF(t.entity)                AS customer,
       TO_CHAR(t.trandate, 'YYYY-MM-DD')   AS invoice_date,
       TO_CHAR(t.duedate, 'YYYY-MM-DD')    AS due_date,
       t.foreigntotal                      AS invoice_total,
       t.foreignamountunpaid               AS amount_unpaid
   FROM transaction t
   WHERE t.type = 'CustInvc'
       AND t.foreignamountunpaid <> 0
   ORDER BY t.tranid
   ```

   Land it as `netsuite_open_ar`, with `invoice_total` and `amount_unpaid` → **Currency**, `invoice_date` and `due_date` → **Date**, the rest → **Text**.

2. Add a table transform reading `netsuite_open_ar` into `netsuite_ar_aging`, with this SQL:

   ```sql
   SELECT
       CASE
           WHEN DATEDIFF(CURRENT_DATE, due_date) <= 0  THEN '0 - Current'
           WHEN DATEDIFF(CURRENT_DATE, due_date) <= 30 THEN '1 - 1-30 days'
           WHEN DATEDIFF(CURRENT_DATE, due_date) <= 60 THEN '2 - 31-60 days'
           WHEN DATEDIFF(CURRENT_DATE, due_date) <= 90 THEN '3 - 61-90 days'
           ELSE '4 - Over 90 days'
       END                     AS aging_bucket,
       COUNT(*)                AS invoices,
       SUM(amount_unpaid)      AS balance
   FROM netsuite_open_ar
   GROUP BY
       CASE
           WHEN DATEDIFF(CURRENT_DATE, due_date) <= 0  THEN '0 - Current'
           WHEN DATEDIFF(CURRENT_DATE, due_date) <= 30 THEN '1 - 1-30 days'
           WHEN DATEDIFF(CURRENT_DATE, due_date) <= 60 THEN '2 - 31-60 days'
           WHEN DATEDIFF(CURRENT_DATE, due_date) <= 90 THEN '3 - 61-90 days'
           ELSE '4 - Over 90 days'
       END
   ORDER BY aging_bucket
   ```

3. Run it. `netsuite_ar_aging` now tells you, in five rows, how much is current versus 30/60/90+ days overdue — the collections view a business reads first. (`due_date` must be typed as **Date** for `DATEDIFF` to work; the exact date-difference function can vary by warehouse — see the [function reference](/get-started/tutorials/transform-with-sql/).)

</Steps>

## Step 6: Put It on a Dashboard

Numbers in a table are fine; a chart is what you send to the CFO. [Publish](/get-started/tutorials/load-and-transform-data/#step-7-publish-the-result) `netsuite_pnl` and `netsuite_ar_aging`, then follow [Build a Dashboard](/get-started/tutorials/build-a-dashboard/) to add:

- a **bar chart** of net income (or revenue) by `period`, and
- a **pie or bar** of A/R `balance` by `aging_bucket`.

That's a live NetSuite financial dashboard — no export, refreshed whenever the workflow runs.

## Step 7: Schedule the Refresh

<Steps>

1. Run the whole workflow once, top to bottom, to confirm every step is green.
2. [Schedule the workflow](/get-started/tutorials/schedule-a-workflow/) — monthly on a close cadence, or nightly if you want the A/R aging fresh each morning.

</Steps>

Because every pull is a full-table replace, each run re-extracts the slice its `WHERE` clause defines — keep those to the window you need (the current year, open invoices only) rather than all of history.

## What You've Built

Starting from an empty workflow, you pulled live NetSuite GL and receivables, shaped them into a **monthly P&L** and an **A/R aging** with two small SQL transforms, put them on a dashboard, and set them to refresh — the core reporting loop a finance team runs, now automated.
