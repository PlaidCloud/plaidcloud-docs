## Pesquisar

A pesquisa de projetos é feita com **Filtro** na parte inferior da lista, ao lado da contagem de linhas. Pressione **/** ou Ctrl/Cmd+F para ir até ele. O filtro procura correspondências nos nomes e rótulos dos projetos e mostra os resultados na hierarquia.


## Criar novos projetos

Para criar um novo projeto:

1. Abra o Analyze
2. Selecione “Projetos” na barra de menus superior
3. Clique no botão “Novo projeto”
4. Preencha as informações do formulário, incluindo a seção “Access Control”
5. Clique em “Criar”

O projeto agora está pronto para você atualizar as permissões de acesso, adicionar proprietários e criar fluxos de trabalho.

<Aside>Por padrão, o projeto ficará acessível a todos os membros do espaço de trabalho atual</Aside>


## Definir uma conta de documentos padrão

Na página inicial do projeto, ao lado de **Ambiente da conexão**, escolha uma **Conta de documentos padrão** para o projeto — ou **Nenhum** para limpá-la.

Dentro do projeto, todo seletor de arquivos lista **Padrão do projeto** primeiro, no lugar da conta que o projeto tem definida no momento. Ele sai da lista quando você sai do projeto, quando o projeto não tem padrão definido, quando essa conta foi excluída ou quando você não tem acesso a ela.

Uma nova etapa de arquivo pré-seleciona Padrão do projeto quando o projeto tem um. As etapas existentes nunca são reescritas — cada uma mantém a conta com a qual foi salva até que você mesmo a altere, já que uma conta de documentos é uma escolha por etapa, enquanto uma etapa normalmente segue o ambiente de conexão do projeto.

Uma etapa deixada em Padrão do projeto passa a usar a conta que for o padrão do projeto quando ela for executada; portanto, alterar o padrão durante uma execução afeta apenas os nós que ainda não começaram — o mesmo que alterar o ambiente de conexão. Se uma etapa é executada em Padrão do projeto e o projeto não tem padrão definido, a execução falha e cita o projeto, em vez de recorrer a outra conta.


## Fixar uma etapa em um único ambiente

As etapas seguem o [ambiente de conexão](/pt-br/guides/projects/project-home/#dados-e-conexões) do projeto, portanto alternar o projeto entre QA e Produção move todas elas. Uma etapa cujo formulário tem uma configuração de **Ambiente** oferece duas opções nela:

- **Project environment** segue o ambiente de conexão do projeto. Mantenha essa opção, a menos que tenha um motivo para não fazê-lo.
- **Fixed environment** ignora o ambiente de conexão do projeto e sempre usa o ambiente que você escolher. Use-a somente para uma etapa que precise permanecer em um único ambiente, independentemente de para qual o projeto seja alternado, como ler dados de referência de Produção em um projeto definido como QA. O ícone de aviso lembra que a etapa não acompanhará uma alternância.

Uma etapa com ambiente fixo adiciona um aviso ao seu log sempre que é executada em um ambiente diferente do do projeto. Se o ambiente fixo dela não existir mais, por exemplo em uma etapa copiada de outro espaço de trabalho, a etapa falha e informa isso, em vez de ser executada em outro lugar.

As etapas de lançamento no ERP sempre usam o ambiente do projeto, portanto **Fixed environment** não está disponível nelas.

O ambiente padrão não pode ser excluído, e nenhum outro ambiente pode ser excluído enquanto um projeto o usar, uma etapa o tiver como ambiente fixo ou um agente o atender. A mensagem informa o que ainda o usa, citando o que você tem acesso e contando o restante.


## Histórico de versões

Todo objeto de um projeto — uma etapa, uma UDF, um fluxo de trabalho, uma dimensão, um layout salvo, um editor de documentos ou de dados e as próprias configurações do projeto — é coberto por backups do histórico de versões. Um backup não é feito a cada salvamento individual; em vez disso, quando um objeto passa 30 segundos sem um novo salvamento, é feito um backup do seu estado estabilizado. Uma sequência de edições — vários salvamentos em rápida sucessão — produz uma única versão com o resultado final, não uma versão por salvamento. O salvamento nunca fica lento esperando por um backup: a contagem regressiva e o próprio backup são executados em segundo plano. Se você precisa de uma versão imediatamente, use **Back up now** para capturar o estado atual na hora e aguardar a conclusão — disponível na interface, na API e como a ação `backup` das ferramentas MCP `*_versions`. O histórico de versões está disponível em todos os planos, inclusive o Free.

As versões anteriores permitem a recuperação em um ponto no tempo: restaure um objeto para uma versão anterior. A restauração é recusada dentro de um projeto bloqueado, como qualquer outra alteração nele.

Uma versão é restaurada no próprio local. Restaurar uma versão de um projeto, dimensão, função definida pelo usuário, etapa, fluxo de trabalho ou editor de dados substitui esse mesmo item, e indicar um item diferente como destino é recusado — por exemplo, "A project version is restored in place. Leave the target out, or set it to this project." Restaurar é uma alteração no item, então exige a mesma função necessária para editá-lo; em um projeto que [restringe linhas](/pt-br/administration/access/managing-security-groups-and-assignments/#quem-pode-alterar-um-projeto-que-restringe-linhas), restaurar o projeto ou uma dimensão que uma coluna restrita lê exige um Arquiteto do projeto. Para recuperar dados antigos de uma tabela como uma tabela separada, restaure um [instantâneo de tabela](/pt-br/guides/data/table-snapshots/) para uma nova tabela.

Além desse acompanhamento automático, os projetos e seus elementos também permitem o controle de versões. Criar uma versão é fácil e você também pode mesclar as alterações de uma versão em outra. Isso oferece uma forma simples de acompanhar instantâneos ou de criar uma versão para desenvolvimento e depois mesclar essas alterações na versão que não é de desenvolvimento quando quiser. Consulte [Colaborar: versões, comparação e compartilhamento](/pt-br/get-started/tutorials/collaborate-versions-and-sharing/) para ver o controle de versões, a comparação e a mesclagem na prática.

Os dados das tabelas têm seu próprio histórico — instantâneos feitos pelo Lakehouse a cada gravação — descrito em [Instantâneos de tabela](/pt-br/guides/data/table-snapshots/).

### Restaurar e reter pelo assistente de IA ou pelo MCP

Pelo assistente de IA ou pelo MCP, `dimension_versions` restaura, retém e libera uma versão de dimensão pelo seu `version_id`, e `restore_project` reverte todas as dimensões do projeto para o último backup, e toda listagem `*_versions` (etapas, UDFs, fluxos de trabalho, dimensões, projetos) mostra o `version_id` de cada versão e se ela está retida. Um `restore` por qualquer ferramenta `*_versions`, ou pela API REST, restaura o item no próprio local: omita o destino ou defina-o como o próprio item. `project_upsert` pode desbloquear um projeto bloqueado e respeita `if_match`, de modo que falha em vez de sobrescrever uma alteração feita desde a última vez que você leu o projeto.


## Gerenciar o acesso ao projeto

### Tipos de acesso

A segurança do projeto foi simplificada em três tipos de acesso:

* Todos os membros do espaço de trabalho
* Somente membros específicos
* Somente grupos de segurança específicos

Definir a segurança do projeto é fácil:

1. Abra o Analyze
2. Selecione “Projetos”
3. Clique no ícone de edição do projeto que você quer restringir
4. Escolha a restrição desejada em “Access Control”
5. Clique em “Update”

Somente um Arquiteto do projeto ou um administrador do locatário pode alterar quem tem acesso a um projeto — o tipo de acesso, os membros e grupos de segurança nele e seus compartilhamentos de dados. Qualquer outra pessoa vê esses painéis somente para leitura, com a observação “Only project Architects can change access.”


## Todos os membros do espaço de trabalho

O acesso “Todos os membros do espaço de trabalho” é a opção mais simples, pois dá acesso a todos os membros do espaço de trabalho e não exige nenhuma atribuição adicional de membros.


## Somente membros específicos

A configuração de acesso “Somente membros específicos” exige a atribuição de cada membro ao projeto. Para atribuir membros a um projeto:

1. Abra o Analyze
2. Selecione “Projetos” na barra de menus superior
3. Clique no ícone de membros
4. Conceda acesso aos membros marcando a caixa de seleção ao lado do nome deles na coluna “Access”
5. Clique em “Update”

Em clouds com um grande número de membros, essa abordagem muitas vezes exige mais esforço do que o desejado, e é aí que os grupos de segurança se tornam úteis.

<Aside>Para adicionar membros, você precisa ser membro do espaço de trabalho.</Aside>


## Somente grupos de segurança específicos

A opção “Somente grupos de segurança específicos” permite atribuir a grupos de segurança específicos a permissão de acessar a conta. Como as restrições de acesso dependem da associação a um ou mais grupos de segurança, a administração do acesso à conta para grupos maiores fica muito mais simples. Isso é particularmente útil quando combinado com a associação automática a grupos do logon único. Ao usar o logon único para definir as atribuições de grupo dos membros, esses grupos também podem ativar e desativar implicitamente o acesso aos projetos.

Para editar os grupos atribuídos:

1. Abra o Analyze
2. Selecione “Projetos” na barra de menus superior
3. Clique no ícone de grupos de segurança
4. Conceda acesso aos grupos de segurança marcando a caixa de seleção ao lado do nome deles na coluna “Access”
5. Clique em “Update”


## Compartilhar dados entre projetos

Um compartilhamento de dados permite que um projeto acesse as tabelas de outro projeto — por exemplo, para que as etapas [Import Project Table](/pt-br/reference/workflow-steps/import/import-project-table/) e [Export Project Table](/pt-br/reference/workflow-steps/export/export-project-table/) possam mover dados entre eles. Um compartilhamento é concedido pelo projeto cujos dados são compartilhados a um outro projeto:

1. Abra o projeto cujos dados você quer compartilhar e vá para a [página inicial do projeto](/pt-br/guides/projects/project-home/).
2. Abra **Access & sharing**. Em **Compartilhamentos de dados**, clique em **Novo compartilhamento de dados**.
3. Em **Selecionar projeto**, escolha o projeto que pode usar os dados deste projeto.
4. Em **Operações permitidas**, marque **Leitura**, **Gravação** ou ambas e clique em **Adicionar compartilhamento de dados**.

**Excluir compartilhamento de dados** remove um compartilhamento, depois que você confirma. Somente um Arquiteto do projeto ou um administrador do locatário pode adicionar ou excluir os compartilhamentos de dados de um projeto.

Um compartilhamento é concedido a um projeto, portanto vale apenas para os membros desse projeto e seus fluxos de trabalho:

- **Ler** por meio de um compartilhamento exige uma função no projeto ao qual ele foi concedido. Quem não tem função lá não obtém nada do compartilhamento.
- **Gravar** por meio de um compartilhamento — criar uma tabela, uma pasta ou uma dimensão no projeto que compartilha — exige um compartilhamento de **Gravação** e a função de Gerente ou Arquiteto no seu próprio projeto, a função que poderia fazer a mesma alteração lá. Qualquer outra pessoa recebe a mensagem "Writing to this project through a data share needs a write share from it to your project, and the Manager or Architect role in your project."

Os fluxos de trabalho são executados com a identidade do próprio projeto, então as etapas Import Project Table e Export Project Table funcionam por meio de um compartilhamento, seja quem for que iniciar a execução.


## Definir diferentes funções de visualização

Muitas vezes um projeto pode exigir várias transformações e tabelas para concluir etapas intermediárias, enquanto o resultado final pode acabar consistindo em apenas algumas tabelas. Os membros nem sempre precisam ver todos os elementos do projeto, às vezes apenas o produto final. O PlaidCloud permite definir diferentes funções de visualização para organizar e controlar facilmente a visibilidade de cada membro.

Existem três funções de visualização integradas: **Arquiteto, Gerente** e **Explorador**

A função **Arquiteto** é a mais simples, pois permite visibilidade e controle totais de projetos, fluxos de trabalho, tabelas, variáveis, editores de dados, hierarquias e funções definidas pelo usuário.

As funções **Gerente** e **Explorador** não têm privilégios de acesso específicos, mas podem ser definidas de forma personalizada. Em outras palavras, você pode escolher quais itens ficam visíveis para cada grupo.

<Aside>**Gerente** e **Explorador** não são grupos de segurança; eles apenas oferecem uma forma conveniente de separar funções e a visibilidade das informações.</Aside>

Você pode tornar todos **Arquitetos** se achar que é necessária a visibilidade de tudo dentro do projeto; caso contrário, você pode designar membros como membros de projeto **Gerente** e/ou **Explorador** e controlar a visibilidade dessa forma.

Para definir a função:

1. Abra o Analyze
2. Selecione “Projetos”
3. Clique no ícone de membros
4. Selecione o membro cuja função você quer alterar
5. Clique duas vezes na função atual dele na coluna “Role”
6. Selecione a função desejada
7. Clique em “Update”


## Gerenciar variáveis do projeto

Ao executar um projeto ou fluxo de trabalho, pode ser útil definir variáveis para tarefas recorrentes a fim de reduzir a desordem e economizar tempo. Essas variáveis funcionam como uma variável algébrica comum, permitindo definir o que a variável representa e qual operação deve segui-la. O PlaidCloud permite definir essas variáveis no nível do projeto, o que afetará todos os fluxos de trabalho desse projeto, ou no nível do fluxo de trabalho, o que afetará somente esse fluxo de trabalho específico.

Para definir uma variável no nível do projeto:

1. Abra o Analyze
2. Selecione “Projetos”
3. Clique no ícone Manage Project Variables

Na tabela de variáveis, você pode ver as variáveis e ver/editar os valores atuais. Você também pode adicionar novas variáveis ou excluir as existentes clicando no botão “New Project Variable”.


## Copiar um projeto

**Copiar projeto** copia um projeto — inteiro ou apenas as partes que você escolher — para um projeto totalmente novo ou para um projeto que já existe.

Para copiar um projeto:

1. Abra o Analyze
2. Selecione "Projetos"
3. Selecione o projeto que você quer copiar
4. Clique no botão **Ações** e escolha **Copiar projeto**
5. Escolha o destino, selecione o que levar e quais dados copiar e clique em **Copiar projeto**
6. Confira o resumo de **Revisar antes de copiar** e clique em **Iniciar cópia**

### Escolher o que copiar

A árvore de seleção lista o que o projeto contém, por tipo — fluxos de trabalho, etapas, tabelas, dimensões, editores de dados, funções definidas pelo usuário. Deixe tudo marcado para copiar o projeto inteiro ou marque somente as partes que você quer.

Você não precisa descobrir do que essas partes dependem. Tudo o que você marca traz suas dependências: as tabelas que uma etapa lê e grava, as dimensões que ela carrega ou nas quais aloca, as funções definidas pelo usuário que ela chama e qualquer subfluxo de trabalho ou macro que ela invoca. Os sensores de um fluxo de trabalho acompanham o fluxo de trabalho.

**Os sensores copiados chegam desativados.** Nada é disparado na cópia até que você ative cada sensor no projeto de destino. Uma importação que sobrescreve itens duplicados não adiciona um segundo sensor quando o fluxo de trabalho de destino já o tem.

### Copiar para um novo projeto

Dê ao novo projeto um nome e um ID. O ID passa a ser o nome do esquema dele e não pode ser alterado depois.

**Os agendamentos chegam pausados.** Quando você copia um projeto inteiro para um novo, os eventos agendados de cada fluxo de trabalho chegam pausados, para que a cópia não comece a executá-los por conta própria. Quando a cópia termina, uma mensagem lista os eventos que estavam ativos no original. Para executar um deles na cópia, selecione-o em **Ferramentas** > **Agendador de eventos** e clique em **Ativar selecionados** — consulte [Pausar um evento](/pt-br/administration/scheduled-events/event-scheduler/#pausar-um-evento).

### Copiar para um projeto existente

Escolha o destino na lista de projetos. A cópia é adicionada a esse projeto, em vez de substituí-lo.

**Você precisa poder alterar o destino.** Uma cópia para um projeto no qual você não tem nenhuma função é recusada, assim como uma cópia para um projeto que foi bloqueado para impedir alterações — verificado antes de qualquer coisa ser lida ou gravada, de modo que uma cópia recusada deixa o destino intacto. Além disso, um projeto não pode ser copiado para ele mesmo.

**Copiar um projeto que restringe linhas exige um Arquiteto do projeto.** A cópia é um novo projeto sem restrição de [acesso a linhas](/pt-br/administration/access/managing-security-groups-and-assignments/#gerenciar-o-acesso-a-linhas), e a cópia informa isso: “This copy is not row-restricted.” Configure o Acesso a linhas na cópia antes de compartilhá-la. Copiar para um projeto existente que restringe linhas também exige um dos Arquitetos dele ou um administrador do locatário.

**O destino mantém suas próprias configurações.** O nome, o ID, o ambiente de conexão de dados, os padrões de armazenamento, a conta de documentos, o tipo de acesso, as listas de acesso e as concessões de acesso a linhas permanecem como estão. Somente o conteúdo que você selecionou é trazido.

Uma etapa definida como **Padrão do projeto** leva essa configuração, não uma conta — depois de copiada, ela passa a usar o padrão que o projeto de destino tiver, não o que tinha na origem.

Quando um item recebido é o mesmo item que já existe no destino, você escolhe o que acontece:

- **Substituir itens duplicados pelos dados recebidos** — a versão recebida substitui a que está no destino.
- **Criar nova cópia dos itens duplicados** — o destino mantém o que tem, e o item recebido é adicionado ao lado dele com ` copy` acrescentado ao nome e um contador se esse nome também já existir.

As variáveis de projeto e de fluxo de trabalho são a exceção a *Criar nova cópia*: uma variável é identificada pelo nome, então não há como adicionar uma segunda cópia dela sem renomeá-la para algo a que nada se refira. Quando o destino já define uma variável que a cópia também traz, o valor do próprio destino é mantido e a cópia informa quais variáveis deixou intactas. *Substituir* trata as variáveis como todo o resto e as substitui.

Essa correspondência é feita por identidade, não por nome — um item que veio originalmente do mesmo projeto é reconhecido como o mesmo item, enquanto dois itens que apenas têm o mesmo nome são tratados como itens diferentes e ambos estarão presentes depois.

### Escolher quantos dados copiar

Em **Data to copy**, duas configurações decidem quais dados acompanham a sua seleção.

**Dados da tabela** define quantas linhas de cada tabela são copiadas:

| Opção | O que é copiado |
| --- | --- |
| **Nenhum dado de tabela** | Tabelas, etapas e o restante da seleção, sem linhas. Este é o padrão. |
| **Completo** | As linhas de todas as tabelas, no mesmo lakehouse e entre lakehouses. |
| **Amostra** | Até o número de **linhas por tabela** que você informar, somente para um novo projeto. O número pode ser de 1 a 1.000.000. |

Uma tabela amostrada contém até essa quantidade de linhas, ou todas as suas linhas quando tem menos. Uma cópia **Completo** ou **Amostra** copia várias tabelas ao mesmo tempo, então um projeto com muitas tabelas termina mais rápido.

**Copy dimension members** copia os membros de toda dimensão da seleção, qualquer que seja a opção de **Dados da tabela** escolhida. Ele vem ativado por padrão, então uma cópia sem dados de tabela ainda chega com as dimensões preenchidas e é rápida de fazer. Desmarque-o para copiar as dimensões sem seus membros.

Pela API REST (`POST /rest/v1/analyze/project/copy`) ou pela ferramenta MCP `project_copy`, defina `data_mode` como `structure`, `full` ou `sample` e `dimension_members` como `true` ou `false`. Quando você omite `dimension_members`, os membros são copiados somente quando as linhas das tabelas são. `project_copy` também retorna os avisos da cópia, como autorizações de gravação no ERP que não foram copiadas.

### Revisar a cópia

Antes de qualquer coisa ser copiada, **Revisar antes de copiar** resume a cópia: o projeto de origem, o destino, a opção de **Dados da tabela**, se os **Membros da dimensão** estão incluídos, o número de tabelas e visões, o tamanho, uma estimativa de tempo, o lakehouse de origem e de destino e quaisquer avisos em **Observação**. Clique em **Iniciar cópia** para começar ou em **Cancelar** para voltar e alterar a seleção.

### Quem pode ver a cópia

Uma cópia feita com dados — linhas de tabelas, membros de dimensões ou ambos — é privada para a pessoa que a fez. Compartilhe-a a partir do novo projeto quando estiver pronto. Uma cópia de um projeto com segurança em nível de linha permanece privada pelo mesmo motivo.

Copiar dados para um projeto existente exige acesso de gravação a esse projeto.

### Autorizações de gravação no ERP na cópia

Uma nova cópia que é privada para você mantém as [autorizações de gravação no ERP](/pt-br/guides/workflows/run-a-workflow/#autorizar-o-projeto-a-lançar) do projeto de origem, para que você possa testar seus fluxos de trabalho de lançamento sem autorizar a cópia novamente. Isso vale para qualquer cópia para um novo projeto feita com dados de tabela (**Completo** ou **Amostra**), membros de dimensões ou ambos. As autorizações são copiadas quando:

- Você é Arquiteto do projeto de origem ou administrador do espaço de trabalho.
- Você mesmo faz a cópia, e não por meio de um agente ou de uma conta de serviço.

Cada autorização é copiada somente se você mesmo pudesse concedê-la hoje: a conexão e o ambiente dela ainda existem e você tem acesso de gravação à conexão. As autorizações copiadas são registradas como suas.

**A cópia chega em Simulate.** Se o **Modo de lançamento no ERP** do projeto de origem for Live, o da cópia é definido como Simulate, de modo que seus fluxos de trabalho montam e verificam o que lançariam sem contatar o ERP. Uma origem definida como Simulate ou Off mantém essa configuração. Quando estiver pronto para lançar de verdade a partir da cópia, defina o **Modo de lançamento no ERP** em **Lançamento no ERP** na página inicial da cópia como Live — consulte [Escolher um modo de lançamento](/pt-br/guides/workflows/run-a-workflow/#escolher-um-modo-de-lançamento). Os agendamentos e sensores ainda chegam pausados e desativados, como descrito acima, então nada é executado na cópia até que você o ative.

Uma cópia para um projeto existente, ou uma sem dados de tabela e sem membros de dimensões, começa sem as autorizações da origem. Autorize-a em **Lançamento no ERP** > **Autorizações de gravação no ERP** na página inicial dela antes de lançar.

**Resultados da cópia** informa o que aconteceu, por exemplo "2 ERP write authorizations copied; ERP posting is in Simulate", junto com quantas não foram copiadas.

### Resultados da cópia

Quando a cópia termina, uma janela **Resultados da cópia** resume as tabelas e os membros de dimensões copiados e lista cada tabela e dimensão por nome com seu resultado — **Copiado**, **Copiado com alterações**, **Amostrado**, **Ignorado** ou **Falhou** — e o motivo de qualquer item ignorado ou com falha. Clique em **Retry failed items** para copiar novamente as tabelas e dimensões com falha; o conteúdo atual delas na cópia é substituído. Você é notificado, por mensagem e por e-mail, quando uma cópia termina ou falha, e pode reabrir os resultados pela mensagem ou, mais tarde, selecionando a cópia na guia **Projetos** e escolhendo **Ver resultado da importação ou cópia** no menu **Ações**.

Os resultados permanecem na cópia até que alguém os dispense. Depois que a cópia terminar, clique em **Dispensar resultado** para removê-los para todos que podem abrir o projeto. Nada no projeto muda, mas os itens com falha não podem mais ser repetidos pela janela. Dispensar exige acesso de edição ao projeto, e o projeto não pode estar bloqueado.

### Atualizar referências

As etapas de fluxo de trabalho de um projeto se referem a tabelas e outros objetos dentro desse projeto. **Atualizar referências** reescreve essas referências para que apontem para a cópia em vez do original — o que quase sempre é o que você quer e é por isso que fica ativado por padrão. Desativá-lo deixa as etapas copiadas apontando de volta para o projeto de onde vieram.

<Aside>A cópia é executada em segundo plano. Uma caixa de diálogo de progresso mostra a cópia avançando pelas fases; você pode clicar em **Executar em segundo plano** para dispensá-la e continuar trabalhando — a lista de projetos é atualizada automaticamente e você é notificado quando a cópia termina.</Aside>

## Ver o relatório do projeto

Quando um projeto ou fluxo de trabalho é dinâmico, manter uma documentação detalhada se torna um desafio. Para ajudar a resolver esse problema, o PlaidCloud oferece a capacidade de gerar um relatório no nível do projeto que documenta em detalhes fluxos de trabalho, etapas de fluxo de trabalho, transformações definidas pelo usuário, variáveis e tabelas. Esse relatório é gerado sob demanda e reflete o estado atual do projeto.

Para baixar o relatório:

1. Abra o Analyze
2. Selecione “Projetos”
3. Clique no ícone de relatório
