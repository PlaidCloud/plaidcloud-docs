A **metric definition** is a business number whose calculation has been agreed and written down: *Net Revenue*, *Headcount (FTE)*, *Units Shipped*. It says which table the number comes from, how the rows are added up, which rows count, and which columns it can be broken down by.

Without one, an AI assistant asked *"what was net revenue in EMEA last quarter?"* decides for itself which table, column and filters to use, and two people asking the same question can get two different numbers. A metric definition takes that decision away from the assistant. A project Architect writes the definition once, a second Architect checks and approves it, and from then on every answer that uses it is calculated the same way.

A metric definition is a recipe, not a stored result. It is recalculated every time it is asked for, and it respects the row access of the person asking: someone who can see only EMEA gets EMEA figures.

<Aside>
Metric definitions are managed through an AI assistant connected over [MCP](../getting-started/) or through the REST API. There is no screen for them in PlaidCloud yet.
</Aside>

## What a Definition Holds

| Part | What it says | Example |
|---|---|---|
| **Name** | What people call the number. Up to 200 characters. | *Net Revenue* |
| **Synonyms** | Other words people use for it, so the assistant recognizes the question. Up to 25. | *revenue*, *sales* |
| **Description** (`memo` in the API) | What the number means and when to use it, for the assistant and for people. Up to 1,000 characters. | *Revenue after returns and discounts. Use for all revenue questions.* |
| **Source table** | The table the rows come from. | `sales_fact` |
| **Joins** | Lookup tables joined to the source, each on one or more column pairs written as `[source column, lookup column]`. Every join must be many-to-one: at most one lookup row per join key. | `region_lookup` on `["region_code", "code"]` |
| **Measure** | How the rows are added up: `sum`, `count`, `count_distinct`, `min`, `max` or `avg` of a column. | `sum` of `net_amount` |
| **Filters** | Which rows count, always. Each filter is a column, an operator (`eq`, `ne`, `in`, `not_in`, `lt`, `le`, `gt`, `ge`, `between`, `is_null`, `not_null`) and its values. | `scenario` `eq` *Actual* |
| **Grain** | The columns the number may be grouped and filtered by when someone asks. | `region`, `product_line`, `fiscal_year` |

A column from a joined table is written as `<table>.<column>`. Every table and column in a definition must exist in the project; a definition that names one that doesn't is refused when it is saved and again when it is approved.

## Who Can Do What

- **Project Architects** write, edit, approve and retire definitions. Only a real project Architect counts: in a public project every member reads as an Architect, and that is not enough.
- **Anyone who can read the project** can see and run the approved definitions. Drafts are visible to Architects only.
- **An approval needs two people.** The Architect who approves a version cannot be the one who wrote that version.
- **A locked project refuses every change.** Defining, editing, approving and retiring all wait until the project is unlocked.

## Define a Metric

If you are a project Architect, ask your connected AI assistant in plain language:

> *"In the **Sales** project, define a metric named **Net Revenue**, with synonyms revenue and sales: the sum of `net_amount` in `sales_fact`, where `scenario` is Actual, that can be broken down by `region`, `product_line` and `fiscal_year`."*

The assistant saves it as a **draft**, and tells you if a table or column it names doesn't exist. Through the REST API, the same definition is:

```json
POST /rest/v1/analyze/metric/definition
{
  "project_id": "<project>",
  "name": "Net Revenue",
  "synonyms": ["revenue", "sales"],
  "memo": "Revenue after returns and discounts. Use for all revenue questions.",
  "definition": {
    "source": "sales_fact",
    "joins": [{"table_id": "region_lookup", "on": [["region_code", "code"]]}],
    "measure": {"agg": "sum", "column": "net_amount"},
    "filters": [{"column": "scenario", "op": "eq", "values": ["Actual"]}],
    "grain": ["region_lookup.region", "product_line", "fiscal_year"]
  }
}
```

A draft can be edited as often as you like. Every edit is a new version of the definition, written by whoever made it.

## Approve a Metric

A draft becomes usable when a **second** Architect approves it.

<Steps>

1. **Read the definition as it is stored now.** Ask the assistant to show you the metric, or fetch it with `GET /rest/v1/analyze/metric/definition`. What comes back includes a `content_digest`: a fingerprint of the name, synonyms, description and definition you are looking at.

2. **Check it.** Is the table right, the measure right, the filters complete, the grain what people will ask for?

3. **Approve that exact content.** Ask the assistant to approve the metric, or call `POST /rest/v1/analyze/metric/approve`, passing the `content_digest` you read as `digest`. If anyone has changed the definition since you read it, the approval is refused and you are asked to read it again, so nobody can approve a version they haven't seen.

</Steps>

Approval runs two checks of its own before it goes through:

- **Every table and column still exists** in the project. The schema may have moved since the draft was saved.
- **Every join is many-to-one** in the data as it is at that moment: on the joined table, there is at most one row per join key. A lookup table with two rows for the same key would double the source rows it matches, so the approval is refused and names the table.

<Aside type="caution" title="The join check runs once, at approval">
The many-to-one check looks at the lookup table's data on the day the metric is approved. If that table later gains a second row for a join key, the approved metric multiplies the source rows that key matches, and nothing warns you. An approved version cannot be approved again, so to run the check again an Architect saves the metric as a new version (re-saving its description is enough) and a different Architect approves that version. Better, keep the lookup's key unique in the workflow that writes it.
</Aside>

Each approval is recorded with who approved it, when, and which version. Editing an approved metric creates a new draft version; the approved version keeps answering questions until the new one is approved in turn.

## Ask About a Metric

Anyone who can read the project can now ask:

> *"What was net revenue by region in FY26?"*

The assistant recognizes the metric by its name or one of its synonyms, takes the breakdown and the filters from your question, and runs the approved definition. A question can only group or filter by a column in the metric's grain; one that asks for anything else is refused rather than answered with a guess.

**Row access is applied to every table the metric reads**, the source and each joined lookup alike, and the answer says whether your access limited the rows. Where a lookup row is hidden from you but the source row it labels is not, the source row still counts, with no label (a null) from that lookup, so a total stays whole. A question that filters or groups on a lookup column treats those rows as having no value for it.

Architects asking about a metric get its **working version**, draft included, so they can preview a change before it is approved, and they read every row, as they do everywhere else. The answer says which version and state it came from.

## Retire a Metric

Retiring a metric takes it out of service for good: people who read the project no longer see it, Architects see it marked retired, and it can no longer be edited or run. An Architect retires one by asking the assistant, or with `POST /rest/v1/analyze/metric/retire`. To replace a retired metric, define a new one.

## Through MCP and the REST API

| Action | MCP tool | REST |
|---|---|---|
| List a project's metrics, each with its full definition | `metric_find` | `GET /rest/v1/analyze/metric/definitions?project_id=` |
| Read one metric | | `GET /rest/v1/analyze/metric/definition?project_id=&metric_id=` |
| Define or edit a draft | `metric_upsert` | `POST` / `PUT /rest/v1/analyze/metric/definition` |
| Approve | `metric_review` with `action: approve` and the `content_digest` as `digest` | `POST /rest/v1/analyze/metric/approve` with `digest` |
| Retire | `metric_review` with `action: retire` | `POST /rest/v1/analyze/metric/retire` |
| Run | `metric_run` with `group_by` and `filters` | `POST /rest/v1/analyze/metric/run` |
| Earlier versions (Architects only) | | `GET /rest/v1/analyze/metric/flashback-versions` |

`metric_upsert` takes a `spec` of `{name, memo, synonyms, definition}` and accepts `dry_run` to check a definition without saving it.
