どんなAIでも、数値について自信たっぷりの文章を書くことはできます。難しいのは、その回答に基づいて行動してよいかどうかを左右する部分、つまり**いつ信頼してよいか**を知ることです。PlaidCloudはまさにそのために作られています。

接続したAIアシスタントにデータの説明を求めると、PlaidCloudは数値を返すだけでは終わりません。その数値をどの程度信頼できるかを評価し、根拠が弱い部分を平易な言葉で伝え、自身の計算を突き合わせ、何も作り話をしません。これが、*それらしく聞こえる*アシスタントと、CFOの前に出せるアシスタントとの違いです。

<Aside>
これは、AIをPlaidCloudに接続する**あらゆる**方法に当てはまります。チーム全体で使う[Microsoft 365 Copilot](/ja/integrations/microsoft-365-copilot/)でも、[MCP](../getting-started/)経由のClaude CodeやCursorなどのコーディングエージェントでも同じです。誠実さはツールではなく、回答に付いてきます。
</Aside>

## すべての回答に信頼度のシグナルが付く

PlaidCloudは自身の回答を**高**、**中**、**低**の信頼度で評価し、*その理由*も伝えます。完全に帰属できたクリーンな結果は「高」で返されます。比較する2つの期間の完全性が同じでない場合や、変化の一部を単一の原因に特定できない場合は、PlaidCloudがそのことを伝え、不確かな数値を確かなものとして提示する代わりに自身の信頼度を下げます。

アシスタントが確信しているかどうかを気にする必要はありません。回答の冒頭で伝えられます。

**評価は、何を対象にしているかを明示します。** 回答は1行の要約で始まります。そこでは、考えられる原因の名前を挙げたり、変動の大半を生んだメンバーを示したり、前年との比較で変化の大きさを示したりできます。そして最後に信頼度の評価で締めくくります。この評価が対象とするのは1点だけです。つまり、変化をそれに寄与した要素へどのように分解したか、そしてそれを生み出したステップまでどのようにさかのぼったか、という点です。上に挙げた原因そのものについての判定ではありません。現在は行にその旨が明記されており、*「分解についての信頼度であり、変動の理由についての信頼度ではありません：高」*のように表示されます。要約が原因を挙げていない場合は後半が省かれるため、述べていない主張を否定することはありません。この点が重要なのは、要約が単独で転送されたり、周囲のページを持たないアシスタントに読まれたりする可能性が最も高い部分だからです。

**評価に条件を付ける内容は、独立した1文として続き**、「注意事項：」という見出しが付きます。以前は、評価とその条件がダッシュでつながれていました。ダッシュは「なぜなら」と読めるため、高い評価の後にダッシュと制限が続くと、評価がすぐ隣の制限そのものに依拠しているように解釈されました。現在は2つの文に分かれており、両者の間に関係があるとは主張しません。条件の内容自体は変わらず、回答の下部にこれまでどおり詳しく記載されます。

**評価を下げた理由は、評点への脚注ではなく、明示された制限です。** 変化の一部が、単一の要因ではなく複数の影響が同時に動いたことに由来する場合、その割合が評価を「高」未満にとどめる要因になります。これは**正直な制限事項**に、その意味と何に関わるかとともに、回答が抱える他のすべての制限と並べて記載されます。評価自体は短いラベルのままです。複数の列を対象とする回答では、単一の数値ではそのすべてについて述べたことにならないため、評価の行にそれらの列にわたって測定した範囲が示されます。

**列ごとに結果が異なる場合、理由はそれを最も必要とする列のものになります。** 以前は、同じ評価を受けた複数の値の列を対象とする回答で、最初に現れた列の理由とその列自身の残差割合が、回答全体のものとして採用されていました。そのため、最も問題のある列の変動の大半が、個々の要因では説明できない部分にあっても、小さな割合を添えて「ほぼクリーン」として公開されることがありました。いずれかの列の変動が分離できない影響に支配されている場合は、現在はそれが示される理由となり、他の列で測定した割合は併記されません。

**変化が反対方向の動きで相殺されたと述べながら、同じ分解をクリーンと評価することはありません。** あるメンバー自身の変化が正味の変化全体より大きくなる場合、両方向の動きが部分的に打ち消し合っています。そのメンバーを挙げる行は、メンバーの変化が正味をわずかに超えた時点でそう述べていましたが、隣の評価がその相殺を重要なものとして数えるのはそれよりかなり先でした。そのため、最大のメンバーが正味をわずかに上回っただけの回答が、動きが相殺されたと述べながら、同じページで同じ分解を*クリーン*と評価することがあり、どちらを信じるべきか分かりませんでした。現在この行は、相殺が評価を下げるほど大きい場合にのみ、動きが互いに相殺されていると述べます。それ未満の場合は、代わりにそのメンバーの割合を示します。たとえば*「line=PERSONAL_AUTO = デルタの101.6% — これはプールにおける持ち分の変動ではなく、そのメンバー自身の変化です」*のように表示し、100%を超える場合は小数点以下1桁まで示すことで、100%をわずかに超える分が丸めによって歪まないようにしています。相殺が重要な回答の表示は従来どおりで、どの要因が動いたかを示す別の行も変わりません。

**回答が制限を抱えている場合、要約は必ず信頼度を述べます。** 以前は、回答の背後のどのステップも固有の警告を出さなかった場合、評価が一切省かれていました。これは、回答全体としては前年との比較で変化の大きさを示せないなどの制限を抱えている場合でも同じでした。この行は単独で転送されることが最も多いため、その沈黙は「制限は下に記載されている」ではなく「伝えることはない」と受け取られていました。現在の要約は評価を述べ、制限も明示します。*「分解についての信頼度：高。注意事項：この変動は前年の変化との比較では測定されていません。」*回答に示すべきことがなければ、従来どおり何も付けずに終わります。

**示された深さは、そのうちどれだけが数値を伴っていたかを示します。** 要約の最後には、回答が何ステップさかのぼったかが記されます。この件数は、回答がどこまで到達したかを示す行内の唯一の情報であるため、読み手はそれを裏付けとして受け取ります。しかし、トレースが到達したものの数値が返ってこなかったステップは、裏付けにはなりません。トレースしたステップのいずれかが空で返った場合、現在の行はそのうち何件が数値を返したかを示します。*「上流を2ステージたどりました。数値が返ったのは2件中1件のみで、残りには数値が一切ありません。」*変化が測定されたものの単一の生成元ステップに特定できなかったステップは、測定された変化が証拠となるため、引き続き数に含まれます。特定できなかったことは、**正直な制限事項**に別途記載されます。すべてのステップが数値を返した要約は、従来どおりの表示です。

## 注意すべきときを教えてくれる

PlaidCloudは、前提を埋もれさせる代わりに、回答に添える平易な注意書きとして示します。

| 回答が示す内容 | 意味 |
| --- | --- |
| 「これはプール全体を表しています」 | この数値は合計です。メンバー（地域、製品、コストセンターなど）の間でどのように変動するかを見るには、特定のメンバーについて質問してください。この注意書きは、回答にメンバー別の内訳が表示されない場合にのみ表示されます。内訳が表示されている場合、この注意書きは当てはまらないため出力されません。注意書きがチェーン内の前のステップを指す場合（「ステージ2（…）」で始まります）、質問を絞り込んでもそのステップには届かないため、そのステップ自体のテーブルをトレースしてください。 |
| 「期間の完全性が同じではありません」 | 一方の期間が月の途中までだったり、短い期間だったりする可能性があり、変動の一部が実際の変化ではなくデータの欠落である可能性があります。引用される行数は結果全体のものです。複数の配賦ブランチを再結合するテーブルでは、すべてのブランチを合算した行数になります。 |
| 「各要素が完全には整合していません」 | 詳細な内訳の合計が見出しの数値と完全には一致しません。この分割は正確なものではなく、目安として扱ってください。 |
| 「正確な原因は部分的です」 | 合計は正しいものの、変化の正確な要因は手元のデータからは完全には特定できません。 |
| 「一部のターゲットを測定できませんでした」 | ホワットイフ分析で、あるステップの計算が失敗したため、そのステップが書き込む結果には推測値ではなく数値が一切ありません。合計は測定できたものを対象とし、そのステップの下流にあるものは、そこから推定するのではなく除外されます。 |
| 「現在のシェアに基づく推定」 | ホワットイフの推定は、影響を受ける結果の間で、変化を各結果の現在のプールに占める割合に応じて分割します。そのため数値は合計と一致しますが、これはモデルが現在どのように構成されているかを反映したものであり、シェアが変動しているかもしれない将来の正確な予測ではありません。 |

これらは細かい注意書きではありません。自信ありげな回答が、データが実際に裏付ける内容を知らないうちに誇張してしまうのを防ぐための安全策です。

**結果の一部だけを説明する注意書きは、どの部分かを明示します。** 注意書きは結果全体ではなく、結果の一部によって発生することがあり、その場合、数値はその部分にのみ属します。そのため、注意書きはまずその部分を名指しします。複数の配賦ブランチを結合した結果では*「ブランチ4（管理コスト）：…」*と表示され、複数の値の列を同時に配賦する結果では*「列margin：…」*のように列が示されます。接頭辞のない注意書きは、質問した結果全体についてのものと読み、接頭辞のある注意書きは、その部分についてのものと読んでください。

**複数の部分に当てはまる場合は、そのすべてを挙げます。** *「列revenue、margin：…」*のようになります。したがって、その一覧にない列は、その注意書きが当てはまらない列です。これが一覧を載せる目的です。3列の結果のうち2列が同じ注意書きを共有している場合、一方だけを挙げるともう一方は対象外のように読めてしまいます。*すべての*部分で発生した注意書きには接頭辞が一切付きません。区別すべきものがないからです。

1つのケースだけは、意図的に異なる表示になります。各部分が**それぞれ独自の数値**でその注意書きを発生させた場合、表示される注意書きは1つの部分のものであり、複数の名前を1つの部分の数値の前に並べると数値の帰属を誤らせてしまいます。そのためその部分を名指しし、他の部分をその後ろに列挙します。*「列revenue（marginでも発生）：…」*のようになります。この文の数値はrevenueのものです。marginも同じ種類の注意書きを、自身の数値で発生させています。

## 何を比較したかを示し、それを時間とは呼ばない

数値がなぜ動いたかを尋ねるには、その間で比較する2つのものを指定する必要があります。通常は2つの期間で、先月と今月、2025年と2026年などです。回答もそれを前提に書かれており、期間の名前を挙げ、変化を1年前の同じ期間と比較して大きさを示し、一方の期間がもう一方より完全でないように見える場合は警告します。

しかし、比較する2つは期間でなくてもかまいません。シナリオ、バージョン、ケース、または予算と実績に比較を向けると、両者の違いについて、どちらが動いたか、何がそれを動かしたか、どのメンバーがそれを担っているかを、まったく問題のない形で説明する回答が得られます。これは機能しますし、活用する価値があります。

問題だったのは、その周辺の言い回しでした。バージョン7とバージョン8を比較したとき、回答は1つさかのぼってバージョン6との差で変化の大きさを示す「前年比」の判定を報告しました。*「昨年の変動の275%の大きさ。6 → 7は-$400,000変動」*というもので、含まれる数値はすべて正しいのに、文の主題が間違っていました。2つのバージョンを期間であるかのように扱い、行数の少ない方をまだ読み込み中かもしれないと述べていたのです。

現在は、比較に使う列が期間かどうかを、列の型、名前、指定した値の形から判断します。期間でない場合は次のようになります。

- 冒頭の行は**比較した期間**ではなく、**比較した値**と述べ、列とその2つの値を挙げます。
- 前年との判定は示されません。さかのぼる前年が存在しないためで、説明なしに比較を未測定のままにするのではなく、**正直な制限事項**でそのことが述べられます。撤回される数値はありません。
- 両側の行数の違いは、期間がまだ読み込み中かもしれないという話ではなく、各側が対象とする範囲の違いとして説明されます。2つのシナリオの間では、小さい側が意図したものであることがよくあります。どちらが少ないかは、**比較した値**と行数の両方が表示される順に従って、1つ目の側または2つ目の側として示されます。以前は「薄い側」と呼んでいましたが、これは行数が少ないことで定義されるため、短い側は短い、としか言っていない文になっていました。冒頭の行でも、以前は「後の側」と呼んでいた箇所を同じ方法で示します。カレンダーのない比較に、カレンダーの言葉を使っていたためです。

判定は意図的に慎重です。型がそう示している場合、**または**名前がそう示している場合、**または**指定した値が日付、月、四半期、年のように見える場合に、列は期間とみなされます。どれか1つで十分なので、整数の`fiscal_year`も、テキストの`2026-03`も、引き続き期間として読み取られ、日付、期間、月、四半期、年の列にまたがる比較は変わりません。

## どの母集団を測定したかを示す

1つのテーブルに対する2つの回答は、似て見えても意味がまったく異なることがあります。一方はすべての行を対象とし、もう一方は単一の事業ライン、エンティティ、プログラムを対象としています。続けて読むと、絞り込んだ数値は広い方の数値の一部だと簡単に思い込まれますが、そうとは限りません。除外されたメンバーは逆方向に動くことがあり、場合によっては絞り込んだ変化がテーブル全体の変化より大きくなるほどです。

各回答は、冒頭の行でそのどちらであるかを述べます。絞り込んでいない回答は、その数値が各期間におけるテーブル自身の合計であり、すべてのメンバーを含むと述べます。絞り込んだ回答は、その数値が各期間におけるそのメンバー自身の合計であり、テーブルの残りは除外していると述べ、さらに数値が正の場合は、その割合がより大きなものの持ち分を測るものではなく、その2つの合計を比較したものだと述べます。絞り込んだ回答の数値が両端で負の場合は、この最後の注記は省かれます。回答はすでに残高がゼロよりさらに下回ったことを伝えており、そこでその割合を通常の比較と呼ぶと要点がぼやけてしまうためです。

どちらの行も、除外されたメンバーがどのように動いたかについては何も述べません。回答はそれらを測定していないため、特徴づけることもしません。

絞り込んでいないという行は、回答がすでに自身の作業内の欠落を報告している場合は省かれます。複数の配賦を再結合するテーブルに関する質問は、ブランチごとに回答されます。そのうちの1つのブランチが帰属できなかった場合、回答はその旨を下で述べます。その上の冒頭の行で「すべてのメンバーを含む」と述べると、何も除外されていないという主張として読まれてしまいます。再結合されたテーブル自身の変化が読み取れなかった場合も同様で、その場合、行が説明すべきテーブル全体の数値は存在しません。

## 絞り込みを適用できなかったときに示す

絞り込みは列を指定しますが、回答が報告するテーブルにその列がない場合があります。ない場合、フィルターする対象がないため、クエリは絞り込まれずに実行され、返ってくるすべての数値はテーブル全体を対象とします。

以前は、ページ上にそのことを示すものが何もありませんでした。回答は、絞り込みを挙げるすべての場所で絞り込みを挙げ続けていました。冒頭の文、上記の母集団の行、テーブル全体ブロックの見出し、メンバー一覧の見出し、要約の行、そして最後のステップごとの説明の6か所です。6か所すべてが、数値の対象ではない母集団を挙げていました。さらに、絞り込んだ数値をそのテーブル全体と比較するためのブロックは、比較を謳う見出しの下に同じ数値を2回表示していました。そのページを見ても、読み手は、尋ねたメンバーがたまたま事業全体である場合のテーブルと区別できませんでした。

現在、回答は数値より前に、まずそのことを述べます。

> **結論：** entity=DEを分離できませんでした（cost_line_adminにはentity列がありません）。そのため、これはテーブル全体の数値です。合計は26.2%減少しました（$4,200,000.00から$3,100,000.00へ）。

訂正が先に来て、数値はその従属になります。冒頭の行は単独で転送される可能性が最も高く、数値の後ろに置かれた訂正は読み飛ばされるためです。渡した設定ではなく欠けている列を名指しするため、間違った列を指定したのか、間違ったテーブルを指定したのかをすぐに判断できます。また、絞り込みを適用「しなかった」ではなく、適用「できなかった」と述べます。「しなかった」と書くとフィルターが実行されたが違いがなかったように読め、絞り込みの場合、尋ねたメンバーが事業全体であることを意味してしまうからです。

その後、絞り込みはページ上のほかのどこにも挙げられません。母集団の行も、テーブル全体ブロックも、メンバー一覧のスコープも、要約への絞り込みマーカーもありません。ステップごとの説明では、絞り込まれずに実行されたステップをフィルターしたステップとしてではなく、絞り込まれていないステップとして示します。

絞り込みが通常どおり適用された回答は変わらず、どちらの場合も数値は動きません。

テーブルが複数の配賦を再結合している場合、ブランチは別々のテーブルであり、違いが生じることがあります。1つがその列を持ち、別の1つが持たない場合です。その場合、絞り込めたブランチを残りの代表とするのではなく、回答は絞り込みを母集団としてどこにも挙げません。ステップごとの説明は、絞り込まれたブランチと絞り込まれなかったブランチを引き続き区別します。何が起きたかは回答自身の言葉で述べられます。以下の[再結合されたテーブルで絞り込めたものと絞り込めなかったものを示す](#再結合されたテーブルで絞り込めたものと絞り込めなかったものを示す)を参照してください。

## 絞り込みのどの部分が適用されたかを示す

絞り込みは複数の列を指定でき、テーブルにはその一部の列があって他にはないことがあります。`lob`列はあるが`region`列がないテーブルで、`lob=COMMERCIAL`と`region=WEST`について尋ねると、数値は事業ラインで絞り込まれ、すべての地域を対象として返されます。

それは有用な回答であり、実際に得られるものです。以前のページは、それをあたかも両方が適用されたかのように報告していました。冒頭の文、母集団の行、テーブル全体の見出し、メンバー一覧の見出し、要約の行、ステップごとの説明のすべてで`region=WEST`を挙げていましたが、並ぶ数値は地域で一度もフィルターされていませんでした。すべての数値は正しく、それらが何を対象としているかについての記述はすべて誤っていました。

## テーブル全体がどう動いたかを示す

## ランキングが何を差し引くかを示す

テーブルが複数の列を同時に報告する場合、たとえば収益と、そこから差し引かれる費用の列、あるいは売上とコストの場合、回答の隣のメンバー一覧はそのうちの1つでランク付けされます。そうすると、その一覧と回答のほかの部分が食い違って見えることがあります。費用の列の変化の大半を占めるとされたブランチが、ランキングの最下位になることがあります。収益とともに費用も減少したメンバーは、正味でほぼゼロになるためです。どちらの記述も正しいのですが、間に何もない状態で一緒に読むと、どちらかが誤っているという結論になりがちです。

## 要因とメンバーは別の切り口であることを示す

トレースのステップ行は、1つの変化について2つの記述を持つことがあります。1つ目は、その背後にある要因です。数値の元になるプールが動いたのであって、このスライスのプール内のシェアが動いたのではない、というものです。2つ目は、変化が位置するメンバーです。1つのブランチがその70%を占める、というものです。

## 書かれた要約は、書かれただけでなく検証される

アシスタントが分析を読みやすい段落にまとめるとき、静かなリスクがあります。文章が注意事項を落としたり、データが述べていない形に数値を丸めたりすることです。PlaidCloudはこの隙間を埋めます。構造化された結果とともに、**分析から直接作成された平易な要約**を返すことができます。それは信頼度を述べ、すべての注意事項を含み、データに対する実際のクエリから得られなかった数値を一切含みません。

これには、アシスタントが言い換えた自身のバージョンに対して実行できる**忠実性チェック**が付属します。信頼度を保っているか、すべての注意事項を保っているか、数値を捏造していないか、を確認します。言い換えがずれた場合は、チェックが検出します。その結果、単に流暢なだけでなく、その下にある数値に*確かに*忠実な文章が得られます。

**「もしこれが変わったら」という回答にも、同じ扱いがされます。** 以前は、数値と注意書きの一覧を返すだけで、物語を組み立てるのは読み手に任されていました。現在は、変化のどれだけを、いくつの結果にわたって説明できるかを述べて始まり、変化が直接及ぶ結果を、適用した変化に対する各結果の割合とともに一覧にし、部分的にしか測定できなかった結果と、まったく測定できなかった結果を、同じ一覧に印なく混ぜずに、それぞれ独自のセクションに置きます。他の結果の結果としてのみ動く結果は別に一覧にされ、上の数値にすでに含まれているものとして印が付くため、重ねて加算することはありません。変化をまったく追跡できない場合、回答は数値ではなく理由から始まります。

**このチェックは、ホワットイフの言い換えを、回答が測定できなかった内容に照らして検証します。** 回答が測定できなかった結果は、影響がゼロなのではなく不明ですが、言い換えられたバージョンが別の結果の数値をそれに対して引用しても、チェックを通過してしまうことがありました。現在は、そのような結果を数値の隣に挙げる節は、それが測定されなかったことも述べなければなりません。述べていない場合、チェックは修正方法を示します。数値を、それが属する結果または合計の隣に置いて、その結果が測定されなかったと述べるか、その結果に割り当てられた数値を取り下げます。また、結果の名前にドル金額が含まれている場合に、ホワットイフ回答自身の文言を拒否することもなくなりました。

## 次の質問を提案する

優れたアナリストは、答えるだけでなく、次に何を尋ねるべきかを教えてくれます。各要約は、分析が実際に見つけたことに基づいて、自然なフォローアップを提案します。数値がプール全体の合計であれば単一のメンバーに絞る、ある次元が変化を牽引しているように見えればその次元で変化を分解する、結果テーブルが複数のステップで構築されていれば特定のステップを指し示す、といった具合です。正確な文言を知らなくても提案に従って行動できます。そのまま依頼するだけです。

これらはいずれも*どれが*という問いに答えるものです。どのメンバーか、どのフィールドか、どのステップかです。さらにもう1つは*いつ*に答えます。回答が主要な要因を挙げてその割合を示す場合、その割合は比較した期間全体で1回だけ測定されます。そのため、1回の跳ね上がりで起きた動きと、着実に積み上がった動きが同じ数値になります。アシスタントは、いくつかのより狭い期間で再実行し、それらを互いに比較することを提案します。それが両者を区別する方法です。狭い期間を1つだけ使っても、同じ2点比較に戻るだけです。同時に、より狭い期間の数値は上の数値と合計が合わないことも述べます。各期間はそれ自体で測定されるため、プール、ドライバー、分割はすべてその期間のために再導出され、それらの割合はより広い期間を分割したものではなく、独自の答えです。特定の期間は挙げません。範囲のどの部分が重要かはあなたが選ぶことであり、それを推測することは、分析がまだ行っていない発見になってしまうからです。2つのシナリオ、2つのバージョン、予算と実績など、期間ではない2つのものを比較した場合は、実行できる狭い範囲がなく、アシスタントはその比較を時間として説明しないため、この提案はまったく表示されません。

さらに2つのケースでは提案が控えられます。どちらも、提案が求めた回答から離れる方向を指してしまうためです。2つの期間の一方がもう一方よりはるかに行数が少ないと回答がすでに報告し、変化に依拠する前にロードを確認するよう求めている場合、その期間をより狭い期間に分割すると、不足が解消されるのではなく分散してしまい、疑義を生んだ行数は、より狭いウィンドウでさらに弱くなります。そして、回答が複数の値の列を対象とし、先頭に挙げる列に独自の割合がない場合は、提案が条件づけるすべての割合が尋ねていない列のものになるため、回答の制限として読めるにもかかわらず、回答にはまったく関係がありません。先頭の列自身が割合を述べている回答には、引き続きこの提案が表示されます。

実行すると、すでに見ているものが返るような提案も省かれます。単一の列を対象とする回答では、アシスタントが最良の説明として選んだフィールドは、メンバーテーブルがすでにグループ化されているフィールドであるため、「そのフィールドで変化を分解する」と提案しても同じテーブルが返ってきました。しかも隣の注記は、数値がページ上のものと一致しないと述べていましたが、実際には完全に一致します。分解が別の列で本当に答えを返す場合、この提案は残ります。

分析が推測で選ばない複数の候補を見つけた場合、たとえば、どちらもテーブルを構築する2つのステップや、変化の説明として区別できないほど近い複数のフィールドがある場合、何から選べるのかを言わずに選ばせるのではなく、**それぞれ**を別々の提案として示します。書かれたとおりに実行できる提案が先に来ます。

それらの候補がフィールドである場合、現在は下の提案だけでなく、発見自体の中で名指しされます。それぞれには、最も強いメンバーと、そのメンバー自身の数値がどれだけ動いたかが、列全体の変化と比べて示されます。そのため、どちらかを選ぶ前に、同点の話のうちどちらが大きいかが分かります。同じスコアだったと述べるだけでは、それが隠れていました。ある自動車モデルでは、同点の両メンバーが列全体より大きく動いており、2つの数値を合わせると列全体の4倍超になりましたが、「複数が同程度のスコア」と伝えられた読み手は、2つを互換なものと受け取り、最初に来た方を報告しました。回答は同時に、候補はプールを分け合うのではなく重なり合うとも述べます。それぞれが同じ変化の別の切り口であるため、数値は1つの合計の部分ではなく、足し合わせても何も表しません。そして、フィールドの*ペア*は検索がスコアリングしたことのないビューであるため、クロス集計は分析が測定したものとしてではなく、次に実行するステップとして、つまり両方で同時に変化を分解するものとして提案されます。

何も見つからなかった検索も、伝える価値があります。変化を分解するフィールドを指定しない場合、アシスタントはそれを最もよく説明するものを探します。試したどれもが報告に値するほど変化を説明しなかった場合、黙り込むのではなくそう述べます。変化はプール全体にわたる広い動きとして読め、最も近かったフィールドは次のものです、とそのフィールドを挙げ、最大のメンバーと、そのメンバーが説明する変化の割合を示します。メンバーを挙げるのは、これが回答に*自信のない*唯一の発見であり、確認できる必要が最も高いからです。また、フォローアップが別のメンバーを先頭にする可能性があるという付随の警告を、検証可能なものにするのもこれです。そのフィールドは、近い勝負ではなく、弱いフィールドの中で最も強いものとして説明される、そのまま実行できる提案として示されます。検索が説明力なしと判断したためです。それによって数値の信頼度は下がりません。何も選ばれていないため、割り引くべき推測がないからです。

これら最後の2つは異なる結果であり、文言がそれらを区別します。複数のフィールドが*同等に良い*スコアだった場合は、候補が名指しされてサイズが示され、2つを同時に切るという提案を含む、それぞれ1つずつの提案になります。一方、*十分に良い*スコアのものがなかった場合は、最も近い1つが、まさにそのものとして提案されます。

**複数の値の列を持つ結果では、注記が検索した列を名指しします。** コスト、収益、マージンが並ぶような結果は、1列ずつ検索される一方、回答自体は要約の列を先頭に置きます。そのため、「何も見つからなかった」という結果は、結果全体への判定として読まれるのではなく、どの列の変化を対象としているかを述べます。名指しされた内容のとおりに読んでください。同じ結果の別の列には、それを説明するフィールドがあるかもしれず、その分解を直接依頼すれば分かります。

**似て見える2つの割合は区別されます。** アシスタントが変化を最もよく説明するフィールドを選ぶとき、報告される数値は、プールにおけるそのフィールドの**シェア**の変動です。ご自身でフィールドによって変化を分解するとき、数値は各メンバー**自身**の変化です。これらは異なる合計に対する異なる測定で、どちらも正しいため、それぞれがどちらであるかを述べ、両方が単なる変化の割合として読まれないようにしています。どちらも、2つの数値が異なると約束することはしません。メンバー別の内訳は、メンバーごとの割合をまったく表示せず、その行は金額です。そのため、不一致と言い表した警告は、行えない比較を探させることになり、確認できない警告は、無視するようになる警告です。それぞれが、2つの尺度が何であるかを述べて、そこで止まります。

これは、検索が何も決められなかった上記の最も近い候補の注記にも当てはまります。最も近かったフィールドについて引用されるシェアも、シェアの変動であり、そのフィールドによる分解は別の尺度を報告します。*基準に届かない*ということは検索についての記述であり、分解が示す内容の上限ではありません。

同点の場合にも当てはまり、そこでは2つの尺度が1つの文に並びます。候補は同じシェアの変動で同点とスコアされ、その隣に表示される数値は、それらのメンバー自身の変化です。そのため、回答は両方の尺度を名指しし、金額がスコアリングで比較されたものであるかのように見せません。2つが異なる大きさになると言い進むこともしません。確認する対象となるシェアの数値がそこには表示されておらず、確認できない警告は、無視するようになる警告だからです。

## これが違う理由

ほとんどのAI分析ツールは、正しいかどうかにかかわらず自信満々です。ダッシュボードに後付けされた汎用チャットボットは、流暢で権威があるように聞こえる回答を作り出しますが、しっかりした回答と誤った回答を見分ける手段は何も与えてくれません。そのようなツールにとって、すべての数値はただの数値です。

PlaidCloudは逆の発想で作られています。信頼できない回答には価値がないため、信頼度の評価、自己突き合わせ、正直な注意事項が、すべての回答の一部になっています。この誠実さこそが核心です。だからこそ、AIが生成した説明を、役員会向け資料、予測、意思決定の中で、手作業で再確認することなく実際に*使う*ことができます。
