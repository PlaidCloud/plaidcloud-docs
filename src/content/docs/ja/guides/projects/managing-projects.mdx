## 検索

プロジェクトの検索には、一覧の下部の行数の横にある**フィルター**を使用します。**/** または Ctrl/Cmd+F を押すと移動できます。フィルターはプロジェクトの名前とラベルから一致するものを検索し、結果を階層内に表示します。


## 新しいプロジェクトの作成

新しいプロジェクトを作成するには、次の手順に従います。

1. Analyze を開きます
2. 上部のメニューバーから「プロジェクト」を選択します
3. 「新規プロジェクト」ボタンをクリックします
4. 「Access Control」セクションを含め、フォームの情報を入力します
5. 「作成」をクリックします

これで、プロジェクトに対してアクセス権限の更新、オーナーの追加、ワークフローの作成を行えます。

<Aside>デフォルトでは、プロジェクトは現在のワークスペースのすべてのメンバーがアクセスできます</Aside>


## デフォルトのドキュメントアカウントの設定

プロジェクトのホームで、**接続環境**の隣にある**デフォルトのドキュメントアカウント**に、プロジェクトのドキュメントアカウントを選択します。解除するには**なし**を選択します。

プロジェクト内では、すべてのファイルセレクターの先頭に**プロジェクトのデフォルト**が表示され、プロジェクトに現在設定されているアカウントの代わりになります。プロジェクトを離れたとき、プロジェクトにデフォルトが設定されていないとき、そのアカウントが削除されたとき、またはそのアカウントへのアクセス権がないときは、一覧から消えます。

新しいファイルステップでは、プロジェクトにデフォルトが設定されている場合、プロジェクトのデフォルトが事前に選択されます。既存のステップが書き換えられることはなく、それぞれ保存時のアカウントのまま、自分で変更するまで維持されます。ドキュメントアカウントはステップごとに選ぶものですが、ステップは通常、プロジェクトの接続環境に従うためです。

プロジェクトのデフォルトのままにしたステップは、実行時にプロジェクトのデフォルトになっているアカウントに解決されます。そのため、実行の途中でデフォルトを変更しても、影響を受けるのはまだ開始していないノードだけです。これは接続環境を変更した場合と同じです。ステップがプロジェクトのデフォルトで実行され、プロジェクトにデフォルトが設定されていない場合、実行は他のアカウントにフォールバックせず、プロジェクト名を示して失敗します。


## ステップを 1 つの環境に固定する

ステップは、プロジェクトの[接続環境](/ja/guides/projects/project-home/#データと接続)に従うため、プロジェクトを QA と本番の間で切り替えると、すべてのステップが一緒に切り替わります。フォームに**環境**設定があるステップでは、そこで 2 つの選択肢を選べます。

- **Project environment** は、プロジェクトの接続環境に従います。特別な理由がない限り、この設定のままにします。
- **Fixed environment** は、プロジェクトの接続環境を無視し、選択した環境を常に使用します。プロジェクトをどの環境に切り替えても 1 つの環境にとどまる必要があるステップ（たとえば、QA に設定したプロジェクトで本番の参照データを読み取る場合など）にのみ使用します。警告アイコンは、そのステップが切り替えに従わないことを示します。

環境を固定したステップは、プロジェクトの環境以外で実行されるたびに、ログに警告を追加します。固定した環境が存在しなくなった場合（たとえば別のワークスペースからコピーしたステップなど）、ステップは別の環境で実行されず、その旨を示して失敗します。

ERP転記ステップは常にプロジェクトの環境を使用するため、これらのステップでは **Fixed environment** を使用できません。

デフォルトの環境は削除できません。また、プロジェクトが使用している間、ステップが固定環境として使用している間、またはエージェントが処理している間は、他の環境も削除できません。メッセージには、何がまだその環境を使用しているかが示されます。アクセス権のあるものは名前が示され、残りは件数で示されます。


## バージョン履歴

プロジェクト内のすべてのオブジェクト（ステップ、UDF、ワークフロー、ディメンション、保存済みレイアウト、ドキュメントやデータエディター、プロジェクト自体の設定）は、バージョン履歴のバックアップの対象です。バックアップは個々の保存のたびに作成されるわけではありません。オブジェクトが 30 秒間追加で保存されなかった時点で、その確定した状態のバックアップが 1 つ作成されます。短時間に連続して複数回保存するなどの一連の編集では、保存ごとのバージョンではなく、最終結果を含む 1 つのバージョンが作成されます。バックアップを待って保存が遅くなることはなく、カウントダウンもバックアップ自体もバックグラウンドで実行されます。今すぐバージョンが必要な場合は、**Back up now** を使用すると、現在の状態を即座に取得し、完了まで待機します。UI、API、および `*_versions` の MCP アクション `backup` で利用できます。バージョン履歴は、Free を含むすべてのプランで利用できます。

過去のバージョンでは、ポイントインタイムリカバリーがサポートされており、オブジェクトを以前のバージョンに復元できます。ロックされたプロジェクト内では、他の変更と同様に、復元は拒否されます。

バージョンはその場で復元されます。プロジェクト、ディメンション、ユーザー定義関数、ステップ、ワークフロー、データエディターのバージョンを復元すると、同じ項目が置き換えられ、別の項目をターゲットに指定すると拒否されます。たとえば、「A project version is restored in place. Leave the target out, or set it to this project.」というメッセージが表示されます。復元は項目への変更にあたるため、その編集と同じロールが必要です。[行を制限する](/ja/administration/access/managing-security-groups-and-assignments/#行を制限しているプロジェクトを変更できるユーザー)プロジェクトで、プロジェクトや、制限された列が読み取るディメンションを復元するには、プロジェクトのアーキテクトが必要です。古いテーブルデータを別のテーブルとして復元するには、[テーブルのスナップショット](/ja/guides/data/table-snapshots/)を新しいテーブルに復元します。

この自動追跡に加えて、プロジェクトとその要素ではバージョン管理も利用できます。バージョンは簡単に作成できるだけでなく、あるバージョンから別のバージョンに変更をマージすることもできます。これにより、スナップショットを簡単に管理したり、開発用のバージョンを作成して、必要なときにその変更を非開発バージョンにマージしたりできます。バージョン管理、比較、マージの実際の使い方については、[コラボレーション: バージョン、比較、共有](/ja/get-started/tutorials/collaborate-versions-and-sharing/)を参照してください。

テーブルデータには独自の履歴があります。Lakehouse が書き込みのたびに取得するスナップショットで、[テーブルのスナップショット](/ja/guides/data/table-snapshots/)で説明しています。

### AI アシスタントまたは MCP による復元と保持

AI アシスタントまたは MCP では、`dimension_versions` がディメンションのバージョンを `version_id` で復元、保持、解放し、`restore_project` がプロジェクト内のすべてのディメンションを最後のバックアップまでロールバックします。また、すべての `*_versions` 一覧（ステップ、UDF、ワークフロー、ディメンション、プロジェクト）には、各バージョンの `version_id` と、保持されているかどうかが表示されます。任意の `*_versions` ツールまたは REST API による `restore` は、項目をその場で復元します。ターゲットを省略するか、項目自体を指定してください。`project_upsert` はロックされたプロジェクトのロックを解除でき、`if_match` に対応しているため、最後にプロジェクトを読み取ってから行われた変更を上書きせず、失敗として扱います。


## プロジェクトアクセスの管理

### アクセスの種類

プロジェクトのセキュリティは、次の 3 種類のアクセスに簡素化されています。

* すべてのワークスペースメンバー
* 特定のメンバーのみ
* 特定のセキュリティグループのみ

プロジェクトのセキュリティは、簡単に設定できます。

1. Analyze を開きます
2. 「プロジェクト」を選択します
3. 制限したいプロジェクトの編集アイコンをクリックします
4. 「Access Control」で目的の制限を選択します
5. 「Update」をクリックします

プロジェクトへのアクセスを変更できるのは、プロジェクトのアーキテクトまたはテナント管理者だけです。変更できるのは、アクセスの種類、プロジェクトのメンバーとセキュリティグループ、データ共有です。それ以外のユーザーには、これらのパネルが読み取り専用で表示され、「Only project Architects can change access.」というメモが表示されます。


## すべてのワークスペースメンバー

「すべてのワークスペースメンバー」のアクセスは、最もシンプルなオプションです。ワークスペースのすべてのメンバーにアクセスを与え、メンバーの追加の割り当ては必要ありません。


## 特定のメンバーのみ

「特定のメンバーのみ」のアクセス設定では、各メンバーをプロジェクトに割り当てる必要があります。プロジェクトにメンバーを割り当てるには、次の手順に従います。

1. Analyze を開きます
2. 上部のメニューバーから「プロジェクト」を選択します
3. メンバーアイコンをクリックします
4. 「Access」列で、メンバーの名前の横にあるチェックボックスを選択してアクセスを許可します
5. 「Update」をクリックします

メンバー数が多いクラウドでは、この方法は想定以上の手間がかかることがあります。そのような場合にセキュリティグループが役立ちます。

<Aside>メンバーを追加するには、ワークスペースのメンバーである必要があります。</Aside>


## 特定のセキュリティグループのみ

「特定のセキュリティグループのみ」のオプションでは、特定のセキュリティグループにアカウントへのアクセス権限を割り当てられます。アクセス制限をセキュリティグループとの関連付けに任せることで、大規模なグループのアカウントアクセスの管理がはるかに簡単になります。これは、シングルサインオンによる自動グループ関連付けと組み合わせると特に役立ちます。シングルサインオンでメンバーのグループ割り当てを設定すると、これらのグループによってプロジェクトへのアクセスを暗黙的に有効化、無効化することもできます。

割り当てられたグループを編集するには、次の手順に従います。

1. Analyze を開きます
2. 上部のメニューバーから「プロジェクト」を選択します
3. セキュリティグループアイコンをクリックします
4. 「Access」列で、セキュリティグループの名前の横にあるチェックボックスを選択してアクセスを許可します
5. 「Update」をクリックします


## プロジェクト間でのデータの共有

データ共有により、あるプロジェクトから別のプロジェクトのテーブルにアクセスできます。たとえば、[Import Project Table](/ja/reference/workflow-steps/import/import-project-table/) ステップと [Export Project Table](/ja/reference/workflow-steps/export/export-project-table/) ステップで、プロジェクト間のデータを移動できるようになります。共有は、データが共有されるプロジェクトが、他の 1 つのプロジェクトに付与します。

1. データを共有したいプロジェクトを開き、その[プロジェクトホーム](/ja/guides/projects/project-home/)に移動します。
2. **Access & sharing** を開きます。**データ共有**の下で、**新規データ共有**をクリックします。
3. **プロジェクトを選択**の下で、このプロジェクトのデータを使用できるプロジェクトを選択します。
4. **許可される操作**の下で、**読み取り**、**書き込み**、またはその両方にチェックを入れ、**データ共有を追加**をクリックします。

**データ共有を削除**をクリックして確認すると、共有が削除されます。プロジェクトのデータ共有を追加、削除できるのは、プロジェクトのアーキテクトまたはテナント管理者だけです。

共有はプロジェクトに付与されるため、そのプロジェクトのメンバーとワークフローにのみ有効です。

- 共有を介した**読み取り**には、共有を付与されたプロジェクトでのロールが必要です。そこでロールを持たないユーザーは、共有から何も得られません。
- 共有を介した**書き込み**（共有元のプロジェクトでのテーブル、フォルダー、ディメンションの作成）には、**書き込み**共有と、自分のプロジェクトでのマネージャーまたはアーキテクトのロール（そこで同じ変更を行えるロール）が必要です。それ以外のユーザーには、「Writing to this project through a data share needs a write share from it to your project, and the Manager or Architect role in your project.」と表示されます。

ワークフローはプロジェクト自身の ID として実行されるため、Import Project Table ステップと Export Project Table ステップは、誰が実行を開始しても共有を介して動作します。


## さまざまな閲覧ロールの設定

プロジェクトでは、中間ステップを完了するために複数の変換やテーブルが必要になる一方で、最終的な結果はわずかなテーブルだけになることがよくあります。メンバーは、プロジェクトのすべての要素を閲覧する必要があるとは限らず、最終成果物だけで足りる場合もあります。PlaidCloud では、さまざまな閲覧ロールを設定して、各メンバーに表示される内容を簡単に整理、制御できます。

組み込みの閲覧ロールは、**アーキテクト**、**マネージャー**、**エクスプローラー**の 3 つです。

**アーキテクト**ロールは最もシンプルで、プロジェクト、ワークフロー、テーブル、変数、データエディター、階層、ユーザー定義関数のすべてを閲覧、管理できます。

**マネージャー**ロールと**エクスプローラー**ロールには特定のアクセス権限はありませんが、カスタム定義できます。つまり、グループごとにどの項目を表示するかを選べます。

<Aside>**マネージャー**と**エクスプローラー**はセキュリティグループではなく、職務と情報の可視性を分けるための便利な手段にすぎません。</Aside>

プロジェクト内のすべてを閲覧する必要があると考える場合は、全員を**アーキテクト**にできます。そうでない場合は、メンバーを**マネージャー**や**エクスプローラー**のプロジェクトメンバーに指定して、可視性を制御できます。

別のロールを設定するには、次の手順に従います。

1. Analyze を開きます
2. 「プロジェクト」を選択します
3. メンバーアイコンをクリックします
4. ロールを変更したいメンバーを選択します
5. 「Role」列で現在のロールをダブルクリックします
6. 目的のロールを選択します
7. 「Update」をクリックします


## プロジェクト変数の管理

プロジェクトやワークフローを実行するときに、繰り返し行う作業のために変数を設定しておくと、煩雑さを減らして時間を節約できます。これらの変数は通常の代数の変数と同じように動作し、変数が何を表すか、その後にどの演算を続けるかを設定できます。PlaidCloud では、これらの変数をプロジェクトレベルで設定すると、そのプロジェクト内のすべてのワークフローに影響し、ワークフローレベルで設定すると、そのワークフローだけに影響します。

プロジェクトレベルの変数を設定するには、次の手順に従います。

1. Analyze を開きます
2. 「プロジェクト」を選択します
3. 「Manage Project Variables」アイコンをクリックします

変数テーブルで、変数を表示したり、現在の値を表示、編集したりできます。「New Project Variable」ボタンをクリックして、変数を新しく追加したり、既存の変数を削除したりすることもできます。


## プロジェクトのコピー

**プロジェクトをコピー**は、プロジェクトの全体、または選択した一部を、新しいプロジェクトまたは既存のプロジェクトにコピーします。

プロジェクトをコピーするには、次の手順に従います。

1. Analyze を開きます
2. 「プロジェクト」を選択します
3. コピーしたいプロジェクトを選択します
4. **アクション**ボタンをクリックし、**プロジェクトをコピー**を選択します
5. ターゲットを選択し、コピーする内容とデータを選んで、**プロジェクトをコピー**をクリックします
6. **コピー前の確認**の概要を確認し、**コピーを開始**をクリックします

### コピーする内容の選択

選択ツリーには、プロジェクトの内容がタイプ別（ワークフロー、ステップ、テーブル、ディメンション、データエディター、ユーザー定義関数）に表示されます。すべてにチェックを入れたままにするとプロジェクト全体がコピーされ、必要な部分だけにチェックを入れることもできます。

それらの部分が何に依存しているかを調べる必要はありません。チェックを入れたものは、その依存関係も一緒にコピーされます。ステップが読み書きするテーブル、ステップがロードまたは配賦の対象とするディメンション、呼び出すユーザー定義関数、呼び出すサブワークフローやマクロなどです。ワークフローのセンサーは、ワークフローと一緒にコピーされます。

**コピーされたセンサーは無効の状態で作成されます。** コピー先のプロジェクトで各センサーを有効にするまで、コピーでは何も起動しません。重複する項目を上書きするインポートでは、コピー先のワークフローにすでにセンサーがある場合、2 つ目のセンサーは追加されません。

### 新しいプロジェクトへのコピー

新しいプロジェクトに名前と ID を付けます。ID はスキーマ名になり、後から変更できません。

**スケジュールは一時停止された状態で作成されます。** プロジェクト全体を新しいプロジェクトにコピーすると、各ワークフローのスケジュールされたイベントは一時停止された状態でコピーされるため、コピーが自動的に実行を始めることはありません。コピーが完了すると、元のプロジェクトで有効だったイベントがメッセージに一覧表示されます。コピーでいずれかのイベントを実行するには、**ツール** > **イベントスケジューラー**でそのイベントを選択し、**選択を有効化**をクリックします。[イベントの一時停止](/ja/administration/scheduled-events/event-scheduler/#イベントの一時停止)を参照してください。

### 既存のプロジェクトへのコピー

プロジェクトの一覧からターゲットを選択します。コピーは、そのプロジェクトを置き換えるのではなく、内容を追加します。

**ターゲットを変更できる必要があります。** ロールを持たないプロジェクトへのコピーや、変更を防ぐためにロックされているプロジェクトへのコピーは拒否されます。これは何かを読み取ったり書き込んだりする前に確認されるため、拒否されたコピーでターゲットが変更されることはありません。また、プロジェクトを自分自身にコピーすることもできません。

**行を制限するプロジェクトをコピーするには、プロジェクトのアーキテクトである必要があります。** コピーは[行アクセス](/ja/administration/access/managing-security-groups-and-assignments/#行アクセスの管理)の制限がない新しいプロジェクトになり、コピー時にその旨が「This copy is not row-restricted.」と表示されます。共有する前に、コピーで行アクセスを設定してください。行を制限する既存のプロジェクトにコピーする場合も同様に、そのプロジェクトのアーキテクトまたはテナント管理者のいずれかである必要があります。

**ターゲットは独自の設定を維持します。** 名前、ID、データ接続の環境、ストレージのデフォルト、ドキュメントアカウント、アクセスの種類、アクセスリスト、行アクセスの付与は、すべてそのまま残ります。コピーされるのは、選択した内容だけです。

**プロジェクトのデフォルト**に設定されたステップは、アカウントではなくその設定自体が引き継がれます。コピー後は、元のプロジェクトで設定されていたものではなく、ターゲットのプロジェクトに設定されているデフォルトに解決されます。

受信する項目が、ターゲットにすでにある項目と同じものである場合は、どうするかを選択します。

- **重複する項目を受信データで上書き** — 受信したバージョンが、ターゲットにあるものを置き換えます。
- **重複する項目の新しいコピーを作成** — ターゲットは現在のものを維持し、受信したものは名前の末尾に ` copy` を付けて並べて追加されます。その名前も使用済みの場合は、連番が付きます。

プロジェクト変数とワークフロー変数は、*新しいコピーを作成*の例外です。変数は名前で識別されるため、何からも参照されない名前に変更しない限り、2 つ目のコピーを追加する方法がないためです。コピーが運ぶ変数をターゲットがすでに定義している場合は、ターゲット自身の値が維持され、コピー時にどの変数をそのままにしたかが通知されます。*上書き*は、変数を他のものと同様に扱い、置き換えます。

この照合は名前ではなく ID によって行われます。元は同じプロジェクトに由来する項目は同じ項目として認識されますが、たまたま同じ名前を共有しているだけの 2 つの項目は別の項目として扱われ、どちらも後に存在します。

### コピーするデータ量の選択

**Data to copy** の下にある 2 つの設定で、選択内容とともにどのデータをコピーするかを決めます。

**テーブルデータ**は、各テーブルの行を何行コピーするかを設定します。

| 選択肢 | コピーされるもの |
| --- | --- |
| **No table data** | 行を含まないテーブル、ステップ、その他の選択内容。これがデフォルトです。 |
| **完全** | 同じレイクハウス内、およびレイクハウス間での、すべてのテーブルの行。 |
| **サンプル** | 入力した**テーブルあたりの行数**まで。新しいプロジェクトの場合のみです。数値は 1 から 1,000,000 までです。 |

サンプリングされたテーブルには、その行数まで、行数がそれより少ない場合はすべての行が含まれます。**完全**または**サンプル**のコピーでは複数のテーブルが同時にコピーされるため、テーブル数の多いプロジェクトでも短時間で完了します。

**Copy dimension members** は、**テーブルデータ**でどれを選択しても、選択内容に含まれるすべてのディメンションのメンバーをコピーします。デフォルトでオンになっているため、テーブルデータなしのコピーでも、メンバーが入力されたディメンションが作成され、短時間で完了します。ディメンションをメンバーなしでコピーするには、チェックを外します。

REST API（`POST /rest/v1/analyze/project/copy`）または `project_copy` MCP ツールでは、`data_mode` に `structure`、`full`、`sample` のいずれか、`dimension_members` に `true` または `false` を設定します。`dimension_members` を省略した場合、メンバーはテーブルの行がコピーされるときにのみコピーされます。`project_copy` は、コピーされなかった ERP 書き込み承認など、コピーの警告も返します。

### コピーの確認

コピーを開始する前に、**コピー前の確認**に、コピーの概要が表示されます。コピー元のプロジェクト、コピー先、**テーブルデータ**の選択、**ディメンションメンバー**を含めるかどうか、テーブルとビューの数、サイズ、推定時間、コピー元とコピー先のレイクハウス、**ご注意**の下の警告が表示されます。**コピーを開始**をクリックして開始するか、**キャンセル**をクリックして戻り、選択内容を変更します。

### コピーを閲覧できるユーザー

データ（テーブルの行、ディメンションメンバー、またはその両方）を含めて作成したコピーは、作成したユーザーだけが閲覧できます。準備ができたら、新しいプロジェクトから共有してください。行レベルセキュリティのあるプロジェクトのコピーも、同じ理由で非公開のままです。

既存のプロジェクトにデータをコピーするには、そのプロジェクトへの書き込みアクセスが必要です。

### コピーでの ERP 書き込み承認

自分だけが閲覧できる新しいコピーには、コピー元のプロジェクトの [ERP書き込み承認](/ja/guides/workflows/run-a-workflow/#プロジェクトに転記を承認する)が引き継がれるため、コピーを再度承認することなく、転記ワークフローをテストできます。これは、テーブルデータ（**完全**または**サンプル**）、ディメンションメンバー、またはその両方を含めて、新しいプロジェクトに作成したすべてのコピーが対象です。承認がコピーされるのは、次の場合です。

- コピー元のプロジェクトのアーキテクトまたはワークスペース管理者である。
- エージェントやサービスアカウントではなく、自分でコピーを作成した。

各承認は、現時点で自分が付与できる場合にのみコピーされます。つまり、その接続と環境がまだ存在し、接続への書き込みアクセスがある場合です。コピーされた承認は、自分のものとして記録されます。

**コピーはシミュレートの状態で作成されます。** コピー元のプロジェクトの **ERP転記モード**がライブの場合、コピーではシミュレートに設定されるため、ワークフローは ERP に接続せずに、転記する内容の作成と確認を行います。コピー元がシミュレートまたはオフに設定されている場合は、その設定が維持されます。コピーから実際に転記する準備ができたら、コピーのホームページの **ERP転記**にある **ERP転記モード**をライブに設定します。[転記モードの選択](/ja/guides/workflows/run-a-workflow/#転記モードの選択)を参照してください。スケジュールとセンサーは、前述のとおり一時停止および無効の状態で作成されるため、有効にするまでコピーでは何も実行されません。

既存のプロジェクトへのコピー、またはテーブルデータもディメンションメンバーも含まないコピーは、コピー元の承認なしで始まります。転記する前に、コピーのホームページの **ERP転記** > **ERP書き込み承認**で承認してください。

**コピー結果**には、たとえば「2 ERP write authorizations copied; ERP posting is in Simulate」のように、何が行われたかと、コピーされなかった数が報告されます。

### コピー結果

コピーが完了すると、**コピー結果**ウィンドウに、コピーされたテーブルとディメンションメンバーの概要が表示され、各テーブルとディメンションが名前と結果（**コピー済み**、**変更付きでコピー済み**、**サンプリング済み**、**スキップ済み**、**失敗**）とともに一覧表示され、スキップまたは失敗したものにはその理由が示されます。**Retry failed items** をクリックすると、失敗したテーブルとディメンションを再度コピーします。コピー内のそれらの現在の内容は置き換えられます。コピーが完了または失敗すると、メッセージとメールで通知されます。結果はメッセージから再度開くことも、後から**プロジェクト**タブでコピーを選択し、**アクション**メニューから**インポートまたはコピーの結果を表示**を選択して開くこともできます。

結果は、誰かが破棄するまでコピーに残ります。コピーが完了したら、**結果を破棄**をクリックすると、プロジェクトを開けるすべてのユーザーから結果が削除されます。プロジェクトの内容は何も変わりませんが、ウィンドウから失敗した項目を再試行することはできなくなります。破棄にはプロジェクトへの編集アクセスが必要で、プロジェクトがロックされていないことも必要です。

### 参照の更新

プロジェクトのワークフローステップは、そのプロジェクト内のテーブルやその他のオブジェクトを参照します。**参照を更新**は、それらの参照を元のプロジェクトではなくコピーを指すように書き換えます。ほとんどの場合、これが望ましい動作であり、デフォルトでオンになっている理由です。オフにすると、コピーされたステップは元のプロジェクトを指したままになります。

<Aside>コピーはバックグラウンドで実行されます。進行状況ダイアログに、コピーが各段階を進んでいく様子が表示されます。**バックグラウンドで実行**をクリックするとダイアログを閉じて作業を続けられます。プロジェクトの一覧は自動的に更新され、コピーが完了すると通知されます。</Aside>

## プロジェクトレポートの表示

プロジェクトやワークフローが動的な場合、詳細なドキュメントを維持するのは困難です。この問題を解決するために、PlaidCloud では、ワークフロー、ワークフローステップ、ユーザー定義変換、変数、テーブルの詳細なドキュメントとなるプロジェクトレベルのレポートを生成できます。このレポートはオンデマンドで生成され、プロジェクトの現在の状態を反映します。

レポートをダウンロードするには、次の手順に従います。

1. Analyze を開きます
2. 「プロジェクト」を選択します
3. レポートアイコンをクリックします
