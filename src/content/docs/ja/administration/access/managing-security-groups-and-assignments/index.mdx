PlaidCloudのセキュリティとアクセスの管理はシンプルです。メンバーは、所属しているグループに基づいてアクセスを許可または拒否されます。メンバーのセキュリティ関連付けの追加や変更は、簡単にカスタマイズできます。

<Aside>各ワークスペースで作成できるセキュリティグループの数に上限はありませんが、セキュリティ管理を容易にするため、数を最小限に抑えることをお勧めします。</Aside>



## セキュリティグループの管理


セキュリティグループは、追加、更新、削除ができます。



**セキュリティグループを管理するには：**


1. Identityを開きます
2. 「Security」タブを選択します
3. ドロップダウンメニューで「Security Groups」をクリックします（既存のグループを表示するフォームが開きます）
4. グループを追加するには、「Create Security Group」をクリックします
5. グループの権限を編集するには、左端のアイコンをクリックします

**グループのメンバーを管理するには：**


1. Identityを開きます
2. 「Security」タブを選択します
3. ドロップダウンメニューで「Security Groups」をクリックします
4. メンバーアイコンをクリックします
5. 追加したいメンバーを「Unassigned Members」列から「Assigned Members」列へドラッグします。メンバーを削除するには、逆方向にドラッグします

<Aside>「Assigned Members」列を空にして保存しても何も変更されず、その旨が通知されます。グループを全員から外すには、メンバーシップを空にするのではなく、そのグループの権限を削除するか、グループ自体を削除してください。</Aside>

<Aside>グループに[行アクセス](#行アクセスの管理)で行が付与されている場合、メンバーシップの変更は約1分以内にダッシュボードへ反映されます。追加したユーザーはダッシュボードでそのグループの行を表示でき、削除したユーザーは表示できなくなります。メンバーの無効化や削除、グループの削除も同様に反映されます。</Aside>

<Aside type="caution">自分自身では付与できない権限は、グループの権限マトリクスを保存しても変更されず、マトリクスにも表示されません。変更が必要な場合は、その権限を持つユーザーに依頼してください。マトリクスで編集できるのは、自分が管理できる権限だけです。</Aside>

## 行アクセスの管理

行アクセスは、1つの列の値に基づいて、セキュリティグループがテーブルのどの行を表示できるかを制限します。たとえば `region` 列でアクセスを制限し、`East` と `Central` を付与したグループには、それらの値を持つ行だけを表示させることができます。プロジェクトと列に関するすべての操作（列の選択、値の取得元の選択、どのグループに何を表示するかの決定）は1つの画面で行え、保存すると即座に反映されます。

行アクセスの設定と変更には、プロジェクトのアーキテクトまたはテナント管理者の権限が必要です。それ以外のユーザーがプロジェクトの「Security」タブを開くと、行アクセスはアーキテクト専用であることが通知され、以下のエントリーポイントは表示されません。

### 行アクセスを開く

どのエントリーポイントからも、同じ行アクセス画面が開きます。

- **テーブルエクスプローラーのツールバー**には**行アクセス**ボタンがあり、テーブルがすでに行を制限している場合はバッジが表示されます。テーブルに制限された列がある場合は最初の制限列で開き、テーブルの他の任意の列に切り替えることもできます。
- **列のファセットメニュー**には**この列で行を制限…** があり、その列で行アクセスを開きます。すでに行を制限している列では、この項目は**この列で行を制限中 - 編集…** と表示されます。
- **プロジェクトの「Security」タブ**には、プロジェクト内の制限されたすべての列が、適用先のテーブル、付与を持つグループ、**同期**の状態とともに一覧表示されます。列を選択して編集するか、**列を制限…** をクリックして新しく開始します。テーブルを選び、次に列を選びます。すでに行を制限している列には、鍵のマークが付きます。
- **Identity → Member** の、メンバーの**行アクセス**タブと、**Identity → Security → Security Groups** の、グループの行アクセスのサマリー。**行アクセスを開く**（または**編集**）で選択した列が開き、**追加**でその行のプロジェクト内の別の列を制限します。

列を指定して開いた場合、画面はその列のままです。**列を制限…** または**追加**で開いた場合は、列を選択できます。

### 行アクセスのグリッド

列でテーブルを制限するには、次の手順を実行します。

1. 上記のいずれかのエントリーポイントから行アクセスを開き、列を指定せずに開いた場合は列を選択します。ピッカーには自由入力のテキストではなく、テーブルの実際の列が表示されます。
2. **値のソース**を選択します。**列**（テーブルの列の一意の値）、**ディメンション**（ディメンションのノード）、**リスト**（手入力する値）のいずれかです。値の型は列のデータ型に従います。
3. セキュリティグループごとに、そのグループが表示できる値にチェックを付けます。グリッドには、プロジェクトにアクセスできるグループと、その列にすでに付与を持つグループが一覧表示されます。
4. **Everyone else** を **sees all rows** または **sees no rows** に設定します。これは、グリッドでチェックが1つもないグループすべてに適用されます。
5. **保存**をクリックします。

保存は即時に反映されます。PlaidCloud自体のクエリは変更に即座に追従し、Supersetダッシュボードは約1分以内に追従します。適用のための別の手順や承認ダイアログはありません。画面の同期状況には、変更がどこまで届いたかが表示されます。詳しくは[ダッシュボードとの同期の維持](#ダッシュボードとの同期の維持)を参照してください。

グリッドは、次のような細かな点も処理します。

- **多数の値。** 値は並べ替えられます。列の値が表示しきれないほど多い場合、グリッドには「More values than fit here — type to search.」と表示され、フィルターボックスで列全体を検索できます。グループがすでに持っている値はすべて保持されます。
- **空白の値。** **空白の値 — 付与のあるすべてのグループに表示**チェックボックスが1つあり、列に値がない行の扱いを決めます。オンにすると、その列に何らかの付与を持つすべてのグループが、それらの行を表示できます。
- **まだ構築されていないテーブル**では、空のリストの代わりに**先にこのテーブルを構築してください（作成するワークフローを実行します）** と表示されます。
- **保存は画面上の値の読み込みを待ちます。** 値の読み込み中（値のソース、ディメンション、テーブルを切り替えた後や、テンプレートを適用した後）は、**保存**が無効になり、「Save is available once this source's values load.」というツールチップが表示されます。読み込みに失敗した場合はグリッドがその旨を表示し、ソースの再選択を求めます。読み込みが成功するまで何も保存されません。

### 1つの列名、すべてのテーブル

制限は、単一のテーブルではなく、プロジェクト内の列の*名前*に対して設定されます。`region` で行が制限されると、プロジェクト内で `region` という名前の列を持つすべてのテーブルが、PlaidCloud自体のクエリでもダッシュボードでも、その制限によってフィルターされます。グリッドの **Applies to** リストには、それらのテーブルが表示されます。リストは列名によって決まるため読み取り専用で、あとから同じ列を持つテーブルを追加した場合も、公開された時点で対象になります。

プロジェクト内にその名前の列を持つテーブルがない場合、ウィンドウには **Applies to 0 tables** の表示に加えて、テーブルが追加されるまでその制限はどのダッシュボードもフィルターしないという警告が表示されます。テーブルに列を追加するか列名を修正すると、警告は消えます。

<Aside type="caution">
**列名は、大文字小文字や空白も含めて完全に一致している必要があります。** `Region` と `region` は別の名前であり、`region` と末尾に空白のある `region ` も別の名前です。ピッカーには実際の列名だけが表示されるため、これが問題になるのは主に、他の場所で列の名前が変更された場合です。その場合、行アクセスは何も制限しないままにするのではなく、警告を表示し、見つかった最も近い列を示します。
</Aside>

<Aside type="caution">
**行を制限するテーブルを公開すると、同じ手順でそのダッシュボードフィルターも設定されます。** ダッシュボードは、公開されたレポートビューを通じてテーブルを読み取ります。そのため、制限された列を持つテーブルを公開または再公開すると、公開が完了する前にPlaidCloudがそのテーブルのダッシュボードフィルターを登録します。登録できない場合は公開が拒否され、その試行で作成されたものはロールバックされます。これにより、制限されたテーブルがフィルターなしのままダッシュボードに残ることはありません。ビューのクエリは制限された列の名前を変更したり、その列から値を導出したりできるため、行を制限するプロジェクトでは*ビュー*を公開できません。[テーブルの公開](/ja/guides/data/publish/)を参照してください。
</Aside>

### 制限の解除

グリッドの**制限を解除**をクリックすると、インラインの確認の後に制限が削除されます。確認メッセージは「Stop restricting rows by ‘region’? Every group's grant on it is removed and everyone sees its rows.」です。その後、行アクセスは「Rows in ‘region’ are no longer restricted.」と通知します。その列のSupersetデータセットも一緒に削除されますが、チャートがまだ使用している場合は削除されません。その場合、行アクセスはデータセットが残ることと、使用しているチャートの数を通知します。

行を制限している間は、列の名前を変更したり削除したりできません。アーキテクトには、先に行アクセスで制限を解除するよう通知されます。それ以外のユーザーには、プロジェクトのアーキテクトに依頼するよう通知されます。

### 行を制限するプロジェクトを変更できるユーザー

プロジェクトのワークフロー、ステップ、ユーザー定義関数は、すべての行を読み取れるプロジェクト自身のサービスIDとして実行されます。それらを変更できるユーザーは、付与されていない行を、自分が読み取れるテーブルにコピーするステップを作成できてしまいます。そのため、プロジェクトで行を制限すると、プロジェクトの動作を誰が変更できるかも制限されます。プロジェクトで少なくとも1つの列が制限されると、次のようになります。

- **自動化はアーキテクト専用になります。** ワークフロー、ステップ、ユーザー定義関数、スケジュール、ワークフロー変数とプロジェクト変数、通知メールテンプレートを変更できるのは、プロジェクトのアーキテクトとテナント管理者だけです。同じ理由で、ワークフローバンドルのインポート、Alteryxワークフローの変換、プロジェクトへのインポート、コピー、復元、プロジェクトの接続環境、デフォルトのドキュメントアカウント、ERP転記モードの変更も、これらのユーザーだけが行えます。それ以外のユーザーも、プロジェクトのワークフローを実行することはできます。**開始**、**停止**、**再開**、**選択したステップを実行**は引き続き使用できます。ステップエディター、ワークフローの編集コントロール、UDFエディター、スケジュールフォームは、これらのユーザーには読み取り専用で開き、依頼先のアーキテクトを示すバナーが表示されます。「This project restricts rows, so only its Architects can change workflows, steps, UDFs, schedules, variables and notify templates. You can still run them.」
- **制限された列が読み取るディメンションはアーキテクト専用になります。** 誰がどの行を表示できるかを決めるディメンション（制限された列の値のソース）は、プロジェクトのアーキテクトまたはテナント管理者と、プロジェクト自身のワークフローだけが変更できます。これには、そのノードとディメンション自体の追加、移動、名前の変更、コピー、クリア、読み込み、復元が含まれます。それ以外のユーザーには、「This dimension decides who sees which rows of ‘region’, so only a project Architect can change it.」と通知されます。どの制限からも読み取られないディメンションは影響を受けません。
- **付与ソーステーブルはアーキテクト専用になります。** 列の[付与のソース](#付与のソーステーブルへのバインド)としてバインドされたテーブルは、行の変更や削除を、プロジェクトのアーキテクト、テナント管理者、プロジェクトのワークフローだけが行えます。データエディター、インポート、コネクターの読み込み、APIのいずれを使う場合も同様です。
- **プロジェクトのコピーはアーキテクト専用です。** コピーには「This copy is not row-restricted.」と表示されます。新しいプロジェクトには、設定するまで制限がありません。
- **以前のバージョンの復元も、他の変更と同じ扱いです。** プロジェクト自身の設定や、上記のディメンションを復元するには、プロジェクトのアーキテクトである必要があります。復元は常にそのバージョンが属する項目に適用されるため、この制限を回避するために別のプロジェクトを対象にすることはできません。[バージョン履歴](/ja/guides/projects/managing-projects/#バージョン履歴)を参照してください。
- **制限されたテーブルのデータ編集**にはアーキテクトが必要です。詳しくは[行アクセスとデータエディター](#行アクセスとデータエディター)を参照してください。
- **制限されたテーブルへのDataFrameの書き込み、レコードの保存、クリア**は、すべての行を表示できる場合を除き、自分の行だけを変更します。詳しくは[制限されたテーブルへのデータの読み込み](#制限されたテーブルへのデータの読み込み)を参照してください。

プロジェクトで最初の列が制限される前に、行アクセスは影響を受けるユーザーを通知します。「Restricting rows here means only Architects can change this project's workflows, steps, UDFs, schedules and notify templates. N members can change them today; they will still be able to run them.」

実行は、スケジュールされたものも含めて、プロジェクトのサービスIDとして実行されるため、これまでとまったく同じように動作します。実行が生成するものは、アーキテクトが設計した内容に従います。制限された列を含まない出力テーブル、エクスポートファイル、通知メール、ログの行は、それを読むユーザーに対してフィルターされません。

**実行の開始時に指定する値。** ワークフローを実行できるユーザーは、変数に独自の値を指定して開始できます。[App Runner](/ja/guides/workflows/use-converted-alteryx-apps/#app-runnerフロントエンド)はフォームの回答でこれを行い、APIやAIツールでも可能です。これらの値はその実行にのみ有効で、ワークフローには保存されず、他の実行、エクスポート、閲覧者には見えません。実行はサービスIDとして行われるため、これらの値によってその実行が読み書きする内容が変わる可能性があります。ワークフローの実行権限は、信頼できる人にのみ付与してください。

**行を制限しないプロジェクト。** これらのルールは、プロジェクトで列が制限された時点で初めて有効になります。何も制限していないプロジェクトでは、プロジェクトの自動化を変更できるユーザーが、プロジェクトのサービスIDとして実行されるステップやユーザー定義関数を作成して、プロジェクトのアクセスを変更し、自分自身をアーキテクトの1人にすることができます。これは仕様です。そのようなプロジェクトは、行の分離を保証しません。そこでの作成権限は、アーキテクトとして信頼できる人に限定するか、列を制限してください。

### ダッシュボードとの同期の維持

行アクセスは、変更がダッシュボードに届くまでの状況を、グリッドと、プロジェクトの「Security」タブの**同期**列に表示します。

| ステータス | 意味 |
|---|---|
| **待機中** | 変更は保存され、ダッシュボードへ送信中です。通常は約1分以内に完了します。 |
| **再試行中** | 送信に失敗し、再試行しています。失敗の理由がステータスの横に表示され、すぐに再送信する**再試行**も表示されます。 |
| **未適用** | プロジェクトの制限は、まだダッシュボードへ送信されていません。 |
| **適用済み** | 制限をダッシュボードへ送信する直近の試行が成功しました。 |
| **ダッシュボードと同期済み** | 行アクセスは、ダッシュボードが適用している内容と、自身が書き込む内容を比較し、両者が一致しています。 |
| **ダッシュボードと差異あり** | ダッシュボードが、行アクセスが書き込む内容を適用していません。Supersetでルールが変更または削除されたか、テーブルの公開ビューをチェックできません。 |
| **エラー** | 制限の送信に失敗しました。理由がステータスの横に表示されます。 |

変更が**適用済み**になると、グリッドはそれをダッシュボードと照合し、**ダッシュボードと同期済み**または**ダッシュボードと差異あり**に移行します。**ダッシュボードと差異あり**と**エラー**ではどちらも**再試行**が表示され、プロジェクトの制限を再送信します。ステータスをまったく読み取れない場合、グリッドには「Couldn't check sync status.」と表示されます。

1つのテーブルが原因の**エラー**では、そのテーブルの名前と対処方法が示されます。たとえば、制限された列なしで公開されたテーブル（「Republish or unpublish it.」）や、制限された列を持つが公開されていないテーブルで、公開するまでダッシュボードがフィルターできないものがあります。ステータスは**エラー**のままで、そのテーブルを公開するか、代わりに公開済みのテーブルの列を制限するまで、公開されていないテーブルの名前が表示されます。そのようなテーブルがあっても、プロジェクトの他の部分が止まることはなく、他のすべてのテーブルは同期が維持されます。

ダッシュボードは、PlaidCloud自体のクエリと同じ付与に従います。

- **その列を持つ公開済みのすべてのテーブルがフィルターされます。** 制限を設定したときに見ていたテーブルだけではありません。
- **一部の値だけを付与されたグループは、他のすべてのユーザーがすべての行を表示できる場合でもフィルターされます。** ダッシュボードのデータセットが存在するすべてのテーブルが対象です。
- **プロジェクトのアーキテクトはすべての行を表示できます。** テーブルエクスプローラーやPlaidCloudの他の場所と同様に、ダッシュボードでも同じです。これは、プロジェクトのアーキテクトグループと、個々のメンバーと共有されているプロジェクトのアーキテクトに適用されます。アーキテクトのアクセスを取り消すと、ダッシュボードには即座に反映されます。メンバーのロールの変更、メンバーまたはそのグループのプロジェクトからの削除、プロジェクトのアクセスタイプの変更、以前のプロジェクトバージョンの復元、グループの削除のいずれでも同様です。
- **セキュリティグループのメンバーシップの変更は、自動的にダッシュボードへ反映されます。** PlaidCloudでユーザーをグループに追加または削除する、メンバーを無効化または削除する、グループを削除する、デフォルトのセキュリティグループに参加する新しいメンバーを追加するといった操作は、そのグループに値を付与しているすべてのプロジェクトで、行アクセスを開き直さなくても、約1分以内にダッシュボードでの表示内容に反映されます。PlaidCloudの外で行われたメンバーシップの変更（Keycloakでの直接の変更や、サインイン時にシングルサインオンがユーザーをグループに配置した場合）は、保存や再試行の必要なく、約15分以内にダッシュボードへ反映されます。

### ディメンションの付与

値のソースに**ディメンション**を選ぶと、ノードにチェックを付けることで、その配下のすべてを付与できます。付与はディメンションに追従します。チェックを付けたノードの配下に追加されたメンバーは、ディメンションの保存後の次の同期でそのグループに付与されます。その配下から移動または削除されたメンバーは付与されなくなります。グリッドを開き直す必要はありません。開き直したときには、チェックを付けたノードにはチェックが付いた状態で表示されます。

チェックを付けたノードの配下にある項目のチェックを外すと、そのノードのチェックも外れ、グループにはチェックされたままのメンバーだけが残ります。そのメンバーに再度チェックを付けても、ノードのチェックは戻りません。ノードのチェックボックスをクリックしてください。**貼り付け**、**すべて選択**、**選択を反転**は、メンバーにチェックを付けるもので、ノードにはチェックを付けません。

名前が行アクセスの値として使用できないディメンションメンバーは、保存時にその名前を示して拒否されます。そのようなメンバーがあとから現れた場合、その行は誰にも付与されず、同期ステータスにその名前が表示されます。「Dimension ‘…’ member ‘…’ cannot be used as a row access value, so its rows are not granted. Rename it in the dimension.」

### 付与のソーステーブルへのバインド

値を手作業でチェックする代わりに、制限された列を、答えをすでに保持しているソーステーブルに結び付けることができます。このテーブルには、グループと、そのグループが表示できる値が1行ずつ入っています。まずグリッドで列を制限し、次に、列、ソーステーブル、およびソーステーブルのグループ列と値の列を指定した[**行アクセスを設定**](/ja/reference/workflow-steps/tables/table-set-row-access/)ワークフローステップを追加します。このステップの最初の実行で、列がそのテーブルにバインドされます。列に手動で設定された付与はクリアされ、付与はテーブルの行から設定されます。

バインドされると、その列は**ソース管理**になります。行アクセスのグリッドでは、ソーステーブルの名前を示すバッジとともにロックされた状態で表示され、**バインディングを削除**をクリックするまで、付与の手動編集は拒否されます。

ステップは実行のたびにソーステーブルを読み直して付与を再適用します。そのテーブルを読み込むまたは更新するワークフローの後にスケジュールすると、ソースデータで追加、削除、再割り当てされたグループが、グリッドを手動で編集しなくても、次の実行で行アクセスに反映されます。

ソーステーブルが誰に何を表示するかを決めるため、その行の変更や削除ができるのは、プロジェクトのアーキテクト、テナント管理者、プロジェクト自身のワークフローだけです。それ以外のユーザーには、「This table supplies the row access grants for ‘region’, so only a project Architect can change its rows or delete it.」と通知されます。

### 制限テンプレート

同じ値のソース、値の型、空白値の設定といった、再利用したい制限の形を作成した場合は、それを一度保存しておけば、列ごとに作り直すことなく、必要な場所に適用できます。

- 開いている行アクセス画面の**テンプレートとして保存…** は、現在の列の形を、名前付きのテナントレベルのテンプレートとして保存します。保存されるのは形だけで、付与は含まれません。
- 別のプロジェクトの列で**テンプレートを適用**すると、その列がテンプレートの形で開始され、すべてのグループの付与は空の状態になるため、ご自身で入力できます。

テンプレートの保存と適用は、どのプロジェクトのアーキテクトでも行えます。テンプレートは テナント全体で共有されるため、名前の変更（**名前の変更…**）と削除（**削除**）にはテナント管理者が必要です。テンプレートを削除しても、それを適用した列の制限はそのまま残ります。

<Aside type="note">
テンプレートはリンクではなくコピーです。あとからテンプレートを編集しても、すでに適用した列は変更されません。後の改訂内容に列を合わせるには、テンプレートをもう一度適用してください。
</Aside>

### SSOグループ属性による付与

列は、PlaidCloudではなくIDプロバイダーから付与を受け取ることもできます。プロジェクトのアーキテクトが、行アクセスで **Accept row-access grants from SSO group attributes** を有効にして、列をオプトインします。

有効にすると、セキュリティグループのKeycloak属性 `row_access.<column>` が、そのグループがその列で表示できる値を設定します。Keycloakでグループに属性を設定すると、プロジェクトへのアクセスをすでに持つグループについて、PlaidCloudが自動的にそれを取り込みます。行アクセス自体でそれ以上設定する項目はなく、付与はPlaidCloud自体のクエリとSupersetダッシュボードの両方で同期されたままになります。

<Aside type="caution">
これは、すでにプロジェクトにアクセスできるグループに値を付与するだけです。プロジェクトへのアクセスがないグループに `row_access.region` を追加しても、そのグループにプロジェクトへのアクセスも付与されるまで、何も付与されません。
</Aside>

### 保存前のプレビュー

行アクセスは、変更を確定する前に、その意味を示します。

- **プレビュー表示ユーザー**フッターには、グループがテーブルの全行のうち何行を表示できるかと、実際の行のサンプルが表示されます。グリッドで任意のグループを選ぶとプレビューできます。プレビューは保存後に更新されます。
- 保存前に、行アクセスは注意すべき点を警告します。何もチェックされていないグループがあり、**Everyone else** の設定ではそのグループがすべての行を表示するのか、まったく表示しないのか。プロジェクトへのアクセスを持つが、どのグループの付与にも含まれていないメンバー。その列の値が空白（`NULL`）で、どのグループにも付与されていない行。

### 制限されたメンバーに表示される内容

制限されたメンバーが名前でテーブルを読み取る場合は、どこでも自分の行だけが取得されます。テーブルエクスプローラーのグリッド、列ファセット、ダウンロード、テーブルのダウンロードダイアログ、閲覧者として読み取るアプリやツール、ダッシュボードが対象です。テーブルエクスプローラーでは、表示しているグリッドが付与によってフィルターされている場合、ツールバーに**アクセス権により行が制限されています**と表示され、フィルターされるダウンロードを開始すると「Rows limited by your access.」と表示されます。すべての行を読み取るアーキテクトには、どちらの通知も表示されません。

### 行アクセスとご自身で記述するクエリ

行アクセスは、定義されているテーブルをフィルターすることで、グループが表示できる行を制限します。ご自身で記述したクエリには、そのフィルターを適用できる単一のテーブルがありません。クエリは、任意の数のテーブルを結合、統合、入れ子にできるためです。そのため、行を制限するプロジェクトでは、PlaidCloudは、何の検証も受けていない行を返すのではなく、呼び出し元が指定したクエリの実行を拒否します。

これは、ご自身のSQLによる読み取り、ご自身のSQLの結果のファイルや別のデータベースへのエクスポート、ファンアウトステップの「Test row 1」プレビューへの行条件の入力に適用されます。アプリやツールがデータを読み取る通常の方法である、名前によるテーブルの読み取りには適用**されません**。それらは付与を適用し、閲覧者が表示できる行を返します。単一テーブルの単純なクエリとして記述された列ファセットも、名前による読み取りとして扱われるため、拒否されずにメンバー自身の値が返されます。

拒否されたユーザーには、どのプロジェクトだったかが通知され、名前による読み取り方法が案内されます。プロジェクトのアーキテクトは、制限された列のすべての値を自分自身に付与できるため、クエリをそのまま実行し、その結果を任意の形式でエクスポートできます。

スプレッドシートのインポートは、それ自体ではご自身で記述したクエリではありません。通常のファイルインポートは制限されたデータをまったく読み取らず、アップロードしたファイルからプロジェクト自身の新しいテーブルを作成するだけなので、行アクセスの影響を受けません。例外は、データの射影を呼び出し元が指定するインポートです。列ごとの式や、動的なExcelマッピングが該当します。対話型のインポート画面では、これらは上記の自由形式のSQLの画面と同じように拒否され、プロジェクトのアーキテクトが必要になります。呼び出し元が指定した射影は、別のテーブルを読み取る可能性があるためです。ワークフローから実行されるインポートは、プロジェクト自身のサービスIDとして実行されるため、どちらの場合も影響を受けません。

<Aside type="caution">
プロジェクトで最初の列を制限すると、そのプロジェクトを使用するすべてのユーザーに対してこの動作が変わります。そのプロジェクトのPanelアプリ、ノートブック、連携が独自のSQLを組み立ててデータを読み取っている場合は、制限する前に、テーブルを名前で読み取るように切り替えてください。そうしないと、アーキテクト以外のすべてのユーザーで動作しなくなります。
</Aside>

### 行アクセスとデータエディター

データエディターはテーブルを直接読み書きするため、行アクセスは両方の側面に適用されます。

制限されたテーブルをデータエディターで開くと、セキュリティグループに付与された行だけが表示されます。これはダッシュボードでも適用されるのと同じフィルターで、制限された列がグリッドに表示されている列に含まれていない場合でも適用されます。

編集内容の保存には、プロジェクトの**アーキテクト**が必要です。保存はテーブルの行を読み取るのではなくまとめて置き換え、行ごとにフィルターされません。そのため、制限されたテーブルでのデータ編集は、読み取りではなく作成操作として扱われ、アーキテクトでないユーザーには、アーキテクトが必要であることが通知されます。制限された列を持たないテーブルは従来どおり編集でき、行を制限しないプロジェクトも同様です。

### 制限されたテーブルへのデータの読み込み

行アクセスで表示できる行が制限されている場合、Pythonクライアント（`PlaidConnection`）で制限されたテーブルにDataFrameを書き込む、またはクリアする操作や、REST APIでレコードを保存する、またはクリアする操作は、自分の行だけを対象に動作します。テーブルのデータを置き換えると、表示できる行だけが置き換えられ、クリアするとそれらの行だけがクリアされ、追加すると行が追加されます。それ以外の行はそのまま残ります。

アクセス権の範囲外の行を含む読み込みは、何かが変更される前に拒否され、エラーには、アクセス権の範囲外の各値と、その値を持つ行数が示されます。制限された列が含まれていない行は、その列が空白であるものとしてチェックされるため、アクセス権に空白の行が含まれていない限り拒否されます。列の型が変わる形でのデータの置き換えも拒否されます。その変更は、プロジェクトのアーキテクトに依頼してください。

プロジェクトのアーキテクト、付与がすべての行をカバーするメンバー、およびプロジェクトのサービスIDとして実行されるワークフローの実行は、従来どおりテーブル全体を書き込みます。制限された列のないテーブルは影響を受けません。

ユーザーがあらゆるテーブルに対して行うこれらの書き込みは、それぞれセキュリティログに記録されます。ワークフローの実行はそこには記録されません。

### 行数とテーブルサイズ

テーブルの行数とストレージサイズはテーブル全体を表すもので、表示できる行を表すものではありません。そのため、制限された閲覧者に、付与の範囲外にある行数が分かってしまいます。行を制限するプロジェクトでは、読み取りがフィルターされるユーザーには、プロジェクトのどのテーブルについても行数やサイズが表示されません。テーブルリスト、検索、テーブルの詳細、スナップショット、AIアシスタント、MCP経由で接続されたAIツールが対象です。これは、制限された列を持たないテーブルを含む、プロジェクト内のすべてのテーブルに適用されます。ホーム、プロジェクトリストと検索、プロジェクトの詳細にあるプロジェクト自体の合計の行数とサイズも、それらのユーザーには非表示になります。

ワークフローの実行履歴にも同じことが当てはまります。各実行とステップが記録した読み取り行数と書き込み行数もテーブル全体を表すため、同じユーザーにはそれらの数値が空白になります。ワークフローとステップの実行履歴、AIアシスタント、MCP経由で接続されたAIツールが対象です。それらのユーザーに対しては、検出事項自体がテーブル全体の件数が変化したことを示してしまうため、[Weave](/ja/guides/ai-assistant/weave-findings/)は、以前の実行と異なる行数や空の値についてステップをチェックしません。

プロジェクトのアーキテクトには従来どおり数値が表示され、行を制限しないプロジェクトのすべてのユーザーも同様です。

### メンバーが表示できる内容の確認

グループに付与された内容ではなく、特定の個人が表示できる内容を確認するには、**Identity → Member** を開き、メンバーを選択して、その**行アクセス**タブを開きます。**有効なアクセス**列には、制限されたすべてのプロジェクトと列について、そのメンバーが所属するすべてのグループを合わせて表示できる値が一覧表示されます。これには、SSOグループ属性による付与や、グループの付与に含まれる空白（`NULL`）の行も含まれます。プロジェクトのアーキテクトはすべての行を読み取るため、**すべての行を表示（アーキテクト）** と表示されます。これはPlaidCloud自体のクエリが適用するのと同じ結果であり、サポートの場面や、問題が報告される前に変更が意図したとおりに動作したことを確認する際に役立ちます。

### より分かりやすいエラー

行アクセスがアクションをブロックした場合（制限されたプロジェクトでご自身が記述したクエリ、アーキテクトなしでの編集、自動化、ディメンション、付与ソーステーブルの変更、上記で説明したその他のケース）、メッセージには、汎用的なエラーではなく、何が制限されているかと、次に何をすべきか（たとえば依頼先のアーキテクト）が示されます。

### 行アクセスの監査

列の制限や制限の解除、およびグループの付与の編集は、いずれもそのプロジェクトの[プロジェクトログ](/ja/get-started/tutorials/collaborate-versions-and-sharing/#プロジェクトログを読む)にエントリーを書き込み、誰がいつ変更したかが記録されます。プロジェクトで **Analyze → Projects → Log** を開くと確認できます。この記録を得るために、行アクセスで有効にする設定はありません。プロジェクトに対する他のすべての追跡対象の変更と同じように記録されます。

## デフォルトのセキュリティグループの設定


新しいメンバーの追加にかかる時間を短縮するには、デフォルトのセキュリティグループのセットを指定します。これにより、各ユーザーを手動で割り当てることなく、新しいメンバーにセキュリティグループの基本セットを付与できます。この設定は、新しいセキュリティグループを追加するときに、Security Groupウィンドウの下部にある「Assign to New Users by Default」というチェックボックスをオンにすることで利用できます。



## セキュリティ監査の実施


セキュリティ監査機能を使うと、すべてのメンバーとグループにわたるグループメンバーシップを確認できます。



**セキュリティ監査を実施するには：**


1. Identityを開きます
2. 「Security」タブを選択します
3. ドロップダウンメニューで「Security Group Audit」をクリックします

PlaidCloudのすべてのテーブルはCSV形式でエクスポートできるため、グループとメンバーの関連付けは、履歴の確認のためだけでなく、ちょっとしたオフラインでの閲覧のために、PlaidCloudの外部で確認することもできます。



**「Security Group Audit」フォームからエクスポートするには：**


1. Identityを開きます
2. 「Security」タブを選択します
3. ドロップダウンメニューで「Security Group Audit」をクリックします
4. テーブルの「Username」の右端にある小さなアイコンをクリックします
5. 好みに応じて「Export CSV」または「Export XLXS」をクリックします

## 利用可能な権限設定の表示


ワークスペースで使用される各アプリケーションには、それぞれ利用可能な権限があります。セキュリティグループの権限は、これらのアプリケーションの権限に基づいています。


各アプリケーションで利用可能な権限の完全なリストは、Security Binで確認できます。



**Security Binにアクセスするには：**


1. Identityを開きます
2. 「Security」を選択します
3. ドロップダウンメニューで「Security Bins」をクリックします

各アプリケーションの詳細なセキュリティ設定を表示するには、左端のタグアイコンを選択します。



ここで確認できる利用可能なセキュリティ設定の情報は、参考情報です。権限の管理について詳しくは、上記のセキュリティグループの管理セクションを参照してください。
