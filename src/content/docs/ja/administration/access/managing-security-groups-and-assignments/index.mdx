PlaidCloud のセキュリティとアクセス管理はシンプルです。メンバーは、所属するグループに基づいてアクセスが許可または拒否されます。メンバーのセキュリティの関連付けは、簡単に追加や変更ができます。

<Aside>各ワークスペースで作成できるセキュリティグループの数に上限はありませんが、セキュリティ管理を容易にするため、数を最小限に抑えることをお勧めします。</Aside>



## セキュリティグループの管理


セキュリティグループは、追加、更新、削除ができます。



**セキュリティグループを管理するには:**


1. ID を開きます
2. レールの **セキュリティグループ** を選択します（既存のグループの一覧が表示されます）
3. グループを追加するには、**New group** をクリックします
4. グループの権限を編集するには、一番左のアイコンをクリックします

**グループのメンバーを管理するには:**


1. ID を開きます
2. レールの **セキュリティグループ** を選択します
3. メンバーアイコンをクリックします
4. グループに所属させるメンバーにチェックを入れ、所属させないメンバーのチェックを外します。フィルターボックスで人を検索できます。[ピッカーを使った割り当て](#ピッカーを使った割り当て)を参照してください
5. **割り当てを更新** をクリックします

<Aside>誰も割り当てずに保存しても何も変更されず、その旨が通知されます。グループの権限を全員から取り除くには、メンバーシップを空にするのではなく、権限を削除するか、グループを削除してください。</Aside>

<Aside>グループに[行アクセス](#行アクセスの管理)で行が付与されている場合、メンバーシップの変更は約 1 分以内にダッシュボードに反映されます。追加した人にはダッシュボードでグループの行が表示され、削除した人には表示されなくなります。メンバーの無効化や削除、およびグループの削除も、同じように反映されます。</Aside>

<Aside type="caution">自分で付与できない権限は、グループの権限マトリックスを保存するときには変更されず、マトリックスにも表示されません。変更が必要な場合は、その権限を持つ人に依頼してください。マトリックスで編集できるのは、自分が管理している権限だけです。</Aside>

<Aside type="caution">メンバーをグループに追加したり、メンバーのグループを選択したりできるのは、そのグループが付与するすべての権限を自分が持っている場合です。アーキテクトとして誰かを招待する場合も同様です。ワークスペース管理者には、この制限はありません。</Aside>

## ピッカーを使った割り当て

人、グループ、その他の項目にアクセスを付与するあらゆる場面で、以前の 2 つのリストに代わって 1 つのチェックリストが使われます。すべての行にチェックボックスがあり、チェックを入れた行が割り当て対象です。これは、グループのメンバー、メンバーのセキュリティグループ、アカウントのメンバー、グループ、エージェント、所有者、接続のアクセス、配布リストのワークスペースメンバー、Weave 準備状況セットのワークフローを設定するために使用します。

- **フィルター。** フィルターボックスに入力して、リストを絞り込みます。一致は部分一致で、大文字と小文字は区別されないため、`smith` と入力すると、それを含むすべての名前またはメールアドレスが見つかり、`@example.com` と入力すると、そのドメインのすべてのユーザーが見つかります。複数の単語を入力すると、そのすべてに一致する行のみが表示されます。
- **メールアドレスの一覧を貼り付け。** スペース、カンマ、セミコロン、改行で区切った複数のメールアドレスを貼り付けると、リストにはちょうどその人たちだけが表示されます。`@example.com` のようなドメイン全体を混ぜることもできます。フィルターの下の行には、貼り付けたエントリのうち一致した数が表示され、見つからなかったものが一覧表示されます。**割り当て** に続けて一致した件数を押すと、一致したすべての人にワンクリックでチェックが入ります。
- **すべて、割り当て済み、未割り当て。** リストの上にある 3 つのボタンで、すべて、割り当て済みのみ、未割り当てのみを切り替えます。それぞれ件数が表示され、フィルターと組み合わせて使用できます。
- **Assign all shown と Unassign all shown。** これらは、フィルターとビューで現在表示されているすべての行にチェックを入れる、またはチェックを外します。非表示の行には影響しません。リストの上の行には、合計のうち何行が表示されているかが示されます。
- **Will add と Will remove。** 保存ボタンをクリックするまで、何も保存されません。チェックを入れた行には **Will add** のピルが表示され、チェックを外した行には **Will remove** が表示されます。サマリーには、たとえば `12 assigned · +3 to add · −1 to remove` のように表示されます。**Undo changes** は、ウィンドウを開いたときの状態にすべてを戻します。
- **変更があった場合のみ保存。** **割り当てを更新**、**メンバーを更新**、**グループを更新** などの保存ボタンは、変更を行ったときにのみ使用できます。
- **キーボード。** **スペース** で、選択した行にチェックを入れる、またはチェックを外します。フィルターボックスでの **Enter** は保存しないため、検索中に押してもアクセスが変更されることはありません。

アクセス権を持つ人は確認できるが変更はできない場合（たとえば、自分が所有していない接続）、ピッカーは読み取り専用になります。すでに割り当てられている人だけが一覧表示され、それを変更するチェックボックスやボタンは表示されません。

## 行アクセスの管理

行アクセスは、1 つの列の値に基づいて、セキュリティグループがテーブルのどの行を見られるかを制限します。たとえば、`region` 列でアクセスを制限し、`East` と `Central` を付与されたグループは、それらの値を持つ行のみに制限できます。プロジェクトと列に関するすべての操作（列の選択、値の取得元の選択、どのグループに何を見せるかの決定）は、1 つの画面で行い、保存するとすぐに有効になります。

行アクセスの設定と変更には、プロジェクトのアーキテクトまたはテナント管理者が必要です。それ以外のユーザーがプロジェクトの **セキュリティ** タブを開くと、行アクセスはアーキテクト専用であると通知され、以下の入口は表示されません。

### 行アクセスを開く

すべての入口は、同じ行アクセス画面を開きます。

- **テーブルエクスプローラーのツールバー** には、**行アクセス** ボタンがあり、テーブルがすでに行を制限している場合はバッジが表示されます。制限された最初の列がある場合はそこで開き、テーブルの他の任意の列に切り替えることもできます。
- **列のファセットメニュー** には、その列で行アクセスを開く **この列で行を制限…** があります。すでに行を制限している列では、この項目は **この列で行を制限中 - 編集…** と表示されます。
- **プロジェクトの セキュリティ タブ** には、プロジェクトで制限されているすべての列が、適用されるテーブル、付与を持つグループ、**同期** の状態とともに一覧表示されます。列を選択して編集するか、**列を制限…** をクリックして新しく開始します。テーブルを選び、次に列を選びます。すでに行を制限している列には、鍵のマークが付きます。
- **ID → メンバー**（メンバーの **行アクセス** タブ）と、**ID → セキュリティ → セキュリティグループ**（グループの行アクセスのサマリー）。**行アクセスを開く**（または **編集**）は選択した列を開き、**追加** はその行のプロジェクトで別の列を制限します。

列で開いた場合、画面はその列のままです。**列を制限…** または **追加** で開いた場合は、列を選択できます。

### 行アクセスのグリッド

列でテーブルを制限するには、次の手順を実行します。

1. 上記のいずれかの入口から行アクセスを開き、列を指定せずに開いた場合は列を選択します。ピッカーには、自由入力ではなく、テーブルの実際の列が表示されます。
2. **値のソース** を選択します。**列**（テーブルの列の個別の値）、**ディメンション**（ディメンションのノード）、**リスト**（入力した値）のいずれかです。値の型は、列のデータ型に従います。
3. セキュリティグループごとに、そのグループが見られる値にチェックを入れます。グリッドには、プロジェクトへのアクセス権を持つグループと、その列にすでに付与を持っているグループが一覧表示されます。
4. **Everyone else** を **sees all rows** または **sees no rows** に設定します。これは、グリッドでチェックが 1 つもないグループすべてに適用されます。
5. **保存** をクリックします。

保存はすぐに有効になります。PlaidCloud 自身のクエリには変更が即座に反映され、Superset ダッシュボードには約 1 分以内に反映されます。適用するための別の手順はなく、**保存** が確認のために止まるのは、付与がソースにもうない値を保持している場合のみです（後述）。画面の同期状況には、変更がどこまで反映されたかが表示されます。[ダッシュボードの同期の維持](#ダッシュボードの同期の維持)を参照してください。

グリッドは、次のような詳細も処理します。

- **多数の値。** 値は並べ替えられます。列の値がグリッドに収まりきらない場合、グリッドには「More values than fit here — type to search.」（収まりきらない値があります。入力して検索してください。）と表示され、フィルターボックスで列全体が検索されます。グループがすでに保持している値はすべて保持されます。
- **ソースにもうない値。** グループに付与された値は、そのソースから失われても、グリッドに残ります。つまり、テーブルのどの行にもその値がなくなった、ディメンションにそのメンバーがなくなった、またはリストにその値がなくなった場合です。その列ヘッダーには警告アイコンが付き、ポインターを合わせると理由が表示されます。**すべて選択**、**選択を反転**、**貼り付け** は、そのような値を各グループが保持しているままにします。チェックを外さない限り、付与から何も削除されません。グループがまだそのような値を保持している状態で **保存** をクリックすると、行アクセスは **Values No Longer in the Source** にグループと値を示して確認します。**Keep and Save** はそのまま保存し、**Remove and Save** は先にすべてのグループの付与からそれらを削除し、確認を閉じると何も保存されません。削除するとグループにチェックされた値が 1 つもなくなる場合、確認には、**Everyone else** に従って、そのグループがすべての行を見られるようになるか、1 行も見られなくなるかが示されます。まだ保存していないチェックは、その値とともに消えます。列の値がグリッドに収まりきらない場合や、そのテーブルがまだ構築されていない場合、行アクセスはテーブルにない値を判断できないため、付与されたすべての値を、マークを付けずに保持します。
- **空白の値。** **空白の値 — 付与のあるすべてのグループに表示** チェックボックス 1 つで、列に値がない行の扱いが決まります。チェックを入れると、その列に何らかの付与があるすべてのグループに、それらの行が表示されます。
- **まだ構築されていないテーブル** には、空のリストの代わりに **先にこのテーブルを構築してください（作成するワークフローを実行します）** と表示されます。
- **保存は、画面上の値を待ちます。** 値の読み込み中（値のソース、ディメンション、テーブルを切り替えた後、またはテンプレートを適用した後）は、**保存** は無効になり、ツールチップに「Save is available once this source's values load.」（このソースの値が読み込まれると保存できます。）と表示されます。読み込みに失敗した場合、グリッドはその旨を表示し、ソースを選び直すよう求めます。読み込みが成功するまで、何も保存されません。

### 1 つの列名、すべてのテーブル

制限は、単一のテーブルではなく、プロジェクト内の列の*名前*に属します。`region` が行を制限すると、プロジェクト内の `region` という名前の列を持つすべてのテーブルが、PlaidCloud 自身のクエリでもダッシュボードでも、それによってフィルターされます。グリッドの **Applies to** リストには、それらのテーブルが表示されます。列名で決まるため、読み取り専用です。後から同じ列を持つテーブルを追加した場合は、公開された時点で自動的に対象になります。

プロジェクト内のどのテーブルにもその名前の列がない場合、ウィンドウには **Applies to 0 tables** の表示に加えて、テーブルができるまで、その制限がどのダッシュボードもフィルターしないという警告が表示されます。テーブルに列を追加するか、列名を修正すると、警告は消えます。

<Aside type="caution">
**列名は、大文字と小文字、空白を含めて、完全に一致する必要があります。** `Region` と `region` は別の名前で、`region` と末尾にスペースのある `region ` も別の名前です。ピッカーには実際の列名のみが表示されるため、これが問題になるのは主に、他の場所で列の名前が変更された場合です。その場合、行アクセスは、何も制限しないまま黙って処理するのではなく、警告を表示し、見つかった最も近い列を示します。
</Aside>

<Aside type="caution">
**行を制限するテーブルを公開すると、同じ手順でそのダッシュボードのフィルターも設定されます。** ダッシュボードは、公開されたレポート用ビューを通じてテーブルを読み取ります。そのため、制限された列を持つテーブルを公開または再公開すると、PlaidCloud は公開の完了前にそのテーブルのダッシュボードフィルターを登録します。登録できない場合、公開は拒否され、その試行で作成されたものはすべてロールバックされるため、制限されたテーブルがフィルターなしでダッシュボードに残ることはありません。ビューのクエリは制限された列の名前を変更したり派生させたりできるため、行を制限するプロジェクトでは*ビュー*を公開できません。[テーブルの公開](/ja/guides/data/publish/)を参照してください。
</Aside>

### 制限の解除

グリッドの **制限を解除** は、インラインの確認の後で制限を削除します。「Stop restricting rows by ‘region’? Every group's grant on it is removed and everyone sees its rows.」（‘region’ による行の制限を解除しますか？ この列に対するすべてのグループの付与が削除され、全員がその行を見られるようになります。）行アクセスは続けて「Rows in ‘region’ are no longer restricted.」（‘region’ の行はもう制限されていません。）と確認します。その列の Superset データセットも一緒に削除されますが、チャートがまだそれを使用している場合は削除されません。その場合、行アクセスはデータセットが残ること、およびいくつのチャートが使用しているかを表示します。

行を制限している間は、列の名前変更や削除はできません。アーキテクトには、まず行アクセスで制限を解除するよう通知されます。それ以外のユーザーには、プロジェクトのアーキテクトに依頼するよう通知されます。

### 行を制限するプロジェクトを変更できるユーザー

プロジェクトのワークフロー、ステップ、ユーザー定義関数は、プロジェクト自身のサービス ID として実行され、すべての行を読み取ります。それらを変更できる人は、自分に付与されていない行を、自分が読み取れるテーブルにコピーするステップを作れてしまいます。そのため、プロジェクトで行を制限すると、プロジェクトの動作を誰が変更できるかも制限されます。プロジェクトが少なくとも 1 つの列を制限すると、次のようになります。

- **自動化はアーキテクト専用です。** ワークフロー、ステップ、ユーザー定義関数、スケジュール、ワークフロー変数とプロジェクト変数、通知メールテンプレートを変更できるのは、プロジェクトのアーキテクトとテナント管理者のみです。同じ理由で、ワークフローバンドルのインポート、Alteryx ワークフローの変換、プロジェクトへのインポート、コピー、復元、プロジェクトの接続環境、デフォルトのドキュメントアカウント、ERP 転記モードの変更も、アーキテクトとテナント管理者のみが行えます。それ以外のユーザーも、プロジェクトのワークフローを実行することはできます。**開始**、**停止**、**再開**、**選択したステップを実行** は引き続き使用できます。ステップエディター、ワークフローの作成コントロール、UDF エディター、スケジュールフォームは、それらのユーザーには読み取り専用で開き、依頼先のアーキテクトを示すバナーが表示されます。「This project restricts rows, so only its Architects can change workflows, steps, UDFs, schedules, variables and notify templates. You can still run them.」（このプロジェクトは行を制限しているため、ワークフロー、ステップ、UDF、スケジュール、変数、通知テンプレートを変更できるのは、そのアーキテクトのみです。実行することは引き続き可能です。）
- **制限された列が読み取るディメンションは、アーキテクト専用です。** どのユーザーにどの行を見せるかを決めるディメンション（制限された列の値のソース）は、プロジェクトのアーキテクトまたはテナント管理者と、プロジェクト自身のワークフローのみが変更できます。これには、ノードの追加、移動、名前変更、コピー、クリア、ロード、復元、およびディメンション自体が含まれます。それ以外のユーザーには、「This dimension decides who sees which rows of ‘region’, so only a project Architect can change it.」（このディメンションは ‘region’ のどの行を誰に見せるかを決めるため、変更できるのはプロジェクトのアーキテクトのみです。）と通知されます。どの制限にも読み取られないディメンションは影響を受けません。
- **付与のソーステーブルは、アーキテクト専用です。** 列の[付与のソース](#付与のソーステーブルへのバインド)としてバインドされたテーブルは、行の変更や削除ができるのは、プロジェクトのアーキテクト、テナント管理者、またはプロジェクトのワークフローのみです。データエディター、インポート、コネクターのロード、API のいずれを通じた場合も同様です。
- **プロジェクトのコピーは、アーキテクト専用です。** コピーには「This copy is not row-restricted.」（このコピーは行が制限されていません。）と表示され、新しいプロジェクトには、設定するまで制限がありません。
- **以前のバージョンの復元も、他の変更と同じ扱いです。** プロジェクト自身の設定、または上記のディメンションを復元するには、プロジェクトのアーキテクトが必要です。復元は常に、そのバージョンが属する項目に適用されるため、これを回避するために別のプロジェクトを指定することはできません。[バージョン履歴](/ja/guides/projects/managing-projects/#バージョン履歴)を参照してください。
- **制限されたテーブルのデータ編集** には、[行アクセスとデータエディター](#行アクセスとデータエディター)で説明されているように、アーキテクトが必要です。
- **制限されたテーブルへの DataFrame の書き込み、レコードの保存、クリア** は、すべての行が見える場合を除き、自分の行のみを変更します。詳細は[制限されたテーブルへのデータのロード](#制限されたテーブルへのデータのロード)を参照してください。
- **制限されたテーブルのインポート、コピー、ブランチの切り替え、復元、削除は、** 自分に見えない行がテーブルに含まれている間は拒否されます。詳細は[制限されたテーブルへのデータのロード](#制限されたテーブルへのデータのロード)を参照してください。

プロジェクトで最初の列を制限する前に、行アクセスは、これが誰に影響するかを通知します。「Restricting rows here means only Architects can change this project's workflows, steps, UDFs, schedules and notify templates. N members can change them today; they will still be able to run them.」（ここで行を制限すると、このプロジェクトのワークフロー、ステップ、UDF、スケジュール、通知テンプレートを変更できるのはアーキテクトのみになります。現在、N 人のメンバーがそれらを変更できます。今後も、それらを実行することはできます。）

実行は、スケジュールされたものも含めて、これまでとまったく同じように動作します。実行はプロジェクトのサービス ID として動作するためです。実行によって生成されるものは、アーキテクトが設計した内容に従います。制限された列を含まない出力テーブル、エクスポートファイル、通知メール、ログの行は、それを読む人に対してフィルターされません。

**実行の開始時に指定する値。** ワークフローを実行できる人は誰でも、その変数に独自の値を指定して開始できます。[アプリランナー](/ja/guides/workflows/use-converted-alteryx-apps/#app-runner-フロントエンド)はフォームの回答を使ってこれを行い、API と AI ツールでも行えます。これらの値はその実行にのみ有効で、ワークフローに保存されることはなく、他の実行、エクスポート、閲覧者に見られることもありません。実行はサービス ID として行われるため、これらの値によって、その実行が読み取るものや書き込むものが変わる可能性があります。そのため、ワークフローを実行する権限は、信頼できる人にのみ付与してください。

**行を制限しないプロジェクト。** これらのルールは、プロジェクトが列を制限した時点で初めて有効になります。何も制限していないプロジェクトでは、プロジェクトの自動化を変更できる人は誰でも、プロジェクトのサービス ID として実行されてプロジェクトのアクセスを変更し、自分自身をアーキテクトの 1 人にするステップやユーザー定義関数を作成できます。これは設計上の仕様です。そのようなプロジェクトは、行の分離を約束していません。そこでの作成権限は、アーキテクトとして信頼できる人に限定するか、列を制限してください。

### ダッシュボードの同期の維持

行アクセスは、変更がダッシュボードに届くまでのどの段階にあるかを、グリッドと、プロジェクトの セキュリティ タブの **同期** 列に表示します。

| ステータス | 意味 |
|---|---|
| **待機中** | 変更が保存され、ダッシュボードへ送信される途中です。通常は約 1 分以内に完了します。 |
| **再試行中** | 送信に失敗し、再試行されています。失敗の理由がステータスの横に表示され、すぐに再送信するための **再試行** があります。 |
| **未適用** | プロジェクトの制限が、まだダッシュボードに送信されていません。 |
| **適用済み** | 制限をダッシュボードに送信する直近の試行が成功しました。 |
| **ダッシュボードと同期済み** | 行アクセスは、ダッシュボードが適用している内容と、自身が書き込む内容を比較し、一致しています。 |
| **ダッシュボードと差異あり** | ダッシュボードが、行アクセスが書き込む内容を適用していません。Superset でルールが変更または削除された、またはテーブルの公開ビューを確認できない場合です。 |
| **エラー** | 制限の送信に失敗しました。理由がステータスの横に表示されます。 |

変更が **適用済み** に到達すると、グリッドはそれをダッシュボードと照合し、**ダッシュボードと同期済み** または **ダッシュボードと差異あり** に移行します。**ダッシュボードと差異あり** と **エラー** のどちらにも **再試行** があり、プロジェクトの制限を再送信します。ステータスをまったく読み取れない場合、グリッドには「Couldn't check sync status.」（同期ステータスを確認できませんでした。）と表示されます。

1 つのテーブルが原因の **エラー** では、そのテーブルが示され、対処法が表示されます。たとえば、制限された列なしで公開されたテーブル（「Republish or unpublish it.」（再公開するか、公開を取り消してください。））や、制限された列を持つが公開されていないテーブルです。後者は、公開されるまでダッシュボードでフィルターできません。ステータスは **エラー** のままで、そのテーブルを公開するか、代わりに公開済みのテーブルで列を制限するまで、未公開のテーブルが示されます。このようなテーブルが、プロジェクトの残りの処理を妨げることはなく、他のすべてのテーブルは同期が保たれます。

ダッシュボードは、PlaidCloud 自身のクエリと同じ付与に従います。

- **その列を持つ公開済みのテーブルはすべてフィルターされます。** 制限を設定したときに見ていたテーブルだけではありません。
- **一部の値のみを付与されたグループは、他のすべてのユーザーがすべての行を見られる場合でもフィルターされます。** ダッシュボードのデータセットが存在するすべてのテーブルが対象です。
- **プロジェクトのアーキテクトは、すべての行を見られます。** ダッシュボードでも、テーブルエクスプローラーや PlaidCloud のその他の場所と同様です。これは、プロジェクトのアーキテクトグループと、個々のメンバーと共有されているプロジェクトのアーキテクトに適用されます。アーキテクトアクセスを取り消すと、ダッシュボードにはすぐに反映されます。メンバーのロールの変更、メンバーまたはそのグループのプロジェクトからの削除、プロジェクトのアクセスタイプの変更、以前のプロジェクトバージョンの復元、グループの削除のいずれの場合も同様です。
- **セキュリティグループのメンバーシップの変更は、自動的にダッシュボードに反映されます。** PlaidCloud でグループに人を追加または削除した場合、メンバーを無効化または削除した場合、グループを削除した場合、デフォルトのセキュリティグループに参加する新しいメンバーを追加した場合、その人がダッシュボードで見られる内容は、そのグループに値を付与しているすべてのプロジェクトで、行アクセスを開き直さなくても約 1 分以内に更新されます。PlaidCloud の外部、つまり Keycloak で直接、またはサインイン時にシングルサインオンによって誰かがグループに配置されるといったメンバーシップの変更は、保存や再試行をしなくても約 15 分以内にダッシュボードに反映されます。

### ディメンションの付与

値のソースとして **ディメンション** を使用する場合は、ノードにチェックを入れると、その配下のすべてが付与されます。付与はディメンションに追従します。チェックを入れたノードの下に追加されたメンバーは、ディメンションが保存された後の次の同期で、そのグループに付与されます。その配下から移動または削除されたメンバーは、付与されなくなります。グリッドを開き直す必要はありません。開き直したときには、チェックを入れたノードは、再びチェックされた状態で表示されます。

ノードを通じてではなく、単独でチェックを入れたメンバーは、ディメンションから削除されても付与されたままで、グリッドには、ソースにもうない値としてマークされます。

チェックを入れたノードの配下にあるものからチェックを外すと、そのノードのチェックも外れ、グループにはまだチェックされているメンバーだけが残ります。そのメンバーに再度チェックを入れても、ノードには再びチェックされません。そのためには、ノード自体のチェックボックスをクリックしてください。**貼り付け**、**すべて選択**、**選択を反転** は、ノードではなく、メンバーにチェックを入れます。

名前が行アクセスの値として使用できないディメンションメンバーは、保存するときに、その名前が示されて拒否されます。そのようなメンバーが後から現れた場合、その行は誰にも付与されず、同期ステータスにそのメンバーが示されます。「Dimension ‘…’ member ‘…’ cannot be used as a row access value, so its rows are not granted. Rename it in the dimension.」（ディメンション ‘…’ のメンバー ‘…’ は行アクセスの値として使用できないため、その行は付与されません。ディメンションで名前を変更してください。）

### 付与のソーステーブルへのバインド

値を手動でチェックする代わりに、制限された列を、答えをすでに保持しているソーステーブル（グループごとに 1 行で、そのグループが見られる値を持つテーブル）に関連付けることができます。まずグリッドで列を制限し、次に、列、ソーステーブル、ソーステーブルのグループ列と値の列を指定した [**行アクセスを設定**](/ja/reference/workflow-steps/tables/table-set-row-access/)ワークフローステップを追加します。ステップの最初の実行で、列がそのテーブルにバインドされます。列の手動で設定された付与はクリアされ、その付与はテーブルの行から設定されます。

バインドされると、その列は**ソース所有**になります。行アクセスのグリッドでは、ソーステーブルを示すバッジとともにロックされた状態で表示され、**バインディングを削除** をクリックするまで、付与の手動編集は拒否されます。

ステップを実行するたびに、ソーステーブルが再読み込みされ、付与が再適用されます。そのテーブルをロードまたは更新するワークフローの後にスケジュールしておくと、ソースデータでグループが追加、削除、または再割り当てされた場合に、グリッドを手動で編集しなくても、次の実行で行アクセスに反映されます。

ソーステーブルが誰に何を見せるかを決めるため、その行の変更やテーブルの削除ができるのは、プロジェクトのアーキテクト、テナント管理者、またはプロジェクト自身のワークフローのみです。それ以外のユーザーには、「This table supplies the row access grants for ‘region’, so only a project Architect can change its rows or delete it.」（このテーブルは ‘region’ の行アクセスの付与を提供するため、その行の変更や削除ができるのは、プロジェクトのアーキテクトのみです。）と通知されます。

### 制限テンプレート

同じ値のソース、値の型、空白値の設定など、再利用したい制限の形を作成した場合は、一度保存しておけば、列ごとに作り直すことなく、必要な場所に適用できます。

- **テンプレートとして保存…** は、開いている行アクセス画面から、現在の列の形を、名前を付けたテナントレベルのテンプレートとして保存します。保存されるのは形のみで、付与は含まれません。
- **テンプレートを適用** は、別のプロジェクトの列で、テンプレートの形からその列を開始します。すべてのグループの付与は空の状態で、入力できるようになっています。

テンプレートの保存と適用は、どのプロジェクトのアーキテクトでも行えます。テンプレートはテナント全体で共有されるため、名前の変更（**名前の変更…**）と削除（**削除**）にはテナント管理者が必要です。テンプレートを削除しても、それが適用された列は、制限されたままです。

<Aside type="note">
テンプレートはコピーであり、リンクではありません。後からテンプレートを編集しても、すでにそれを適用した列は変更されません。後の改訂内容に列を更新するには、テンプレートをもう一度適用してください。
</Aside>

### SSO グループ属性からの付与

列は、PlaidCloud ではなく、ID プロバイダーから付与を受け取ることもできます。プロジェクトのアーキテクトは、行アクセスで **Accept row-access grants from SSO group attributes** を有効にして、列をオプトインします。

有効にすると、セキュリティグループの Keycloak 属性 `row_access.<column>` が、その列を通じてそのグループが見られる値を設定します。Keycloak でグループに属性を設定すると、PlaidCloud は、プロジェクトへのアクセス権をすでに持つグループに対して、それを自動的に取り込みます。行アクセス自体で設定する項目は他にありません。付与は、PlaidCloud 自身のクエリと Superset ダッシュボードの両方で同期が保たれます。

<Aside type="caution">
これは、すでにプロジェクトにアクセスできるグループにのみ値を付与します。プロジェクトへのアクセス権がないグループに `row_access.region` を追加しても、そのグループにもプロジェクトへのアクセスが付与されるまでは、何も付与されません。
</Aside>

### 保存前のプレビュー

行アクセスは、変更を確定する前に、それが何を意味するかを示します。

- **プレビュー表示ユーザー…** フッターには、グループが合計のうち何行を見られるかと、その行のサンプルが表示されます。グリッドで任意のグループを選ぶと、プレビューできます。プレビューは、保存後に更新されます。
- 保存する前に、行アクセスは、確認が必要な点について警告します。何もチェックされていないグループ（**Everyone else** の設定に応じて、すべての行を見られるのか、1 行も見られないのか）、プロジェクトへのアクセス権があるにもかかわらず、どのグループの付与にも含まれていないメンバー、およびその列の値が空白（`NULL`）で、どのグループにも付与されていない行です。

### 制限されたメンバーに見えるもの

制限されたメンバーが名前でテーブルを読み取る場所では、どこでも自分の行のみが取得されます。具体的には、テーブルエクスプローラーのグリッド、列のファセット、ダウンロード、テーブルのダウンロードダイアログ、閲覧者として読み取るアプリやツール、ダッシュボードです。テーブルエクスプローラーは、表示しているグリッドが自分の付与によってフィルターされている場合、ツールバーに **アクセス権により行が制限されています** を表示し、フィルターされるダウンロードを開始すると、「Rows limited by your access.」（アクセス権により行が制限されています。）と表示されます。すべての行を読み取るアーキテクトには、どちらの通知も表示されません。

### 行アクセスと自分で作成するクエリ

行アクセスによって行が制限されている場合でも、プロジェクトのクエリ画面で独自の SQL クエリを実行して、付与で許可されている行をそのまま取得できます。結果は CSV、Excel、JSON にエクスポートでき、エクスポートにはそれらの行のみが含まれ、**アクセス権により行が制限されています** の通知が表示されます。プロジェクトのアーキテクトは、制限された列のあらゆる値を自分自身に付与できるため、すべての行を読み取り、通知は表示されません。

パーセント記号（`%`）を含む付与の値は、クエリ画面で付与された行を返し、そのようなクエリを CSV としてダウンロードすることもできます。

プロジェクトのアーキテクトでないメンバーには、次の操作は引き続き拒否されます。

- Snowflake または Databricks のプロジェクトウェアハウスで、独自の自由形式の SQL を実行する。
- Postgres 系のウェアハウスから、独自の SQL の結果をエクスポートする。
- 独自の SQL の結果を別のデータベースにエクスポートする。
- ファンアウトステップの「Test row 1」プレビューに行の条件を入力する。
- ガバナンス対象のテーブルを、以前のスナップショット時点で読み取る（タイムトラベル）。

拒否された人には、どのプロジェクトだったかが通知され、名前で読み取る方法が案内されます。名前でテーブルを読み取る方法は、アプリやツールがデータを読み取る通常の方法で、付与が適用され、閲覧者に権限のある行が返されます。単一のテーブルに対する単純なクエリとして記述された列ファセットも、名前で読み取られるため、拒否されずにメンバー自身の値が返されます。プロジェクトのアーキテクトは、これらのいずれも記述どおりに実行できます。

行アクセスはガバナンス対象の列でビューをフィルターするため、ビューはその列を元の名前のまま保持する必要があります。ガバナンス対象の列を削除または名前変更したビューは、フィルターされません。

スプレッドシートのインポートは、それ自体では、自分で作成したクエリではありません。通常のファイルのインポートは、制限されたデータをまったく読み取らず、アップロードしたファイルからプロジェクト自身の新しいテーブルを作成するだけなので、行アクセスの影響を受けません。例外は、データの射影が呼び出し元から指定されるインポート、つまり列ごとの式や動的な Excel マッピングです。対話型のインポート画面では、これらは上記の自由形式 SQL の対象と同じように拒否され、プロジェクトのアーキテクトが必要です。呼び出し元が指定する射影は、別のテーブルを読み取る可能性があるためです。ワークフローから実行されるインポートは、プロジェクト自身のサービス ID で実行されるため、どちらの場合も影響を受けません。

<Aside type="caution">
プロジェクトで最初の列を制限すると、それを使用するすべての人に対してこれが変わります。そのプロジェクトの Panel アプリ、ノートブック、連携が、Snowflake または Databricks のウェアハウスで独自の SQL を組み立てている場合、または Postgres 系のウェアハウスから独自のクエリ結果をエクスポートしている場合は、制限する前に、テーブルを名前で読み取る方式に切り替えてください。そうしないと、アーキテクトでないすべてのユーザーに対して動作しなくなります。
</Aside>

### 行アクセスとデータエディター

データエディターはテーブルを直接読み書きするため、行アクセスは両側に適用されます。

制限されたテーブルをデータエディターで開くと、セキュリティグループに付与された行のみが表示されます。これはダッシュボードでも同じフィルターが適用され、制限された列がグリッドに表示されている列の 1 つでない場合にも適用されます。

編集内容を保存するには、プロジェクトの **アーキテクト** が必要です。保存はテーブルの行を読み取るのではなく一括して置き換えるものであり、行ごとにフィルターされないため、制限されたテーブルのデータ編集は、読み取りではなく作成操作として扱われます。アーキテクトでない人には、それが必要であることが通知されます。制限された列を持たないテーブルは、これまでどおり編集でき、行を制限しないプロジェクトも同様です。

### 制限されたテーブルへのデータのロード

行アクセスによって表示される行が制限されている場合、Python クライアント（`PlaidConnection`）で DataFrame を制限されたテーブルに書き込んだりクリアしたり、REST API でレコードを保存したりクリアしたりする操作は、自分の行のみが対象になります。テーブルのデータを置き換えると見える行だけが置き換えられ、クリアするとそれらの行だけがクリアされ、追加すると行が追加されます。他のすべての行は、そのまま残ります。

アクセス権の範囲外の行を含むロードは、何かが変更される前に拒否され、エラーには、アクセス権の範囲外の各値と、その値を持つ行数が示されます。制限された列を省略した行は、その列が空白であるものとして確認されるため、アクセス権に空白の行が含まれていない限り、拒否されます。列の型が変わるようなデータの置き換えも拒否されます。その変更は、プロジェクトのアーキテクトに依頼してください。

プロジェクトのアーキテクト、付与がすべての行をカバーするメンバー、およびプロジェクトのサービス ID として実行されるワークフローの実行は、テーブル全体に書き込みます。制限された列を持たないテーブルは影響を受けません。

制限されたテーブル全体を置き換える、または削除するその他の操作は、自分に見えない行がテーブルに含まれている間は拒否され、何も変更されません。これには、テーブルへのファイルのインポート、別のプロジェクトからのテーブルのコピー、そのブランチの切り替えまたはマージ、アーカイブからの復元やプロジェクトの保持されたスナップショットの復元の一部としての復元、削除、削除後の復旧、およびテーブルを空にしてから再び埋めるその他の操作が含まれます。制限された列が空白の行は、アクセス権に空白の行が含まれていない限り、見えない行として扱われます。自分が作成した、自分の行のみを含むテーブルなど、すべての行が見えるテーブルは、置き換えや削除ができます。

人が行うこれらの書き込みは、拒否されたものも含めて、どのテーブルに対するものでも、セキュリティログに記録されます。ワークフローの実行は、そこには記録されません。

### 行数とテーブルサイズ

テーブルの行数とストレージサイズは、閲覧可能な行ではなく、テーブル全体を表すため、制限されたユーザーに、付与された範囲を超えて何行存在するかを知らせてしまいます。行を制限するプロジェクトでは、読み取りがフィルターされるすべてのユーザーに、プロジェクトのどのテーブルの行数やサイズも表示されません。これは、テーブル一覧、検索、テーブルの詳細、スナップショット、および MCP 経由で接続された AI アシスタントや AI ツールに適用されます。制限された列を持たないテーブルを含め、プロジェクト内のすべてのテーブルが対象です。ホーム、プロジェクト一覧と検索、プロジェクトの詳細にある合計行数やサイズなど、プロジェクト自身の合計も、そのユーザーには非表示になります。

ワークフローの実行履歴にも同じことが当てはまります。各実行とステップが記録した読み取り行数と書き込み行数も、テーブル全体を表すため、同じユーザーには、ワークフローとステップの実行履歴、および MCP 経由で接続された AI アシスタントや AI ツールで、これらの数値が空白になります。そのようなユーザーに対して、[Weave](/ja/guides/ai-assistant/weave-findings/) は、行数や空の値が以前の実行と異なるステップをチェックしません。検出事項自体が、テーブル全体の件数が動いたことを知らせてしまうためです。

プロジェクトのアーキテクトには、これまでどおり数値が表示され、行を制限しないプロジェクトでは全員に表示されます。

### メンバーに見えるものの確認

グループに付与されているものではなく、特定の人に何が見えるかを確認するには、**ID → メンバー** を開き、メンバーを選択して、その **行アクセス** タブを開きます。その **有効なアクセス** 列には、制限されたすべてのプロジェクトと列について、そのメンバーがすべてのグループを合わせて見られる値が一覧表示されます。SSO グループ属性からの付与や、グループの付与に含まれている場合の空白（`NULL`）の行も含まれます。プロジェクトのアーキテクトは、すべての行を読み取るため、**すべての行を表示（アーキテクト）** と表示されます。これは PlaidCloud 自身のクエリが適用するのと同じ答えであるため、サポートや、問題が報告される前に変更が意図どおりに機能したかを確認するのに便利です。

### わかりやすいエラー

行アクセスが操作をブロックする場合（制限されたプロジェクトで自分で作成したクエリ、アーキテクトなしでの編集、自動化、ディメンション、付与のソーステーブルの変更、上記のその他のケース）、メッセージには、一般的な失敗ではなく、何が制限されているか、および依頼先のアーキテクトなど、次に何をすべきかが示されます。

### 行アクセスは監査される

列の制限または制限解除、およびグループの付与の編集は、いずれもそのプロジェクトの[プロジェクトログ](/ja/get-started/tutorials/collaborate-versions-and-sharing/#プロジェクトログを読む)にエントリを書き込み、誰がいつ変更したかが記録されます。確認するには、プロジェクトで **Analyze → Projects → Log** を開きます。この記録を残すために、行アクセスで何かを有効にする必要はありません。プロジェクトに対する他のすべての追跡対象の変更と同じ方法で記録されます。

## デフォルトのセキュリティグループの設定


新しいメンバーを追加する時間を短縮するには、デフォルトのセキュリティグループのセットを指定します。これにより、各人を手動で割り当てなくても、新しいメンバーに基本となるセキュリティグループのセットが付与されます。この設定は、新しいセキュリティグループを追加するときに、セキュリティグループウィンドウの下部にある「新規ユーザーにデフォルトで割り当て」のチェックボックスにチェックを入れると利用できます。



## セキュリティ監査の実行


セキュリティ監査機能では、すべてのメンバーとグループにわたるグループのメンバーシップを確認できます。



**セキュリティ監査を実行するには:**


1. ID を開きます
2. レールの **セキュリティ** の下にある **Group audit** を選択します

PlaidCloud のすべてのテーブルは CSV ファイル形式でエクスポートできるため、グループとメンバーの関連付けは、履歴の確認のため、または単にオフラインで眺めるために、PlaidCloud の外部で確認できます。



**「Security Group Audit」フォームからエクスポートするには:**


1. ID を開きます
2. レールの **セキュリティ** の下にある **Group audit** を選択します
3. テーブルの「ユーザー名」の右端にある小さなアイコンをクリックします
4. 好みに応じて、「CSVのエクスポート」または「Export XLXS」をクリックします

## 利用可能な権限設定の表示


ワークスペースで使用される各アプリケーションには、それぞれ利用可能な権限があります。セキュリティグループの権限は、これらのアプリケーションの権限に基づいています。


各アプリケーションで利用可能な権限の完全な一覧は、Security Bin で確認できます。



**Security Bin にアクセスするには:**


1. ID を開きます
2. 「セキュリティ」を選択します
3. ドロップダウンメニューで「Security Bins」をクリックします

各アプリケーションの詳細なセキュリティ設定を表示するには、左端のタグアイコンを選択します。



この利用可能なセキュリティ設定の情報は、参照用です。権限の管理の詳細については、上記のセキュリティグループの管理のセクションを参照してください。
