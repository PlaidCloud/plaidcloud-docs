*約30分 · 準備状況のチェック、インポート、検証済みの実行*

1つの Alteryx ワークフローを PlaidCloud にエンドツーエンドで移行します。準備ができているかを確認し、インポートして変換し、問題なく変換された部分と確認が必要な部分を読み取り、実行します。これは自信をつけるための最初の移行であり、すべてを網羅するものではありません。内容をよく理解しているワークフローを選び、できれば正しいと分かっている出力も用意して、変換後の実行結果が正しいかどうかを判断できるようにしてください。

PlaidCloud のインポーターは、ワークフローグラフを保持し、参照されているファイルを Document にアップロードし、マクロワークフローを生成し、各 Alteryx ツールをネイティブのワークフローステップまたはマネージドエグゼキューターにマッピングします。ワークフローの大部分は、ほとんど手作業なしで変換されます。このチュートリアルで正直にお伝えするのは残りの部分です。注意が必要なツールもあり、PlaidCloud はどのツールかを正確に示すため、すぐにそこへ進めます。

## 前提条件

- PlaidCloud ワークスペースと、インポート先のプロジェクト。依存関係を監査しやすくするため、移行専用のプロジェクトを使用してください。
- Alteryx ワークフローファイル1つ。`.yxmd`（ワークフロー）、`.yxwz`（分析アプリ）、`.yxmc`（マクロ）のいずれかです。
- そのワークフローが実行時に読み取るファイル。ワークフローファイルと一緒にまとめておいてください。
- PlaidCloud がインポートしたファイルを保存するための、ドキュメントアカウントとフォルダー。

## ステップ1: 準備状況をチェックする

クリーンなインポートは、完全なパッケージから始まります。インポーターを開く前に、ワークフローが使用するものをすべて集めてください。

1. ワークフローファイル本体と、そのワークフローが呼び出すマクロ（ネストされたマクロを含む）を `.yxmc` ファイルとして用意します。
2. 入力データファイル: CSV、TSV、Excel、Access、YXDB、XML、JSON、データベースの抽出ファイル。
3. 同じフォルダーに置かれた空間データのサイドカーファイル: シェイプファイルのグループ（`.shp`、`.shx`、`.dbf`、`.prj`）、MapInfo のグループ（`.tab`、`.map`、`.id`、`.dat`）、投影ファイル。サイドカーファイルの欠落は、空間データの差異が生じる一般的な原因です。
4. ワークフローが参照するレポート用の素材: 画像、PDF、テンプレート、マップレイヤー。
5. 分析アプリの場合は、ユーザーが通常入力する値: テキスト、数値、日付、ファイルやフォルダーの選択、ドロップダウンやチェックボックスの選択。これらは、実行前に設定するワークフロー変数になります。

次に、2つの点を決めます。アップロードされたファイルを保存する Document フォルダーと、このワークフローを構造面（変換して実行できるか）で検証するか、正しいと分かっている出力と照らして（同じ結果になるか）検証するかです。

> **正しいと分かっている出力を用意しましょう。** Alteryx での実行で得られた信頼できる結果がある場合は、パッケージと一緒に保管してください。ステップ4で「実行できた」を「正しい」に変えるのは、この結果です。

ワークフロー1つから複数のワークフローのポートフォリオへ進むときは、このステップの完全版である [Alteryx 移行準備チェックリスト](/ja/guides/workflows/alteryx-migration-readiness-checklist/)を参照してください。

## ステップ2: インポートして変換する

1. PlaidCloud で対象のプロジェクトを開きます。
2. **ツール → Alteryxワークフローをインポート**を開きます。
3. 対象のプロジェクトを選択し、`.yxmd`、`.yxwz`、`.yxmc` ファイルを選択します。
4. 必要に応じて、ワークフロー、ステップ、テーブル名のプレフィックスを設定します。テーブル名にはすでにワークフロー自身の名前がプレフィックスとして付くため、ワークフロー1つだけの場合は独自のプレフィックスは不要です。
5. インポートしたファイルを保存するドキュメントアカウントとフォルダーを選択します。
6. ワークフローが実行時に必要とする、参照先のファイルまたはフォルダーを追加します。
7. インポートを開始します。

インポートが完了すると、ウィンドウのフォームが**変換レポート**に置き換わります。確信度が高くマッピングされたステップの数、レビューが必要なステップの数、そして該当するステップがある場合は、確信度の低い各ステップの名前、操作、確信度、メモを示すテーブルが表示されます。このレポートが移行の中心です。フラグが付いたステップには同じメモがキャンバス上のステップのメモにも記録されているため、そのステップに直接移動できます。

PlaidCloud は、インポートした依存ファイルを選択した Document フォルダーに保存し、変換後のステップをそのパスに向けます。そのため、デスクトップのファイルシステムがなくても、ワークフローを繰り返し実行できます。

> **コメントとコンテナーも引き継がれます。** コメントボックスはメモとハイライトボックスとして取り込まれ、Tool Container はグループになります。Alteryx のときと同じようにワークフローを説明するもので、実行時の処理は追加されません。**Control Container** のゲートも保持されます。そのステップは、ゲートされたデータに行がある場合にのみ実行されるように設定された状態でインポートされます。

## ステップ3: 変換された内容と注意が必要な内容をレビューする

生成された高度なワークフローを開き、変換レポートを上から順に確認します。ほとんどのステップは高い確信度で変換され、対応は不要です。フラグが付いたステップこそ、最初の移行で信頼を築く部分です。各メモを読んで判断してください。

部分的な変換の実際の姿と、それぞれのケースが意味することを次に示します。

| 表示内容 | 意味 | 対応 |
|---|---|---|
| 確信度が高いステップ | ネイティブのステップまたはエグゼキューターに問題なくマッピングされた | 何もしなくて構いません。気になる場合は抜き取りで確認してください |
| レビュー対象としてフラグが付いたステップ | 変換されたが、確認すべき注意点がある | メモを読み、結果が期待どおりか確認します |
| 未変換とマークされたステップ | 誤ったマッピングを推測で行わないよう、インポーターが変換を拒否した | Alteryx で原因を修正して再インポートするか、ステップを手動で作成します |
| まだ存在しないテーブルへの参照 | ワークフローが作成していない Calgary データセットまたは外部で作成されたデータセット | 実行前に、指定されたテーブルをロードします |

最初の移行で出会う可能性の高いフラグをいくつか紹介します。

- **ランダムサンプリング**（Create Samples、Random % Sample）では、サイズと割合は正確に引き継がれますが、レコードは PlaidCloud が独自に抽出します。どの行が選ばれたかではなく、件数と割合で検証してください。
- **XGBoost モデル**は、scikit-learn の勾配ブースティング分類器として変換されます。同一の値ではなく統計的な同等性が得られると考えて、ステップのメモを確認してください。
- **未変換のステップは、ワークフローがそこに到達したときに意図的に失敗します。** そのため、未解決のゲートや存在しないテーブルがある変換結果が、何も問題がないかのように最後まで実行されることはありません。この率直さは意図的なものです。インポーターは、誤った数値を正しい数値として報告することを拒否します。

> **実行が成功しても、正しいとは限りません。** レポートは確認すべき場所を示し、次のステップの検証は数値を信頼してよいかどうかを示します。誰かが出力に依存しているワークフローでは、検証を省略しないでください。

各ツールファミリーがどのように変換されるかの一覧は、[Alteryx 変換マトリックス](/ja/reference/alteryx-conversion-matrix/)を参照してください。

## ステップ4: 変数を設定し、実行して検証する

1. 変換後のワークフローキャンバスで、生成されたステップとブランチを確認します。
2. **ワークフロー変数**を設定します。これらは、変換されたアプリの質問と実行時パラメーターです。ファイル変数とフォルダー変数はステップ2の Document パスに向け、値は Alteryx での実行時に使用したものに合わせます。
3. 個別のステップではなく、ワークフローの**実行**をクリックし、各ステップが順番に実行される様子をログで確認します。
4. 実行履歴、ステップの出力、準備状況に関するメモを確認します。

その後、ステップ1で選択したレベルで検証します。

- **構造面** — ワークフローが開き、グラフに期待どおりのブランチとマクロがあり、入力がアップロードされ、変数が表示され、実行が完了していること。準備状況の確認と棚卸しには、これで十分です。
- **出力の一致** — スキーマ、行数、行の値を、信頼できる Alteryx の出力と比較します。ワークフローで明示的にソートしていない限り、行の順序は無視されます。該当する場合は、null の扱い、数値の精度、日付、ジオメトリも確認してください。

比較結果が一致しない場合は、次の順に原因を調べます。入力ファイルの欠落または相違、変数の値の相違、ソーススナップショットの相違、次に null、日付、丸め、照合順序の相違、最後に空間参照またはジオメトリ形式です。原因を修正し、再実行して、もう一度比較します。完全なチェックリストは、[検証ガイド](/ja/guides/workflows/validate-converted-alteryx-workflows/)にあります。

> **再インポートしても問題ありません。** パッケージを修正して再度インポートすると、最初のインポートを上書きせず、新しいテーブルセットが作成されます。新しいワークフローに問題がなければ、以前のワークフローとそのテーブルを削除してください。

## ワークフローを移行できました

1つの Alteryx ワークフローを、準備状況のチェックから PlaidCloud での検証済みの実行まで進めました。同じくらい重要なこととして、変換レポートを読んで、問題なく変換された部分と確認が必要な部分を見分けられるようになりました。これで一連の流れは完了です。これをワークフローごとに繰り返し、規模の大きなポートフォリオでは、専用のプロジェクトにバッチ単位で移行してください。
