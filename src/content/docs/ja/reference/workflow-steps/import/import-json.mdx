## 説明

PlaidCloud DocumentからJSONテキストファイルをインポートします。

JSONファイルの詳細については、JSONの公式サイト（http://json.org/）を参照してください。

JSONファイルでは列の順序は保持され*ません*。ソースファイルの列の順序が、インポートされたデータテーブルの列の順序に反映されるとは限りません。

JSONのインポートは、ドキュメント全体をメモリに読み込むのではなく一時ストレージ経由でストリーミングされるため、非常に大きなファイルでもメモリ不足にならずにインポートできます。大きなドキュメントの後半で初めて現れる列も、インポートされるテーブルに含まれます。ネストされたオブジェクトと配列は、標準的なコンパクトなJSONテキストとしてインポートされるため、後続のステップで任意のJSONツールを使って解析できます。

## 固有の設定項目

### JSONデータの向き

次のデータセットを考えてみましょう。

| ID | Name | Gender | State |
| 1 | Jack | M | MO |
| 2 | Jill | F | MO |
| 3 | George | M | VA |
| 4 | Abe | M | KY |

JSONファイルは、次の3つのデータ形式のいずれかでインポートできます。

* Records: データはPythonの辞書のセットに保存され、各行は \{Column -> Value, …} の形式で保存されます。例を示します。


```json
[{ "ID": 1, "Name": "Jack", "Gender": "M", "State": "MO" }, { "ID": 2, "Name": "Jill", "Gender": "F", "State": "MO" }, { "ID": 3, "Name": "George", "Gender": "M", "State": "VA" }, { "ID": 4, "Name": "Abe", "Gender": "M", "State": "KY" }]
```

* Index: データはネストされたPythonの辞書のセットに保存され、各行は \{Index -> \{Column -> Value, …},…} の形式で保存されます。例を示します。


```json
{ "0": { "ID": 1, "Name": "Jack", "Gender": "M", "State": "MO" }, "1": { "ID": 2, "Name": "Jill", "Gender": "F", "State": "MO" }, "2": { "ID": 3, "Name": "George", "Gender": "M", "State": "VA" }, "3": { "ID": 4, "Name": "Abe", "Gender": "M", "State": "KY" } }
```

* Split: データは単一のPythonの辞書のセットに保存され、値はリストに保存されます。例を示します。


```json
{ "columns": ["ID", "Name", "Gender", "State"], "index": [0, 1, 2, 3], "data": [ [1, "Jack", "M", "MO"], [2, "Jill", "F", "MO"], [3, "George", "M", "VA"], [4, "Abe", "M", "KY"] ] }
```

上記の形式に加えて、改行区切りのJSON（NDJSON）も使用できます。これは、配列で囲まず、1行に1つの独立したJSONオブジェクトを記述する形式です。例を示します。

```json
{ "ID": 1, "Name": "Jack", "Gender": "M", "State": "MO" }
{ "ID": 2, "Name": "Jill", "Gender": "F", "State": "MO" }
```


### ドキュメント全体

各ファイルのJSONをそのまま保持するには、**その他の JSON オプション**で**各ファイルを JSON ドキュメント全体を保持する 1 行としてインポートする**（`whole_document`）を選択します。すると、各ファイルは、JSONドキュメント全体を保持する1行としてインポートされ、数値は記述されたとおりに保持されます。

### 日付とタイムスタンプ

フィールドのすべての値が、次のレイアウトのいずれか同じ1つに従っている場合、そのフィールドは日付またはタイムスタンプとしてインポートされます。

| レイアウト | 日付 | タイムスタンプ |
| --- | --- | --- |
| ISO 8601 | `2026-01-23` | `2026-01-23T23:14:00` |
| 月が先 | `01-23-2026` または `01-23-26` | `01-23-2026 11:14:00 PM`（12時間制の時刻） |
| 日が先 | `23-01-2026` または `23-01-26` | `23-01-2026 23:14:00`（24時間制の時刻） |
| 2桁の年が先 | `99-01-23` | `99-01-23 23:14:00`（24時間制の時刻） |

フィールド内のすべての値は、行の並び順に関係なく、同じ方法で読み取られます。`01/23/2026` や `01-23-2026 23:14:00` など、これ以外のレイアウトのフィールドはテキストとしてインポートされます。値のレイアウトが混在しているフィールドも同様ですが、`01-23-2026` と `01-24-26` のように2桁の年と4桁の年が混在する場合は、インポートが停止し、そのフィールドを示すエラーが表示されます。

#### 値が複数のレイアウトに一致する場合

`01-03-2026` は1月3日にも3月1日にも読み取れ、`23-01-26` は2026年1月23日にも、年が先として読むと2023年1月26日にも読み取れます。フィールドのすべての値が上記の複数のレイアウトに一致する場合は、ステップの**日付形式**が、日、月、年の順序によって読み取り方を決めます。

* 「月日」で始まる選択肢は、月が先として読み取ります。`01-03-2026` は1月3日になります。
* 「日月」または「省略形」で始まる選択肢は、日が先として読み取ります。`01-03-2026` は3月1日、`23-01-26` は2026年1月23日になります。
* それ以外の日付形式では、インポートが停止し、そのフィールドと、読み取り方が決まる選択肢を示すエラーが表示されます。

これらの選択肢は、すべての値の日と月が12以下の場合、タイムスタンプも、もう一方の時刻表記として読み取ります。「月日」の選択肢は `01-03-2026 23:14:00` を1月3日として読み取り、「日月」または「省略形」の選択肢は `01-03-2026 11:14:00 PM` を3月1日として読み取ります。それ以外の日付形式では、表のとおりに、日が先なら24時間制の時刻、月が先なら12時間制の時刻として読み取ります。

2桁の年が先のレイアウトを読み取る日付形式の選択肢はないため、`26-01-23` のようなフィールドは、ほかの読み方ができない場合にのみ年が先としてインポートされます（`99-01-23` の場合など）。`2026-01-23` のように4桁の年で書かれた日付は、ISO 8601 としてインポートされます。

ネストされたオブジェクトや配列の中にもタイムスタンプを含むファイルは例外です。上記のチェックはいずれも適用されず、複数のレイアウトに一致する値が、行ごとに異なる読み方をされることがあります。
