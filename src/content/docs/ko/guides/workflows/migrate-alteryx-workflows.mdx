PlaidCloud는 Alteryx 워크플로, 분석 앱, 매크로를 PlaidCloud에서 검토, 일정 등록, 매개변수화, 실행할 수 있는 고급 워크플로로 변환합니다. 가져오기 기능은 워크플로 그래프를 유지하고, 참조된 파일을 문서에 업로드하며, 필요할 때 매크로 워크플로를 만들고, 도구를 기본 워크플로 단계 또는 관리형 작업 실행기에 매핑합니다.

워크플로 하나, 관련 워크플로 그룹 또는 대규모 Alteryx 포트폴리오를 PlaidCloud로 옮길 때 이 가이드를 사용하십시오.

<Aside type="note">
  변환된 워크플로는 수작업이 거의 필요 없도록 설계되었습니다. 운영 워크플로의 경우 PlaidCloud 검증을 통해 정기 실행을 예약하기 전에 준비 상태를 명확히 기록할 수 있습니다.
</Aside>

## PlaidCloud가 만드는 항목

PlaidCloud는 Alteryx 설계를 바탕으로 실행 가능한 고급 워크플로를 만듭니다.

- 워크플로 도구는 원래의 업스트림 및 다운스트림 관계가 유지된 PlaidCloud 워크플로 단계가 됩니다.
- Alteryx 매크로는 명시적인 매크로 입력과 매크로 출력을 가진 PlaidCloud 매크로 워크플로가 됩니다.
- 분석 앱의 질문은 사용자가 실행 전에 설정할 수 있는 제어된 워크플로 변수가 됩니다.
- 입력 파일, 출력 파일, 공간 보조 파일, 이미지, PDF, 생성된 아티팩트는 가져오기 중에 선택한 경로의 문서에 저장됩니다.
- Assisted Modeling(머신 러닝) 파이프라인은 기본 ML Train 및 ML Score 워크플로 단계가 됩니다.
- 퍼지 매칭, 공간 처리, PDF 추출, OCR, NLP, 보고와 같은 고급 작업은 기본 SQL 또는 워크플로 작업이 가장 적합하지 않을 때 PlaidCloud의 관리형 작업 실행기를 통해 실행됩니다.
- 주석 상자와 Tool Container는 워크플로 캔버스에 메모, 강조 상자, 그룹으로 나타납니다. 원본에서 설명하던 내용을 그대로 설명하며, 실행 시 추가 작업은 없습니다.
- Browse와 기타 뷰어 전용 개체는 단계가 아니라 캔버스의 일부로 변환되므로 실행 시 추가 작업이 없습니다. 모든 단계의 출력 테이블을 이미 확인할 수 있기 때문입니다.

## 시작하기 전에

가져오기 전에 워크플로 파일과 종속성을 함께 모으십시오.

1. Alteryx 워크플로, 앱, 매크로 파일(`.yxmd`, `.yxwz`, `.yxmc`)을 포함합니다.
2. CSV, Excel, Access, YXDB, XML, JSON, 데이터베이스 추출 파일 등의 입력 데이터 파일을 포함합니다.
3. 공간 보조 파일을 함께 포함합니다. 예를 들어 shapefile 그룹과 MapInfo 파일은 같은 폴더에 두십시오.
4. 이미지, PDF, 지도 레이어, 템플릿 같은 보고서 자산을 포함합니다.
5. 변환된 워크플로를 만들 PlaidCloud 프로젝트를 선택합니다.
6. PlaidCloud가 가져온 파일을 업로드할 문서 계정과 폴더를 선택합니다.
7. 이 마이그레이션에 구조 검증만 필요한지, 출력 일치 검증이 필요한지 결정합니다.

## 워크플로 가져오기

1. PlaidCloud에서 대상 프로젝트를 엽니다.
2. **Tools → Alteryx 워크플로 가져오기**를 엽니다.
3. 대상 프로젝트를 선택하고 가져올 `.yxmd`, `.yxwz` 또는 `.yxmc` 파일을 선택합니다.
4. 필요하면 워크플로, 단계, 테이블 이름 접두사를 설정합니다. 테이블 이름에는 이미 워크플로 자체 이름이 접두사로 붙습니다. 아래의 [변환된 워크플로의 테이블 이름](#변환된-워크플로의-테이블-이름)을 참조하십시오.
5. 가져온 파일을 저장할 문서 계정과 폴더를 선택합니다.
6. 워크플로가 실행 시 필요로 하는 참조 파일이나 폴더를 추가합니다.
7. 가져오기를 시작합니다.
8. 문제 없이 가져오면 창이 자동으로 닫히고 생성된 고급 워크플로가 열립니다. 직접 닫을 필요가 없습니다. 다시 확인할 만한 내용은 가져오기를 지연시키지 않고 나중에 토스트 알림으로 표시됩니다.
9. 워크플로에 변환되지 않은 단계가 있거나, 읽어야 할 파일이 없거나, 그 밖에 확인이 필요한 문제가 있으면 창이 열린 채로 유지되며 변환 보고서가 표시되므로 계속하기 전에 검토할 수 있습니다.

확인이 필요한 단계가 있으면(제외되었거나 변환되지 않은 도구 등) 가져오기 창은 양식을 변환 보고서로 바꿉니다. 보고서에는 높은 신뢰도로 매핑된 단계 수와 검토가 필요한 단계 수의 요약이 표시되고, 신뢰도가 낮거나 주의가 필요한 단계의 이름, 작업, 신뢰도, 참고 사항을 나열한 테이블이 표시됩니다. 워크플로를 실행하기 전에 이를 활용해 확인할 가치가 있는 단계로 바로 이동하십시오. 이러한 단계에는 캔버스의 단계 메모에도 같은 신뢰도 참고 사항이 있습니다.

PlaidCloud는 가져온 종속성을 가져오기 중에 선택한 문서 위치에 저장합니다. 변환된 단계는 이러한 문서 경로를 참조하므로, 워크플로는 데스크톱 파일 시스템에 의존하지 않고 반복해서 실행할 수 있습니다.

### 누락된 파일

워크플로가 읽는 파일이 없다는 이유만으로(예: 업로드된 적 없는 네트워크 공유 경로) 가져오기가 더 이상 실패하지 않습니다. 워크플로는 그대로 변환되며, 변환 보고서에는 누락된 각 파일이 다음 정보와 함께 나열됩니다.

- 파일을 업로드할 문서 경로.
- 파일을 읽던 원래 Alteryx 경로.
- 워크플로가 해당 파일에서 기대하는 시트.
- 해당 파일을 읽는 Alteryx 도구.

대부분의 파일은 보고서에 표시된 경로에 업로드한 다음 워크플로를 다시 실행하면 되며, 다시 가져올 필요가 없습니다. 일부 유형의 누락된 파일은 실행 시점이 아니라 변환 시점에 읽으므로, 보고서는 파일을 제자리에 둔 뒤 워크플로를 다시 가져오라고 안내합니다. Alteryx 평면 ASCII 레이아웃 파일, 와일드카드 입력, Dynamic Input 템플릿, FirstRow 이름 바꾸기 원본이 여기에 해당합니다.

꺼져 있는 Tool Container 안의 도구만 읽는 파일은 이 목록에 나타나지 않으며 문서로 복사되지도 않습니다. 해당 도구는 애초에 가져오지 않으므로([캔버스의 주석 및 Tool Container](#캔버스의-주석-및-tool-container) 참조), 변환된 워크플로에는 그 파일이 필요한 단계가 없습니다. 파일도 함께 가져오려면 Alteryx에서 컨테이너를 켜거나, 꺼져 있는 컨테이너의 도구를 일반 단계로 가져오는 옵션을 사용하여 가져오십시오.

<Aside type="note" title="워크플로를 실행할 때 파일이 여전히 없는 경우">
변환된 Input 또는 가져오기 단계의 원본 파일을 업로드하지 않은 채 워크플로를 실행하면, 단계는 "No files found at &lt;path&gt;; the target table was created empty." 경고와 함께 끝나고 다른 가져오기 단계와 마찬가지로 워크플로는 계속 진행됩니다. 파일을 업로드하고 워크플로를 다시 실행하면 로드됩니다.
</Aside>

워크플로의 그 밖의 문제(PlaidCloud가 읽을 수 없는 매크로나 평면 파일 레이아웃, 대상 경로에 이미 있는 내용이 다른 파일, 변환할 수 없는 도구)는 가져오기 전체를 실패시키는 대신 해당 단계 하나에 경고를 표시하므로, 워크플로의 나머지는 그대로 변환됩니다.

### 가져오기가 거부되는 경우

업로드한 파일을 전혀 변환할 수 없으면 부분 결과를 만들지 않고 가져오기가 즉시 거부되며, 오류 메시지에 해야 할 일이 안내됩니다. 이는 파일이 Alteryx 워크플로가 아닌 경우, Alteryx 패키지(`.yxzp`)인 경우(이때는 Alteryx Designer에서 `.yxmd` 워크플로를 내보내 사용하는 파일과 함께 업로드하십시오), 워크플로 파일이 없거나 읽을 권한이 없는 경우, 또는 필요한 테이블 이름이 가져오기가 스스로 해결할 수 없는 방식으로 충돌하는 경우에 발생합니다.

변환기 자체에 내부 결함이 발생하면 결함을 알리는 메시지와 함께 가져오기가 거부됩니다. "PlaidCloud could not convert this workflow because of a converter defect (&lt;error&gt;). It has been logged for the PlaidCloud team; include the request ID when you contact support." 이 경우 파일에는 문제가 없습니다. 팀이 기록된 실패를 확인할 수 있도록 메시지의 요청 ID와 함께 지원팀에 문의하십시오.

### 변환된 워크플로의 테이블 이름

변환된 각 단계는 자신이 유래한 Alteryx 도구의 이름을 딴 테이블(예: 도구 4의 `tool_4_out`)을 씁니다. Alteryx는 파일마다 도구에 번호를 매기므로 이 이름은 워크플로 간에 반복되는데, PlaidCloud 프로젝트는 하나의 테이블 네임스페이스입니다. 따라서 모든 가져오기는 테이블에 워크플로 자체 이름을 접두사로 붙여 `03_measure_the_quality_of_data_tool_4_out`과 같은 이름을 만듭니다. 덕분에 Alteryx 워크플로가 담긴 폴더 전체를 서로의 결과를 덮어쓰지 않고 하나의 프로젝트에 가져올 수 있습니다.

<Aside type="caution" title="이름이 같은 두 워크플로">
두 가져오기를 구분해 주는 것은 워크플로 이름뿐입니다. 이름이 같은 두 파일, 구두점이나 공백만 다른 이름(예: `Sales Report`와 `Sales-Report`), 또는 이름이 없는 파일은 모두 같은 접두사를 만듭니다. 이런 파일을 가져올 때는 **테이블 이름 접두사**를 직접 설정하거나, 별도의 프로젝트로 가져오십시오.

이러한 가져오기는 더 이상 서로를 덮어쓰지 않습니다. 프로젝트에 이미 있는 테이블 이름을 요청하는 가져오기는 `-duplicate-` 접미사가 붙은 이름의 자체 테이블을 받으며, 해당 단계는 그 테이블을 사용합니다. 각 가져오기는 자신의 결과를 유지하지만 두 번째 가져오기의 테이블 이름은 읽기 어려워지므로, 직접 접두사를 설정하는 것이 여전히 좋습니다.
</Aside>

같은 워크플로를 두 번 가져오는 경우(처음 가져온 결과를 바로잡아야 할 때 발생)도 마찬가지로, 두 번째 가져오기는 첫 번째 결과를 덮어쓰지 않고 자체 테이블 집합을 받습니다. 새 결과가 만족스러우면 이전 가져오기의 워크플로와 테이블을 삭제하십시오.

가져오기 중에 직접 **테이블 이름 접두사**를 설정하면 기본값을 재정의할 수 있으며, 비워 두면 접두사 없는 `tool_4_out` 이름으로 돌아갑니다. 변환된 단계 자체를 제외하면 이 이름에 의존하는 것은 없으므로, 나중에 테이블 이름을 바꾸면 그 테이블을 읽는 단계를 다시 지정해야 합니다.

### Parquet으로 기록되는 출력

`.parquet` 또는 `.avro`를 쓰는 Output Data 도구는 해당 형식의 내보내기 단계로 변환됩니다. `.yxdb`, `.hyper`, `.dbf`를 쓰는 도구는 Parquet으로 기록됩니다. `.yxdb` 출력의 경우 같은 폴더에 이름이 같은 `.parquet` 파일이 만들어집니다.

해당 `.yxdb` 파일을 읽는 변환된 워크플로는 `.parquet`를 자동으로 읽습니다. [Alteryx YXDB 가져오기](/ko/reference/workflow-steps/import/import-alteryx-yxdb/) 단계는 `.yxdb`가 없으면 이름이 같은 `.parquet`로 대체하고 그 사실을 알리는 경고를 표시합니다.

### 캔버스의 주석 및 Tool Container

Alteryx 작성자가 작업 주위에 그려 둔 메모와 그룹도 함께 변환됩니다.

- 텍스트가 있는 주석 상자는 그려진 위치와 크기 그대로 캔버스의 **메모**가 됩니다.
- 도구 집합 주위를 빈 외곽선으로 그린 주석 상자는 Alteryx에서 하던 역할 그대로 **강조 상자**가 됩니다.
- 연결된 문서를 표시하는 주석 상자는 링크를 텍스트로 유지합니다.
- **Tool Container**는 안에 그려진 단계를 담는 **그룹**이 되며, 캡션, 접힘 여부, 꺼짐 여부를 유지합니다. 중첩된 컨테이너는 중첩된 그룹으로 변환되고, 두 컨테이너 안에 모두 있는 단계는 두 그룹에 모두 속합니다.

직접 그린 것과 같은 방식으로 이동, 편집, 색 변경, 삭제할 수 있습니다.

원본과 다르게 동작하는 부분이 두 가지 있습니다.

- **꺼져 있는 Tool Container의 도구는 전혀 가져오지 않습니다.** Alteryx도 이 도구를 실행하지 않으므로, 가져오면 아무 일도 하지 않는 단계가 워크플로에 생기게 됩니다. 컨테이너 자체는 캡션이 있는 강조 상자로 그대로 변환되므로 무엇이 있었는지 확인할 수 있습니다. 도구를 가져오려면 Alteryx에서 컨테이너를 켠 다음 다시 가져오십시오. (API 또는 AI 에이전트를 통해 가져올 때는, 비활성화된 컨테이너의 도구를 실행 가능한 일반 단계로 가져오는 옵션도 사용할 수 있습니다. 모든 것이 꺼진 상태로 제공되는 샘플 워크플로에 유용합니다.)
- **상자 색상은 그대로 옮겨지지 않습니다.** 캔버스에서는 고정된 여섯 가지 색만 제공하고 Alteryx 상자는 거의 항상 흰색이나 회색이어서, 모두 같은 색조로 나타나게 됩니다. 대신 캔버스 기본값으로 가져오며, 원하는 색은 마우스 오른쪽 클릭 메뉴에서 설정하십시오.

메모의 텍스트는 이제 중립적인 회색으로 표시됩니다. 이전에는 어두운 캔버스에서 호박색/주황색으로 표시되었는데, Alteryx에서 그대로 가져온 평범한 주석에도 경고처럼 보이는 색이었습니다.

단계를 전혀 담지 않게 되는 Tool Container(꺼져 있거나 주석만 들어 있었기 때문)도 캔버스에서 사라지지 않고 캡션이 있는 강조 상자로 나타납니다.

도구 없이 주석뿐인 워크플로(도구가 없는 문서 페이지)는 해당 주석이 담긴 캔버스로 가져오며, 실행 가능한 단계로는 변환되지 않았다고 알립니다. 실행할 것이 없었으므로 이는 실패가 아니라 정확한 결과입니다.

### Control Container

Alteryx **Control Container**는 **컨트롤** 입력에 연결된 스트림에 레코드가 있을 때만 내부 도구를 실행합니다. 이 게이트는 컨테이너의 윤곽만이 아니라 컨테이너와 함께 변환됩니다.

- 컨테이너는 다른 컨테이너와 마찬가지로 캔버스의 **그룹**이 되며 캡션과 내용을 유지합니다.
- 컨테이너 안에 있던 모든 단계는 게이트 데이터에 행이 있을 때만 실행되고 없으면 건너뛰도록 설정된 채로 가져옵니다. 그 안에 중첩된 컨테이너의 단계에도 같은 게이트가 적용됩니다. 조건을 직접 연결할 필요가 없습니다.
- **컨트롤** 입력에 아무것도 연결되지 않은 Control Container는 시각적 그룹일 뿐이었으므로 Tool Container와 똑같이 변환됩니다.
- 아무것도 감싸지 않은 Control Container는 캡션이 강조 상자로 캔버스에 유지됩니다.

<Aside type="caution" title="가져오기가 해석하지 못한 게이트">
**컨트롤** 입력에 데이터를 공급하는 도구가 테스트할 데이터를 만들지 않아 게이트를 만들 수 없는 경우가 있습니다. 가져오기는 더 이상 이를 조용히 넘어가지 않습니다. 컨테이너는 변환되지 않음으로 표시된 단계로 나타나며, 내부 도구가 그대로면 매번 실행된다는 참고 사항이 붙고, 조치가 필요한 단계로 변환 보고서에 나열됩니다. 이 단계는 워크플로가 도달하면 실패하므로, 아무 문제 없는 것처럼 변환 결과를 끝까지 실행할 수 없습니다.

이전에는 내부 도구가 조건 없이 실행되도록 가져왔고 캔버스에는 이를 알리는 표시가 없었는데, 이는 같은 문제의 조용한 형태입니다.

해결하려면 **컨트롤** 입력이 데이터를 만드는 도구에서 오도록 Alteryx 워크플로를 변경한 뒤 다시 가져오거나, 표시된 단계를 삭제하고 컨테이너 안에 있던 단계에 직접 게이트를 설정하십시오. [단계 조건](/ko/guides/workflows/step-conditions/)을 참조하십시오.
</Aside>

### Browse 도구

Alteryx **Browse**는 뷰어입니다. 도달한 레코드를 표시할 뿐 아무것도 변경하지 않으며 출력 커넥터가 없습니다. PlaidCloud에서는 모든 단계의 출력 테이블을 바로 열어 볼 수 있으므로, 작성자가 Browse로 보려던 내용은 바로 위 단계에서 한 번의 클릭으로 확인할 수 있습니다. 해당 단계를 선택하고 테이블을 보십시오.

따라서 Browse는 단계가 아니라 캔버스의 일부로 변환됩니다. 단계를 만들지 않고, 테이블을 점유하지 않으며, 변환기가 처리하지 못한 도구에도 포함되지 않습니다.

- **테이블이 만들어지지 않습니다.** 이전에는 각 Browse가 워크플로가 나중에 버리는 아무 일도 하지 않는 단계가 되었으며, 아무도 쓰지 않고 읽지도 않는 자체 웨어하우스 테이블을 점유했습니다. 179개 워크플로로 이루어진 Alteryx 참조 세트 전체에서 그런 테이블이 152개였습니다.
- **끊어진 분기는 문제를 일으킨 도구에서 한 번만 보고됩니다.** 이전에는 Browse에 *공급하는* 도구가 변환에 실패할 때마다 Browse도 변환 실패 도구로 변환 보고서에 나열되어, 같은 문제가 두 번 나타났습니다. 실제로 고쳐야 하는 도구에서 한 번, 실행될 수조차 없었던 뷰어에서 한 번이었습니다. 참조 세트에서 보고된 실패 중 14건이 이런 경우였습니다. 이런 항목은 사라졌으며, 실제 원인인 도구는 계속 보고됩니다.

이는 실패 자체가 아니라 변환 보고서의 오해를 부르는 항목을 없앤 것입니다. 모든 도구가 변환된 상태로 변환되는 워크플로의 수는 이전과 같습니다.

<Aside type="caution" title="테이블 이름을 알리며 중지되는 워크플로">
한 가지 형태의 워크플로는 이제 이전에 실행되던 지점에서 중지되며, 이는 새로운 문제가 아니라 수정 사항입니다.

워크플로가 매크로 내부 도구에 이를 호출하는 캔버스의 도구와 같은 번호를 매긴 경우, 매크로 아래의 단계가 매크로 자체 출력 대신 Browse의 테이블 이름으로 확인되었습니다. 이러한 워크플로를 다시 가져오면 해당 단계는 존재하지 않는 테이블을 알리며 중지됩니다.

이 단계는 Browse의 레코드를 읽은 적이 없습니다. 그 테이블은 가져올 때 만들어졌지만 이후 아무것도 쓰지 않았으며(워크플로가 만들어지기 전에 Browse 자체가 제거되었기 때문), 그래서 단계는 **빈** 테이블을 읽었고 실행은 레코드를 하나도 처리하지 않은 채 성공으로 보고되었습니다. 생성된 수치는 아무것도 없는 데이터에서 나왔고 이를 알려 주는 표시도 없었습니다. 이제 테이블이 만들어지지 않으므로 단계가 그 사실을 알립니다.

**복구 방법:** 해당 단계를 원래 읽도록 그려진 테이블, 즉 위에 있는 매크로 단계의 출력으로 다시 지정한 다음 워크플로를 다시 실행하십시오.
</Aside>

이 릴리스 이전에 가져온 워크플로는 테이블을 포함하여 당시의 변환 결과를 유지합니다. 이 변경을 적용하려면 다시 가져오십시오.

### Calgary 데이터베이스

Alteryx **Calgary 데이터베이스**(`.cydb` 파일)는 독점 인덱스 저장소입니다. PlaidCloud는 이 파일 형식을 읽을 수 없으며 공개된 사양도 없습니다. 이를 사용하는 모든 도구를 거부하는 대신, 변환은 각 `.cydb` 경로를 가져오기에 적용된 테이블 접두사 아래 `calgary_<database name>`이라는 일반 PlaidCloud 테이블 하나로 취급합니다. 데이터베이스가 일반 테이블이 되면 이를 중심으로 만들어진 도구도 일반 작업이 됩니다. 저장된 쿼리는 필터가 되고, 교차 집계 버킷은 조건부 개수가 되며, 로더의 필드 목록은 열 집합이 됩니다.

- 변환된 **Calgary Loader**는 입력으로 해당 테이블을 씁니다. 선언된 인덱스 유형은 변환 중에 삭제되지만(웨어하우스는 스스로 인덱싱합니다) 필드 목록은 유지됩니다.
- 변환된 **Calgary Input**은 저장된 쿼리를 필터로 적용하여 테이블을 다시 읽습니다. 데이터베이스에 무엇이 있었는지 워크플로 파일에는 기록되어 있지 않으므로, 테이블의 열은 단계가 실행될 때 확인됩니다.
- 변환된 **Calgary Input (Count Only)** 또는 **Calgary Cross Count**는 테이블을 집계로 읽습니다. 일반 인덱스 필드는 행을 그룹화하고, 사용자 지정 필드의 이름이 지정된 각 값은 개수를 세는 열 하나가 됩니다.
- 변환된 **Calgary Join**은 들어오는 각 레코드를 테이블과 대조하여, 일치한 레코드를 유지하고 입력 자체의 열을 그대로 전달합니다. 들어오는 필드가 공간 값이 아닌 일반 값일 때 변환됩니다. 그렇지 않은 경우는 아래의 [Calgary Join 및 Cross Count Append](#calgary-join-및-cross-count-append)를 참조하십시오.
- 변환된 **Calgary Cross Count Append**는 같은 방식으로 들어오는 각 레코드를 테이블과 대조한 다음, 일치한 데이터베이스 레코드 수를 입력에 추가하여 보고합니다. 이 경우에도 들어오는 필드가 공간 값이 아닌 일반 값일 때 해당됩니다.

<Aside type="caution" title="이름이 같은 두 데이터베이스">
서로 다른 디렉터리에 있는 이름이 같은 두 `.cydb` 파일은 같은 PlaidCloud 테이블을 가리키며, 리더가 어느 쪽을 사용하려 했는지 워크플로만으로는 알 수 없습니다. Loader와 관련된 모든 리더는 추측하는 대신 두 파일을 모두 알리며 거부합니다. 원본 데이터베이스 중 하나의 이름을 바꾸고 다시 가져오십시오.
</Aside>

**직접 만들지 않은 데이터베이스를 읽는 워크플로는 테이블 이름을 알리며 중지되는 단계를 갖게 됩니다.** Alteryx가 제공하는 인구통계 및 참조 `.cydb` 파일이 대표적인 경우입니다. 워크플로 어디에서도 이를 쓰지 않았으므로 읽을 PlaidCloud 테이블이 아직 없습니다. 해당 테이블이 생기기 전까지 변환된 단계는 아무것도 읽지 않고 성공으로 보고하는 대신 중지되고 테이블 이름을 알립니다. 워크플로를 실행하기 전에, Alteryx로 읽을 수 있다면 원래의 `.cydb`에서, 아니면 데이터가 실제로 있는 곳에서 원본 데이터를 해당 이름의 테이블로 내보내십시오.

#### Calgary 쿼리의 Or, And, Not

Calgary 쿼리는 데이터베이스의 인덱스 필드에 대한 `And`, `Or`, `Not`의 트리이며, 이제 이 트리는 작성된 그대로 변환됩니다. 트리 어디에서든 `Or`가 있어도, 둘 이상의 조건을 감싼 `Not`도 변환됩니다. 포함 또는 시작 문자열 조건도 변환되며, 개수 경로에서는 SQL LIKE로, 레코드 읽기에서는 부분 문자열 일치로 변환됩니다. 이는 Calgary Input의 레코드 읽기, 개수만 읽기, Calgary Cross Count, Cross Count 사용자 지정 필드 안의 버킷에 적용됩니다.

일부 쿼리 형태는 여전히 변환되지 않으며, 각각 변환 보고서와 단계에 자신을 알립니다.

- 열 비교 대신 공간 조회(또는 부정된 포함/시작 문자열 조건)를 사용하는 쿼리. 열 수준에 해당하는 것이 없는 인덱스 작업입니다.
- **Skip Records** 또는 **Max Records**로 제한된 읽기. 대체 테이블에는 건너뛰거나 제한할 기준이 되는 레코드 순서가 없습니다.
- 둘 이상의 사용자 지정 필드로 그룹화된 Cross Count. 개수는 실제로 데이터베이스 전체에 대한 하나의 집계이지만, 결과 열의 이름이나 순서를 Alteryx가 문서화하지 않았고 비교할 사례도 없습니다.
- 개수를 셀 열을 지정하지 않은 개수만 읽기. 데이터베이스 자체의 열은 워크플로 파일에서 읽을 수 없기 때문입니다.
- 데이터 필드를 저장하지 않는 **Calgary Loader**. 열이 없는 테이블을 쓰게 됩니다.
- 데이터베이스를 전혀 지정하지 않은 Calgary 도구.

#### Calgary Join 및 Cross Count Append

**Calgary Join**과 **Calgary Cross Count Append**는 들어오는 모든 레코드를 데이터베이스의 인덱스 중 하나를 통해 대조하는데, 워크플로 파일에는 인덱스의 *이름*은 기록되지만 *종류*는 기록되지 않습니다. 같은 구성이 인덱스에 일반 값이 있으면 동등 조인을 뜻하고, 공간 지오메트리가 있으면 "어떤 점이 이 도형 안에 들어가는가" 일치를 뜻하지만, 파일만으로는 어느 쪽인지 알 수 없습니다.

변환은 **들어오는 필드 자체의 선언된 유형**으로 판단합니다. 공간 인덱스는 공간 필드와 짝을 이룰 수밖에 없으므로 다음과 같이 처리됩니다.

- 공간 개체로 유형이 지정된 들어오는 필드는 중지되며, 필드 이름, 도출된 해석, 그리고 **Spatial Match** 단계로 일치를 다시 구성할 대체 테이블을 알립니다.
- 유형을 확인할 수 없는 들어오는 필드는 그 점을 이유로 알리며 중지됩니다. 추측하지 않습니다.
- 공간 값이 아닌 일반 들어오는 필드는 대체 테이블과 대조하여 변환됩니다.

어느 경우든 단계는 자신이 취한 해석과 그 근거가 된 필드 유형을 기록하므로, 동의하지 않는 변환도 추론에 의존할 필요 없이 그 과정을 보여 줍니다.

**Calgary Cross Count Append는 공간 값이 아닌 일반 들어오는 필드에서 변환되며**, Calgary Join과 같습니다. Join은 일치한 레코드를 유지하는 반면 Append는 각 입력 레코드가 일치한 데이터베이스 레코드 수를 보고합니다. 입력 레코드마다 일치 수를 세어 그 수를 입력에 추가합니다. 아무것도 일치하지 않은 입력 레코드는 사라지지 않고 0으로 집계되며, 동일한 입력 레코드 두 개는 각자 행을 유지합니다. 개수는 고유한 값 집합이 아니라 레코드마다 계산됩니다. 일반 교차 집계 필드 하나는 이렇게 변환되지만, *이름이 지정된* 사용자 지정 값의 그리드는 변환되지 **않습니다**. 값마다 개수 열이 하나씩 추가되는데 Alteryx가 그 열이 몇 개인지, 이름이 무엇인지 문서화하지 않았기 때문입니다.

**Count Only 모드의 Calgary Join**도 같은 방식으로 변환됩니다. 일치한 레코드를 유지하는 대신 입력 레코드마다 일치한 데이터베이스 레코드 수를 세며, 일치하는 것이 없는 레코드는 0으로 집계됩니다.

**Calgary Join 또는 Cross Count Append**는 단일 값이 아니라 인덱스 값의 범위와 대조하는 경우, 일치하지 않은 레코드 출력이 다운스트림에 연결된 경우, 데이터베이스와 대조할 필드를 지정하지 않은 경우, 대조할 레코드를 가져올 입력에 아무것도 연결되지 않은 경우에도 자신을 알리며 중지됩니다.

변환된 Loader와 그것이 쓴 내용을 읽는 리더는 서로 연결되므로, 리더가 테이블을 채우는 쓰기와 동시에 실행될 수 없습니다.

Calgary Input의 열은 텍스트로 나타납니다. 대체 테이블은 데이터베이스 자체의 유형이 아니라 이름만 제공하기 때문입니다.

### 인 데이터베이스 도구

인 데이터베이스(In-Database) 워크플로는 Alteryx 엔진이 아니라 웨어하우스에서 작업을 수행하며 PlaidCloud 단계는 이미 웨어하우스 SQL이므로, 인 데이터베이스 **작업** 도구는 인 메모리 쌍둥이 도구와 정확히 같은 단계로 변환됩니다. Filter In-DB는 필터, Formula In-DB는 수식, Summarize In-DB는 집계가 되며 Join, Select, Sample, Sort, Union, Browse도 마찬가지입니다.

변환되지 않는 것은 체인 양 끝의 두 도구입니다. **Connect In-DB**와 **Write Data In-DB**는 그 사이의 도구가 유지하고 SQL을 보내는 실시간 웨어하우스 연결을 열며, PlaidCloud에는 이렇게 열려 있는 연결에 해당하는 기능이 없습니다. 각각 도구 이름과 대체 방법을 알리는 검토 대상 단계로 나타납니다. 대체 방법은 PlaidCloud 연결에 바인딩된 SQL 가져오기 또는 내보내기 단계입니다. 두 끝점을 해당 단계로 바꾸면 그 사이의 작업 도구는 그대로 변환됩니다.

Data Stream In, Data Stream Out, Dynamic Input In-DB, Dynamic Output In-DB, In-Database Macro Input/Output은 같은 이유로 이름을 알리며 거부됩니다.

### 위치 기준 Join 또는 Multi-Row Formula가 공급하는 Union

레코드 위치로 일치시키는 **Join** 또는 **Multi-Row Formula**에서 읽는 **Union**이 있는 워크플로는 깔끔하게 변환되었지만 실행하면 해결할 수 없는 열 때문에 중간에 중지될 수 있었습니다. 변환은 정상으로 보였고, 워크플로를 실행해야만 문제가 드러났습니다.

이 문제는 수정되었으며 이러한 워크플로는 이제 올바른 결과로 실행됩니다. 이전에 가져온 워크플로에서 이 오류가 발생했다면 다시 실행하십시오. 다시 가져올 필요는 없습니다.

### Join Multiple 출력 열

**Join Multiple**이 Select 탭의 모든 필드를 나열하면 Alteryx Designer는 각 필드 이름을 `Input_#1_<field>`, `Input_#2_<field>` 같은 형태로 지정합니다. 변환된 다중 테이블 조인은 이러한 열을 일반 출력 이름으로 유지하고 탭의 이름 바꾸기와 선택 해제를 적용합니다. 이 수정 이전에 변환된 Join Multiple은 출력 열 없이 변환되어 실행 시 단계가 실패했습니다. 수정 사항을 적용하려면 해당 워크플로를 다시 가져오십시오.

### Cross Tab 백분율 및 합계 열

파생 방식인 **Percent Row**, **Percent Column**, **Total Column**, **Total Row** 중 하나를 가진 **Cross Tab**은 변환을 중지시키고 그 아래의 모든 단계도 함께 중지시켰습니다. 이제 네 가지 모두 변환됩니다.

- **Percent Row**와 **Percent Column**은 데이터 필드의 행 합계 또는 열 합계에서 해당 셀이 차지하는 비율입니다.
- **Total Column**은 도구가 기록한 이름으로 된 해당 행 합계입니다.
- **Total Row**는 그룹화 필드에 값이 없이 합계를 담은 추가 레코드입니다.

도구가 각 셀에 대해 어떤 방식을 계산하든 모든 합계는 데이터 필드의 합입니다.

<Aside type="caution" title="백분율 척도를 한 번 확인하십시오">
백분율 열은 0에서 100 사이의 척도로 기록됩니다. Alteryx는 이 방식을 "값을 기준으로 백분율을 계산한다"고만 문서화했을 뿐 어떤 척도인지 밝히지 않으므로, 이 해석은 Alteryx가 명시한 내용이 아니라 열이 표시되는 방식에서 추론한 것입니다. 변환된 Cross Tab의 수치가 게시용 보고서에 반영되기 전에 원본 실행 결과와 하나 이상 비교해 보십시오.
</Aside>

두 가지 형태는 여전히 변환되지 않고 검토 대상으로 표시됩니다. 그룹화 필드가 없는 Cross Tab의 **Total Row**는 두 사본을 구분할 방법이 없이 같은 레코드를 두 번 만들게 되고, 도구가 이름을 기록하지 않은 **Total Column**은 출력에서 아예 누락됩니다.

### Alteryx 배정밀도 열은 전체 정밀도를 유지합니다

Alteryx **배정밀도** 열은 이제 Alteryx 자체가 계산에 사용하는 정밀도와 일치하는 64비트 숫자 열로 변환됩니다. 이전에는 유효 숫자 약 7자리의 32비트 열로 변환되어, 그보다 자릿수가 많은 값은 읽을 때 조용히 반올림되었고 그 값을 기반으로 한 모든 계산이 오류를 이어받았습니다. 실제 사례로 16,862,441.27이 16,862,442.00으로 읽혔습니다.

변환된 매크로 안에서 매크로 입력으로 전달된 배정밀도 열은 이전에는 텍스트로 도착했지만, 이제는 숫자로 도착합니다. 매크로 논리가 이전의 텍스트 동작(문자열 연결, 앞자리 0 서식, 텍스트 패턴 일치)에 의존했다면, 실제 숫자는 다르게 동작할 수 있으므로 다시 변환한 후 검토하십시오.

이 수정 이전에 변환된 워크플로는 변환 당시의 열 유형을 유지합니다. 이 변경을 적용하려면 다시 가져오십시오.

### 변환된 워크플로의 매크로

매크로는 Alteryx 매크로 엔진을 에뮬레이션하는 것이 아니라 PlaidCloud의 기본 구성 요소로 변환됩니다. 모든 매크로 유형이 일급 워크플로 기능에 매핑되므로, 변환된 매크로는 원본과 동일한 레코드별 또는 반복별 동작으로 같은 논리를 완전한 충실도로 실행합니다.

- **표준 매크로**는 호출하는 워크플로에 인라인으로 포함됩니다. 매크로의 도구가 캔버스의 일반 단계가 되므로 신뢰해야 하는 블랙박스가 없으며, 모든 단계를 보고, 검토하고, 편집할 수 있습니다. 중첩된 표준 매크로는 깊이에 관계없이 인라인으로 포함되며, 스스로를 호출하는 매크로는 무한 반복되는 대신 감지되어 이름이 표시됩니다.
- **배치 매크로**는 제어 매개변수의 레코드마다 한 번씩 실행되는 매크로 워크플로가 되며, 각 패스의 출력은 하나의 스트림으로 다시 수집됩니다. 이는 Alteryx가 수행하는 그룹별 실행과 같습니다. 제어 매개변수는 Alteryx에서 배치를 구동하는 것과 똑같이 패스별 변수로 바인딩됩니다.
- **반복 매크로**는 패스 사이에 상태를 전달하고 매크로가 수렴할 때까지 실행되는 기본 워크플로 루프가 됩니다. 루프의 패스 한도는 Alteryx가 매크로를 실행할 때 사용하는 설정과 같은 매크로 자체의 **Maximum Number of Iterations**입니다. 이 값이 Alteryx의 폭주 방지 기본값으로 남아 있거나 설정되지 않은 경우, 변환은 자체 상한을 적용합니다. 매크로가 그 한도에서도 수렴하지 않으면, 실행은 부분 결과를 최종 답으로 보고하는 대신 도달한 한도를 알리며 **중지됩니다**. 상한보다 많은 패스가 실제로 필요한 매크로는 더 높은 값으로 다시 가져올 수 있으며, 가져오기의 `iteration_ceiling` 옵션이 이를 설정합니다.
- **제어 매개변수, Macro Input 및 Macro Output 포트, Action 도구, Detour 분기**는 모두 기본 대응 기능으로 변환되므로 매크로를 연결하는 구조가 근사되지 않고 보존됩니다. 배치 또는 반복 매크로 안에서 호출되는 매크로도 호출한 매크로와 함께 확인되어 변환됩니다.

두 가지 구성은 변환하지 않고 이름을 알리며 거부하므로 가져오는 시점에 알 수 있습니다. 다른 반복 매크로 안에 중첩된 반복 매크로와 In-Database Macro Input/Output 도구입니다.

<Aside type="caution" title="이전에 멈추던 배치 매크로가 이제 완료됩니다">
이전 변환에서는 각 패스가 자체 출력 테이블을 쓰고 결과를 모으는 단계가 이를 모두 이름으로 다시 읽었습니다. 그래서 레코드가 수십 개 정도인 매크로도 그만큼의 테이블에 걸친 하나의 쿼리를 만들었고 데이터베이스가 이를 계획하지 못했습니다. 워크플로가 중간에 중지되었고 원인을 가리킬 만한 단서도 없었습니다.

이제 패스는 결과를 모으는 단계가 직접 읽는 하나의 테이블에 누적되며, 이 테이블은 각 실행을 시작할 때 제대로 비워지므로 패스를 만들지 않는 매크로의 실행은 이전 실행의 행을 다시 제공하는 대신 빈 결과를 반환합니다.

배치 매크로 워크플로가 이전에 멈추거나 중간에 실패했다면 다시 가져와서 수정 사항을 적용하십시오.
</Aside>

<Aside type="tip" title="Location Optimizer의 선형 거리 사례는 기본으로 변환됩니다">
점수가 수정되지 않은 선형 거리 최소화(수요까지의 총 거리 또는 가중 거리를 최소화하는 K개 사이트 선택)인 **Location Optimizer**는 기본 [위치 최적화](/ko/reference/workflow-steps/optimization/location-optimizer/) 단계로 직접 변환됩니다. 이는 PlaidCloud의 HiGHS 솔버에서 풀리는 p-median MIP입니다. 후보 및 수요 테이블과 사이트 수는 그대로 유지되며, 결과를 신뢰하기 전에 거리 열을 확인하십시오.
</Aside>

<Aside type="caution" title="다른 Location Optimizer 매크로는 거부됩니다">
**Location Optimizer** 매크로는 검색의 점수 산정 패스일 뿐입니다. 후보 위치 집합 생성, 위치 수, 생성 한도, 시드 같은 검색 자체는 워크플로 파일이 아니라 호출하는 도구와 Alteryx 엔진에 있습니다. 위의 선형 거리 사례를 벗어나는 경우(중력 커널, 맞춤 점수 매크로, 높을수록 좋은 목적 함수, 점수 산정 전의 거리 변환(고정 시설 비용, Summarize, 조인))에는 PlaidCloud에 해당 최적화 루프에 대응하는 기능이 없습니다. 이제 매크로 호출은 매크로 이름, 후보 집합이 도착하는 입력, 이를 순위로 매기는 출력, 점수가 높은 쪽이 이기는지 낮은 쪽이 이기는지를 알려 주는 검토 대상 단계로 나타납니다.

**이러한 매크로는 이전에는 변환되어 정상으로 실행되었지만 수치가 틀렸습니다.** 일반 매크로로 취급되어 점수 산정 패스가 하나의 후보 집합에 대해 정확히 한 번 실행되고 실행은 성공으로 보고되었습니다. 결과는 답처럼 보였지만 최적화된 것이 아니라 한 번 점수를 매긴 추측이었습니다. 이런 워크플로를 다시 가져왔을 때 이전에는 작동하던 것이 거부된다면, 이전 결과는 신뢰해서는 안 되는 것이었습니다.
</Aside>

### 변환된 워크플로의 보고서

보고서 레이아웃이 참조하는 이미지는 이제 워크플로와 함께 패키징되므로, 변환된 보고서는 Alteryx 컴퓨터에만 있던 자산 때문에 실패하는 대신 문서에서 이미지를 찾습니다. 이는 고정 경로로 지정된 이미지에 적용되며, 바이트가 워크플로에 포함된 이미지나 레코드마다 열에서 경로를 가져오는 이미지에는 가져올 별도의 파일이 없습니다.

원본 데이터를 읽을 수 없었던 보고서 조각은 이제 그렇게 보고됩니다. 테이블의 열을 읽을 수 없는 경우 이를 기반으로 한 보고서 스니펫은 건너뛰어졌고 보고서 테이블 섹션은 비어 있는 채로 나왔으며, 둘 다 성공으로 보고된 실행에서 발생했습니다. 이제 단계는 열 정보를 읽을 수 없었다는 사실과 그 이유를 알리며 중지됩니다. **이전에 섹션이 누락된 채로 나오던 보고서는 이제 설명과 함께 중지될 수 있습니다.** 이에 대한 수정 항목은 [2026년 8월](/ko/releases/2026-08/)을 참조하십시오.

## 변환된 워크플로 사용

가져온 후에는 다른 PlaidCloud 고급 워크플로와 같은 방식으로 워크플로를 사용합니다.

1. 변환된 워크플로 캔버스를 엽니다.
2. 생성된 단계와 분기를 검토합니다.
3. 변환된 앱 질문이나 런타임 매개변수에 대해 워크플로 변수를 설정합니다.
4. 워크플로를 실행합니다.
5. 실행 이력, 단계 출력, 준비 상태 참고 사항, 생성된 아티팩트를 검토합니다.
6. 반복 운영 준비가 되면 워크플로 일정을 등록합니다.

변환된 **Download** 도구는 단계에 포함된 URL이 아니라 REST 연결을 통해 외부 엔드포인트에 접근하는 [REST 요청](/ko/reference/workflow-steps/general/rest-request/) 단계가 됩니다. 실행하기 전에 단계에 REST 연결을 할당하십시오. 변환기는 가져올 때 준비 상태 참고 사항으로 이를 알립니다. 연결을 설정하려면 [연결 만들기](/ko/guides/connections/create-connection/)를 참조하십시오.

변환된 매크로는 PlaidCloud 매크로 워크플로로 사용할 수 있습니다. Alteryx 매크로를 호출하던 워크플로는 매크로 단계를 통해 생성된 PlaidCloud 매크로를 호출합니다. 매크로 실행은 서로 격리되므로 동시에 실행되는 워크플로가 같은 매크로 정의를 안전하게 사용할 수 있습니다.

## 변환 검증

PlaidCloud는 실용적인 두 가지 검증 수준을 지원합니다.

### 구조 검증

구조 검증은 워크플로가 실행 가능한 PlaidCloud DAG로 변환되었는지 확인합니다.

- 모든 Alteryx 도구에 PlaidCloud 변환 경로가 있습니다.
- 필요한 매크로를 찾았거나 생성했습니다.
- 필요한 입력 파일이 문서에 업로드되었습니다.
- 매크로 입력과 매크로 출력이 연결되어 있습니다.
- 사용자가 제어하는 입력에 대해 워크플로 변수가 만들어졌습니다.
- 생성된 워크플로를 열 수 있으며 PlaidCloud에서 실행할 수 있습니다.

구조 검증은 마이그레이션 준비 상태, 인벤토리 검토, 초기 포트폴리오 변환에 유용합니다.

### 출력 일치 검증

출력 일치 검증은 PlaidCloud 실행 결과를 신뢰할 수 있는 Alteryx 출력과 비교합니다.

- 출력 스키마가 일치합니다.
- 행 수가 일치합니다.
- 행 값이 일치합니다.
- 워크플로가 순서에 명시적으로 의존하지 않는 한 행 순서는 무시됩니다.

보고서, 지도, PDF, 이미지, 모델 아티팩트를 만드는 워크플로는 팀이 출력을 사용하는 방식에 따라 생성된 아티팩트 또는 그 바탕이 되는 데이터를 검증하십시오.

자세한 검증 체크리스트는 [변환된 Alteryx 워크플로 검증](/ko/guides/workflows/validate-converted-alteryx-workflows/)을 참조하십시오.

### 무작위 샘플링

행 값에서는 샘플링 도구가 의도적인 예외입니다.
**Create Samples**와 **Random % Sample**은 모두 무작위로 추출하며, Alteryx는 시드가 설정되어 있으면
실행할 때마다 같은 레코드를 반환합니다. PlaidCloud는 자체 생성기로 추출하므로 다음과 같습니다.

- 샘플 크기, 백분율, Estimation / Validation / Holdout 분할
  비율은 그대로 유지됩니다.
- **각 샘플에 포함된 레코드는 Alteryx가 선택하는 레코드와 다르며, 다시 실행하면
  또 다른 집합이 선택됩니다.**

변환된 각 단계는 변환 보고서와 단계 자체에서 이 사실을 알리며,
변환에 실패한 도구로 보고되지는 않습니다. 이러한 단계는 행 값이 아니라 행 수와
비율로 검증하십시오.

어떤 레코드가 어떤 샘플에 들어가는지가 실제로 중요한 경우(정확히 재현해야 하는 모델이나
이미 결과를 게시한 홀드아웃)에는 대신 열로 샘플을 결정하십시오. 샘플 배정을 계산하는
**Formula** 단계와 샘플마다 하나의 **Filter** 단계를 사용합니다.

## 머신 러닝(Assisted Modeling) 변환

Machine Learning 도구군으로 만든 Alteryx 머신 러닝 파이프라인은 PlaidCloud의 기본 ML 단계로 변환됩니다.

- **Classification** 또는 **Regression** 도구는 업스트림의 Assisted Modeling 및 Transformation 단계, 다운스트림의 **Fit** 도구와 함께 하나의 [ML: 모델 학습](/ko/reference/workflow-steps/machine-learning/ml-train/) 단계로 통합됩니다. 이 단계는 Alteryx 워크플로의 정확한 알고리즘, 대상 변수, 특성 열, 하이퍼파라미터를 유지하며, 학습된 모델을 학습 지표가 기록된 한 행짜리 모델 테이블로 씁니다.
- 각 **Predict** 도구는 학습된 모델 테이블과 데이터 입력을 읽는 [ML: 점수 산출](/ko/reference/workflow-steps/machine-learning/ml-score/) 단계가 됩니다. 예측 열의 이름은 대상 변수 이름에 `_predicted` 접미사를 붙인 것입니다.
- **XGBoost 분류기**는 근사 참고 사항과 함께 변환됩니다. 모델은 scikit-learn 그래디언트 부스팅 분류기로 학습되며, 대응하는 기능이 없는 XGBoost 고유의 트리 매개변수는 단계의 매핑 참고 사항에 나열됩니다. 일치를 신뢰하기 전에 모델 지표를 Alteryx 실행 결과와 비교하여 검증하십시오.
- **Image Recognition** 도구는 워크플로 안에서 이미지 분류기를 학습하고 새 이미지를 이에 대해 점수화하며, 이 모든 과정이 제자리에서 이루어집니다. 외부 계정이 필요 없고 이미지 데이터가 PlaidCloud 밖으로 나가지 않습니다. 모델을 가리키는 다운스트림 **Predict**가 이에 대해 점수를 산출합니다. ML 계열의 나머지와 다르게 전달되는 점이 두 가지 있으므로, 일치를 신뢰하기 전에 검증하십시오. 첫째, 분류기는 Alteryx에서 복사한 것이 아니라 사용자가 레이블을 지정한 이미지로 다시 학습되며 이 학습은 비결정적입니다. 같은 워크플로를 두 번 변환하면 모델이 약간 다르게 만들어지므로 예측은 비트 단위로 일치하지 않고 충실한 근사입니다. 둘째, 학습은 CPU에서 실행되므로 이미지가 수백에서 수천 개 정도인 세트는 몇 분이 걸립니다. Image Recognition은 워크스페이스별로 활성화되므로, 변환된 워크플로가 활성화되지 않았다고 보고하면 관리자에게 켜 달라고 요청하십시오.
- **AutoML** 도구는 Classification 및 Regression과 같은 방식으로 [ML: 모델 학습](/ko/reference/workflow-steps/machine-learning/ml-train/) 단계로 통합됩니다. AutoML은 Alteryx 실행 시 후보 알고리즘 중 실제로 어떤 것이 선택되었는지 기록하지 않으므로, 변환은 자동 검색을 재현하는 대신 ML Train이 지원하는 선택된 첫 번째 알고리즘을 고르고 그 선택을 참고 사항으로 남깁니다. 변환된 AutoML 단계를 자체 Alteryx 결과와 비교하십시오.
- 모델을 대화형으로 선택했고 워크플로 파일에 저장하지 않은 **Assisted Modeling 마법사**는 변환할 수 없습니다. 가져오기 기능은 복구된 대상 변수가 참고 사항에 기록된 자리 표시자 단계를 유지하므로, ML Train 단계를 직접 구성할 수 있습니다.
- **독립형 원-핫 인코딩 단계**는 변환 보고서에 표시됩니다. 통합된 ML Train 단계가 범주형 특성을 내부적으로 원-핫 인코딩하므로, 독립형 단계는 대개 대체할 필요가 없습니다.

모든 변환과 마찬가지로 통합된 단계는 신뢰도와 참고 사항을 변환 보고서와 캔버스에 담고 있으므로, 다시 확인할 만한 파이프라인을 쉽게 찾을 수 있습니다.

## 변환 범위 검토

[Alteryx 변환 매트릭스](/ko/reference/alteryx-conversion-matrix/)에는 지원되는 각 Alteryx 개체, 해당 범위 수준, 변환 중에 사용되는 PlaidCloud 작업이 나열되어 있습니다.

매트릭스를 통해 가져오기 기능이 각 도구군을 처리하는 방식을 파악하십시오.

- 일반적인 데이터 준비, 조인, 필터, 수식, 정렬, 합집합, 샘플링, 형태 변환을 위한 기본 DAG 단계.
- 매크로 입력, 매크로 출력, 매크로 호출, 제어 매개변수, 매크로 동시 실행을 위한 매크로 단계.
- 확인란, 드롭다운, 텍스트 상자, 라디오 버튼, 폴더 선택기, 파일 선택기 같은 분석 앱 질문을 위한 제어된 워크플로 변수.
- 입력, 출력, 디렉터리, 동적 파일 동작을 위한 문서 기반 파일 작업.
- Assisted Modeling 머신 러닝 파이프라인을 위한 기본 ML Train 및 ML Score 단계.
- 각 Alteryx Calgary 데이터베이스를 위한 대체 테이블. 따라서 Calgary Loader, Input, Cross Count, Join 도구는 즉시 거부되는 대신 일반 테이블에 대해 변환됩니다. [Calgary 데이터베이스](#calgary-데이터베이스)를 참조하십시오.
- 특수한 공간, 퍼지 매칭, PDF, OCR, NLP, 보고, 아티팩트 작업을 위한 관리형 작업 실행기.
- Alteryx 전용 데스크톱 렌더러나 독점 파일 형식을 재현하는 대신 PlaidCloud가 오래 유지되고 공유할 수 있는 아티팩트를 만드는 클라우드 네이티브 대응 기능.

## Alteryx 커버리지 보고서

가입하기 전에 Alteryx 워크플로에 무엇이 있는지 확인하십시오.

1. 공개 페이지 `https://app.plaidcloud.com/#coverage-report`를 엽니다. 페이지 제목은 **See what's in your Alteryx workflows**입니다.
2. **Drop an Alteryx workflow here**에 파일을 끌어다 놓거나 **파일 선택**을 선택합니다. 워크플로(`.yxmd`), 매크로(`.yxmc`) 또는 패키지(`.yxzp`)를 최대 10MB까지 허용합니다. PlaidCloud가 파일을 읽고 발견한 도구와 가장 많이 사용된 도구를 표시합니다. 파일에 저장된 자격 증명은 제거됩니다.
3. **Work email**을 입력하고 서비스 약관과 개인정보 처리방침에 동의한 다음 **Email me a verification link**를 선택합니다.

전체 보고서는 사용자의 무료 PlaidCloud 워크스페이스에서 만들어집니다. PlaidCloud는 업로드한 파일을 **Alteryx migration**이라는 프로젝트로 변환하며, 첫 번째 워크스페이스 관리자가 홈을 열면 **Alteryx 커버리지 보고서**가 표시됩니다. 이 보고서에는 각 워크플로와 함께 PlaidCloud가 인식하여 변환할 수 있는 도구의 수, **검토 필요** 상태인 도구의 수, 변환된 워크플로를 여는 **열기** 버튼이 나열됩니다. 데이터 파일은 보고서에 포함되지 않으므로, 워크플로가 읽는 파일을 업로드한 다음 실행하십시오. 보고서의 버튼은 **자체 웨어하우스 사용**과 **마이그레이션 검증**으로 연결됩니다. 업로드한 파일은 7일 동안 보관됩니다.

이미 PlaidCloud 계정이 있으면 입력한 이메일 주소로 링크가 포함된 **Your coverage report is ready — sign in to view it** 메시지가 전송됩니다. 로그인하고 보고서를 연 다음 **워크스페이스**를 선택하고 **Add the report**를 선택하십시오. 워크스페이스 조직의 관리자만 추가할 수 있으며, 보고서는 다음에 워크스페이스를 열 때 열립니다. 이메일을 무시해도 워크스페이스에는 아무 변화가 없습니다. 유효하지 않거나 만료된 링크는 그렇다고 알려 주며, 만료된 업로드는 다시 업로드해야 합니다.

변환한 후에는 Alteryx 출력과 대조하여 [일치하는지 증명](/ko/guides/workflows/validate-converted-alteryx-workflows/#마이그레이션-검증)하십시오.

## 권장 마이그레이션 방법

대규모 포트폴리오는 배치로 나누어 마이그레이션하십시오.

1. 워크플로와 매크로를 마이그레이션 프로젝트로 가져옵니다.
2. 개별 수식이나 비즈니스 논리를 검토하기 전에 종속성 패키지를 완성합니다.
3. 배치 전체에서 구조 검증을 실행합니다.
4. 운영 워크플로, 규제 대상 워크플로, 다운스트림 소비자가 있는 워크플로에 대해 출력 일치 검증을 우선적으로 수행합니다.
5. 검증된 워크플로를 대상 운영 프로젝트로 승격합니다.
6. 운영 실행 일정을 등록하고 실행 이력을 모니터링합니다.
