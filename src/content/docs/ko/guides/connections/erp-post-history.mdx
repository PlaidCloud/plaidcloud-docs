워크플로가 ERP에 전기할 때(Sage Intacct 또는 NetSuite 분개, Acumatica, Business Central 또는 Xero 문서, Dynamics 365 Finance & Operations, Oracle Fusion, Workday Financials 또는 SAP S/4HANA Cloud 분개, SAP 문서) PlaidCloud는 같은 문서가 두 번 전기되지 않도록 각 전기 시도를 테넌트별 영구 원장에 기록합니다. **ERP 전기 이력**은 이 원장에 대한 읽기 전용 보기로, 모든 시도와 현재 상태를 ERP 자체의 문서 번호 및 타임스탬프와 함께 보여 주며 프로젝트별로 필터링할 수 있습니다.

이는 전기 단계가 기록하는 실행별 결과 테이블을 보완합니다. 결과 테이블은 한 번의 실행 결과이고, 전기 이력은 모든 실행과 워크플로에 걸친 상시 기록이며 실행이 끝난 시점에 고정되지 않고 각 전기를 전체 수명 주기에 걸쳐 추적합니다.

<Aside type="note">
전기 이력은 **읽기 전용**이며 전기나 원장을 변경하지 않습니다. REST API와 MCP 도구로 제공되며, 이미 액세스 권한이 있는 하나의 프로젝트로 범위가 한정됩니다. 볼 수 있는 권한이 있는 모든 프로젝트와 연결에 걸친 전기를 검토하는 테넌트 수준 화면은 [전기 등록부](/ko/guides/connections/posting-register/)를 사용하십시오.
</Aside>

## 각 전기에 표시되는 내용

각 행은 하나의 연결에서 하나의 ERP 환경에 전기된(또는 전기를 시도한) 문서 하나입니다.

| 필드 | 의미 |
|---|---|
| `project_id` | 전기를 수행한 프로젝트. |
| `connection_id` | 사용한 ERP 연결. |
| `environment_id` | 전기 대상 연결 환경(예: 샌드박스와 프로덕션). |
| `natural_key` | 전기 단계가 도출한 문서의 비즈니스 키. |
| `state` | 전기의 현재 수명 주기 상태(아래 참조). |
| `confirmation_id` | ERP가 문서 번호를 할당한 후의 ERP 자체 문서 번호. 시뮬레이션된 전기에는 설정되지 않습니다. |
| `run_id` | 전기를 수행한 워크플로 실행. |
| `submitted_at`, `created_at`, `updated_at` | 전기가 제출된 시각, 처음 기록된 시각, 마지막으로 변경된 시각. |

[시뮬레이션 모드](/ko/guides/workflows/run-a-workflow/#전기-모드-선택)에서 수행한 전기는 시뮬레이션됨으로 표시되어 실제 전기와 한눈에 구별됩니다. 아래의 [시뮬레이션된 전기](#시뮬레이션된-전기)를 참조하십시오.

## 수명 주기 상태

전기는 ERP가 처리하는 동안 다음 상태를 거쳐 이동합니다.

| 상태 | 의미 |
|---|---|
| `preflighted` | 검증되고 클레임되었으며 아직 ERP로 전송되지 않았습니다. |
| `submitted` | ERP로 전송되었으며 결과는 아직 알 수 없습니다. |
| `pending` | 비동기 처리를 위해 접수되었으며 최종 결과를 기다리고 있습니다. |
| `posted` | 전기가 확인되었으며 `confirmation_id`에 ERP 문서 번호가 들어 있습니다. |
| `rejected` | ERP가 전기를 거부했습니다. |
| `in_doubt` | 결과를 확인할 수 없습니다. 재시도하기 전에 사람이 ERP에서 직접 확인해야 합니다. |
| `reversed` | 이전에 전기된 문서가 역분개되었습니다. |

<Aside type="caution">
`in_doubt` 전기는 말 그대로 알 수 없는 상태이며 실패한 것이 아닙니다. 조치를 취할지 결정하기 전에 ERP 자체에서 확인하십시오. 무작정 다시 실행하지 마십시오.

PlaidCloud는 읽어 올 수 없는 시간 초과나 서버 오류, 인식하지 못하는 상태 등 ERP가 무엇을 했는지 알 수 없을 때마다 전기나 역분개를 `in_doubt`로 기록합니다. 이러한 응답을 `rejected`로 기록하지 않는데, 그렇게 하면 문서가 ERP에 있을 수도 있는데 없다는 인상을 주기 때문입니다.
</Aside>

## 시뮬레이션된 전기

[시뮬레이션 모드](/ko/guides/workflows/run-a-workflow/#전기-모드-선택)로 시작한 실행은 전기 단계가 보낼 내용을 검증하지만 ERP에는 접속하지 않습니다. 전기되었을 내용은 여전히 여기에 시뮬레이션됨으로 표시되어 기록되므로, ERP가 이를 본 적이 없어 `confirmation_id`가 없다는 점을 제외하면 `natural_key`와 만들어진 요청을 포함하여 실제 전기를 검토하는 것과 같은 방식으로 검토할 수 있습니다.

시뮬레이션된 항목은 실제 전기의 멱등 쓰기를 보호하는 슬롯을 차지하거나 막지 않습니다. 나중에 같은 문서를 실제로 실행하면 실제 전기가 진행되고 시뮬레이션된 레코드를 대체합니다. 전기 원장이 구성되지 않은 워크스페이스에서도 시뮬레이션 실행은 정상적으로 검증되며, 단지 여기에 아무것도 기록하지 않습니다.

프로젝트의 시뮬레이션된 항목을 실제 항목과 별도로 지우려면 `DELETE /rest/v1/analyze/erp/write/history/simulated?project_id=<project>`(`connection_id`로 범위를 좁힐 수 있음) 또는 같은 인수를 사용하는 `erp_clear_simulated_postings` MCP 도구를 사용하십시오. 어느 쪽이든 시뮬레이션된 행만 제거되며 실제 전기는 건드리지 않습니다. 한 번 지우면 양쪽에서 제거되므로 응답에는 지워진 이력 행과 [전기 등록부](/ko/guides/connections/posting-register/) 자체의 시뮬레이션 저장소 행이 모두 보고됩니다.

<Aside type="note">
SAP 전기, 첨부 파일 및 RFC 단계는 시뮬레이션 시 드라이 런이 아니라 완전히 건너뛰므로 시뮬레이션된 항목이 생성되지 않습니다. [전기 모드 선택](/ko/guides/workflows/run-a-workflow/#전기-모드-선택)을 참조하십시오.
</Aside>

## 이력 읽기

모든 읽기는 액세스할 수 있는 하나의 프로젝트로 범위가 한정됩니다. 해당 프로젝트에 대한 읽기 권한, 즉 나머지 프로젝트 작업에 필요한 것과 같은 권한이 필요합니다.

### REST로 읽기

```
GET /rest/v1/analyze/erp/write/history?project_id=<project>
```

선택적 쿼리 매개변수로 결과를 좁힐 수 있습니다.

| 매개변수 | 효과 |
|---|---|
| `connection_id` | 이 연결에서 수행한 전기만. |
| `state` | 이 상태의 전기만(예: `state=in_doubt`). |
| `limit` | 페이지 크기(기본값 100). |
| `cursor` | 이전 페이지의 `next_cursor`. |

결과는 최신순으로 반환됩니다. 페이지가 `limit`까지 채워지면 응답에 `next_cursor`가 포함됩니다. 이를 `cursor`로 다시 전달하여 다음 페이지를 읽고, `next_cursor`가 null이면 중지합니다.

### MCP로 읽기

같은 인수로 `erp_post_history` 도구를 호출합니다. `project_id`(필수)와 선택적 `connection_id`, `state`, `limit`, `cursor`를 사용합니다. 같은 행이 같은 방식으로 페이지 단위로 반환됩니다.

## 일반적인 검토

- **프로젝트에서 아직 불확실한 모든 항목:** `state=in_doubt` — ERP에서 직접 확인해야 하는 전기.
- **특정 실행이 전기한 내용:** 프로젝트의 이력을 읽고 `run_id`로 일치시킵니다.
- **문서가 실제로 전기되었는지 여부:** 해당 행을 찾아 `state`와 `confirmation_id`를 확인합니다.
