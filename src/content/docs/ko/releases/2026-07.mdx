## 추가됨

- **새로운 런처.** 이제 로그인하면 런처가 열립니다. 런처는 최근 프로젝트, 대시보드와 패널 앱, 고정한 항목, 마지막 실행이 실패한 워크플로를 한 페이지의 타일로 모아 보여 주며, 세 개의 레인으로 구성되어 바로 조치할 수 있습니다. 타일을 열고, 워크플로를 실행하고, 실패한 실행으로 이동하거나, 타일을 닫을 수 있습니다. 런처뿐 아니라 이미 사용 중인 목록과 문서 브라우저에서도 프로젝트, 워크플로, 테이블, 차원, 데이터 편집기, 대시보드, 패널 앱, 파일 또는 폴더 단위의 문서를 고정할 수 있습니다. 프로젝트 타일에는 프로젝트 요약(워크플로 실행, 워크플로, 테이블, 레코드)이 표시되며, 프로젝트의 홈 탭에서 **런처 타일 이미지**를 사용해 프로젝트별로 설정할 수 있는 흐릿한 배경 이미지가 들어갑니다. 타일 보기와 밀도 높은 목록 보기를 전환하고, 보고 싶지 않은 유형을 숨기고, **Ctrl/Cmd-K**를 눌러 입력하는 즉시 프로젝트, 워크플로, 테이블, 대시보드, 패널 앱을 검색할 수 있습니다. [런처](/ko/guides/launcher/)를 참조하십시오.

- **REST 요청 단계에 컬렉션이나 사양 붙여넣기.** Postman, OpenAPI/Swagger, HAR 소스마다 파일 선택기 옆에 **붙여넣기…** 버튼이 추가되어, 내용을 먼저 문서에 저장하지 않고 바로 입력할 수 있습니다. [REST 요청 단계](/ko/guides/workflows/rest-request-step/#파일을-선택하는-대신-컬렉션-또는-사양-붙여넣기)를 참조하십시오.

- **REST 연결에 API 정의 연결.** 일반 REST 및 MuleSoft 연결에 자체 OpenAPI 3.x 또는 Swagger 2.0 정의를 둘 수 있습니다. 게시된 주소를 사용하거나 문서에 보관한 사양 파일을 사용할 수 있습니다. 연결의 **API 정의**에서 한 번만 설정하면, 해당 연결을 사용하는 모든 REST 요청 단계에서 **엔드포인트 소스**를 **연결의 API 정의에서**로 지정하여 API의 엔드포인트를 나열할 수 있으며, 메서드, 매개변수, 본문이 자동으로 채워지므로 단계마다 정의를 다시 입력할 필요가 없습니다. [일반 REST 연결](/ko/reference/connectors/rest/generic-rest/#api-정의) 및 [REST 요청 단계](/ko/guides/workflows/rest-request-step/#연결의-api-정의-재사용)를 참조하십시오.

- **MuleSoft를 연결 유형으로 사용할 수 있습니다.** **새 연결** 메뉴에서 MuleSoft Anypoint 게이트웨이를 추가하고 다른 REST 연결과 똑같이 구성하십시오. 사용하는 게이트웨이 주소와 필요한 인증 방식을 지정하면 됩니다. [MuleSoft REST 커넥터](/ko/reference/connectors/rest/mulesoft/)를 참조하십시오.

- **PlaidCloud Git 연결.** 간소화된 양식으로 워크스페이스의 자체 관리형 Git 서버에 연결합니다. 계정 이름, 메모, 리포지토리 경로, 기본 브랜치, 선택 사항인 시작 경로만 입력하면 되며, 서버 URL, 사용자 이름, 토큰, SSH 키는 입력할 필요가 없습니다. Git 서버와 그에 대한 액세스 권한이 일반 PlaidCloud 로그인에서 제공되기 때문입니다. Server Panel 앱의 빌드가 PlaidCloud Git 연결을 가리키도록 하면 외부 GitHub 계정이나 액세스 토큰 없이 워크스페이스 안에서 빌드를 완전히 자동화할 수 있습니다. 외부 Git 공급자(GitHub, GitLab, Bitbucket, Forgejo, Gitea)는 기존의 전체 연결 양식을 그대로 사용합니다. [PlaidCloud Git 연결](/ko/guides/connections/plaidcloud-git/)을 참조하십시오.

- **통화 — 금액을 위해 만들어진 열 데이터 유형.** 모든 열 데이터 유형 목록(단계 출력 열 매핑, 데이터 매퍼 그리드, 테이블의 **열 속성**, MCP/AI 도구)에서 이제 **통화**를 선택할 수 있습니다. 통화는 정밀도 18자리, 소수점 이하 4자리(대략 ±100조, 1/10,000 단위까지 정확)의 정확한 고정 소수점 유형입니다. 메모리 내 너비가 숫자(Numeric)의 절반이므로, 금액 중심의 대시보드와 워크플로 단계는 스캔하는 데이터가 약 절반으로 줄어 더 빠르게 실행됩니다. 숫자는 여전히 고정밀 기본 유형(38자리, 소수점 이하 10자리)으로 유지됩니다. 통화는 항상 사용자가 명시적으로 선택하는 유형이며, 가져오기, 유형 감지, SQL 결과, 파생 열은 계속 숫자를 기본값으로 사용합니다. 열에 한 번 설정하면 읽기, 다운스트림 단계, 테이블 재구축을 거쳐도 유지됩니다. 통화의 집계 결과는 숫자로 반환됩니다. 이 옵션은 플랫폼 업데이트가 워크스페이스에 적용된 후에 나타납니다. [통화 데이터 유형](/ko/guides/data/currency-data-type/)을 참조하십시오.

- **변경되지 않은 소스 파일의 재가져오기 건너뛰기** — 파일 가져오기 단계(CSV, Excel, 고정 너비, JSON, Avro, Parquet, Alteryx yxdb, dbf, XML, Access)에 새로운 **소스 파일이 변경되지 않았으면 다시 가져오기 건너뛰기** 옵션이 추가되었습니다. 이 옵션을 켜면 소스 파일과 단계 설정이 마지막으로 성공한 실행 이후 변경되지 않은 경우 워크플로 실행에서 다운로드, 변환, 테이블 재구축 전체를 건너뛰므로, 예약된 다시 로드가 같은 작업을 반복하지 않습니다. **기본적으로 켜져 있습니다.** 항상 다시 가져오려면 단계에서 이 옵션의 선택을 해제하십시오. 변경 여부는 각 파일의 크기와 수정 시간으로 감지하며, 소스에서 제공하는 경우 콘텐츠 해시도 함께 사용합니다. 수동으로 한 번 실행하는 가져오기는 항상 실행됩니다. [CSV 가져오기](/ko/reference/workflow-steps/import/import-csv/)를 참조하십시오.

- **워크플로의 머신 러닝 — ML: 모델 학습 및 ML: 점수 산출 단계.** 어떤 테이블로든 모델을 학습시키고(선형 회귀와 로지스틱 회귀, 의사 결정 트리, 랜덤 포레스트, 그래디언트 부스팅 등 일곱 가지 알고리즘 중에서 선택), 그 모델로 데이터에 점수를 매겨 예측 열을 추가하는 작업을 모두 워크플로 안에서 수행합니다. 학습된 모델은 다른 테이블과 마찬가지로 워크플로를 따라 흐르며, 알고리즘, 설정, 특성, 학습 지표가 함께 기록됩니다. 알고리즘이나 설정을 잘못 입력하면 단계를 저장할 때 오류로 알려 줍니다. [ML: 모델 학습](/ko/reference/workflow-steps/machine-learning/ml-train/) 및 [ML: 점수 산출](/ko/reference/workflow-steps/machine-learning/ml-score/)을 참조하십시오.

- **PlaidCloud 관리형 버킷 문서 계정.** 클라우드 프로젝트, 자격 증명, 리전, 스토리지 티어를 설정하거나 조정할 필요 없이 한 단계로 완전 관리형 파일 스토리지를 문서에 추가합니다. Business 및 Enterprise 요금제에서 사용할 수 있습니다. [PlaidCloud 관리형 버킷 계정 추가](/ko/guides/documents/adding-accounts/add-managed-bucket-account/)를 참조하십시오.

- **최소 권한 액세스로 OneDrive 또는 SharePoint 사이트 연결.** Microsoft 관리자가 명시적으로 권한을 부여한 사이트에만 접근할 수 있는 문서 계정으로 OneDrive for Business 또는 SharePoint 사이트를 추가합니다. 이는 Microsoft 365 테넌트 전체가 아니라 Microsoft의 Sites.Selected 모델을 사용합니다. 계정의 서비스로 OneDrive를 선택하고, 앱 등록의 클라이언트 ID, 비밀, 테넌트 ID를 입력하고, 권한이 부여된 사이트의 URL을 붙여넣은 다음, 해당 사이트의 문서 라이브러리 중 하나를 시작 폴더로 선택합니다. 권한을 부여하지 않은 사이트(급여, 인사 등)에는 전혀 접근할 수 없습니다. [OneDrive / SharePoint 계정 추가](/ko/guides/documents/adding-accounts/add-onedrive-account/)를 참조하십시오.

- **더욱 강력해진 REST 요청 단계.** 이제 REST 요청은 드라이버 테이블의 행마다 호출을 분산할 수 있습니다. 행당 요청 하나를 보내며, 선택적으로 행 필터를 지정할 수 있고, 키 열을 결과로 가져옵니다. 동시성 제한, 요청 속도 상한, 안전한 재실행을 위한 선택형 멱등성 키, 오류 발생 시 계속 진행 옵션, 행별 실패에 대한 명확한 보고도 제공합니다. 새로운 작성 보조 기능으로 요청을 더 쉽게 만들고 확인할 수 있습니다. curl 명령에서 가져오기, 변수 토큰 삽입 및 강조 표시(드라이버 테이블의 열 포함), 첫 번째 분산 행 테스트, 실행 전에 확정된 요청과 페이지 매김 미리 보기, 저장하지 않은 초안 복원, 선택한 연결 제자리 편집, 성공적으로 테스트하지 않은 요청을 저장하기 전 확인을 지원합니다. [REST 요청 단계](/ko/guides/workflows/rest-request-step/)를 참조하십시오.

- **확장된 도움말 및 지원 환경.** 티켓과 답글에 스크린샷과 파일을 첨부할 수 있고(이미지는 인라인으로 표시됨), 정렬과 필터가 가능한 지원 콘솔에서 티켓을 처리할 수 있습니다(답변, 내부 메모 추가, 담당 지정, 우선순위 설정, PlaidCloud로 에스컬레이션). 새 티켓 알림을 Slack, Teams 또는 이메일 채널로 보내고, 티켓에 답글이 달리면 티켓 소유자에게 이메일을 보내며, 너무 오래 응답이 없는 티켓을 자동으로 에스컬레이션합니다. [도움 받기](/ko/guides/support/getting-help/), [지원 콘솔](/ko/guides/support/support-console/), [지원 관리](/ko/guides/support/managing-support/)를 참조하십시오.

- **AI 질문을 위한 분석 경로.** 가장 자주 분석하는 테이블에 알아보기 쉬운 이름을 붙이고 그중 하나를 기본값으로 지정하면, 매번 프로젝트와 테이블을 지정하지 않고도 사용자와 AI 어시스턴트가 "Operations Results"에 대해 묻거나 그냥 "지난 분기에 무엇이 바뀌었나요?"라고 물을 수 있습니다. Microsoft 365 Copilot과 MCP로 연결된 모든 에이전트에서 작동합니다. [분석 경로](/ko/integrations/ai-coding-agents/analysis-paths/)를 참조하십시오.

- **더 똑똑하고 더 정직한 AI 배부 비용 추적.** MCP로 연결된 AI 에이전트에게 배부 결과가 왜 바뀌었는지 물으면, 이제 답변에 쉬운 말로 된 신뢰 수준과 유의 사항이 함께 제공됩니다. 원인이 서로 겹치는 여러 요인의 혼합인 경우, 현재 계층이나 드라이버 가중치에 따라 달라지는 경우, 변화의 일부가 단지 완료되지 않은 데이터 로드 때문일 수 있는 경우를 알려 주며, 이러한 신뢰 신호는 후속 에이전트가 답변을 요약하더라도 그대로 전달됩니다. 관리자는 풀 또는 드라이버 데이터가 최근에 다시 로드되지 않은 경우 신뢰도를 낮추고 답변에 표시하는 선택형 검사를 켤 수도 있습니다. 여러 배부 브랜치로 만들어진 결과의 경우, 신뢰도는 이제 각 브랜치가 변화에서 차지하는 비중에 따라 가중되므로, 작고 불안정한 브랜치 하나가 그 외에는 깨끗한 답변의 신뢰도를 끌어내리지 않습니다. 드라이버 가중치 변경 가정 질문("이 비용 센터의 인원이 두 배가 되면 어떻게 됩니까?")도 할 수 있으며, 전체 근본 원인 분석을 AI 에이전트뿐 아니라 REST API로도 실행할 수 있습니다. [MCP로 연결된 AI 에이전트로 배부 추적하기](/ko/integrations/ai-coding-agents/tracing-allocations/)를 참조하십시오.

- **신뢰할 수 있고 AI가 검증할 수 있는 서면 추적 요약.** MCP로 연결된 AI 에이전트에게 배부 결과가 왜 바뀌었는지 물으면, 이제 **분석에서 직접 만들어진 쉬운 말의 요약**을 반환할 수 있습니다. 이 요약은 신뢰 수준을 명시하고, 모든 유의 사항을 포함하며, 실제 쿼리에서 나오지 않은 수치는 인용하지 않습니다. 함께 제공되는 **충실도 검사**를 통해 에이전트는 자신이 다시 표현한 버전이 신뢰도와 모든 유의 사항을 유지했고 없는 내용을 만들어 내지 않았는지 확인할 수 있으므로, 서술은 단순히 매끄러운 것을 넘어 *입증 가능하게* 충실합니다. 각 요약은 자연스러운 다음 질문도 제안합니다. 단일 멤버로 범위 좁히기, 차원별로 변화 분해하기, 결과 테이블이 둘 이상의 단계로 만들어진 경우 특정 생성 단계 지정하기가 그 예이므로, 정확한 표현을 몰라도 더 깊이 파고들 수 있습니다. [신뢰할 수 있는 답변](/ko/integrations/ai-coding-agents/honest-answers/)을 참조하십시오.

- **시각적 워크플로 디자이너에서 단계 데이터 미리 보기.** 새 창을 열지 않고 단계의 출력을 그 자리에서 확인합니다. 처음 100개 행의 미리 보기를 유형이 지정된 열, 행 수와 열 수, 다중 출력 단계용 선택기와 함께 캔버스 아래쪽에 고정할 수 있습니다. 다른 단계를 클릭하면 미리 보기 대상이 바뀌고, 실행이 끝나면 새로 고쳐지며, 한 번의 클릭으로 전체 테이블 탐색기를 열 수 있습니다. [단계 데이터 미리 보기](/ko/guides/workflows/preview-step-data/)를 참조하십시오.

- **실수로 인한 변경으로부터 Panel 앱 잠그기.** 내 Panel 앱의 각 행에 있는 잠금 아이콘은 기존의 워크플로 및 단계 잠금과 같은 방식으로 앱을 보호합니다. 잠겨 있는 동안에는 편집, 제거, 다시 빌드가 실행되지 않으며 서버 앱 브랜치에 대한 git 푸시도 더 이상 앱을 다시 빌드하지 않습니다. 반면 앱 열기, 로그, 사용량 지표는 계속 작동합니다. 이는 보안 통제가 아니라 실수를 막기 위한 보호 장치이며, Panel 앱을 편집할 수 있는 사람은 누구나 잠금을 해제할 수 있습니다. [앱 잠그기](/ko/guides/panel-apps/using/#앱-잠그기)를 참조하십시오.

- **워크플로 단계에 자동으로 번호가 매겨집니다.** 이제 모든 단계에 번호가 있습니다. 시각적 캔버스의 배지, 단계 그리드의 첫 번째 열, 실행 로그, 워크플로 문서 보고서, AI 어시스턴트 목록에 같은 "단계 7"이 표시되므로, 복잡하게 가져온 워크플로에서 이름으로 단계를 설명하는 대신 팀원이나 AI 에이전트에게 "단계 7"을 가리켜 알려 줄 수 있습니다. 번호는 흐름을 따르며(단계는 항상 자신에게 입력을 공급하는 단계보다 뒤에 번호가 매겨짐), 캔버스 위치는 왼쪽에서 오른쪽, 위에서 아래 순서로 동순위를 결정하고, 워크플로를 편집하는 동안 모든 사용자의 캔버스에서 번호가 실시간으로 다시 매겨지며 번호가 바뀐 단계는 잠시 강조 표시됩니다. 단계를 마우스 오른쪽 버튼으로 클릭하거나 배지를 클릭하면 "단계 7 — Clean Customer Names"와 같이 바로 붙여넣을 수 있는 참조를 복사할 수 있습니다. [단계 번호](/ko/guides/workflows/step-numbers/)를 참조하십시오.

- **새 워크플로 단계 두 가지 — 디렉터리 목록과 행 수 검증.** 디렉터리 목록은 문서 디렉터리의 파일을 나열한 테이블(선택적 파일 패턴과 하위 디렉터리 옵션 포함)을 작성하므로, 다운스트림 단계가 현재 존재하는 파일에 따라 동작할 수 있습니다. 행 수 검증은 두 테이블의 행 수가 다르면 워크플로를 실패시키는 데이터 품질 게이트입니다. [디렉터리 목록](/ko/reference/workflow-steps/document/directory-listing/) 및 [행 수 검증](/ko/reference/workflow-steps/workflow-control/row-count-assert/)을 참조하십시오.

- **시각적 워크플로 디자이너에서 워크플로 로그로 바로 이동.** 캔버스 도구 모음의 **로그 보기** 버튼은 열려 있는 워크플로로 이미 필터링된 프로젝트 로그 보기를 엽니다. 프로젝트 영역에서 접근하던 것과 같은 전체 실행 로그입니다. [고급 워크플로](/ko/guides/workflows/advanced-workflows/#로그-보기)를 참조하십시오.

## 변경됨

- **Table Update는 소스를 변경하는 대신 대상 테이블에 씁니다.** 이전에 **Table In-Place Update**였던 단계의 이름이 이제 **Table Update**이며, **새 단계** 메뉴에 다시 표시됩니다. 소스를 읽고, 필터와 일치하는 행을 업데이트하고, 변경된 행과 변경되지 않은 행을 모두 선택한 대상 테이블에 쓰며, 비교할 수 있도록 소스는 그대로 둡니다. 대상의 열은 단계를 마지막으로 연 이후 업스트림에서 추가된 열까지 포함하여 항상 소스의 열을 그대로 반영합니다. 더 이상 제자리에서 업데이트하지 않으므로, 테이블을 제자리에서 변경할 수 없는 웨어하우스를 포함한 모든 웨어하우스에서 실행됩니다. 뷰도 유효한 대상입니다. 이 변경 이전에 저장된 단계는 실행하기 전에 대상 테이블을 선택해야 하며, 업데이트된 행을 기대하며 소스를 읽던 단계는 새 대상을 가리키도록 변경해야 합니다. [Table Update](/ko/reference/workflow-steps/tables/table-update/)를 참조하십시오.

- **다중 테이블 조인이 동적 소스 및 대상 테이블을 허용합니다.** 테이블 선택기에서 **동적**을 선택하고 목록에서 고르는 대신 테이블 이름이나 프로젝트 경로를 입력하십시오. 둘 다 워크플로가 실행될 때 확정되는 `{variable}` 토큰을 포함할 수 있으므로, 조인이 `/03 Results/FACT_GL_{year}`에 쓰고 기간마다 다른 테이블을 가져올 수 있습니다. 대상이 없으면 생성됩니다. 다른 모든 단계의 테이블은 이미 이런 방식으로 작동했으며, 다중 테이블 조인은 이전에 목록에서 선택한 테이블이 필요했고 그렇지 않으면 저장할 수 없었습니다. 동적 소스의 열은 설계 시점에 읽을 수 없으므로 측면 패널에서 직접 입력합니다. [다중 테이블 조인 단계](/ko/guides/workflows/multi-table-join-step/)를 참조하십시오.

- **다중 테이블 조인의 출력 열에 식이나 상수를 사용할 수 있습니다.** 이제 출력 열의 값은 소스 열(해당 열을 소유한 캔버스 별칭 포함), **상수**, **식**의 세 가지 중 정확히 하나에서 가져옵니다. **표현식 열 추가**는 행을 추가하고, 열 브라우저에 캔버스의 모든 테이블이 표시되는 전체 식 편집기를 열므로, 하나의 값이 조인된 여러 테이블에 걸칠 수 있습니다. **조인 후 필터**는 이제 일반 텍스트 상자가 아니라 같은 편집기이며, `result.column_name`으로 참조할 수 있는 출력 열을 나열합니다. 편집기는 세 개의 탭으로 줄어듭니다. 내부 전용인 **고급(서버 설정)** 탭은 없어졌으며, 해당 설정은 저장할 때 그대로 유지됩니다. [다중 테이블 조인 단계](/ko/guides/workflows/multi-table-join-step/)를 참조하십시오.

- **파일 가져오기가 대용량 파일을 처리하고 소스 데이터 유형을 유지합니다.** Excel, JSON, Parquet, Alteryx yxdb, dBASE, 고정 너비 파일 가져오기는 더 이상 파일 전체를 메모리에 로드하지 않으므로, 이전에 메모리 부족 오류로 실패하던 대용량 파일도 가져올 수 있습니다. 실질적인 한계는 메모리가 아니라 디스크 공간입니다. 소스의 데이터 유형(소수, 날짜, 타임스탬프)은 텍스트를 거치지 않고 대상 테이블로 그대로 전달되며, Parquet 타임스탬프 열은 시간 정밀도를 모두 유지합니다(이전에는 날짜로 잘렸음). 의도적으로 변경하지 않은 부분도 있습니다. 비어 있는 숫자 셀은 여전히 0으로 로드되고, 파일 이름, 경로, 워크시트 이름, 행 번호, 마지막 수정 열은 이전과 정확히 동일하게 동작하며, 행 번호는 소스 파일별로 계산됩니다. [Excel 가져오기](/ko/reference/workflow-steps/import/import-excel/), [JSON 가져오기](/ko/reference/workflow-steps/import/import-json/), [Parquet 가져오기](/ko/reference/workflow-steps/import/import-parquet/)를 참조하십시오.

- **JSON 가져오기가 줄 바꿈으로 구분된 파일을 허용하고 표준 JSON 텍스트를 생성합니다.** JSON 가져오기 단계는 이제 JSON 배열뿐 아니라 줄 바꿈으로 구분된 JSON(NDJSON, 한 줄에 객체 하나)도 허용하며, 중첩된 객체와 배열은 Python 스타일 표기가 아니라 표준 압축 JSON 텍스트로 테이블에 들어가므로, 다운스트림 단계에서 어떤 JSON 도구로든 구문 분석할 수 있습니다. [JSON 가져오기](/ko/reference/workflow-steps/import/import-json/)를 참조하십시오.

- **Git 연결의 리포지토리, 브랜치, 폴더 선택.** Git 연결 양식은 더 이상 리포지토리 경로, 브랜치 이름, 시작 경로를 직접 입력하도록 요구하지 않으며, 실시간 목록에서 선택합니다. 서버와 자격 증명을 입력하고(PlaidCloud Git 연결은 입력할 것이 없음), 새로 고침을 클릭하여 연결이 접근할 수 있는 리포지토리를 나열하고, 하나를 선택하여 브랜치를 로드한 다음, 폴더를 탐색하여 선택 사항인 시작 경로를 설정하므로, 잘못 입력한 이름 때문에 연결이 조용히 깨지는 일이 없습니다. 기존 연결을 편집할 때는 저장된 암호를 다시 입력하지 않고도 탐색할 수 있습니다. PlaidCloud Git과 모든 외부 공급자(GitHub, GitLab, Bitbucket, Forgejo, Gitea)에 적용됩니다. [PlaidCloud Git 연결](/ko/guides/connections/plaidcloud-git/)을 참조하십시오.

- **AI 비용 추적이 더 정확해졌고 오도되기 어려워졌습니다.** 가정 추정치는 이제 상한이 아니라 분산된 대상 전체에 걸쳐 합산되는 실제 대상별 수치이며, 단일 대상으로 범위를 좁힐 수 있습니다. 입력 풀 대신 드라이버 또는 기준 테이블을 가리키면 에이전트가 추정을 거부하고 그 이유를 설명합니다. 드라이버 가중치 변경 가정은 정확합니다. 드라이버가 실제로 나누는 금액만 이동하고 그대로 통과하는 비용은 건드리지 않습니다. 에이전트는 이제 오해를 부르는 형태를 인식하고 신뢰도를 낮춥니다. 큰 증감이 상쇄되어 순변화가 작은 합계, 또는 드라이버가 좌우하는 것이 아니라 대부분 통과하는 변화가 그 예이며, 드라이버가 통제하는 금액이 실제로 얼마나 움직였는지를 명시하고, 분할이 신뢰할 수 없을 때 단일 "지배적 요인"을 과장하지 않습니다. 또한 차원 계층 배부를 귀속되지 않은 채로 두지 않고 설명합니다. 데이터 최신성 검사는 이제 드라이버 및 기준 테이블까지 포함하고, 둘 이상의 배부 단계로 만들어진 결과는 단계를 선택하여 추적하거나(필터가 한 단계에서만 생성된 행으로 좁혀지면 자동으로) 추적할 수 있으며, 이전 연도 데이터가 없는 전년 대비 비교는 변화를 "정상"이라고 부르는 대신 그 사실을 알려 줍니다. [MCP로 연결된 AI 에이전트로 배부 추적하기](/ko/integrations/ai-coding-agents/tracing-allocations/)를 참조하십시오.

- **외부 테이블: 소스에서 단일 테이블의 열 새로 고침.** 외부 테이블 가져오기 및 내보내기 단계에서 테이블별 **소스 검사** 버튼은 이제 연결된 데이터베이스에서 선택한 테이블의 현재 열을 바로 읽어 해당 테이블의 매핑만 제자리에서 업데이트합니다. 단계를 만든 이후 소스 테이블의 열이 바뀐 경우, 전체 연결에 대해 검색을 다시 실행하지 않고도 유용합니다. [외부 데이터베이스 테이블 가져오기](/ko/reference/workflow-steps/import/import-external-database-tables/)를 참조하십시오.
- **시각적 워크플로 디자이너의 접속 현황에 실제 아바타가 표시됩니다.** 여러 사람이 같은 고급 워크플로를 열어 두면, 도구 모음의 접속 현황 행에 각 사람이 gravatar(없으면 이니셜)로 표시되며, 한 사람이 여러 브라우저 탭에서 열어 두어도 한 번만 표시됩니다. [고급 워크플로](/ko/guides/workflows/advanced-workflows/#접속-중인-사용자)를 참조하십시오.

- **Server Panel 앱을 열 때 실제 진행 상황이 표시됩니다.** 이전의 대기 화면은 시작하는 동안 하나의 메시지만 표시하다가 일반적인 시간 초과를 알렸으므로, 전혀 시작되지 못하는 앱이 단순히 느린 앱과 똑같아 보였습니다. 이제 시작 중, 준비 중, 로드 중 같은 실제 단계를 보고하고, 실제 실패는 근본 원인과 함께 몇 초 안에 보고하며, 앱이 이미 준비되어 있으면 곧바로 통과시킵니다. 시작은 되었지만 로드 중에 실패하는 앱(예: 패키지 누락)은 빈 페이지를 제공하는 대신 오류와 함께 실패로 보고됩니다. [Panel 앱 만들기](/ko/guides/panel-apps/creating/)를 참조하십시오.

## 수정됨

- **Table Update가 저장할 때 Null로 설정을 더 이상 버리지 않습니다.** 열 매퍼는 업데이트하는 열을 **소스 열** 제목 아래에 나열하고, **대상 열**은 비워 두었으며, **Null로 설정** 컨트롤은 전혀 제공하지 않았습니다. 그리고 단계를 저장하면 Null로 설정이 지정된 모든 열에서 이 설정이 조용히 사라져 해당 값이 더 이상 지워지지 않았습니다. 이제 매퍼는 상수, 식, Null로 설정과 함께 **업데이트 열** 제목을 표시하고 네 가지를 모두 유지합니다. 이전에 열을 비우던 단계가 있다면 Null로 설정이 여전히 선택되어 있는지 확인하십시오. [Table Update](/ko/reference/workflow-steps/tables/table-update/)를 참조하십시오.

- **Table Upsert가 StarRocks 워크스페이스에서 API로 작동합니다.** 해당 워크스페이스가 사용하는 병합은 워크플로 엔진에서는 접근할 수 있었지만 REST API에서는 접근할 수 없었고, API는 이 경로에서 사용하지 않는 문을 계속 요구했으므로 그곳에서는 API로 업서트를 실행할 수 없었습니다. [Table Upsert](/ko/reference/workflow-steps/tables/table-upsert/)를 참조하십시오.

- **매크로 안의 Table Upsert가 이제 잘못된 테이블에 쓰지 않고 중지됩니다.** StarRocks 워크스페이스에서는 매크로의 복사본이 아니라 프로젝트 자체 테이블에 조용히 병합했습니다. 이제 명확한 오류를 보고하며, 근본적인 제한이 해결될 때까지 해당 워크스페이스에서 매크로 업서트는 사용할 수 없습니다. [Table Upsert](/ko/reference/workflow-steps/tables/table-upsert/)를 참조하십시오.

- **다중 테이블 조인 단계를 저장할 때 수정해야 할 항목을 알려 줍니다.** 해결해야 할 항목이 남은 채 저장하면 무엇이 잘못되었는지 알려 주는 대신 내부 오류로 실패했습니다. 이제 첫 번째 문제가 있는 탭으로 전환하고 모든 문제를 나열하며, 각 탭에 문제 수 배지가 표시됩니다. **캔버스에서 선택…** 옵션의 선택기는 더 이상 단계 양식 뒤에 열려 접근할 수 없는 일이 없습니다. [다중 테이블 조인 단계](/ko/guides/workflows/multi-table-join-step/)를 참조하십시오.

- **동적 Excel 가져오기가 다시 작동합니다.** 저장된 열 매핑이 아니라 워크시트에서 열을 검색하도록 구성된 Excel 가져오기가 실행할 때마다 실패했습니다. 이제 구성된 대로 가져옵니다. [Excel 가져오기](/ko/reference/workflow-steps/import/import-excel/)를 참조하십시오.

- **빈 워크시트가 여러 워크시트 Excel 가져오기를 더 이상 실패시키지 않습니다.** Excel 가져오기가 여러 워크시트를 다루는데 그중 하나가 비어 있으면, 이제 단계 전체를 실패시키는 대신 해당 워크시트에서 행을 0개 로드하고 계속 진행합니다. [Excel 가져오기](/ko/reference/workflow-steps/import/import-excel/)를 참조하십시오.

- **JSON 가져오기가 대용량 문서의 뒷부분에 나타나는 열을 더 이상 누락하지 않습니다.** 첫 번째 값이 대용량 JSON 파일의 깊은 위치에서 나타나는 열이 가져온 테이블에서 조용히 누락될 수 있었습니다. 이제 문서의 모든 열이 포함됩니다. [JSON 가져오기](/ko/reference/workflow-steps/import/import-json/)를 참조하십시오.
- **AI 어시스턴트가 실행 시 실패하는 식을 더 이상 승인하지 않습니다.** 일부 식 함수는 Python 키워드와 이름이 같으며(`IF`, `AND`, `OR`, `NOT`) 끝에 밑줄을 붙여 `func.if_(...)`와 같이 작성합니다. 어시스턴트는 이를 거꾸로 알고 있었습니다. 실제 함수가 아니어서 실행 시 실패하는 `func._if(...)`를 승인하고, 올바른 `func.if_(...)`는 거부했습니다. 이제 작동하는 형식은 받아들이고 작동하지 않는 형식은 거부하며, 잘못 입력하면 올바른 철자를 알려 줍니다. 초안을 작성할 때 참조하는 함수 참조도 이에 맞게 수정되었습니다. [IF](/ko/reference/expressions/lakehouse-v2/06-condition-functions/if/)를 참조하십시오.

- **기본, API 키 또는 Bearer 토큰 인증을 사용하는 REST 연결이 이제 실제로 인증합니다.** OAuth 2.0 자격 증명만 전송되었으므로, 나머지 세 가지 중 하나로 구성된 연결은 인증을 확인하는 API에서 실패했습니다. 이제 네 가지 모두 구성된 대로 작동합니다. **기본 헤더**에 자격 증명을 직접 넣어 우회했다면, 이제 연결 자체의 인증이 우선하므로 해당 행을 제거해도 됩니다. [일반 REST 연결](/ko/reference/connectors/rest/generic-rest/#인증)을 참조하십시오.

- **Postman 컬렉션 또는 API 사양에서 엔드포인트 나열이 다시 작동합니다.** REST 요청 단계에서 **카탈로그 로드**가 문서에서 선택했든 주소에서 가져왔든 모든 소스(Postman 컬렉션과 OpenAPI/Swagger 사양)에 대해 오류를 보고했습니다. 이제 엔드포인트를 다시 나열하며, 아직 선택하지 않은 경우에는 먼저 파일이나 주소를 선택하라고 알려 줍니다. [REST 요청 단계](/ko/guides/workflows/rest-request-step/)를 참조하십시오.

- **REST 연결의 기본 헤더가 이제 실제로 전송됩니다.** REST 연결의 **기본 헤더**에 설정한 헤더가 단계의 요청 미리 보기에는 표시되었지만 실제 요청에서는 빠져 있었습니다. 이제 해당 연결을 통한 모든 요청과 함께 전송되며, 페이지 매김 읽기의 각 페이지와 행별 분산의 각 요청도 포함됩니다. 개별 단계에 설정한 헤더는 연결에 있는 같은 이름의 헤더보다 우선합니다. 기본 헤더가 구성된 연결이 있다면 전송하려는 내용이 맞는지 확인하십시오. [일반 REST 연결](/ko/reference/connectors/rest/generic-rest/#기본-헤더)을 참조하십시오.

- **Server Panel 앱의 리포지토리에 푸시하면 이제 앱이 다시 빌드됩니다.** PlaidCloud Git 또는 GitHub 연결에서 Server Panel 앱을 게시하는 것은 항상 작동했지만, 이후 연결 브랜치에 대한 푸시는 반영되지 않았습니다. 누군가 수동으로 다시 게시할 때까지 앱이 처음 빌드된 버전을 계속 제공했습니다. 이제 [Git에서 Panel 앱 배포](/ko/guides/panel-apps/deploy-from-git/)에 설명된 대로 푸시하면 자동으로 다시 빌드하고 다시 배포합니다. 잠긴 앱은 잠금을 해제할 때까지 계속 다시 빌드를 건너뜁니다. 기존 앱이나 연결은 변경할 필요가 없습니다.

- **단계 실행 조건의 이름 바꾸기가 다시 작동합니다.** 단계가 실행되기 전에 충족해야 하는 조건을 설정할 때 이제 각 조건의 이름을 바꿀 수 있습니다. 구성 패널의 새 **이름** 필드를 편집하거나 목록에서 조건을 두 번 클릭하십시오. 조건을 마우스 오른쪽 버튼으로 클릭하면 **이름 바꾸기**와 **삭제**도 사용할 수 있습니다. [단계의 실행 조건](/ko/guides/workflows/step-conditions/)을 참조하십시오.

- **가져오기에서 열을 읽을 수 없을 때 더 명확한 오류가 표시됩니다.** CSV 또는 텍스트 가져오기를 설정하거나 자동으로 만들 때 PlaidCloud가 소스 파일에서 열을 하나도 읽을 수 없으면(예: 일부 Microsoft Access 텍스트 내보내기, 또는 구분 기호나 따옴표가 맞지 않는 파일), 이제 단계를 실행해 나중에 혼란스러운 메시지와 함께 실패하게 두지 않고 가져오기를 저장하거나 만드는 즉시 바로 알려 줍니다. 구분 기호, 따옴표, 이스케이프 설정을 조정하거나 파일을 수정한 다음 다시 시도하십시오. [CSV 가져오기](/ko/reference/workflow-steps/import/import-csv/)를 참조하십시오.

- **관리형 버킷 이름 충돌을 이제 알기 쉽게 설명합니다.** 이미 사용 중인 버킷 이름으로 PlaidCloud 관리형 버킷 문서 계정을 만들면 이전에는 일반적인 "내부 서버 오류"로 실패했습니다. 이제 **버킷 이름** 필드가 충돌을 직접 표시하고 버킷 이름은 전역적으로 고유해야 한다고 설명하며, 회사 이름을 접두사로 추가하는 등 더 구체적인 이름을 고르는 방법을 안내합니다. [PlaidCloud 관리형 버킷 계정 추가](/ko/guides/documents/adding-accounts/add-managed-bucket-account/)를 참조하십시오.

- **OneDrive 및 SharePoint 문서 계정 — 탐색 및 다운로드 수정.** 구성된 OneDrive 또는 SharePoint 문서 계정을 열면 이제 오류로 실패하지 않고 안정적으로 폴더와 파일을 나열하며, Microsoft 관리자가 사이트의 링크 공유를 꺼 둔 경우에도 파일 다운로드가 작동합니다. 다운로드가 더 이상 공유 링크 생성에 의존하지 않으므로, 잠긴 사이트의 파일도 오류 없이 열립니다. [OneDrive / SharePoint 계정 추가](/ko/guides/documents/adding-accounts/add-onedrive-account/)를 참조하십시오.

- **가져오기가 읽는 테이블을 삭제하면 이제 경고합니다.** **가져오기: 외부 프로젝트 테이블** 단계가 읽는 테이블을 삭제하면, PlaidCloud는 이제 이를 사용 중인 것으로 인식하고 일반 삭제를 제공하는 대신 **테이블을 강제로 삭제하시겠습니까?** 옵션을 선택하여 강제 삭제를 확인하도록 요구하므로, 다른 프로젝트가 의존하는 테이블이 실수로 제거되지 않습니다. 여기에는 이 프로젝트의 데이터를 공유하는 *다른* 프로젝트의 단계에서 오는 참조도 포함되며, 이러한 참조는 해당 프로젝트의 단계 세부 정보 없이 확인 창에 표시됩니다(해당 프로젝트에 대한 액세스 권한이 없을 수 있기 때문입니다). [Import Project Table](/ko/reference/workflow-steps/import/import-project-table/)을 참조하십시오.

- **조인 단계 — 출력 열 수정.** 내부, 외부, 안티, 교차 조인의 출력 열 탭은 이제 두 소스에서 매핑한 열만 나열하고 매핑된 소스 열을 제거하면 오래된 행을 삭제합니다. 열 매퍼 도구 모음과 여러 행 선택이 복원되었습니다. 요약은 기본적으로 꺼져 있는 토글이 되어 조인이 출력을 강제로 그룹화하지 않으며, 켜면 새 열의 기본값이 데이터 유형에 따른 집계가 되고 열마다 재정의할 수 있습니다. 다중 테이블 조인의 출력 열은 이제 조인 그래프 디자이너에서의 이름 변경과 제거를 따라갑니다. [Table Inner Join](/ko/reference/workflow-steps/tables/table-inner-join/) 및 [다중 테이블 조인 단계](/ko/guides/workflows/multi-table-join-step/)를 참조하십시오.

- **REST 요청 안정성 수정.** 이제 JSON 요청 본문에서 변수가 안정적으로 치환되고, 요청별 시간 제한과 재시도 설정이 적용되며(재시도는 멱등 메서드로 제한되므로 POST/PUT/PATCH는 다시 전송되지 않음), 속도 제한 응답은 백오프와 함께 재시도되고, 캡처된 원시 JSON에서 요청 자격 증명이 마스킹됩니다. 테스트 요청은 이제 성공한 경우에도 응답 상태 코드를 표시하고, 단일 객체 응답은 하나의 행으로 가져옵니다. 센서 및 웹훅으로 트리거되는 워크플로는 트리거의 메타데이터와 수신 페이로드를 변수로 읽을 수도 있습니다. [REST 요청 단계](/ko/guides/workflows/rest-request-step/)를 참조하십시오.

- **AI 비용 추적 수정.** 이제 비용 추적은 공백이나 기호가 포함된 모델 열 이름을 처리하고, 알아보기 쉬운 이름으로 지정한 테이블을 확인하며, 모델 실행 단계와 프로젝트 복사본의 결과에서도 작동하고, 모든 워크스페이스 유형에서 작동합니다. 이상 징후 감지는 이제 비정상적으로 큰 변동을 표시하고 연도 경계를 넘어서도 분기로 표기된 기간을 실제 시간 순서로 유지하며, 두 가지 잘못된 표시 버그도 수정되었습니다. 가중치 기준이 비어 있는 상태에서 시작할 때 나타나던 "0에서" 급증과, 이전 값이 음수일 때 부호가 잘못된 백분율 변화입니다.

- **프로젝트 테이블 가져오기/내보내기가 비어 있는 소스에 대해 경고합니다.** Import Project Table 또는 Export Project Table 단계가 행이 없는 소스 테이블에서 복사하면, 이제 소스가 비어 있었다는 경고와 함께 끝나므로, 단계가 조용히 성공한 것처럼 보이는 대신 예상치 못한 빈 결과를 쉽게 알아챌 수 있습니다. 대개 단계가 실행될 때 소스 프로젝트의 데이터가 아직 구축되지 않았다는 뜻입니다. [Import Project Table](/ko/reference/workflow-steps/import/import-project-table/) 및 [Export to External Project Table](/ko/reference/workflow-steps/export/export-project-table/)을 참조하십시오.

- **테이블 번들이 이제 각 열의 차원, 메모, 형식을 함께 전달합니다.** 이전에는 테이블을 번들로 내보내 다른 프로젝트로 가져오면 가져온 테이블의 모든 열에서 차원 연결이 비어 있었고, 열의 메모와 표시 형식도 마찬가지였습니다. 이후 단계는 읽는 테이블에서 열 설정을 가져오기 때문에, 가져온 테이블이 이 빈틈을 그로부터 만들어지는 모든 것에 전달할 수 있었습니다. 이제 이러한 설정이 번들과 함께 이동하고 가져올 때 복원됩니다. 열이 대상 프로젝트에 없는 차원을 가리키는 경우에는 깨진 링크로 복원되는 대신 해당 연결 하나만 삭제되고 가져오기 로그에 이름이 표시되므로, 차원을 만든 후 다시 연결하십시오. 이 변경 이전에 내보낸 번들은 이전과 똑같이 가져옵니다.

- **만들고 구성 열기가 이제 DAG 워크플로에 맞는 보기를 엽니다.** 새 고급(DAG) 워크플로에서 **만들고 구성 열기**를 사용하면 시각적 워크플로 디자이너 캔버스 대신 클래식 단계 그리드가 열렸습니다. 이제 워크플로를 두 번 클릭할 때와 마찬가지로 캔버스가 열립니다. [고급 워크플로](/ko/guides/workflows/advanced-workflows/)를 참조하십시오.

- **Panel 앱 종속성을 앱 옆에 둘 수 있습니다.** Git 리포지토리에서 빌드한 서버 측 Panel 앱은 이제 리포지토리 루트뿐 아니라 진입점 옆에 둔 `requirements.txt`도 설치하므로, 공유 리포지토리의 하위 폴더에 저장된 앱도 자체 패키지(예: `plotly`, `holoviews`, `hvplot`)를 선언할 수 있으며 라이브러리 누락으로 빈 화면이 표시되지 않습니다. [Panel 앱 만들기](/ko/guides/panel-apps/creating/#종속성-추가하기)를 참조하십시오.

- **폴더 간에 크거나 많은 문서 이동.** 한 문서 폴더에서 다른 폴더로 여러 파일을 한꺼번에 또는 대용량 파일 하나를 이동하는 작업이 이제 안정적으로 작동합니다. 파일 목록이 일관되게 유지되도록 이동은 한 번에 하나씩 실행되며, 대용량 이동은 중간에 끊기지 않고 완료될 만큼 충분한 시간이 주어집니다.

- **AI 어시스턴트가 밑줄로 시작하는 이름의 열을 참조하는 식을 더 이상 거부하지 않습니다.** 이름이 밑줄로 시작하는 열(예: `_MajorAccountFlag`)을 참조하는 식이 이제 허용됩니다. 그리고 식이 `is`, `is not`, `not`으로 열을 검사하면, 이는 보기와 달리 열에서는 어떤 행과도 일치하지 않거나 오류가 발생하는데, 어시스턴트는 단순히 거부하는 대신 작동하는 연산자(null 검사에는 `is_(None)`, `!=`, `~`)를 안내합니다.

- **AI 어시스턴트가 유효한 함수를 더 이상 거부하지 않습니다.** 식 선택기의 목록에 없던 실제 함수(`rtrim`, `ltrim`, `to_char`, `substring` 등 다수)가 알 수 없는 함수로 거부되었고, 소문자 형식이 허용되는 경우에도 대문자로 쓴 함수 이름(`func.SUM`)은 거부되었습니다. 이제 어시스턴트는 선택기의 목록뿐 아니라 워크스페이스 자체의 함수 목록과도 대조하며, 대소문자를 구분하지 않고 확인합니다.

- **Panel 앱에서 더 이상 텍스트가 보이지 않는 문제가 없습니다.** 일치하는 페이지 템플릿을 사용하지 않는 앱을 포함하여 모든 Panel 앱에 플랫폼 전체 테마 기본값이 적용되었습니다. 그런 앱에서는 흰색 페이지에 흰색 텍스트가 그려져 앱이 빈 것처럼 보였고 로그에는 이를 설명하는 내용이 없었습니다. 이제 앱이 테마가 적용된 템플릿을 선택하지 않는 한 자체 모양을 유지합니다. 기존 앱은 다음에 다시 빌드하거나 다시 게시할 때 이 수정이 적용됩니다.

- **대기 화면이 더 이상 Panel 앱의 모양을 바꾸지 않습니다.** Server Panel 앱이 시작되는 동안 그 뒤의 화면이 자체 배경과 밝은/어두운 색상을 설정했고, 앱은 이를 재정의할 방법 없이 그대로 상속받았으므로, 앱이 잘못된 캔버스 색상으로 렌더링되거나 자체 설정이 아니라 운영 체제의 밝은/어두운 기본 설정을 따를 수 있었습니다. 이제 앱이 시작되면 대기 화면이 완전히 제거됩니다. 또한 열었던 주소에서 아무것도 빠뜨리지 않아, 앱이 읽는 쿼리 매개변수(`?theme=dark` 등)도 이제 앱에 전달됩니다.

- **아카이브를 풀 때 폴더 구조가 유지됩니다.** `.zip` 또는 `.tar.gz`를 문서로 압축 해제하면 모든 것이 대상 폴더로 평면화되었습니다. `data/master/accounts.csv`가 들어 있는 아카이브에서 단순한 `accounts.csv`가 만들어졌으므로, 서로 다른 폴더에 있는 같은 이름의 파일이 충돌했습니다. 이제 중첩된 아카이브는 폴더 구조를 그대로 유지한 채 풀립니다. 평면 아카이브와 단일 파일 `.gz`/`.bz2`는 변경되지 않습니다. SFTP 문서 계정에서는 대상 폴더가 이미 존재해야 하므로, 중첩된 아카이브는 그곳에 이미 만들어 둔 경로로 푸십시오.

- **잘못된 일정이 더 이상 이벤트 스케줄러를 망가뜨리지 않습니다.** 반복 규칙을 사용할 수 없는 예약 이벤트 하나(30일까지 있는 달의 31일 같은 불가능한 날짜, 또는 형식이 잘못된 항목)가 워크스페이스 전체의 이벤트 스케줄러 목록과 일정 달력을 내부 서버 오류로 실패시켰고, 프로젝트가 열리지 않을 수도 있었습니다. 이제 읽을 수 없는 일정은 다음 실행을 빈칸으로 표시할 뿐이며, 화면의 나머지는 정상적으로 로드됩니다. [이벤트 스케줄러](/ko/administration/scheduled-events/event-scheduler/)를 참조하십시오.

- **워크플로 실패가 이제 실제로 무엇이 잘못되었는지 알려 줍니다.** 백그라운드 작업 안에서 워크플로 단계가 실패하면 실행 로그와 알림 이메일에 해당 작업에 대한 일반적인 메시지("Exception importing directly from remote sql")만 표시되었고, 소스 시스템의 암호 만료 같은 실제 원인은 접근할 수 있는 어디에도 나타나지 않았습니다. 이제 근본 실패 원인이 로그와 이메일로 전달됩니다. 하나의 공통 원인으로 여러 테이블이 실패하면 테이블마다가 아니라 한 번만 보고되며, 메시지에서 자격 증명은 제거됩니다.

- **다른 호스트로 보내는 REST 요청이 더 이상 연결의 자격 증명을 전송하지 않습니다.** REST 요청 단계가 경로가 아니라 전체 주소를 사용하는 경우(많은 API가 반환하는 페이지 매김 링크 포함) 두 가지 문제가 있었습니다. 주소가 연결의 호스트에 이어 붙여져 요청이 완전히 실패했고, 요청이 어디로 가든 연결의 인증과 기본 헤더가 첨부되었습니다. 이제 전체 주소는 주어진 그대로 사용되며, 주소가 연결 자체의 호스트를 가리키지 않는 한 자격 증명과 기본 헤더는 전송되지 않으므로, 페이지 매김은 계속 작동하면서도 타사 주소는 자격 증명을 받지 않습니다. [REST 요청 단계](/ko/guides/workflows/rest-request-step/)를 참조하십시오.

- **기본 인증 REST 연결을 편집해도 더 이상 암호를 잃지 않습니다.** 기본 인증을 사용하는 REST 연결을 변경한 뒤 암호를 다시 입력하지 않고 저장하면 저장된 비밀이 삭제되었습니다. 이제 네 가지 인증 유형 모두에서 저장된 암호가 유지됩니다. 요청 미리 보기의 불일치 두 가지도 수정되었습니다. 단계에서 대소문자를 달리하여 설정한 헤더는 실제 요청이 처리하는 방식과 동일하게 통합되며, 빈 헤더 값은 이제 문자 그대로의 "None" 텍스트가 아니라 빈 값으로 전송됩니다. [일반 REST 연결](/ko/reference/connectors/rest/generic-rest/#인증)을 참조하십시오.

- **테이블을 결합해도 각 열의 차원과 서식이 유지됩니다.** Union, Union All, 배부, 다중 테이블 조인이 여러 소스를 하나의 출력 열로 병합할 때, 열의 차원, 메모, 형식 설정은 정렬상 마지막에 오는 소스에서 결정되었습니다. 차원에 대해 아무것도 지정하지 않은 소스가 차원을 지정한 소스를 가릴 수 있었으므로, 비슷한 열은 복구되는 동안에도 어떤 열은 다시 구축해도 연결되지 않은 채로 남았습니다. 이제 차원을 지정한 소스가 아무 언급이 없는 소스보다 우선하고, 그대로 전달된 열이 이름이 바뀐 열보다 우선하며, 소스 간의 실제 불일치는 조용히 해결되지 않고 단계 로그에 보고됩니다. 또한 집계된 열의 이름을 바꿔도(`SUM(amount)`를 `total_amount`로) 합계가 구성원을 식별한 적이 없는데도 소스 열의 차원이 합계에 복사되지 않습니다. [Table Union All](/ko/reference/workflow-steps/tables/table-union-all/) 및 [Table Union Distinct](/ko/reference/workflow-steps/tables/table-union-distinct/)를 참조하십시오.

- **Table Melt가 작성한 열 매핑을 따릅니다.** 멜트의 매핑에서 의도적으로 제외한 열이 뒤에서 단계에 다시 추가되었고, 집계 단계에서는 이 때문에 단계 전체가 실패했습니다. 이제 값 열을 명시한 매핑은 작성한 그대로 사용됩니다. [Table Melt](/ko/reference/workflow-steps/tables/table-melt/)를 참조하십시오.

- **다른 프로젝트에서 테이블 복사가 다시 작동합니다.** 프로젝트 간에 테이블을 복사하는 단계가 더 이상 존재하지 않는 작업을 호출했으므로 모든 실행이 서버에서 실패했습니다. 이제 Import Project Table 단계와 같은 메커니즘을 사용하며, 소스가 비어 있으면 실패하는 대신 경고를 보고합니다. [Import Project Table](/ko/reference/workflow-steps/import/import-project-table/)을 참조하십시오.

- **행 수 검증이 매크로 안에서 작동합니다.** Macro Run 또는 Macro Concurrent 단계 안에 중첩된 행 수 검증 단계가 서버 측 오류로 실패했고, 최상위 실행만 작동했기 때문에 눈에 띄지 않았습니다. 이제 어떤 중첩 수준에서도 올바르게 실행됩니다. [행 수 검증](/ko/reference/workflow-steps/workflow-control/row-count-assert/)을 참조하십시오.
- **업스트림 비용 풀이 아직 구축되지 않았을 때 비용 추적이 더 이상 중단되지 않습니다.** 배부 결과가 왜 바뀌었는지 물을 때, 배부에 입력되는 테이블이 생성되지 않았으면(대개 모델의 해당 부분을 실행하지 않았기 때문) 이전에는 완전히 실패했습니다. 이제 추적이 완료됩니다. 해당 단계에 대해 측정된 합계는 계속 보고하고, 업스트림 분해는 추측하지 않고 귀속할 수 없음으로 표시하며, 다시 추적하기 전에 어떤 입력을 다시 구축해야 하는지 알려 줍니다. 합계가 움직이지 않은 단계는, 누락된 풀에 대해 측정된 것이 있다고 암시하지 않은 채 변동 없음으로 보고됩니다.

- **테이블 세부 정보에 실시간 행 수가 표시됩니다.** 테이블의 세부 정보를 열면 웨어하우스에서 행 수를 읽으므로, SQL로 데이터를 쓴 후에도 정확하게 유지됩니다. 이전에는 테이블의 구조가 새로 고쳐질 때까지 오래된 수치가 표시될 수 있었습니다. 데이터 저장소가 개수를 추정만 할 수 있는 경우에는 이제 정확한 것처럼 표시되지 않고 근사치로 표시됩니다.

## 제거됨

- **오래된 레거시 가져오기 및 내보내기 단계 폐기** — SAS7BDAT 가져오기, HTML 가져오기, HTML 내보내기 단계가 제거되었습니다. 이러한 형식에는 현재의 가져오기 및 내보내기 단계를 사용하십시오.

- **X12 EDI 가져오기 단계 폐기** — 단계 유형이 제거되었습니다. 이 단계는 한 번도 제대로 작동하지 않았고, 모든 X12 EDI 가져오기가 실행 시 실패했습니다. PlaidCloud에서 EDI 데이터가 필요하면 CSV나 JSON 같은 지원되는 형식으로 변환한 다음 그것을 가져오십시오.

- **앱 내 암호 재설정 옵션 폐기** — 계정(아바타) 메뉴에서 **암호 재설정** 항목이 제거되었습니다. 암호를 재설정하려면 로그인 페이지의 **암호를 잊으셨습니까?** 링크를 사용하십시오.

## 보안

- **보안 할당 변경이 즉시 적용됩니다.** 보안 그룹의 범위나 멤버 편집, 그룹 삭제, 멤버의 보안 그룹 변경, 멤버 활성화 및 비활성화는 모두 지연되어 적용되었습니다. 대부분의 권한은 최대 30초가 걸렸고, 워크스페이스의 Git 서버에 대한 액세스는 해당 사람이 다음에 로그인할 때까지 적용되지 않았는데, 액세스 권한이 취소된 사람의 경우 영원히 적용되지 않을 수도 있었습니다. 이제 이러한 모든 변경은 저장하는 즉시 플랫폼 전체에 적용됩니다. 구성할 것은 없습니다. 이전에 부여하거나 취소한 액세스를 검토하고 이제 정확하게 반영되었을 것으로 기대하십시오. [보안 그룹 및 할당 관리](/ko/administration/access/managing-security-groups-and-assignments/)를 참조하십시오.
