A gestão de segurança e de acesso do PlaidCloud é simples. O acesso de um membro é concedido ou negado com base nos grupos a que esse membro está associado. Adicionar ou alterar a associação de segurança de um membro é fácil de personalizar.

<Aside>Cada área de trabalho pode ter um número ilimitado de grupos de segurança, mas recomendamos minimizar esse número para facilitar a gestão da segurança.</Aside>



## Gerir grupos de segurança


Os grupos de segurança podem ser adicionados, atualizados ou eliminados.



**Para gerir grupos de segurança:**


1. Abra Identity
2. Selecione o separador “Security”
3. Clique em “Security Groups” no menu pendente (é apresentado um formulário com os grupos existentes)
4. Para adicionar um grupo, clique em “Create Security Group”
5. Para editar as permissões de um grupo, clique no ícone mais à esquerda

**Para gerir os membros de um grupo:**


1. Abra Identity
2. Selecione o separador “Security”
3. Clique em “Security Groups” no menu pendente
4. Clique no ícone Member
5. Arraste os membros pretendidos da coluna “Unassigned Members” para a coluna “Assigned Members”, ou vice-versa para remover membros

<Aside>Guardar com a coluna “Assigned Members” vazia não faz qualquer alteração e informa-o disso. Para retirar um grupo a todas as pessoas, remova as suas permissões ou elimine o grupo, em vez de esvaziar a respetiva lista de membros.</Aside>

<Aside>Se a um grupo forem concedidas linhas através de [Acesso a linhas](#gerir-o-acesso-a-linhas), uma alteração de membros chega aos painéis de controlo em cerca de um minuto: quem for adicionado passa a ver aí as linhas do grupo e quem for removido deixa de as ver. Desativar ou eliminar um membro, e eliminar um grupo, produzem efeito da mesma forma.</Aside>

<Aside type="caution">As permissões que não pode conceder a si próprio são deixadas como estão quando guarda a matriz de permissões de um grupo e não são apresentadas nela. Se precisar de alterar uma delas, peça a alguém que detenha essa permissão — a matriz só edita aquilo que controla.</Aside>

## Gerir o acesso a linhas

O acesso a linhas restringe as linhas de uma tabela que um grupo de segurança pode ver, com base no valor de uma coluna. Por exemplo, uma coluna `region` pode restringir o acesso, ficando um grupo com concessão de `East` e `Central` limitado às linhas que contêm esses valores. Tudo o que diz respeito a um projeto e a uma coluna — escolher a coluna, escolher a origem dos respetivos valores e decidir que grupo vê o quê — é feito num único ecrã, e guardar produz efeito de imediato.

Configurar e alterar o acesso a linhas exige um Arquiteto do projeto ou um administrador da área de trabalho. Quem não o for e abrir o separador Security de um projeto é informado de que o acesso a linhas é exclusivo dos Arquitetos, e os pontos de entrada abaixo não lhe são apresentados.

### Abrir o acesso a linhas

Todos os pontos de entrada abrem o mesmo ecrã de acesso a linhas:

- **A barra de ferramentas do Explorador de tabelas** tem um botão **Acesso a linhas**, com um indicador quando a tabela já restringe linhas. Abre na primeira coluna restringida da tabela, se existir, e pode mudar para qualquer outra coluna da tabela.
- **O menu de facetas de uma coluna** tem **Restringir linhas por esta coluna…**, que abre o acesso a linhas nessa coluna. Numa coluna que já restringe linhas, o item apresenta **Linhas restringidas por esta coluna — editar…**.
- **O separador Security de um projeto** lista todas as colunas restringidas do projeto, com as tabelas a que se aplicam, os grupos que detêm concessões e o respetivo estado de **Sincronizar**. Selecione uma coluna para a editar ou clique em **Restringir uma coluna…** para iniciar uma nova: escolha uma tabela e, depois, uma coluna. As colunas que já restringem linhas são assinaladas com um cadeado.
- **Identity → Member**, no separador **Acesso a linhas** de um membro, e **Identity → Security → Security Groups**, no resumo de acesso a linhas de um grupo. **Abrir acesso por linha** (ou **Editar**) abre a coluna selecionada; **Adicionar** restringe outra coluna no projeto dessa linha.

Quando aberto numa coluna, o ecrã mantém-se nessa coluna. Quando aberto com **Restringir uma coluna…** ou **Adicionar**, permite escolher uma.

### A grelha de acesso a linhas

Para restringir uma tabela por uma coluna:

1. Abra o acesso a linhas a partir de qualquer um dos pontos de entrada acima e escolha a coluna, se não chegou com uma — o seletor oferece as colunas reais da tabela, não texto livre.
2. Escolha uma **Origem do valor** — **Coluna** (os valores distintos de uma coluna de uma tabela), **Dimensão** (nós de uma dimensão) ou **Lista** (valores que introduz). O tipo de valor segue o tipo de dados da coluna.
3. Para cada grupo de segurança, assinale os valores que esse grupo pode ver. A grelha lista os grupos com acesso ao projeto, mais qualquer grupo que já detenha uma concessão na coluna.
4. Defina **Everyone else** como **sees all rows** ou **sees no rows** — isto abrange qualquer grupo sem seleções na grelha.
5. Clique em **Guardar**.

Guardar é imediato. As consultas do próprio PlaidCloud seguem a alteração de imediato e os seus painéis de controlo Superset em cerca de um minuto — não existe um passo separado para a aplicar nem uma caixa de diálogo de aprovação. O estado de sincronização do ecrã mostra até onde a alteração chegou; consulte [Manter os painéis de controlo sincronizados](#manter-os-painéis-de-controlo-sincronizados).

A grelha trata também dos pormenores por si:

- **Muitos valores.** Os valores são ordenados. Quando uma coluna tem mais valores do que os que cabem, a grelha indica “More values than fit here — type to search.” e a caixa de filtro pesquisa em toda a coluna, mantendo todos os valores que um grupo já detém.
- **Valores em branco.** Uma caixa de verificação **Valores em branco — visíveis para todos os grupos com uma concessão** decide as linhas sem valor na coluna. Se a assinalar, todos os grupos com qualquer concessão na coluna veem essas linhas.
- **Uma tabela que ainda não foi compilada** mostra **Compile primeiro esta tabela (execute o fluxo de trabalho que a cria)** em vez de uma lista vazia.
- **Guardar aguarda os valores no ecrã.** Enquanto os valores carregam — depois de mudar a origem do valor, a dimensão ou a tabela, ou de aplicar um modelo — **Guardar** fica desativado com a dica “Save is available once this source's values load.” Se um carregamento falhar, a grelha indica-o e pede que escolha novamente a origem; nada é guardado até um carregamento ter êxito.

### Um nome de coluna, todas as tabelas

Uma restrição pertence ao *nome* de uma coluna no projeto, não a uma única tabela. Depois de `region` restringir linhas, todas as tabelas do projeto com uma coluna chamada `region` ficam filtradas por ela, tanto nas consultas do próprio PlaidCloud como nos painéis de controlo. A lista **Applies to** da grelha mostra essas tabelas. É só de leitura, porque quem decide é o nome da coluna, e uma tabela que adicione mais tarde com a mesma coluna fica abrangida logo que for publicada.

Quando nenhuma tabela do projeto tem uma coluna com esse nome, a janela avisa que a restrição não filtrará nenhum painel de controlo até que exista uma, além de mostrar **Applies to 0 tables**. Adicione a coluna a uma tabela, ou corrija o nome da coluna, e o aviso desaparece.

<Aside type="caution">
**O nome de uma coluna tem de corresponder exatamente** — incluindo maiúsculas e espaços. `Region` e `region` são nomes diferentes, tal como `region` e `region ` com um espaço no final. O seletor só oferece nomes de colunas reais, pelo que isto importa sobretudo se uma coluna for renomeada noutro local — o acesso a linhas avisa então e indica a coluna mais próxima que encontrou, em vez de não restringir nada em silêncio.
</Aside>

<Aside type="caution">
**Publicar uma tabela que restringe linhas configura o respetivo filtro de painel de controlo no mesmo passo.** Os painéis de controlo leem uma tabela através da sua vista de relatórios publicada, pelo que, quando publica ou volta a publicar uma tabela que tem uma coluna restringida, o PlaidCloud regista o filtro de painel de controlo dessa tabela antes de a publicação terminar. Se não o conseguir fazer, a publicação é recusada e tudo o que essa tentativa criou é revertido, de modo que uma tabela restringida nunca fica sem filtro nos painéis de controlo. Uma *vista* não pode ser publicada num projeto que restringe linhas, porque a consulta de uma vista pode mudar o nome da coluna restringida ou derivá-la. Consulte [Publicar tabelas](/pt-pt/guides/data/publish/).
</Aside>

### Deixar de restringir

**Deixar de restringir**, na grelha, remove a restrição após uma confirmação em linha — “Stop restricting rows by ‘region’? Every group's grant on it is removed and everyone sees its rows.” O acesso a linhas confirma então “Rows in ‘region’ are no longer restricted.” O conjunto de dados Superset da coluna é removido com ela, a menos que ainda existam gráficos que o utilizem; nesse caso, o acesso a linhas indica que o conjunto de dados se mantém e quantos gráficos o utilizam.

Uma coluna não pode ser renomeada nem eliminada enquanto restringir linhas. Um Arquiteto é informado de que deve primeiro deixar de a restringir no acesso a linhas; os restantes utilizadores são informados de que devem pedir a um Arquiteto do projeto.

### Quem pode alterar um projeto que restringe linhas

Os fluxos de trabalho, passos e funções definidas pelo utilizador de um projeto são executados como a identidade de serviço do próprio projeto, que lê todas as linhas. Quem os puder alterar poderia fazer um passo copiar linhas que não lhe foram concedidas para uma tabela que pode ler, pelo que restringir linhas num projeto restringe também quem pode alterar aquilo que o projeto faz. Quando um projeto restringe pelo menos uma coluna:

- **A automatização é exclusiva dos Arquitetos.** Só os Arquitetos do projeto e os administradores da área de trabalho podem alterar fluxos de trabalho, passos, funções definidas pelo utilizador, agendamentos, variáveis de fluxo de trabalho e de projeto e modelos de correio eletrónico de notificação — e, pela mesma razão, importar um pacote de fluxo de trabalho, converter um fluxo de trabalho Alteryx, ou importar, copiar ou restaurar para o projeto, ou alterar o seu ambiente de ligação, a conta de documentos predefinida ou o modo de lançamento ERP. Todos os outros podem continuar a executar os fluxos de trabalho do projeto: **Início**, **Parar**, **Retomar** e **Executar passos selecionados** continuam disponíveis. O editor de passos, os controlos de criação do fluxo de trabalho, o editor de UDF e o formulário de agendamento abrem em modo só de leitura para eles, com um aviso que indica os Arquitetos a quem recorrer: “This project restricts rows, so only its Architects can change workflows, steps, UDFs, schedules, variables and notify templates. You can still run them.”
- **As dimensões lidas por uma coluna restringida são exclusivas dos Arquitetos.** Uma dimensão que decide quem vê que linhas — a origem de valores de uma coluna restringida — só pode ser alterada por um Arquiteto do projeto ou por um administrador da área de trabalho, e pelos fluxos de trabalho do próprio projeto. Isto abrange adicionar, mover, renomear, copiar, limpar, carregar e restaurar os seus nós, bem como a própria dimensão. Os restantes utilizadores recebem a mensagem “This dimension decides who sees which rows of ‘region’, so only a project Architect can change it.” As dimensões que nenhuma restrição lê não são afetadas.
- **Uma tabela de origem das concessões é exclusiva dos Arquitetos.** Uma tabela associada como [origem das concessões](#associar-concessões-a-uma-tabela-de-origem) de uma coluna só pode ter as suas linhas alteradas, ou ser eliminada, por um Arquiteto do projeto, um administrador da área de trabalho ou os fluxos de trabalho do projeto — seja através do Editor de dados, de uma importação, de um carregamento de conector ou da API.
- **Copiar o projeto é exclusivo dos Arquitetos**, e a cópia indica “This copy is not row-restricted.” — o novo projeto não tem qualquer restrição até que configure uma.
- **Restaurar uma versão anterior é uma alteração como qualquer outra.** Restaurar as definições do próprio projeto, ou uma dimensão acima indicada, exige um Arquiteto do projeto. Um restauro aplica-se sempre ao item a que a versão pertence, pelo que não pode ser direcionado para outro projeto de modo a contornar esta regra — consulte [Histórico de versões](/pt-pt/guides/projects/managing-projects/#histórico-de-versões).
- **Editar dados numa tabela restringida** exige um Arquiteto, conforme descrito em [Acesso a linhas e Editor de dados](#acesso-a-linhas-e-editor-de-dados).

Antes de a primeira coluna de um projeto ser restringida, o acesso a linhas indica quem é afetado: “Restricting rows here means only Architects can change this project's workflows, steps, UDFs, schedules and notify templates. N members can change them today; they will still be able to run them.”

As execuções continuam a funcionar exatamente como antes, incluindo as agendadas, porque são executadas como a identidade de serviço do projeto. O que uma execução produz segue a conceção que os respetivos Arquitetos lhe deram: uma tabela de saída sem a coluna restringida, um ficheiro exportado, um correio eletrónico de notificação ou uma linha de registo não é filtrado para quem o lê.

**Valores indicados no início de uma execução.** Quem pode executar um fluxo de trabalho pode iniciá-lo com valores próprios para as suas variáveis — o [App Runner](/pt-pt/guides/workflows/use-converted-alteryx-apps/#a-interface-app-runner) fá-lo com as respostas do seu formulário, e a API e as ferramentas de IA também o podem fazer. Esses valores aplicam-se apenas a essa execução: nunca são guardados no fluxo de trabalho e nenhuma outra execução, exportação ou leitor os vê. Como a execução decorre como identidade de serviço, os valores podem alterar o que essa execução lê e escreve, pelo que a permissão para executar fluxos de trabalho deve ser concedida a pessoas em quem confia.

**Projetos que não restringem linhas.** Estas regras só produzem efeito depois de um projeto restringir uma coluna. Num projeto que não restringe nenhuma, quem pode alterar a automatização do projeto pode escrever um passo ou uma função definida pelo utilizador que — sendo executado como a identidade de serviço do projeto — altere o acesso ao projeto, tornando-se um dos seus Arquitetos. Isto é intencional: um projeto desses não promete isolamento de linhas. Limite os direitos de criação, nesses projetos, a pessoas em quem confiaria como Arquitetos, ou restrinja uma coluna.

### Manter os painéis de controlo sincronizados

O acesso a linhas mostra em que ponto está uma alteração a caminho dos seus painéis de controlo, na grelha e na coluna **Sincronizar** do separador Security do projeto:

| Estado | O que significa |
|---|---|
| **Em espera** | Uma alteração está guardada e a caminho dos painéis de controlo. Normalmente fica resolvida em cerca de um minuto. |
| **A tentar novamente** | Um envio falhou e está a ser repetido. O motivo da falha é apresentado junto ao estado, com **Tentar novamente** para enviar de novo de imediato. |
| **Ainda não aplicado** | As restrições do projeto ainda não foram enviadas para os painéis de controlo. |
| **Aplicado** | A última tentativa de enviar as restrições para os painéis de controlo teve êxito. |
| **Sincronizado com os painéis de controlo** | O acesso a linhas comparou o que os painéis de controlo impõem com o que escreveria, e coincidem. |
| **Os painéis de controlo diferem** | Os painéis de controlo não impõem o que o acesso a linhas escreveria — uma regra foi alterada ou eliminada no Superset, ou não é possível verificar a vista publicada de uma tabela. |
| **Erro** | O envio das restrições falhou. O motivo é apresentado junto ao estado. |

Quando uma alteração chega a **Aplicado**, a grelha verifica-a nos painéis de controlo e passa para **Sincronizado com os painéis de controlo** ou **Os painéis de controlo diferem**. **Os painéis de controlo diferem** e **Erro** oferecem ambos **Tentar novamente**, que envia de novo as restrições do projeto. Se o estado não puder ser lido de todo, a grelha indica “Não foi possível verificar o estado da sincronização.”

Um **Erro** causado por uma tabela indica o nome dessa tabela e o que fazer — por exemplo, uma tabela publicada sem a sua coluna restringida (“Republish or unpublish it.”), ou uma tabela com uma coluna restringida que não está publicada, a qual os painéis de controlo não conseguem filtrar até ser publicada. O estado mantém-se em **Erro** e indica a tabela não publicada até que a publique ou restrinja a coluna numa tabela publicada. Uma tabela assim não bloqueia o resto do projeto: todas as outras tabelas são mantidas em sincronização.

Os painéis de controlo seguem as mesmas concessões que as consultas do próprio PlaidCloud:

- **Todas as tabelas publicadas com a coluna são filtradas**, não apenas a tabela que estava a ver quando configurou a restrição.
- **Um grupo com concessão apenas de alguns valores é filtrado mesmo quando todos os outros veem todas as linhas**, em todas as tabelas cujo conjunto de dados de painel de controlo exista.
- **Os Arquitetos do projeto veem todas as linhas**, nos painéis de controlo tal como no Explorador de tabelas e no resto do PlaidCloud. Aplica-se aos grupos de Arquitetos do projeto e aos Arquitetos de um projeto partilhado com membros individuais. Retirar o acesso de Arquiteto produz efeito de imediato nos painéis de controlo, quer altere a função do membro, remova o membro ou o respetivo grupo do projeto, altere o tipo de acesso do projeto, restaure uma versão anterior do projeto ou elimine o grupo.
- **As alterações à pertença a grupos de segurança chegam sozinhas aos painéis de controlo.** Adicionar alguém a um grupo ou removê-lo no PlaidCloud, desativar ou eliminar um membro, eliminar um grupo ou adicionar um novo membro que se junta aos seus grupos de segurança predefinidos atualiza o que essa pessoa vê nos painéis de controlo em cerca de um minuto, em todos os projetos que concedem valores a esse grupo, sem que ninguém precise de reabrir o acesso a linhas. Uma alteração de pertença feita fora do PlaidCloud — diretamente no Keycloak, ou por início de sessão único que coloque alguém num grupo no momento do início de sessão — chega aos painéis de controlo em cerca de 15 minutos, sem nada para guardar ou repetir.

### Concessões de dimensão

Com **Dimensão** como origem do valor, assinale um nó para conceder tudo o que está abaixo dele. A concessão acompanha a dimensão: um membro adicionado sob um nó assinalado passa a ser concedido a esse grupo na sincronização seguinte à gravação da dimensão, e um membro movido para fora dele, ou removido, deixa de ser concedido — ninguém precisa de reabrir a grelha. Quando a reabre, os nós que assinalou voltam a aparecer assinalados.

Desassinalar qualquer item abaixo de um nó assinalado desassinala o nó, e o grupo fica apenas com os membros que continuam assinalados. Voltar a assinalar esse membro não assinala o nó de novo — clique na caixa do próprio nó para isso. **Colar**, **Selecionar tudo** e **Inverter** assinalam membros, nunca nós.

Um membro de dimensão cujo nome não pode ser usado como valor de acesso a linhas é recusado ao guardar, com indicação do nome. Se um membro assim surgir mais tarde, as suas linhas não são concedidas a ninguém e o estado de sincronização indica-o: “Dimension ‘…’ member ‘…’ cannot be used as a row access value, so its rows are not granted. Rename it in the dimension.”

### Associar concessões a uma tabela de origem

Em vez de assinalar os valores manualmente, pode apontar uma coluna restringida para uma tabela de origem
que já contenha a resposta — uma linha por grupo e o valor que este pode ver. Restrinja primeiro a coluna na
grelha e, depois, adicione um passo de fluxo de trabalho [**Definir acesso às linhas**](/pt-pt/reference/workflow-steps/tables/table-set-row-access/)
que indique a coluna, a tabela de origem e as colunas de grupo e de valor da tabela de origem. A primeira
execução do passo associa a coluna a essa tabela: as concessões definidas manualmente na coluna são
limpas e as suas concessões passam a ser definidas a partir das linhas da tabela.

Uma vez associada, a coluna passa a ser **propriedade da origem**: a grelha de acesso a linhas mostra-a bloqueada, com um indicador
que indica a tabela de origem, e a edição manual das suas concessões é recusada até clicar em **Remover associação**.

Cada execução posterior do passo volta a ler a tabela de origem e a reaplicar as concessões — agende-o
depois do fluxo de trabalho que carrega ou atualiza essa tabela, e um grupo adicionado, removido ou reatribuído
nos dados de origem chega ao acesso a linhas na execução seguinte, sem que ninguém edite a grelha manualmente.

Como é a tabela de origem que decide quem vê o quê, só um Arquiteto do projeto, um administrador da área de trabalho ou os
fluxos de trabalho do próprio projeto podem alterar as suas linhas ou eliminá-la. Os restantes utilizadores recebem a mensagem “This table
supplies the row access grants for ‘region’, so only a project Architect can change its rows or
delete it.”

### Modelos de restrição

Se criou uma forma de restrição que pretende reutilizar — a mesma origem de valor, o mesmo tipo de valor e a mesma
definição de valores em branco —, guarde-a uma vez e aplique-a onde for necessário, em vez de a reconstruir
coluna a coluna.

- **Guardar como modelo…**, a partir de um ecrã de acesso a linhas aberto, guarda a forma da coluna atual como
  um modelo com nome, ao nível da área de trabalho. Guarda apenas a forma — nenhuma concessão a acompanha.
- **Aplicar modelo**, na coluna de outro projeto, inicia essa coluna a partir da forma do modelo,
  com as concessões de todos os grupos vazias para que as preencha.

Qualquer Arquiteto do projeto pode guardar e aplicar modelos. Mudar o nome (**Mudar o nome…**) e eliminar
(**Eliminar**) um modelo exige um administrador da área de trabalho, uma vez que um modelo é partilhado por toda a área de trabalho.
Eliminar um modelo deixa as colunas às quais foi aplicado restringidas tal como estão.

<Aside type="note">
Os modelos são cópias, não ligações. Editar um modelo depois não altera nenhuma coluna que
já o tenha aplicado — aplique o modelo de novo para atualizar uma coluna com uma revisão
posterior.
</Aside>

### Concessões a partir de atributos de grupo SSO

Uma coluna também pode obter as suas concessões do seu fornecedor de identidade em vez do PlaidCloud. Um
Arquiteto do projeto ativa uma coluna a partir do acesso a linhas, ativando **Accept row-access grants from
SSO group attributes**.

Depois de ativado, o atributo Keycloak `row_access.<column>` de um grupo de segurança define os valores que esse
grupo pode ver através dessa coluna — defina o atributo no grupo no Keycloak e o PlaidCloud
assimila-o automaticamente para qualquer grupo que já tenha acesso ao projeto. Não há mais nada
a configurar no próprio acesso a linhas, e as concessões mantêm-se sincronizadas tanto nas consultas do próprio PlaidCloud
como nos painéis de controlo Superset.

<Aside type="caution">
Isto só concede valores a um grupo que já consegue aceder ao projeto. Adicionar `row_access.region`
a um grupo sem acesso ao projeto não lhe concede nada até que o grupo tenha também acesso
ao projeto.
</Aside>

### Pré-visualizar antes de guardar

O acesso a linhas mostra o que uma alteração significa antes de a confirmar:

- Um rodapé **Pré-visualizar como** mostra quantas das linhas da tabela um grupo veria, em relação ao total, com uma amostra das próprias linhas — escolha qualquer grupo na grelha para o pré-visualizar. A pré-visualização é atualizada depois de guardar.
- Antes de guardar, o acesso a linhas avisa-o de tudo o que merece uma segunda análise: um grupo sem nada assinalado, e se isso significa que vê todas as linhas ou nenhuma, de acordo com a definição **Everyone else**; membros com acesso ao projeto que não estão abrangidos pela concessão de nenhum grupo; ou linhas cujo valor nessa coluna está em branco (`NULL`) e que nenhum grupo tem concedidas.

### O que vê um membro restringido

Sempre que um membro restringido lê uma tabela pelo nome, obtém apenas as suas linhas — a grelha, as facetas de coluna e as transferências do Explorador de tabelas, a caixa de diálogo de transferência de tabelas, as aplicações e ferramentas que leem como o visualizador, e os painéis de controlo. O Explorador de tabelas mostra **Linhas limitadas pelo seu acesso** na barra de ferramentas quando a grelha que está a ver foi filtrada pelas suas concessões, e iniciar uma transferência que será filtrada indica “Rows limited by your access.” Um Arquiteto, que lê todas as linhas, não vê nenhum dos avisos.

### Acesso a linhas e consultas que escreve por si

O acesso a linhas limita as linhas que um grupo pode ver filtrando a tabela em relação à qual está definido. Uma consulta que alguém escreve por si não tem uma única tabela à qual associar esse filtro — uma consulta pode juntar, combinar ou aninhar as tabelas que quiser —, pelo que, num projeto que restringe linhas, o PlaidCloud recusa executar uma consulta fornecida por quem a invoca em vez de devolver linhas que nada validou.

Isto aplica-se à leitura através de SQL próprio, à exportação dos resultados de SQL próprio para um ficheiro ou para outra base de dados e à escrita de uma condição de linha na pré-visualização “Test row 1” de um passo de expansão. **Não** se aplica à leitura de uma tabela pelo nome, que é a forma habitual de as aplicações e ferramentas lerem dados — essas aplicam as concessões e devolvem as linhas a que o visualizador tem direito. Uma faceta de coluna escrita como uma consulta simples de uma única tabela também é lida pelo nome, pelo que devolve os valores do próprio membro em vez de ser recusada.

Quem for recusado é informado de qual era o projeto e é encaminhado para os leitores por nome. Um Arquiteto do projeto pode executar a consulta tal como escrita e exportar os respetivos resultados em qualquer formato, porque um Arquiteto já pode conceder a si próprio todos os valores de todas as colunas restringidas.

Importar uma folha de cálculo não é, por si só, uma consulta que escreveu por si — uma importação de ficheiro normal não lê quaisquer dados restringidos, limita-se a criar a nova tabela do próprio projeto a partir do ficheiro que carregou, pelo que não é afetada pelo acesso a linhas. A exceção é uma importação cuja projeção de dados é fornecida por quem a invoca: uma expressão por coluna ou um mapeamento dinâmico do Excel. No ecrã de importação interativo, estas são recusadas da mesma forma que as superfícies de SQL livre acima, e exigem um Arquiteto do projeto, porque uma projeção fornecida por quem a invoca poderia ler outra tabela. Uma importação executada a partir de um fluxo de trabalho não é afetada em qualquer dos casos, porque é executada sob a identidade de serviço do próprio projeto.

<Aside type="caution">
Restringir a primeira coluna de um projeto altera isto para todos os que o utilizam. Se uma aplicação Panel, um bloco de notas ou uma integração nesse projeto lê dados compondo o seu próprio SQL, passe-a a ler a tabela pelo nome antes de restringir — caso contrário, deixa de funcionar para todos os que não sejam Arquitetos.
</Aside>

### Acesso a linhas e Editor de dados

O Editor de dados lê e escreve diretamente numa tabela, pelo que o acesso a linhas se aplica a ambos os lados.

Abrir uma tabela restringida no Editor de dados mostra apenas as linhas concedidas ao seu grupo de segurança — o mesmo filtro que o acompanha num painel de controlo, e aplica-se mesmo quando a coluna restringida não é uma das colunas apresentadas na grelha.

Guardar as suas edições exige **Arquiteto** no projeto. Uma gravação substitui as linhas da tabela por inteiro em vez de as ler, e não é filtrada linha a linha, pelo que editar dados numa tabela restringida é tratado como uma ação de criação e não como uma leitura: quem não for Arquiteto é informado de que precisa dessa função. Uma tabela sem coluna restringida é editada como antes, tal como qualquer projeto que não restrinja linhas.

### Contagens de linhas e tamanhos das tabelas

A contagem de linhas e o tamanho de armazenamento de uma tabela descrevem a tabela inteira, e não as linhas que pode ver, pelo que indicariam a um leitor restringido quantas linhas existem para lá da sua concessão. Num projeto que restringe linhas, quem tem as leituras filtradas não vê a contagem de linhas nem o tamanho de nenhuma das tabelas do projeto — em listas de tabelas, na pesquisa, nos detalhes das tabelas e nos instantâneos, e através do assistente de IA e das ferramentas de IA ligadas por MCP. Isto abrange todas as tabelas do projeto, incluindo as que não têm coluna restringida. Os totais do próprio projeto também lhes ficam ocultos — a contagem total de linhas e o tamanho na página inicial, nas listas e na pesquisa de projetos e nos detalhes do projeto.

O mesmo se aplica ao histórico de execuções de fluxos de trabalho. As linhas lidas e escritas que cada execução e cada passo registaram também descrevem a tabela inteira, pelo que, para os mesmos leitores, esses valores ficam em branco — no histórico de execuções de um fluxo de trabalho e de um passo, e através do assistente de IA e das ferramentas de IA ligadas por MCP. Para eles, o [Weave](/pt-pt/guides/ai-assistant/weave-findings/) não verifica nos passos se há linhas ou valores vazios diferentes das execuções anteriores, pois uma constatação indicaria por si só que a contagem da tabela inteira se alterou.

Os Arquitetos do projeto veem os valores como antes, tal como todos os utilizadores de um projeto que não restringe linhas.

### Ver o que um membro pode ver

Para verificar o que uma pessoa específica pode ver, em vez do que é concedido a um grupo: abra **Identity → Member**, selecione o membro e abra o respetivo separador **Acesso a linhas**. A sua coluna **Acesso efetivo** lista, para cada projeto e coluna restringidos, os valores que esse membro vê através de todos os seus grupos combinados — incluindo concessões de atributos de grupo SSO e linhas em branco (`NULL`) quando a concessão de um grupo as inclui. Um Arquiteto do projeto aparece como **Vê todas as linhas (Architect)**, uma vez que um Arquiteto lê todas as linhas. É a mesma resposta que as consultas do próprio PlaidCloud aplicam, pelo que é útil para o suporte e para confirmar que uma alteração fez o que pretendia antes de alguém comunicar um problema.

### Erros mais claros

Quando o acesso a linhas bloqueia uma ação — uma consulta que escreveu por si num projeto restringido, uma edição sem Arquiteto, uma alteração à automatização, a uma dimensão ou a uma tabela de origem das concessões, e os outros casos descritos acima —, a mensagem indica o que está restringido e o que fazer a seguir, como os Arquitetos a quem recorrer, em vez de uma falha genérica.

### O acesso a linhas é auditado

Restringir ou deixar de restringir uma coluna e editar as concessões de um grupo escrevem todos uma entrada no [Registo do projeto](/pt-pt/get-started/tutorials/collaborate-versions-and-sharing/#ler-o-registo-do-projeto) desse projeto — quem fez a alteração e quando. Abra **Analyze → Projects → Log** no projeto para a ver. Não é preciso ativar nada no acesso a linhas para obter este registo; é registado da mesma forma que todas as outras alterações monitorizadas de um projeto.

## Definir grupos de segurança predefinidos


Para reduzir o tempo necessário para adicionar novos membros, identifique um conjunto de grupos de segurança predefinidos. Isto fornece um conjunto de base de grupos de segurança para novos membros, sem ser necessário atribuir cada pessoa manualmente. A definição está disponível ao adicionar um novo grupo de segurança, se assinalar a caixa na parte inferior da janela Security Group que diz “Assign to New Users by Default”.



## Realizar uma auditoria de segurança


A capacidade de auditoria de segurança permite ver a pertença a grupos em todos os membros e grupos.



**Para realizar uma auditoria de segurança:**


1. Abra Identity
2. Selecione o separador “Security”
3. Clique em “Security Group Audit” no menu pendente

Como todas as tabelas do PlaidCloud podem ser exportadas em formato CSV, as associações entre grupos e membros podem ser revistas fora do PlaidCloud, para fins históricos ou simplesmente para uma visualização offline descontraída.



**Para exportar a partir do formulário “Security Group Audit”:**


1. Abra Identity
2. Selecione o separador “Security”
3. Clique em “Security Group Audit” no menu pendente
4. Clique no pequeno ícone à direita de “Username” na tabela
5. Clique em “Export CSV” ou “Export XLXS”, consoante a sua preferência

## Ver as definições de permissões disponíveis


Cada aplicação utilizada na área de trabalho tem permissões específicas disponíveis. As permissões dos grupos de segurança baseiam-se nessas permissões das aplicações.


A lista completa de permissões disponíveis para cada aplicação pode ser consultada no Security Bin.



**Para aceder ao Security Bin:**


1. Abra Identity
2. Selecione “Security”
3. Clique em “Security Bins” no menu pendente

Para ver as definições de segurança detalhadas de cada aplicação, selecione o ícone de etiquetas no extremo esquerdo.



Estas informações sobre as definições de segurança disponíveis são meramente informativas. Para detalhes sobre a gestão de permissões, consulte a secção Gerir grupos de segurança acima.
