A gestão de segurança e acessos do PlaidCloud é simples. A um membro é concedido ou negado o acesso consoante os grupos a que está associado. Adicionar ou alterar a associação de segurança de um membro é facilmente personalizável.

<Aside>Cada área de trabalho pode ter um número ilimitado de grupos de segurança, mas recomendamos minimizar esse número para facilitar a gestão da segurança.</Aside>



## Gerir grupos de segurança


É possível adicionar, atualizar ou eliminar grupos de segurança.



**Para gerir grupos de segurança:**


1. Abra Identity
2. Selecione o separador “Security”
3. Clique em “Security Groups” no menu pendente (será apresentado um formulário com os grupos existentes)
4. Para adicionar um grupo, clique em “Create Security Group”
5. Para editar as permissões de um grupo, clique no ícone mais à esquerda

**Para gerir os membros de um grupo:**


1. Abra Identity
2. Selecione o separador “Security”
3. Clique em “Security Groups” no menu pendente
4. Clique no ícone Member
5. Arraste os membros pretendidos da coluna “Unassigned Members” para a coluna “Assigned Members” ou vice-versa para os remover

<Aside>Guardar com a coluna “Assigned Members” vazia não faz qualquer alteração e informa-o disso. Para retirar um grupo a todos, remova as respetivas permissões ou elimine o grupo, em vez de esvaziar a sua lista de membros.</Aside>

<Aside>Se um grupo tiver linhas concedidas através de [Acesso a linhas](#gerir-o-acesso-a-linhas), uma alteração de membros chega aos painéis de controlo em cerca de um minuto: quem adicionar passa a ver aí as linhas do grupo e quem remover deixa de as ver. Desativar ou eliminar um membro e eliminar um grupo têm efeito da mesma forma.</Aside>

<Aside type="caution">As permissões que não pode conceder a si próprio são deixadas como estão quando guarda a matriz de permissões de um grupo e não são apresentadas nela. Se precisar de alterar uma, peça a alguém que detenha essa permissão — a matriz só edita o que controla.</Aside>

## Gerir o acesso a linhas

O Acesso a linhas restringe as linhas de uma tabela que um grupo de segurança pode ver, com base no valor de uma coluna. Por exemplo, uma coluna `region` pode restringir o acesso, ficando um grupo com `East` e `Central` limitado às linhas que têm esses valores. Tudo o que diz respeito a um projeto e a uma coluna — escolher a coluna, escolher a origem dos seus valores e decidir qual o grupo que vê o quê — faz-se num único ecrã, e guardar tem efeito imediato.

Configurar e alterar o Acesso a linhas exige um Arquiteto do projeto ou um administrador do inquilino. Qualquer outra pessoa que abra o separador Security de um projeto é informada de que o acesso a linhas é exclusivo dos Arquitetos, e os pontos de entrada abaixo não lhe aparecem.

### Abrir o acesso a linhas

Todos os pontos de entrada abrem o mesmo ecrã de Acesso a linhas:

- **A barra de ferramentas do Explorador de tabelas** tem um botão **Acesso a linhas**, com um indicador quando a tabela já restringe linhas. Abre na primeira coluna restringida da tabela, se existir, e pode mudar para qualquer outra coluna da tabela.
- **O menu de facetas de uma coluna** tem **Restringir linhas por esta coluna…**, que abre o Acesso a linhas nessa coluna. Numa coluna que já restringe linhas, o item apresenta **Linhas restringidas por esta coluna — editar…**.
- **O separador Security de um projeto** lista todas as colunas restringidas do projeto, com as tabelas a que se aplicam, os grupos que detêm concessões e o respetivo estado de **Sincronizar**. Selecione uma coluna para a editar ou clique em **Restringir uma coluna…** para iniciar uma nova: escolha uma tabela e depois uma coluna. As colunas que já restringem linhas estão assinaladas com um cadeado.
- **Identity → Member**, no separador **Acesso a linhas** de um membro, e **Identity → Security → Security Groups**, no resumo de Acesso a linhas de um grupo. **Abrir acesso por linha** (ou **Editar**) abre a coluna selecionada; **Adicionar** restringe outra coluna no projeto dessa linha.

Quando aberto numa coluna, o ecrã permanece nessa coluna. Quando aberto com **Restringir uma coluna…** ou **Adicionar**, permite-lhe escolher uma.

### A grelha de acesso a linhas

Para restringir uma tabela por uma coluna:

1. Abra o Acesso a linhas a partir de qualquer um dos pontos de entrada acima e escolha a coluna, se não tiver chegado com uma — o seletor oferece as colunas reais da tabela, não texto livre.
2. Escolha uma **Origem do valor** — **Coluna** (os valores distintos de uma coluna de uma tabela), **Dimensão** (nós de uma dimensão) ou **Lista** (valores que introduz). O tipo de valor segue o tipo de dados da coluna.
3. Para cada grupo de segurança, assinale os valores que esse grupo pode ver. A grelha lista os grupos com acesso ao projeto, mais qualquer grupo que já detenha uma concessão na coluna.
4. Defina **Everyone else** como **sees all rows** ou **sees no rows** — isto abrange qualquer grupo sem seleções na grelha.
5. Clique em **Guardar**.

Guardar tem efeito imediato. As consultas do próprio PlaidCloud seguem a alteração de imediato e os seus painéis de controlo do Superset em cerca de um minuto — não há um passo separado para a aplicar nem uma caixa de diálogo de aprovação. O estado de sincronização do ecrã mostra até onde a alteração chegou; consulte [Manter os painéis de controlo sincronizados](#manter-os-painéis-de-controlo-sincronizados).

A grelha trata também dos detalhes por si:

- **Muitos valores.** Os valores estão ordenados. Quando uma coluna tem mais valores do que os que cabem, a grelha indica “Há mais valores do que os que cabem aqui — escreva para pesquisar.” e a caixa de filtro pesquisa a coluna inteira, mantendo todos os valores que um grupo já detém.
- **Valores em branco.** Uma caixa **Valores em branco — visíveis para todos os grupos com uma concessão** decide as linhas sem valor na coluna. Assinale-a e todos os grupos com qualquer concessão na coluna veem essas linhas.
- **Uma tabela que ainda não foi compilada** mostra **Compile primeiro esta tabela (execute o fluxo de trabalho que a cria)** em vez de uma lista vazia.
- **Guardar aguarda pelos valores apresentados no ecrã.** Enquanto os valores carregam — depois de mudar a origem do valor, a dimensão ou a tabela, ou de aplicar um modelo — **Guardar** fica desativado com a sugestão “Guardar fica disponível quando os valores desta origem forem carregados.” Se um carregamento falhar, a grelha indica-o e pede-lhe que escolha novamente a origem; nada é guardado até um carregamento ser bem-sucedido.

### Um nome de coluna, todas as tabelas

Uma restrição pertence ao *nome* de uma coluna no projeto, não a uma única tabela. Quando `region` restringe linhas, todas as tabelas do projeto com uma coluna chamada `region` ficam filtradas por ela, tanto nas consultas do próprio PlaidCloud como nos painéis de controlo. A lista **Applies to** da grelha mostra essas tabelas. É só de leitura, porque é o nome da coluna que a determina, e uma tabela que adicione mais tarde com a mesma coluna fica abrangida assim que for publicada.

Quando nenhuma tabela do projeto tem uma coluna com esse nome, a janela avisa de que a restrição não filtrará nenhum painel de controlo enquanto não existir uma tabela nessas condições, além de mostrar **Applies to 0 tables**. Adicione a coluna a uma tabela ou corrija o nome da coluna, e o aviso desaparece.

<Aside type="caution">
**O nome de uma coluna tem de corresponder exatamente** — incluindo maiúsculas/minúsculas e espaços em branco. `Region` e `region` são nomes diferentes, tal como `region` e `region ` com um espaço no fim. O seletor só oferece nomes de colunas reais, pelo que isto importa sobretudo se uma coluna for renomeada noutro local — o Acesso a linhas avisa então e indica a coluna mais próxima que encontrou, em vez de não restringir silenciosamente nada.
</Aside>

<Aside type="caution">
**Publicar uma tabela que restringe linhas configura o respetivo filtro de painel de controlo no mesmo passo.** Os painéis de controlo leem uma tabela através da sua vista de relatórios publicada, pelo que, quando publica ou volta a publicar uma tabela que contém uma coluna restringida, o PlaidCloud regista o filtro de painel de controlo dessa tabela antes de a publicação terminar. Se não conseguir, a publicação é recusada e tudo o que essa tentativa criou é revertido, de modo que uma tabela restringida nunca fica sem filtro nos painéis de controlo. Uma *vista* não pode ser publicada num projeto que restringe linhas, porque a consulta de uma vista pode mudar o nome da coluna restringida ou derivá-la. Consulte [Publicar tabelas](/pt-pt/guides/data/publish/).
</Aside>

### Deixar de restringir

**Deixar de restringir**, na grelha, remove a restrição após uma confirmação na própria página — “Deixar de restringir linhas por ‘region’? A concessão de todos os grupos nessa coluna é removida e todos passam a ver as suas linhas.” O Acesso a linhas confirma então “As linhas em ‘region’ já não estão restringidas.” O conjunto de dados do Superset da coluna desaparece com ela, a menos que ainda existam gráficos a utilizá-lo; nesse caso, o Acesso a linhas indica que o conjunto de dados se mantém e quantos gráficos o utilizam.

Uma coluna não pode ser renomeada nem eliminada enquanto restringir linhas. Um Arquiteto é informado de que deve primeiro deixar de a restringir no Acesso a linhas; qualquer outra pessoa é informada de que deve pedir a um Arquiteto do projeto.

### Quem pode alterar um projeto que restringe linhas

Os fluxos de trabalho, passos e funções definidas pelo utilizador de um projeto são executados como a identidade de serviço do próprio projeto, que lê todas as linhas. Quem os puder alterar poderia fazer com que um passo copiasse para uma tabela legível por si linhas a que não tem acesso, pelo que restringir linhas num projeto restringe também quem pode alterar o que o projeto faz. A partir do momento em que um projeto restringe pelo menos uma coluna:

- **A automatização é exclusiva dos Arquitetos.** Apenas os Arquitetos do projeto e os administradores do inquilino podem alterar fluxos de trabalho, passos, funções definidas pelo utilizador, agendamentos, variáveis de fluxo de trabalho e de projeto e modelos de correio eletrónico de notificação — e, pela mesma razão, importar um pacote de fluxo de trabalho, converter um fluxo de trabalho Alteryx, importar, copiar ou restaurar para o projeto, ou alterar o respetivo ambiente de ligação, a conta de documentos predefinida ou o modo de lançamento ERP. Todas as outras pessoas continuam a poder executar os fluxos de trabalho do projeto: **Início**, **Parar**, **Retomar** e **Executar passos selecionados** continuam disponíveis. O editor de passos, os controlos de criação do fluxo de trabalho, o editor de UDF e o formulário de agendamento abrem-se só de leitura para elas, com um aviso que indica os Arquitetos a quem pedir: “Este projeto restringe linhas, pelo que só os respetivos Arquitetos podem alterar fluxos de trabalho, passos, UDF, agendamentos, variáveis e modelos de notificação. Continua a poder executá-los.”
- **As dimensões que uma coluna restringida lê são exclusivas dos Arquitetos.** Uma dimensão que decide quem vê que linhas — a origem dos valores de uma coluna restringida — só pode ser alterada por um Arquiteto do projeto ou por um administrador do inquilino, e pelos próprios fluxos de trabalho do projeto. Isto abrange adicionar, mover, mudar o nome, copiar, limpar, carregar e restaurar os seus nós, bem como a própria dimensão. Qualquer outra pessoa é informada: “Esta dimensão decide quem vê que linhas de ‘region’, pelo que só um Arquiteto do projeto a pode alterar.” As dimensões que nenhuma restrição lê não são afetadas.
- **Uma tabela de origem de concessões é exclusiva dos Arquitetos.** Uma tabela associada como [origem de concessões](#associar-concessões-a-uma-tabela-de-origem) de uma coluna só pode ter as suas linhas alteradas, ou ser eliminada, por um Arquiteto do projeto, por um administrador do inquilino ou pelos fluxos de trabalho do projeto — seja através do Editor de dados, de uma importação, de um carregamento de conector ou da API.
- **Copiar o projeto é exclusivo dos Arquitetos**, e a cópia indica “Esta cópia não tem linhas restringidas.” — o novo projeto não tem qualquer restrição até que defina uma.
- **Restaurar uma versão anterior é uma alteração como qualquer outra.** Restaurar as definições do próprio projeto, ou uma dimensão acima referida, exige um Arquiteto do projeto. Uma restauração aplica-se sempre ao item a que a versão pertence, pelo que não pode ser apontada a outro projeto para contornar esta regra — consulte [Histórico de versões](/pt-pt/guides/projects/managing-projects/#histórico-de-versões).
- **Editar dados numa tabela restringida** exige um Arquiteto, conforme descrito em [Acesso a linhas e o Editor de dados](#acesso-a-linhas-e-o-editor-de-dados).

Antes de a primeira coluna de um projeto ser restringida, o Acesso a linhas informa quem é afetado: “Restringir linhas aqui significa que só os Arquitetos podem alterar os fluxos de trabalho, passos, UDF, agendamentos e modelos de notificação deste projeto. Atualmente, N membros podem alterá-los; continuarão a poder executá-los.”

As execuções continuam a funcionar exatamente como antes, incluindo as agendadas, porque são executadas como a identidade de serviço do projeto. O que uma execução produz segue a conceção que os seus Arquitetos lhe deram: uma tabela de saída sem a coluna restringida, um ficheiro exportado, uma mensagem de notificação ou uma linha de registo não é filtrado para quem o lê.

**Valores indicados no início de uma execução.** Quem puder executar um fluxo de trabalho pode iniciá-lo com valores próprios para as suas variáveis — o [App Runner](/pt-pt/guides/workflows/use-converted-alteryx-apps/#a-interface-app-runner) fá-lo com as respostas do seu formulário, e a API e as ferramentas de IA também o podem fazer. Esses valores aplicam-se apenas a essa execução: nunca são guardados no fluxo de trabalho e nenhuma outra execução, exportação ou leitor os vê. Como a execução decorre como a identidade de serviço, os valores podem alterar o que essa execução lê e escreve, pelo que deve conceder a permissão para executar fluxos de trabalho a pessoas em quem confia.

**Projetos que não restringem linhas.** Estas regras só têm efeito a partir do momento em que um projeto restringe uma coluna. Num projeto que não restringe nenhuma, quem puder alterar a automatização do projeto pode escrever um passo ou uma função definida pelo utilizador que — sendo executado como a identidade de serviço do projeto — altera o acesso ao projeto, tornando-se um dos seus Arquitetos. É intencional: um projeto assim não promete qualquer isolamento de linhas. Reserve aí os direitos de criação a pessoas em quem confiaria como Arquitetos, ou restrinja uma coluna.

### Manter os painéis de controlo sincronizados

O Acesso a linhas mostra em que ponto está uma alteração no caminho até aos seus painéis de controlo, na grelha e na coluna **Sincronizar** do separador Security do projeto:

| Estado | O que significa |
|---|---|
| **Em espera** | Uma alteração está guardada e a caminho dos painéis de controlo. Normalmente fica resolvida em cerca de um minuto. |
| **A tentar novamente** | Um envio falhou e está a ser repetido. O motivo da falha é apresentado junto ao estado, com **Tentar novamente** para voltar a enviar de imediato. |
| **Ainda não aplicado** | As restrições do projeto ainda não foram enviadas para os painéis de controlo. |
| **Aplicado** | A última tentativa de enviar as restrições para os painéis de controlo foi bem-sucedida. |
| **Sincronizado com os painéis de controlo** | O Acesso a linhas comparou o que os painéis de controlo aplicam com o que escreveria, e coincidem. |
| **Os painéis de controlo diferem** | Os painéis de controlo não aplicam o que o Acesso a linhas escreveria — uma regra foi alterada ou eliminada no Superset, ou a vista publicada de uma tabela não pode ser verificada. |
| **Erro** | O envio das restrições falhou. O motivo é apresentado junto ao estado. |

Quando uma alteração chega a **Aplicado**, a grelha verifica-a face aos painéis de controlo e passa para **Sincronizado com os painéis de controlo** ou **Os painéis de controlo diferem**. **Os painéis de controlo diferem** e **Erro** oferecem ambos **Tentar novamente**, que volta a enviar as restrições do projeto. Se não for possível ler o estado, a grelha indica “Não foi possível verificar o estado da sincronização.”

Um **Erro** causado por uma tabela identifica-a e diz o que fazer — por exemplo, uma tabela publicada sem a sua coluna restringida (“Volte a publicá-la ou anule a publicação.”), ou uma tabela com uma coluna restringida que não está publicada, a qual os painéis de controlo não conseguem filtrar até ser publicada. O estado mantém-se em **Erro** e indica a tabela não publicada até que a publique ou restrinja a coluna numa tabela publicada. Uma tabela assim não bloqueia o resto do projeto: todas as outras tabelas são mantidas em sincronia.

Os painéis de controlo seguem as mesmas concessões que as consultas do próprio PlaidCloud:

- **Todas as tabelas publicadas com a coluna são filtradas**, não apenas a tabela que estava a ver quando configurou a restrição.
- **Um grupo a quem só foram concedidos alguns valores é filtrado mesmo quando todos os outros veem todas as linhas**, em todas as tabelas cujo conjunto de dados do painel de controlo exista.
- **As alterações à associação a grupos de segurança chegam sozinhas aos painéis de controlo.** Adicionar alguém a um grupo ou removê-lo no PlaidCloud, desativar ou eliminar um membro, eliminar um grupo ou adicionar um novo membro que integra os seus grupos de segurança predefinidos atualiza o que essas pessoas veem nos painéis de controlo em cerca de um minuto, em todos os projetos que concedem valores a esse grupo, sem que ninguém volte a abrir o Acesso a linhas. Uma alteração de associação feita fora do PlaidCloud — diretamente no Keycloak, ou por o início de sessão único colocar alguém num grupo no momento do início de sessão — chega aos painéis de controlo em cerca de 15 minutos, sem nada para guardar ou repetir.

### Concessões por dimensão

Com **Dimensão** como origem do valor, assinale um nó para conceder tudo o que está abaixo dele. A concessão acompanha a dimensão: um membro adicionado sob um nó assinalado fica concedido a esse grupo na sincronização seguinte à gravação da dimensão, e um membro movido de debaixo dele, ou removido, deixa de ser concedido — ninguém precisa de voltar a abrir a grelha. Quando a voltar a abrir, os nós que assinalou aparecem novamente assinalados.

Desassinalar qualquer elemento abaixo de um nó assinalado desassinala o nó, e o grupo fica apenas com os membros ainda assinalados. Voltar a assinalar esse membro não assinala o nó de novo — clique na caixa do próprio nó para isso. **Colar**, **Selecionar tudo** e **Inverter** assinalam membros, nunca nós.

Um membro de dimensão cujo nome não pode ser utilizado como valor de acesso a linhas é recusado ao guardar, sendo identificado pelo nome. Se esse membro surgir mais tarde, as suas linhas não são concedidas a ninguém, e o estado de sincronização identifica-o: “A dimensão ‘…’ tem o membro ‘…’ que não pode ser utilizado como valor de acesso a linhas, pelo que as suas linhas não são concedidas. Mude-lhe o nome na dimensão.”

### Associar concessões a uma tabela de origem

Em vez de assinalar valores manualmente, pode apontar uma coluna restringida a uma tabela de origem
que já contenha a resposta — uma linha por grupo e o valor que este pode ver. Restrinja primeiro a coluna
na grelha e adicione depois um passo de fluxo de trabalho [**Definir acesso às linhas**](/pt-pt/reference/workflow-steps/tables/table-set-row-access/)
que indique a coluna, a tabela de origem e as colunas de grupo e de valor da tabela de origem. A primeira
execução do passo associa a coluna a essa tabela: as concessões definidas manualmente na coluna são
limpas e as concessões passam a ser definidas a partir das linhas da tabela.

Depois de associada, a coluna passa a ser **propriedade da origem**: a grelha de Acesso a linhas mostra-a
bloqueada, com um indicador que identifica a tabela de origem, e a edição manual das suas concessões é
recusada até que clique em **Remover associação**.

Cada execução seguinte do passo volta a ler a tabela de origem e a reaplicar as concessões — agende-o
depois do fluxo de trabalho que carrega ou atualiza essa tabela, e um grupo adicionado, removido ou
reatribuído nos dados de origem chega ao Acesso a linhas na execução seguinte, sem que ninguém edite a grelha
manualmente.

Como é a tabela de origem que decide quem vê o quê, apenas um Arquiteto do projeto, um administrador do inquilino
ou os próprios fluxos de trabalho do projeto podem alterar as suas linhas ou eliminá-la. Qualquer outra pessoa
é informada: “Esta tabela fornece as concessões de acesso a linhas de ‘region’, pelo que só um Arquiteto
do projeto pode alterar as suas linhas ou eliminá-la.”

### Modelos de restrição

Se criou uma forma de restrição que pretende reutilizar — a mesma origem do valor, o mesmo tipo de valor e
a mesma definição de valores em branco — guarde-a uma vez e aplique-a onde for necessário, em vez de a
reconstruir coluna a coluna.

- **Guardar como modelo…**, num ecrã de Acesso a linhas aberto, guarda a forma da coluna atual como um
  modelo com nome, ao nível do inquilino. Guarda apenas a forma — não leva consigo concessões.
- **Aplicar modelo**, na coluna de outro projeto, inicia essa coluna a partir da forma do modelo,
  com as concessões de todos os grupos vazias para que as preencha.

Qualquer Arquiteto de projeto pode guardar e aplicar modelos. Mudar o nome (**Mudar o nome…**) e eliminar
(**Eliminar**) um modelo exige um administrador do inquilino, uma vez que um modelo é partilhado por todo o inquilino.
Eliminar um modelo deixa as colunas a que foi aplicado restringidas tal como estão.

<Aside type="note">
Os modelos são cópias, não ligações. Editar um modelo depois disso não altera nenhuma coluna que
já o tenha aplicado — aplique novamente o modelo para atualizar uma coluna com uma revisão
posterior.
</Aside>

### Concessões a partir de atributos de grupo SSO

Uma coluna pode também obter as suas concessões do seu fornecedor de identidade em vez do PlaidCloud. Um
Arquiteto do projeto ativa uma coluna a partir do Acesso a linhas, ativando **Accept row-access grants from
SSO group attributes**.

Depois de ativado, o atributo do Keycloak `row_access.<column>` de um grupo de segurança define os valores que esse
grupo pode ver através dessa coluna — defina o atributo no grupo no Keycloak e o PlaidCloud
deteta-o automaticamente para qualquer grupo que já tenha acesso ao projeto. Não há mais nada
a configurar no próprio Acesso a linhas, e as concessões mantêm-se sincronizadas tanto nas consultas do próprio PlaidCloud
como nos painéis de controlo do Superset.

<Aside type="caution">
Isto só concede valores a um grupo que já consiga aceder ao projeto. Adicionar `row_access.region`
a um grupo sem acesso ao projeto não lhe concede nada até que o grupo receba também acesso ao
projeto.
</Aside>

### Pré-visualizar antes de guardar

O Acesso a linhas mostra o que uma alteração significa antes de a confirmar:

- Um rodapé **Pré-visualizar como** mostra quantas das linhas da tabela um grupo veria, em relação ao total, com uma amostra das próprias linhas — escolha qualquer grupo na grelha para o pré-visualizar. A pré-visualização é atualizada depois de guardar.
- Antes de guardar, o Acesso a linhas avisa-o sobre tudo o que mereça uma segunda análise: um grupo sem nada assinalado, e se isso significa que vê todas as linhas ou nenhuma, de acordo com a sua definição **Everyone else**; membros com acesso ao projeto que não são abrangidos pela concessão de nenhum grupo; ou linhas cujo valor nessa coluna está em branco (`NULL`) e que não foram concedidas a nenhum grupo.

### O que vê um membro restringido

Sempre que um membro restringido lê uma tabela pelo nome, obtém apenas as suas linhas — a grelha, as facetas de coluna e as transferências do Explorador de tabelas, a caixa de diálogo de transferência da tabela, as aplicações e ferramentas que leem como o espectador, e os painéis de controlo. O Explorador de tabelas mostra **Linhas limitadas pelo seu acesso** na barra de ferramentas quando a grelha que está a ver foi filtrada pelas suas concessões, e iniciar uma transferência que será filtrada indica “Linhas limitadas pelo seu acesso.” Um Arquiteto, que lê todas as linhas, não vê nenhum dos avisos.

### Acesso a linhas e consultas que escreve por si

O Acesso a linhas limita as linhas que um grupo pode ver filtrando a tabela relativamente à qual está definido. Uma consulta que alguém escreve por si não tem uma única tabela à qual anexar esse filtro — uma consulta pode juntar, combinar ou aninhar quantas tabelas quiser — pelo que, num projeto que restringe linhas, o PlaidCloud recusa-se a executar uma consulta fornecida pelo autor da chamada, em vez de devolver linhas que nada validou.

Isto aplica-se à leitura através de SQL próprio, à exportação dos resultados de SQL próprio para um ficheiro ou para outra base de dados, e à introdução de uma condição de linha na pré-visualização “Test row 1” de um passo de expansão. **Não** se aplica à leitura de uma tabela pelo nome, que é a forma habitual de as aplicações e ferramentas lerem dados — estas aplicam as concessões e devolvem as linhas a que o espectador tem direito. Uma faceta de coluna escrita como uma consulta simples a uma única tabela também é lida pelo nome, pelo que devolve os valores do próprio membro em vez de ser recusada.

Quem for recusado é informado de qual era o projeto e remetido para os leitores por nome. Um Arquiteto do projeto pode executar a consulta tal como está escrita e exportar os respetivos resultados em qualquer formato, porque um Arquiteto já pode conceder a si próprio todos os valores de todas as colunas restringidas.

Importar uma folha de cálculo não é, por si só, uma consulta que escreveu por si — uma importação de ficheiro normal não lê quaisquer dados restringidos, limita-se a criar a nova tabela do próprio projeto a partir do ficheiro que carregou, pelo que não é afetada pelo Acesso a linhas. A exceção é uma importação cuja projeção de dados é fornecida pelo autor da chamada: uma expressão por coluna ou um mapeamento dinâmico do Excel. No ecrã de importação interativo, estas são recusadas da mesma forma que as superfícies de SQL livre acima referidas e exigem um Arquiteto do projeto, porque uma projeção fornecida pelo autor da chamada poderia ler outra tabela. Uma importação executada a partir de um fluxo de trabalho não é afetada em nenhum dos casos, uma vez que é executada sob a identidade de serviço do próprio projeto.

<Aside type="caution">
Restringir a sua primeira coluna num projeto altera isto para todos os que o utilizam. Se uma aplicação Panel, um bloco de notas ou uma integração nesse projeto ler dados compondo o seu próprio SQL, passe-a a ler a tabela pelo nome antes de restringir — caso contrário, deixa de funcionar para todos os que não sejam Arquitetos.
</Aside>

### Acesso a linhas e o Editor de dados

O Editor de dados lê e escreve diretamente numa tabela, pelo que o Acesso a linhas se aplica a ele em ambos os sentidos.

Abrir uma tabela restringida no Editor de dados mostra apenas as linhas concedidas ao seu grupo de segurança — o mesmo filtro que o acompanha num painel de controlo, e que se aplica mesmo quando a coluna restringida não é uma das colunas apresentadas na grelha.

Guardar as suas edições exige **Arquiteto** no projeto. Uma gravação substitui as linhas da tabela em bloco em vez de as ler, e não é filtrada linha a linha, pelo que editar dados numa tabela restringida é tratado como uma ação de criação e não como uma leitura: quem não for Arquiteto é informado de que precisa dessa função. Uma tabela sem coluna restringida é editada como antes, tal como qualquer projeto que não restrinja linhas.

### Contagens de linhas e tamanhos das tabelas

A contagem de linhas e o tamanho de armazenamento de uma tabela descrevem a tabela inteira, não as linhas que pode ver, pelo que revelariam a um leitor restringido quantas linhas existem para além da sua concessão. Num projeto que restringe linhas, quem tiver as leituras filtradas não vê a contagem de linhas nem o tamanho de nenhuma tabela do projeto — nas listas de tabelas, na pesquisa, nos detalhes das tabelas e nos instantâneos, e através do assistente de IA e das ferramentas de IA ligadas por MCP. Isto abrange todas as tabelas do projeto, incluindo tabelas sem coluna restringida. Os totais do próprio projeto também lhes ficam ocultos — a contagem total de linhas e o tamanho em Home, nas listas de projetos e na pesquisa, e nos detalhes do projeto.

O mesmo se aplica ao histórico de execuções de fluxos de trabalho. As linhas lidas e escritas que cada execução e cada passo registaram também descrevem a tabela inteira, pelo que, para os mesmos leitores, esses valores ficam em branco — no histórico de execuções de um fluxo de trabalho e de um passo, e através do assistente de IA e das ferramentas de IA ligadas por MCP. Para eles, o [Weave](/pt-pt/guides/ai-assistant/weave-findings/) não verifica nos passos linhas ou valores vazios em comparação com execuções anteriores, uma vez que uma constatação revelaria por si só que a contagem da tabela inteira se alterou.

Os Arquitetos do projeto veem os valores como antes, tal como todos os utilizadores de um projeto que não restringe linhas.

### Ver o que um membro pode ver

Para verificar o que uma pessoa específica pode ver, em vez do que é concedido a um grupo: abra **Identity → Member**, selecione o membro e abra o respetivo separador **Acesso a linhas**. A coluna **Acesso efetivo** lista, para cada projeto e coluna restringidos, os valores que esse membro vê através de todos os seus grupos combinados — incluindo concessões de atributos de grupo SSO e linhas em branco (`NULL`) quando a concessão de um grupo as inclui. Um Arquiteto de projeto aparece como **Vê todas as linhas (Architect)**, uma vez que um Arquiteto lê todas as linhas. É a mesma resposta que as consultas do próprio PlaidCloud aplicam, pelo que é útil para o suporte e para confirmar que uma alteração fez o que pretendia antes de alguém comunicar um problema.

### Erros mais claros

Quando o Acesso a linhas bloqueia uma ação — uma consulta que escreveu por si num projeto restringido, uma edição sem Arquiteto, uma alteração à automatização, a uma dimensão ou a uma tabela de origem de concessões, e os restantes casos descritos acima — a mensagem indica o que está restringido e o que fazer a seguir, como os Arquitetos a quem pedir, em vez de uma falha genérica.

### O acesso a linhas é auditado

Restringir ou deixar de restringir uma coluna, e editar as concessões de um grupo, escrevem todos uma entrada no [Registo do projeto](/pt-pt/get-started/tutorials/collaborate-versions-and-sharing/#ler-o-registo-do-projeto) desse projeto — quem fez a alteração e quando. Abra **Analyze → Projects → Log** no projeto para a ver. Nada no Acesso a linhas tem de ser ativado para obter este rasto; é registado da mesma forma que qualquer outra alteração rastreada a um projeto.

## Definir grupos de segurança predefinidos


Para reduzir o tempo necessário para adicionar novos membros, identifique um conjunto de grupos de segurança predefinidos. Isto fornece um conjunto de base de grupos de segurança aos novos membros, sem necessidade de atribuir manualmente cada pessoa. A definição está disponível ao adicionar um novo grupo de segurança, se assinalar a caixa no fundo da janela Security Group que diz “Assign to New Users by Default”.



## Realizar uma auditoria de segurança


A capacidade de auditoria de segurança permite ver a associação a grupos de todos os membros e grupos.



**Para realizar uma auditoria de segurança:**


1. Abra Identity
2. Selecione o separador “Security”
3. Clique em “Security Group Audit” no menu pendente

Como todas as tabelas no PlaidCloud são exportáveis no formato de ficheiro CSV, as associações de membros a grupos podem ser revistas fora do PlaidCloud, seja para fins históricos ou apenas para uma agradável visualização offline.



**Para exportar a partir do formulário “Security Group Audit”:**


1. Abra Identity
2. Selecione o separador “Security”
3. Clique em “Security Group Audit” no menu pendente
4. Clique no pequeno ícone à direita de “Username” na tabela
5. Clique em “Export CSV” ou “Export XLXS”, consoante a sua preferência

## Ver as definições de permissões disponíveis


Cada aplicação utilizada na área de trabalho tem permissões específicas disponíveis. As permissões dos grupos de segurança baseiam-se nessas permissões das aplicações.


A lista completa de permissões disponíveis para cada aplicação pode ser consultada no Security Bin.



**Para aceder ao Security Bin:**


1. Abra Identity
2. Selecione “Security”
3. Clique em “Security Bins” no menu pendente

Para ver as definições de segurança detalhadas de cada aplicação, selecione o ícone de etiquetas no extremo esquerdo.



Esta informação sobre as definições de segurança disponíveis é meramente informativa. Para obter detalhes sobre a gestão de permissões, consulte a secção Gerir grupos de segurança acima.
