## Pesquisar

A pesquisa de projetos é feita com **Filtro** na parte inferior da lista, junto à contagem de linhas. Prima **/** ou Ctrl/Cmd+F para ir diretamente para ele. O filtro procura correspondências nos nomes e nas etiquetas dos projetos e mostra os resultados na hierarquia.


## Criar novos projetos

Para criar um novo projeto:

1. Abra o Analyze
2. Selecione “Projetos” na barra de menus superior
3. Clique no botão “Novo projeto”
4. Preencha as informações do formulário, incluindo a secção “Access Control”
5. Clique em “Criar”

O projeto fica então pronto para atualizar as permissões de acesso, adicionar proprietários e criar fluxos de trabalho.

<Aside>Por predefinição, o projeto fica acessível a todos os membros da área de trabalho atual</Aside>


## Definir uma conta de documentos predefinida

Na página inicial do projeto, junto a **Ambiente da ligação**, escolha uma **Conta de documentos predefinida** para o projeto — ou **Nenhum** para a limpar.

Dentro do projeto, todos os seletores de ficheiros listam **Predefinição do projeto** em primeiro lugar, em representação da conta que o projeto tiver definida nesse momento. Deixa de constar da lista quando sai do projeto, quando o projeto não tem predefinição definida, quando essa conta foi eliminada ou quando deixa de ter acesso a ela.

Um novo passo de ficheiro pré-seleciona Predefinição do projeto quando o projeto tem uma. Os passos existentes nunca são reescritos — cada um mantém a conta com que foi guardado até que a altere, uma vez que a conta de documentos é uma escolha por passo, ao passo que um passo normalmente segue o ambiente da ligação do projeto.

Um passo deixado em Predefinição do projeto resolve para a conta que for a predefinição do projeto quando é executado, pelo que alterar a predefinição a meio de uma execução afeta apenas os nós que ainda não começaram — tal como alterar o ambiente da ligação. Se um passo for executado em Predefinição do projeto e o projeto não tiver predefinição definida, a execução falha e indica o projeto, em vez de recorrer a outra conta.


## Fixar um passo num único ambiente

Os passos seguem o [ambiente da ligação](/pt-pt/guides/projects/project-home/#dados-e-ligações) do projeto, pelo que alternar o projeto entre QA e Produção move-os todos. Um passo cujo formulário tenha uma definição **Ambiente** oferece duas opções:

- **Project environment** segue o ambiente da ligação do projeto. Mantenha esta opção, salvo se tiver um motivo para não o fazer.
- **Fixed environment** ignora o ambiente da ligação do projeto e utiliza sempre o ambiente que escolher. Utilize-a apenas para um passo que tenha de permanecer num único ambiente independentemente da alternância do projeto, como ler dados de referência de Produção num projeto definido para QA. O ícone de aviso é um lembrete de que o passo não acompanha uma alternância.

Um passo com um ambiente fixo adiciona um aviso ao respetivo registo sempre que é executado num ambiente diferente do do projeto. Se o seu ambiente fixo já não existir, por exemplo num passo copiado de outra área de trabalho, o passo falha e indica-o, em vez de ser executado noutro local.

Os passos de lançamento ERP utilizam sempre o ambiente do projeto, pelo que **Fixed environment** não está disponível para eles.

O ambiente predefinido não pode ser eliminado e nenhum outro ambiente pode ser eliminado enquanto um projeto o utilizar, um passo o tiver como ambiente fixo ou um agente o servir. A mensagem indica o que ainda o utiliza, identificando o que o utilizador pode aceder e contando o restante.


## Histórico de versões

Todos os objetos de um projeto — um passo, uma UDF, um fluxo de trabalho, uma dimensão, um esquema guardado, um editor de documentos ou de dados e as próprias definições do projeto — são abrangidos por cópias de segurança do histórico de versões. Não é feita uma cópia de segurança em cada gravação individual; em vez disso, quando um objeto fica 30 segundos sem nova gravação, é feita uma cópia de segurança do seu estado estabilizado. Uma série de edições — várias gravações em rápida sucessão — produz uma única versão com o resultado final, e não uma versão por gravação. A gravação nunca é atrasada à espera de uma cópia de segurança: a contagem decrescente e a própria cópia de segurança decorrem ambas em segundo plano. Se precisar de uma versão de imediato, utilize **Back up now** para capturar o estado atual de imediato e aguardar a conclusão — disponível na interface, na API e como a ação `backup` das ferramentas MCP `*_versions`. O histórico de versões está disponível em todos os planos, incluindo o Free.

As versões anteriores permitem a recuperação num ponto no tempo: restaurar um objeto para uma versão anterior. O restauro é recusado num projeto bloqueado, tal como qualquer outra alteração aí.

Uma versão é restaurada no próprio local. Restaurar uma versão de um projeto, dimensão, função definida pelo utilizador, passo, fluxo de trabalho ou editor de dados substitui esse mesmo item, e indicar um item diferente como destino é recusado — por exemplo, “A project version is restored in place. Leave the target out, or set it to this project.” O restauro é uma alteração ao item, pelo que exige a mesma função que a sua edição; num projeto que [restringe linhas](/pt-pt/administration/access/managing-security-groups-and-assignments/#quem-pode-alterar-um-projeto-que-restringe-linhas), restaurar o projeto ou uma dimensão que uma coluna restrita lê exige um Arquiteto do projeto. Para recuperar dados antigos de uma tabela como uma tabela separada, restaure um [instantâneo da tabela](/pt-pt/guides/data/table-snapshots/) para uma nova tabela.

Além deste acompanhamento automático, os projetos e os seus elementos também permitem criar versões. Criar uma versão é simples e também pode intercalar alterações de uma versão para outra. Isto proporciona uma forma simples de acompanhar instantâneos ou de criar uma versão para desenvolvimento e depois intercalar essas alterações na versão que não é de desenvolvimento quando pretender. Consulte [Colaborar: versões, comparação e partilha](/pt-pt/get-started/tutorials/collaborate-versions-and-sharing/) para ver a criação de versões, a comparação e a intercalação na prática.

Os dados das tabelas têm o seu próprio histórico — instantâneos tirados pelo Lakehouse em cada escrita — descrito em [Instantâneos de tabelas](/pt-pt/guides/data/table-snapshots/).

### Restaurar e reter através do assistente de IA ou do MCP

Através do assistente de IA ou do MCP, `dimension_versions` restaura, retém e liberta uma versão de dimensão pelo respetivo `version_id`, e `restore_project` repõe todas as dimensões do projeto na última cópia de segurança, e cada listagem `*_versions` (passos, UDFs, fluxos de trabalho, dimensões, projetos) mostra o `version_id` de cada versão e se está retida. Um `restore` através de qualquer ferramenta `*_versions`, ou da API REST, restaura o item no próprio local: omita o destino ou defina-o como o próprio item. `project_upsert` pode desbloquear um projeto bloqueado e respeita `if_match`, falhando em vez de substituir uma alteração feita desde a última vez que leu o projeto.


## Gerir o acesso ao projeto

### Tipos de acesso

A segurança dos projetos foi simplificada em três tipos de acesso:

* Todos os membros da área de trabalho
* Apenas membros específicos
* Apenas grupos de segurança específicos

Definir a segurança do projeto é fácil:

1. Abra o Analyze
2. Selecione “Projetos”
3. Clique no ícone de edição do projeto que pretende restringir
4. Escolha a restrição pretendida em “Access Control”
5. Clique em “Update”

Apenas um Arquiteto do projeto ou um administrador do inquilino pode alterar quem tem acesso a um projeto — o seu tipo de acesso, os membros e os grupos de segurança que nele constam e as suas partilhas de dados. Qualquer outra pessoa vê esses painéis só de leitura, com a nota “Only project Architects can change access.”


## Todos os membros da área de trabalho

O acesso “Todos os membros da área de trabalho” é a opção mais simples, uma vez que dá acesso a todos os membros da área de trabalho e não exige qualquer atribuição adicional de membros.


## Apenas membros específicos

A definição de acesso “Apenas membros específicos” exige a atribuição de cada membro ao projeto. Para atribuir membros a um projeto:

1. Abra o Analyze
2. Selecione “Projetos” na barra de menus superior
3. Clique no ícone de membros
4. Conceda acesso aos membros selecionando a caixa de verificação junto ao respetivo nome na coluna “Access”
5. Clique em “Update”

Em clouds com um grande número de membros, esta abordagem pode exigir mais esforço do que o desejável, e é aí que os grupos de segurança se tornam úteis.

<Aside>Para adicionar membros, tem de ser membro da área de trabalho.</Aside>


## Apenas grupos de segurança específicos

A opção “Apenas grupos de segurança específicos” permite atribuir a grupos de segurança específicos a permissão de aceder à conta. Com as restrições de acesso baseadas na associação a um ou mais grupos de segurança, a administração do acesso à conta para grupos maiores é muito mais simples. Isto é particularmente útil quando combinado com a associação automática a grupos do início de sessão único. Ao utilizar o início de sessão único para definir as atribuições de membros a grupos, estes grupos também podem ativar e desativar implicitamente o acesso a projetos.

Para editar os grupos atribuídos:

1. Abra o Analyze
2. Selecione “Projetos” na barra de menus superior
3. Clique no ícone de grupos de segurança
4. Conceda acesso aos grupos de segurança selecionando a caixa de verificação junto ao respetivo nome na coluna “Access”
5. Clique em “Update”


## Partilhar dados entre projetos

Uma partilha de dados permite que um projeto aceda às tabelas de outro projeto — por exemplo, para que os passos [Import Project Table](/pt-pt/reference/workflow-steps/import/import-project-table/) e [Export Project Table](/pt-pt/reference/workflow-steps/export/export-project-table/) possam mover dados entre eles. Uma partilha é concedida pelo projeto cujos dados são partilhados, a um outro projeto:

1. Abra o projeto cujos dados pretende partilhar e aceda à respetiva [página inicial do projeto](/pt-pt/guides/projects/project-home/).
2. Abra **Access & sharing**. Em **Partilhas de dados**, clique em **Nova partilha de dados**.
3. Em **Selecionar projeto**, escolha o projeto que pode utilizar os dados deste projeto.
4. Em **Operações permitidas**, assinale **Leitura**, **Escrita** ou ambas e clique em **Adicionar partilha de dados**.

**Eliminar partilha de dados** remove uma partilha, após confirmação. Apenas um Arquiteto do projeto ou um administrador do inquilino pode adicionar ou eliminar as partilhas de dados de um projeto.

Uma partilha é concedida a um projeto, pelo que fala apenas pelos membros e pelos fluxos de trabalho desse projeto:

- **Ler** através de uma partilha exige uma função no projeto a que foi concedida. Quem não tiver função aí não obtém nada da partilha.
- **Escrever** através de uma partilha — criar uma tabela, uma pasta ou uma dimensão no projeto que partilha — exige uma partilha de **Escrita** e a função de Gestor ou Arquiteto no seu próprio projeto, a função que poderia fazer a mesma alteração aí. A qualquer outra pessoa é indicado “Writing to this project through a data share needs a write share from it to your project, and the Manager or Architect role in your project.”

Os fluxos de trabalho são executados com a identidade do seu próprio projeto, pelo que os passos Import Project Table e Export Project Table funcionam através de uma partilha independentemente de quem inicia a execução.


## Definir diferentes funções de visualização

Muitas vezes, um projeto pode exigir várias transformações e tabelas para concluir passos intermédios, enquanto o resultado final pode consistir apenas em algumas tabelas. Os membros nem sempre precisam de ver todos os elementos do projeto, por vezes apenas o produto final. O PlaidCloud permite definir diferentes funções de visualização para reduzir facilmente a desarrumação e controlar a visibilidade de cada membro.

Existem três funções de visualização incorporadas: **Arquiteto, Gestor** e **Explorador**

A função **Arquiteto** é a mais simples, pois permite visibilidade e controlo totais sobre projetos, fluxos de trabalho, tabelas, variáveis, editores de dados, hierarquias e funções definidas pelo utilizador.

As funções **Gestor** e **Explorador** não têm privilégios de acesso específicos, mas podem ser definidas à medida. Por outras palavras, pode escolher quais os itens visíveis para cada grupo.

<Aside>**Gestor*** *e **Explorador** não são grupos de segurança; apenas proporcionam uma forma conveniente de segregar funções e a visibilidade da informação.</Aside>

Pode tornar todos **Arquiteto** se considerar necessária a visibilidade de tudo no projeto; caso contrário, pode designar os membros como membros do projeto **Gestor** e/ou **Explorador** e controlar a visibilidade dessa forma.

Para definir a função:

1. Abra o Analyze
2. Selecione “Projetos”
3. Clique no ícone de membros
4. Selecione o membro cuja função pretende alterar
5. Faça duplo clique na função atual na coluna “Role”
6. Selecione a função pretendida
7. Clique em “Update”


## Gerir variáveis do projeto

Ao executar um projeto ou um fluxo de trabalho, pode ser útil definir variáveis para tarefas recorrentes, de modo a reduzir a desarrumação e poupar tempo. Estas variáveis funcionam tal como uma variável algébrica normal, permitindo definir o que a variável representa e que operação deve segui-la. O PlaidCloud permite definir estas variáveis ao nível do projeto, o que afeta todos os fluxos de trabalho desse projeto, ou ao nível do fluxo de trabalho, o que afeta apenas esse fluxo de trabalho específico.

Para definir uma variável ao nível do projeto:

1. Abra o Analyze
2. Selecione “Projetos”
3. Clique no ícone Manage Project Variables

A partir da tabela de variáveis, pode ver as variáveis e ver/editar os valores atuais. Também pode adicionar novas variáveis ou eliminar as existentes clicando no botão “New Project Variable”.


## Copiar um projeto

**Copiar projeto** copia um projeto — na totalidade ou apenas as partes que escolher — para um projeto totalmente novo ou para um projeto que já existe.

Para copiar um projeto:

1. Abra o Analyze
2. Selecione "Projetos"
3. Selecione o projeto que pretende copiar
4. Clique no botão **Ações** e escolha **Copiar projeto**
5. Escolha o destino, selecione o que trazer e que dados copiar e clique em **Copiar projeto**
6. Verifique o resumo **Rever antes de copiar** e clique em **Iniciar cópia**

### Escolher o que copiar

A árvore de seleção lista o que o projeto contém, por tipo — fluxos de trabalho, passos, tabelas, dimensões, editores de dados, funções definidas pelo utilizador. Deixe tudo assinalado para copiar o projeto inteiro ou assinale apenas as partes pretendidas.

Não precisa de determinar de que dependem essas partes. Tudo o que assinalar traz consigo as suas dependências: as tabelas que um passo lê e escreve, as dimensões que carrega ou em relação às quais aloca, as funções definidas pelo utilizador que chama e qualquer subfluxo de trabalho ou macro que invoque. Os sensores de um fluxo de trabalho acompanham o fluxo de trabalho.

**Os sensores copiados chegam desativados.** Nada é disparado na cópia até ativar cada sensor no projeto de destino. Uma importação que substitui itens duplicados não adiciona um segundo sensor quando o fluxo de trabalho de destino já o tem.

### Copiar para um novo projeto

Atribua ao novo projeto um nome e um ID. O ID passa a ser o nome do seu esquema e não pode ser alterado mais tarde.

**Os agendamentos chegam em pausa.** Quando copia um projeto inteiro para um novo, os eventos agendados de cada fluxo de trabalho chegam em pausa, para que a cópia não comece a executá-los por si própria. Quando a cópia termina, uma mensagem lista os eventos que estavam ativos no original. Para executar um na cópia, selecione-o em **Ferramentas** > **Agendador de eventos** e clique em **Ativar selecionados** — consulte [Colocar um evento em pausa](/pt-pt/administration/scheduled-events/event-scheduler/#pausar-um-evento).

### Copiar para um projeto existente

Escolha o destino na lista de projetos. A cópia acrescenta ao projeto em vez de o substituir.

**É necessário poder alterar o destino.** Uma cópia para um projeto em que não tem função é recusada, tal como uma cópia para um projeto que foi bloqueado para impedir alterações — verificado antes de qualquer leitura ou escrita, pelo que uma cópia recusada deixa o destino intacto. Um projeto também não pode ser copiado para si próprio.

**Copiar um projeto que restringe linhas exige um Arquiteto do projeto.** A cópia é um novo projeto sem restrição de [acesso a linhas](/pt-pt/administration/access/managing-security-groups-and-assignments/#gerir-o-acesso-a-linhas), e a cópia informa-o disso: “This copy is not row-restricted.” Configure o Acesso a linhas na cópia antes de a partilhar. Copiar para um projeto existente que restringe linhas exige igualmente um dos seus Arquitetos ou um administrador do inquilino.

**O destino mantém as suas próprias definições.** O nome, o ID, o ambiente de ligação de dados, as predefinições de armazenamento, a conta de documentos, o tipo de acesso, as listas de acesso e as concessões de acesso a linhas ficam como estão. Apenas o conteúdo que selecionou é trazido.

Um passo definido como **Predefinição do projeto** leva essa definição consigo, e não uma conta — depois de copiado, resolve para a predefinição que o projeto de destino tiver, e não para a que tinha na origem.

Quando um item recebido é o mesmo item que já existe no destino, escolhe o que acontece:

- **Substituir itens duplicados pelos dados recebidos** — a versão recebida substitui a que está no destino.
- **Criar nova cópia dos itens duplicados** — o destino mantém o que tem e o item recebido é adicionado a seu lado com ` copy` acrescentado ao nome, e um contador se esse nome também estiver ocupado.

As variáveis de projeto e de fluxo de trabalho são a exceção a *Criar nova cópia dos itens duplicados*: uma variável é identificada pelo nome, pelo que não há forma de adicionar uma segunda cópia sem a renomear para algo a que nada se refira. Quando o destino já define uma variável que a cópia também transporta, o valor do próprio destino é mantido e a cópia indica quais as variáveis que deixou intactas. *Substituir itens duplicados pelos dados recebidos* trata as variáveis como tudo o resto e substitui-as.

Esta correspondência é por identidade, não por nome — um item que veio originalmente do mesmo projeto é reconhecido como o mesmo item, enquanto dois itens que apenas partilham o mesmo nome são tratados como itens diferentes e ambos existirão depois.

### Escolher a quantidade de dados a copiar

Em **Data to copy**, duas definições determinam que dados são trazidos com a sua seleção.

**Dados da tabela** define quantas linhas de cada tabela são copiadas:

| Opção | O que é copiado |
| --- | --- |
| **No table data** | Tabelas, passos e o resto da seleção, sem linhas. Esta é a opção predefinida. |
| **Completo** | Todas as linhas de todas as tabelas, no mesmo Lakehouse e entre Lakehouses. |
| **Amostra** | Até ao número de **linhas por tabela** que introduzir, apenas para um novo projeto. O número pode ir de 1 a 1 000 000. |

Uma tabela amostrada contém até esse número de linhas, ou todas as suas linhas quando tem menos. Uma cópia **Completo** ou **Amostra** copia várias tabelas em simultâneo, pelo que um projeto com muitas tabelas termina mais depressa.

**Copy dimension members** copia os membros de todas as dimensões da seleção, qualquer que seja a opção de **Dados da tabela** que escolher. Está ativado por predefinição, pelo que uma cópia sem dados de tabela chega na mesma com dimensões preenchidas e é rápida de fazer. Desmarque-o para copiar as dimensões sem os respetivos membros.

Através da API REST (`POST /rest/v1/analyze/project/copy`) ou da ferramenta MCP `project_copy`, defina `data_mode` como `structure`, `full` ou `sample` e `dimension_members` como `true` ou `false`. Quando omite `dimension_members`, os membros só são copiados quando as linhas das tabelas também o são. `project_copy` devolve também os avisos da cópia, como as autorizações de escrita no ERP que não foram copiadas.

### Rever a cópia

Antes de copiar seja o que for, **Rever antes de copiar** resume a cópia: o projeto de origem, o destino, a opção de **Dados da tabela**, se os **Membros da dimensão** estão incluídos, o número de tabelas e vistas, o tamanho, um tempo estimado, o Lakehouse de origem e de destino e quaisquer avisos em **Tenha em atenção**. Clique em **Iniciar cópia** para começar ou em **Cancelar** para voltar atrás e alterar a seleção.

### Quem pode ver a cópia

Uma cópia feita com dados — linhas de tabelas, membros de dimensões ou ambos — é privada da pessoa que a fez. Partilhe-a a partir do novo projeto quando estiver pronta. Uma cópia de um projeto com segurança ao nível da linha permanece privada pelo mesmo motivo.

Copiar dados para um projeto existente exige acesso de escrita a esse projeto.

### Autorizações de escrita no ERP na cópia

Uma nova cópia privada para si mantém as [autorizações de escrita no ERP](/pt-pt/guides/workflows/run-a-workflow/#autorizar-o-projeto-a-lançar) do projeto de origem, para que possa testar os respetivos fluxos de trabalho de lançamento sem voltar a autorizar a cópia. Isso aplica-se a qualquer cópia para um novo projeto feita com dados de tabela (**Completo** ou **Amostra**), membros de dimensões ou ambos. As autorizações são copiadas quando:

- É Arquiteto do projeto de origem ou administrador da área de trabalho.
- Faz a cópia pessoalmente, e não através de um agente ou de uma conta de serviço.

Cada autorização só é copiada se a pudesse conceder hoje: a respetiva ligação e ambiente ainda existem e tem acesso de escrita à ligação. As autorizações copiadas são registadas como suas.

**A cópia chega em Simulate.** Se o **Modo de lançamento ERP** do projeto de origem for Live, o da cópia é definido como Simulate, pelo que os respetivos fluxos de trabalho constroem e verificam o que lançariam sem contactar o ERP. Uma origem definida como Simulate ou Off mantém essa definição. Quando estiver pronto para lançar a sério a partir da cópia, defina o **Modo de lançamento ERP** em **Lançamento ERP** na página inicial da cópia como Live — consulte [Escolher um modo de lançamento](/pt-pt/guides/workflows/run-a-workflow/#escolher-um-modo-de-lançamento). Os agendamentos e os sensores continuam a chegar em pausa e desativados, como descrito acima, pelo que nada é executado na cópia até o ativar.

Uma cópia para um projeto existente, ou uma sem dados de tabela nem membros de dimensões, começa sem as autorizações da origem. Autorize-a em **Lançamento ERP** > **Autorizações de escrita no ERP** na respetiva página inicial antes de lançar.

**Resultados da cópia** indica o que aconteceu, por exemplo “2 ERP write authorizations copied; ERP posting is in Simulate”, juntamente com quantas não foram copiadas.

### Resultados da cópia

Quando a cópia termina, uma janela **Resultados da cópia** resume as tabelas e os membros de dimensões copiados e lista cada tabela e dimensão pelo nome com o respetivo resultado — **Copiado**, **Copiado com alterações**, **Amostrado**, **Ignorado** ou **Falhou** — e o motivo de qualquer uma que tenha sido ignorada ou tenha falhado. Clique em **Retry failed items** para copiar novamente as tabelas e dimensões com falha; o seu conteúdo atual na cópia é substituído. É notificado, por mensagem e por correio eletrónico, quando uma cópia termina ou falha, e pode reabrir os resultados a partir da mensagem ou mais tarde, selecionando a cópia no separador **Projetos** e escolhendo **Ver resultado da importação ou cópia** no menu **Ações**.

Os resultados permanecem na cópia até alguém os dispensar. Depois de a cópia terminar, clique em **Dispensar resultado** para os remover para todos os que podem abrir o projeto. Nada no projeto muda, mas os itens com falha deixam de poder ser repetidos a partir da janela. Dispensar exige acesso de edição ao projeto e o projeto não pode estar bloqueado.

### Atualizar referências

Os passos de fluxo de trabalho de um projeto referem-se a tabelas e a outros objetos dentro desse projeto. **Atualizar referências** reescreve essas referências para que apontem para a cópia e não para o original — o que é quase sempre o pretendido e é o motivo pelo qual está ativado por predefinição. Desativá-lo deixa os passos copiados a apontar para o projeto de onde vieram.

<Aside>A cópia é executada em segundo plano. Uma caixa de diálogo de progresso mostra a cópia a avançar pelas suas fases; pode clicar em **Executar em segundo plano** para a dispensar e continuar a trabalhar — a lista de projetos é atualizada automaticamente e é notificado quando a cópia termina.</Aside>

## Ver o relatório do projeto

Quando um projeto ou fluxo de trabalho é dinâmico, manter documentação detalhada torna-se um desafio. Para ajudar a resolver este problema, o PlaidCloud permite gerar um relatório ao nível do projeto que fornece documentação detalhada dos fluxos de trabalho, dos passos de fluxo de trabalho, das transformações definidas pelo utilizador, das variáveis e das tabelas. Este relatório é gerado a pedido e reflete o estado atual do projeto.

Para transferir o relatório:

1. Abra o Analyze
2. Selecione “Projetos”
3. Clique no ícone do relatório
