## Pesquisar

Para pesquisar projetos, utilize a caixa de filtro no canto inferior esquerdo da hierarquia. O filtro de pesquisa procura correspondências nos nomes e nas etiquetas dos projetos e mostra os resultados na hierarquia acima.


## Criar novos projetos

Para criar um novo projeto:

1. Abra o Analyze
2. Selecione “Projetos” na barra de menus superior
3. Clique no botão “Novo projeto”
4. Preencha as informações do formulário, incluindo a secção “Access Control”
5. Clique em “Criar”

O projeto fica pronto para atualizar as permissões de acesso, adicionar proprietários e criar fluxos de trabalho.

<Aside>Por predefinição, o projeto fica acessível a todos os membros da área de trabalho atual</Aside>


## Definir uma conta de documentos predefinida

Na página inicial do projeto, junto a **Ambiente da ligação**, escolha uma **Conta de documentos predefinida** para o projeto — ou **Nenhum** para a limpar.

Dentro do projeto, todos os seletores de ficheiros apresentam primeiro **Predefinição do projeto**, que representa a conta que o projeto tiver definida nesse momento. Esta opção desaparece da lista quando sai do projeto, quando o projeto deixa de ter uma predefinição, quando essa conta é eliminada ou quando deixa de ter acesso a ela.

Um novo passo de ficheiro seleciona previamente Predefinição do projeto quando o projeto tem uma. Os passos existentes nunca são reescritos — cada um mantém a conta com que foi guardado até a alterar manualmente, pois a conta de documentos é uma escolha de cada passo, ao contrário do ambiente da ligação.

Um passo deixado em Predefinição do projeto utiliza a conta que for a predefinida do projeto no momento em que é executado, pelo que alterar a predefinição a meio de uma execução afeta apenas os nós que ainda não começaram — tal como acontece ao alterar o ambiente da ligação. Se um passo for executado em Predefinição do projeto e o projeto não tiver predefinição, a execução falha e indica o projeto, em vez de recorrer a outra conta.


## Histórico de versões

Todos os objetos de um projeto — um passo, uma UDF, um fluxo de trabalho, uma dimensão, um esquema guardado, um editor de documentos ou de dados e as próprias definições do projeto — estão abrangidos pelas cópias de segurança do histórico de versões. Não é feita uma cópia de segurança em cada gravação individual; em vez disso, quando um objeto passa 30 segundos sem nova gravação, é feita uma cópia de segurança do seu estado estabilizado. Uma série de edições — várias gravações em rápida sucessão — produz uma única versão com o resultado final, e não uma versão por gravação. A gravação nunca fica mais lenta à espera de uma cópia de segurança: a contagem decrescente e a própria cópia de segurança decorrem em segundo plano. Se precisar de uma versão de imediato, utilize **Back up now** para capturar o estado atual de imediato e aguardar que termine — disponível na interface, na API e como a ação `backup` das ferramentas MCP `*_versions`. O histórico de versões está disponível em todos os planos, incluindo o Free.

As versões anteriores permitem a recuperação para um ponto no tempo: restaurar um objeto para uma versão anterior. O restauro é recusado num projeto bloqueado, tal como qualquer outra alteração nesse projeto.

Uma versão é restaurada no próprio item. Restaurar uma versão de um projeto, dimensão, função definida pelo utilizador, passo, fluxo de trabalho ou editor de dados substitui esse mesmo item, e indicar outro item como destino é recusado — por exemplo, "Uma versão de projeto é restaurada no próprio projeto. Omita o destino ou defina-o como este projeto." Restaurar é uma alteração ao item, pelo que exige a mesma função que editá-lo; num projeto que [restringe linhas](/pt-pt/administration/access/managing-security-groups-and-assignments/#quem-pode-alterar-um-projeto-que-restringe-linhas), restaurar o projeto ou uma dimensão lida por uma coluna restrita exige um Arquiteto do projeto. Para recuperar dados antigos de uma tabela como uma tabela separada, restaure um [instantâneo de tabela](/pt-pt/guides/data/table-snapshots/) para uma nova tabela.

Além deste registo automático, os projetos e os respetivos elementos também permitem o controlo de versões. Não só é fácil criar uma versão, como também pode intercalar alterações de uma versão para outra. Esta é uma forma simples de manter instantâneos ou de criar uma versão para desenvolvimento e, depois, intercalar essas alterações na versão que não é de desenvolvimento quando quiser. Consulte [Colaborar: versões, comparação e partilha](/pt-pt/get-started/tutorials/collaborate-versions-and-sharing/) para ver o controlo de versões, a comparação e a intercalação na prática.

Os dados das tabelas têm o seu próprio histórico — instantâneos criados pelo Lakehouse em cada escrita — descrito em [Instantâneos de tabelas](/pt-pt/guides/data/table-snapshots/).

### Restaurar e reter através do assistente de IA ou do MCP

Através do assistente de IA ou do MCP, `dimension_versions` restaura, retém e liberta uma versão de dimensão pelo seu `version_id`, e `restore_project` reverte todas as dimensões do projeto para a última cópia de segurança; todas as listagens `*_versions` (passos, UDF, fluxos de trabalho, dimensões, projetos) mostram o `version_id` de cada versão e se está retida. Um `restore` através de qualquer ferramenta `*_versions`, ou da API REST, restaura o item no próprio item: omita o destino ou defina-o como o próprio item. `project_upsert` pode desbloquear um projeto bloqueado e respeita `if_match`, pelo que falha em vez de substituir uma alteração feita desde a última vez que leu o projeto.


## Gerir o acesso ao projeto

### Tipos de acesso

A segurança dos projetos foi simplificada em três tipos de acesso:

* Todos os membros da área de trabalho
* Apenas membros específicos
* Apenas grupos de segurança específicos

Definir a segurança do projeto é simples:

1. Abra o Analyze
2. Selecione “Projetos”
3. Clique no ícone de edição do projeto que pretende restringir
4. Escolha a restrição pretendida em “Access Control”
5. Clique em “Atualizar”

Apenas um Arquiteto do projeto ou um administrador do inquilino pode alterar quem tem acesso a um projeto — o tipo de acesso, os membros e grupos de segurança associados e as partilhas de dados. Os restantes utilizadores veem esses painéis só de leitura, com a nota “Apenas os Arquitetos do projeto podem alterar o acesso.”


## Todos os membros da área de trabalho

O acesso “Todos os membros da área de trabalho” é a opção mais simples, pois dá acesso a todos os membros da área de trabalho e não exige qualquer atribuição adicional de membros.


## Apenas membros específicos

A definição de acesso “Apenas membros específicos” exige a atribuição de cada membro ao projeto. Para atribuir membros a um projeto:

1. Abra o Analyze
2. Selecione “Projetos” na barra de menus superior
3. Clique no ícone de membros
4. Conceda acesso aos membros marcando a caixa de verificação junto ao respetivo nome na coluna “Access”
5. Clique em “Atualizar”

Em clouds com um grande número de membros, esta abordagem pode exigir mais esforço do que o desejável, e é aí que os grupos de segurança se tornam úteis.

<Aside>Para adicionar membros, tem de ser membro da área de trabalho.</Aside>


## Apenas grupos de segurança específicos

A opção “Apenas grupos de segurança específicos” permite conceder a grupos de segurança específicos permissão de acesso à conta. Como as restrições de acesso dependem da associação a um ou mais grupos de segurança, a administração do acesso à conta para grupos maiores é muito mais simples. Isto é particularmente útil em conjunto com a associação automática a grupos através de início de sessão único. Ao utilizar o início de sessão único para definir as atribuições de grupos dos membros, estes grupos também podem ativar e desativar implicitamente o acesso aos projetos.

Para editar os grupos atribuídos:

1. Abra o Analyze
2. Selecione “Projetos” na barra de menus superior
3. Clique no ícone de grupos de segurança
4. Conceda acesso aos grupos de segurança marcando a caixa de verificação junto ao respetivo nome na coluna “Access”
5. Clique em “Atualizar”


## Partilhar dados entre projetos

Uma partilha de dados permite que um projeto aceda às tabelas de outro projeto — por exemplo, para que os passos [Import Project Table](/pt-pt/reference/workflow-steps/import/import-project-table/) e [Export Project Table](/pt-pt/reference/workflow-steps/export/export-project-table/) possam mover dados entre eles. Uma partilha é concedida pelo projeto cujos dados são partilhados a um outro projeto:

1. Abra o projeto cujos dados pretende partilhar e aceda ao separador **Início**.
2. Em **Gestão de partilha de dados**, clique em **Nova partilha de dados**.
3. Em **Selecionar projeto**, escolha o projeto que pode utilizar os dados deste projeto.
4. Em **Operações permitidas**, marque **Leitura**, **Escrita** ou ambas e clique em **Adicionar partilha de dados**.

**Eliminar partilha de dados** remove uma partilha. Apenas um Arquiteto do projeto ou um administrador do inquilino pode adicionar ou eliminar as partilhas de dados de um projeto.

Uma partilha é concedida a um projeto, pelo que só se aplica aos membros e aos fluxos de trabalho desse projeto:

- **Ler** através de uma partilha exige uma função no projeto a que foi concedida. Quem não tiver função nesse projeto não obtém nada da partilha.
- **Escrever** através de uma partilha — criar uma tabela, uma pasta ou uma dimensão no projeto que partilha — exige uma partilha de **Escrita** e a função de Gestor ou Arquiteto no seu próprio projeto, a função que permitiria fazer a mesma alteração aí. Os restantes utilizadores recebem a mensagem "Escrever neste projeto através de uma partilha de dados exige uma partilha de escrita deste projeto para o seu projeto e a função de Gestor ou Arquiteto no seu projeto."

Os fluxos de trabalho são executados com a identidade do próprio projeto, pelo que os passos Import Project Table e Export Project Table funcionam através de uma partilha independentemente de quem inicia a execução.


## Definir diferentes funções de visualização

Muitas vezes, um projeto pode exigir várias transformações e tabelas para concluir passos intermédios, enquanto o resultado final pode consistir apenas em algumas tabelas. Os membros nem sempre precisam de ver todos os elementos do projeto, por vezes apenas o produto final. O PlaidCloud permite definir diferentes funções de visualização para simplificar e controlar facilmente a visibilidade de cada membro.

Existem três funções de visualização incorporadas: **Arquiteto, Gestor,** e **Explorador**

A função **Arquiteto** é a mais simples, pois permite visibilidade e controlo totais de projetos, fluxos de trabalho, tabelas, variáveis, editores de dados, hierarquias e funções definidas pelo utilizador.

As funções **Gestor** e **Explorador** não têm privilégios de acesso específicos, mas podem ser personalizadas. Por outras palavras, pode escolher que itens são visíveis para cada grupo.

<Aside>**Gestor*** *e **Explorador** não são grupos de segurança; apenas oferecem uma forma prática de separar funções e a visibilidade da informação.</Aside>

Pode tornar todos **Arquiteto** se considerar necessária a visibilidade de tudo no projeto; caso contrário, pode designar membros como membros do projeto **Gestor** e/ou **Explorador** e controlar a visibilidade dessa forma.

Para definir a função:

1. Abra o Analyze
2. Selecione “Projetos”
3. Clique no ícone de membros
4. Selecione o membro cuja função pretende alterar
5. Faça duplo clique na função atual na coluna “Role”
6. Selecione a função pretendida
7. Clique em “Atualizar”


## Gerir variáveis do projeto

Ao executar um projeto ou fluxo de trabalho, pode ser útil definir variáveis para tarefas recorrentes, de modo a reduzir a confusão e poupar tempo. Estas variáveis funcionam como uma variável algébrica normal, permitindo definir o que a variável representa e que operação se lhe segue. O PlaidCloud permite definir estas variáveis ao nível do projeto, o que afeta todos os fluxos de trabalho desse projeto, ou ao nível do fluxo de trabalho, o que afeta apenas esse fluxo de trabalho específico.

Para definir uma variável ao nível do projeto:

1. Abra o Analyze
2. Selecione “Projetos”
3. Clique no ícone Manage Project Variables

Na tabela de variáveis, pode ver as variáveis e ver/editar os valores atuais. Também pode adicionar novas variáveis ou eliminar variáveis existentes clicando no botão “New Project Variable”.


## Copiar um projeto

**Copiar projeto** copia um projeto — na totalidade ou apenas as partes que escolher — para um projeto totalmente novo ou para um projeto que já existe.

Para copiar um projeto:

1. Abra o Analyze
2. Selecione "Projetos"
3. Selecione o projeto que pretende copiar
4. Clique no botão **Ações** e escolha **Copiar projeto**
5. Escolha o destino, selecione o que pretende trazer e que dados copiar e clique em **Copiar projeto**
6. Verifique o resumo **Rever antes de copiar** e clique em **Iniciar cópia**

### Escolher o que copiar

A árvore de seleção lista o conteúdo do projeto, por tipo — fluxos de trabalho, passos, tabelas, dimensões, editores de dados, funções definidas pelo utilizador. Deixe tudo marcado para copiar o projeto inteiro ou marque apenas as partes que pretende.

Não precisa de determinar de que dependem essas partes. Tudo o que marcar traz consigo as respetivas dependências: as tabelas que um passo lê e escreve, as dimensões que carrega ou contra as quais faz alocações, as funções definidas pelo utilizador que chama e qualquer subfluxo de trabalho ou macro que invoca. Os sensores de um fluxo de trabalho acompanham o fluxo de trabalho.

**Os sensores copiados chegam desativados.** Nada é acionado na cópia até ativar cada sensor no projeto de destino. Uma importação que substitui itens duplicados não acrescenta um segundo sensor quando o fluxo de trabalho de destino já o tem.

### Copiar para um novo projeto

Atribua um nome e um ID ao novo projeto. O ID passa a ser o nome do esquema e não pode ser alterado mais tarde.

**Os agendamentos chegam em pausa.** Quando copia um projeto inteiro para um novo, os eventos agendados de cada fluxo de trabalho chegam em pausa, para que a cópia não comece a executá-los por si só. Quando a cópia termina, uma mensagem lista os eventos que estavam ativos no original. Para executar um deles na cópia, selecione-o em **Ferramentas** > **Agendador de eventos** e clique em **Ativar selecionados** — consulte [Pausar um evento](/pt-pt/administration/scheduled-events/event-scheduler/#pausar-um-evento).

### Copiar para um projeto existente

Escolha o destino na lista de projetos. A cópia acrescenta conteúdo a esse projeto em vez de o substituir.

**Tem de poder alterar o destino.** Uma cópia para um projeto no qual não tem nenhuma função é recusada, tal como uma cópia para um projeto que foi bloqueado para impedir alterações — isto é verificado antes de qualquer leitura ou escrita, pelo que uma cópia recusada deixa o destino intacto. Também não é possível copiar um projeto para si próprio.

**Copiar um projeto que restringe linhas exige um Arquiteto do projeto.** A cópia é um novo projeto sem restrição de [acesso a linhas](/pt-pt/administration/access/managing-security-groups-and-assignments/#gerir-o-acesso-a-linhas), e a cópia informa disso: “Esta cópia não tem restrição de linhas.” Configure o Acesso a linhas na cópia antes de a partilhar. Copiar para um projeto existente que restringe linhas também exige um dos seus Arquitetos ou um administrador do inquilino.

**O destino mantém as suas próprias definições.** O nome, o ID, o ambiente da ligação de dados, as predefinições de armazenamento, a conta de documentos, o tipo de acesso, as listas de acesso e as concessões de acesso a linhas ficam todos como estão. Apenas o conteúdo selecionado é trazido.

Um passo definido como **Predefinição do projeto** transporta essa definição, não uma conta — depois de copiado, utiliza a predefinição que o projeto de destino tiver, e não a que tinha no projeto de origem.

Quando um item recebido é o mesmo item que um já existente no destino, pode escolher o que acontece:

- **Substituir itens duplicados pelos dados recebidos** — a versão recebida substitui a que existe no destino.
- **Criar nova cópia dos itens duplicados** — o destino mantém o que tem, e o item recebido é acrescentado ao lado com ` copy` anexado ao nome, e um contador se esse nome também já existir.

As variáveis de projeto e de fluxo de trabalho são a exceção a *Criar nova cópia*: uma variável é identificada pelo nome, pelo que não é possível acrescentar uma segunda cópia sem lhe mudar o nome para algo a que nada faz referência. Quando o destino já define uma variável que a cópia também traz, o valor do próprio destino é mantido e a cópia indica as variáveis que deixou inalteradas. *Substituir* trata as variáveis como tudo o resto e substitui-as.

Esta correspondência é feita pela identidade e não pelo nome — um item que veio originalmente do mesmo projeto é reconhecido como o mesmo item, enquanto dois itens que apenas partilham o mesmo nome são tratados como itens diferentes e ambos estarão presentes no final.

### Escolher quantos dados copiar

Em **Data to copy**, duas definições determinam que dados acompanham a seleção.

**Dados da tabela** define quantas linhas de cada tabela são copiadas:

| Opção | O que é copiado |
| --- | --- |
| **Sem dados da tabela** | As tabelas, os passos e o resto da seleção, sem linhas. É a predefinição. |
| **Completo** | Todas as linhas de cada tabela, no mesmo lakehouse e entre lakehouses. |
| **Amostra** | Até ao número de **linhas por tabela** que introduzir, apenas para um novo projeto. O número pode ser de 1 a 1 000 000. |

Uma tabela amostrada contém até esse número de linhas, ou todas as suas linhas quando tem menos. Uma cópia **Completo** ou **Amostra** copia várias tabelas em simultâneo, pelo que um projeto com muitas tabelas termina mais depressa.

**Copy dimension members** copia os membros de todas as dimensões da seleção, independentemente da opção de **Dados da tabela** escolhida. Está ativada por predefinição, pelo que uma cópia sem dados de tabelas chega mesmo assim com dimensões preenchidas e é rápida de fazer. Desmarque-a para copiar as dimensões sem os respetivos membros.

Através da API REST (`POST /rest/v1/analyze/project/copy`) ou da ferramenta MCP `project_copy`, defina `data_mode` como `structure`, `full` ou `sample` e `dimension_members` como `true` ou `false`. Quando omite `dimension_members`, os membros só são copiados quando as linhas das tabelas o são. `project_copy` também devolve os avisos da cópia, como as autorizações de escrita no ERP que não foram copiadas.

### Rever a cópia

Antes de qualquer cópia, **Rever antes de copiar** resume a operação: o projeto de origem, o destino, a opção de **Dados da tabela**, se os **Membros da dimensão** são incluídos, o número de tabelas e vistas, o tamanho, um tempo estimado, o lakehouse de origem e de destino e quaisquer avisos em **Tenha em atenção**. Clique em **Iniciar cópia** para começar ou em **Cancelar** para voltar atrás e alterar a seleção.

### Quem pode ver a cópia

Uma cópia feita com dados — linhas de tabelas, membros de dimensões ou ambos — é privada para a pessoa que a fez. Partilhe-a a partir do novo projeto quando estiver pronto. Uma cópia de um projeto com segurança ao nível da linha mantém-se privada pelo mesmo motivo.

Copiar dados para um projeto existente exige acesso de escrita a esse projeto.

### Autorizações de escrita no ERP na cópia

Uma nova cópia privada mantém as [autorizações de escrita no ERP](/pt-pt/guides/workflows/run-a-workflow/#autorizar-o-projeto-a-lançar) do projeto de origem, para que possa testar os respetivos fluxos de trabalho de lançamento sem voltar a autorizar a cópia. Isto aplica-se a qualquer cópia para um novo projeto feita com dados de tabelas (**Completo** ou **Amostra**), membros de dimensões ou ambos. As autorizações são copiadas quando:

- É Arquiteto do projeto de origem ou administrador da área de trabalho.
- Faz a cópia pessoalmente, e não através de um agente ou de uma conta de serviço.

Cada autorização só é copiada se a pudesse conceder hoje: a respetiva ligação e ambiente ainda existem e tem acesso de escrita à ligação. As autorizações copiadas ficam registadas em seu nome.

**A cópia chega em Simulate.** Se o **Modo de lançamento ERP** do projeto de origem for Live, o da cópia é definido como Simulate, para que os respetivos fluxos de trabalho preparem e verifiquem o que lançariam sem contactar o ERP. Uma origem definida como Simulate ou Off mantém essa definição. Quando estiver pronto para efetuar lançamentos reais a partir da cópia, defina o **Modo de lançamento ERP** em **Lançamento ERP** na página inicial da cópia como Live — consulte [Escolher um modo de lançamento](/pt-pt/guides/workflows/run-a-workflow/#escolher-um-modo-de-lançamento). Os agendamentos e sensores continuam a chegar em pausa e desativados, como descrito acima, pelo que nada é executado na cópia até os ativar.

Uma cópia para um projeto existente, ou uma sem dados de tabelas e sem membros de dimensões, começa sem as autorizações da origem. Autorize-a em **Lançamento ERP** > **Autorizações de escrita no ERP** na respetiva página inicial antes de efetuar lançamentos.

**Resultados da cópia** indica o que aconteceu, por exemplo "2 autorizações de escrita no ERP copiadas; o lançamento ERP está em Simulate", juntamente com o número de autorizações não copiadas.

### Resultados da cópia

Quando a cópia termina, uma janela **Resultados da cópia** resume as tabelas e os membros de dimensões copiados e lista cada tabela e dimensão pelo nome com o respetivo resultado — **Copiado**, **Copiado com alterações**, **Amostrado**, **Ignorado** ou **Falhou** — e o motivo de qualquer item ignorado ou com falha. Clique em **Retry failed items** para voltar a copiar as tabelas e dimensões com falha; o conteúdo atual na cópia é substituído. É notificado, por mensagem e por e-mail, quando uma cópia termina ou falha, e pode reabrir os resultados a partir da mensagem ou, mais tarde, selecionando a cópia no separador **Projetos** e escolhendo **Ver resultado da importação ou cópia** no menu **Ações**.

Os resultados permanecem na cópia até alguém os dispensar. Quando a cópia terminar, clique em **Dispensar resultado** para os remover para todos os que podem abrir o projeto. Nada no projeto é alterado, mas os itens com falha deixam de poder ser repetidos a partir da janela. Dispensar exige acesso de edição ao projeto, e o projeto não pode estar bloqueado.

### Atualizar referências

Os passos dos fluxos de trabalho de um projeto referem-se a tabelas e a outros objetos desse projeto. **Atualizar referências** reescreve essas referências para que apontem para a cópia em vez do original — o que é quase sempre o pretendido, e é por isso que está ativado por predefinição. Desativá-lo deixa os passos copiados a apontar para o projeto de onde vieram.

<Aside>A cópia é executada em segundo plano. Uma caixa de diálogo de progresso mostra o avanço da cópia pelas suas fases; pode clicar em **Executar em segundo plano** para a fechar e continuar a trabalhar — a lista de projetos é atualizada automaticamente e é notificado quando a cópia termina.</Aside>

## Ver o relatório do projeto

Quando um projeto ou fluxo de trabalho é dinâmico, manter documentação detalhada torna-se um desafio. Para ajudar a resolver este problema, o PlaidCloud permite gerar um relatório ao nível do projeto com documentação detalhada de fluxos de trabalho, passos de fluxos de trabalho, transformações definidas pelo utilizador, variáveis e tabelas. Este relatório é gerado a pedido e reflete o estado atual do projeto.

Para transferir o relatório:

1. Abra o Analyze
2. Selecione “Projetos”
3. Clique no ícone de relatório
