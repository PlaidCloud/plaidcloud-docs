Ein Tag markiert einen Commit als bedeutsam – in der Regel eine Version wie `v1.2.0`. Ein Release baut auf einem Tag auf und ergänzt lesbare Hinweise und optionale Dateianhänge, damit Benutzer bestimmte Versionen in der Weboberfläche durchsuchen und herunterladen können.

## Tag erstellen

Sie können einen Tag über die Benutzeroberfläche oder aus Ihrem lokalen Klon erstellen.

**In der Benutzeroberfläche:**

1. Öffnen Sie Ihr Repository und wählen Sie **Releases** und dann **Tags**.
2. Wählen Sie **Create Tag**.
3. Geben Sie einen Tag-Namen ein (zum Beispiel `v1.2.0`), wählen Sie den Ziel-Branch oder Commit und wählen Sie **Create Tag**.

**Über die Befehlszeile:**

```bash
git tag v1.2.0
git push origin v1.2.0
```

Um einen bestimmten früheren Commit zu taggen, übergeben Sie dessen Commit-ID, statt sich auf `HEAD` zu verlassen:

```bash
git tag v1.2.0 abc1234
git push origin v1.2.0
```

## Release veröffentlichen

1. Öffnen Sie Ihr Repository und wählen Sie **Releases**.
2. Wählen Sie **New Release**.
3. Wählen Sie im Feld **Tag Name** einen vorhandenen Tag oder geben Sie einen neuen Namen ein, um einen Tag an der Spitze des aktuellen Standard-Branches zu erstellen.
4. Geben Sie einen **Release Title** ein und schreiben Sie Release-Hinweise im Markdown-Text – Changelogs, Upgrade-Anweisungen und bekannte Probleme gehören hierher.
5. Wählen Sie **This is a pre-release**, wenn die Version noch nicht für den allgemeinen Gebrauch bereit ist, oder **Entwurf speichern**, um später fortzufahren, ohne zu veröffentlichen.
6. Wählen Sie **Publish Release**, wenn es so weit ist.

<Aside>Release-Entwürfe sind nur für Repository-Mitglieder mit Schreibzugriff sichtbar. Ein Pre-Release ist für alle mit Zugriff sichtbar, wird aber von der Kennzeichnung „Latest“ in der Repository-Übersicht ausgenommen.</Aside>

## Dateien anhängen

Hochgeladene Dateien erscheinen auf der Release-Seite als benannte Download-Links neben dem automatisch generierten Quellarchiv.

1. Gehen Sie im Formular zum Erstellen oder Bearbeiten des Releases zum Abschnitt **Attach Files**.
2. Ziehen Sie Dateien in den Upload-Bereich oder wählen Sie ihn zum Durchsuchen aus – gängig sind erstellte Binärdateien, komprimierte Archive, Prüfsummen und Signaturen.
3. Wiederholen Sie dies für jede Datei und veröffentlichen oder aktualisieren Sie dann das Release.

Halten Sie einzelne Dateien in einer vernünftigen Größe, damit Downloads für Ihr Team schnell bleiben.

<Aside type="tip">Für installierbare Pakete – npm-Module, Container-Images, PyPI-Wheels und Ähnliches – ist die [Paket-Registry](/de/guides/git/packages/) besser geeignet als Release-Anhänge. Sie versteht Versionsauflösung, Abhängigkeitsmetadaten und Client-Werkzeuge (`npm`, `pip`, `docker pull`) auf eine Weise, die ein einfacher Dateidownload nicht bietet.</Aside>

## Releases anzeigen und herunterladen

1. Wählen Sie **Releases**, um die vollständige Liste zu sehen, die neuesten zuerst.
2. Das neueste Release, das kein Pre-Release ist, ist mit einem Badge **Latest** hervorgehoben.
3. Jeder Eintrag zeigt Tag-Namen, Release-Titel, Hinweise und Links zu:
   - **Source code** – automatisch generierte `zip`- und `tar.gz`-Archive des getaggten Commits.
   - **Assets** – alle Dateien, die Sie beim Veröffentlichen des Releases angehängt haben.
4. Wählen Sie einen Dateilink, um die Datei direkt herunterzuladen, oder kopieren Sie die URL, um sie weiterzugeben.

Um zwei Releases zu vergleichen, öffnen Sie ihre Tag-Namen als Vergleichs-URL:

```bash
https://git.example.plaidcloud.com/you/my-repo/compare/v1.1.0...v1.2.0
```
