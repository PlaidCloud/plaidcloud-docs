## Beschreibung

Der Schritt **REST-Anfrage** ruft eine REST-API als einen Schritt in einem Workflow auf. Er ist ein einzelner Schritt im Postman-Stil für den gesamten Ablauf „erstellen → senden → prüfen“: Wählen Sie einen Endpunkt (von Hand eingegeben oder aus einer Postman-Collection, einer OpenAPI-/Swagger-Spezifikation oder einer HAR-Aufzeichnung importiert), legen Sie Header, Abfrageparameter und einen Body fest, senden Sie eine **Testanfrage**, um die aktuelle Antwort zu sehen, und speichern Sie dann den Schritt.

Sie bestimmen, wohin die Antwort geht. Standardmäßig wird sie in eine **Tabelle** geparst. Alternativ kann der Schritt die Antwort in **Workflow-Variablen** erfassen, sodass ein späterer Schritt anhand des Statuscodes verzweigen oder einen Wert aus dem Body lesen kann.

Wenn Sie den Browser schließen oder neu laden, bevor Sie speichern, behält der Editor in diesem Browser einen lokalen Entwurf. Öffnen Sie denselben Schritt erneut und wählen Sie auf Nachfrage **Wiederherstellen**, um die nicht gespeicherten Anfrageeinstellungen zurückzuholen.

<Aside type="note">Der REST-Anfrage-Schritt ersetzt die älteren REST-Schritte durch einen einheitlichen Schritt. Verwenden Sie ihn für neue Arbeiten. Vorhandene Schritte vom Typ REST, REST importieren und Postman importieren werden bei der Aktualisierung Ihres Workspace in REST-Anfrage umgewandelt, wobei ein Timeout von 300 Sekunden und das gleiche Wiederholungsverhalten beibehalten werden. Ein Schritt, der sich nicht sauber umwandeln lässt, bleibt unverändert, und Ihr Administrator sieht in einem Bericht, welche das sind.</Aside>

## Bevor Sie beginnen

In der Regel benötigen Sie eine **Verbindung** vom Typ REST, die die Basis-URL und die Authentifizierung für den Dienst enthält. Der Schritt kann auch eine vollständig qualifizierte URL direkt ohne Verbindung aufrufen. Siehe [REST-Verbindungen](/de/reference/connectors/rest/).

## Einen REST-Anfrage-Schritt hinzufügen

1. Öffnen Sie den Workflow und fügen Sie an der gewünschten Stelle einen Schritt hinzu.
2. Wählen Sie **REST Request (unified)** als Schritttyp (unter den REST-Schritten). Der Editor öffnet sich mit einer Registerkarte **Anfrage**, einer Registerkarte **Antwort** und einer Registerkarte **Tabellendatenauswahl**.

## Die Anfrage aufbauen

Auf der Registerkarte **Anfrage**:

### Endpunktquelle

Wählen Sie, wie Sie den Endpunkt angeben, dann füllt PlaidCloud die Anfrage für Sie aus:

- **Manuell** — geben Sie Methode und URL selbst ein.
- **Aus der API-Definition der Verbindung** — verwenden Sie die OpenAPI-/Swagger-Definition, die in der gewählten Verbindung gespeichert ist, damit Sie sie nicht in jedem Schritt erneut angeben müssen. Siehe [Die API-Definition einer Verbindung wiederverwenden](#die-api-definition-einer-verbindung-wiederverwenden) weiter unten.
- **Postman-Collection (Datei)** / **Postman-Collection (URL)** — Import aus einer Postman-Collection.
- **OpenAPI / Swagger (URL)** / **OpenAPI / Swagger (Datei)** — Import aus einer API-Spezifikation.
- **HAR-Archiv (Datei)** — importieren Sie eine Anfrage, die aus dem Netzwerkprotokoll Ihres Browsers aufgezeichnet wurde.

Wählen Sie bei einer importierten Quelle **Katalog laden**, um die verfügbaren Endpunkte aufzulisten, und wählen Sie dann unter **Endpunkt** einen aus. Der Schritt füllt Methode, URL, Header, Abfrageparameter und Body aus, wobei er das Beispiel oder den Standardwert jedes Parameters verwendet; ein optionaler Parameter, der keines von beiden hat, beginnt ausgeschaltet. Wenn die Anfrage bereits etwas enthält, das Sie eingegeben haben, fragt der Schritt nach, bevor er es ersetzt. Drücken Sie **Ctrl+Z** (**Cmd+Z** auf einem Mac), wenn Sie nicht in ein Feld tippen, oder wählen Sie **Ersetzen rückgängig machen**, um die vorherige Anfrage zurückzuholen.

Ein großer Katalog lässt sich leicht eingrenzen: Geben Sie in **Nach Methode, Pfad oder Name filtern…** etwas ein, um nur die passenden Endpunkte aufzulisten. Der Katalog zeigt an, wie viele Endpunkte er enthält (**12 von 340** bei aktivem Filter) und wann er geladen wurde, und der Schritt weist darauf hin, wenn eine sehr große Definition an ihrer Vorschaugrenze abgeschnitten wurde.

### Eine Collection oder Spezifikation einfügen, statt eine Datei zu wählen

Die drei dateibasierten Quellen — Postman-Collection, OpenAPI/Swagger und HAR-Archiv — bieten jeweils neben der Dateiauswahl eine Schaltfläche **Einfügen…**. Verwenden Sie sie, wenn Sie den Inhalt zur Hand haben, ihn aber nicht in Document gespeichert haben: Fügen Sie das JSON ein und wählen Sie **Dies verwenden**. Der Katalog wird sofort geladen, sodass Sie anschließend nicht auf **Katalog laden** klicken müssen.

Der eingefügte Inhalt wird anstelle der Dateiauswahl verwendet und bleibt so lange erhalten, wie der Schritt geöffnet bleibt — er wird nicht mit dem Schritt gespeichert. Fügen Sie ihn daher erneut ein, wenn Sie den Schritt erneut öffnen und den Katalog daraus neu laden möchten. Wenn Sie für dieselbe Quelle eine Datei wählen, hat die Datei Vorrang und der eingefügte Inhalt wird verworfen — der Schritt teilt Ihnen mit, wenn das geschieht.

Sie können auch eine `.json`-Datei auf die Quellenauswahl ziehen. Der Schritt prüft den Inhalt anhand der gewählten Quelle und sagt Ihnen, was nicht stimmt, etwa wenn eine Postman-Collection eingefügt wurde, wo eine OpenAPI-Spezifikation erwartet wird, oder wenn eine Datei kein JSON ist. Außerdem hat jede Quelle einen Link **How do I get a …?**, der erklärt, wie Sie eine Postman-Collection, eine OpenAPI-Spezifikation oder eine HAR-Datei exportieren.

<Aside type="note">Einfügen und Ablegen akzeptieren JSON. Speichern Sie bei einer YAML-Spezifikation die Datei in Document und wählen Sie sie stattdessen aus.</Aside>

### Die API-Definition einer Verbindung wiederverwenden

Konnektoren, die für einen bestimmten Dienst entwickelt wurden, kennen ihre Endpunkte bereits. Generische REST- und MuleSoft-Verbindungen nicht — sie können auf jede beliebige API zeigen —, daher können Sie die Definition der API an die Verbindung selbst anhängen.

Legen Sie sie einmalig an der Verbindung fest (siehe [Generische REST-Verbindung](/de/reference/connectors/rest/generic-rest/#api-definition)) und gehen Sie dann in jedem Schritt, der diese Verbindung verwendet, so vor:

1. Wählen Sie unter **Verbindung** die Verbindung.
2. Setzen Sie **Endpunktquelle** auf **Aus der API-Definition der Verbindung**.
3. Wählen Sie **Katalog laden** und wählen Sie Ihren Endpunkt.

Jeder Schritt, der diese Verbindung gemeinsam nutzt, bietet dieselbe Endpunktliste an, und wenn Sie die Definition an der Verbindung aktualisieren, werden alle aktualisiert.

### Verbindungsübersicht und Umgebung

Unter der Auswahl **Verbindung** zeigt eine Übersichtszeile, was der Schritt verwenden wird: den Authentifizierungstyp, den Host und wie viele Standard-Header die Verbindung mit jeder Anfrage sendet. Wählen Sie die Aktualisierungsschaltfläche neben der Auswahl, nachdem Sie die Verbindung geändert haben, um Authentifizierung, Host und Standard-Header neu zu laden, ohne den Schritt erneut zu öffnen. Wenn die Verbindung Umgebungen definiert, legt die Auswahl **Umgebung** fest, gegen welche der Schritt ausgeführt wird.

<Aside type="note">
Die **URL** einer Definition muss aus dem Internet erreichbar sein. Wenn die Spezifikation Ihrer API nur in Ihrem eigenen Netzwerk veröffentlicht ist, laden Sie die Datei stattdessen in Document hoch und wählen Sie sie an der Verbindung als Datei aus.
</Aside>

### Verbindung, Methode und Endpunkt

- **Verbindung** — die REST-Verbindung, mit der authentifiziert wird. Lassen Sie sie leer, um eine vollständig qualifizierte URL direkt aufzurufen. Mit der Bearbeitungsverknüpfung neben der Auswahl können Sie die gewählte Verbindung anzeigen oder bearbeiten, ohne den Anfrage-Editor zu verlassen.
- **Methode** — `GET`, `POST`, `PUT`, `PATCH`, `DELETE`, `HEAD` oder `OPTIONS`.
- **Endpunkt** — der Pfad (wenn eine Verbindung festgelegt ist) oder eine vollständige URL.

### Header, Abfrageparameter und Body

- **Header** und **Abfrageparameter** sind bearbeitbare Tabellen mit Name-/Wert-Zeilen, jeweils mit einem Schalter **Bei** und einer Beschreibung. Fügen Sie Zeilen mit **Hinzufügen** hinzu und entfernen Sie sie mit **Entfernen**.
- **Body** enthält die Nutzdaten der Anfrage (JSON, Formular oder Rohdaten) in einem Code-Editor.

**JSON formatieren** rückt den Body ein, und **JSON validieren** prüft ihn und meldet Zeile und Spalte jedes Fehlers. Beide lesen jede Variable `{{…}}` als Wert, sodass Ihre Variablen genau so bleiben, wie sie geschrieben sind. **Variablenreferenz…** listet jede Variable auf, die Sie in der Anfrage verwenden können, und **Einfügen `{{…}}`** setzt eine Variable an die Cursorposition.

Während Sie bearbeiten, markiert der Schritt Probleme unter der Anfrage:

- Ein Header- oder Abfrageparametername, der zweimal vorkommt, wobei ein Wert verloren ginge.
- Ein Headername, der wie ein Tippfehler aussieht, mit einem Vorschlag **Did you mean…**, etwa `Authorisation` für `Authorization`.
- Ein Geheimnis, etwa ein Wert für `Authorization` oder `X-API-Key`, im Klartext eingegeben. Bewahren Sie es in einer Projektvariablen auf und schreiben Sie `{{project_var.NAME}}`, damit das Geheimnis nicht im Schritt gespeichert wird.
- Ein JSON-Body ohne Header `Content-Type: application/json`, was einige Server mit HTTP 415 ablehnen.
- Eine URL mit falsch geschriebenem Schema, einem doppelten Schrägstrich im Pfad, einem abschließenden Schrägstrich oder überzähligen Leerzeichen.

### Variablenersetzung

An jeder Stelle im Endpunkt, in den Headern, Abfragewerten oder im Body können Sie zur Laufzeit eine Variable einfügen, indem Sie ihren Namen in doppelte geschweifte Klammern setzen: `{{name}}`. Sie können auch `{{var.name}}` für eine Variable der Workflow-Ausführung oder `{{project_var.name}}` für eine Projektvariable schreiben — das Präfix ist optional, und beide lösen denselben Namen auf.

Der Editor hebt erkannte `{{...}}`-Token im Endpunkt, in den Tabellen für Header und Abfragen und im Body-Editor hervor, sodass Ersetzungen vor dem Testen oder Speichern leicht zu erkennen sind.

Nur doppelte geschweifte Klammern werden ersetzt, daher bleibt ein einzelnes `{` oder `}` in einem JSON-Body genau so, wie es geschrieben ist — Sie können Variablen also frei in JSON mischen, zum Beispiel `{"id": "{{var.order_id}}", "qty": 1}`. Ein unbekannter Variablenname lässt den Schritt fehlschlagen, sodass ein Tippfehler sofort auffällt.

Wenn der Workflow durch einen Sensor oder Webhook gestartet wird, stehen außerdem vier Trigger-Variablen zur Verfügung: `{{trigger_sensor_id}}`, `{{trigger_sensor_type}}`, `{{trigger_fired_at}}` und `{{trigger_payload_json}}` (die eingehenden Nutzdaten als JSON-Zeichenfolge — parsen Sie sie in einem späteren Schritt, um verschachtelte Felder zu erreichen). Bei einer manuellen oder geplanten Ausführung werden diese zu einer leeren Zeichenfolge aufgelöst.

### Die Anfrage testen

- **Testanfrage senden** sendet die Anfrage mit Ihren aktuellen Einstellungen und zeigt die aktuelle Antwort direkt an, sodass Sie vor dem Speichern bestätigen können, dass der Aufruf funktioniert. Drücken Sie **Ctrl+Enter** (**Cmd+Enter** auf einem Mac), um von überall im Formular zu senden. Eine Statuszeile zeigt den HTTP-Status und die Antwortzeit an, und ein Timer zählt hoch, solange die Anfrage unterwegs ist. (Dabei wird eine einzelne Anfrage gesendet; die Paginierung läuft nur, wenn der Schritt ausgeführt wird.)
- **Paginierung testen** folgt der konfigurierten Paginierung und meldet, wie viele Datensätze über die Seiten hinweg zurückkommen (bis zu einer Vorschaugrenze), sodass Sie vor einer vollständigen Ausführung bestätigen können, dass der Paginierungsmodus und seine Parameter/Pfade korrekt verkettet sind. Es werden nur so viele Seiten abgerufen, wie nötig sind, um die Grenze zu erreichen.
- **Als curl kopieren** kopiert einen äquivalenten curl-Befehl in die Zwischenablage, zum Teilen oder zur Fehlersuche (mit maskierten Geheimnissen).
- **Aus curl importieren** macht das Gegenteil: Fügen Sie einen curl-Befehl ein — zum Beispiel „Als cURL kopieren“ aus einem Browser —, und seine Methode, URL, Header und sein Body ersetzen die aktuelle Anfrage. Basic-Auth (`-u`) wird zu einem Authorization-Header; nicht unterstützte Optionen werden gemeldet, statt stillschweigend verworfen zu werden. Mit **Ersetzen rückgängig machen** stellen Sie die vorherigen Werte wieder her.

Die Antwort öffnet sich in einem Viewer mit den Ansichten **Formatiert** und **Kompakt**. Die letzten fünf Testergebnisse bleiben erhalten, solange der Schritt geöffnet ist, und Sie können eines auswählen, um es erneut anzusehen oder erneut auszuführen. Wenn die Antwort eine Liste von Datensätzen enthält, setzt **Vorschlagen** den **Elementpfad** auf die erste Liste, die es findet.

Die Gruppe **Anfragevorschau** zeigt die Anfrage genau so, wie eine Ausführung sie senden würde, mit aufgelösten Variablen und maskierten Geheimnissen, ohne etwas zu senden. Wählen Sie **Vorschau aktualisieren**, nachdem Sie bearbeitet haben.

Wenn Sie die ausgehenden Anfragefelder ändern und speichern, bevor eine **Testanfrage senden** erfolgreich war, fragt PlaidCloud **Ohne erfolgreichen Test speichern?**, und Sie wählen **Trotzdem speichern** oder gehen zurück. Verwenden Sie im Fan-out-Modus **Zeile 1 testen**, um die erste Treiberzeile vor dem Speichern zu testen.

## Die Antwort weiterleiten

Legen Sie auf der Registerkarte **Antwort** das **Antwortziel** fest:

### Tabelle (Standard)

Die Antwort wird in die **Zieltabelle** geparst, die in diesem Modus erforderlich ist. Wählen Sie eine vorhandene Tabelle oder erstellen Sie über die Auswahl eine neue; Ansichten werden nicht angeboten. Die Gruppe **Paginierung und Analyse** steuert, wie:

- **Zeilenformat** — **Objekt** (Standard), wenn jeder Datensatz ein JSON-Objekt ist, oder **Array**, wenn jeder Datensatz eine Liste von Werten ist. Array ist bei **Eine Anfrage pro Tabellenzeile** nicht verfügbar. Der **Elementpfad** gibt an, wo die Datensätze in der Antwort liegen.
- **Paginierungsmodus** — **Keine Seitenumbrechung** (Standard), **Offset-Paginierung**, **Paginierung nach Seitennummer**, **Paginierung über nächste Seiten-URL**, **Cursor-Paginierung** oder **Paginierung über Link-Header (RFC 5988)**. **Modusparameter** und **Modus-Pfade** geben an, welche Parameter und Antwortfelder die Paginierung steuern, und sie sind nur verfügbar, wenn ein Paginierungsmodus gewählt ist. Die Wahl eines Modus füllt beide mit seinen Standardwerten, die Sie bearbeiten können.

  | Modus | Standard der Modusparameter | Standard der Modus-Pfade | Funktionsweise der Paginierung |
  | --- | --- | --- | --- |
  | Offset | `{"offset": "offset", "limit": "limit"}` | `{"has_more": ["has_more"]}` | Sendet die Abfrageparameter für Offset und Limit und liest weiter, solange `has_more` der Antwort wahr ist. |
  | Seitennummer | `{"offset": "page"}` | `{"has_more": ["has_more"]}` | Sendet die Seitennummer im Parameter `page` und sendet kein Limit. |
  | Nächste Seiten-URL | `{}` | `{"next": ["next"]}` | Fordert die URL an, die sich im Pfad `next` jeder Antwort befindet. Eine relative URL wird relativ zu der Seite gelesen, von der sie stammt. |
  | Cursor | `{"cursor": "after"}` | `{"has_more": ["has_more"], "cursor": ["next_cursor"]}` | Sendet den Cursor der vorherigen Antwort im Parameter `after`. Fügen Sie `"send_as": "header"` oder `"send_as": "body_field"` zu den **Modusparametern** hinzu, um ihn stattdessen als Anfrage-Header oder als Body-Feld zu senden. Um den Cursor aus einem Antwort-Header zu lesen, etwa dem Header `x-ms-continuation`, den Azure Cosmos DB sendet, tragen Sie `"token_header": "x-ms-continuation"` anstelle von `has_more` und `cursor` in die **Modus-Pfade** ein; die letzte Seite ist die ohne den Header. |
  | Link-Header | `{"rel": "next"}` | `{}` | Folgt der Relation des Antwort-Headers `Link`, die durch `rel` benannt ist. |

  Offset und Seitennummer akzeptieren in den **Modusparametern** weitere Schlüssel: `start` ist der erste Offset bzw. die erste Seitennummer (Standard 0), `stop_on_empty` stoppt bei der ersten Seite ohne Datensätze am Elementpfad, sodass die Antwort kein Feld `has_more` benötigt, und `send_limit` legt fest, ob der Parameter `limit` gesendet wird (Standard true für Offset, false für Seitennummer).
- **Rohes JSON ausgeben, statt Zeilen zu analysieren** — speichert die Rohdaten, statt sie in Spalten zu parsen.
- **Wiederholungen** (0 bis 100) und **Timeout (s)** (1 bis 600) — wie sich die Anfrage bei Fehlern verhält und wie lange sie laufen darf. Eine Ausführung wartet bis zum festgelegten Timeout; **Testanfrage senden**, **Zeile 1 testen** und **Paginierung testen** warten höchstens 300 s. Wiederholungen decken Verbindungsfehler, Serverfehler (5xx) und Ratenbegrenzung (HTTP 429) bei idempotenten Methoden (GET, HEAD, OPTIONS, DELETE) ab. Ein POST, PUT oder PATCH wird nur nach einer Ratenbegrenzungsantwort (HTTP 429) wiederholt, die Ihnen mitteilt, dass der Server damit nichts getan hat, und nie nach einem Serverfehler, sodass ein nicht idempotenter Anfrage-Body nie zweimal gesendet wird, nachdem der Server möglicherweise bereits gehandelt hat; wenn die API einen Header `Retry-After` zurückgibt, wartet der Schritt das angeforderte Intervall (auf 2 Minuten begrenzt), bevor er es erneut versucht.

Die Registerkarte **Tabellendatenauswahl** ordnet die Felder der Antwort den Spalten der Zieltabelle zu. **Quelle untersuchen → Populate** füllt die Zuordnung anhand einer aktuellen Antwort: Es sendet die Anfrage des Schritts über seine Verbindung, so wie es eine Ausführung tun würde. Dafür ist eine Verbindung erforderlich, und es fragt vorher nach, wenn die Methode etwas anderes als GET, HEAD oder OPTIONS ist. **Zusammenfassen** und **Eindeutig** werden hier nicht angeboten, weil der Schritt die geparste Antwort direkt in die Zieltabelle schreibt.

### Workflow-Variablen

Setzen Sie **Ziel** auf **Workflow-Variablen** und geben Sie ein **Variablenpräfix** an (ein einfacher Name wie `my_call`). Der Schritt sendet **eine** Anfrage und schreibt vier Workflow-Variablen:

| Variable | Inhalt |
|----------|----------|
| `{prefix}_status` | HTTP-Statuscode (zum Beispiel `200`). |
| `{prefix}_body` | Antwort-Body als Zeichenfolge (JSON-Antworten werden als JSON-Text gespeichert). |
| `{prefix}_headers` | Antwort-Header als JSON-Text. |
| `{prefix}_elapsed_ms` | Wie lange die Anfrage gedauert hat, in Millisekunden. |

Verweisen Sie in nachfolgenden Schritten wie auf jede Workflow-Variable darauf — zum Beispiel `{my_call_status}`. Das ist der Baustein für Muster nach dem Prinzip „eine Anfrage senden, dann anhand des Ergebnisses verzweigen“.

<Aside type="caution">Das Präfix muss mit einem Buchstaben oder Unterstrich beginnen und darf nur Buchstaben, Ziffern und Unterstriche enthalten. Es darf keiner der reservierten Namen `cloud`, `project`, `model` oder `date` sein. Im Variablenmodus erfasst der Schritt eine einzelne Antwort — Paginierung und Zeilenanalyse gelten nicht.</Aside>

## Eine Anfrage pro Tabellenzeile senden

Standardmäßig sendet der Schritt **eine** Anfrage. Um eine API einmal pro Zeile einer Tabelle aufzurufen — zum Beispiel jede Kunden-ID in einer Tabelle nachzuschlagen oder jede Zeile als Datensatz per POST zu senden —, setzen Sie **Senden** (auf der Registerkarte Anfrage) auf **Eine Anfrage pro Tabellenzeile**. Dadurch werden die Felder der Treibertabelle eingeblendet:

- **Treibertabelle** — wählen Sie die Tabelle, deren Zeilen die Anfragen steuern. Wählen Sie sie mit der Auswahl aus den Tabellen des Workflows oder geben Sie einen Tabellennamen ein. Die Spalten jeder Zeile stehen als Token `{{row.column}}` zur Verfügung.
- **Treiberfilter** *(optional)* — eine SQL-`WHERE`-Klausel, die einschränkt, welche Zeilen verwendet werden.
- **Schlüsselspalten** *(optional)* — durch Kommas getrennte Treiberspalten, die in jede Ausgabezeile übernommen werden, sodass die Ergebnisse wieder mit dem Treiber verknüpft werden können.
- **Zeilenlimit** und **Parallelität** — die maximale Anzahl der zu verarbeitenden Zeilen und wie viele Anfragen gleichzeitig laufen.
- **Max. Anfr./Sek.** *(optional)* — begrenzen Sie, wie schnell Anfragen über alle Worker hinweg gestartet werden, damit eine Lastspitze nicht das Ratenlimit der API auslöst (0 = kein Limit). Der Wert kann ein Bruch sein: 0.5 startet alle zwei Sekunden eine Anfrage. Ein Wert über 1000 wird mit einer Warnung als 1000 ausgeführt. Das ist unabhängig von der **Parallelität**: Die Parallelität begrenzt, wie viele gleichzeitig laufen, während Max. Anfr./Sek. festlegt, wie oft eine neue gestartet wird.
- **Add Idempotency-Key header** *(optional)* — sendet bei einer einzelnen POST-, PUT- oder PATCH-Anfrage pro Zeile (ohne Paginierung) einen stabilen Header `Idempotency-Key`, der aus jeder Zeile abgeleitet wird, sodass eine erneute Ausführung des Schritts bei einer Idempotenz unterstützenden API keine Datensätze doppelt anlegt (dieselbe Zeile sendet immer denselben Schlüssel, sodass die API die Wiederholung dedupliziert). Bei GET/HEAD/DELETE oder bei aktivem Paginierungsmodus wird er mit einer Warnung ignoriert. Eine Anfrage, die bereits einen eigenen `Idempotency-Key` setzt, behält ihn.
- **Antwort** — wie jede Antwort zu Zeilen wird. **Geparste Datensätze** (Standard) schreibt jeden Antwortdatensatz als Zeile. **Text (eine Zeile pro Anfrage)** schreibt eine Zeile pro Anfrage mit den Spalten `DownloadData` und `DownloadHeaders`; eine fehlgeschlagene Anfrage wird verworfen. **Rohtext, Fehler als Zeilen** schreibt ebenfalls eine Zeile pro Anfrage, behält aber den Body genau so, wie der Server ihn gesendet hat, fügt eine Spalte `DownloadStatus` hinzu und behält einen HTTP- oder Transportfehler als Zeile mit seinem Fehler-Body und Status. Anmeldedaten werden im Body, in den Headern und im Fehlertext jeder Rohzeile maskiert, und einer Weiterleitung zu einem anderen Ursprung wird bei einer Anfrage, die Anmeldedaten enthält, nicht gefolgt. Paginierung gilt für die Textmodi nicht. Bei **Text (eine Zeile pro Anfrage)** schreibt **Keep error response** (`keep_error_response`) den Body einer Antwort ab HTTP 400 genauso in die Zeile wie bei einem Erfolg, statt die Zeile fehlschlagen zu lassen, und **DownloadStatus, DownloadReason und DownloadUrl zur Ausgabe hinzufügen** (`response_meta`) fügt die Spalten `DownloadStatus`, `DownloadReason` und `DownloadUrl` mit Status, Grund und endgültiger URL der Antwort hinzu. Beide sind standardmäßig ausgeschaltet. Das Schrittformular hat die Option **DownloadStatus, DownloadReason und DownloadUrl zur Ausgabe hinzufügen**; setzen Sie `keep_error_response` mit einem KI-Assistenten oder über die REST-API.
- **Continue on error** — wenn eingeschaltet, wird eine fehlgeschlagene Zeile aufgezeichnet und der Schritt endet mit einer Warnung, statt beim ersten Fehler abzubrechen. Das Ausführungsprotokoll nennt die ersten fehlgeschlagenen Zeilen (anhand ihrer Schlüsselspalten) und den jeweiligen Fehler, sodass Sie erkennen können, welche Zeilen warum fehlgeschlagen sind.

Verwenden Sie Token `{{row.column}}` an beliebiger Stelle im Endpunkt, in der Abfrage, den Headern oder im Body, um die Werte dieser Zeile einzusetzen — zum Beispiel `GET /customers/{{row.customer_id}}`. Ein Wert in einem Abfrageparameter wird einmal URL-kodiert, sodass der Server `A 1` und `a/b` so erhält, wie sie eingegeben wurden. Frühere Versionen kodierten ihn zweimal, und der Server erhielt `A%201` und `a%2Fb`. Wenn bei einem POST-, PUT- oder PATCH-Schritt **Add Idempotency-Key header** eingeschaltet ist und ein Zeilenwert in seiner Abfrage kodiert werden muss, ändert sich sein Schlüssel einmalig nach dem Upgrade, weil sich die Anfrage geändert hat. Eine erneute Ausführung, die über das Upgrade hinweg läuft, kann für jede solche Zeile eine wiederholte Anfrage senden. Werte, die nur aus Buchstaben, Ziffern und `-._~` bestehen, bleiben unverändert. Die Antwortdatensätze jeder Zeile werden in die Zieltabelle geparst (wobei etwaige Schlüsselspalten vorangestellt werden); bei eingeschaltetem **Rohes JSON ausgeben, statt Zeilen zu analysieren** erhalten Sie stattdessen eine Zeile pro Anfrage.

Das Menü **Einfügen `{{row.column}}`** listet die Spalten der gewählten Treibertabelle auf, sodass Sie ein Token im Stil von `{{row.customer_id}}` in den Endpunkt oder den Body — je nachdem, welches Feld Sie zuletzt bearbeitet haben — einfügen können, statt Spaltennamen von Hand zu tippen. Während Sie bearbeiten, listet das Formular außerdem die von Ihnen verwendeten Token `{{row.column}}` auf und hebt rot hervor, welche keine Spalte der Treibertabelle sind, sodass Tippfehler vor der Ausführung des Schritts auffallen.

**Zeile 1 testen** liest die erste Treiberzeile (unter Beachtung des Treiberfilters), setzt ihre Werte in Endpunkt, Abfrage, Header und Body ein und sendet diese eine Anfrage — so können Sie bestätigen, dass das Fan-out korrekt verdrahtet ist, bevor Sie es über jede Zeile ausführen. Die Antwort wird wie bei **Testanfrage senden** direkt angezeigt, zusammen mit den verwendeten Werten der Treiberzeile. **Preview Row 1** löst ebenso die Werte `{{row.column}}` der ersten Treiberzeile auf und zeigt die aufgelöste Anfrage an, ohne sie zu senden.

<Aside type="note">Eine Anfrage pro Tabellenzeile schreibt in eine Tabelle — sie kann nicht in Workflow-Variablen erfassen. Das Antwortziel bleibt **Tabelle**.</Aside>

## Den Schritt ausführen

Der REST-Anfrage-Schritt wird wie jeder andere ausgeführt — als Teil einer vollständigen Ausführung oder einzeln (siehe [Einen einzelnen Schritt in einem Workflow ausführen](/de/guides/workflows/running-one-step-in-a-workflow/)). Im Tabellenmodus schreibt er die geparste (oder rohe) Antwort in die Zieltabelle; im Variablenmodus setzt er die vier Variablen, die spätere Schritte lesen können.
