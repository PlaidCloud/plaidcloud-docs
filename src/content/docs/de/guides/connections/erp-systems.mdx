Ein **System** ist eine ERP-Verbindung in einer Umgebung. Der Schritt **Belege buchen**, eine Buchung aus einer Datei und jeder andere Buchungsweg (siehe [Belege in ERP-Systemen buchen](/de/guides/connections/post-documents/)) senden jeden Beleg an ein System, und das System entscheidet, wie der Beleg aufgebaut, geprüft und gesendet wird. Jede ERP-Verbindung, die Sie sehen können, erscheint von selbst als System — fünf SAP-Verbindungen sind fünf Systeme, Cloud und lokal installiert nebeneinander —, und dieselbe Verbindung in einer Sandbox- und einer Produktions-[Umgebung](/de/guides/connections/create-connection/#umgebungen) sind zwei Systeme mit jeweils eigenen Einstellungen.

Sie richten Systeme einmal pro Umgebung ein. Jedes Projekt in dieser Umgebung teilt sich das Raster, welche Entität wohin bucht, und die Einstellungen jedes Systems. Nur Live schalten gilt pro Projekt.

## Systeme öffnen

Öffnen Sie das [Buchungsregister](/de/guides/connections/posting-register/) und wählen Sie in der Navigationsleiste unter **Einstellungen** den Eintrag **Systeme**. Die Kopfzeile enthält:

- Eine Umgebungsauswahl: die Umgebung, deren Systeme aufgeführt sind.
- Eine Projektauswahl, die bei **Kein Projekt** beginnt. Wählen Sie ein Projekt, um zu sehen, ob jedes System darin Live ist, und um live zu schalten.
- **Aktionen**, mit **In diesem Projekt live schalten…** (für einen Projektarchitekten sichtbar), **In eine andere Umgebung kopieren…** (für einen Workspace-Administrator sichtbar), **Vorschlagen, welche Gesellschaft wohin bucht…** und **Änderungsverlauf**.

Die Seite zeigt zwei Karten: **Systeme · *Umgebung*** und **Welche Gesellschaft wohin bucht**. Ist in der Umgebung keine ERP-Verbindung vorhanden, zeigt die Seite **Keine Systeme zum Buchen**: Fügen Sie unter „Verbindungen“ eine Verbindung zu einem ERP-System hinzu, dann erscheint sie hier.

## Die Systemliste

Jedes System ist eine Zeile: sein Name, sein ERP-Typ und eine Reihe von Pills.

| Pill | Bedeutung |
|---|---|
| **Cloud** | Ein Cloud-System. |
| **Lokal installiert · Agent online** | Ein lokal installiertes System, dessen Agent sich in den letzten fünf Minuten gemeldet hat. |
| **Lokal installiert · Agent offline seit *Zeit*** / **Lokal installiert · Agent nicht verbunden** | Der Agent ist nicht online, oder kein Agent bedient diese Umgebung. |
| **Kann buchen** | In das System kann gebucht werden. |
| **Nicht geprüft** | Ein lokal installiertes System, dessen Agent nicht online ist. |
| **Live** / **Simulieren** | Nur mit gewähltem Projekt sichtbar: ob dieses System in diesem Projekt tatsächlich bucht. |
| **Stillgelegt** | Das System nimmt keine neuen Buchungen an. Wird anstelle von Live oder Simulieren angezeigt. |

Eine Zeile kann außerdem zwei Schaltflächen tragen:

- **Erneut verbinden** — wird angezeigt, wenn der Agent eines lokal installierten Systems nicht online ist. Sie öffnet die Verbindung, damit Sie sich erneut anmelden können.
- **Live schalten ›** — wird einem Projektarchitekten angezeigt, mit gewähltem Projekt, bei einem System, das nicht Stillgelegt ist, buchen kann und noch auf Simulieren steht. Siehe [Live schalten](#live-schalten).

### Was eine Zeile beim Öffnen zeigt

Öffnen Sie eine Zeile mit dem Umschalter links. Sie zeigt drei Dinge und eine Reihe von Links.

**Was noch zu tun ist** ist die Checkliste dessen, was zwischen dem System und dem Buchen steht, jeweils mit der Angabe, wer es erledigt. Ein erledigter Punkt ist abgehakt und als erledigt markiert.

| Eintrag | Wer | Erledigt, wenn |
|---|---|---|
| Servicekonto und seine Berechtigungen | **IT** | Vorerst immer erledigt; nichts einzurichten. |
| Agent installiert und online (nur lokal installiert) | **IT** | Der Agent ist online. |
| Eine Entität bucht in dieses System | **Workspace-Administrator** | Eine Zeile von [Welche Gesellschaft wohin bucht](#welche-gesellschaft-wohin-bucht) nennt dieses System. |
| Live schalten | **Projektarchitekt** | Das System ist im gewählten Projekt Live. |

**Was es kann** ist eine Zeile, zum Beispiel „Nimmt Journale, Ausgangsrechnungen an · storniert Journale · Antworten im Aufruf“. Sie führt die Belegarten auf, die das System aufnimmt, die, die es stornieren kann, und ob seine Antwort als **Antworten im Aufruf** oder **Antworten später** zurückkommt. Die vollständige Liste für jedes System steht weiter unten unter [Was jedes System kann](#was-jedes-system-kann).

**Kopie seiner Listen** zeigt, wie alt die Kopie der Konten, Gesellschaften und Perioden des Systems ist, mit **Jetzt aktualisieren** und **Kopie ansehen**. Siehe [Die Kopie der Listen eines Systems](#die-kopie-der-listen-eines-systems).

Die Links darunter sind **Für die IT**, **Einstellungen…**, **Als stillgelegt markieren** (oder **Aus „Stillgelegt“ zurückholen**) und **Verlauf**, der den [Änderungsverlauf](#änderungsverlauf) nur für dieses System öffnet.

## Die vorhandenen Einstellungen

Jede Einstellung hat einen Startwert, und die meisten Projekte ändern nie eine.

| Einstellung | Wo | Wer ändert sie | Startwert |
|---|---|---|---|
| Welche Entität wohin bucht | [Systeme](#welche-gesellschaft-wohin-bucht), einmal pro Umgebung | Ein Workspace-Administrator | Keine Zeilen. Ohne Zeilen nimmt das einzige System, das nicht Stillgelegt ist und unter **Systeme** aufgeführt wird, jede Entität auf. |
| Stillgelegt | Die Zeile eines Systems | Ein Workspace-Administrator | Nicht stillgelegt |
| Simulieren oder Live | [Live schalten](#live-schalten), pro System, pro Projekt | Der Architect des Projekts | Simulieren |
| **Immer erforderliche Werte** | Die [Einstellungen](#systemeinstellungen) eines Systems | Ein Workspace-Administrator | Keine |
| **Code-Zuordnungen** (einschließlich der Entitätszuordnung) | Die [Einstellungen](#systemeinstellungen) eines Systems | Ein Workspace-Administrator | Keine |
| **Die eigene Funktion des Kunden** (SAP lokal installiert) | Die [Einstellungen](#systemeinstellungen) eines Systems | Ein Workspace-Administrator | Keine, oder die Funktion, die ein konvertierter Schritt mitbringt |
| Halteregeln | [Halteregeln](#halteregeln), pro System | Ein Register-Administrator (`erp.register.admin`) | Nichts ist angehalten |
| **Für eine Person zurückhalten** | Der Schritt, unter **Mehr ▸** | Der Ersteller des Schritts | Nichts ist angehalten |
| **Wer benachrichtigt wird** | Der Schritt, unter **Mehr ▸** | Der Ersteller des Schritts | **Wer den Lauf gestartet hat** |
| **Rundungskonto und Grenzwert** | Der Schritt, unter **Mehr ▸** | Der Ersteller des Schritts | Keine Rundung |
| **Wenn ein gebuchter Beleg geändert zurückkommt** | Der Schritt, unter **Mehr ▸** | Der Ersteller des Schritts | **Nachfragen (Startwert). Der Beleg erscheint unter „Aufmerksamkeit erforderlich“ mit zwei Optionen.** |

Die vier Schritteinstellungen werden zusammen mit dem Schritt unter [Belege in ERP-Systemen buchen](/de/guides/connections/post-documents/) beschrieben; die Haltefunktion eines Schritts wird [weiter unten](#die-eigene-haltefunktion-eines-schritts) beschrieben.

## Systemeinstellungen

Wählen Sie bei einer geöffneten Zeile **Einstellungen…**. Der Dialog **Einstellungen: *System*** kann nur von einem Workspace-Administrator bearbeitet werden; alle anderen sehen **Nur ein Workspace-Administrator kann diese ändern.** **Speichern** ersetzt die gesamten Einstellungen des Systems, und jede Änderung wird im [Änderungsverlauf](#änderungsverlauf) erfasst.

**Immer erforderliche Werte** sind Werte, die jedem an dieses System gesendeten Beleg hinzugefügt werden, als Paare aus **Wert** und **Setzen auf**. Ein System liest die Werte, die es braucht, über ihren Namen, und eine eigene Spalte des Belegs mit gleicher Bedeutung hat Vorrang vor dem Wert des Systems:

| System | Wert | Verwendet für |
|---|---|---|
| Sage Intacct | `gl_journal_id` | Das Journal, in das eine Journalbuchung bucht, wenn der Beleg kein `journal_type` hat. |
| Sage 100 | `bank_code` | Das Bankkonto, von dem eine Zahlung abgebucht wird, wenn der Beleg kein `bank_code` hat. |

**Code-Zuordnungen** legen fest, welcher Code hier einem anderen Code im System entspricht: eine **Dimension**, **Unser Code** und **Code im System**. Verwenden Sie die Dimension `entity` für eine Entität, deren Gesellschaft im System einen anderen Code hat, und `account` für ein Konto. Die [Prüfungen](#prüfungen-gegen-die-listen) schlagen einen Code über seine Zuordnung in den Listen des Systems nach, oder wie geschrieben, wenn er keine hat, und eine Entitätszuordnung erlaubt es dem Raster außerdem, dieses System für diese Entität [vorzuschlagen](#vorgeschlagene-zeilen).

**Die eigene Funktion des Kunden** erscheint nur bei SAP lokal installiert. Nennen Sie die Funktion für jede **Belegart**. Die Einstellungen nennen nur die Funktion: Die Feldzuordnung jeder Funktion — welches SAP-Feld welche Spalte aufnimmt — bleibt unverändert im System gespeichert, und eine Funktion, die ein konvertierter SAP-Buchungsschritt mitgebracht hat, behält die Feldzuordnung, die der Schritt hatte. Siehe [SAP lokal installiert](#sap-lokal-installiert).

## Welche Gesellschaft wohin bucht

Die zweite Karte ist das Raster, welche Entität ab welchem Datum in welches System bucht; es wird einmal pro Umgebung festgelegt und von jedem Projekt darin geteilt. Jede Zeile besteht aus einer Entität, **→**, einem System und einem optionalen **Von (JJJJ-MM-TT)**.

1. Wählen Sie **Zeile hinzufügen**, geben Sie die Entität ein und wählen Sie unter **System auswählen** ein System. Angeboten werden nur Systeme, die nicht Stillgelegt sind.
2. Lassen Sie **Von (JJJJ-MM-TT)** leer für „von Anfang an“, oder geben Sie das Datum an, ab dem die Entität in dieses System bucht. Um eine Entität mitten im Jahr in ein anderes System zu verlagern, behalten Sie ihre erste Zeile bei und fügen Sie eine zweite Zeile für das neue System ab dem Datum des Wechsels hinzu, zum Beispiel `2026-07-01`.
3. Wählen Sie **Speichern**. Ein Datum, das nicht in dieser Form vorliegt, wird mit **Ein Datum sieht so aus: 2026-07-01.** abgelehnt.

Zum Bearbeiten des Rasters ist ein Workspace-Administrator nötig; alle anderen sehen es schreibgeschützt. Eine bereits gespeicherte Entität kann nicht umbenannt werden: Entfernen Sie ihre Zeile mit dem Kreuz am Ende und fügen Sie eine andere hinzu. Entitäten, die Belege genannt haben, die aber noch keine Zeile nennt, werden ohne gewähltes System aufgeführt; gibt es gar keine, zeigt die Karte **Noch keine Entitäten. Es sind die, die in den Tabellen gefunden werden, in die Sie buchen. Fügen Sie eine Zeile hinzu, um eine zu benennen.**

### Wie ein Beleg sein System findet

Ein Beleg bucht über die Systeme der Umgebung seines Projekts.

- Sein System ist die jüngste Zeile der Entität, deren **Von**-Datum am oder vor dem Buchungsdatum des Belegs liegt (heute, wenn er keines hat).
- Hat das Raster der Umgebung gar keine Zeilen und wird nur ein System, das nicht Stillgelegt ist, unter **Systeme** aufgeführt, nimmt dieses System jeden Beleg auf.
- Ein Beleg, dessen Entität an diesem Datum von keiner Zeile abgedeckt wird, wird nicht gebucht und meldet, dass es für seine Entität kein System gibt.
- Ein Beleg, dessen Zeile ein Stillgelegtes System nennt, wird nicht gebucht und meldet, dass das System stillgelegt ist.

### Vorgeschlagene Zeilen

Für eine Entität, die noch keine Zeile nennt, schlägt das Raster ein System vor, wenn genau ein System der Umgebung, das nicht Stillgelegt ist, diese Entität nennt — über eine [Code-Zuordnung](#systemeinstellungen) `entity` oder in der eigenen Kopie seiner Gesellschaftsliste. Die Zeile zeigt **Vorgeschlagen** und bleibt schreibgeschützt, bis Sie **Übernehmen** wählen; nur übernommene Zeilen werden gespeichert.

**Vorschlagen, welche Gesellschaft wohin bucht…** unter **Aktionen** ist der Vorschlag von Weave aus der Data Foundation: Bei gewähltem Projekt trägt es jede Entität ein, die die Data Foundation des Projekts geladen hat, zusammen mit der Verbindung, aus der sie geladen wurde. Nichts wird von einem Modell berechnet und nichts gespeichert: Die Zeilen werden ausgefüllt, eine Meldung nennt die Anzahl, und Sie lesen jede und wählen **Speichern**. Ist nichts geladen, steht dort **Noch keine Vorschläge.**

### Zeilen, die Sie hier nicht ändern können

- Eine Zeile, deren System Stillgelegt ist, wird schreibgeschützt mit **Stillgelegt** angezeigt. Beim Speichern des Rasters bleibt sie erhalten.
- Eine Zeile, deren System Sie nicht sehen können, wird schreibgeschützt mit **Nicht in dieser Liste** angezeigt. Beim Speichern des Rasters wird sie entfernt, daher bittet **Speichern** zuerst um Bestätigung unter **Zuordnung speichern**.

## Live schalten

Nichts bucht tatsächlich, bevor jemand bewusst live schaltet. Live schalten gilt pro System und pro Projekt: In einem Projekt können einige Systeme Live sein, während andere noch auf Simulieren stehen. Ein neues, kopiertes oder zur Probe genutztes Projekt startet bei jedem System auf Simulieren, bis jemand darin live schaltet.

1. Wählen Sie das Projekt in der Projektauswahl der Kopfzeile.
2. Wählen Sie **Live schalten ›** in der Zeile eines Systems oder **In diesem Projekt live schalten…** unter **Aktionen** für jedes System, das buchen kann und noch nicht Live ist. Ohne gewähltes Projekt wird Ihnen **Wählen Sie ein Projekt, in dem live gegangen werden soll.** mitgeteilt.
3. Der Dialog **Live schalten** prüft zuerst, was sich ändern würde, ohne etwas zu ändern, und zeigt es an:
   - **Diese werden Live**: die Systeme, die tatsächlich buchen werden.
   - **Der Buchungsmodus des Projekts wechselt auf Live, sodass jedes Live-System tatsächlich bucht.** — wird angezeigt, wenn das Projekt selbst noch nicht im Modus Live ist.
   - **Bereits Live**: die Systeme, die es schon sind.
   - ***System* kann nicht Live werden:** mit dem Grund: Das System ist Stillgelegt, das Projekt ist gesperrt, Sie haben keinen Schreibzugriff auf diese Verbindung, oder es ist kein System, in das Sie buchen können.
4. Wählen Sie **Live schalten**. Die Schaltfläche ist nur aktiv, wenn mindestens ein System Live würde.

Beim Live-Schalten wird die Autorisierung des Projekts für diese Systeme in dieser Umgebung geschrieben, und der Buchungsmodus des Projekts wird auf Live gesetzt, wo er es nicht war. Jedes System, das live geht, wird im [Änderungsverlauf](#änderungsverlauf) erfasst. Live schalten wird nie in eine andere Umgebung oder ein anderes Projekt kopiert.

Zum Live-Schalten ist der Architect des Projekts nötig, in einem Projekt, das nicht gesperrt ist, mit Ihrem eigenen Schreibzugriff auf jede Verbindung. Dieselbe Prüfung gilt über die REST-API (`POST /erp/go-live`) und über das MCP-Tool `erp_go_live`, das zudem ein delegiertes KI-Token ablehnt: Eine Person schaltet live, nie ein Agent in ihrem Auftrag. Beide melden nur, was sich ändern würde, sofern `dry_run` nicht auf false gesetzt ist.

## Ein System stilllegen

Wählen Sie bei einer geöffneten Zeile **Als stillgelegt markieren** und bestätigen Sie mit **Stilllegen**: Das System wird nicht mehr zum Buchen angeboten, bis es zurückgeholt wird. Seine Zeilen im Raster bleiben erhalten, und an es geleitete Belege werden nicht gebucht. **Aus „Stillgelegt“ zurückholen** macht dies rückgängig. Beides erfordert einen Workspace-Administrator und wird im [Änderungsverlauf](#änderungsverlauf) erfasst.

## Für die IT

**Für die IT** öffnet **Für die IT: *System***, was das Produkt in diesem System tut, damit es zugelassen und geprüft werden kann:

- **Meldet sich an als** — das Konto, mit dem sich die Verbindung anmeldet.
- **Stapelgröße** — die Stapelgröße, die die Einstellungen des Systems festlegen, oder **Nicht festgelegt**.
- **Agent** und **Agent-Version** — bei einem lokal installierten System.
- **Unser Name** — jede Funktion oder jeder Dienst, die das Produkt beim Namen aufruft, mit dem Zeitpunkt der letzten Verwendung. Bei SAP lokal installiert sind das die in den [Einstellungen](#systemeinstellungen) festgelegten Funktionen. Bevor etwas gebucht oder getestet wurde, steht dort **Noch nichts. Es wird aufgeführt, sobald in dieses System gebucht oder es getestet wurde.**

Ist die Anmeldung abgelaufen, sagt der Dialog das und bietet **Erneut verbinden** an.

## In eine andere Umgebung kopieren

Richten Sie eine Sandbox einmal ein und kopieren Sie sie in die Produktion, statt alles erneut einzugeben. Wählen Sie **In eine andere Umgebung kopieren…** unter **Aktionen** (nur Workspace-Administrator).

1. Wählen Sie die Umgebung unter **Kopieren nach**.
2. Jedes System dieser Umgebung wird aufgeführt und angekreuzt, wenn dieselbe Verbindung in der anderen Umgebung ein System ist; eines, das es nicht ist, wird als ***System* (nicht in dieser Umgebung)** angezeigt und kann nicht angekreuzt werden.
3. Wählen Sie **Kopieren** und bestätigen Sie.

Für jedes angekreuzte System ersetzt die Kopie dessen Einstellungen, Code-Zuordnungen und SAP-Funktionen in der anderen Umgebung durch diese und fügt die Zeilen des Rasters hinzu, die es nennen und die der anderen Umgebung fehlen (dieselbe Entität ab demselben Datum). Bereits vorhandene Zeilen bleiben unverändert. Das Ergebnis nennt, wie viele Zeilen des Rasters und wie viele Systemeinstellungen kopiert wurden. Live schalten wird nicht kopiert: Jedes Projekt in der anderen Umgebung bleibt auf Simulieren, bis dort jemand live schaltet.

## Die Kopie der Listen eines Systems

Die Prüfungen vergleichen Belege mit den eigenen **Konten**, **Gesellschaften** und **Perioden** des Systems. PlaidCloud hält von jeder eine Kopie, die aus dem System selbst gelesen wird:

- **Zu Beginn jeder Live-Ausführung bei einem Live-System**, aus dem System, mit bis zu 60 Sekunden für den gesamten Lesevorgang. Nur der Lesevorgang dieser Ausführung kann einen Beleg anhalten.
- **Bei Jetzt aktualisieren**, in einer geöffneten Zeile. Das Aktualisieren kontaktiert Ihr ERP-System wie das Buchen, daher sind ein Workspace-Administrator und Ihr eigener Schreibzugriff auf diese Verbindung nötig. Es meldet, wie viele Konten, Gesellschaften und Perioden gelesen wurden und wie lange das Lesen dauerte. Eine aktualisierte Kopie dient der Ansicht: Sie speist keine Prüfung.

Jede Liste zeigt ihr Alter in der Zeile — etwa „Konten vor 3 Stunden gelesen“, „Perioden teilweise, vor 2 Tagen gelesen“ oder „Gesellschaften noch nicht gelesen“ — oder dass sie nicht gelesen werden konnte und warum. Eine Kopie, die abgebrochen wurde oder leer zurückkam, ersetzt die vorherige nicht.

**Kopie ansehen** öffnet **Kopie der Listen**, eine Liste nach der anderen (**Konten**, **Gesellschaften** oder **Perioden**), mit **Code**, **Name**, **Blockiert**, **Status im System**, **Von** und **Bis**. Es werden bis zu die ersten 5.000 Zeilen angezeigt. Steuercodes, Kunden und Lieferanten werden nicht kopiert; sie bleiben dem System überlassen.

Eine Simulieren-Ausführung liest nichts aus dem System, daher laufen diese Prüfungen in Simulieren nicht, und das System entscheidet beim Live-Schalten.

## Prüfungen gegen die Listen

Zu Beginn einer Live-Ausführung bei einem Live-System wird jeder Beleg gegen die Listen geprüft, die diese Ausführung gelesen hat. Eine Prüfung, deren Liste nicht gelesen werden konnte, nur teilweise oder leer zurückkam oder nicht rechtzeitig fertig wurde, gilt als nicht geprüft — nie bestanden, nie ein Stopp —, und das System entscheidet. Die Seite der Ausführung zeigt, welche Prüfungen bei jedem Beleg liefen.

- **Period open** (Offene Periode). Die Periode des Belegs wird über seinen Periodencode gefunden, ansonsten über die Perioden, in die sein Buchungsdatum fällt. Er wird nur angehalten, wenn jede Periode, die ihn enthält, im System für Buchungen geschlossen ist — eine Anpassungsperiode, die sich mit seinem Monat überschneidet, hält das Datum offen. Eine Periode, deren Status das System in Worten meldet, die PlaidCloud nicht kennt, wird nicht geprüft.
- **Die Entität ist eine Gesellschaft.** Wurde die Gesellschaftsliste gelesen, muss die Entität des Belegs — über ihre Code-Zuordnung `entity`, falls vorhanden, sonst wie geschrieben — eine der Gesellschaften des Systems sein.
- **Die Konten sind vorhanden.** Wurde die Kontenliste gelesen, muss das Konto jeder Zeile — über seine Code-Zuordnung `account`, falls vorhanden, sonst wie geschrieben — im System vorhanden und nicht für Buchungen gesperrt sein. Numerische Codes stimmen unabhängig von führenden Nullen überein, sodass `6100` auch `0000006100` findet.

Ein angehaltener Beleg ist Nicht gebucht, mit dem Grund, etwa „Zeile 3: Konto 6100 ist nicht in *System*“. Welche Listen jedes ERP-System bietet, steht in der Tabelle unten.

## Halteregeln

Nichts wird angehalten, bevor eine Regel es verlangt. Ein Beleg, den eine Regel anhält, wartet als Freigabe erforderlich darauf, dass eine Person ihn unter [Genehmigungen](/de/guides/connections/posting-register/) freigibt; alles andere, was seine Prüfungen besteht, wird ohne Freigabe gesendet. Wählen Sie in der Navigationsleiste unter **Einstellungen** den Eintrag **Halteregeln**.

Die Liste hat **Name**, **Gilt für**, **Anhalten, wenn**, **Freigegeben von** und **Von**. Ohne Regeln steht dort **Nichts ist angehalten**. Jeder mit `erp.register.view` kann die Regeln lesen; Hinzufügen, Bearbeiten und Löschen erfordern einen Register-Administrator (`erp.register.admin`), der in der Symbolleiste **Neue Regel**, **Bearbeiten** und **Löschen** sieht. Das Löschen einer Regel verhindert, dass sie etwas Neues anhält; bereits wartende Belege warten weiter, bis jemand entscheidet. Jede Änderung wird im [Änderungsverlauf](#änderungsverlauf) erfasst.

### Die Bedingungen einer Regel

**Neue Regel** öffnet **Neue Halteregel**:

1. Geben Sie der Regel einen **Namen**, zum Beispiel „Journale über 250.000“.
2. Wählen Sie das System unter **Gilt für**. Angeboten werden die Systeme jeder Umgebung, die Sie sehen können.
3. Kreuzen Sie unter **Anhalten, wenn** an, was einen Beleg anhält. Alles Angekreuzte muss zutreffen; ohne Häkchen wird nichts angehalten.
   - **Der Betrag liegt über** einem Wert, **in der eigenen Währung der Gesellschaft**: Die Größe des Belegs ist die Summe seiner Sollbeträge plus positiver lokaler Beträge, oder seine Transaktionsbeträge, wenn die Tabelle keine lokalen enthält.
   - **Er wurde aus einer Datei gebucht**.
   - **Es ist ein** **Storno**, eine **Gutschrift** oder eine **Korrektur** — kreuzen Sie eines der drei an.
   - **Er ist als ungewöhnlich markiert** — siehe [Als ungewöhnlich markiert](#als-ungewöhnlich-markiert).
   - **Immer, zum Beispiel während des Abschlusses** — hält jeden Beleg des Systems an; es schaltet die anderen Bedingungen aus.
4. Wählen Sie unter **Freigegeben von**, wer freigibt: **Die Freigeber des Registers** oder **Namentlich genannte Personen** — kreuzen Sie die Personen an und, optional, die durch Kommas getrennten Entitäten, für die sie freigeben (leer bedeutet jede Entität).
5. Wählen Sie **Speichern**. Die Schaltfläche ist aktiv, sobald die Regel einen Namen, ein System, mindestens eine Bedingung, einen Betrag, der eine Zahl ist, und bei namentlich genannten Personen mindestens eine Person hat.

Ein angehaltener Beleg hält jeden anderen Beleg seiner Gruppe an, sodass eine Gruppe als Ganzes freigegeben und gebucht wird.

### Wer freigeben kann

Ein Freigeber benötigt `erp.register.approve` und eine eigene Berechtigung für die Verbindung des Belegs. Nennt die Regel Personen, geben nur diese Personen frei — und nur für die Entitäten, die sie aufführt, falls sie welche aufführt. Niemand gibt einen Beleg frei, den er selbst gesendet hat: weder die Person, die die Ausführung gestartet hat, noch die Person, deren **Diese buchen** ihn gesendet hat.

Eine Freigabe, die erteilt wurde, als der Beleg in Simulieren gesendet wurde, zählt nicht für ein Live-Senden: Wird derselbe Beleg später Live gesendet, wird er für eine neue Entscheidung erneut angehalten.

Verlangt Ihr Workspace für Buchungen eine Funktionstrennung, wird eine davon erfasste Stornierung, Gutschrift oder Korrektur auch ohne Regel für eine zweite Person angehalten.

### Die eigene Haltefunktion eines Schritts

Ein Schritt **Belege buchen** kann mehr anhalten als seine Systeme, unter **Mehr ▸** → **Für eine Person zurückhalten**. Seine Bedingungen sind **Der Betrag liegt über**, **Er wurde aus einer Datei gebucht**, **Es ist eine Stornierung, Gutschrift oder Korrektur**, **Er ist als ungewöhnlich markiert** und **Immer**, auf dieselbe Weise kombiniert; ohne Häkchen wird nichts zusätzlich angehalten. Die Haltefunktion eines Schritts ergänzt nur die Regeln des Systems — sie kann nicht freigeben, was eine Systemregel anhält —, und ihre Belege werden von den Freigebern des Registers freigegeben. Namentlich genannte Freigeber werden in einer Systemregel festgelegt.

Das Ändern der Haltefunktion eines Schritts über die REST-API (`PUT /erp/steps/{step_id}/holds`) oder das MCP-Tool `erp_hold_upsert` erfordert `analyze.step.write` und die Rolle Architect oder Manager im Projekt, das nicht gesperrt sein darf.

### Als ungewöhnlich markiert

Ein Beleg wird als ungewöhnlich markiert, wenn im Vergleich zu dem, was seine Entität zuvor gebucht hat:

- sein Betrag mehr als zehnmal größer oder kleiner ist als die letzte Buchung derselben Referenz;
- er ein Konto, einen Kunden, einen Lieferanten oder einen Handelspartner verwendet, den seine Entität in ihren letzten 500 Belegen nicht verwendet hat; oder
- sein Buchungsdatum außerhalb seiner Periode liegt.

Jede Markierung hält den Satz fest, der sagt, warum, etwa „Das Buchungsdatum 2026-08-02 liegt außerhalb der Periode 2026-07.“ Die Markierung wird aus früheren Belegen der Entität berechnet; es wird kein KI-Modell aufgerufen. Eine Entität ohne frühere Belege wird nie markiert.

## Was jedes System kann

Jedes unten aufgeführte System kann in Simulieren laufen, wobei jeder Beleg aufgebaut und geprüft, aber nichts gesendet wird. Ein Beleg einer Art, die sein System nicht aufnimmt, ist Nicht gebucht; er wird nicht in eine andere Art umgewandelt.

| System | Wo | Nimmt auf | Storniert | Antwort | Listen für die Prüfungen |
|---|---|---|---|---|---|
| NetSuite | Cloud | Journale, Ausgangsrechnungen | Journale | Im Aufruf | Konten, Tochtergesellschaften, Buchungsperioden |
| Sage Intacct | Cloud | Journale, Ausgangsrechnungen | Journale | Im Aufruf | Konten, Entitäten, Berichtsperioden |
| QuickBooks | Cloud | Journale, Ausgangsrechnungen, Eingangsrechnungen, Gutschriften | Journale, Ausgangsrechnungen | Im Aufruf | Konten, die Gesellschaft, Monate abgeschlossen bis zum Abschlussdatum der Bücher |
| Xero | Cloud | Journale, Ausgangsrechnungen, Eingangsrechnungen, Gutschriften | Journale, Ausgangsrechnungen | Im Aufruf | Konten, die Organisation, Monate abgeschlossen bis zum Sperrdatum |
| Acumatica | Cloud | Journale, Ausgangsrechnungen, Eingangsrechnungen, Zahlungen, Gutschriften | Journale | Später | Konten, Filialen, Finanzperioden |
| Business Central | Cloud | Journale | Journale | Im Aufruf | Gesellschaften, Konten, Buchungsperioden |

Eine Antwort **später** trifft nach dem Senden ein, und der Beleg ist Wartend, bis sie da ist; ein Beleg, dessen Antwort nie feststeht, ist Unbestätigt, was Sie im [Buchungsregister](/de/guides/connections/posting-register/) klären.

### SAP lokal installiert

SAP lokal installiert bucht über den Agent, indem für jede Belegart die eigene Funktion des Kunden aufgerufen wird — festgelegt unter [**Die eigene Funktion des Kunden**](#systemeinstellungen). Ein Beleg, dessen Art keine Funktion hat oder dessen Feldzuordnung der Funktion kein Feld für die Referenz des Belegs enthält, ist Nicht gebucht. Das Konvertieren eines vorhandenen SAP-Buchungsschritts bringt dessen Funktion und Feldzuordnung in das System, wenn das System für diese Belegart noch keine Funktion hat; siehe [Belege in ERP-Systemen buchen](/de/guides/connections/post-documents/).

- **Simulieren** baut dieselbe Anfrage auf und hält vor dem Agent an: Nichts erreicht SAP.
- **Live** übergibt die Belege an den Agent, der die Umgebung des Systems bedient. Der Agent schreibt die Antworten von SAP in einen Bericht im Standard-Dokumentenkonto des Projekts (unter `/erp_posting/sap`), und jeder Beleg bleibt Wartend, bis dieser Bericht gelesen wurde. Ein Projekt ohne Standard-Dokumentenkonto kann nicht Live in SAP buchen, und seine Belege sind mit diesem Grund Nicht gebucht.
- **Ist der Agent offline**, wird nichts gesendet: Die Belege sind Nicht gebucht, mit der Angabe, dass der Agent offline war, und können wiederholt werden, sobald er zurück ist. Nimmt der Agent die Belege nicht innerhalb von etwa 18 Sekunden an, werden sie ungesendet zurückgenommen und auf dieselbe Weise Nicht gebucht.
- Ein Beleg, den der Bericht von SAP unentschieden lässt, ist Unbestätigt. Klären Sie ihn im Buchungsregister.

### Sage 100

Sage 100 ist lokal installiert und hat keine Netzwerk-API: Belege erreichen es über den Agent, der die Business Object Interface von Sage ausführt.

- **Eine Gesellschaft pro Verbindung.** Die Verbindung nennt die Sage-Gesellschaft und ihre Währung. Ein Beleg für eine andere Gesellschaft oder mit einer Zeile in einer anderen Währung wird nicht gesendet.
- **Journale** werden als Hauptbuch-Journalbuchungen gebucht. Die Referenz eines Journals ist in Sage seine Beschreibung, daher darf sie höchstens 30 Zeichen lang sein.
- **Zahlungen** werden als manuelle AP-Schecks für Zahlungen außerhalb von Sage gebucht: ein Lieferant pro Zahlung, die Referenz als Schecknummer (höchstens 7 Zeichen), ein `bank_code` (aus dem Beleg oder aus den [immer erforderlichen Werten](#systemeinstellungen) des Systems) und jede Zeile mit der Angabe der Rechnung, die sie begleicht, mit positivem Betrag.
- **In einer Live-Ausführung** fragt der Agent zuerst Sage: Ein Journal mit einem Datum in einer von Sage geschlossenen Periode wird angehalten, ebenso eine Zahlung für eine Rechnung, die Sage nicht offen hält.
- **Nach dem Senden** ist ein Beleg nur dann Gebucht, wenn ihn die Buchungstabellen von Sage zeigen. Ein Beleg, der in einen Sage-Stapel eingegeben, aber noch nicht aktualisiert wurde, bleibt Wartend; ein Hintergrunddurchlauf fragt den Agent höchstens einmal pro Stunde erneut, und einer, der nach sieben Tagen noch wartet, wird Unbestätigt.

## Änderungsverlauf

Jede Änderung an einem System wird mit Verfasser und Zeitpunkt erfasst: **Systemeinstellungen**, **Stillgelegt**, **SAP-Funktion**, **Code-Zuordnung**, **Welche Gesellschaft wohin bucht**, **Halteregel**, **Live schalten** und **Listenkopie** (jedes Lesen der Listen eines Systems). Wählen Sie **Änderungsverlauf** in der Navigationsleiste unter **Einstellungen** oder im Menü **Aktionen**, oder **Verlauf** in der Zeile eines Systems für nur dieses System. Die Liste hat **Wann**, **Von**, **Was**, **System**, **Welche**, **Von** und **Bis**.

Sie sehen die Änderungen an Systemen, für die Sie eine Berechtigung haben; ein Live schalten nur für Projekte, die Sie erreichen können, und die Haltefunktion eines Schritts nur in Projekten, die Sie erreichen können.

## Wer was tun darf

Jede der folgenden Regeln wird vom Server geprüft, für die App, die REST-API und die MCP-Tools gleich, sofern die Zeile nichts anderes sagt.

| Aktion | Sie benötigen |
|---|---|
| Systeme, die Einstellungen eines Systems, das Raster und seine Kopie der Listen sehen | `analyze.connection.read`, und nur die Verbindungen, die Sie sehen können |
| Einstellungen ändern, ein System stilllegen, das Raster speichern, in eine andere Umgebung kopieren | Einen Workspace-Administrator |
| Die Listen eines Systems aktualisieren | Einen Workspace-Administrator auf der Seite Systeme, oder `analyze.connection.read` über die REST-API und das MCP-Tool `erp_system_lists`; in beiden Fällen Ihren eigenen Schreibzugriff auf diese Verbindung |
| Live schalten | Der Architect des Projekts in einem Projekt, das nicht gesperrt ist, mit Ihrem eigenen Schreibzugriff auf jede Verbindung; eine Person, nie ein delegiertes KI-Token |
| Halteregeln lesen | `erp.register.view` |
| Die Halteregel eines Systems hinzufügen, ändern oder löschen | Einen Register-Administrator (`erp.register.admin`) |
| Die eigene Haltefunktion eines Schritts ändern | `analyze.step.write` und die Rolle Architect oder Manager im Projekt, das nicht gesperrt sein darf |
| Einen angehaltenen Beleg freigeben | `erp.register.approve` und Ihre eigene Berechtigung für die Verbindung des Belegs; in der Regel genannt, wenn sie Personen nennt; nie Ihr eigenes Senden |
