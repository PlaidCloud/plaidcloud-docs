## Suchen

Projekte suchen Sie über das Filterfeld unten links in der Hierarchie. Der Suchfilter durchsucht Projektnamen und Bezeichnungen nach Treffern und zeigt die Ergebnisse oben in der Hierarchie an.


## Neue Projekte erstellen

So erstellen Sie ein neues Projekt:

1. Öffnen Sie Analyze.
2. Wählen Sie in der oberen Menüleiste „Projekte“ aus.
3. Klicken Sie auf die Schaltfläche „Neues Projekt“.
4. Füllen Sie das Formular aus, einschließlich des Abschnitts „Access Control“.
5. Klicken Sie auf „Create“.

Das Projekt ist nun bereit, um Zugriffsberechtigungen zu aktualisieren, Eigentümer hinzuzufügen und Workflows zu erstellen.

<Aside>Standardmäßig können alle Mitglieder des aktuellen Workspace auf das Projekt zugreifen.</Aside>


## Ein Standard-Dokumentenkonto festlegen

Wählen Sie auf der Projektstartseite neben **Verbindungsumgebung** ein **Standard-Dokumentkonto** für das Projekt aus, oder wählen Sie **Keine**, um die Einstellung zu entfernen.

Innerhalb des Projekts führt jede Dateiauswahl zuerst **Project Default** auf, stellvertretend für das Konto, das für das Projekt aktuell festgelegt ist. Der Eintrag verschwindet aus der Liste, sobald Sie das Projekt verlassen, das Projekt keinen Standard mehr hat, das Konto gelöscht wurde oder Sie keinen Zugriff mehr darauf haben.

Ein neuer Dateischritt wählt Project Default vorab aus, wenn das Projekt einen Standard hat. Bestehende Schritte werden nie umgeschrieben: Jeder behält das Konto, mit dem er gespeichert wurde, bis Sie es selbst ändern, denn ein Dokumentenkonto wird anders als die Verbindungsumgebung pro Schritt gewählt.

Ein Schritt, der auf Project Default steht, verwendet bei der Ausführung das Konto, das zu diesem Zeitpunkt der Standard des Projekts ist. Eine Änderung des Standards während einer laufenden Ausführung betrifft daher nur die Knoten, die noch nicht gestartet wurden, genau wie bei einer Änderung der Verbindungsumgebung. Wird ein Schritt auf Project Default ausgeführt und das Projekt hat keinen Standard, schlägt die Ausführung fehl und nennt das Projekt, statt auf ein anderes Konto auszuweichen.


## Versionsverlauf

Jedes Objekt in einem Projekt ist durch Versionsverlauf-Backups abgedeckt: ein Schritt, eine UDF, ein Workflow, eine Dimension, ein gespeichertes Layout, ein Dokument- oder Dateneditor sowie die Einstellungen des Projekts selbst. Ein Backup entsteht nicht bei jedem einzelnen Speichern. Stattdessen wird einmal ein Backup des gesicherten Zustands erstellt, sobald ein Objekt 30 Sekunden lang nicht erneut gespeichert wurde. Eine Reihe von Änderungen, also mehrere Speichervorgänge in kurzer Folge, erzeugt eine einzige Version mit dem Endergebnis und nicht eine Version pro Speichervorgang. Das Speichern wird nie durch das Warten auf ein Backup verlangsamt: Der Countdown und das Backup selbst laufen im Hintergrund. Wenn Sie sofort eine Version benötigen, verwenden Sie **Back up now**, um den aktuellen Zustand unmittelbar zu sichern und auf den Abschluss zu warten. Die Funktion steht in der Benutzeroberfläche, in der API und als MCP-Aktion `backup` der `*_versions`-Werkzeuge zur Verfügung. Der Versionsverlauf ist in jedem Tarif verfügbar, auch im Free-Tarif.

Frühere Versionen ermöglichen eine Wiederherstellung zu einem bestimmten Zeitpunkt: Sie setzen ein Objekt auf eine frühere Version zurück. In einem gesperrten Projekt wird die Wiederherstellung abgelehnt, genau wie jede andere Änderung dort.

Eine Version wird an Ort und Stelle wiederhergestellt. Die Wiederherstellung einer Version eines Projekts, einer Dimension, einer benutzerdefinierten Funktion, eines Schritts, eines Workflows oder eines Dateneditors ersetzt dasselbe Element, und die Angabe eines anderen Elements als Ziel wird abgelehnt, zum Beispiel mit „A project version is restored in place. Leave the target out, or set it to this project.“ Eine Wiederherstellung ist eine Änderung am Element und erfordert daher dieselbe Rolle wie dessen Bearbeitung. Bei einem Projekt, das [Zeilen einschränkt](/de/administration/access/managing-security-groups-and-assignments/#wer-ein-projekt-mit-zeileneinschränkung-ändern-darf), erfordert die Wiederherstellung des Projekts oder einer Dimension, die eine eingeschränkte Spalte liest, einen Projekt-Architect. Um alte Tabellendaten als separate Tabelle zurückzubringen, stellen Sie einen [Tabellen-Snapshot](/de/guides/data/table-snapshots/) in einer neuen Tabelle wieder her.

Zusätzlich zu dieser automatischen Nachverfolgung bieten Projekte und ihre Elemente auch eine Versionierung. Eine Version zu erstellen ist nicht nur einfach, Sie können auch Änderungen von einer Version in eine andere zusammenführen. So behalten Sie Snapshots mühelos im Blick oder erstellen eine Version für die Entwicklung und führen die Änderungen später in die Nicht-Entwicklungsversion zusammen. Versionierung, Vergleich und Zusammenführung in der Praxis finden Sie unter [Zusammenarbeit: Versionen, Vergleich und Freigabe](/de/get-started/tutorials/collaborate-versions-and-sharing/).

Tabellendaten haben einen eigenen Verlauf: Snapshots, die das Lakehouse bei jedem Schreibvorgang erstellt. Sie sind unter [Tabellen-Snapshots](/de/guides/data/table-snapshots/) beschrieben.

### Wiederherstellen und Halten über den KI-Assistenten oder MCP

Über den KI-Assistenten oder MCP stellt `dimension_versions` eine Dimensionsversion anhand ihrer `version_id` wieder her, hält sie fest und gibt sie wieder frei. `restore_project` setzt jede Dimension im Projekt auf ihr letztes Backup zurück, und jede `*_versions`-Auflistung (Schritte, UDFs, Workflows, Dimensionen, Projekte) zeigt die `version_id` jeder Version und ob sie gehalten wird. Eine `restore`-Aktion über ein beliebiges `*_versions`-Werkzeug oder die REST-API stellt das Element an Ort und Stelle wieder her: Lassen Sie das Ziel weg oder setzen Sie es auf das Element selbst. `project_upsert` kann ein gesperrtes Projekt entsperren und berücksichtigt `if_match`, sodass der Vorgang fehlschlägt, statt eine Änderung zu überschreiben, die seit Ihrem letzten Lesen des Projekts erfolgt ist.


## Projektzugriff verwalten

### Zugriffsarten

Die Projektsicherheit wurde auf drei Zugriffsarten vereinfacht:

* Alle Arbeitsbereichsmitglieder
* Nur bestimmte Mitglieder
* Nur bestimmte Sicherheitsgruppen

Die Projektsicherheit festzulegen ist einfach:

1. Öffnen Sie Analyze.
2. Wählen Sie „Projekte“ aus.
3. Klicken Sie auf das Bearbeiten-Symbol des Projekts, das Sie einschränken möchten.
4. Wählen Sie unter „Access Control“ die gewünschte Einschränkung.
5. Klicken Sie auf „Update“.

Nur ein Projekt-Architect oder ein Mandantenadministrator kann ändern, wer Zugriff auf ein Projekt hat: die Zugriffsart, die Mitglieder und Sicherheitsgruppen sowie die Datenfreigaben. Alle anderen sehen diese Bereiche schreibgeschützt, mit dem Hinweis „Only project Architects can change access.“


## Alle Arbeitsbereichsmitglieder

Der Zugriff „Alle Arbeitsbereichsmitglieder“ ist die einfachste Option, da er allen Mitgliedern des Workspace Zugriff gewährt und keine zusätzliche Zuweisung von Mitgliedern erfordert.


## Nur bestimmte Mitglieder

Die Zugriffseinstellung „Nur bestimmte Mitglieder“ erfordert, dass Sie jedes Mitglied dem Projekt zuweisen. So weisen Sie einem Projekt Mitglieder zu:

1. Öffnen Sie Analyze.
2. Wählen Sie in der oberen Menüleiste „Projekte“ aus.
3. Klicken Sie auf das Mitglieder-Symbol.
4. Gewähren Sie Mitgliedern Zugriff, indem Sie in der Spalte „Access“ das Kontrollkästchen neben ihrem Namen aktivieren.
5. Klicken Sie auf „Update“.

Bei Clouds mit sehr vielen Mitgliedern kann dieses Vorgehen mehr Aufwand bedeuten als gewünscht. Hier sind Sicherheitsgruppen nützlich.

<Aside>Um Mitglieder hinzuzufügen, müssen Sie Mitglied des Workspace sein.</Aside>


## Nur bestimmte Sicherheitsgruppen

Mit der Option „Nur bestimmte Sicherheitsgruppen“ können Sie bestimmten Sicherheitsgruppen die Berechtigung für den Zugriff auf das Konto erteilen. Da der Zugriff von der Zugehörigkeit zu einer oder mehreren Sicherheitsgruppen abhängt, ist die Verwaltung des Kontozugriffs für größere Gruppen deutlich einfacher. Das ist besonders nützlich in Kombination mit der automatischen Gruppenzuordnung per Single Sign-on. Wenn Sie die Gruppenzuweisungen der Mitglieder über Single Sign-on festlegen, können diese Gruppen auch implizit den Zugriff auf Projekte aktivieren und deaktivieren.

So bearbeiten Sie zugewiesene Gruppen:

1. Öffnen Sie Analyze.
2. Wählen Sie in der oberen Menüleiste „Projekte“ aus.
3. Klicken Sie auf das Sicherheitsgruppen-Symbol.
4. Gewähren Sie Sicherheitsgruppen Zugriff, indem Sie in der Spalte „Access“ das Kontrollkästchen neben ihrem Namen aktivieren.
5. Klicken Sie auf „Update“.


## Daten zwischen Projekten freigeben

Eine Datenfreigabe ermöglicht es einem Projekt, auf die Tabellen eines anderen Projekts zuzugreifen, zum Beispiel damit die Schritte [Import Project Table](/de/reference/workflow-steps/import/import-project-table/) und [Export Project Table](/de/reference/workflow-steps/export/export-project-table/) Daten zwischen ihnen übertragen können. Eine Freigabe wird von dem Projekt erteilt, dessen Daten freigegeben werden, und zwar für ein anderes Projekt:

1. Öffnen Sie das Projekt, dessen Daten Sie freigeben möchten, und wechseln Sie zu seiner Registerkarte **Startseite**.
2. Klicken Sie unter **Datenfreigabe-Verwaltung** auf **Neue Datenfreigabe**.
3. Wählen Sie unter **Projekt auswählen** das Projekt aus, das die Daten dieses Projekts verwenden darf.
4. Aktivieren Sie unter **Zulässige Vorgänge** die Option **Lesen**, **Schreiben** oder beide, und klicken Sie auf **Datenfreigabe hinzufügen**.

**Datenfreigabe löschen** entfernt eine Freigabe. Nur ein Projekt-Architect oder ein Mandantenadministrator kann die Datenfreigaben eines Projekts hinzufügen oder löschen.

Eine Freigabe wird einem Projekt erteilt und gilt daher nur für die Mitglieder und Workflows dieses Projekts:

- **Lesen** über eine Freigabe erfordert eine Rolle in dem Projekt, dem sie erteilt wurde. Wer dort keine Rolle hat, erhält über die Freigabe nichts.
- **Schreiben** über eine Freigabe, also das Erstellen einer Tabelle, eines Ordners oder einer Dimension im freigebenden Projekt, erfordert eine Freigabe mit **Schreiben** sowie die Rolle Manager oder Architect in Ihrem eigenen Projekt, also die Rolle, die dieselbe Änderung dort vornehmen könnte. Allen anderen wird mitgeteilt: „Writing to this project through a data share needs a write share from it to your project, and the Manager or Architect role in your project.“

Workflows werden unter der eigenen Identität ihres Projekts ausgeführt. Die Schritte Import Project Table und Export Project Table funktionieren daher über eine Freigabe, unabhängig davon, wer die Ausführung startet.


## Verschiedene Anzeigerollen festlegen

Oft erfordert ein Projekt mehrere Transformationen und Tabellen für Zwischenschritte, während das Endergebnis nur aus wenigen Tabellen besteht. Mitglieder müssen nicht immer alle Elemente des Projekts sehen, manchmal reicht das Endergebnis. PlaidCloud bietet Ihnen die Möglichkeit, verschiedene Anzeigerollen festzulegen, um die Ansicht übersichtlich zu halten und die Sichtbarkeit für jedes Mitglied zu steuern.

Es gibt drei integrierte Anzeigerollen: **Architect, Manager** und **Explorer**

Die Rolle **Architect** ist die einfachste, da sie vollständige Sichtbarkeit und Kontrolle über Projekte, Workflows, Tabellen, Variablen, Dateneditoren, Hierarchien und benutzerdefinierte Funktionen bietet.

Die Rollen **Manager** und **Explorer** haben keine festgelegten Zugriffsrechte, können aber individuell definiert werden. Mit anderen Worten: Sie können wählen, welche Elemente für jede Gruppe sichtbar sind.

<Aside>**Manager*** *und **Explorer** sind keine Sicherheitsgruppen. Sie bieten lediglich eine praktische Möglichkeit, Aufgaben und die Sichtbarkeit von Informationen zu trennen.</Aside>

Sie können alle Mitglieder zu einem **Architect** machen, wenn Sie die Sichtbarkeit aller Inhalte im Projekt für erforderlich halten. Andernfalls können Sie Mitglieder als **Manager** und/oder **Explorer** des Projekts festlegen und die Sichtbarkeit auf diese Weise steuern.

So legen Sie eine andere Rolle fest:

1. Öffnen Sie Analyze.
2. Wählen Sie „Projekte“ aus.
3. Klicken Sie auf das Mitglieder-Symbol.
4. Wählen Sie das Mitglied aus, dessen Rolle Sie ändern möchten.
5. Doppelklicken Sie in der Spalte „Role“ auf die aktuelle Rolle.
6. Wählen Sie die gewünschte Rolle aus.
7. Klicken Sie auf „Update“.


## Projektvariablen verwalten

Beim Ausführen eines Projekts oder Workflows kann es hilfreich sein, Variablen für wiederkehrende Aufgaben festzulegen, um Unübersichtlichkeit zu verringern und Zeit zu sparen. Diese Variablen funktionieren wie eine gewöhnliche algebraische Variable: Sie legen fest, was die Variable darstellt und welche Operation darauf folgen soll. In PlaidCloud können Sie diese Variablen auf Projektebene festlegen, was alle Workflows in diesem Projekt betrifft, oder auf Workflow-Ebene, was nur diesen einen Workflow betrifft.

So legen Sie eine Variable auf Projektebene fest:

1. Öffnen Sie Analyze.
2. Wählen Sie „Projekte“ aus.
3. Klicken Sie auf das Symbol „Manage Project Variables“.

In der Variablentabelle können Sie die Variablen und ihre aktuellen Werte anzeigen und bearbeiten. Außerdem können Sie neue Variablen hinzufügen oder vorhandene löschen, indem Sie auf die Schaltfläche „New Project Variable“ klicken.


## Ein Projekt kopieren

**Projekt kopieren** kopiert ein Projekt, entweder vollständig oder nur die ausgewählten Teile, in ein brandneues Projekt oder in ein bereits vorhandenes Projekt.

So kopieren Sie ein Projekt:

1. Öffnen Sie Analyze.
2. Wählen Sie „Projekte“ aus.
3. Wählen Sie das Projekt aus, das Sie kopieren möchten.
4. Klicken Sie auf die Schaltfläche **Aktionen** und wählen Sie **Projekt kopieren**.
5. Wählen Sie das Ziel, legen Sie fest, was übernommen werden soll und wie viele Daten, und klicken Sie auf **Projekt kopieren**.
6. Prüfen Sie die Zusammenfassung unter **Vor dem Kopieren prüfen** und klicken Sie auf **Kopieren starten**.

### Auswählen, was kopiert wird

Die Auswahlstruktur listet nach Typ auf, was das Projekt enthält: Workflows, Schritte, Tabellen, Dimensionen, Dateneditoren, benutzerdefinierte Funktionen. Lassen Sie alles aktiviert, um das gesamte Projekt zu kopieren, oder aktivieren Sie nur die gewünschten Teile.

Sie müssen nicht selbst herausfinden, wovon diese Teile abhängen. Alles, was Sie auswählen, bringt seine Abhängigkeiten mit: die Tabellen, die ein Schritt liest und schreibt, die Dimensionen, die er lädt oder auf die er umlegt, die benutzerdefinierten Funktionen, die er aufruft, sowie jeden Unter-Workflow und jedes Makro, das er aufruft. Die Sensoren eines Workflows werden mit dem Workflow kopiert.

**Kopierte Sensoren sind deaktiviert.** Auf der Kopie wird nichts ausgelöst, bis Sie jeden Sensor im Zielprojekt aktivieren. Ein Import, der doppelte Elemente überschreibt, fügt keinen zweiten Sensor hinzu, wenn der Ziel-Workflow ihn bereits hat.

### In ein neues Projekt kopieren

Geben Sie dem neuen Projekt einen Namen und eine ID. Die ID wird zu seinem Schemanamen und kann später nicht mehr geändert werden.

**Zeitpläne sind angehalten.** Wenn Sie ein ganzes Projekt in ein neues kopieren, werden die geplanten Ereignisse jedes Workflows angehalten übernommen, damit die Kopie sie nicht von selbst ausführt. Nach Abschluss des Kopiervorgangs listet eine Meldung die Ereignisse auf, die im Original aktiv waren. Um eines davon auf der Kopie auszuführen, wählen Sie es unter **Werkzeuge** > **Ereignisplaner** aus und klicken Sie auf **Ausgewählte aktivieren**. Siehe [Ein Ereignis anhalten](/de/administration/scheduled-events/event-scheduler/#ein-ereignis-anhalten).

### In ein vorhandenes Projekt kopieren

Wählen Sie das Ziel aus der Projektliste. Die Kopie wird dem Projekt hinzugefügt und ersetzt es nicht.

**Sie müssen das Ziel ändern dürfen.** Das Kopieren in ein Projekt, in dem Sie keine Rolle haben, wird abgelehnt, ebenso das Kopieren in ein Projekt, das gegen Änderungen gesperrt wurde. Dies wird geprüft, bevor etwas gelesen oder geschrieben wird, sodass ein abgelehnter Kopiervorgang das Ziel unverändert lässt. Ein Projekt kann außerdem nicht in sich selbst kopiert werden.

**Das Kopieren eines Projekts, das Zeilen einschränkt, erfordert einen Projekt-Architect.** Die Kopie ist ein neues Projekt ohne Einschränkung des [Zeilenzugriffs](/de/administration/access/managing-security-groups-and-assignments/#zeilenzugriff-verwalten), und die Kopie weist darauf hin: „This copy is not row-restricted.“ Richten Sie den Zeilenzugriff auf der Kopie ein, bevor Sie sie freigeben. Auch das Kopieren in ein vorhandenes Projekt, das Zeilen einschränkt, erfordert einen seiner Architects oder einen Mandantenadministrator.

**Das Ziel behält seine eigenen Einstellungen.** Name, ID, Datenverbindungsumgebung, Speicherstandards, Dokumentenkonto, Zugriffsart, Zugriffslisten und Zeilenzugriffsberechtigungen bleiben unverändert. Nur die ausgewählten Inhalte werden übernommen.

Ein Schritt, der auf **Project Default** steht, übernimmt diese Einstellung und nicht ein Konto: Nach dem Kopieren verwendet er den Standard des Zielprojekts und nicht den des Quellprojekts.

Wenn ein eingehendes Element dasselbe Element ist wie eines, das bereits im Ziel vorhanden ist, legen Sie fest, was geschieht:

- **Doppelte Elemente mit eingehenden Daten überschreiben**: Die eingehende Version ersetzt die im Ziel vorhandene.
- **Neue Kopie doppelter Elemente erstellen**: Das Ziel behält, was es hat, und das eingehende Element wird daneben hinzugefügt, wobei seinem Namen ` copy` angehängt wird, bei einem bereits vergebenen Namen zusätzlich ein Zähler.

Projekt- und Workflow-Variablen sind die Ausnahme von *Neue Kopie erstellen*: Eine Variable wird über ihren Namen identifiziert, daher lässt sich keine zweite Kopie hinzufügen, ohne sie in etwas umzubenennen, worauf nichts verweist. Wenn das Ziel bereits eine Variable definiert, die auch die Kopie enthält, bleibt der eigene Wert des Ziels erhalten, und die Kopie teilt Ihnen mit, welche Variablen sie unverändert gelassen hat. *Überschreiben* behandelt Variablen wie alles andere und ersetzt sie.

Dieser Abgleich erfolgt über die Identität und nicht über den Namen: Ein Element, das ursprünglich aus demselben Projekt stammt, wird als dasselbe Element erkannt, während zwei Elemente, die zufällig denselben Namen tragen, als verschiedene Elemente behandelt werden und anschließend beide vorhanden sind.

### Festlegen, wie viele Daten kopiert werden

| Modus | Was kopiert wird |
| --- | --- |
| **Nur Struktur** | Tabellen, Schritte und der Rest der Auswahl, ohne Zeilen. |
| **Vollständige Daten** | Die Zeilen jeder Tabelle, im selben Lakehouse und über Lakehouses hinweg. |
| **Stichprobe** | Bis zu der von Ihnen eingegebenen Anzahl von Zeilen aus jeder Tabelle, nur für ein neues Projekt. Die Zahl kann zwischen 1 und 1.000.000 liegen. |

Eine Tabelle mit Stichprobe enthält bis zu dieser Anzahl von Zeilen oder alle ihre Zeilen, wenn sie weniger hat.

### Die Kopie prüfen

Bevor etwas kopiert wird, fasst **Vor dem Kopieren prüfen** den Kopiervorgang zusammen: das Quellprojekt, das Ziel, den Datenmodus, die Anzahl der Tabellen und Ansichten, die Größe, die geschätzte Dauer, das Quell- und das Ziel-Lakehouse sowie alle Warnungen unter **Bitte beachten**. Klicken Sie auf **Kopieren starten**, um zu beginnen, oder auf **Abbrechen**, um zurückzugehen und die Auswahl zu ändern.

### Wer die Kopie sehen kann

Eine Kopie, die mit Daten erstellt wurde, ist privat und nur für die Person sichtbar, die sie erstellt hat. Geben Sie sie aus dem neuen Projekt frei, wenn Sie so weit sind. Eine Kopie eines Projekts mit Sicherheit auf Zeilenebene bleibt aus demselben Grund privat.

Zum Kopieren von Daten in ein vorhandenes Projekt ist Schreibzugriff auf dieses Projekt erforderlich.

### Kopierergebnisse

Wenn das Kopieren abgeschlossen ist, listet ein Fenster **Kopierergebnisse** das Ergebnis jeder Tabelle namentlich auf, bei fehlgeschlagenen Tabellen mit dem Grund. Klicken Sie auf **Fehlgeschlagene Tabellen wiederholen**, um nur diese Tabellen erneut zu kopieren; der Inhalt einer wiederholten Tabelle wird ersetzt. Sie werden per Nachricht und per E-Mail benachrichtigt, wenn ein Kopiervorgang abgeschlossen ist oder fehlschlägt. Die Ergebnisse können Sie über die Nachricht erneut öffnen oder später, indem Sie die Kopie auf der Registerkarte **Projekte** auswählen und im Menü **Aktionen** die Option **Import- oder Kopierergebnis anzeigen** wählen.

Die Ergebnisse bleiben an der Kopie, bis jemand sie verwirft. Sobald der Kopiervorgang abgeschlossen ist, klicken Sie auf **Ergebnis verwerfen**, um sie für alle zu entfernen, die das Projekt öffnen können. Im Projekt ändert sich nichts, aber die fehlgeschlagenen Tabellen können nicht mehr über das Fenster wiederholt werden. Das Verwerfen erfordert Bearbeitungszugriff auf das Projekt, und das Projekt darf nicht gesperrt sein.

### Referenzen aktualisieren

Die Workflow-Schritte eines Projekts verweisen auf Tabellen und andere Objekte innerhalb dieses Projekts. **Referenzen aktualisieren** schreibt diese Verweise so um, dass sie auf die Kopie statt auf das Original zeigen. Das ist fast immer gewünscht und deshalb standardmäßig aktiviert. Wenn Sie die Option deaktivieren, verweisen die kopierten Schritte weiterhin auf das Projekt, aus dem sie stammen.

<Aside>Das Kopieren läuft im Hintergrund. Ein Fortschrittsdialog zeigt, wie der Kopiervorgang seine Phasen durchläuft. Sie können auf **Im Hintergrund ausführen** klicken, um ihn zu schließen und weiterzuarbeiten: Die Projektliste wird automatisch aktualisiert, und Sie werden benachrichtigt, wenn der Kopiervorgang abgeschlossen ist.</Aside>

## Den Projektbericht anzeigen

Wenn ein Projekt oder Workflow dynamisch ist, wird es schwierig, eine ausführliche Dokumentation zu pflegen. Um dieses Problem zu lösen, kann PlaidCloud einen Bericht auf Projektebene erzeugen, der Workflows, Workflow-Schritte, benutzerdefinierte Transformationen, Variablen und Tabellen detailliert dokumentiert. Dieser Bericht wird bei Bedarf erzeugt und spiegelt den aktuellen Zustand des Projekts wider.

So laden Sie den Bericht herunter:

1. Öffnen Sie Analyze.
2. Wählen Sie „Projekte“ aus.
3. Klicken Sie auf das Berichtssymbol.
