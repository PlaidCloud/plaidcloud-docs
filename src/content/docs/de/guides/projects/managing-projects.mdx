## Suchen

Projekte suchen Sie mit dem Filterfeld unten links in der Hierarchie. Der Suchfilter durchsucht Projektnamen und Labels nach Treffern und zeigt die Ergebnisse in der darüberliegenden Hierarchie an.


## Neue Projekte erstellen

So erstellen Sie ein neues Projekt:

1. Öffnen Sie Analyze.
2. Wählen Sie in der oberen Menüleiste „Projekte“ aus.
3. Klicken Sie auf die Schaltfläche „Neues Projekt“.
4. Füllen Sie das Formular aus, einschließlich des Abschnitts „Access Control“.
5. Klicken Sie auf „Create“.

Das Projekt ist nun bereit, um Zugriffsberechtigungen zu aktualisieren, Eigentümer hinzuzufügen und Workflows zu erstellen.

<Aside>Standardmäßig ist das Projekt für alle Mitglieder des aktuellen Workspace zugänglich.</Aside>


## Ein Standard-Dokumentkonto festlegen

Wählen Sie auf der Projektstartseite neben **Verbindungsumgebung** ein **Standard-Dokumentkonto** für das Projekt aus – oder **Keine**, um es zu entfernen.

Innerhalb des Projekts führt jede Dateiauswahl zuerst **Projektstandard** auf, stellvertretend für das Konto, das das Projekt aktuell festgelegt hat. Der Eintrag verschwindet aus der Liste, sobald Sie das Projekt verlassen, sobald das Projekt keinen Standard festgelegt hat, sobald dieses Konto gelöscht wurde oder sobald Sie keinen Zugriff mehr darauf haben.

Ein neuer Dateischritt wählt Projektstandard vor, wenn das Projekt einen hat. Vorhandene Schritte werden nie umgeschrieben – jeder behält das Konto, mit dem er gespeichert wurde, bis Sie es selbst ändern, da ein Dokumentkonto eine Entscheidung pro Schritt ist, während ein Schritt normalerweise der Verbindungsumgebung des Projekts folgt.

Ein Schritt, der auf Projektstandard belassen wird, wird beim Ausführen auf das Konto aufgelöst, das dann der Standard des Projekts ist. Eine Änderung des Standards während einer Ausführung betrifft daher nur die Knoten, die noch nicht gestartet sind – genauso wie eine Änderung der Verbindungsumgebung. Wenn ein Schritt mit Projektstandard läuft und das Projekt keinen Standard festgelegt hat, schlägt die Ausführung fehl und nennt das Projekt, anstatt auf ein anderes Konto zurückzufallen.


## Einen Schritt auf eine Umgebung festlegen

Schritte folgen der [Verbindungsumgebung](/de/guides/projects/project-home/#daten--verbindungen) des Projekts, sodass das Umschalten des Projekts zwischen QA und Produktion alle Schritte mitnimmt. Ein Schritt, dessen Formular eine Einstellung **Umgebung** hat, bietet dort zwei Auswahlmöglichkeiten:

- **Projektumgebung** folgt der Verbindungsumgebung des Projekts. Behalten Sie diese Einstellung, sofern Sie keinen Grund für eine andere haben.
- **Feste Umgebung** ignoriert die Verbindungsumgebung des Projekts und verwendet immer die Umgebung, die Sie auswählen. Verwenden Sie sie nur für einen Schritt, der auf einer Umgebung bleiben muss, egal worauf das Projekt umgeschaltet wird, etwa um Referenzdaten aus der Produktion in einem auf QA gesetzten Projekt zu lesen. Das Warnsymbol erinnert daran, dass der Schritt einer Umschaltung nicht folgt.

Ein Schritt mit fester Umgebung fügt seinem Protokoll bei jeder Ausführung eine Warnung hinzu, wenn er auf einer anderen Umgebung als der des Projekts läuft. Existiert seine feste Umgebung nicht mehr, zum Beispiel bei einem aus einem anderen Workspace kopierten Schritt, schlägt der Schritt fehl und meldet das, anstatt woanders zu laufen.

ERP-Buchungsschritte verwenden immer die Umgebung des Projekts, daher ist **Feste Umgebung** für sie nicht verfügbar.

Die Standardumgebung kann nicht gelöscht werden, und eine andere Umgebung kann nicht gelöscht werden, solange ein Projekt sie verwendet, ein Schritt sie als feste Umgebung hat oder ein Agent sie bedient. Die Meldung nennt, was sie noch verwendet: Was Sie sehen dürfen, wird namentlich genannt, der Rest wird gezählt.


## Versionsverlauf

Jedes Objekt in einem Projekt – ein Schritt, eine UDF, ein Workflow, eine Dimension, ein gespeichertes Layout, ein Dokument- oder Daten-Editor und die Einstellungen des Projekts selbst – wird durch Sicherungen im Versionsverlauf abgedeckt. Eine Sicherung wird nicht bei jedem einzelnen Speichern erstellt. Stattdessen wird eine Sicherung des stabilen Zustands erstellt, sobald ein Objekt 30 Sekunden lang nicht erneut gespeichert wurde. Eine Folge von Änderungen – mehrere Speichervorgänge in rascher Folge – erzeugt eine einzige Version mit dem Endergebnis, nicht eine Version pro Speichern. Das Speichern wird nie durch das Warten auf eine Sicherung verlangsamt: Der Countdown und die Sicherung selbst laufen beide im Hintergrund. Wenn Sie sofort eine Version benötigen, erfassen Sie mit **Back up now** den aktuellen Zustand unmittelbar und warten, bis der Vorgang abgeschlossen ist – verfügbar in der Benutzeroberfläche, in der API und als `*_versions`-MCP-Aktion `backup`. Der Versionsverlauf ist in jedem Tarif verfügbar, auch in Free.

Frühere Versionen unterstützen die Wiederherstellung zu einem bestimmten Zeitpunkt: Sie stellen ein Objekt auf eine frühere Version zurück. In einem gesperrten Projekt wird die Wiederherstellung abgelehnt, genau wie jede andere Änderung dort.

Eine Version wird an Ort und Stelle wiederhergestellt. Die Wiederherstellung einer Version eines Projekts, einer Dimension, einer benutzerdefinierten Funktion, eines Schritts, eines Workflows oder eines Daten-Editors ersetzt genau dieses Element, und die Angabe eines anderen Elements als Ziel wird abgelehnt – zum Beispiel mit „A project version is restored in place. Leave the target out, or set it to this project.“ Die Wiederherstellung ist eine Änderung des Elements und erfordert daher dieselbe Rolle wie dessen Bearbeitung. Bei einem Projekt, das [Zeilen einschränkt](/de/administration/access/managing-security-groups-and-assignments/#wer-ein-projekt-mit-zeileneinschränkung-ändern-darf), erfordert die Wiederherstellung des Projekts oder einer Dimension, die eine eingeschränkte Spalte liest, einen Projekt-Architect. Um alte Tabellendaten als separate Tabelle zurückzuholen, stellen Sie einen [Tabellen-Snapshot](/de/guides/data/table-snapshots/) in einer neuen Tabelle wieder her.

Zusätzlich zu dieser automatischen Nachverfolgung unterstützen Projekte und ihre Elemente auch Versionierung. Das Erstellen einer Version ist nicht nur einfach, Sie können auch Änderungen von einer Version in eine andere zusammenführen. So behalten Sie Snapshots auf einfache Weise im Blick oder erstellen eine Version für die Entwicklung und führen deren Änderungen später in die Nicht-Entwicklungsversion zusammen. Versionierung, Vergleich und Zusammenführung in der Praxis finden Sie unter [Zusammenarbeit: Versionen, Vergleich und Teilen](/de/get-started/tutorials/collaborate-versions-and-sharing/).

Tabellendaten haben einen eigenen Verlauf – Snapshots, die das Lakehouse bei jedem Schreibvorgang erstellt – der unter [Tabellen-Snapshots](/de/guides/data/table-snapshots/) behandelt wird.

### Wiederherstellen und Halten über den KI-Assistenten oder MCP

Über den KI-Assistenten oder MCP stellt `dimension_versions` eine Dimensionsversion anhand ihrer `version_id` wieder her, hält sie und gibt sie frei, und `restore_project` setzt jede Dimension im Projekt auf ihre letzte Sicherung zurück. Jede `*_versions`-Auflistung (Schritte, UDFs, Workflows, Dimensionen, Projekte) zeigt die `version_id` jeder Version und ob sie gehalten wird. Ein `restore` über ein beliebiges `*_versions`-Tool oder die REST-API stellt das Element an Ort und Stelle wieder her: Lassen Sie das Ziel weg oder setzen Sie es auf das Element selbst. `project_upsert` kann ein gesperrtes Projekt entsperren und berücksichtigt `if_match`, sodass der Vorgang fehlschlägt, anstatt eine Änderung zu überschreiben, die seit Ihrem letzten Lesen des Projekts vorgenommen wurde.


## Projektzugriff verwalten

### Zugriffsarten

Die Projektsicherheit wurde auf drei Zugriffsarten vereinfacht:

* Alle Arbeitsbereichsmitglieder
* Nur bestimmte Mitglieder
* Nur bestimmte Sicherheitsgruppen

Die Projektsicherheit ist einfach einzurichten:

1. Öffnen Sie Analyze.
2. Wählen Sie „Projekte“ aus.
3. Klicken Sie auf das Bearbeitungssymbol des Projekts, das Sie einschränken möchten.
4. Wählen Sie unter „Access Control“ die gewünschte Einschränkung aus.
5. Klicken Sie auf „Update“.

Nur ein Projekt-Architect oder ein Mandantenadministrator kann ändern, wer Zugriff auf ein Projekt hat – seine Zugriffsart, die Mitglieder und Sicherheitsgruppen darin und seine Datenfreigaben. Alle anderen sehen diese Bereiche schreibgeschützt mit dem Hinweis „Only project Architects can change access.“


## Alle Arbeitsbereichsmitglieder

Der Zugriff „Alle Arbeitsbereichsmitglieder“ ist die einfachste Option, da er allen Mitgliedern des Workspace Zugriff gewährt und keine zusätzliche Zuweisung von Mitgliedern erfordert.


## Nur bestimmte Mitglieder

Die Zugriffseinstellung „Nur bestimmte Mitglieder“ erfordert die Zuweisung jedes Mitglieds zum Projekt. So weisen Sie einem Projekt Mitglieder zu:

1. Öffnen Sie Analyze.
2. Wählen Sie in der oberen Menüleiste „Projekte“ aus.
3. Klicken Sie auf das Mitgliedersymbol.
4. Gewähren Sie Mitgliedern Zugriff, indem Sie in der Spalte „Access“ das Kontrollkästchen neben ihrem Namen aktivieren.
5. Klicken Sie auf „Update“.

Bei Clouds mit sehr vielen Mitgliedern erfordert dieser Ansatz oft mehr Aufwand als gewünscht, und hier sind Sicherheitsgruppen nützlich.

<Aside>Um Mitglieder hinzuzufügen, müssen Sie Mitglied des Workspace sein.</Aside>


## Nur bestimmte Sicherheitsgruppen

Die Option „Nur bestimmte Sicherheitsgruppen“ ermöglicht es, bestimmten Sicherheitsgruppen die Berechtigung für den Zugriff auf das Konto zuzuweisen. Da die Zugriffsbeschränkungen auf der Zugehörigkeit zu einer oder mehreren Sicherheitsgruppen beruhen, ist die Verwaltung des Kontozugriffs für größere Gruppen deutlich einfacher. Das ist besonders nützlich in Kombination mit der automatischen Gruppenzuordnung per Single Sign-on. Wenn Sie die Gruppenzuweisungen der Mitglieder per Single Sign-on festlegen, können diese Gruppen den Zugriff auf Projekte auch implizit aktivieren und deaktivieren.

So bearbeiten Sie zugewiesene Gruppen:

1. Öffnen Sie Analyze.
2. Wählen Sie in der oberen Menüleiste „Projekte“ aus.
3. Klicken Sie auf das Sicherheitsgruppensymbol.
4. Gewähren Sie Sicherheitsgruppen Zugriff, indem Sie in der Spalte „Access“ das Kontrollkästchen neben ihrem Namen aktivieren.
5. Klicken Sie auf „Update“.


## Daten zwischen Projekten teilen

Eine Datenfreigabe ermöglicht es einem Projekt, auf die Tabellen eines anderen Projekts zuzugreifen – zum Beispiel, damit die Schritte [Import Project Table](/de/reference/workflow-steps/import/import-project-table/) und [Export Project Table](/de/reference/workflow-steps/export/export-project-table/) Daten zwischen ihnen verschieben können. Eine Freigabe wird von dem Projekt erteilt, dessen Daten geteilt werden, und zwar an ein anderes Projekt:

1. Öffnen Sie das Projekt, dessen Daten Sie teilen möchten, und wechseln Sie zu seiner [Projektstartseite](/de/guides/projects/project-home/).
2. Öffnen Sie **Access & sharing**. Klicken Sie unter **Datenfreigaben** auf **Neue Datenfreigabe**.
3. Wählen Sie unter **Projekt auswählen** das Projekt aus, das die Daten dieses Projekts verwenden darf.
4. Aktivieren Sie unter **Zulässige Vorgänge** **Lesen**, **Schreiben** oder beides, und klicken Sie auf **Datenfreigabe hinzufügen**.

**Datenfreigabe löschen** entfernt eine Freigabe. Nur ein Projekt-Architect oder ein Mandantenadministrator kann die Datenfreigaben eines Projekts hinzufügen oder löschen.

Eine Freigabe wird an ein Projekt erteilt und gilt daher nur für die Mitglieder und Workflows dieses Projekts:

- **Lesen** über eine Freigabe erfordert eine Rolle in dem Projekt, an das sie erteilt wurde. Wer dort keine Rolle hat, erhält über die Freigabe nichts.
- **Schreiben** über eine Freigabe – das Erstellen einer Tabelle, eines Ordners oder einer Dimension im freigebenden Projekt – erfordert eine Freigabe mit **Schreiben** und die Rolle Manager oder Architect in Ihrem eigenen Projekt, also die Rolle, die dieselbe Änderung dort vornehmen könnte. Allen anderen wird mitgeteilt: „Writing to this project through a data share needs a write share from it to your project, and the Manager or Architect role in your project.“

Workflows laufen mit der eigenen Identität ihres Projekts, daher funktionieren die Schritte Import Project Table und Export Project Table über eine Freigabe, unabhängig davon, wer die Ausführung startet.


## Unterschiedliche Anzeigerollen festlegen

Oft erfordert ein Projekt mehrere Transformationen und Tabellen für Zwischenschritte, während das Endergebnis nur aus wenigen Tabellen besteht. Mitglieder müssen nicht immer alle Elemente des Projekts sehen, manchmal nur das Endprodukt. PlaidCloud bietet Ihnen die Möglichkeit, unterschiedliche Anzeigerollen festzulegen, um die Übersicht zu verbessern und die Sichtbarkeit für jedes Mitglied zu steuern.

Es gibt drei integrierte Anzeigerollen: **Architect, Manager** und **Explorer**

Die Rolle **Architect** ist die einfachste, da sie volle Sichtbarkeit und Kontrolle über Projekte, Workflows, Tabellen, Variablen, Daten-Editoren, Hierarchien und benutzerdefinierte Funktionen ermöglicht.

Die Rollen **Manager** und **Explorer** haben keine festgelegten Zugriffsrechte, können aber benutzerdefiniert festgelegt werden. Mit anderen Worten: Sie können wählen, welche Elemente für jede Gruppe sichtbar sind.

<Aside>**Manager*** *und **Explorer** sind keine Sicherheitsgruppen, sondern bieten nur eine bequeme Möglichkeit, Aufgaben und die Sichtbarkeit von Informationen zu trennen.</Aside>

Sie können alle zu einem **Architect** machen, wenn Sie die Sichtbarkeit von allem im Projekt für erforderlich halten. Andernfalls können Sie Mitglieder als Projektmitglieder mit der Rolle **Manager** und/oder **Explorer** festlegen und die Sichtbarkeit auf diese Weise steuern.

So legen Sie eine andere Rolle fest:

1. Öffnen Sie Analyze.
2. Wählen Sie „Projekte“ aus.
3. Klicken Sie auf das Mitgliedersymbol.
4. Wählen Sie das Mitglied aus, dessen Rolle Sie ändern möchten.
5. Doppelklicken Sie in der Spalte „Role“ auf die aktuelle Rolle.
6. Wählen Sie die gewünschte Rolle aus.
7. Klicken Sie auf „Update“.


## Projektvariablen verwalten

Beim Ausführen eines Projekts oder Workflows kann es nützlich sein, Variablen für wiederkehrende Aufgaben festzulegen, um Unübersichtlichkeit zu verringern und Zeit zu sparen. Diese Variablen funktionieren wie eine gewöhnliche algebraische Variable: Sie legen fest, was die Variable darstellt und welche Operation darauf folgen soll. In PlaidCloud können Sie diese Variablen auf Projektebene festlegen, was alle Workflows in diesem Projekt betrifft, oder auf Workflow-Ebene, was nur diesen einen Workflow betrifft.

So legen Sie eine Variable auf Projektebene fest:

1. Öffnen Sie Analyze.
2. Wählen Sie „Projekte“ aus.
3. Klicken Sie auf das Symbol „Manage Project Variables“.

In der Variablentabelle können Sie die Variablen ansehen und die aktuellen Werte anzeigen oder bearbeiten. Sie können außerdem neue Variablen hinzufügen oder vorhandene löschen, indem Sie auf die Schaltfläche „New Project Variable“ klicken.


## Ein Projekt kopieren

**Projekt kopieren** kopiert ein Projekt – ganz oder nur die ausgewählten Teile – in ein brandneues Projekt oder in ein bereits vorhandenes Projekt.

So kopieren Sie ein Projekt:

1. Öffnen Sie Analyze.
2. Wählen Sie „Projekte“ aus.
3. Wählen Sie das Projekt aus, das Sie kopieren möchten.
4. Klicken Sie auf die Schaltfläche **Aktionen** und wählen Sie **Projekt kopieren**.
5. Wählen Sie das Ziel aus, legen Sie fest, was übernommen und welche Daten kopiert werden sollen, und klicken Sie auf **Projekt kopieren**.
6. Prüfen Sie die Zusammenfassung unter **Vor dem Kopieren prüfen** und klicken Sie auf **Kopieren starten**.

### Auswählen, was kopiert wird

Die Auswahlstruktur listet nach Typ auf, was das Projekt enthält – Workflows, Schritte, Tabellen, Dimensionen, Daten-Editoren, benutzerdefinierte Funktionen. Lassen Sie alles aktiviert, um das gesamte Projekt zu kopieren, oder aktivieren Sie nur die gewünschten Teile.

Sie müssen nicht selbst ermitteln, wovon diese Teile abhängen. Alles, was Sie aktivieren, bringt seine Abhängigkeiten mit: die Tabellen, die ein Schritt liest und schreibt, die Dimensionen, die er lädt oder auf die er umlegt, die benutzerdefinierten Funktionen, die er aufruft, sowie jeden Sub-Workflow oder jedes Makro, das er aufruft. Die Sensoren eines Workflows kommen mit dem Workflow.

**Kopierte Sensoren sind deaktiviert.** Auf der Kopie wird nichts ausgelöst, bis Sie jeden Sensor im Zielprojekt einschalten. Ein Import, der doppelte Elemente überschreibt, fügt keinen zweiten Sensor hinzu, wenn der Ziel-Workflow ihn bereits hat.

### In ein neues Projekt kopieren

Geben Sie dem neuen Projekt einen Namen und eine ID. Die ID wird zu seinem Schemanamen und kann später nicht mehr geändert werden.

**Zeitpläne sind pausiert.** Wenn Sie ein ganzes Projekt in ein neues kopieren, werden die geplanten Ereignisse jedes Workflows pausiert übernommen, damit die Kopie sie nicht von selbst ausführt. Wenn die Kopie abgeschlossen ist, listet eine Nachricht die Ereignisse auf, die im Original aktiv waren. Um eines auf der Kopie auszuführen, wählen Sie es unter **Werkzeuge** > **Ereignisplaner** aus und klicken Sie auf **Ausgewählte aktivieren** – siehe [Ein Ereignis pausieren](/de/administration/scheduled-events/event-scheduler/#ein-ereignis-anhalten).

### In ein vorhandenes Projekt kopieren

Wählen Sie das Ziel aus der Projektliste aus. Die Kopie wird dem Projekt hinzugefügt, anstatt es zu ersetzen.

**Sie müssen das Ziel ändern können.** Eine Kopie in ein Projekt, in dem Sie keine Rolle haben, wird abgelehnt, ebenso eine Kopie in ein Projekt, das gegen Änderungen gesperrt wurde – dies wird geprüft, bevor etwas gelesen oder geschrieben wird, sodass eine abgelehnte Kopie das Ziel unberührt lässt. Ein Projekt kann außerdem nicht in sich selbst kopiert werden.

**Das Kopieren eines Projekts, das Zeilen einschränkt, erfordert einen Projekt-Architect.** Die Kopie ist ein neues Projekt ohne Einschränkung des [Zeilenzugriffs](/de/administration/access/managing-security-groups-and-assignments/#zeilenzugriff-verwalten), und die Kopie weist darauf hin: „This copy is not row-restricted.“ Richten Sie den Zeilenzugriff auf der Kopie ein, bevor Sie sie teilen. Das Kopieren in ein vorhandenes Projekt, das Zeilen einschränkt, erfordert ebenfalls einen seiner Architects oder einen Mandantenadministrator.

**Das Ziel behält seine eigenen Einstellungen.** Name, ID, Datenverbindungsumgebung, Speicherstandards, Dokumentkonto, Zugriffsart, Zugriffslisten und Zeilenzugriffsberechtigungen bleiben unverändert. Es werden nur die von Ihnen ausgewählten Inhalte übernommen.

Ein Schritt, der auf **Projektstandard** gesetzt ist, überträgt diese Einstellung und kein Konto – nach dem Kopieren wird sie auf den Standard aufgelöst, den das Zielprojekt hat, nicht auf den, den es in der Quelle hatte.

Wenn ein eingehendes Element dasselbe Element ist wie eines, das bereits im Ziel vorhanden ist, legen Sie fest, was geschieht:

- **Overwrite duplicate items with incoming data** – Doppelte Elemente mit eingehenden Daten überschreiben: Die eingehende Version ersetzt die im Ziel.
- **Create new copy of duplicate items** – Neue Kopie doppelter Elemente erstellen: Das Ziel behält, was es hat, und das eingehende Element wird daneben hinzugefügt, wobei ` copy` an seinen Namen angehängt wird, plus ein Zähler, falls dieser Name ebenfalls vergeben ist.

Projekt- und Workflow-Variablen sind die Ausnahme von *Neue Kopie erstellen*: Eine Variable wird anhand ihres Namens identifiziert, daher gibt es keine Möglichkeit, eine zweite Kopie hinzuzufügen, ohne sie in etwas umzubenennen, worauf nichts verweist. Wenn das Ziel bereits eine Variable definiert, die auch die Kopie enthält, bleibt der eigene Wert des Ziels erhalten, und die Kopie teilt Ihnen mit, welche Variablen sie unberührt gelassen hat. *Überschreiben* behandelt Variablen wie alles andere und ersetzt sie.

Dieser Abgleich erfolgt nach Identität, nicht nach Name – ein Element, das ursprünglich aus demselben Projekt stammt, wird als dasselbe Element erkannt, während zwei Elemente, die nur zufällig denselben Namen haben, als verschiedene Elemente behandelt werden und danach beide vorhanden sind.

### Festlegen, wie viele Daten kopiert werden

Unter **Data to copy** bestimmen zwei Einstellungen, welche Daten mit Ihrer Auswahl übernommen werden.

**Tabellendaten** legt fest, wie viele Zeilen jeder Tabelle kopiert werden:

| Auswahl | Was kopiert wird |
| --- | --- |
| **No table data** | Tabellen, Schritte und der Rest der Auswahl, ohne Zeilen. Das ist der Standard. |
| **Vollständig** | Die Zeilen jeder Tabelle, auf demselben Lakehouse und lakehouseübergreifend. |
| **Stichprobe** | Bis zu der Anzahl **Zeilen pro Tabelle**, die Sie eingeben, nur für ein neues Projekt. Die Zahl kann 1 bis 1.000.000 betragen. |

Eine Stichprobentabelle enthält bis zu dieser Anzahl Zeilen oder alle ihre Zeilen, wenn sie weniger hat. Eine Kopie mit **Vollständig** oder **Stichprobe** kopiert mehrere Tabellen gleichzeitig, sodass ein Projekt mit vielen Tabellen schneller fertig ist.

**Copy dimension members** kopiert die Elemente jeder Dimension in der Auswahl, unabhängig davon, welche **Tabellendaten**-Auswahl Sie treffen. Die Option ist standardmäßig aktiviert, sodass eine Kopie ohne Tabellendaten dennoch mit gefüllten Dimensionen ankommt und schnell erstellt ist. Deaktivieren Sie sie, um die Dimensionen ohne ihre Elemente zu kopieren.

Über die REST-API (`POST /rest/v1/analyze/project/copy`) oder das MCP-Tool `project_copy` setzen Sie `data_mode` auf `structure`, `full` oder `sample` und `dimension_members` auf `true` oder `false`. Wenn Sie `dimension_members` weglassen, werden Elemente nur kopiert, wenn auch Tabellenzeilen kopiert werden. `project_copy` gibt außerdem die Warnungen der Kopie zurück, etwa ERP-Schreibautorisierungen, die nicht kopiert wurden.

### Die Kopie prüfen

Bevor etwas kopiert wird, fasst **Vor dem Kopieren prüfen** die Kopie zusammen: das Projekt, aus dem sie stammt, wohin sie geht, die Auswahl unter **Tabellendaten**, ob **Dimensionselemente** enthalten sind, die Anzahl der Tabellen und Ansichten, die Größe, eine geschätzte Dauer, das Quell- und das Ziel-Lakehouse sowie alle Warnungen unter **Bitte beachten**. Klicken Sie auf **Kopieren starten**, um zu beginnen, oder auf **Abbrechen**, um zurückzugehen und die Auswahl zu ändern.

### Wer die Kopie sehen kann

Eine Kopie, die mit Daten erstellt wurde – Tabellenzeilen, Dimensionselemente oder beides – ist privat für die Person, die sie erstellt hat. Teilen Sie sie vom neuen Projekt aus, wenn Sie bereit sind. Eine Kopie eines Projekts mit Sicherheit auf Zeilenebene bleibt aus demselben Grund privat.

Das Kopieren von Daten in ein vorhandenes Projekt erfordert Schreibzugriff auf dieses Projekt.

### ERP-Schreibautorisierungen in der Kopie

Eine neue Kopie, die für Sie privat ist, behält die [ERP-Schreibautorisierungen](/de/guides/workflows/run-a-workflow/#das-projekt-zum-buchen-autorisieren) des Quellprojekts, sodass Sie ihre Buchungs-Workflows testen können, ohne die Kopie erneut zu autorisieren. Das gilt für jede Kopie in ein neues Projekt, die mit Tabellendaten (**Vollständig** oder **Stichprobe**), Dimensionselementen oder beidem erstellt wird. Die Autorisierungen werden kopiert, wenn:

- Sie ein Architect des Quellprojekts oder ein Workspace-Administrator sind.
- Sie die Kopie selbst erstellen, nicht über einen Agenten oder ein Dienstkonto.

Jede Autorisierung wird nur kopiert, wenn Sie sie heute selbst erteilen könnten: Ihre Verbindung und Umgebung existieren noch, und Sie haben Schreibzugriff auf die Verbindung. Die kopierten Autorisierungen werden als Ihre erfasst.

**Die Kopie kommt im Modus Simulate an.** Wenn der **ERP-Buchungsmodus** des Quellprojekts Live ist, wird der der Kopie auf Simulate gesetzt, sodass ihre Workflows aufbauen und prüfen, was sie buchen würden, ohne das ERP zu kontaktieren. Eine Quelle mit Simulate oder Off behält diese Einstellung. Wenn Sie bereit sind, von der Kopie aus tatsächlich zu buchen, setzen Sie den **ERP-Buchungsmodus** unter **ERP-Buchung** auf der Startseite der Kopie auf Live – siehe [Einen Buchungsmodus wählen](/de/guides/workflows/run-a-workflow/#einen-buchungsmodus-wählen). Zeitpläne und Sensoren kommen weiterhin pausiert und deaktiviert an, wie oben beschrieben, sodass auf der Kopie nichts läuft, bis Sie es einschalten.

Eine Kopie in ein vorhandenes Projekt oder eine ohne Tabellendaten und ohne Dimensionselemente beginnt ohne die Autorisierungen der Quelle. Autorisieren Sie sie unter **ERP-Buchung** > **ERP-Schreibautorisierungen** auf ihrer Startseite, bevor sie bucht.

**Kopierergebnisse** berichtet, was geschehen ist, zum Beispiel „2 ERP write authorizations copied; ERP posting is in Simulate“, sowie wie viele nicht kopiert wurden.

### Kopierergebnisse

Wenn die Kopie abgeschlossen ist, fasst ein Fenster **Kopierergebnisse** die kopierten Tabellen und Dimensionselemente zusammen und listet jede Tabelle und Dimension mit Namen und Ergebnis auf – **Kopiert**, **Mit Änderungen kopiert**, **Stichprobe**, **Übersprungen** oder **Fehlgeschlagen** – sowie dem Grund für jedes übersprungene oder fehlgeschlagene Element. Klicken Sie auf **Retry failed items**, um die fehlgeschlagenen Tabellen und Dimensionen erneut zu kopieren; ihr aktueller Inhalt in der Kopie wird ersetzt. Sie werden per Nachricht und per E-Mail benachrichtigt, wenn eine Kopie abgeschlossen ist oder fehlschlägt, und Sie können die Ergebnisse über die Nachricht erneut öffnen oder später, indem Sie die Kopie auf der Registerkarte **Projekte** auswählen und im Menü **Aktionen** **Import- oder Kopierergebnis anzeigen** wählen.

Die Ergebnisse bleiben an der Kopie, bis jemand sie verwirft. Sobald die Kopie abgeschlossen ist, klicken Sie auf **Ergebnis verwerfen**, um sie für alle zu entfernen, die das Projekt öffnen können. Im Projekt ändert sich nichts, aber seine fehlgeschlagenen Elemente können nicht mehr aus dem Fenster wiederholt werden. Das Verwerfen erfordert Bearbeitungszugriff auf das Projekt, und das Projekt darf nicht gesperrt sein.

### Referenzen aktualisieren

Die Workflow-Schritte eines Projekts verweisen auf Tabellen und andere Objekte innerhalb dieses Projekts. **Referenzen aktualisieren** schreibt diese Verweise so um, dass sie auf die Kopie statt auf das Original zeigen – was fast immer gewünscht ist und der Grund dafür, dass die Option standardmäßig aktiviert ist. Wenn Sie sie deaktivieren, zeigen die kopierten Schritte weiterhin auf das Projekt, aus dem sie stammen.

<Aside>Das Kopieren läuft im Hintergrund. Ein Fortschrittsdialog zeigt, wie die Kopie ihre Phasen durchläuft. Sie können auf **Im Hintergrund ausführen** klicken, um ihn zu schließen und weiterzuarbeiten – die Projektliste wird automatisch aktualisiert, und Sie werden benachrichtigt, wenn die Kopie abgeschlossen ist.</Aside>

## Den Projektbericht anzeigen

Wenn ein Projekt oder Workflow dynamisch ist, wird es zur Herausforderung, eine ausführliche Dokumentation zu pflegen. Um dieses Problem zu lösen, bietet PlaidCloud die Möglichkeit, einen Bericht auf Projektebene zu erzeugen, der Workflows, Workflow-Schritte, benutzerdefinierte Transformationen, Variablen und Tabellen ausführlich dokumentiert. Dieser Bericht wird bei Bedarf erzeugt und spiegelt den aktuellen Zustand des Projekts wider.

So laden Sie den Bericht herunter:

1. Öffnen Sie Analyze.
2. Wählen Sie „Projekte“ aus.
3. Klicken Sie auf das Berichtssymbol.
