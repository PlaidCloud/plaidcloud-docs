## Suchen

Projekte suchen Sie über das Filterfeld unten links in der Hierarchie. Der Suchfilter durchsucht Projektnamen und Beschriftungen nach Treffern und zeigt die Ergebnisse in der Hierarchie darüber an.


## Neue Projekte erstellen

So erstellen Sie ein neues Projekt:

1. Öffnen Sie Analyze
2. Wählen Sie in der oberen Menüleiste „Projekte“ aus
3. Klicken Sie auf die Schaltfläche „Neues Projekt“
4. Füllen Sie das Formular einschließlich des Abschnitts „Access Control“ aus
5. Klicken Sie auf „Erstellen“

Das Projekt ist jetzt bereit, um Zugriffsberechtigungen anzupassen, Eigentümer hinzuzufügen und Workflows zu erstellen.

<Aside>Standardmäßig ist das Projekt für alle Mitglieder des aktuellen Workspace zugänglich</Aside>


## Ein Standard-Dokumentenkonto festlegen

Wählen Sie auf der Startseite des Projekts neben **Verbindungsumgebung** ein **Standard-Dokumentkonto** für das Projekt aus – oder **Keine**, um die Auswahl zu entfernen.

Innerhalb des Projekts führt jede Dateiauswahl **Projektstandard** an erster Stelle auf, stellvertretend für das Konto, das im Projekt gerade festgelegt ist. Der Eintrag verschwindet aus der Liste, sobald Sie das Projekt verlassen, sobald im Projekt kein Standard festgelegt ist, sobald dieses Konto gelöscht wurde oder sobald Sie keinen Zugriff mehr darauf haben.

Ein neuer Dateischritt wählt Projektstandard vor, wenn das Projekt einen Standard hat. Bestehende Schritte werden nie umgeschrieben – jeder behält das Konto, mit dem er gespeichert wurde, bis Sie es selbst ändern, denn ein Dokumentenkonto ist anders als die Verbindungsumgebung eine Auswahl pro Schritt.

Ein Schritt, der auf Projektstandard steht, wird bei seiner Ausführung zu dem Konto aufgelöst, das dann der Standard des Projekts ist. Wenn Sie den Standard während einer Ausführung ändern, wirkt sich das daher nur auf die Knoten aus, die noch nicht gestartet sind – genau wie beim Ändern der Verbindungsumgebung. Läuft ein Schritt auf Projektstandard und ist im Projekt kein Standard festgelegt, schlägt die Ausführung fehl und nennt das Projekt, statt auf ein anderes Konto auszuweichen.


## Versionsverlauf

Jedes Objekt in einem Projekt – ein Schritt, eine UDF, ein Workflow, eine Dimension, ein gespeichertes Layout, ein Dokument- oder Dateneditor und die Einstellungen des Projekts selbst – wird durch Sicherungen des Versionsverlaufs erfasst. Eine Sicherung wird nicht bei jedem einzelnen Speichern erstellt; stattdessen wird, sobald ein Objekt 30 Sekunden lang nicht erneut gespeichert wurde, eine Sicherung seines abgeschlossenen Zustands erstellt. Eine Reihe von Bearbeitungen – mehrere Speichervorgänge kurz hintereinander – ergibt eine einzige Version mit dem Endergebnis, nicht eine Version pro Speichervorgang. Das Speichern wird nie durch das Warten auf eine Sicherung verlangsamt: Der Countdown und die Sicherung selbst laufen beide im Hintergrund. Wenn Sie sofort eine Version benötigen, verwenden Sie **Back up now**, um den aktuellen Zustand sofort zu erfassen und auf den Abschluss zu warten – verfügbar in der Benutzeroberfläche, in der API und als `*_versions`-MCP-Aktion `backup`. Der Versionsverlauf ist in jedem Tarif verfügbar, auch in Free.

Frühere Versionen ermöglichen eine Wiederherstellung zu einem bestimmten Zeitpunkt: Sie stellen ein Objekt auf eine frühere Version zurück. Innerhalb eines gesperrten Projekts wird das Wiederherstellen abgelehnt, wie jede andere Änderung dort.

Eine Version wird an Ort und Stelle wiederhergestellt. Das Wiederherstellen einer Version eines Projekts, einer Dimension, einer benutzerdefinierten Funktion, eines Schritts, eines Workflows oder eines Dateneditors ersetzt genau dieses Element; wird ein anderes Element als Ziel angegeben, wird dies abgelehnt – zum Beispiel: „Eine Projektversion wird an Ort und Stelle wiederhergestellt. Lassen Sie das Ziel weg oder setzen Sie es auf dieses Projekt.“ Das Wiederherstellen ist eine Änderung am Element und erfordert daher dieselbe Rolle wie das Bearbeiten; in einem Projekt, das [Zeilen einschränkt](/de/administration/access/managing-security-groups-and-assignments/#wer-ein-projekt-mit-zeileneinschränkung-ändern-darf), erfordert das Wiederherstellen des Projekts oder einer Dimension, die eine eingeschränkte Spalte liest, einen Architect des Projekts. Um alte Tabellendaten als separate Tabelle zurückzuholen, stellen Sie einen [Tabellen-Snapshot](/de/guides/data/table-snapshots/) in einer neuen Tabelle wieder her.

Zusätzlich zu dieser automatischen Nachverfolgung lassen sich Projekte und ihre Elemente auch versionieren. Eine Version ist nicht nur einfach erstellt, Sie können auch Änderungen von einer Version in eine andere zusammenführen. So können Sie auf einfache Weise Snapshots nachverfolgen oder eine Version für die Entwicklung anlegen und diese Änderungen bei Bedarf in die Nicht-Entwicklungsversion zusammenführen. Unter [Zusammenarbeiten: Versionen, Vergleich und Freigabe](/de/get-started/tutorials/collaborate-versions-and-sharing/) finden Sie Versionierung, Vergleich und Zusammenführen in der Praxis.

Tabellendaten haben einen eigenen Verlauf – Snapshots, die das Lakehouse bei jedem Schreibvorgang erstellt –, beschrieben unter [Tabellen-Snapshots](/de/guides/data/table-snapshots/).

### Wiederherstellen und Festhalten über den KI-Assistenten oder MCP

Über den KI-Assistenten oder MCP stellt `dimension_versions` eine Dimensionsversion anhand ihrer `version_id` wieder her, hält sie fest oder gibt sie frei, `restore_project` setzt jede Dimension im Projekt auf ihre letzte Sicherung zurück, und jede `*_versions`-Auflistung (Schritte, UDFs, Workflows, Dimensionen, Projekte) zeigt die `version_id` jeder Version und ob sie festgehalten wird. Ein `restore` über ein beliebiges `*_versions`-Werkzeug oder die REST-API stellt das Element an Ort und Stelle wieder her: Lassen Sie das Ziel weg oder setzen Sie es auf das Element selbst. `project_upsert` kann ein gesperrtes Projekt entsperren und berücksichtigt `if_match`, sodass der Aufruf fehlschlägt, statt eine Änderung zu überschreiben, die seit Ihrem letzten Lesen des Projekts vorgenommen wurde.


## Projektzugriff verwalten

### Zugriffsarten

Die Projektsicherheit wurde auf drei Zugriffsarten vereinfacht:

* Alle Arbeitsbereichsmitglieder
* Nur bestimmte Mitglieder
* Nur bestimmte Sicherheitsgruppen

Die Projektsicherheit lässt sich einfach festlegen:

1. Öffnen Sie Analyze
2. Wählen Sie „Projekte“ aus
3. Klicken Sie auf das Bearbeitungssymbol des Projekts, das Sie einschränken möchten
4. Wählen Sie unter „Access Control“ die gewünschte Einschränkung aus
5. Klicken Sie auf „Aktualisieren“

Nur ein Architect des Projekts oder ein Tenant-Administrator kann ändern, wer Zugriff auf ein Projekt hat – seine Zugriffsart, die Mitglieder und Sicherheitsgruppen darauf und seine Datenfreigaben. Alle anderen sehen diese Bereiche schreibgeschützt mit dem Hinweis „Nur Architects des Projekts können den Zugriff ändern.“


## Alle Arbeitsbereichsmitglieder

Der Zugriff „Alle Arbeitsbereichsmitglieder“ ist die einfachste Option, da er allen Mitgliedern des Workspace Zugriff gewährt und keine weitere Zuweisung von Mitgliedern erfordert.


## Nur bestimmte Mitglieder

Die Zugriffseinstellung „Nur bestimmte Mitglieder“ erfordert, dass jedes Mitglied dem Projekt zugewiesen wird. So weisen Sie einem Projekt Mitglieder zu:

1. Öffnen Sie Analyze
2. Wählen Sie in der oberen Menüleiste „Projekte“ aus
3. Klicken Sie auf das Mitgliedersymbol
4. Gewähren Sie Mitgliedern Zugriff, indem Sie das Kontrollkästchen neben ihrem Namen in der Spalte „Access“ aktivieren
5. Klicken Sie auf „Aktualisieren“

Bei Clouds mit sehr vielen Mitgliedern kann dieser Ansatz oft mehr Aufwand erfordern als gewünscht – hier sind Sicherheitsgruppen hilfreich.

<Aside>Um Mitglieder hinzuzufügen, müssen Sie Mitglied des Workspace sein.</Aside>


## Nur bestimmte Sicherheitsgruppen

Mit der Option „Nur bestimmte Sicherheitsgruppen“ können Sie bestimmten Sicherheitsgruppen die Berechtigung für den Zugriff auf das Konto erteilen. Da die Zugriffsbeschränkungen auf der Zugehörigkeit zu einer oder mehreren Sicherheitsgruppen beruhen, ist die Verwaltung des Kontozugriffs für größere Gruppen deutlich einfacher. Das ist besonders in Kombination mit der automatischen Gruppenzuordnung per Single Sign-on nützlich. Wenn Sie die Gruppenzuweisungen der Mitglieder über Single Sign-on festlegen, können diese Gruppen den Zugriff auf Projekte auch implizit aktivieren und deaktivieren.

So bearbeiten Sie die zugewiesenen Gruppen:

1. Öffnen Sie Analyze
2. Wählen Sie in der oberen Menüleiste „Projekte“ aus
3. Klicken Sie auf das Symbol für Sicherheitsgruppen
4. Gewähren Sie Sicherheitsgruppen Zugriff, indem Sie das Kontrollkästchen neben ihrem Namen in der Spalte „Access“ aktivieren
5. Klicken Sie auf „Aktualisieren“


## Daten zwischen Projekten freigeben

Mit einer Datenfreigabe kann ein Projekt auf die Tabellen eines anderen Projekts zugreifen – zum Beispiel, damit die Schritte [Import Project Table](/de/reference/workflow-steps/import/import-project-table/) und [Export Project Table](/de/reference/workflow-steps/export/export-project-table/) Daten zwischen ihnen verschieben können. Eine Freigabe wird von dem Projekt erteilt, dessen Daten freigegeben werden, und zwar für genau ein anderes Projekt:

1. Öffnen Sie das Projekt, dessen Daten Sie freigeben möchten, und wechseln Sie zu seiner Registerkarte **Startseite**.
2. Klicken Sie unter **Datenfreigabe-Verwaltung** auf **Neue Datenfreigabe**.
3. Wählen Sie unter **Projekt auswählen** das Projekt aus, das die Daten dieses Projekts verwenden darf.
4. Aktivieren Sie unter **Zulässige Vorgänge** die Option **Lesen**, **Schreiben** oder beide, und klicken Sie auf **Datenfreigabe hinzufügen**.

**Datenfreigabe löschen** entfernt eine Freigabe. Nur ein Architect des Projekts oder ein Tenant-Administrator kann die Datenfreigaben eines Projekts hinzufügen oder löschen.

Eine Freigabe wird einem Projekt erteilt und gilt daher nur für die Mitglieder und Workflows dieses Projekts:

- **Lesen** über eine Freigabe erfordert eine Rolle in dem Projekt, dem sie erteilt wurde. Wer dort keine Rolle hat, erhält über die Freigabe nichts.
- **Schreiben** über eine Freigabe – das Erstellen einer Tabelle, eines Ordners oder einer Dimension im freigebenden Projekt – erfordert eine **Schreiben**-Freigabe und die Rolle Manager oder Architect in Ihrem eigenen Projekt, also die Rolle, mit der Sie dieselbe Änderung dort vornehmen könnten. Alle anderen erhalten die Meldung „Das Schreiben in dieses Projekt über eine Datenfreigabe erfordert eine Schreibfreigabe von diesem Projekt für Ihr Projekt sowie die Rolle Manager oder Architect in Ihrem Projekt.“

Workflows werden unter der eigenen Identität ihres Projekts ausgeführt, daher funktionieren die Schritte Import Project Table und Export Project Table über eine Freigabe unabhängig davon, wer die Ausführung startet.


## Unterschiedliche Anzeigerollen festlegen

Häufig erfordert ein Projekt mehrere Transformationen und Tabellen für Zwischenschritte, während das Endergebnis nur aus wenigen Tabellen besteht. Mitglieder müssen nicht immer alle Elemente des Projekts sehen, manchmal nur das Endprodukt. PlaidCloud bietet Ihnen die Möglichkeit, unterschiedliche Anzeigerollen festzulegen, um die Ansicht übersichtlich zu halten und die Sichtbarkeit für jedes Mitglied zu steuern.

Es gibt drei integrierte Anzeigerollen: **Architect, Manager,** und **Explorer**

Die Rolle **Architect** ist die einfachste, da sie volle Sichtbarkeit und Kontrolle über Projekte, Workflows, Tabellen, Variablen, Dateneditoren, Hierarchien und benutzerdefinierte Funktionen gewährt.

Die Rollen **Manager** und **Explorer** haben keine festgelegten Zugriffsrechte, können aber individuell definiert werden. Mit anderen Worten: Sie können wählen, welche Elemente für jede Gruppe sichtbar sind.

<Aside>**Manager*** *und **Explorer** sind keine Sicherheitsgruppen, sie bieten lediglich eine bequeme Möglichkeit, Aufgaben und die Sichtbarkeit von Informationen zu trennen.</Aside>

Sie können alle zu **Architect** machen, wenn Sie der Meinung sind, dass alles im Projekt sichtbar sein muss; andernfalls können Sie Mitglieder als Projektmitglieder mit der Rolle **Manager** und/oder **Explorer** festlegen und die Sichtbarkeit auf diese Weise steuern.

So legen Sie eine andere Rolle fest:

1. Öffnen Sie Analyze
2. Wählen Sie „Projekte“ aus
3. Klicken Sie auf das Mitgliedersymbol
4. Wählen Sie das Mitglied aus, dessen Rolle Sie ändern möchten
5. Doppelklicken Sie in der Spalte „Role“ auf seine aktuelle Rolle
6. Wählen Sie die gewünschte Rolle aus
7. Klicken Sie auf „Aktualisieren“


## Projektvariablen verwalten

Beim Ausführen eines Projekts oder Workflows kann es sinnvoll sein, Variablen für wiederkehrende Aufgaben festzulegen, um die Übersicht zu verbessern und Zeit zu sparen. Diese Variablen funktionieren wie eine normale algebraische Variable: Sie legen fest, wofür die Variable steht und welche Operation darauf folgen soll. In PlaidCloud können Sie diese Variablen auf Projektebene festlegen, was sich auf alle Workflows in diesem Projekt auswirkt, oder auf Workflow-Ebene, was sich nur auf diesen bestimmten Workflow auswirkt.

So legen Sie eine Variable auf Projektebene fest:

1. Öffnen Sie Analyze
2. Wählen Sie „Projekte“ aus
3. Klicken Sie auf das Symbol zum Verwalten der Projektvariablen

In der Variablentabelle können Sie die Variablen ansehen und die aktuellen Werte anzeigen oder bearbeiten. Über die Schaltfläche „New Project Variable“ können Sie außerdem neue Variablen hinzufügen oder bestehende löschen.


## Ein Projekt kopieren

**Projekt kopieren** kopiert ein Projekt – vollständig oder nur die Teile, die Sie auswählen – in ein ganz neues Projekt oder in ein bereits vorhandenes Projekt.

So kopieren Sie ein Projekt:

1. Öffnen Sie Analyze
2. Wählen Sie „Projekte“ aus
3. Wählen Sie das Projekt aus, das Sie kopieren möchten
4. Klicken Sie auf die Schaltfläche **Aktionen** und wählen Sie **Projekt kopieren**
5. Wählen Sie das Ziel, legen Sie fest, was übernommen und welche Daten kopiert werden sollen, und klicken Sie auf **Projekt kopieren**
6. Prüfen Sie die Zusammenfassung **Vor dem Kopieren prüfen** und klicken Sie auf **Kopieren starten**

### Auswählen, was kopiert wird

Die Auswahlstruktur listet nach Typ auf, was das Projekt enthält – Workflows, Schritte, Tabellen, Dimensionen, Dateneditoren, benutzerdefinierte Funktionen. Lassen Sie alles aktiviert, um das gesamte Projekt zu kopieren, oder aktivieren Sie nur die gewünschten Teile.

Sie müssen nicht selbst ermitteln, wovon diese Teile abhängen. Alles, was Sie aktivieren, bringt seine Abhängigkeiten mit: die Tabellen, die ein Schritt liest und schreibt, die Dimensionen, die er lädt oder für Umlagen verwendet, die benutzerdefinierten Funktionen, die er aufruft, und jeden Sub-Workflow oder jedes Makro, das er aufruft. Die Sensoren eines Workflows werden mit dem Workflow übernommen.

**Kopierte Sensoren werden deaktiviert übernommen.** In der Kopie wird nichts ausgelöst, bis Sie jeden Sensor im Zielprojekt einschalten. Ein Import, der doppelte Elemente überschreibt, fügt keinen zweiten Sensor hinzu, wenn der Ziel-Workflow ihn bereits hat.

### In ein neues Projekt kopieren

Geben Sie dem neuen Projekt einen Namen und eine ID. Die ID wird zu seinem Schemanamen und kann später nicht mehr geändert werden.

**Zeitpläne werden pausiert übernommen.** Wenn Sie ein ganzes Projekt in ein neues kopieren, werden die geplanten Ereignisse jedes Workflows pausiert übernommen, sodass die Kopie sie nicht von selbst ausführt. Nach Abschluss der Kopie listet eine Meldung die Ereignisse auf, die im Original aktiv waren. Um eines davon in der Kopie auszuführen, wählen Sie es unter **Werkzeuge** > **Ereignisplaner** aus und klicken Sie auf **Ausgewählte aktivieren** – siehe [Ein Ereignis pausieren](/de/administration/scheduled-events/event-scheduler/#ein-ereignis-anhalten).

### In ein vorhandenes Projekt kopieren

Wählen Sie das Ziel aus der Projektliste aus. Die Kopie ergänzt dieses Projekt, statt es zu ersetzen.

**Sie müssen das Ziel ändern dürfen.** Eine Kopie in ein Projekt, in dem Sie keine Rolle haben, wird abgelehnt, ebenso eine Kopie in ein Projekt, das gegen Änderungen gesperrt wurde – geprüft, bevor irgendetwas gelesen oder geschrieben wird, sodass eine abgelehnte Kopie das Ziel unverändert lässt. Ein Projekt kann außerdem nicht in sich selbst kopiert werden.

**Das Kopieren eines Projekts, das Zeilen einschränkt, erfordert einen Architect des Projekts.** Die Kopie ist ein neues Projekt ohne Einschränkung des [Zeilenzugriffs](/de/administration/access/managing-security-groups-and-assignments/#zeilenzugriff-verwalten), und die Kopie weist Sie darauf hin: „Diese Kopie ist nicht zeilenbeschränkt.“ Richten Sie den Zeilenzugriff für die Kopie ein, bevor Sie sie freigeben. Das Kopieren in ein vorhandenes Projekt, das Zeilen einschränkt, erfordert ebenso einen seiner Architects oder einen Tenant-Administrator.

**Das Ziel behält seine eigenen Einstellungen.** Name, ID, Datenverbindungsumgebung, Speicherstandards, Dokumentenkonto, Zugriffsart, Zugriffslisten und Zeilenzugriffsberechtigungen bleiben unverändert. Nur die ausgewählten Inhalte werden übernommen.

Ein Schritt, der auf **Projektstandard** steht, übernimmt diese Einstellung, nicht ein Konto – nach dem Kopieren wird er zu dem Standard aufgelöst, den das Zielprojekt hat, nicht zu dem aus der Quelle.

Ist ein eingehendes Element dasselbe Element wie eines, das bereits im Ziel vorhanden ist, entscheiden Sie, was geschieht:

- **Doppelte Elemente mit eingehenden Daten überschreiben** – die eingehende Version ersetzt die im Ziel.
- **Neue Kopie doppelter Elemente erstellen** – das Ziel behält, was es hat, und das eingehende Element wird daneben hinzugefügt, wobei an seinen Namen ` copy` angehängt wird, und ein Zähler, wenn auch dieser Name vergeben ist.

Projekt- und Workflow-Variablen sind die Ausnahme von *Neue Kopie erstellen*: Eine Variable wird über ihren Namen identifiziert, daher lässt sich keine zweite Kopie hinzufügen, ohne sie in etwas umzubenennen, worauf nichts verweist. Wenn das Ziel bereits eine Variable definiert, die auch die Kopie mitbringt, bleibt der eigene Wert des Ziels erhalten, und die Kopie teilt Ihnen mit, welche Variablen sie unverändert gelassen hat. *Überschreiben* behandelt Variablen wie alles andere und ersetzt sie.

Dieser Abgleich erfolgt nach Identität, nicht nach Name – ein Element, das ursprünglich aus demselben Projekt stammt, wird als dasselbe Element erkannt, während zwei Elemente, die lediglich denselben Namen haben, als verschiedene Elemente behandelt werden und danach beide vorhanden sind.

### Festlegen, wie viele Daten kopiert werden

Unter **Data to copy** legen zwei Einstellungen fest, welche Daten mit Ihrer Auswahl übernommen werden.

**Tabellendaten** legt fest, wie viele Zeilen jeder Tabelle kopiert werden:

| Auswahl | Was kopiert wird |
| --- | --- |
| **Keine Tabellendaten** | Tabellen, Schritte und der Rest der Auswahl, ohne Zeilen. Dies ist der Standard. |
| **Vollständig** | Alle Zeilen jeder Tabelle, im selben Lakehouse und über Lakehouses hinweg. |
| **Stichprobe** | Bis zu der Anzahl an **Zeilen pro Tabelle**, die Sie eingeben, nur für ein neues Projekt. Die Anzahl kann zwischen 1 und 1.000.000 liegen. |

Eine Stichprobentabelle enthält bis zu so viele Zeilen oder alle ihre Zeilen, wenn sie weniger hat. Eine Kopie mit **Vollständig** oder **Stichprobe** kopiert mehrere Tabellen gleichzeitig, sodass ein Projekt mit vielen Tabellen schneller fertig ist.

**Copy dimension members** kopiert die Elemente jeder Dimension in der Auswahl, unabhängig davon, welche Auswahl Sie unter **Tabellendaten** treffen. Die Option ist standardmäßig aktiviert, sodass auch eine Kopie ohne Tabellendaten mit gefüllten Dimensionen ankommt und schnell erstellt ist. Deaktivieren Sie sie, um die Dimensionen ohne ihre Elemente zu kopieren.

Setzen Sie über die REST-API (`POST /rest/v1/analyze/project/copy`) oder das MCP-Werkzeug `project_copy` den Wert `data_mode` auf `structure`, `full` oder `sample` und `dimension_members` auf `true` oder `false`. Wenn Sie `dimension_members` weglassen, werden Elemente nur kopiert, wenn auch Tabellenzeilen kopiert werden. `project_copy` gibt außerdem die Warnungen der Kopie zurück, etwa zu ERP-Schreibautorisierungen, die nicht kopiert wurden.

### Die Kopie prüfen

Bevor etwas kopiert wird, fasst **Vor dem Kopieren prüfen** die Kopie zusammen: das Quellprojekt, das Ziel, die Auswahl unter **Tabellendaten**, ob **Dimensionselemente** einbezogen werden, die Anzahl der Tabellen und Ansichten, die Größe, eine geschätzte Dauer, das Quell- und Ziel-Lakehouse sowie alle Warnungen unter **Bitte beachten**. Klicken Sie auf **Kopieren starten**, um zu beginnen, oder auf **Abbrechen**, um zurückzugehen und die Auswahl zu ändern.

### Wer die Kopie sehen kann

Eine Kopie mit Daten – Tabellenzeilen, Dimensionselementen oder beidem – ist privat für die Person, die sie erstellt hat. Geben Sie sie aus dem neuen Projekt frei, wenn Sie so weit sind. Eine Kopie eines Projekts mit Sicherheit auf Zeilenebene bleibt aus demselben Grund privat.

Das Kopieren von Daten in ein vorhandenes Projekt erfordert Schreibzugriff auf dieses Projekt.

### ERP-Schreibautorisierungen in der Kopie

Eine neue Kopie, die privat für Sie ist, behält die [ERP-Schreibautorisierungen](/de/guides/workflows/run-a-workflow/#das-projekt-zum-buchen-autorisieren) des Quellprojekts, sodass Sie ihre Buchungs-Workflows testen können, ohne die Kopie erneut zu autorisieren. Das gilt für jede Kopie in ein neues Projekt, die mit Tabellendaten (**Vollständig** oder **Stichprobe**), Dimensionselementen oder beidem erstellt wird. Die Autorisierungen werden kopiert, wenn:

- Sie Architect des Quellprojekts oder Workspace-Administrator sind.
- Sie die Kopie selbst erstellen, nicht über einen Agent oder ein Dienstkonto.

Jede Autorisierung wird nur kopiert, wenn Sie sie heute selbst erteilen könnten: Ihre Verbindung und Umgebung existieren noch, und Sie haben Schreibzugriff auf die Verbindung. Die kopierten Autorisierungen werden als Ihre erfasst.

**Die Kopie kommt im Modus „Simulieren“ an.** Steht der **ERP-Buchungsmodus** des Quellprojekts auf „Live“, wird er in der Kopie auf „Simulieren“ gesetzt, sodass ihre Workflows aufbauen und prüfen, was sie buchen würden, ohne das ERP zu kontaktieren. Eine Quelle mit „Simulieren“ oder „Aus“ behält diese Einstellung. Wenn Sie aus der Kopie tatsächlich buchen möchten, setzen Sie den **ERP-Buchungsmodus** unter **ERP-Buchung** auf der Startseite der Kopie auf „Live“ – siehe [Einen Buchungsmodus auswählen](/de/guides/workflows/run-a-workflow/#einen-buchungsmodus-wählen). Zeitpläne und Sensoren werden weiterhin wie oben beschrieben pausiert bzw. deaktiviert übernommen, sodass in der Kopie nichts ausgeführt wird, bis Sie es einschalten.

Eine Kopie in ein vorhandenes Projekt oder eine ohne Tabellendaten und ohne Dimensionselemente startet ohne die Autorisierungen der Quelle. Autorisieren Sie sie unter **ERP-Buchung** > **ERP-Schreibautorisierungen** auf ihrer Startseite, bevor sie bucht.

**Kopierergebnisse** meldet, was geschehen ist, zum Beispiel „2 ERP-Schreibautorisierungen kopiert; ERP-Buchung ist im Modus Simulieren“, zusammen mit der Anzahl der nicht kopierten.

### Kopierergebnisse

Nach Abschluss der Kopie fasst ein Fenster **Kopierergebnisse** die kopierten Tabellen und Dimensionselemente zusammen und führt jede Tabelle und Dimension mit Namen und Ergebnis auf – **Kopiert**, **Mit Änderungen kopiert**, **Stichprobe**, **Übersprungen** oder **Fehlgeschlagen** – sowie den Grund für jedes übersprungene oder fehlgeschlagene Element. Klicken Sie auf **Retry failed items**, um die fehlgeschlagenen Tabellen und Dimensionen erneut zu kopieren; ihre aktuellen Inhalte in der Kopie werden ersetzt. Sie werden per Nachricht und per E-Mail benachrichtigt, wenn eine Kopie abgeschlossen ist oder fehlschlägt, und können die Ergebnisse über die Nachricht erneut öffnen oder später, indem Sie die Kopie auf der Registerkarte **Projekte** auswählen und im Menü **Aktionen** die Option **Import- oder Kopierergebnis anzeigen** wählen.

Die Ergebnisse bleiben an der Kopie, bis jemand sie verwirft. Sobald die Kopie abgeschlossen ist, klicken Sie auf **Ergebnis verwerfen**, um sie für alle zu entfernen, die das Projekt öffnen können. Am Projekt ändert sich nichts, aber seine fehlgeschlagenen Elemente können danach nicht mehr aus dem Fenster heraus erneut versucht werden. Das Verwerfen erfordert Bearbeitungszugriff auf das Projekt, und das Projekt darf nicht gesperrt sein.

### Referenzen aktualisieren

Die Workflow-Schritte eines Projekts verweisen auf Tabellen und andere Objekte innerhalb dieses Projekts. **Referenzen aktualisieren** schreibt diese Verweise so um, dass sie auf die Kopie statt auf das Original zeigen – was fast immer gewünscht ist und weshalb die Option standardmäßig aktiviert ist. Wenn Sie sie deaktivieren, verweisen die kopierten Schritte weiterhin auf das Projekt, aus dem sie stammen.

<Aside>Das Kopieren läuft im Hintergrund. Ein Fortschrittsdialog zeigt, wie die Kopie ihre Phasen durchläuft; Sie können auf **Im Hintergrund ausführen** klicken, um ihn zu schließen und weiterzuarbeiten – die Projektliste wird automatisch aktualisiert, und Sie werden benachrichtigt, wenn die Kopie abgeschlossen ist.</Aside>

## Den Projektbericht anzeigen

Wenn ein Projekt oder Workflow dynamisch ist, wird es schwierig, eine detaillierte Dokumentation zu pflegen. Um dieses Problem zu lösen, bietet PlaidCloud die Möglichkeit, einen Bericht auf Projektebene zu erzeugen, der Workflows, Workflow-Schritte, benutzerdefinierte Transformationen, Variablen und Tabellen detailliert dokumentiert. Dieser Bericht wird bei Bedarf erzeugt und spiegelt den aktuellen Zustand des Projekts wider.

So laden Sie den Bericht herunter:

1. Öffnen Sie Analyze
2. Wählen Sie „Projekte“ aus
3. Klicken Sie auf das Berichtssymbol
