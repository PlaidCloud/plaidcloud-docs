**In portables Format exportieren** verpackt die Workflows eines Projekts als eigenständiges Python-Programm, das ohne Verbindung zu PlaidCloud auf [DuckDB](https://duckdb.org) läuft. Es erzeugt eine portable Kopie der Logik und der Daten des Projekts, die offline und für sich allein läuft.

Es handelt sich um einen Export in nur einer Richtung. Das erzeugte Paket ist eine Momentaufnahme; es wird nicht zurücksynchronisiert, und ein erneuter Export nach Änderungen erzeugt ein neues Paket.

<Aside type="caution" title="Wiedergabetreue nach bestem Bemühen">
Der Export gibt SQL-basierte Transformationsschritte exakt wieder. Proprietäre Operationen und solche mit Nebenwirkungen – Umlagen, Dimensionsladevorgänge, Benachrichtigungen, Dokument- und Berichtsschritte, Skripte – werden als **Stubs** exportiert: Ihre ursprüngliche Konfiguration bleibt erhalten und, sofern die Ausgabetabelle materialisiert war, werden ihre Daten als Snapshot mitgeliefert, der Schritt selbst wird jedoch nicht erneut ausgeführt. Die Wiedergabetreue jedes Schritts ist in `COVERAGE.md` im Paket festgehalten. Für garantierte, vollständig neu berechnete Ergebnisse führen Sie das Projekt in PlaidCloud aus.
</Aside>

## Ein Projekt exportieren

1. Öffnen Sie **Analysieren** und wählen Sie die Registerkarte **Projekte**.
2. Wählen Sie ein einzelnes Projekt aus.
3. Öffnen Sie das Menü **Aktionen** (oder klicken Sie mit der rechten Maustaste auf das Projekt) und wählen Sie **In portables Format exportieren** – die Option steht neben **Export Project**.
4. Im Dialogfeld:
   - **Dokumentkonto** – das Dokumentenkonto, in das das Paket geschrieben wird.
   - **Ordnerpfad** – der Ordner innerhalb dieses Kontos, zum Beispiel `/exports`.
   - **Include data** – wenn aktiviert (Standard), werden Quell- und Snapshot-Tabellen als Parquet mitgeliefert, sodass das Paket ohne externe Daten läuft. Deaktivieren Sie die Option, um nur den Code und die Schemaverträge auszuliefern, die Sie dann selbst befüllen.
5. Klicken Sie auf **Exportieren**. Nach Abschluss bestätigt eine Meldung, wohin das Paket geschrieben wurde und von wie vielen Tabellen ein Snapshot erstellt wurde.

Die Aktion erfordert Zugriff auf das Projekt und Lesezugriff auf seine Tabellen – dieselbe Zugriffsebene, die heute für den Export von Tabellendaten nötig ist.

## Was das Paket enthält

Der Export ist eine `.zip`-Datei mit folgendem Inhalt:

- `pipeline_<workflow>.py` – ein Skript pro Workflow, mit den Schritten in Ausführungsreihenfolge.
- `config.py` – Engine-Auswahl (standardmäßig DuckDB) und der Schemaname des Projekts.
- `_runtime.py` – ein kleiner Engine-Shim; die einzige Abhängigkeit neben DuckDB.
- `stubs.py` – Funktionen ohne Wirkung für nicht portable Operationen, die jeweils die ursprüngliche Schrittkonfiguration enthalten.
- `data/` – Parquet-Snapshots von Quell- und eingefrorenen Tabellen (wenn **Include data** aktiviert war).
- `requirements.txt` – die Python-Abhängigkeiten (nur `duckdb`).
- `README.md`, `COVERAGE.md`, `RUN_ORDER.md` – wie das Paket ausgeführt wird, die Wiedergabetreue pro Schritt und die Reihenfolge, in der die Workflow-Skripte auszuführen sind.

## Das Paket ausführen

1. Entpacken Sie das Paket und erstellen Sie eine Python-Umgebung:

   ```bash
   python -m venv .venv && source .venv/bin/activate
   pip install -r requirements.txt
   ```

2. Führen Sie jedes Workflow-Skript in der in `RUN_ORDER.md` aufgeführten Reihenfolge aus:

   ```bash
   python pipeline_<workflow>.py
   ```

Jedes Skript erstellt seine Tabellen in einer lokalen DuckDB-Datenbank (standardmäßig `export.duckdb`). SQL-Transformationsschritte werden live neu berechnet; Stub-Schritte geben einen Hinweis aus und lassen ihre als Snapshot gesicherte Ausgabe unverändert. Um das Paket statt auf DuckDB auf Ihr eigenes Warehouse auszurichten, setzen Sie `ENGINE` in `config.py`.
