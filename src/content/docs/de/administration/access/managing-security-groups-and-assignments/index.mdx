Die Sicherheits- und Zugriffsverwaltung von PlaidCloud ist unkompliziert. Einem Mitglied wird der Zugriff anhand der Gruppen gewährt oder verweigert, denen es angehört. Die Sicherheitszuordnung eines Mitglieds lässt sich einfach hinzufügen oder ändern.

<Aside>Jeder Workspace kann beliebig viele Sicherheitsgruppen haben. Wir empfehlen jedoch, ihre Anzahl gering zu halten, um die Sicherheitsverwaltung zu vereinfachen.</Aside>



## Sicherheitsgruppen verwalten


Sicherheitsgruppen können hinzugefügt, aktualisiert oder gelöscht werden.



**So verwalten Sie Sicherheitsgruppen:**


1. Öffnen Sie Identity
2. Wählen Sie die Registerkarte „Security“
3. Klicken Sie im Dropdown-Menü auf „Sicherheitsgruppen“ (es wird ein Formular mit den vorhandenen Gruppen angezeigt)
4. Um eine Gruppe hinzuzufügen, klicken Sie auf „Create Security Group“
5. Um die Berechtigungen einer Gruppe zu bearbeiten, klicken Sie auf das Symbol ganz links

**So verwalten Sie Gruppenmitglieder:**


1. Öffnen Sie Identity
2. Wählen Sie die Registerkarte „Security“
3. Klicken Sie im Dropdown-Menü auf „Sicherheitsgruppen“
4. Klicken Sie auf das Mitglieder-Symbol
5. Ziehen Sie die gewünschten Mitglieder aus der Spalte „Unassigned Members“ in die Spalte „Assigned Members“ oder umgekehrt, um Mitglieder zu entfernen

<Aside>Wenn Sie speichern, während die Spalte „Assigned Members“ leer ist, ändert sich nichts, und Sie werden darauf hingewiesen. Um eine Gruppe allen zu entziehen, entfernen Sie ihre Berechtigungen oder löschen Sie die Gruppe, statt ihre Mitgliedschaft zu leeren.</Aside>

<Aside>Wenn einer Gruppe über [Zeilenzugriff](#zeilenzugriff-verwalten) Zeilen gewährt werden, erreicht eine Änderung der Mitgliedschaft die Dashboards innerhalb von etwa einer Minute: Wer hinzugefügt wird, sieht dort die Zeilen der Gruppe, und wer entfernt wird, sieht sie nicht mehr. Das Deaktivieren oder Löschen eines Mitglieds und das Löschen einer Gruppe wirken auf dieselbe Weise.</Aside>

<Aside type="caution">Berechtigungen, die Sie sich selbst nicht erteilen können, bleiben beim Speichern der Berechtigungsmatrix einer Gruppe unverändert und werden darin nicht angezeigt. Wenn Sie eine davon ändern müssen, wenden Sie sich an jemanden, der diese Berechtigung besitzt – die Matrix bearbeitet immer nur das, was Sie steuern können.</Aside>

## Zeilenzugriff verwalten

Zeilenzugriff schränkt anhand der Werte einer Spalte ein, welche Zeilen einer Tabelle eine Sicherheitsgruppe sehen kann. Beispielsweise kann eine Spalte `region` den Zugriff einschränken: Eine Gruppe, der `East` und `Central` gewährt werden, sieht nur Zeilen mit diesen Werten. Alles für ein Projekt und eine Spalte – die Spalte auswählen, die Herkunft ihrer Werte festlegen und bestimmen, welche Gruppe was sieht – geschieht in einem einzigen Bildschirm, und das Speichern wirkt sofort.

Zeilenzugriff einzurichten und zu ändern erfordert einen Projekt-Architect oder einen Mandantenadministrator. Alle anderen, die die Registerkarte „Security“ eines Projekts öffnen, erfahren, dass Zeilenzugriff nur für Architects verfügbar ist, und die unten genannten Einstiegspunkte werden ihnen nicht angezeigt.

### Zeilenzugriff öffnen

Jeder Einstiegspunkt öffnet denselben Zeilenzugriff-Bildschirm:

- **Die Symbolleiste des Tabellen-Explorers** enthält die Schaltfläche **Zeilenzugriff**, mit einem Hinweiszähler, wenn die Tabelle bereits Zeilen einschränkt. Sie öffnet sich bei der ersten eingeschränkten Spalte der Tabelle, falls vorhanden, und Sie können zu jeder anderen Spalte der Tabelle wechseln.
- **Das Facettenmenü einer Spalte** enthält **Zeilen nach dieser Spalte einschränken…**, wodurch Zeilenzugriff für diese Spalte geöffnet wird. Bei einer Spalte, die bereits Zeilen einschränkt, lautet der Eintrag **Zeilen durch diese Spalte eingeschränkt – bearbeiten…**.
- **Die Registerkarte „Security“ eines Projekts** listet jede eingeschränkte Spalte des Projekts auf, mit den Tabellen, für die sie gilt, den Gruppen mit Gewährungen und dem **Synchronisieren**-Status. Wählen Sie eine Spalte, um sie zu bearbeiten, oder klicken Sie auf **Spalte einschränken…**, um eine neue zu beginnen: Wählen Sie eine Tabelle und dann eine Spalte. Spalten, die bereits Zeilen einschränken, sind mit einem Schloss markiert.
- **Identity → Member**, auf der Registerkarte **Zeilenzugriff** eines Mitglieds, und **Identity → Security → Sicherheitsgruppen**, in der Zeilenzugriff-Übersicht einer Gruppe. **Zeilenzugriff öffnen** (oder **Bearbeiten**) öffnet die ausgewählte Spalte; **Hinzufügen** schränkt eine weitere Spalte im Projekt dieser Zeile ein.

Wird der Bildschirm für eine Spalte geöffnet, bleibt er bei dieser Spalte. Wird er mit **Spalte einschränken…** oder **Hinzufügen** geöffnet, können Sie eine Spalte auswählen.

### Das Zeilenzugriff-Raster

So schränken Sie eine Tabelle nach einer Spalte ein:

1. Öffnen Sie Zeilenzugriff über einen der oben genannten Einstiegspunkte und wählen Sie die Spalte, falls Sie nicht bereits mit einer angekommen sind – die Auswahl bietet die tatsächlichen Spalten der Tabelle an, keine freie Texteingabe.
2. Wählen Sie eine **Wertequelle** – **Spalte** (die eindeutigen Werte einer Tabellenspalte), **Dimension** (Knoten einer Dimension) oder **Liste** (Werte, die Sie eingeben). Der Werttyp folgt dem Datentyp der Spalte.
3. Aktivieren Sie für jede Sicherheitsgruppe die Werte, die diese Gruppe sehen darf. Das Raster listet die Gruppen mit Zugriff auf das Projekt auf sowie jede Gruppe, die bereits eine Gewährung für die Spalte besitzt.
4. Legen Sie **Everyone else** auf **sees all rows** oder **sees no rows** fest – das gilt für jede Gruppe ohne Markierungen im Raster.
5. Klicken Sie auf **Speichern**.

Das Speichern wirkt sofort. Die eigenen Abfragen von PlaidCloud folgen der Änderung unmittelbar und Ihre Superset-Dashboards innerhalb von etwa einer Minute – es gibt keinen separaten Schritt zum Anwenden und keinen Genehmigungsdialog. Der Synchronisierungsstatus des Bildschirms zeigt, wie weit die Änderung gelangt ist; siehe [Dashboards synchron halten](#dashboards-synchron-halten).

Das Raster übernimmt außerdem die Details für Sie:

- **Viele Werte.** Die Werte sind sortiert. Hat eine Spalte mehr Werte, als Platz finden, meldet das Raster „More values than fit here — type to search.“, und das Filterfeld durchsucht die gesamte Spalte, wobei jeder Wert erhalten bleibt, den eine Gruppe bereits besitzt.
- **Leere Werte.** Ein einziges Kontrollkästchen **Leere Werte – sichtbar für jede Gruppe mit einer Gewährung** bestimmt über die Zeilen ohne Wert in der Spalte. Aktivieren Sie es, und jede Gruppe mit einer beliebigen Gewährung für die Spalte sieht diese Zeilen.
- **Eine Tabelle, die noch nicht erstellt ist,** zeigt **Erstellen Sie diese Tabelle zuerst (führen Sie den Workflow aus, der sie erstellt)** statt einer leeren Liste.
- **Speichern wartet auf die angezeigten Werte.** Solange Werte geladen werden – nachdem Sie die Wertequelle, die Dimension oder die Tabelle gewechselt oder eine Vorlage angewendet haben –, ist **Speichern** deaktiviert, mit dem Tooltip „Save is available once this source's values load.“ Schlägt ein Ladevorgang fehl, teilt das Raster dies mit und bittet Sie, die Quelle erneut auszuwählen; es wird nichts gespeichert, bis ein Ladevorgang erfolgreich war.

### Ein Spaltenname, jede Tabelle

Eine Einschränkung gehört zu einem Spalten*namen* im Projekt, nicht zu einer einzelnen Tabelle. Sobald `region` Zeilen einschränkt, wird jede Tabelle im Projekt mit einer Spalte namens `region` danach gefiltert, in den eigenen Abfragen von PlaidCloud ebenso wie in Dashboards. Die Liste **Applies to** des Rasters zeigt diese Tabellen. Sie ist schreibgeschützt, weil der Spaltenname sie bestimmt, und eine Tabelle, die Sie später mit derselben Spalte hinzufügen, ist abgedeckt, sobald sie veröffentlicht wird.

Wenn keine Tabelle im Projekt eine Spalte mit diesem Namen hat, warnt das Fenster zusätzlich zur Anzeige **Applies to 0 tables**, dass die Einschränkung kein Dashboard filtert, bis eine Tabelle diese Spalte hat. Fügen Sie die Spalte einer Tabelle hinzu oder korrigieren Sie den Spaltennamen, und die Warnung verschwindet.

<Aside type="caution">
**Ein Spaltenname muss exakt übereinstimmen** – einschließlich Groß-/Kleinschreibung und Leerzeichen. `Region` und `region` sind verschiedene Namen, ebenso `region` und `region ` mit einem Leerzeichen am Ende. Die Auswahl bietet nur tatsächliche Spaltennamen an, daher spielt das vor allem eine Rolle, wenn eine Spalte an anderer Stelle umbenannt wird – Zeilenzugriff warnt Sie dann und nennt die ähnlichste gefundene Spalte, statt stillschweigend nichts einzuschränken.
</Aside>

<Aside type="caution">
**Das Veröffentlichen einer Tabelle, die Zeilen einschränkt, richtet ihren Dashboard-Filter im selben Schritt ein.** Dashboards lesen eine Tabelle über ihre veröffentlichte Berichtsansicht. Wenn Sie also eine Tabelle mit einer eingeschränkten Spalte veröffentlichen oder erneut veröffentlichen, registriert PlaidCloud den Dashboard-Filter dieser Tabelle, bevor die Veröffentlichung abgeschlossen ist. Gelingt das nicht, wird die Veröffentlichung abgelehnt und alles, was dieser Versuch angelegt hat, wird zurückgenommen, sodass eine eingeschränkte Tabelle nie ungefiltert in Dashboards landet. Eine *Ansicht* kann in einem Projekt, das Zeilen einschränkt, nicht veröffentlicht werden, weil die Abfrage einer Ansicht die eingeschränkte Spalte umbenennen oder ableiten kann. Siehe [Tabellen veröffentlichen](/de/guides/data/publish/).
</Aside>

### Eine Einschränkung aufheben

**Einschränkung aufheben** im Raster entfernt die Einschränkung nach einer Bestätigung im Raster – „Stop restricting rows by ‚region‘? Every group's grant on it is removed and everyone sees its rows.“ Zeilenzugriff bestätigt anschließend „Rows in ‚region‘ are no longer restricted.“ Das Superset-Dataset der Spalte wird mit entfernt, sofern es nicht noch von Diagrammen verwendet wird; in diesem Fall teilt Zeilenzugriff mit, dass das Dataset bestehen bleibt und wie viele Diagramme es verwenden.

Eine Spalte kann nicht umbenannt oder gelöscht werden, solange sie Zeilen einschränkt. Ein Architect wird aufgefordert, die Einschränkung zuerst in Zeilenzugriff aufzuheben; allen anderen wird gesagt, sie sollen einen Projekt-Architect fragen.

### Wer ein Projekt mit Zeilenbeschränkung ändern darf

Die Workflows, Schritte und benutzerdefinierten Funktionen eines Projekts laufen als die eigene Dienstidentität des Projekts, die jede Zeile liest. Wer sie ändern kann, könnte einen Schritt dazu bringen, Zeilen, die ihm nicht gewährt wurden, in eine Tabelle zu kopieren, die er lesen kann. Daher schränkt die Zeilenbeschränkung eines Projekts auch ein, wer ändern darf, was das Projekt tut. Sobald ein Projekt mindestens eine Spalte einschränkt:

- **Automatisierung ist nur für Architects.** Nur Projekt-Architects und Mandantenadministratoren können Workflows, Schritte, benutzerdefinierte Funktionen, Zeitpläne, Workflow- und Projektvariablen sowie E-Mail-Vorlagen für Benachrichtigungen ändern – und aus demselben Grund ein Workflow-Bundle importieren, einen Alteryx-Workflow konvertieren oder in das Projekt importieren, kopieren oder wiederherstellen bzw. seine Verbindungsumgebung, sein Standard-Dokumentenkonto oder seinen ERP-Buchungsmodus ändern. Alle anderen können die Workflows des Projekts weiterhin ausführen: **Start**, **Beenden**, **Fortsetzen** und **Ausgewählte(n) Schritt(e) ausführen** bleiben verfügbar. Der Schritt-Editor, die Bearbeitungssteuerelemente des Workflows, der UDF-Editor und das Zeitplanformular öffnen sich für sie schreibgeschützt, mit einem Banner, das die Architects nennt, die Sie fragen können: „This project restricts rows, so only its Architects can change workflows, steps, UDFs, schedules, variables and notify templates. You can still run them.“
- **Dimensionen, die eine eingeschränkte Spalte liest, sind nur für Architects.** Eine Dimension, die bestimmt, wer welche Zeilen sieht – die Wertequelle einer eingeschränkten Spalte –, können nur ein Projekt-Architect oder ein Mandantenadministrator sowie die eigenen Workflows des Projekts ändern. Das umfasst das Hinzufügen, Verschieben, Umbenennen, Kopieren, Leeren, Laden und Wiederherstellen ihrer Knoten sowie die Dimension selbst. Alle anderen erhalten die Meldung „This dimension decides who sees which rows of ‚region‘, so only a project Architect can change it.“ Dimensionen, die keine Einschränkung liest, sind nicht betroffen.
- **Eine Quelltabelle für Gewährungen ist nur für Architects.** Die Zeilen einer Tabelle, die als [Quelle der Gewährungen](#gewährungen-an-eine-quelltabelle-binden) einer Spalte gebunden ist, können nur von einem Projekt-Architect, einem Mandantenadministrator oder den Workflows des Projekts geändert werden, ebenso das Löschen der Tabelle – über den Dateneditor, einen Import, ein Connector-Laden oder die API gleichermaßen.
- **Das Kopieren des Projekts ist nur für Architects**, und die Kopie meldet „This copy is not row-restricted.“ – das neue Projekt trägt keine Einschränkung, bis Sie eine einrichten.
- **Das Wiederherstellen einer früheren Version ist eine Änderung wie jede andere.** Das Wiederherstellen der eigenen Einstellungen des Projekts oder einer oben genannten Dimension erfordert einen Projekt-Architect. Eine Wiederherstellung gilt immer für das Element, zu dem die Version gehört, und kann daher nicht auf ein anderes Projekt gerichtet werden, um dies zu umgehen – siehe [Versionsverlauf](/de/guides/projects/managing-projects/#versionsverlauf).
- **Das Bearbeiten von Daten in einer eingeschränkten Tabelle** erfordert einen Architect, wie unter [Zeilenzugriff und Dateneditor](#zeilenzugriff-und-dateneditor) beschrieben.

Bevor die erste Spalte eines Projekts eingeschränkt wird, teilt Zeilenzugriff mit, wen das betrifft: „Restricting rows here means only Architects can change this project's workflows, steps, UDFs, schedules and notify templates. N members can change them today; they will still be able to run them.“

Ausführungen laufen genau wie bisher weiter, auch zeitgesteuerte, weil sie als Dienstidentität des Projekts laufen. Was eine Ausführung erzeugt, folgt dem Entwurf, den ihre Architects ihr gegeben haben: Eine Ausgabetabelle ohne die eingeschränkte Spalte, eine Exportdatei, eine Benachrichtigungs-E-Mail oder eine Protokollzeile wird für diejenigen, die sie lesen, nicht gefiltert.

**Beim Start einer Ausführung angegebene Werte.** Jeder, der einen Workflow ausführen kann, kann ihn mit eigenen Werten für seine Variablen starten – der [App Runner](/de/guides/workflows/use-converted-alteryx-apps/#das-app-runner-frontend) tut dies mit den Antworten seines Formulars, und die API und KI-Tools können es ebenfalls. Diese Werte gelten nur für diese Ausführung: Sie werden nie im Workflow gespeichert, und keine andere Ausführung, kein Export und kein Leser sieht sie. Da die Ausführung als Dienstidentität läuft, können die Werte ändern, was diese Ausführung liest und schreibt. Erteilen Sie die Berechtigung zum Ausführen von Workflows daher Personen, denen Sie vertrauen.

**Projekte ohne Zeilenbeschränkung.** Diese Regeln gelten erst, wenn ein Projekt eine Spalte einschränkt. In einem Projekt, das keine einschränkt, kann jeder, der die Automatisierung des Projekts ändern kann, einen Schritt oder eine benutzerdefinierte Funktion schreiben, die – als Dienstidentität des Projekts ausgeführt – den Zugriff auf das Projekt ändert und die Person selbst zu einem seiner Architects macht. Das ist beabsichtigt: Ein solches Projekt verspricht keine Zeilenisolation. Beschränken Sie Bearbeitungsrechte dort auf Personen, denen Sie als Architects vertrauen würden, oder schränken Sie eine Spalte ein.

### Dashboards synchron halten

Zeilenzugriff zeigt, wo eine Änderung auf dem Weg zu Ihren Dashboards steht, im Raster und in der Spalte **Synchronisieren** der Registerkarte „Security“ des Projekts:

| Status | Bedeutung |
|---|---|
| **Wartend** | Eine Änderung ist gespeichert und auf dem Weg zu den Dashboards. Sie ist normalerweise innerhalb von etwa einer Minute erledigt. |
| **Wird wiederholt** | Eine Übermittlung ist fehlgeschlagen und wird erneut versucht. Der Grund für den Fehler wird neben dem Status angezeigt, mit **Wiederholen**, um sofort erneut zu senden. |
| **Noch nicht angewendet** | Die Einschränkungen des Projekts wurden noch nicht an die Dashboards gesendet. |
| **Angewendet** | Der letzte Versuch, die Einschränkungen an die Dashboards zu senden, war erfolgreich. |
| **Mit Dashboards synchron** | Zeilenzugriff hat verglichen, was Dashboards durchsetzen, mit dem, was es schreiben würde, und beides stimmt überein. |
| **Dashboards weichen ab** | Dashboards setzen nicht durch, was Zeilenzugriff schreiben würde – eine Regel wurde in Superset geändert oder gelöscht, oder die veröffentlichte Ansicht einer Tabelle kann nicht geprüft werden. |
| **Fehler** | Das Senden der Einschränkungen ist fehlgeschlagen. Der Grund wird neben dem Status angezeigt. |

Sobald eine Änderung **Angewendet** erreicht, prüft das Raster sie gegen die Dashboards und wechselt zu **Mit Dashboards synchron** oder **Dashboards weichen ab**. **Dashboards weichen ab** und **Fehler** bieten beide **Wiederholen** an, wodurch die Einschränkungen des Projekts erneut gesendet werden. Kann der Status gar nicht gelesen werden, zeigt das Raster „Nicht prüfbar“ an.

Ein **Fehler**, der durch eine einzelne Tabelle verursacht wird, nennt die Tabelle und sagt, was zu tun ist – zum Beispiel eine Tabelle, die ohne ihre eingeschränkte Spalte veröffentlicht wurde („Republish or unpublish it.“), oder eine Tabelle mit einer eingeschränkten Spalte, die nicht veröffentlicht ist und die Dashboards erst filtern können, wenn sie veröffentlicht wird. Der Status bleibt auf **Fehler** und nennt die nicht veröffentlichte Tabelle, bis Sie sie veröffentlichen oder stattdessen die Spalte in einer veröffentlichten Tabelle einschränken. Eine solche Tabelle hält den Rest des Projekts nicht auf: Jede andere Tabelle wird weiter synchron gehalten.

Dashboards folgen denselben Gewährungen wie die eigenen Abfragen von PlaidCloud:

- **Jede veröffentlichte Tabelle mit der Spalte wird gefiltert**, nicht nur die Tabelle, die Sie beim Einrichten der Einschränkung angesehen haben.
- **Eine Gruppe, der nur einige Werte gewährt wurden, wird auch dann gefiltert, wenn alle anderen jede Zeile sehen**, und zwar in jeder Tabelle, deren Dashboard-Dataset existiert.
- **Projekt-Architects sehen jede Zeile**, in Dashboards ebenso wie im Tabellen-Explorer und im übrigen PlaidCloud. Das gilt für die Architect-Gruppen des Projekts und für die Architects eines Projekts, das mit einzelnen Mitgliedern geteilt wird. Der Entzug des Architect-Zugriffs wirkt in Dashboards sofort, egal ob Sie die Rolle des Mitglieds ändern, das Mitglied oder seine Gruppe aus dem Projekt entfernen, den Zugriffstyp des Projekts ändern, eine frühere Projektversion wiederherstellen oder die Gruppe löschen.
- **Änderungen der Mitgliedschaft in Sicherheitsgruppen erreichen die Dashboards von selbst.** Jemanden in PlaidCloud zu einer Gruppe hinzuzufügen oder zu entfernen, ein Mitglied zu deaktivieren oder zu löschen, eine Gruppe zu löschen oder ein neues Mitglied hinzuzufügen, das Ihren Standard-Sicherheitsgruppen beitritt, aktualisiert in jedem Projekt, das dieser Gruppe Werte gewährt, innerhalb von etwa einer Minute, was die Person in Dashboards sieht – ohne dass jemand Zeilenzugriff erneut öffnen muss. Eine Änderung der Mitgliedschaft außerhalb von PlaidCloud – direkt in Keycloak oder durch Single Sign-on, das jemanden bei der Anmeldung in eine Gruppe einordnet – erreicht die Dashboards innerhalb von etwa 15 Minuten, ohne dass etwas gespeichert oder wiederholt werden muss.

### Dimensionsgewährungen

Wenn **Dimension** die Wertequelle ist, aktivieren Sie einen Knoten, um alles darunter zu gewähren. Die Gewährung folgt der Dimension: Ein Mitglied, das unter einem aktivierten Knoten hinzugefügt wird, wird dieser Gruppe bei der nächsten Synchronisierung nach dem Speichern der Dimension gewährt, und ein Mitglied, das unter ihm herausgeschoben oder entfernt wird, wird nicht mehr gewährt – niemand muss das Raster erneut öffnen. Wenn Sie es erneut öffnen, erscheinen die Knoten, die Sie aktiviert hatten, wieder aktiviert.

Wenn Sie etwas unterhalb eines aktivierten Knotens deaktivieren, wird der Knoten deaktiviert, und die Gruppe behält nur die weiterhin aktivierten Mitglieder. Das erneute Aktivieren dieses Mitglieds aktiviert den Knoten nicht wieder – klicken Sie dafür auf das eigene Kästchen des Knotens. **Einfügen**, **Alle auswählen** und **Umkehren** aktivieren Mitglieder, nie Knoten.

Ein Dimensionsmitglied, dessen Name nicht als Zeilenzugriffswert verwendet werden kann, wird beim Speichern unter Nennung des Namens abgelehnt. Erscheint ein solches Mitglied später, werden seine Zeilen niemandem gewährt, und der Synchronisierungsstatus nennt es: „Dimension ‚…‘ member ‚…‘ cannot be used as a row access value, so its rows are not granted. Rename it in the dimension.“

### Gewährungen an eine Quelltabelle binden

Statt Werte von Hand zu aktivieren, können Sie eine eingeschränkte Spalte auf eine Quelltabelle verweisen lassen, die die Antwort bereits enthält – eine Zeile pro Gruppe und dem Wert, den sie sehen darf. Schränken Sie die Spalte zuerst im Raster ein und fügen Sie dann einen [**Zeilenzugriff festlegen**](/de/reference/workflow-steps/tables/table-set-row-access/)-Schritt zum Workflow hinzu, der die Spalte, die Quelltabelle sowie die Gruppen- und Wertespalten der Quelltabelle angibt. Die erste Ausführung des Schritts bindet die Spalte an diese Tabelle: Die von Hand gesetzten Gewährungen der Spalte werden gelöscht, und ihre Gewährungen werden aus den Zeilen der Tabelle gesetzt.

Nach der Bindung ist die Spalte **quellgesteuert**: Das Zeilenzugriff-Raster zeigt sie gesperrt an, mit einem Kennzeichen, das die Quelltabelle nennt, und das manuelle Bearbeiten ihrer Gewährungen wird abgelehnt, bis Sie auf **Bindung entfernen** klicken.

Jede weitere Ausführung des Schritts liest die Quelltabelle erneut ein und wendet die Gewährungen erneut an – planen Sie ihn nach dem Workflow, der diese Tabelle lädt oder aktualisiert, und eine in den Quelldaten hinzugefügte, entfernte oder neu zugeordnete Gruppe erreicht Zeilenzugriff bei der nächsten Ausführung, ohne dass jemand das Raster von Hand bearbeitet.

Weil die Quelltabelle bestimmt, wer was sieht, können nur ein Projekt-Architect, ein Mandantenadministrator oder die eigenen Workflows des Projekts ihre Zeilen ändern oder sie löschen. Alle anderen erhalten die Meldung „This table supplies the row access grants for ‚region‘, so only a project Architect can change its rows or delete it.“

### Einschränkungsvorlagen

Wenn Sie eine Einschränkungsform aufgebaut haben, die Sie wiederverwenden möchten – dieselbe Wertequelle, derselbe Werttyp und dieselbe Einstellung für leere Werte –, speichern Sie sie einmal und wenden Sie sie überall an, wo sie gebraucht wird, statt sie Spalte für Spalte neu aufzubauen.

- **Als Vorlage speichern…** aus einem geöffneten Zeilenzugriff-Bildschirm speichert die Form der aktuellen Spalte als benannte Vorlage auf Mandantenebene. Es wird nur die Form gespeichert – es werden keine Gewährungen mitgeführt.
- **Vorlage anwenden** bei der Spalte eines anderen Projekts beginnt diese Spalte mit der Form der Vorlage, wobei die Gewährungen jeder Gruppe leer sind und von Ihnen ausgefüllt werden.

Jeder Projekt-Architect kann Vorlagen speichern und anwenden. Das Umbenennen (**Umbenennen…**) und Löschen (**Löschen**) einer Vorlage erfordert einen Mandantenadministrator, da eine Vorlage im gesamten Mandanten geteilt wird. Das Löschen einer Vorlage lässt die Spalten, auf die sie angewendet wurde, unverändert eingeschränkt.

<Aside type="note">
Vorlagen sind Kopien, keine Verknüpfungen. Das spätere Bearbeiten einer Vorlage ändert keine Spalte, die sie bereits angewendet hat – wenden Sie die Vorlage erneut an, um eine Spalte auf den Stand einer späteren Überarbeitung zu bringen.
</Aside>

### Gewährungen aus SSO-Gruppenattributen

Eine Spalte kann ihre Gewährungen auch von Ihrem Identitätsanbieter statt von PlaidCloud beziehen. Ein Projekt-Architect aktiviert dies für eine Spalte in Zeilenzugriff über **Accept row-access grants from SSO group attributes**.

Sobald aktiviert, legt das Keycloak-Attribut `row_access.<column>` einer Sicherheitsgruppe die Werte fest, die diese Gruppe über die Spalte sehen kann – setzen Sie das Attribut in Keycloak an der Gruppe, und PlaidCloud übernimmt es automatisch für jede Gruppe, die bereits Zugriff auf das Projekt hat. In Zeilenzugriff selbst ist nichts weiter zu konfigurieren, und die Gewährungen bleiben sowohl in den eigenen Abfragen von PlaidCloud als auch in Superset-Dashboards synchron.

<Aside type="caution">
Dies gewährt nur Werte an eine Gruppe, die das Projekt bereits erreichen kann. Wenn Sie `row_access.region` zu einer Gruppe ohne Projektzugriff hinzufügen, gewährt das ihr nichts, bis die Gruppe auch Zugriff auf das Projekt erhält.
</Aside>

### Vorschau vor dem Speichern

Zeilenzugriff zeigt Ihnen, was eine Änderung bedeutet, bevor Sie sie übernehmen:

- Eine Fußzeile **Vorschau als** zeigt, wie viele der Zeilen der Tabelle eine Gruppe von der Gesamtzahl sehen würde, mit einer Auswahl der Zeilen selbst – wählen Sie eine beliebige Gruppe im Raster, um sie in der Vorschau anzuzeigen. Die Vorschau wird nach dem Speichern aktualisiert.
- Vor dem Speichern warnt Zeilenzugriff vor allem, was einen zweiten Blick wert ist: eine Gruppe ohne Markierungen, und ob das unter Ihrer Einstellung **Everyone else** bedeutet, dass sie alle oder keine Zeilen sieht; Mitglieder mit Projektzugriff, die von keiner Gruppengewährung abgedeckt sind; oder Zeilen, deren Wert in dieser Spalte leer (`NULL`) ist und die keiner Gruppe gewährt werden.

### Was ein eingeschränktes Mitglied sieht

Überall dort, wo ein eingeschränktes Mitglied eine Tabelle über ihren Namen liest, erhält es nur seine Zeilen – im Raster des Tabellen-Explorers, in Spaltenfacetten und Downloads, im Tabellen-Download-Dialog, in Apps und Tools, die als Betrachter lesen, und in Dashboards. Der Tabellen-Explorer zeigt in seiner Symbolleiste **Zeilen durch Ihren Zugriff eingeschränkt** an, wenn das angezeigte Raster nach Ihren Gewährungen gefiltert wurde, und beim Starten eines Downloads, der gefiltert wird, erscheint „Rows limited by your access.“ Ein Architect, der jede Zeile liest, sieht keinen der beiden Hinweise.

### Zeilenzugriff und selbst geschriebene Abfragen

Zeilenzugriff begrenzt, welche Zeilen eine Gruppe sehen darf, indem die Tabelle gefiltert wird, für die er definiert ist. Eine Abfrage, die jemand selbst schreibt, hat keine einzelne Tabelle, an die sich dieser Filter anhängen ließe – eine Abfrage kann beliebig viele Tabellen verknüpfen, kombinieren oder verschachteln –, daher lehnt PlaidCloud in einem Projekt, das Zeilen einschränkt, die Ausführung einer vom Aufrufer gelieferten Abfrage ab, statt Zeilen zurückzugeben, die nichts geprüft hat.

Das gilt für das Lesen über eigenes SQL, das Exportieren der Ergebnisse eigenen SQLs in eine Datei oder eine andere Datenbank und das Eingeben einer Zeilenbedingung in die Vorschau „Test row 1“ eines Fan-out-Schritts. Es gilt **nicht** für das Lesen einer Tabelle über ihren Namen, den üblichen Weg, auf dem Apps und Tools Daten lesen – diese wenden die Gewährungen an und geben die Zeilen zurück, auf die der Betrachter Anspruch hat. Eine Spaltenfacette, die als einfache Abfrage einer einzelnen Tabelle geschrieben ist, wird ebenfalls über den Namen gelesen und liefert daher die eigenen Werte des Mitglieds, statt abgelehnt zu werden.

Wer abgelehnt wird, erfährt, um welches Projekt es sich handelte, und wird auf die Leser über den Namen hingewiesen. Ein Projekt-Architect kann die Abfrage wie geschrieben ausführen und ihre Ergebnisse in jedem Format exportieren, weil ein Architect sich ohnehin jeden Wert jeder eingeschränkten Spalte selbst gewähren kann.

Der Import einer Tabellenkalkulation ist für sich genommen keine selbst geschriebene Abfrage – ein gewöhnlicher Dateiimport liest keine eingeschränkten Daten, er legt nur die neue Tabelle des Projekts aus der hochgeladenen Datei an und ist daher von Zeilenzugriff nicht betroffen. Die Ausnahme ist ein Import, dessen Datenprojektion vom Aufrufer geliefert wird: ein Ausdruck pro Spalte oder eine dynamische Excel-Zuordnung. Im interaktiven Importbildschirm werden diese genauso abgelehnt wie die oben genannten Oberflächen mit freiem SQL und erfordern einen Projekt-Architect, weil eine vom Aufrufer gelieferte Projektion eine andere Tabelle lesen könnte. Ein aus einem Workflow ausgeführter Import ist in beiden Fällen nicht betroffen, da er unter der eigenen Dienstidentität des Projekts läuft.

<Aside type="caution">
Das Einschränken Ihrer ersten Spalte in einem Projekt ändert dies für alle, die es nutzen. Wenn eine Panel-App, ein Notebook oder eine Integration in diesem Projekt Daten liest, indem sie eigenes SQL zusammensetzt, stellen Sie sie vor dem Einschränken auf das Lesen der Tabelle über ihren Namen um – andernfalls funktioniert sie für alle, die kein Architect sind, nicht mehr.
</Aside>

### Zeilenzugriff und Dateneditor

Der Dateneditor liest und schreibt eine Tabelle direkt, daher gilt Zeilenzugriff für ihn auf beiden Seiten.

Das Öffnen einer eingeschränkten Tabelle im Dateneditor zeigt nur die Zeilen, die Ihrer Sicherheitsgruppe gewährt werden – derselbe Filter, der Ihnen in ein Dashboard folgt, und er gilt auch dann, wenn die eingeschränkte Spalte nicht zu den im Raster angezeigten Spalten gehört.

Das Speichern Ihrer Änderungen erfordert **Architect** im Projekt. Ein Speichern ersetzt die Zeilen der Tabelle im Ganzen, statt sie zu lesen, und wird nicht zeilenweise gefiltert. Daher gilt das Bearbeiten von Daten in einer eingeschränkten Tabelle als Authoring-Aktion statt als Lesezugriff: Wer kein Architect ist, erfährt, dass er ihn braucht. Eine Tabelle ohne eingeschränkte Spalte wird wie zuvor bearbeitet, ebenso jedes Projekt, das keine Zeilen einschränkt.

### Zeilenanzahl und Tabellengrößen

Die Zeilenanzahl und die Speichergröße einer Tabelle beschreiben die gesamte Tabelle, nicht die Zeilen, die Sie sehen dürfen, und würden einem eingeschränkten Leser daher verraten, wie viele Zeilen jenseits seiner Gewährung existieren. In einem Projekt, das Zeilen einschränkt, sieht jeder, dessen Lesezugriffe gefiltert werden, für keine Tabelle des Projekts eine Zeilenanzahl oder Größe – in Tabellenlisten, der Suche, den Tabellendetails und Snapshots sowie über den KI-Assistenten und KI-Tools, die über MCP verbunden sind. Das umfasst jede Tabelle im Projekt, auch Tabellen ohne eingeschränkte Spalte. Auch die Gesamtwerte des Projekts sind für sie verborgen – die Gesamtzeilenanzahl und -größe auf der Startseite, in Projektlisten und der Suche sowie in den Projektdetails.

Dasselbe gilt für den Workflow-Ausführungsverlauf. Die gelesenen und geschriebenen Zeilen, die jede Ausführung und jeder Schritt aufgezeichnet hat, beschreiben ebenfalls die gesamte Tabelle, weshalb diese Angaben für dieselben Leser leer bleiben – im Ausführungsverlauf eines Workflows und eines Schritts sowie über den KI-Assistenten und KI-Tools, die über MCP verbunden sind. Für sie prüft [Weave](/de/guides/ai-assistant/weave-findings/) Schritte nicht auf Zeilen oder leere Werte, die sich von früheren Ausführungen unterscheiden, da ein Befund selbst verraten würde, dass sich die Gesamtzahl der Tabelle verändert hat.

Projekt-Architects sehen die Angaben wie zuvor, ebenso alle in einem Projekt, das keine Zeilen einschränkt.

### Sehen, was ein Mitglied sehen kann

Um zu prüfen, was eine bestimmte Person sehen kann, statt was einer Gruppe gewährt wird: Öffnen Sie **Identity → Member**, wählen Sie das Mitglied und öffnen Sie seine Registerkarte **Zeilenzugriff**. Die Spalte **Effektiver Zugriff** listet für jedes eingeschränkte Projekt und jede eingeschränkte Spalte die Werte auf, die dieses Mitglied über alle seine Gruppen zusammen sieht – einschließlich Gewährungen aus SSO-Gruppenattributen und leerer (`NULL`) Zeilen, wo die Gewährung einer Gruppe sie einschließt. Ein Projekt-Architect wird als **Sieht jede Zeile (Architect)** angezeigt, da ein Architect jede Zeile liest. Es ist dieselbe Antwort, die die eigenen Abfragen von PlaidCloud anwenden, und daher nützlich für den Support und um zu bestätigen, dass eine Änderung das Gewünschte bewirkt hat, bevor jemand ein Problem meldet.

### Klarere Fehlermeldungen

Wo Zeilenzugriff eine Aktion blockiert – eine selbst geschriebene Abfrage in einem eingeschränkten Projekt, eine Bearbeitung ohne Architect, eine Änderung an der Automatisierung, an einer Dimension oder an einer Quelltabelle für Gewährungen und die anderen oben beschriebenen Fälle –, nennt die Meldung, was eingeschränkt ist und was als Nächstes zu tun ist, etwa die Architects, die Sie fragen können, statt eines allgemeinen Fehlers.

### Zeilenzugriff wird protokolliert

Das Einschränken oder Aufheben der Einschränkung einer Spalte und das Bearbeiten der Gewährungen einer Gruppe schreiben jeweils einen Eintrag in das [Projektprotokoll](/de/get-started/tutorials/collaborate-versions-and-sharing/#das-projektprotokoll-lesen) dieses Projekts – wer die Änderung wann vorgenommen hat. Öffnen Sie **Analyze → Projects → Log** im Projekt, um ihn zu sehen. Für diese Nachverfolgung muss nichts an Zeilenzugriff aktiviert werden; sie wird genauso aufgezeichnet wie jede andere verfolgte Änderung an einem Projekt.

## Standard-Sicherheitsgruppen festlegen


Um den Aufwand beim Hinzufügen neuer Mitglieder zu verringern, legen Sie eine Reihe von Standard-Sicherheitsgruppen fest. Das liefert neuen Mitgliedern eine Basis an Sicherheitsgruppen, ohne dass jeder Person manuell Gruppen zugewiesen werden müssen. Die Einstellung steht beim Hinzufügen einer neuen Sicherheitsgruppe zur Verfügung, wenn Sie das Kontrollkästchen am unteren Rand des Fensters „Sicherheitsgruppe“ aktivieren, das „Assign to New Users by Default“ lautet.



## Sicherheitsaudit durchführen


Das Sicherheitsaudit ermöglicht es, die Gruppenmitgliedschaft über alle Mitglieder und Gruppen hinweg einzusehen.



**So führen Sie ein Sicherheitsaudit durch:**


1. Öffnen Sie Identity
2. Wählen Sie die Registerkarte „Security“
3. Klicken Sie im Dropdown-Menü auf „Security Group Audit“

Da alle Tabellen in PlaidCloud als CSV-Datei exportiert werden können, lassen sich die Zuordnungen von Gruppen und Mitgliedern auch außerhalb von PlaidCloud prüfen, sei es für historische Zwecke oder einfach zur Ansicht offline.



**So exportieren Sie aus dem Formular „Security Group Audit“:**


1. Öffnen Sie Identity
2. Wählen Sie die Registerkarte „Security“
3. Klicken Sie im Dropdown-Menü auf „Security Group Audit“
4. Klicken Sie auf das kleine Symbol ganz rechts neben „Username“ in der Tabelle
5. Klicken Sie je nach Vorliebe auf „Export CSV“ oder „Export XLXS“

## Verfügbare Berechtigungseinstellungen anzeigen


Jede im Workspace verwendete Anwendung hat bestimmte verfügbare Berechtigungen. Die Berechtigungen der Sicherheitsgruppen basieren auf diesen Anwendungsberechtigungen.


Die vollständige Liste der verfügbaren Berechtigungen jeder Anwendung kann im Security Bin angezeigt werden.



**So greifen Sie auf den Security Bin zu:**


1. Öffnen Sie Identity
2. Wählen Sie „Security“
3. Klicken Sie im Dropdown-Menü auf „Security Bins“

Um die detaillierten Sicherheitseinstellungen jeder Anwendung anzuzeigen, wählen Sie das Tag-Symbol ganz links.



Diese Informationen zu den verfügbaren Sicherheitseinstellungen dienen nur der Information. Einzelheiten zur Verwaltung von Berechtigungen finden Sie oben im Abschnitt „Sicherheitsgruppen verwalten“.
