Die Sicherheits- und Zugriffsverwaltung von PlaidCloud ist unkompliziert. Einem Mitglied wird der Zugriff gewährt oder verweigert, je nachdem, welchen Gruppen es angehört. Die Sicherheitszuordnung eines Mitglieds lässt sich einfach hinzufügen oder ändern.

<Aside>Pro Workspace ist eine unbegrenzte Anzahl von Sicherheitsgruppen zulässig. Wir empfehlen jedoch, deren Anzahl gering zu halten, um die Sicherheitsverwaltung zu vereinfachen.</Aside>



## Sicherheitsgruppen verwalten


Sicherheitsgruppen können hinzugefügt, aktualisiert oder gelöscht werden.



**So verwalten Sie Sicherheitsgruppen:**


1. Öffnen Sie Identity.
2. Wählen Sie die Registerkarte „Security“.
3. Klicken Sie im Dropdown-Menü auf „Sicherheitsgruppen“ (es wird ein Formular mit den vorhandenen Gruppen angezeigt).
4. Um eine Gruppe hinzuzufügen, klicken Sie auf „Create Security Group“.
5. Um die Berechtigungen einer Gruppe zu bearbeiten, klicken Sie auf das Symbol ganz links.

**So verwalten Sie Gruppenmitglieder:**


1. Öffnen Sie Identity.
2. Wählen Sie die Registerkarte „Security“.
3. Klicken Sie im Dropdown-Menü auf „Sicherheitsgruppen“.
4. Klicken Sie auf das Mitglieder-Symbol.
5. Ziehen Sie die gewünschten Mitglieder aus der Spalte „Unassigned Members“ in die Spalte „Assigned Members“ oder umgekehrt, um Mitglieder zu entfernen.

<Aside>Wenn Sie speichern, während die Spalte „Assigned Members“ leer ist, ändert sich nichts, und Sie werden darauf hingewiesen. Um einer Gruppe alle Mitglieder zu entziehen, entfernen Sie ihre Berechtigungen oder löschen Sie die Gruppe, statt die Mitgliedschaft zu leeren.</Aside>

<Aside>Wenn einer Gruppe über [Zeilenzugriff](#zeilenzugriff-verwalten) Zeilen gewährt werden, erreicht eine Änderung der Mitgliedschaft die Dashboards innerhalb von etwa einer Minute: Wer hinzugefügt wird, sieht dort die Zeilen der Gruppe, und wer entfernt wird, sieht sie nicht mehr. Das Deaktivieren oder Löschen eines Mitglieds und das Löschen einer Gruppe wirken sich auf dieselbe Weise aus.</Aside>

<Aside type="caution">Berechtigungen, die Sie sich selbst nicht erteilen können, bleiben unverändert, wenn Sie die Berechtigungsmatrix einer Gruppe speichern, und werden darin nicht angezeigt. Wenn Sie eine davon ändern müssen, wenden Sie sich an jemanden, der diese Berechtigung besitzt – die Matrix bearbeitet immer nur, was Sie selbst steuern.</Aside>

## Zeilenzugriff verwalten

Der Zeilenzugriff schränkt anhand der Werte einer einzelnen Spalte ein, welche Zeilen einer Tabelle eine Sicherheitsgruppe sehen kann. Beispielsweise kann eine Spalte `region` den Zugriff einschränken: Eine Gruppe mit den Gewährungen `East` und `Central` sieht nur Zeilen mit diesen Werten. Alles für ein Projekt und eine Spalte – die Spalte auswählen, die Herkunft ihrer Werte festlegen und bestimmen, welche Gruppe was sieht – erfolgt auf einem einzigen Bildschirm, und das Speichern wirkt sofort.

Zum Einrichten und Ändern des Zeilenzugriffs sind ein Projekt-Architect oder ein Tenant-Administrator erforderlich. Alle anderen, die die Registerkarte „Security“ eines Projekts öffnen, erhalten den Hinweis, dass der Zeilenzugriff nur Architects vorbehalten ist, und die unten beschriebenen Einstiegspunkte werden ihnen nicht angezeigt.

### Zeilenzugriff öffnen

Jeder Einstiegspunkt öffnet denselben Zeilenzugriff-Bildschirm:

- **Die Symbolleiste des Tabellen-Explorers** enthält eine Schaltfläche **Zeilenzugriff**, die ein Kennzeichen trägt, wenn die Tabelle bereits Zeilen einschränkt. Sie öffnet die erste eingeschränkte Spalte der Tabelle, sofern vorhanden, und Sie können zu jeder anderen Spalte der Tabelle wechseln.
- **Das Facettenmenü einer Spalte** enthält **Zeilen nach dieser Spalte einschränken…**, womit der Zeilenzugriff für diese Spalte geöffnet wird. Bei einer Spalte, die bereits Zeilen einschränkt, lautet der Eintrag **Zeilen durch diese Spalte eingeschränkt – bearbeiten…**.
- **Die Registerkarte „Security“ eines Projekts** listet jede eingeschränkte Spalte des Projekts auf, mit den Tabellen, auf die sie sich bezieht, den Gruppen mit Gewährungen und ihrem Status unter **Synchronisieren**. Wählen Sie eine Spalte zum Bearbeiten aus oder klicken Sie auf **Spalte einschränken…**, um eine neue zu beginnen: Wählen Sie eine Tabelle, dann eine Spalte. Spalten, die bereits Zeilen einschränken, sind mit einem Schloss gekennzeichnet.
- **Identity → Member**, auf der Registerkarte **Zeilenzugriff** eines Mitglieds, und **Identity → Security → Sicherheitsgruppen**, in der Zeilenzugriff-Übersicht einer Gruppe. **Zeilenzugriff öffnen** (oder **Bearbeiten**) öffnet die ausgewählte Spalte; **Hinzufügen** schränkt eine weitere Spalte im Projekt dieser Zeile ein.

Wird der Bildschirm für eine Spalte geöffnet, bleibt er bei dieser Spalte. Wird er über **Spalte einschränken…** oder **Hinzufügen** geöffnet, können Sie eine Spalte auswählen.

### Das Zeilenzugriff-Raster

So schränken Sie eine Tabelle nach einer Spalte ein:

1. Öffnen Sie den Zeilenzugriff über einen der oben genannten Einstiegspunkte und wählen Sie die Spalte aus, falls Sie ohne Spalte angekommen sind – die Auswahl bietet die tatsächlichen Spalten der Tabelle an, keinen Freitext.
2. Wählen Sie eine **Wertequelle** – **Spalte** (die eindeutigen Werte einer Tabellenspalte), **Dimension** (Knoten einer Dimension) oder **Liste** (Werte, die Sie eingeben). Der Werttyp richtet sich nach dem Datentyp der Spalte.
3. Aktivieren Sie für jede Sicherheitsgruppe die Werte, die diese Gruppe sehen darf. Das Raster listet die Gruppen mit Zugriff auf das Projekt auf sowie jede Gruppe, die bereits eine Gewährung für die Spalte besitzt.
4. Stellen Sie **Everyone else** auf **sees all rows** oder **sees no rows** – das gilt für jede Gruppe ohne Markierungen im Raster.
5. Klicken Sie auf **Speichern**.

Das Speichern wirkt sofort. Die eigenen Abfragen von PlaidCloud folgen der Änderung unmittelbar und Ihre Superset-Dashboards innerhalb von etwa einer Minute – es gibt keinen separaten Schritt zum Anwenden, und **Speichern** fragt nur dann nach, wenn eine Gewährung einen Wert enthält, den ihre Quelle nicht mehr hat (siehe unten). Der Synchronisierungsstatus des Bildschirms zeigt, wie weit die Änderung gekommen ist; siehe [Dashboards synchron halten](#dashboards-synchron-halten).

Das Raster übernimmt außerdem die Details für Sie:

- **Viele Werte.** Die Werte sind sortiert. Hat eine Spalte mehr Werte, als hineinpassen, zeigt das Raster „More values than fit here — type to search.“ an, und das Filterfeld durchsucht die gesamte Spalte, wobei jeder Wert erhalten bleibt, den eine Gruppe bereits besitzt.
- **Werte, die die Quelle nicht mehr hat.** Ein Wert, der einer Gruppe gewährt wurde, bleibt im Raster, wenn seine Quelle ihn verliert – keine Zeile der Tabelle enthält ihn mehr, die Dimension hat den Member nicht mehr, oder die Liste enthält ihn nicht mehr. Seine Spaltenüberschrift trägt ein Warnsymbol, und beim Daraufzeigen wird der Grund angezeigt. **Alle auswählen**, **Umkehren** und **Einfügen** lassen einen solchen Wert so, wie ihn jede Gruppe besitzt. Aus einer Gewährung wird nichts entfernt, solange Sie die Markierung nicht selbst aufheben: Wenn Sie auf **Speichern** klicken, während eine Gruppe noch einen solchen Wert besitzt, nennt der Zeilenzugriff die Gruppen und Werte unter **Values No Longer in the Source** und fragt nach. **Keep and Save** speichert sie unverändert, **Remove and Save** entfernt sie zuerst aus der Gewährung jeder Gruppe, und wenn Sie die Nachfrage schließen, wird nichts gespeichert. Würde das Entfernen dazu führen, dass bei einer Gruppe nichts mehr markiert ist, teilt die Nachfrage mit, ob diese Gruppe dann alle Zeilen oder keine sehen würde, gemäß **Everyone else**. Eine noch nicht gespeicherte Markierung entfällt zusammen mit ihrem Wert. Hat eine Spalte mehr Werte, als hineinpassen, oder ist ihre Tabelle noch nicht erstellt, kann der Zeilenzugriff nicht feststellen, welche Werte der Tabelle fehlen, und behält daher jeden gewährten Wert bei, ohne einen zu kennzeichnen.
- **Leere Werte.** Ein Kontrollkästchen **Leere Werte – sichtbar für jede Gruppe mit einer Gewährung** entscheidet über die Zeilen ohne Wert in der Spalte. Wenn Sie es aktivieren, sieht jede Gruppe mit irgendeiner Gewährung für die Spalte diese Zeilen.
- **Eine noch nicht erstellte Tabelle** zeigt statt einer leeren Liste **Erstellen Sie diese Tabelle zuerst (führen Sie den Workflow aus, der sie erstellt)** an.
- **Speichern wartet auf die angezeigten Werte.** Während Werte geladen werden – nachdem Sie Wertequelle, Dimension oder Tabelle gewechselt oder eine Vorlage angewendet haben –, ist **Speichern** deaktiviert, mit dem Tooltip „Save is available once this source's values load.“ Schlägt ein Ladevorgang fehl, teilt das Raster dies mit und bittet Sie, die Quelle erneut auszuwählen; es wird nichts gespeichert, bis ein Ladevorgang erfolgreich war.

### Ein Spaltenname, jede Tabelle

Eine Einschränkung gehört zu einem Spalten*namen* im Projekt, nicht zu einer einzelnen Tabelle. Sobald `region` Zeilen einschränkt, wird jede Tabelle im Projekt mit einer Spalte namens `region` danach gefiltert – in den eigenen Abfragen von PlaidCloud ebenso wie in Dashboards. Die Liste **Applies to** im Raster zeigt diese Tabellen. Sie ist schreibgeschützt, weil der Spaltenname sie bestimmt, und eine Tabelle, die Sie später mit derselben Spalte hinzufügen, ist abgedeckt, sobald sie veröffentlicht ist.

Hat keine Tabelle im Projekt eine Spalte mit diesem Namen, warnt das Fenster zusätzlich zur Anzeige von **Applies to 0 tables**, dass die Einschränkung kein Dashboard filtert, bis es eine solche Tabelle gibt. Fügen Sie die Spalte zu einer Tabelle hinzu oder korrigieren Sie den Spaltennamen, dann verschwindet die Warnung.

<Aside type="caution">
**Ein Spaltenname muss genau übereinstimmen** – einschließlich Groß-/Kleinschreibung und Leerzeichen. `Region` und `region` sind verschiedene Namen, ebenso `region` und `region ` mit einem nachgestellten Leerzeichen. Die Auswahl bietet nur tatsächliche Spaltennamen an, daher spielt dies vor allem eine Rolle, wenn eine Spalte an anderer Stelle umbenannt wird – der Zeilenzugriff warnt Sie dann und nennt die ähnlichste gefundene Spalte, statt stillschweigend nichts einzuschränken.
</Aside>

<Aside type="caution">
**Das Veröffentlichen einer Tabelle, die Zeilen einschränkt, richtet im selben Schritt ihren Dashboard-Filter ein.** Dashboards lesen eine Tabelle über ihre veröffentlichte Berichtsansicht. Wenn Sie also eine Tabelle mit einer eingeschränkten Spalte veröffentlichen oder erneut veröffentlichen, registriert PlaidCloud den Dashboard-Filter dieser Tabelle, bevor die Veröffentlichung abgeschlossen ist. Gelingt das nicht, wird die Veröffentlichung abgelehnt und alles, was dieser Versuch erstellt hat, wird zurückgesetzt, sodass eine eingeschränkte Tabelle nie ungefiltert in Dashboards landet. Eine *Ansicht* kann in einem Projekt, das Zeilen einschränkt, nicht veröffentlicht werden, weil die Abfrage einer Ansicht die eingeschränkte Spalte umbenennen oder ableiten kann. Siehe [Tabellen veröffentlichen](/de/guides/data/publish/).
</Aside>

### Eine Einschränkung aufheben

**Einschränkung aufheben** im Raster entfernt die Einschränkung nach einer Bestätigung direkt im Dialog – „Stop restricting rows by ‘region’? Every group's grant on it is removed and everyone sees its rows.“ Der Zeilenzugriff bestätigt dann „Rows in ‘region’ are no longer restricted.“ Das Superset-Dataset der Spalte wird mit entfernt, es sei denn, Diagramme verwenden es noch; in diesem Fall teilt der Zeilenzugriff mit, dass das Dataset bestehen bleibt und wie viele Diagramme es verwenden.

Eine Spalte kann nicht umbenannt oder gelöscht werden, solange sie Zeilen einschränkt. Ein Architect wird aufgefordert, die Einschränkung zuerst im Zeilenzugriff aufzuheben; alle anderen werden aufgefordert, einen Projekt-Architect zu fragen.

### Wer ein Projekt mit Zeilenzugriff ändern kann

Die Workflows, Schritte und benutzerdefinierten Funktionen eines Projekts laufen unter der eigenen Dienstidentität des Projekts, die jede Zeile liest. Wer sie ändern kann, könnte einen Schritt so gestalten, dass Zeilen, für die er keine Gewährung hat, in eine Tabelle kopiert werden, die er lesen kann. Daher schränkt das Einschränken von Zeilen in einem Projekt auch ein, wer ändern darf, was das Projekt tut. Sobald ein Projekt mindestens eine Spalte einschränkt:

- **Automatisierung ist nur Architects vorbehalten.** Nur Projekt-Architects und Tenant-Administratoren können Workflows, Schritte, benutzerdefinierte Funktionen, Zeitpläne, Workflow- und Projektvariablen sowie E-Mail-Vorlagen für Benachrichtigungen ändern – und aus demselben Grund ein Workflow-Bundle importieren, einen Alteryx-Workflow konvertieren oder in das Projekt importieren, kopieren oder wiederherstellen bzw. dessen Verbindungsumgebung, Standard-Dokumentenkonto oder ERP-Buchungsmodus ändern. Alle anderen können die Workflows des Projekts weiterhin ausführen: **Start**, **Beenden**, **Fortsetzen** und **Ausgewählte(n) Schritt(e) ausführen** bleiben verfügbar. Der Schritt-Editor, die Bearbeitungssteuerelemente des Workflows, der UDF-Editor und das Zeitplanformular öffnen sich für sie schreibgeschützt, mit einem Banner, das die Architects nennt, die Sie fragen können: „This project restricts rows, so only its Architects can change workflows, steps, UDFs, schedules, variables and notify templates. You can still run them.“
- **Dimensionen, die eine eingeschränkte Spalte liest, sind nur Architects vorbehalten.** Eine Dimension, die entscheidet, wer welche Zeilen sieht – die Wertequelle einer eingeschränkten Spalte –, kann nur von einem Projekt-Architect oder einem Tenant-Administrator geändert werden sowie von den eigenen Workflows des Projekts. Das umfasst das Hinzufügen, Verschieben, Umbenennen, Kopieren, Leeren, Laden und Wiederherstellen ihrer Knoten sowie die Dimension selbst. Alle anderen erhalten die Meldung „This dimension decides who sees which rows of ‘region’, so only a project Architect can change it.“ Dimensionen, die keine Einschränkung liest, sind nicht betroffen.
- **Die Quelltabelle der Gewährungen ist nur Architects vorbehalten.** Die Zeilen einer Tabelle, die als [Quelle der Gewährungen](#gewährungen-an-eine-quelltabelle-binden) gebunden ist, können nur von einem Projekt-Architect, einem Tenant-Administrator oder den Workflows des Projekts geändert oder gelöscht werden – gleichermaßen über den Dateneditor, einen Import, einen Connector-Ladevorgang oder die API.
- **Das Kopieren des Projekts ist nur Architects vorbehalten**, und die Kopie meldet „This copy is not row-restricted.“ – das neue Projekt enthält keine Einschränkung, bis Sie eine einrichten.
- **Das Wiederherstellen einer früheren Version ist eine Änderung wie jede andere.** Für das Wiederherstellen der eigenen Einstellungen des Projekts oder einer oben genannten Dimension ist ein Projekt-Architect erforderlich. Eine Wiederherstellung gilt immer für das Element, zu dem die Version gehört, und kann daher nicht auf ein anderes Projekt gerichtet werden, um dies zu umgehen – siehe [Versionsverlauf](/de/guides/projects/managing-projects/#versionsverlauf).
- **Das Bearbeiten von Daten in einer eingeschränkten Tabelle** erfordert einen Architect, wie unter [Zeilenzugriff und Dateneditor](#zeilenzugriff-und-dateneditor) beschrieben.
- **DataFrame-Schreibvorgänge, Datensatz-Speicherungen und Leerungen in eine eingeschränkte Tabelle ändern nur Ihre eigenen Zeilen**, sofern Sie nicht jede Zeile sehen, wie unter [Daten in eine eingeschränkte Tabelle laden](#daten-in-eine-eingeschränkte-tabelle-laden) beschrieben.

Bevor die erste Spalte eines Projekts eingeschränkt wird, teilt der Zeilenzugriff mit, wen dies betrifft: „Restricting rows here means only Architects can change this project's workflows, steps, UDFs, schedules and notify templates. N members can change them today; they will still be able to run them.“

Ausführungen funktionieren genau wie zuvor weiter, auch geplante, weil sie unter der Dienstidentität des Projekts laufen. Was eine Ausführung erzeugt, folgt dem Design, das ihre Architects ihr gegeben haben: Eine Ausgabetabelle ohne die eingeschränkte Spalte, eine Exportdatei, eine Benachrichtigungs-E-Mail oder eine Protokollzeile wird für diejenigen, die sie lesen, nicht gefiltert.

**Beim Start einer Ausführung angegebene Werte.** Wer einen Workflow ausführen darf, kann ihn mit eigenen Werten für seine Variablen starten – der [App Runner](/de/guides/workflows/use-converted-alteryx-apps/#das-app-runner-frontend) tut dies mit den Antworten seines Formulars, und die API und die KI-Tools können es ebenfalls. Diese Werte gelten nur für diese eine Ausführung: Sie werden nie im Workflow gespeichert, und keine andere Ausführung, kein Export und kein Leser sieht sie. Da die Ausführung unter der Dienstidentität läuft, können die Werte ändern, was diese Ausführung liest und schreibt. Erteilen Sie die Berechtigung zum Ausführen von Workflows daher Personen, denen Sie vertrauen.

**Projekte ohne Zeilenzugriff.** Diese Regeln gelten erst, wenn ein Projekt eine Spalte einschränkt. In einem Projekt ohne Einschränkung kann jeder, der die Automatisierung des Projekts ändern darf, einen Schritt oder eine benutzerdefinierte Funktion schreiben, die – unter der Dienstidentität des Projekts ausgeführt – den Zugriff auf das Projekt ändert und die Person selbst zu einem seiner Architects macht. Das ist beabsichtigt: Ein solches Projekt verspricht keine Zeilenisolierung. Beschränken Sie Autorenrechte dort auf Personen, denen Sie als Architects vertrauen würden, oder schränken Sie eine Spalte ein.

### Dashboards synchron halten

Der Zeilenzugriff zeigt, wo eine Änderung auf dem Weg zu Ihren Dashboards steht, im Raster und in der Spalte **Synchronisieren** auf der Registerkarte „Security“ des Projekts:

| Status | Bedeutung |
|---|---|
| **Wartend** | Eine Änderung ist gespeichert und auf dem Weg zu den Dashboards. Sie ist normalerweise innerhalb von etwa einer Minute erledigt. |
| **Wird wiederholt** | Ein Sendevorgang ist fehlgeschlagen und wird erneut versucht. Der Grund für den Fehler wird neben dem Status angezeigt, mit **Wiederholen**, um sofort erneut zu senden. |
| **Noch nicht angewendet** | Die Einschränkungen des Projekts wurden noch nicht an die Dashboards gesendet. |
| **Angewendet** | Der letzte Versuch, die Einschränkungen an die Dashboards zu senden, war erfolgreich. |
| **Mit Dashboards synchron** | Der Zeilenzugriff hat verglichen, was die Dashboards durchsetzen, mit dem, was er schreiben würde, und beides stimmt überein. |
| **Dashboards weichen ab** | Die Dashboards setzen nicht durch, was der Zeilenzugriff schreiben würde – eine Regel wurde in Superset geändert oder gelöscht, oder die veröffentlichte Ansicht einer Tabelle kann nicht geprüft werden. |
| **Fehler** | Das Senden der Einschränkungen ist fehlgeschlagen. Der Grund wird neben dem Status angezeigt. |

Sobald eine Änderung **Angewendet** erreicht, prüft das Raster sie gegen die Dashboards und wechselt zu **Mit Dashboards synchron** oder **Dashboards weichen ab**. **Dashboards weichen ab** und **Fehler** bieten beide **Wiederholen** an, wodurch die Einschränkungen des Projekts erneut gesendet werden. Kann der Status überhaupt nicht gelesen werden, zeigt das Raster „Synchronisierungsstatus nicht prüfbar.“ an.

Ein **Fehler**, der durch eine einzelne Tabelle verursacht wird, nennt die Tabelle und sagt, was zu tun ist – zum Beispiel eine Tabelle, die ohne ihre eingeschränkte Spalte veröffentlicht wurde („Republish or unpublish it.“), oder eine Tabelle mit einer eingeschränkten Spalte, die nicht veröffentlicht ist und die Dashboards erst filtern können, wenn sie es ist. Der Status bleibt bei **Fehler** und nennt die nicht veröffentlichte Tabelle, bis Sie sie veröffentlichen oder stattdessen die Spalte einer veröffentlichten Tabelle einschränken. Eine solche Tabelle hält den Rest des Projekts nicht auf: Alle anderen Tabellen werden auf dem aktuellen Stand gehalten.

Dashboards folgen denselben Gewährungen wie die eigenen Abfragen von PlaidCloud:

- **Jede veröffentlichte Tabelle mit der Spalte wird gefiltert**, nicht nur die Tabelle, die Sie beim Einrichten der Einschränkung angesehen haben.
- **Eine Gruppe, der nur einige Werte gewährt wurden, wird gefiltert, auch wenn alle anderen jede Zeile sehen**, und zwar in jeder Tabelle, deren Dashboard-Dataset existiert.
- **Projekt-Architects sehen jede Zeile**, in Dashboards ebenso wie im Tabellen-Explorer und im Rest von PlaidCloud. Das gilt für die Architect-Gruppen des Projekts und für die Architects eines Projekts, das mit einzelnen Mitgliedern geteilt wird. Das Entziehen des Architect-Zugriffs wirkt in Dashboards sofort, unabhängig davon, ob Sie die Rolle des Mitglieds ändern, das Mitglied oder seine Gruppe aus dem Projekt entfernen, den Zugriffstyp des Projekts ändern, eine frühere Projektversion wiederherstellen oder die Gruppe löschen.
- **Änderungen an der Mitgliedschaft in Sicherheitsgruppen erreichen die Dashboards von selbst.** Wenn Sie in PlaidCloud jemanden zu einer Gruppe hinzufügen oder entfernen, ein Mitglied deaktivieren oder löschen, eine Gruppe löschen oder ein neues Mitglied hinzufügen, das Ihren Standard-Sicherheitsgruppen beitritt, wird das, was die Person in Dashboards sieht, innerhalb von etwa einer Minute aktualisiert – in jedem Projekt, das dieser Gruppe Werte gewährt –, ohne dass jemand den Zeilenzugriff erneut öffnen muss. Eine Änderung der Mitgliedschaft, die außerhalb von PlaidCloud erfolgt – direkt in Keycloak oder dadurch, dass Single Sign-on jemanden bei der Anmeldung in eine Gruppe einordnet –, erreicht die Dashboards innerhalb von etwa 15 Minuten, ohne dass etwas gespeichert oder wiederholt werden muss.

### Dimensionsgewährungen

Wenn **Dimension** die Wertequelle ist, aktivieren Sie einen Knoten, um alles darunter zu gewähren. Die Gewährung folgt der Dimension: Ein Member, das unter einem aktivierten Knoten hinzugefügt wird, wird dieser Gruppe bei der nächsten Synchronisierung nach dem Speichern der Dimension gewährt, und ein Member, das darunter herausverschoben oder entfernt wird, wird nicht mehr gewährt – niemand muss das Raster erneut öffnen. Wenn Sie es erneut öffnen, erscheinen die Knoten, die Sie aktiviert hatten, wieder aktiviert.

Ein Member, das Sie einzeln und nicht über einen Knoten aktiviert haben, bleibt gewährt, wenn es aus der Dimension entfernt wird, und das Raster kennzeichnet es als Wert, den die Quelle nicht mehr hat.

Wenn Sie etwas unterhalb eines aktivierten Knotens deaktivieren, wird der Knoten deaktiviert, und die Gruppe behält nur die Member, die noch aktiviert sind. Wenn Sie dieses Member erneut aktivieren, wird der Knoten nicht wieder aktiviert – klicken Sie dafür auf das Kontrollkästchen des Knotens selbst. **Einfügen**, **Alle auswählen** und **Umkehren** aktivieren Member, niemals Knoten.

Ein Dimensions-Member, dessen Name nicht als Zeilenzugriffswert verwendet werden kann, wird beim Speichern abgelehnt, wobei es genannt wird. Erscheint ein solches Member später, werden seine Zeilen niemandem gewährt, und der Synchronisierungsstatus nennt es: „Dimension ‘…’ member ‘…’ cannot be used as a row access value, so its rows are not granted. Rename it in the dimension.“

### Gewährungen an eine Quelltabelle binden

Statt Werte von Hand zu aktivieren, können Sie eine eingeschränkte Spalte auf eine Quelltabelle
verweisen lassen, die die Antwort bereits enthält – eine Zeile pro Gruppe und dem Wert, den sie sehen darf.
Schränken Sie die Spalte zuerst im Raster ein und fügen Sie dann einen
[**Zeilenzugriff festlegen**](/de/reference/workflow-steps/tables/table-set-row-access/)-Workflow-Schritt hinzu,
der die Spalte, die Quelltabelle sowie die Gruppen- und Wertespalte der Quelltabelle benennt. Die erste Ausführung
des Schritts bindet die Spalte an diese Tabelle: Die von Hand gesetzten Gewährungen der Spalte werden gelöscht,
und ihre Gewährungen werden aus den Zeilen der Tabelle gesetzt.

Nach der Bindung ist die Spalte **quellengesteuert**: Das Zeilenzugriff-Raster zeigt sie gesperrt an, mit einem Kennzeichen,
das die Quelltabelle nennt, und das manuelle Bearbeiten ihrer Gewährungen wird abgelehnt, bis Sie auf **Bindung entfernen** klicken.

Jede weitere Ausführung des Schritts liest die Quelltabelle erneut ein und wendet die Gewährungen erneut an – planen Sie ihn
nach dem Workflow, der diese Tabelle lädt oder aktualisiert. Eine Gruppe, die in den Quelldaten hinzugefügt, entfernt oder neu zugewiesen wird,
erreicht den Zeilenzugriff bei der nächsten Ausführung, ohne dass jemand das Raster von Hand bearbeitet.

Da die Quelltabelle bestimmt, wer was sieht, können nur ein Projekt-Architect, ein Tenant-Administrator oder die
eigenen Workflows des Projekts ihre Zeilen ändern oder sie löschen. Alle anderen erhalten die Meldung „This table
supplies the row access grants for ‘region’, so only a project Architect can change its rows or
delete it.“

### Einschränkungsvorlagen

Wenn Sie eine Einschränkungsform aufgebaut haben, die Sie wiederverwenden möchten – dieselbe Wertequelle, derselbe Werttyp und
dieselbe Einstellung für leere Werte –, speichern Sie sie einmal und wenden Sie sie überall an, wo sie gebraucht wird, statt sie
Spalte für Spalte neu aufzubauen.

- **Als Vorlage speichern…** speichert im geöffneten Zeilenzugriff-Bildschirm die Form der aktuellen Spalte als
  benannte Vorlage auf Tenant-Ebene. Es wird nur die Form gespeichert – Gewährungen werden nicht mitgenommen.
- **Vorlage anwenden** startet bei der Spalte eines anderen Projekts mit der Form der Vorlage,
  wobei die Gewährungen jeder Gruppe leer sind und von Ihnen ausgefüllt werden können.

Jeder Projekt-Architect kann Vorlagen speichern und anwenden. Zum Umbenennen (**Umbenennen…**) und Löschen
(**Löschen**) einer Vorlage ist ein Tenant-Administrator erforderlich, da eine Vorlage für den gesamten Tenant gilt.
Wird eine Vorlage gelöscht, bleiben die Spalten, auf die sie angewendet wurde, wie sie sind eingeschränkt.

<Aside type="note">
Vorlagen sind Kopien, keine Verknüpfungen. Eine nachträgliche Bearbeitung einer Vorlage ändert keine Spalte,
die sie bereits angewendet hat – wenden Sie die Vorlage erneut an, um eine Spalte auf den Stand einer späteren
Überarbeitung zu bringen.
</Aside>

### Gewährungen aus SSO-Gruppenattributen

Eine Spalte kann ihre Gewährungen auch von Ihrem Identitätsanbieter statt von PlaidCloud beziehen. Ein
Projekt-Architect aktiviert dies für eine Spalte im Zeilenzugriff, indem er **Accept row-access grants from
SSO group attributes** einschaltet.

Sobald dies aktiviert ist, legt das Keycloak-Attribut `row_access.<column>` einer Sicherheitsgruppe die Werte fest, die
diese Gruppe über diese Spalte sehen kann – setzen Sie das Attribut in Keycloak an der Gruppe, und PlaidCloud
übernimmt es automatisch für jede Gruppe, die bereits Zugriff auf das Projekt hat. Im Zeilenzugriff selbst ist nichts
weiter zu konfigurieren, und die Gewährungen bleiben sowohl in den eigenen Abfragen von PlaidCloud als auch in Superset-Dashboards synchron.

<Aside type="caution">
Dies gewährt nur Werte an eine Gruppe, die das Projekt bereits erreichen kann. Wenn Sie `row_access.region`
zu einer Gruppe ohne Projektzugriff hinzufügen, gewährt das ihr nichts, bis die Gruppe auch Zugriff auf das
Projekt erhält.
</Aside>

### Vorschau vor dem Speichern

Der Zeilenzugriff zeigt Ihnen, was eine Änderung bedeutet, bevor Sie sie übernehmen:

- Eine Fußzeile **Vorschau als** zeigt, wie viele der Zeilen der Tabelle eine Gruppe von der Gesamtzahl sehen würde, mit einer Stichprobe der Zeilen selbst – wählen Sie eine beliebige Gruppe im Raster, um sie in der Vorschau anzuzeigen. Die Vorschau wird nach dem Speichern aktualisiert.
- Vor dem Speichern warnt der Zeilenzugriff vor allem, was einen zweiten Blick wert ist: eine Gruppe ohne Markierungen und ob das bedeutet, dass sie gemäß Ihrer Einstellung **Everyone else** alle Zeilen oder keine sieht; Mitglieder mit Projektzugriff, die von keiner Gewährung einer Gruppe abgedeckt werden; oder Zeilen, deren Wert in dieser Spalte leer (`NULL`) ist und die keiner Gruppe gewährt werden.

### Was ein eingeschränktes Mitglied sieht

Überall dort, wo ein eingeschränktes Mitglied eine Tabelle über ihren Namen liest, erhält es nur seine Zeilen – im Raster des Tabellen-Explorers, in den Spaltenfacetten und Downloads, im Tabellen-Download-Dialog, in Apps und Tools, die als Betrachter lesen, sowie in Dashboards. Der Tabellen-Explorer zeigt **Zeilen durch Ihren Zugriff eingeschränkt** in seiner Symbolleiste an, wenn das Raster, das Sie ansehen, anhand Ihrer Gewährungen gefiltert wurde, und beim Starten eines Downloads, der gefiltert wird, erscheint „Zeilen durch Ihren Zugriff eingeschränkt.“ Ein Architect, der jede Zeile liest, sieht keinen der beiden Hinweise.

### Zeilenzugriff und selbst geschriebene Abfragen

Der Zeilenzugriff begrenzt, welche Zeilen eine Gruppe sehen darf, indem er die Tabelle filtert, für die er definiert ist. Eine Abfrage, die jemand selbst schreibt, hat keine einzelne Tabelle, an die dieser Filter angehängt werden kann – eine Abfrage kann beliebig viele Tabellen verknüpfen, kombinieren oder verschachteln. Daher lehnt PlaidCloud in einem Projekt, das Zeilen einschränkt, die Ausführung einer vom Aufrufer gelieferten Abfrage ab, statt Zeilen zurückzugeben, die nichts geprüft hat.

Das betrifft das Lesen über Ihr eigenes SQL, das Exportieren der Ergebnisse Ihres eigenen SQL in eine Datei oder in eine andere Datenbank und das Eingeben einer Zeilenbedingung in die Vorschau „Test row 1“ eines Fan-out-Schritts. Es betrifft **nicht** das Lesen einer Tabelle über ihren Namen, was der übliche Weg ist, auf dem Apps und Tools Daten lesen – diese wenden die Gewährungen an und geben die Zeilen zurück, auf die der Betrachter Anspruch hat. Eine Spaltenfacette, die als einfache Abfrage einer einzelnen Tabelle geschrieben ist, wird ebenfalls über den Namen gelesen, sodass sie die eigenen Werte des Mitglieds zurückgibt, statt abgelehnt zu werden.

Wer abgelehnt wird, erfährt, um welches Projekt es sich handelte, und wird auf die Leser über den Namen hingewiesen. Ein Projekt-Architect kann die Abfrage wie geschrieben ausführen und ihre Ergebnisse in jedem Format exportieren, weil ein Architect sich bereits jeden Wert jeder eingeschränkten Spalte selbst gewähren kann.

Der Import einer Tabellenkalkulation ist für sich genommen keine selbst geschriebene Abfrage – ein gewöhnlicher Dateiimport liest überhaupt keine eingeschränkten Daten, sondern erstellt lediglich die neue Tabelle des Projekts aus der hochgeladenen Datei und ist daher vom Zeilenzugriff nicht betroffen. Die Ausnahme ist ein Import, dessen Datenprojektion vom Aufrufer geliefert wird: ein Ausdruck pro Spalte oder eine dynamische Excel-Zuordnung. Auf dem interaktiven Importbildschirm werden diese auf dieselbe Weise abgelehnt wie die oben genannten Oberflächen mit freiem SQL und erfordern einen Projekt-Architect, weil eine vom Aufrufer gelieferte Projektion eine andere Tabelle lesen könnte. Ein Import, der aus einem Workflow ausgeführt wird, ist in beiden Fällen nicht betroffen, weil er unter der eigenen Dienstidentität des Projekts läuft.

<Aside type="caution">
Das Einschränken Ihrer ersten Spalte in einem Projekt ändert dies für alle, die es verwenden. Wenn eine Panel-App, ein Notebook oder eine Integration in diesem Projekt Daten liest, indem sie eigenes SQL zusammensetzt, stellen Sie sie vor dem Einschränken darauf um, die Tabelle über ihren Namen zu lesen – andernfalls funktioniert sie für alle, die keine Architects sind, nicht mehr.
</Aside>

### Zeilenzugriff und Dateneditor

Der Dateneditor liest und schreibt eine Tabelle direkt, daher gilt der Zeilenzugriff für ihn auf beiden Seiten.

Wenn Sie eine eingeschränkte Tabelle im Dateneditor öffnen, werden nur die Zeilen angezeigt, die Ihre Sicherheitsgruppe gewährt bekommen hat – derselbe Filter, der Ihnen in ein Dashboard folgt, und er gilt auch dann, wenn die eingeschränkte Spalte nicht zu den im Raster angezeigten Spalten gehört.

Zum Speichern Ihrer Änderungen ist **Architect** im Projekt erforderlich. Ein Speichervorgang ersetzt die Zeilen der Tabelle vollständig, statt sie zu lesen, und wird nicht Zeile für Zeile gefiltert. Daher gilt das Bearbeiten von Daten in einer eingeschränkten Tabelle als Authoring-Aktion und nicht als Lesezugriff: Wer kein Architect ist, erhält die Meldung, dass er diese Rolle benötigt. Eine Tabelle ohne eingeschränkte Spalte wird wie bisher bearbeitet, ebenso jedes Projekt, das keine Zeilen einschränkt.

### Daten in eine eingeschränkte Tabelle laden

Wenn der Zeilenzugriff die Zeilen begrenzt, die Sie sehen, wirkt das Schreiben eines DataFrames in eine eingeschränkte Tabelle oder deren Leeren mit dem Python-Client (`PlaidConnection`) sowie das Speichern von Datensätzen darin oder deren Leeren über die REST-API nur auf Ihre eigenen Zeilen. Das Ersetzen der Daten der Tabelle ersetzt nur die Zeilen, die Sie sehen können, das Leeren leert nur diese Zeilen, und das Anhängen fügt Zeilen hinzu; alle anderen Zeilen bleiben unverändert.

Ein Ladevorgang mit einer Zeile außerhalb Ihres Zugriffs wird abgelehnt, bevor sich etwas ändert, und der Fehler nennt jeden Wert außerhalb Ihres Zugriffs mit der Anzahl der Zeilen, die ihn enthalten. Eine Zeile, in der die eingeschränkte Spalte fehlt, wird als leer in dieser Spalte geprüft und daher abgelehnt, sofern Ihr Zugriff keine leeren Zeilen einschließt. Das Ersetzen der Daten auf eine Weise, die den Typ einer Spalte ändern würde, wird ebenfalls abgelehnt; bitten Sie einen Projekt-Architect, diese Änderung vorzunehmen.

Projekt-Architects, Mitglieder, deren Gewährungen jede Zeile abdecken, und Workflow-Ausführungen, die unter der Dienstidentität des Projekts laufen, schreiben wie bisher die gesamte Tabelle. Eine Tabelle ohne eingeschränkte Spalte ist nicht betroffen.

Jeder dieser Schreibvorgänge, den eine Person in einer beliebigen Tabelle vornimmt, wird im Sicherheitsprotokoll festgehalten. Workflow-Ausführungen werden dort nicht aufgezeichnet.

### Zeilenanzahlen und Tabellengrößen

Die Zeilenanzahl und die Speichergröße einer Tabelle beschreiben die gesamte Tabelle, nicht die Zeilen, die Sie sehen dürfen, und würden einem eingeschränkten Leser daher verraten, wie viele Zeilen jenseits seiner Gewährung existieren. In einem Projekt, das Zeilen einschränkt, sieht jeder, dessen Lesezugriffe gefiltert werden, für keine Tabelle des Projekts eine Zeilenanzahl oder Größe – in Tabellenlisten, der Suche, den Tabellendetails und Snapshots sowie über den KI-Assistenten und die über MCP verbundenen KI-Tools. Das gilt für jede Tabelle im Projekt, auch für Tabellen ohne eingeschränkte Spalte. Auch die Gesamtwerte des Projekts sind für sie ausgeblendet – die Gesamtzeilenanzahl und -größe auf der Startseite, in Projektlisten und der Suche sowie in den Projektdetails.

Dasselbe gilt für den Ausführungsverlauf von Workflows. Die gelesenen und geschriebenen Zeilen, die jede Ausführung und jeder Schritt aufgezeichnet hat, beschreiben ebenfalls die gesamte Tabelle, daher bleiben diese Angaben für dieselben Leser leer – im Ausführungsverlauf eines Workflows und eines Schritts sowie über den KI-Assistenten und die über MCP verbundenen KI-Tools. Für sie prüft [Weave](/de/guides/ai-assistant/weave-findings/) Schritte nicht darauf, ob Zeilen- oder Leerwerte von früheren Ausführungen abweichen, da ein Befund selbst verraten würde, dass sich die Gesamtanzahl der Tabelle verändert hat.

Projekt-Architects sehen die Angaben wie bisher, ebenso alle in einem Projekt, das keine Zeilen einschränkt.

### Sehen, was ein Mitglied sehen kann

Um zu prüfen, was eine bestimmte Person sehen kann, statt was einer Gruppe gewährt wird: Öffnen Sie **Identity → Member**, wählen Sie das Mitglied aus und öffnen Sie seine Registerkarte **Zeilenzugriff**. Die Spalte **Effektiver Zugriff** listet für jedes eingeschränkte Projekt und jede eingeschränkte Spalte die Werte auf, die dieses Mitglied über alle seine Gruppen zusammen sieht – einschließlich Gewährungen aus SSO-Gruppenattributen und leerer (`NULL`) Zeilen, wo die Gewährung einer Gruppe sie einschließt. Ein Projekt-Architect wird als **Sieht jede Zeile (Architect)** angezeigt, da ein Architect jede Zeile liest. Es ist dieselbe Antwort, die die eigenen Abfragen von PlaidCloud anwenden, daher ist sie nützlich für den Support und um zu bestätigen, dass eine Änderung das bewirkt hat, was Sie wollten, bevor jemand ein Problem meldet.

### Klarere Fehlermeldungen

Wo der Zeilenzugriff eine Aktion blockiert – eine selbst geschriebene Abfrage in einem eingeschränkten Projekt, eine Bearbeitung ohne Architect, eine Änderung an der Automatisierung, an einer Dimension oder an einer Quelltabelle der Gewährungen sowie die anderen oben beschriebenen Fälle –, nennt die Meldung, was eingeschränkt ist und was als Nächstes zu tun ist, etwa welche Architects Sie fragen können, statt eines allgemeinen Fehlers.

### Der Zeilenzugriff wird protokolliert

Das Einschränken oder Aufheben der Einschränkung einer Spalte sowie das Bearbeiten der Gewährungen einer Gruppe schreiben jeweils einen Eintrag in das [Projektprotokoll](/de/get-started/tutorials/collaborate-versions-and-sharing/#das-projektprotokoll-lesen) dieses Projekts – wer die Änderung wann vorgenommen hat. Öffnen Sie **Analyze → Projects → Log** im Projekt, um ihn zu sehen. Dafür muss nichts am Zeilenzugriff aktiviert werden; er wird genauso aufgezeichnet wie jede andere nachverfolgte Änderung an einem Projekt.

## Standard-Sicherheitsgruppen festlegen


Um den Aufwand beim Hinzufügen neuer Mitglieder zu verringern, legen Sie eine Reihe von Standard-Sicherheitsgruppen fest. Dies stellt neuen Mitgliedern eine Grundausstattung an Sicherheitsgruppen bereit, ohne dass jede Person manuell zugewiesen werden muss. Die Einstellung ist beim Hinzufügen einer neuen Sicherheitsgruppe verfügbar, wenn Sie unten im Fenster „Sicherheitsgruppe“ das Kontrollkästchen „Assign to New Users by Default“ aktivieren.



## Sicherheitsprüfung durchführen


Die Funktion zur Sicherheitsprüfung ermöglicht es, die Gruppenmitgliedschaft über alle Mitglieder und Gruppen hinweg einzusehen.



**So führen Sie eine Sicherheitsprüfung durch:**


1. Öffnen Sie Identity.
2. Wählen Sie die Registerkarte „Security“.
3. Klicken Sie im Dropdown-Menü auf „Security Group Audit“.

Da alle Tabellen in PlaidCloud als CSV-Datei exportiert werden können, lassen sich die Zuordnungen von Gruppen und Mitgliedern außerhalb von PlaidCloud überprüfen, sei es zu historischen Zwecken oder einfach für etwas Offline-Lesevergnügen.



**So exportieren Sie aus dem Formular „Security Group Audit“:**


1. Öffnen Sie Identity.
2. Wählen Sie die Registerkarte „Security“.
3. Klicken Sie im Dropdown-Menü auf „Security Group Audit“.
4. Klicken Sie auf das kleine Symbol ganz rechts neben „Username“ in der Tabelle.
5. Klicken Sie je nach Wunsch auf „Export CSV“ oder „Export XLXS“.

## Verfügbare Berechtigungseinstellungen anzeigen


Jede im Workspace verwendete Anwendung hat spezifische verfügbare Berechtigungen. Die Berechtigungen der Sicherheitsgruppen basieren auf diesen Anwendungsberechtigungen.


Die vollständige Liste der verfügbaren Berechtigungen für jede Anwendung kann im Security Bin eingesehen werden.



**So greifen Sie auf den Security Bin zu:**


1. Öffnen Sie Identity.
2. Wählen Sie „Security“.
3. Klicken Sie im Dropdown-Menü auf „Security Bins“.

Um die detaillierten Sicherheitseinstellungen für jede Anwendung anzuzeigen, wählen Sie das Tag-Symbol ganz links.



Diese Informationen zu den verfügbaren Sicherheitseinstellungen dienen nur zur Information. Details zur Verwaltung von Berechtigungen finden Sie im obigen Abschnitt „Sicherheitsgruppen und Zuweisungen verwalten“.
