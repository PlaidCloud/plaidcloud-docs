Die Sicherheits- und Zugriffsverwaltung von PlaidCloud ist unkompliziert. Ein Mitglied erhält oder verliert den Zugriff anhand der Gruppen, denen es zugeordnet ist. Die Sicherheitszuordnung eines Mitglieds lässt sich einfach hinzufügen oder ändern.

<Aside>Jeder Workspace darf beliebig viele Sicherheitsgruppen enthalten, wir empfehlen jedoch, ihre Anzahl gering zu halten, um die Sicherheitsverwaltung zu erleichtern.</Aside>



## Sicherheitsgruppen verwalten


Sicherheitsgruppen können hinzugefügt, aktualisiert oder gelöscht werden.



**So verwalten Sie Sicherheitsgruppen:**


1. Öffnen Sie Identity
2. Wählen Sie die Registerkarte „Security“
3. Klicken Sie im Dropdown-Menü auf „Security Groups“ (dadurch wird ein Formular mit den vorhandenen Gruppen angezeigt)
4. Um eine Gruppe hinzuzufügen, klicken Sie auf „Create Security Group“
5. Um die Berechtigungen einer Gruppe zu bearbeiten, klicken Sie auf das Symbol ganz links

**So verwalten Sie Gruppenmitglieder:**


1. Öffnen Sie Identity
2. Wählen Sie die Registerkarte „Security“
3. Klicken Sie im Dropdown-Menü auf „Security Groups“
4. Klicken Sie auf das Symbol „Member“
5. Ziehen Sie die gewünschten Mitglieder aus der Spalte „Unassigned Members“ in die Spalte „Assigned Members“ oder umgekehrt, um Mitglieder zu entfernen

<Aside>Das Speichern bei leerer Spalte „Assigned Members“ ändert nichts und teilt Ihnen das mit. Um eine Gruppe allen Mitgliedern zu entziehen, entfernen Sie ihre Berechtigungen oder löschen Sie die Gruppe, anstatt ihre Mitgliederliste zu leeren.</Aside>

<Aside>Wenn eine Gruppe über den [Zeilenzugriff](#zeilenzugriff-verwalten) Zeilen erhält, erreicht eine Änderung der Mitgliedschaft die Dashboards innerhalb von etwa einer Minute: Wer hinzugefügt wird, sieht dort die Zeilen der Gruppe, und wer entfernt wird, sieht sie nicht mehr. Das Deaktivieren oder Löschen eines Mitglieds und das Löschen einer Gruppe wirken auf dieselbe Weise.</Aside>

<Aside type="caution">Berechtigungen, die Sie sich selbst nicht erteilen können, bleiben beim Speichern der Berechtigungsmatrix einer Gruppe unberührt und werden in ihr nicht angezeigt. Wenn Sie eine davon ändern müssen, wenden Sie sich an jemanden, der diese Berechtigung besitzt – die Matrix bearbeitet immer nur das, was Sie steuern können.</Aside>

## Zeilenzugriff verwalten

Der Zeilenzugriff schränkt anhand der Werte einer Spalte ein, welche Zeilen einer Tabelle eine Sicherheitsgruppe sehen kann. Beispielsweise kann eine Spalte `region` den Zugriff einschränken, sodass eine Gruppe mit den Werten `East` und `Central` nur Zeilen mit diesen Werten sieht. Alles für ein Projekt und eine Spalte – die Auswahl der Spalte, die Festlegung der Herkunft ihrer Werte und die Entscheidung, welche Gruppe was sieht – geschieht in einem einzigen Bildschirm, und das Speichern wirkt sofort.

Das Einrichten und Ändern des Zeilenzugriffs erfordert einen Projekt-Architect oder einen Mandantenadministrator. Alle anderen, die die Registerkarte „Security“ eines Projekts öffnen, erfahren, dass der Zeilenzugriff nur für Architects vorgesehen ist, und die unten genannten Einstiegspunkte erscheinen für sie nicht.

### Zeilenzugriff öffnen

Jeder Einstiegspunkt öffnet denselben Bildschirm für den Zeilenzugriff:

- **Die Symbolleiste des Tabellen-Explorers** enthält die Schaltfläche **Zeilenzugriff**, mit einem Hinweis-Badge, wenn die Tabelle bereits Zeilen einschränkt. Sie öffnet sich auf der ersten eingeschränkten Spalte der Tabelle, sofern vorhanden, und Sie können zu jeder anderen Spalte der Tabelle wechseln.
- **Das Facettenmenü einer Spalte** enthält **Zeilen nach dieser Spalte einschränken…**, wodurch der Zeilenzugriff für diese Spalte geöffnet wird. Bei einer Spalte, die bereits Zeilen einschränkt, lautet der Eintrag **Zeilen durch diese Spalte eingeschränkt – bearbeiten…**.
- **Die Registerkarte „Security“ eines Projekts** listet jede eingeschränkte Spalte des Projekts auf, mit den Tabellen, für die sie gilt, den Gruppen mit Gewährungen und ihrem Status unter **Synchronisieren**. Wählen Sie eine Spalte aus, um sie zu bearbeiten, oder klicken Sie auf **Spalte einschränken…**, um eine neue zu beginnen: Wählen Sie eine Tabelle und dann eine Spalte. Spalten, die bereits Zeilen einschränken, sind mit einem Schloss markiert.
- **Identity → Member**, auf der Registerkarte **Zeilenzugriff** eines Mitglieds, und **Identity → Security → Security Groups**, in der Zeilenzugriff-Übersicht einer Gruppe. **Zeilenzugriff öffnen** (oder **Bearbeiten**) öffnet die ausgewählte Spalte; **Hinzufügen** schränkt eine weitere Spalte im Projekt dieser Zeile ein.

Wenn der Bildschirm auf einer Spalte geöffnet wird, bleibt er bei dieser Spalte. Wird er mit **Spalte einschränken…** oder **Hinzufügen** geöffnet, können Sie eine Spalte auswählen.

### Das Zeilenzugriff-Raster

So schränken Sie eine Tabelle nach einer Spalte ein:

1. Öffnen Sie den Zeilenzugriff über einen der oben genannten Einstiegspunkte und wählen Sie die Spalte, falls Sie nicht bereits mit einer angekommen sind – die Auswahl bietet die tatsächlichen Spalten der Tabelle an, keinen freien Text.
2. Wählen Sie eine **Wertequelle** – **Spalte** (die eindeutigen Werte einer Tabellenspalte), **Dimension** (Knoten einer Dimension) oder **Liste** (Werte, die Sie eingeben). Der Werttyp richtet sich nach dem Datentyp der Spalte.
3. Aktivieren Sie für jede Sicherheitsgruppe die Werte, die diese Gruppe sehen darf. Das Raster listet die Gruppen mit Zugriff auf das Projekt auf sowie jede Gruppe, die bereits eine Gewährung für die Spalte besitzt.
4. Stellen Sie **Everyone else** auf **sees all rows** oder **sees no rows** – das gilt für jede Gruppe ohne Markierungen im Raster.
5. Klicken Sie auf **Speichern**.

Das Speichern wirkt sofort. Die eigenen Abfragen von PlaidCloud folgen der Änderung unmittelbar und Ihre Superset-Dashboards innerhalb von etwa einer Minute – es gibt keinen separaten Schritt zum Anwenden und keinen Genehmigungsdialog. Der Synchronisierungsstatus des Bildschirms zeigt, wie weit die Änderung gekommen ist; siehe [Dashboards synchron halten](#dashboards-synchron-halten).

Das Raster übernimmt außerdem die Details für Sie:

- **Viele Werte.** Die Werte sind sortiert. Wenn eine Spalte mehr Werte hat, als angezeigt werden können, meldet das Raster „More values than fit here — type to search.“, und das Filterfeld durchsucht die gesamte Spalte, wobei jeder Wert erhalten bleibt, den eine Gruppe bereits besitzt.
- **Leere Werte.** Ein Kontrollkästchen **Leere Werte – sichtbar für jede Gruppe mit einer Gewährung** entscheidet über die Zeilen ohne Wert in der Spalte. Wenn Sie es aktivieren, sieht jede Gruppe mit irgendeiner Gewährung für die Spalte diese Zeilen.
- **Eine Tabelle, die noch nicht erstellt ist**, zeigt statt einer leeren Liste **Erstellen Sie diese Tabelle zuerst (führen Sie den Workflow aus, der sie erstellt)** an.
- **Das Speichern wartet auf die angezeigten Werte.** Während Werte geladen werden – nachdem Sie die Wertequelle, die Dimension oder die Tabelle gewechselt oder eine Vorlage angewendet haben –, ist **Speichern** deaktiviert, mit dem Tooltip „Save is available once this source's values load.“ Schlägt ein Ladevorgang fehl, teilt das Raster dies mit und bittet Sie, die Quelle erneut auszuwählen; es wird nichts gespeichert, bis ein Ladevorgang erfolgreich ist.

### Ein Spaltenname, jede Tabelle

Eine Einschränkung gehört zu einem Spalten*namen* im Projekt, nicht zu einer einzelnen Tabelle. Sobald `region` Zeilen einschränkt, wird jede Tabelle im Projekt mit einer Spalte namens `region` danach gefiltert, sowohl in den eigenen Abfragen von PlaidCloud als auch in Dashboards. Die Liste **Applies to** des Rasters zeigt diese Tabellen. Sie ist schreibgeschützt, weil der Spaltenname sie bestimmt, und eine Tabelle, die Sie später mit derselben Spalte hinzufügen, wird erfasst, sobald sie veröffentlicht ist.

Wenn keine Tabelle im Projekt eine Spalte mit diesem Namen hat, warnt das Fenster zusätzlich zur Anzeige **Applies to 0 tables**, dass die Einschränkung kein Dashboard filtert, bis eine Tabelle diese Spalte hat. Fügen Sie die Spalte einer Tabelle hinzu oder korrigieren Sie den Spaltennamen, und die Warnung verschwindet.

<Aside type="caution">
**Ein Spaltenname muss exakt übereinstimmen** – einschließlich Groß- und Kleinschreibung sowie Leerzeichen. `Region` und `region` sind verschiedene Namen, ebenso `region` und `region ` mit einem nachgestellten Leerzeichen. Die Auswahl bietet nur tatsächliche Spaltennamen an, daher spielt dies vor allem eine Rolle, wenn eine Spalte an anderer Stelle umbenannt wird – der Zeilenzugriff warnt Sie dann und nennt die ähnlichste gefundene Spalte, statt stillschweigend nichts einzuschränken.
</Aside>

<Aside type="caution">
**Das Veröffentlichen einer Tabelle, die Zeilen einschränkt, richtet im selben Schritt ihren Dashboard-Filter ein.** Dashboards lesen eine Tabelle über ihre veröffentlichte Berichtsansicht. Wenn Sie also eine Tabelle mit einer eingeschränkten Spalte veröffentlichen oder erneut veröffentlichen, registriert PlaidCloud den Dashboard-Filter dieser Tabelle, bevor die Veröffentlichung abgeschlossen ist. Gelingt das nicht, wird die Veröffentlichung abgelehnt und alles, was dieser Versuch angelegt hat, wird zurückgenommen, sodass eine eingeschränkte Tabelle nie ungefiltert in Dashboards verbleibt. Eine *Ansicht* kann in einem Projekt, das Zeilen einschränkt, nicht veröffentlicht werden, weil die Abfrage einer Ansicht die eingeschränkte Spalte umbenennen oder ableiten kann. Siehe [Tabellen veröffentlichen](/de/guides/data/publish/).
</Aside>

### Eine Einschränkung aufheben

**Einschränkung aufheben** im Raster entfernt die Einschränkung nach einer Bestätigung direkt im Dialog – „Stop restricting rows by ‚region‘? Every group's grant on it is removed and everyone sees its rows.“ Der Zeilenzugriff bestätigt dann „Rows in ‚region‘ are no longer restricted.“ Das Superset-Dataset der Spalte wird mit entfernt, es sei denn, Diagramme verwenden es noch; in diesem Fall teilt der Zeilenzugriff mit, dass das Dataset bestehen bleibt und wie viele Diagramme es verwenden.

Eine Spalte kann nicht umbenannt oder gelöscht werden, solange sie Zeilen einschränkt. Ein Architect wird aufgefordert, die Einschränkung zuerst im Zeilenzugriff aufzuheben; alle anderen werden aufgefordert, sich an einen Projekt-Architect zu wenden.

### Wer ein Projekt mit Zeilenbeschränkung ändern darf

Die Workflows, Schritte und benutzerdefinierten Funktionen eines Projekts laufen unter der eigenen Dienstidentität des Projekts, die jede Zeile liest. Wer sie ändern kann, könnte einen Schritt dazu bringen, Zeilen, für die er keine Gewährung hat, in eine Tabelle zu kopieren, die er lesen kann. Deshalb schränkt die Zeilenbeschränkung eines Projekts auch ein, wer ändern darf, was das Projekt tut. Sobald ein Projekt mindestens eine Spalte einschränkt:

- **Automatisierung ist nur für Architects.** Nur Projekt-Architects und Mandantenadministratoren können Workflows, Schritte, benutzerdefinierte Funktionen, Zeitpläne, Workflow- und Projektvariablen sowie E-Mail-Vorlagen für Benachrichtigungen ändern – und aus demselben Grund ein Workflow-Bundle importieren, einen Alteryx-Workflow konvertieren oder in das Projekt importieren, kopieren oder wiederherstellen oder die Verbindungsumgebung, das Standard-Dokumentenkonto oder den ERP-Buchungsmodus ändern. Alle anderen können die Workflows des Projekts weiterhin ausführen: **Start**, **Beenden**, **Fortsetzen** und **Ausgewählte(n) Schritt(e) ausführen** bleiben verfügbar. Der Schritteditor, die Bearbeitungssteuerelemente des Workflows, der UDF-Editor und das Zeitplanformular öffnen sich für sie schreibgeschützt, mit einem Banner, das die Architects nennt, an die sie sich wenden können: „This project restricts rows, so only its Architects can change workflows, steps, UDFs, schedules, variables and notify templates. You can still run them.“
- **Dimensionen, die eine eingeschränkte Spalte liest, sind nur für Architects.** Eine Dimension, die bestimmt, wer welche Zeilen sieht – die Wertequelle einer eingeschränkten Spalte –, kann nur von einem Projekt-Architect oder einem Mandantenadministrator und von den eigenen Workflows des Projekts geändert werden. Das umfasst das Hinzufügen, Verschieben, Umbenennen, Kopieren, Leeren, Laden und Wiederherstellen ihrer Knoten sowie die Dimension selbst. Alle anderen erhalten die Meldung „This dimension decides who sees which rows of ‚region‘, so only a project Architect can change it.“ Dimensionen, die keine Einschränkung liest, sind nicht betroffen.
- **Eine Quelltabelle für Gewährungen ist nur für Architects.** Die Zeilen einer Tabelle, die als [Quelle der Gewährungen](#gewährungen-an-eine-quelltabelle-binden) einer Spalte gebunden ist, können nur von einem Projekt-Architect, einem Mandantenadministrator oder den Workflows des Projekts geändert werden, und nur von ihnen kann sie gelöscht werden – gleichermaßen über den Dateneditor, einen Import, einen Connector-Ladevorgang oder die API.
- **Das Kopieren des Projekts ist nur für Architects**, und die Kopie meldet „This copy is not row-restricted.“ – das neue Projekt hat keine Einschränkung, bis Sie eine einrichten.
- **Das Wiederherstellen einer früheren Version ist eine Änderung wie jede andere.** Das Wiederherstellen der eigenen Einstellungen des Projekts oder einer oben genannten Dimension erfordert einen Projekt-Architect. Eine Wiederherstellung gilt immer für das Element, zu dem die Version gehört, und kann daher nicht auf ein anderes Projekt gerichtet werden, um dies zu umgehen – siehe [Versionsverlauf](/de/guides/projects/managing-projects/#versionsverlauf).
- **Das Bearbeiten von Daten in einer eingeschränkten Tabelle** erfordert einen Architect, wie unter [Zeilenzugriff und Dateneditor](#zeilenzugriff-und-dateneditor) beschrieben.

Bevor die erste Spalte eines Projekts eingeschränkt wird, teilt der Zeilenzugriff mit, wen dies betrifft: „Restricting rows here means only Architects can change this project's workflows, steps, UDFs, schedules and notify templates. N members can change them today; they will still be able to run them.“

Ausführungen laufen genau wie zuvor weiter, auch zeitgesteuerte, weil sie unter der Dienstidentität des Projekts laufen. Was eine Ausführung erzeugt, folgt dem Design, das ihre Architects ihr gegeben haben: Eine Ausgabetabelle ohne die eingeschränkte Spalte, eine Exportdatei, eine Benachrichtigungs-E-Mail oder eine Protokollzeile wird für diejenigen, die sie lesen, nicht gefiltert.

**Werte, die beim Start einer Ausführung angegeben werden.** Jeder, der einen Workflow ausführen kann, kann ihn mit eigenen Werten für seine Variablen starten – der [App Runner](/de/guides/workflows/use-converted-alteryx-apps/#das-app-runner-frontend) tut dies mit den Antworten seines Formulars, und die API und die KI-Tools können es ebenfalls. Diese Werte gelten nur für diese Ausführung: Sie werden nie im Workflow gespeichert, und keine andere Ausführung, kein Export und kein anderer Leser sieht sie. Da die Ausführung unter der Dienstidentität läuft, können die Werte ändern, was diese Ausführung liest und schreibt. Erteilen Sie die Berechtigung zum Ausführen von Workflows daher Personen, denen Sie vertrauen.

**Projekte ohne Zeilenbeschränkung.** Diese Regeln gelten erst, wenn ein Projekt eine Spalte einschränkt. In einem Projekt, das keine einschränkt, kann jeder, der die Automatisierung des Projekts ändern kann, einen Schritt oder eine benutzerdefinierte Funktion schreiben, die – unter der Dienstidentität des Projekts laufend – den Zugriff des Projekts ändert und die Person selbst zu einem seiner Architects macht. Das ist beabsichtigt: Ein solches Projekt verspricht keine Zeilenisolierung. Beschränken Sie Bearbeitungsrechte dort auf Personen, denen Sie als Architects vertrauen würden, oder schränken Sie eine Spalte ein.

### Dashboards synchron halten

Der Zeilenzugriff zeigt, wo eine Änderung auf dem Weg zu Ihren Dashboards steht, im Raster und in der Spalte **Synchronisieren** auf der Registerkarte „Security“ des Projekts:

| Status | Bedeutung |
|---|---|
| **Wartend** | Eine Änderung ist gespeichert und auf dem Weg zu den Dashboards. Sie ist normalerweise innerhalb von etwa einer Minute abgeschlossen. |
| **Wird wiederholt** | Eine Übermittlung ist fehlgeschlagen und wird erneut versucht. Der Grund für den Fehler wird neben dem Status angezeigt, mit **Wiederholen**, um sofort erneut zu senden. |
| **Noch nicht angewendet** | Die Einschränkungen des Projekts wurden noch nicht an die Dashboards gesendet. |
| **Angewendet** | Der letzte Versuch, die Einschränkungen an die Dashboards zu senden, war erfolgreich. |
| **Mit Dashboards synchron** | Der Zeilenzugriff hat verglichen, was die Dashboards durchsetzen, mit dem, was er schreiben würde, und beides stimmt überein. |
| **Dashboards weichen ab** | Die Dashboards setzen nicht durch, was der Zeilenzugriff schreiben würde – eine Regel wurde in Superset geändert oder gelöscht, oder die veröffentlichte Ansicht einer Tabelle kann nicht geprüft werden. |
| **Fehler** | Das Senden der Einschränkungen ist fehlgeschlagen. Der Grund wird neben dem Status angezeigt. |

Sobald eine Änderung **Angewendet** erreicht, prüft das Raster sie gegen die Dashboards und wechselt zu **Mit Dashboards synchron** oder **Dashboards weichen ab**. **Dashboards weichen ab** und **Fehler** bieten beide **Wiederholen** an, wodurch die Einschränkungen des Projekts erneut gesendet werden. Wenn der Status überhaupt nicht gelesen werden kann, meldet das Raster „Couldn't check sync status.“

Ein **Fehler**, der durch eine einzelne Tabelle verursacht wird, nennt die Tabelle und sagt, was zu tun ist – zum Beispiel eine Tabelle, die ohne ihre eingeschränkte Spalte veröffentlicht wurde („Republish or unpublish it.“), oder eine Tabelle mit einer eingeschränkten Spalte, die nicht veröffentlicht ist und die Dashboards erst filtern können, wenn sie veröffentlicht wird. Der Status bleibt auf **Fehler** und nennt die nicht veröffentlichte Tabelle, bis Sie sie veröffentlichen oder stattdessen die Spalte in einer veröffentlichten Tabelle einschränken. Eine solche Tabelle hält den Rest des Projekts nicht auf: Jede andere Tabelle wird weiterhin synchron gehalten.

Dashboards folgen denselben Gewährungen wie die eigenen Abfragen von PlaidCloud:

- **Jede veröffentlichte Tabelle mit der Spalte wird gefiltert**, nicht nur die Tabelle, die Sie beim Einrichten der Einschränkung angesehen haben.
- **Eine Gruppe, der nur einige Werte gewährt wurden, wird gefiltert, auch wenn alle anderen alle Zeilen sehen**, und zwar in jeder Tabelle, für die das Dashboard-Dataset existiert.
- **Projekt-Architects sehen jede Zeile**, in Dashboards ebenso wie im Tabellen-Explorer und im übrigen PlaidCloud. Das gilt für die Architect-Gruppen des Projekts und für die Architects eines mit einzelnen Mitgliedern geteilten Projekts. Der Entzug des Architect-Zugriffs wird in Dashboards sofort wirksam, ganz gleich, ob Sie die Rolle des Mitglieds ändern, das Mitglied oder seine Gruppe aus dem Projekt entfernen, den Zugriffstyp des Projekts ändern, eine frühere Projektversion wiederherstellen oder die Gruppe löschen.
- **Änderungen der Mitgliedschaft in Sicherheitsgruppen erreichen die Dashboards von selbst.** Wenn Sie in PlaidCloud jemanden zu einer Gruppe hinzufügen oder entfernen, ein Mitglied deaktivieren oder löschen, eine Gruppe löschen oder ein neues Mitglied hinzufügen, das Ihren Standard-Sicherheitsgruppen beitritt, wird das, was die Person in Dashboards sieht, innerhalb von etwa einer Minute aktualisiert, und zwar in jedem Projekt, das dieser Gruppe Werte gewährt, ohne dass jemand den Zeilenzugriff erneut öffnen muss. Eine Änderung der Mitgliedschaft außerhalb von PlaidCloud – direkt in Keycloak oder dadurch, dass Single Sign-on jemanden bei der Anmeldung in eine Gruppe einordnet – erreicht die Dashboards innerhalb von etwa 15 Minuten, ohne dass etwas gespeichert oder wiederholt werden muss.

### Dimensionsgewährungen

Wenn **Dimension** die Wertequelle ist, aktivieren Sie einen Knoten, um alles darunter zu gewähren. Die Gewährung folgt der Dimension: Ein Mitglied, das unter einem aktivierten Knoten hinzugefügt wird, wird dieser Gruppe bei der nächsten Synchronisierung nach dem Speichern der Dimension gewährt, und ein Mitglied, das aus diesem Knoten herausverschoben oder entfernt wird, wird nicht mehr gewährt – niemand muss das Raster erneut öffnen. Wenn Sie es erneut öffnen, werden die Knoten, die Sie aktiviert hatten, wieder aktiviert angezeigt.

Wenn Sie etwas unterhalb eines aktivierten Knotens deaktivieren, wird der Knoten deaktiviert, und die Gruppe behält nur die Mitglieder, die noch aktiviert sind. Wenn Sie dieses Mitglied erneut aktivieren, wird der Knoten nicht wieder aktiviert – klicken Sie dafür auf das eigene Kontrollkästchen des Knotens. **Einfügen**, **Alle auswählen** und **Umkehren** aktivieren Mitglieder, niemals Knoten.

Ein Dimensionsmitglied, dessen Name nicht als Zeilenzugriffswert verwendet werden kann, wird beim Speichern abgelehnt, wobei es benannt wird. Wenn ein solches Mitglied später erscheint, werden seine Zeilen niemandem gewährt, und der Synchronisierungsstatus nennt es: „Dimension ‚…‘ member ‚…‘ cannot be used as a row access value, so its rows are not granted. Rename it in the dimension.“

### Gewährungen an eine Quelltabelle binden

Anstatt Werte von Hand zu aktivieren, können Sie eine eingeschränkte Spalte auf eine Quelltabelle verweisen lassen, die die Antwort bereits enthält – eine Zeile pro Gruppe und dem Wert, den sie sehen darf. Schränken Sie die Spalte zuerst im Raster ein und fügen Sie dann einen Workflow-Schritt [**Zeilenzugriff festlegen**](/de/reference/workflow-steps/tables/table-set-row-access/) hinzu, der die Spalte, die Quelltabelle sowie die Gruppen- und Wertspalte der Quelltabelle benennt. Die erste Ausführung des Schritts bindet die Spalte an diese Tabelle: Die von Hand gesetzten Gewährungen der Spalte werden gelöscht, und ihre Gewährungen werden aus den Zeilen der Tabelle gesetzt.

Nach der Bindung ist die Spalte **quellengesteuert**: Das Zeilenzugriff-Raster zeigt sie gesperrt an, mit einem Badge, das die Quelltabelle nennt, und das manuelle Bearbeiten ihrer Gewährungen wird abgelehnt, bis Sie auf **Bindung entfernen** klicken.

Jede spätere Ausführung des Schritts liest die Quelltabelle erneut ein und wendet die Gewährungen erneut an – planen Sie ihn nach dem Workflow, der diese Tabelle lädt oder aktualisiert, und eine in den Quelldaten hinzugefügte, entfernte oder neu zugeordnete Gruppe erreicht den Zeilenzugriff bei der nächsten Ausführung, ohne dass jemand das Raster von Hand bearbeitet.

Da die Quelltabelle bestimmt, wer was sieht, können nur ein Projekt-Architect, ein Mandantenadministrator oder die eigenen Workflows des Projekts ihre Zeilen ändern oder sie löschen. Alle anderen erhalten die Meldung „This table supplies the row access grants for ‚region‘, so only a project Architect can change its rows or delete it.“

### Einschränkungsvorlagen

Wenn Sie eine Einschränkungsform erstellt haben, die Sie wiederverwenden möchten – dieselbe Wertequelle, derselbe Werttyp und dieselbe Einstellung für leere Werte –, speichern Sie sie einmal und wenden Sie sie überall an, wo sie gebraucht wird, anstatt sie Spalte für Spalte neu aufzubauen.

- **Als Vorlage speichern…** speichert in einem geöffneten Zeilenzugriff-Bildschirm die Form der aktuellen Spalte als benannte Vorlage auf Mandantenebene. Es wird nur die Form gespeichert – es werden keine Gewährungen mitgenommen.
- **Vorlage anwenden** beginnt bei der Spalte eines anderen Projekts mit der Form der Vorlage, wobei die Gewährungen aller Gruppen leer sind und von Ihnen ausgefüllt werden können.

Jeder Projekt-Architect kann Vorlagen speichern und anwenden. Das Umbenennen (**Umbenennen…**) und Löschen (**Löschen**) einer Vorlage erfordert einen Mandantenadministrator, da eine Vorlage mandantenweit geteilt wird. Das Löschen einer Vorlage lässt die Spalten, auf die sie angewendet wurde, so eingeschränkt, wie sie sind.

<Aside type="note">
Vorlagen sind Kopien, keine Verknüpfungen. Eine nachträgliche Bearbeitung einer Vorlage ändert keine Spalte, die sie bereits angewendet hat – wenden Sie die Vorlage erneut an, um eine Spalte auf den Stand einer späteren Überarbeitung zu bringen.
</Aside>

### Gewährungen aus SSO-Gruppenattributen

Eine Spalte kann ihre Gewährungen auch von Ihrem Identitätsanbieter statt von PlaidCloud beziehen. Ein Projekt-Architect aktiviert dies für eine Spalte im Zeilenzugriff, indem er **Accept row-access grants from SSO group attributes** aktiviert.

Sobald dies aktiviert ist, legt das Keycloak-Attribut `row_access.<column>` einer Sicherheitsgruppe die Werte fest, die diese Gruppe über diese Spalte sehen kann – setzen Sie das Attribut in Keycloak für die Gruppe, und PlaidCloud übernimmt es automatisch für jede Gruppe, die bereits Zugriff auf das Projekt hat. Im Zeilenzugriff selbst ist nichts weiter zu konfigurieren, und die Gewährungen bleiben sowohl in den eigenen Abfragen von PlaidCloud als auch in Superset-Dashboards synchron.

<Aside type="caution">
Dies gewährt nur Werte an eine Gruppe, die das Projekt bereits erreichen kann. Wenn Sie `row_access.region` einer Gruppe ohne Projektzugriff hinzufügen, gewährt das ihr nichts, bis die Gruppe auch Zugriff auf das Projekt erhält.
</Aside>

### Vorschau vor dem Speichern

Der Zeilenzugriff zeigt Ihnen, was eine Änderung bedeutet, bevor Sie sie festschreiben:

- Eine Fußzeile **Vorschau als** zeigt, wie viele der Zeilen der Tabelle eine Gruppe von der Gesamtzahl sehen würde, mit einer Stichprobe der Zeilen selbst – wählen Sie eine beliebige Gruppe im Raster aus, um sie in der Vorschau anzuzeigen. Die Vorschau wird nach dem Speichern aktualisiert.
- Vor dem Speichern warnt Sie der Zeilenzugriff vor allem, was einen zweiten Blick wert ist: eine Gruppe ohne Markierung und ob das bedeutet, dass sie bei Ihrer Einstellung **Everyone else** alle Zeilen oder keine sieht; Mitglieder mit Projektzugriff, die von keiner Gewährung einer Gruppe erfasst werden; oder Zeilen, deren Wert in dieser Spalte leer (`NULL`) ist und die keiner Gruppe gewährt werden.

### Was ein eingeschränktes Mitglied sieht

Überall dort, wo ein eingeschränktes Mitglied eine Tabelle über ihren Namen liest, erhält es nur seine Zeilen – im Raster, in den Spaltenfacetten und Downloads des Tabellen-Explorers, im Dialog zum Herunterladen von Tabellen, in Apps und Tools, die als der Betrachter lesen, und in Dashboards. Der Tabellen-Explorer zeigt in seiner Symbolleiste **Zeilen durch Ihren Zugriff eingeschränkt** an, wenn das Raster, das Sie ansehen, anhand Ihrer Gewährungen gefiltert wurde, und das Starten eines Downloads, der gefiltert wird, meldet „Rows limited by your access.“ Ein Architect, der jede Zeile liest, sieht keinen der beiden Hinweise.

### Zeilenzugriff und Abfragen, die Sie selbst schreiben

Der Zeilenzugriff begrenzt, welche Zeilen eine Gruppe sehen darf, indem er die Tabelle filtert, für die er definiert ist. Eine Abfrage, die jemand selbst schreibt, hat keine einzelne Tabelle, an die sich dieser Filter anhängen ließe – eine Abfrage kann beliebig viele Tabellen verknüpfen, kombinieren oder verschachteln –, daher lehnt PlaidCloud in einem Projekt, das Zeilen einschränkt, die Ausführung einer vom Aufrufer gelieferten Abfrage ab, anstatt Zeilen zurückzugeben, die nichts geprüft hat.

Das gilt für das Lesen über Ihr eigenes SQL, den Export der Ergebnisse Ihres eigenen SQL in eine Datei oder in eine andere Datenbank und die Eingabe einer Zeilenbedingung in die Vorschau „Test row 1“ eines Fan-out-Schritts. Es gilt **nicht** für das Lesen einer Tabelle über ihren Namen, den üblichen Weg, auf dem Apps und Tools Daten lesen – diese wenden die Gewährungen an und liefern die Zeilen, auf die der Betrachter Anspruch hat. Eine Spaltenfacette, die als einfache Abfrage einer einzelnen Tabelle geschrieben ist, wird ebenfalls über den Namen gelesen und liefert daher die eigenen Werte des Mitglieds, anstatt abgelehnt zu werden.

Wer abgelehnt wird, erfährt, um welches Projekt es sich handelte, und wird auf die Leser über den Namen hingewiesen. Ein Projekt-Architect kann die Abfrage wie geschrieben ausführen und ihre Ergebnisse in jedem Format exportieren, weil ein Architect sich bereits jeden Wert jeder eingeschränkten Spalte selbst gewähren kann.

Der Import einer Tabellenkalkulation ist für sich genommen keine Abfrage, die Sie selbst geschrieben haben – ein gewöhnlicher Dateiimport liest überhaupt keine eingeschränkten Daten, er legt lediglich die neue Tabelle des Projekts aus der hochgeladenen Datei an und ist daher vom Zeilenzugriff nicht betroffen. Die Ausnahme ist ein Import, dessen Datenprojektion vom Aufrufer geliefert wird: ein Ausdruck pro Spalte oder eine dynamische Excel-Zuordnung. Auf dem interaktiven Importbildschirm werden diese genauso abgelehnt wie die oben genannten Oberflächen mit freiem SQL und erfordern einen Projekt-Architect, weil eine vom Aufrufer gelieferte Projektion eine andere Tabelle lesen könnte. Ein Import, der aus einem Workflow läuft, ist in beiden Fällen nicht betroffen, da er unter der eigenen Dienstidentität des Projekts läuft.

<Aside type="caution">
Die Einschränkung Ihrer ersten Spalte in einem Projekt ändert dies für alle, die es verwenden. Wenn eine Panel-App, ein Notebook oder eine Integration in diesem Projekt Daten liest, indem sie ihr eigenes SQL zusammensetzt, stellen Sie sie vor der Einschränkung auf das Lesen der Tabelle über den Namen um – andernfalls funktioniert sie für alle, die keine Architects sind, nicht mehr.
</Aside>

### Zeilenzugriff und Dateneditor

Der Dateneditor liest und schreibt eine Tabelle direkt, daher gilt der Zeilenzugriff für ihn auf beiden Seiten.

Wenn Sie eine eingeschränkte Tabelle im Dateneditor öffnen, sehen Sie nur die Zeilen, die Ihrer Sicherheitsgruppe gewährt sind – derselbe Filter, der Ihnen in ein Dashboard folgt, und er gilt auch dann, wenn die eingeschränkte Spalte nicht zu den im Raster angezeigten Spalten gehört.

Das Speichern Ihrer Änderungen erfordert **Architect** im Projekt. Ein Speichern ersetzt die Zeilen der Tabelle insgesamt, anstatt sie zu lesen, und wird nicht Zeile für Zeile gefiltert. Daher wird das Bearbeiten von Daten in einer eingeschränkten Tabelle als Authoring-Aktion und nicht als Lesevorgang behandelt: Wer kein Architect ist, erfährt, dass er diese Rolle benötigt. Eine Tabelle ohne eingeschränkte Spalte wird wie bisher bearbeitet, ebenso jedes Projekt, das keine Zeilen einschränkt.

### Zeilenanzahl und Tabellengrößen

Die Zeilenanzahl und die Speichergröße einer Tabelle beschreiben die gesamte Tabelle, nicht die Zeilen, die Sie sehen dürfen, und würden einem eingeschränkten Leser daher verraten, wie viele Zeilen jenseits seiner Gewährung existieren. In einem Projekt, das Zeilen einschränkt, sieht jeder, dessen Lesezugriffe gefiltert werden, für keine Tabelle des Projekts eine Zeilenanzahl oder Größe – in Tabellenlisten, in der Suche, in Tabellendetails und Snapshots sowie über den KI-Assistenten und über MCP verbundene KI-Tools. Das gilt für jede Tabelle im Projekt, auch für Tabellen ohne eingeschränkte Spalte. Auch die eigenen Summen des Projekts sind für sie ausgeblendet – die Gesamtzeilenanzahl und -größe auf der Startseite, in Projektlisten und in der Suche sowie in den Projektdetails.

Dasselbe gilt für den Ausführungsverlauf von Workflows. Die gelesenen und geschriebenen Zeilen, die jede Ausführung und jeder Schritt aufgezeichnet hat, beschreiben ebenfalls die gesamte Tabelle, daher bleiben diese Zahlen für dieselben Leser leer – im Ausführungsverlauf eines Workflows und eines Schritts sowie über den KI-Assistenten und über MCP verbundene KI-Tools. Für sie prüft [Weave](/de/guides/ai-assistant/weave-findings/) Schritte nicht darauf, ob Zeilen- oder Leerwerte im Vergleich zu früheren Ausführungen abweichen, da ein Befund selbst verraten würde, dass sich die Gesamtanzahl der Tabelle verändert hat.

Projekt-Architects sehen die Zahlen wie bisher, ebenso alle in einem Projekt, das keine Zeilen einschränkt.

### Sehen, was ein Mitglied sehen kann

Um zu prüfen, was eine bestimmte Person sehen kann, statt was eine Gruppe gewährt bekommt: Öffnen Sie **Identity → Member**, wählen Sie das Mitglied aus und öffnen Sie dessen Registerkarte **Zeilenzugriff**. Die Spalte **Effektiver Zugriff** listet für jedes eingeschränkte Projekt und jede eingeschränkte Spalte die Werte auf, die dieses Mitglied über alle seine Gruppen zusammen sieht – einschließlich Gewährungen aus SSO-Gruppenattributen und leerer (`NULL`) Zeilen, wenn die Gewährung einer Gruppe sie einschließt. Ein Projekt-Architect wird als **Sieht jede Zeile (Architect)** angezeigt, da ein Architect jede Zeile liest. Es ist dieselbe Antwort, die die eigenen Abfragen von PlaidCloud anwenden, und daher nützlich für den Support und um zu bestätigen, dass eine Änderung das bewirkt hat, was Sie beabsichtigten, bevor sich jemand über ein Problem meldet.

### Klarere Fehlermeldungen

Wo der Zeilenzugriff eine Aktion blockiert – eine selbst geschriebene Abfrage in einem eingeschränkten Projekt, eine Bearbeitung ohne Architect, eine Änderung der Automatisierung, einer Dimension oder einer Quelltabelle für Gewährungen und die übrigen oben beschriebenen Fälle –, nennt die Meldung, was eingeschränkt ist und was als Nächstes zu tun ist, etwa die Architects, an die Sie sich wenden können, statt eines allgemeinen Fehlers.

### Der Zeilenzugriff wird protokolliert

Das Einschränken oder Aufheben der Einschränkung einer Spalte und das Bearbeiten der Gewährungen einer Gruppe schreiben jeweils einen Eintrag in das [Projektprotokoll](/de/get-started/tutorials/collaborate-versions-and-sharing/#das-projektprotokoll-lesen) dieses Projekts – wer die Änderung vorgenommen hat und wann. Öffnen Sie **Analyze → Projects → Log** für das Projekt, um ihn zu sehen. Für diese Nachverfolgung muss beim Zeilenzugriff nichts aktiviert werden; sie wird auf dieselbe Weise aufgezeichnet wie jede andere nachverfolgte Änderung an einem Projekt.

## Standard-Sicherheitsgruppen festlegen


Um den Aufwand beim Hinzufügen neuer Mitglieder zu verringern, legen Sie eine Reihe von Standard-Sicherheitsgruppen fest. Dadurch erhalten neue Mitglieder eine Grundausstattung an Sicherheitsgruppen, ohne dass Sie jeder Person einzeln Gruppen zuweisen müssen. Die Einstellung ist beim Hinzufügen einer neuen Sicherheitsgruppe verfügbar, wenn Sie unten im Fenster „Security Group“ das Kontrollkästchen „Assign to New Users by Default“ aktivieren.



## Sicherheitsaudit durchführen


Mit der Sicherheitsaudit-Funktion können Sie die Gruppenmitgliedschaft über alle Mitglieder und Gruppen hinweg einsehen.



**So führen Sie ein Sicherheitsaudit durch:**


1. Öffnen Sie Identity
2. Wählen Sie die Registerkarte „Security“
3. Klicken Sie im Dropdown-Menü auf „Security Group Audit“

Da alle Tabellen in PlaidCloud als CSV-Datei exportiert werden können, lassen sich die Zuordnungen von Gruppen und Mitgliedern außerhalb von PlaidCloud überprüfen, sei es für historische Zwecke oder einfach zum Vergnügen bei der Offline-Ansicht.



**So exportieren Sie aus dem Formular „Security Group Audit“:**


1. Öffnen Sie Identity
2. Wählen Sie die Registerkarte „Security“
3. Klicken Sie im Dropdown-Menü auf „Security Group Audit“
4. Klicken Sie in der Tabelle ganz rechts neben „Username“ auf das kleine Symbol
5. Klicken Sie je nach Wunsch auf „Export CSV“ oder „Export XLXS“

## Verfügbare Berechtigungseinstellungen anzeigen


Jede im Workspace verwendete Anwendung hat bestimmte verfügbare Berechtigungen. Die Berechtigungen der Sicherheitsgruppen basieren auf diesen Anwendungsberechtigungen.


Die vollständige Liste der verfügbaren Berechtigungen für jede Anwendung kann im Security Bin angezeigt werden.



**So greifen Sie auf den Security Bin zu:**


1. Öffnen Sie Identity
2. Wählen Sie „Security“
3. Klicken Sie im Dropdown-Menü auf „Security Bins“

Um die detaillierten Sicherheitseinstellungen jeder Anwendung anzuzeigen, wählen Sie das Tags-Symbol ganz links.



Diese Informationen zu den verfügbaren Sicherheitseinstellungen dienen nur zur Information. Details zur Verwaltung von Berechtigungen finden Sie im obigen Abschnitt „Sicherheitsgruppen verwalten“.
