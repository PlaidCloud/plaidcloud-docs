Die Sicherheits- und Zugriffsverwaltung von PlaidCloud ist unkompliziert. Einem Mitglied wird der Zugriff auf Grundlage der Gruppen gewährt oder verweigert, denen das Mitglied zugeordnet ist. Die Sicherheitszuordnung eines Mitglieds lässt sich einfach hinzufügen oder ändern.

<Aside>Pro Workspace ist eine unbegrenzte Anzahl von Sicherheitsgruppen zulässig, wir empfehlen jedoch, die Anzahl gering zu halten, um die Sicherheitsverwaltung zu vereinfachen.</Aside>



## Sicherheitsgruppen verwalten


Sicherheitsgruppen können hinzugefügt, aktualisiert oder gelöscht werden.



**So verwalten Sie Sicherheitsgruppen:**


1. Öffnen Sie Identität.
2. Wählen Sie in der Navigationsleiste **Sicherheitsgruppen** aus (es wird eine Liste der vorhandenen Gruppen angezeigt).
4. Um eine Gruppe hinzuzufügen, klicken Sie auf „Create Security Group“.
5. Um die Berechtigungen einer Gruppe zu bearbeiten, klicken Sie auf das Symbol ganz links.

**So verwalten Sie Gruppenmitglieder:**


1. Öffnen Sie Identität.
2. Wählen Sie in der Navigationsleiste **Sicherheitsgruppen** aus.
3. Klicken Sie auf das Symbol „Member“.
4. Ziehen Sie die gewünschten Mitglieder aus der Spalte „Unassigned Members“ in die Spalte „Assigned Members“ oder umgekehrt, um Mitglieder zu entfernen.

<Aside>Das Speichern bei leerer Spalte „Assigned Members“ bewirkt keine Änderung und weist Sie darauf hin. Um eine Gruppe allen Mitgliedern zu entziehen, entfernen Sie ihre Berechtigungen oder löschen Sie die Gruppe, statt ihre Mitgliederliste zu leeren.</Aside>

<Aside>Wenn einer Gruppe über [Zeilenzugriff](#zeilenzugriff-verwalten) Zeilen gewährt werden, wirkt sich eine Änderung der Mitgliedschaft innerhalb von etwa einer Minute auf Dashboards aus: Wer hinzugefügt wird, sieht dort die Zeilen der Gruppe, und wer entfernt wird, sieht sie nicht mehr. Das Deaktivieren oder Löschen eines Mitglieds sowie das Löschen einer Gruppe werden auf dieselbe Weise wirksam.</Aside>

<Aside type="caution">Berechtigungen, die Sie sich nicht selbst erteilen können, bleiben beim Speichern der Berechtigungsmatrix einer Gruppe unverändert und werden darin nicht angezeigt. Wenn Sie eine davon ändern müssen, wenden Sie sich an jemanden, der diese Berechtigung besitzt – die Matrix bearbeitet immer nur, was Sie selbst kontrollieren.</Aside>

<Aside type="caution">Sie können ein Mitglied zu einer Gruppe hinzufügen oder die Gruppen eines Mitglieds festlegen, wenn Sie jede Berechtigung besitzen, die die Gruppe gewährt. Dasselbe gilt, wenn Sie jemanden als Architect einladen. Workspace-Administratoren unterliegen dieser Einschränkung nicht.</Aside>

## Zeilenzugriff verwalten

Der Zeilenzugriff schränkt anhand der Werte einer Spalte ein, welche Zeilen einer Tabelle eine Sicherheitsgruppe sehen kann. Beispielsweise kann eine Spalte `region` den Zugriff einschränken: Eine Gruppe, der `East` und `Central` gewährt wurden, ist auf Zeilen mit diesen Werten beschränkt. Alles für ein Projekt und eine Spalte – die Auswahl der Spalte, die Wahl der Herkunft ihrer Werte und die Entscheidung, welche Gruppe was sieht – geschieht in einem einzigen Bildschirm, und das Speichern wirkt sofort.

Das Einrichten und Ändern des Zeilenzugriffs erfordert einen Projekt-Architect oder einen Mandantenadministrator. Alle anderen, die die Registerkarte „Sicherheit“ eines Projekts öffnen, erhalten den Hinweis, dass der Zeilenzugriff nur Architects vorbehalten ist, und die unten genannten Einstiegspunkte werden für sie nicht angezeigt.

### Zeilenzugriff öffnen

Jeder Einstiegspunkt öffnet denselben Bildschirm für den Zeilenzugriff:

- **Die Symbolleiste des Tabellen-Explorers** enthält eine Schaltfläche **Zeilenzugriff**, die ein Badge anzeigt, wenn die Tabelle bereits Zeilen einschränkt. Sie öffnet sich mit der ersten eingeschränkten Spalte der Tabelle, sofern vorhanden, und Sie können zu jeder anderen Spalte der Tabelle wechseln.
- **Das Facettenmenü einer Spalte** enthält **Zeilen nach dieser Spalte einschränken…**, wodurch der Zeilenzugriff für diese Spalte geöffnet wird. Bei einer Spalte, die bereits Zeilen einschränkt, lautet der Eintrag **Zeilen durch diese Spalte eingeschränkt – bearbeiten…**.
- **Die Registerkarte „Sicherheit“ eines Projekts** listet jede eingeschränkte Spalte des Projekts auf, mit den Tabellen, auf die sie sich bezieht, den Gruppen mit Gewährungen und ihrem **Synchronisieren**-Status. Wählen Sie eine Spalte aus, um sie zu bearbeiten, oder klicken Sie auf **Spalte einschränken…**, um eine neue zu beginnen: Wählen Sie eine Tabelle und dann eine Spalte. Spalten, die bereits Zeilen einschränken, sind mit einem Schloss markiert.
- **Identität → Member**, auf der Registerkarte **Zeilenzugriff** eines Mitglieds, und **Identität → Sicherheit → Sicherheitsgruppen**, in der Zeilenzugriff-Übersicht einer Gruppe. **Zeilenzugriff öffnen** (oder **Bearbeiten**) öffnet die ausgewählte Spalte; **Hinzufügen** schränkt eine weitere Spalte im Projekt dieser Zeile ein.

Wird der Bildschirm für eine Spalte geöffnet, bleibt er bei dieser Spalte. Wird er mit **Spalte einschränken…** oder **Hinzufügen** geöffnet, können Sie eine Spalte auswählen.

### Das Zeilenzugriff-Raster

So schränken Sie eine Tabelle anhand einer Spalte ein:

1. Öffnen Sie den Zeilenzugriff über einen der oben genannten Einstiegspunkte und wählen Sie die Spalte, falls Sie nicht bereits mit einer angekommen sind – die Auswahl bietet die tatsächlichen Spalten der Tabelle an, keinen freien Text.
2. Wählen Sie eine **Wertequelle** – **Spalte** (die eindeutigen Werte einer Tabellenspalte), **Dimension** (Knoten einer Dimension) oder **Liste** (Werte, die Sie selbst eingeben). Der Werttyp richtet sich nach dem Datentyp der Spalte.
3. Aktivieren Sie für jede Sicherheitsgruppe die Werte, die diese Gruppe sehen darf. Das Raster listet die Gruppen mit Zugriff auf das Projekt auf sowie jede Gruppe, die bereits eine Gewährung für die Spalte besitzt.
4. Stellen Sie **Everyone else** auf **sees all rows** oder **sees no rows** – das gilt für jede Gruppe ohne Markierungen im Raster.
5. Klicken Sie auf **Speichern**.

Das Speichern wirkt sofort. Die eigenen Abfragen von PlaidCloud folgen der Änderung unmittelbar und Ihre Superset-Dashboards innerhalb von etwa einer Minute – es gibt keinen separaten Schritt zum Anwenden, und **Speichern** fragt nur dann nach, wenn eine Gewährung einen Wert enthält, den ihre Quelle nicht mehr hat (siehe unten). Der Synchronisierungsstatus des Bildschirms zeigt, wie weit die Änderung gekommen ist; siehe [Dashboards synchron halten](#dashboards-synchron-halten).

Das Raster übernimmt außerdem die Details für Sie:

- **Viele Werte.** Die Werte sind sortiert. Wenn eine Spalte mehr Werte hat, als hineinpassen, meldet das Raster „More values than fit here — type to search.“, und das Filterfeld durchsucht die gesamte Spalte, wobei jeder Wert erhalten bleibt, den eine Gruppe bereits besitzt.
- **Werte, die die Quelle nicht mehr hat.** Ein Wert, der einer Gruppe gewährt wurde, bleibt im Raster, wenn seine Quelle ihn verliert – keine Zeile der Tabelle enthält ihn mehr, die Dimension hat den Member nicht mehr, oder die Liste enthält ihn nicht mehr. Seine Spaltenüberschrift trägt ein Warnsymbol, und beim Daraufzeigen wird der Grund genannt. **Alle auswählen**, **Umkehren** und **Einfügen** belassen einen solchen Wert so, wie ihn jede Gruppe besitzt. Aus einer Gewährung wird nichts entfernt, solange Sie die Markierung nicht selbst aufheben: Wenn Sie auf **Speichern** klicken, während eine Gruppe noch einen solchen Wert besitzt, nennt der Zeilenzugriff die Gruppen und Werte unter **Values No Longer in the Source** und fragt nach. **Keep and Save** speichert sie unverändert, **Remove and Save** entfernt sie zuerst aus der Gewährung jeder Gruppe, und das Schließen der Rückfrage speichert nichts. Würde das Entfernen dazu führen, dass bei einer Gruppe nichts mehr markiert ist, nennt die Rückfrage, ob diese Gruppe dann alle Zeilen oder keine sieht, gemäß **Everyone else**. Eine noch nicht gespeicherte Markierung verschwindet mit ihrem Wert. Wenn eine Spalte mehr Werte hat, als hineinpassen, oder ihre Tabelle noch nicht erstellt ist, kann der Zeilenzugriff nicht feststellen, welche Werte der Tabelle fehlen, und behält daher jeden gewährten Wert bei, ohne einen zu markieren.
- **Leere Werte.** Ein Kontrollkästchen **Leere Werte – sichtbar für jede Gruppe mit einer Gewährung** bestimmt die Zeilen ohne Wert in der Spalte. Aktivieren Sie es, und jede Gruppe mit einer beliebigen Gewährung für die Spalte sieht diese Zeilen.
- **Eine noch nicht erstellte Tabelle** zeigt statt einer leeren Liste **Erstellen Sie diese Tabelle zuerst (führen Sie den Workflow aus, der sie erstellt)** an.
- **Speichern wartet auf die angezeigten Werte.** Während Werte geladen werden – nachdem Sie die Wertequelle, die Dimension oder die Tabelle gewechselt oder eine Vorlage angewendet haben –, ist **Speichern** deaktiviert, mit dem Tooltip „Save is available once this source's values load.“ Schlägt ein Ladevorgang fehl, meldet das Raster dies und bittet Sie, die Quelle erneut auszuwählen; es wird nichts gespeichert, bis ein Ladevorgang erfolgreich ist.

### Ein Spaltenname, jede Tabelle

Eine Einschränkung gehört zu einem Spalten*namen* im Projekt, nicht zu einer einzelnen Tabelle. Sobald `region` Zeilen einschränkt, wird jede Tabelle im Projekt mit einer Spalte namens `region` dadurch gefiltert, sowohl in den eigenen Abfragen von PlaidCloud als auch in Dashboards. Die Liste **Applies to** des Rasters zeigt diese Tabellen. Sie ist schreibgeschützt, weil der Spaltenname sie bestimmt, und eine Tabelle, die Sie später mit derselben Spalte hinzufügen, wird erfasst, sobald sie veröffentlicht ist.

Wenn keine Tabelle im Projekt eine Spalte mit diesem Namen hat, warnt das Fenster zusätzlich zur Anzeige von **Applies to 0 tables**, dass die Einschränkung kein Dashboard filtert, bis eine Tabelle die Spalte hat. Fügen Sie die Spalte einer Tabelle hinzu oder korrigieren Sie den Spaltennamen, und die Warnung verschwindet.

<Aside type="caution">
**Ein Spaltenname muss exakt übereinstimmen** – einschließlich Groß-/Kleinschreibung und Leerzeichen. `Region` und `region` sind verschiedene Namen, ebenso `region` und `region ` mit einem Leerzeichen am Ende. Die Auswahl bietet nur tatsächliche Spaltennamen an, daher spielt das vor allem eine Rolle, wenn eine Spalte an anderer Stelle umbenannt wird – der Zeilenzugriff warnt Sie dann und nennt die ähnlichste gefundene Spalte, statt stillschweigend nichts einzuschränken.
</Aside>

<Aside type="caution">
**Das Veröffentlichen einer Tabelle, die Zeilen einschränkt, richtet im selben Schritt ihren Dashboard-Filter ein.** Dashboards lesen eine Tabelle über ihre veröffentlichte Berichtsansicht. Wenn Sie also eine Tabelle mit einer eingeschränkten Spalte veröffentlichen oder erneut veröffentlichen, registriert PlaidCloud den Dashboard-Filter dieser Tabelle, bevor die Veröffentlichung abgeschlossen ist. Gelingt das nicht, wird die Veröffentlichung abgelehnt und alles, was dieser Versuch erstellt hat, rückgängig gemacht, sodass eine eingeschränkte Tabelle nie ungefiltert in Dashboards landet. Eine *Ansicht* kann in einem Projekt, das Zeilen einschränkt, nicht veröffentlicht werden, da die Abfrage einer Ansicht die eingeschränkte Spalte umbenennen oder ableiten kann. Siehe [Tabellen veröffentlichen](/de/guides/data/publish/).
</Aside>

### Eine Einschränkung aufheben

**Einschränkung aufheben** im Raster entfernt die Einschränkung nach einer Bestätigung direkt im Raster – „Stop restricting rows by ‘region’? Every group's grant on it is removed and everyone sees its rows.“ Der Zeilenzugriff bestätigt anschließend „Rows in ‘region’ are no longer restricted.“ Das Superset-Dataset der Spalte wird mit entfernt, sofern es nicht noch von Diagrammen verwendet wird; in diesem Fall teilt der Zeilenzugriff mit, dass das Dataset bestehen bleibt und wie viele Diagramme es verwenden.

Eine Spalte kann nicht umbenannt oder gelöscht werden, solange sie Zeilen einschränkt. Ein Architect wird aufgefordert, die Einschränkung zuerst im Zeilenzugriff aufzuheben; alle anderen werden aufgefordert, einen Projekt-Architect zu fragen.

### Wer ein Projekt mit Zeileneinschränkung ändern darf

Die Workflows, Schritte und benutzerdefinierten Funktionen eines Projekts laufen unter der eigenen Dienstidentität des Projekts, die jede Zeile liest. Wer sie ändern kann, könnte einen Schritt so gestalten, dass Zeilen, die ihm nicht gewährt wurden, in eine für ihn lesbare Tabelle kopiert werden. Daher schränkt die Zeileneinschränkung in einem Projekt auch ein, wer ändern darf, was das Projekt tut. Sobald ein Projekt mindestens eine Spalte einschränkt:

- **Automatisierung ist Architects vorbehalten.** Nur Projekt-Architects und Mandantenadministratoren können Workflows, Schritte, benutzerdefinierte Funktionen, Zeitpläne, Workflow- und Projektvariablen sowie E-Mail-Vorlagen für Benachrichtigungen ändern – und aus demselben Grund ein Workflow-Bundle importieren, einen Alteryx-Workflow konvertieren, in das Projekt importieren, kopieren oder wiederherstellen oder seine Verbindungsumgebung, das Standard-Dokumentenkonto oder den ERP-Buchungsmodus ändern. Alle anderen können die Workflows des Projekts weiterhin ausführen: **Start**, **Beenden**, **Fortsetzen** und **Ausgewählte(n) Schritt(e) ausführen** bleiben verfügbar. Der Schritt-Editor, die Bearbeitungssteuerelemente des Workflows, der UDF-Editor und das Zeitplanformular öffnen sich für sie schreibgeschützt, mit einem Banner, das die Architects nennt, die Sie fragen können: „This project restricts rows, so only its Architects can change workflows, steps, UDFs, schedules, variables and notify templates. You can still run them.“
- **Dimensionen, die eine eingeschränkte Spalte liest, sind Architects vorbehalten.** Eine Dimension, die bestimmt, wer welche Zeilen sieht – die Wertequelle einer eingeschränkten Spalte –, kann nur von einem Projekt-Architect oder einem Mandantenadministrator sowie von den eigenen Workflows des Projekts geändert werden. Das umfasst das Hinzufügen, Verschieben, Umbenennen, Kopieren, Leeren, Laden und Wiederherstellen ihrer Knoten sowie die Dimension selbst. Alle anderen erhalten die Meldung „This dimension decides who sees which rows of ‘region’, so only a project Architect can change it.“ Dimensionen, die keine Einschränkung liest, sind nicht betroffen.
- **Eine Quelltabelle für Gewährungen ist Architects vorbehalten.** Die Zeilen einer Tabelle, die als [Quelle der Gewährungen](#gewährungen-an-eine-quelltabelle-binden) einer Spalte gebunden ist, können nur von einem Projekt-Architect, einem Mandantenadministrator oder den Workflows des Projekts geändert oder die Tabelle gelöscht werden – gleichermaßen über den Dateneditor, einen Import, einen Connector-Ladevorgang oder die API.
- **Das Kopieren des Projekts ist Architects vorbehalten**, und die Kopie meldet „This copy is not row-restricted.“ – das neue Projekt enthält keine Einschränkung, bis Sie eine einrichten.
- **Das Wiederherstellen einer früheren Version ist eine Änderung wie jede andere.** Das Wiederherstellen der eigenen Einstellungen des Projekts oder einer oben genannten Dimension erfordert einen Projekt-Architect. Eine Wiederherstellung bezieht sich immer auf das Element, zu dem die Version gehört, und kann daher nicht auf ein anderes Projekt gerichtet werden, um dies zu umgehen – siehe [Versionsverlauf](/de/guides/projects/managing-projects/#versionsverlauf).
- **Das Bearbeiten von Daten in einer eingeschränkten Tabelle** erfordert einen Architect, wie unter [Zeilenzugriff und Dateneditor](#zeilenzugriff-und-dateneditor) beschrieben.
- **DataFrame-Schreibvorgänge, Datensatz-Speicherungen und Leerungen in einer eingeschränkten Tabelle ändern nur Ihre eigenen Zeilen**, sofern Sie nicht jede Zeile sehen, wie unter [Daten in eine eingeschränkte Tabelle laden](#daten-in-eine-eingeschränkte-tabelle-laden) beschrieben.
- **Importe, Kopien, Branch-Wechsel, Wiederherstellungen und Löschungen einer eingeschränkten Tabelle werden abgelehnt**, solange sie eine Zeile enthält, die Sie nicht sehen können, wie unter [Daten in eine eingeschränkte Tabelle laden](#daten-in-eine-eingeschränkte-tabelle-laden) beschrieben.

Bevor die erste Spalte eines Projekts eingeschränkt wird, teilt der Zeilenzugriff mit, wen das betrifft: „Restricting rows here means only Architects can change this project's workflows, steps, UDFs, schedules and notify templates. N members can change them today; they will still be able to run them.“

Ausführungen laufen wie bisher weiter, auch zeitplangesteuerte, da sie unter der Dienstidentität des Projekts laufen. Was eine Ausführung erzeugt, folgt dem Entwurf, den ihre Architects ihr gegeben haben: Eine Ausgabetabelle ohne die eingeschränkte Spalte, eine Exportdatei, eine Benachrichtigungs-E-Mail oder eine Protokollzeile wird für diejenigen, die sie lesen, nicht gefiltert.

**Beim Start einer Ausführung übergebene Werte.** Jeder, der einen Workflow ausführen darf, kann ihn mit eigenen Werten für seine Variablen starten – der [App Runner](/de/guides/workflows/use-converted-alteryx-apps/#das-app-runner-frontend) tut dies mit den Antworten seines Formulars, und die API und KI-Tools können es ebenfalls. Diese Werte gelten nur für diese Ausführung: Sie werden nie im Workflow gespeichert, und keine andere Ausführung, kein anderer Export und kein anderer Leser sieht sie. Da die Ausführung unter der Dienstidentität läuft, können die Werte ändern, was diese Ausführung liest und schreibt. Erteilen Sie die Berechtigung zum Ausführen von Workflows daher nur Personen, denen Sie dies anvertrauen.

**Projekte ohne Zeileneinschränkung.** Diese Regeln greifen erst, wenn ein Projekt eine Spalte einschränkt. In einem Projekt ohne Einschränkung kann jeder, der die Automatisierung des Projekts ändern darf, einen Schritt oder eine benutzerdefinierte Funktion schreiben, die – unter der Dienstidentität des Projekts laufend – den Zugriff auf das Projekt ändert und die Person selbst zu einem seiner Architects macht. Das ist so beabsichtigt: Ein solches Projekt verspricht keine Zeilenisolation. Beschränken Sie die Bearbeitungsrechte dort auf Personen, denen Sie als Architects vertrauen würden, oder schränken Sie eine Spalte ein.

### Dashboards synchron halten

Der Zeilenzugriff zeigt, wo eine Änderung auf dem Weg zu Ihren Dashboards steht, im Raster und in der Spalte **Synchronisieren** der Registerkarte „Sicherheit“ des Projekts:

| Status | Bedeutung |
|---|---|
| **Wartend** | Eine Änderung ist gespeichert und auf dem Weg zu den Dashboards. Sie ist normalerweise innerhalb von etwa einer Minute abgeschlossen. |
| **Wird wiederholt** | Eine Übermittlung ist fehlgeschlagen und wird erneut versucht. Der Grund für den Fehler wird neben dem Status angezeigt, mit **Wiederholen**, um sofort erneut zu senden. |
| **Noch nicht angewendet** | Die Einschränkungen des Projekts wurden noch nicht an die Dashboards gesendet. |
| **Angewendet** | Der letzte Versuch, die Einschränkungen an die Dashboards zu senden, war erfolgreich. |
| **Mit Dashboards synchron** | Der Zeilenzugriff hat verglichen, was die Dashboards durchsetzen und was er schreiben würde, und beides stimmt überein. |
| **Dashboards weichen ab** | Die Dashboards setzen nicht durch, was der Zeilenzugriff schreiben würde – eine Regel wurde in Superset geändert oder gelöscht, oder die veröffentlichte Ansicht einer Tabelle kann nicht geprüft werden. |
| **Fehler** | Das Senden der Einschränkungen ist fehlgeschlagen. Der Grund wird neben dem Status angezeigt. |

Sobald eine Änderung **Angewendet** erreicht, prüft das Raster sie gegen die Dashboards und wechselt zu **Mit Dashboards synchron** oder **Dashboards weichen ab**. **Dashboards weichen ab** und **Fehler** bieten beide **Wiederholen** an, wodurch die Einschränkungen des Projekts erneut gesendet werden. Kann der Status überhaupt nicht gelesen werden, meldet das Raster „Couldn't check sync status.“

Ein **Fehler**, der durch eine einzelne Tabelle verursacht wird, nennt die Tabelle und sagt, was zu tun ist – zum Beispiel eine Tabelle, die ohne ihre eingeschränkte Spalte veröffentlicht wurde („Republish or unpublish it.“), oder eine Tabelle mit einer eingeschränkten Spalte, die nicht veröffentlicht ist und die Dashboards nicht filtern können, bis sie es ist. Der Status bleibt auf **Fehler** und nennt die nicht veröffentlichte Tabelle, bis Sie sie veröffentlichen oder stattdessen die Spalte in einer veröffentlichten Tabelle einschränken. Eine solche Tabelle hält den Rest des Projekts nicht auf: Jede andere Tabelle wird auf dem aktuellen Stand gehalten.

Dashboards folgen denselben Gewährungen wie die eigenen Abfragen von PlaidCloud:

- **Jede veröffentlichte Tabelle mit der Spalte wird gefiltert**, nicht nur die Tabelle, die Sie beim Einrichten der Einschränkung betrachtet haben.
- **Eine Gruppe, der nur einige Werte gewährt wurden, wird gefiltert, auch wenn alle anderen jede Zeile sehen**, in jeder Tabelle, deren Dashboard-Dataset existiert.
- **Projekt-Architects sehen jede Zeile**, in Dashboards ebenso wie im Tabellen-Explorer und im Rest von PlaidCloud. Das gilt für die Architect-Gruppen des Projekts und für die Architects eines Projekts, das mit einzelnen Mitgliedern geteilt wird. Der Entzug des Architect-Zugriffs wird in Dashboards sofort wirksam, unabhängig davon, ob Sie die Rolle des Mitglieds ändern, das Mitglied oder seine Gruppe aus dem Projekt entfernen, den Zugriffstyp des Projekts ändern, eine frühere Projektversion wiederherstellen oder die Gruppe löschen.
- **Änderungen der Mitgliedschaft in Sicherheitsgruppen erreichen Dashboards von selbst.** Das Hinzufügen oder Entfernen einer Person in einer Gruppe in PlaidCloud, das Deaktivieren oder Löschen eines Mitglieds, das Löschen einer Gruppe oder das Hinzufügen eines neuen Mitglieds, das Ihren Standard-Sicherheitsgruppen beitritt, aktualisiert innerhalb von etwa einer Minute, was die Person in Dashboards sieht – in jedem Projekt, das dieser Gruppe Werte gewährt, ohne dass jemand den Zeilenzugriff erneut öffnen muss. Eine Änderung der Mitgliedschaft außerhalb von PlaidCloud – direkt in Keycloak oder durch Single Sign-on, das eine Person bei der Anmeldung einer Gruppe zuordnet – erreicht die Dashboards innerhalb von etwa 15 Minuten, ohne dass etwas gespeichert oder wiederholt werden muss.

### Dimensionsgewährungen

Wenn **Dimension** die Wertequelle ist, aktivieren Sie einen Knoten, um alles darunter zu gewähren. Die Gewährung folgt der Dimension: Ein Member, der unter einem aktivierten Knoten hinzugefügt wird, wird dieser Gruppe bei der nächsten Synchronisierung nach dem Speichern der Dimension gewährt, und ein Member, der unter ihm herausgeschoben oder entfernt wird, wird nicht mehr gewährt – niemand muss das Raster erneut öffnen. Wenn Sie es erneut öffnen, werden die Knoten, die Sie aktiviert hatten, wieder als aktiviert angezeigt.

Ein Member, den Sie einzeln und nicht über einen Knoten aktiviert haben, bleibt gewährt, wenn er aus der Dimension entfernt wird, und das Raster kennzeichnet ihn als Wert, den die Quelle nicht mehr hat.

Wenn Sie etwas unterhalb eines aktivierten Knotens deaktivieren, wird der Knoten deaktiviert, und die Gruppe behält nur die Member, die noch aktiviert sind. Wenn Sie diesen Member erneut aktivieren, wird der Knoten nicht wieder aktiviert – klicken Sie dazu auf das Kontrollkästchen des Knotens selbst. **Einfügen**, **Alle auswählen** und **Umkehren** aktivieren Member, niemals Knoten.

Ein Dimensions-Member, dessen Name nicht als Zeilenzugriffswert verwendet werden kann, wird beim Speichern abgelehnt, unter Nennung des Members. Erscheint ein solcher Member später, werden seine Zeilen niemandem gewährt, und der Synchronisierungsstatus nennt ihn: „Dimension ‘…’ member ‘…’ cannot be used as a row access value, so its rows are not granted. Rename it in the dimension.“

### Gewährungen an eine Quelltabelle binden

Statt Werte von Hand zu aktivieren, können Sie eine eingeschränkte Spalte auf eine Quelltabelle verweisen lassen, die die Antwort bereits enthält – eine Zeile pro Gruppe und dem Wert, den sie sehen darf. Schränken Sie zuerst die Spalte im Raster ein und fügen Sie dann einen Workflow-Schritt [**Zeilenzugriff festlegen**](/de/reference/workflow-steps/tables/table-set-row-access/) hinzu, der die Spalte, die Quelltabelle sowie die Gruppen- und Wertespalten der Quelltabelle benennt. Die erste Ausführung des Schritts bindet die Spalte an diese Tabelle: Die von Hand festgelegten Gewährungen der Spalte werden gelöscht, und ihre Gewährungen werden aus den Zeilen der Tabelle gesetzt.

Nach der Bindung ist die Spalte **quellengesteuert**: Das Zeilenzugriff-Raster zeigt sie gesperrt an, mit einem Badge, das die Quelltabelle nennt, und das manuelle Bearbeiten ihrer Gewährungen wird abgelehnt, bis Sie auf **Bindung entfernen** klicken.

Jede spätere Ausführung des Schritts liest die Quelltabelle erneut und wendet die Gewährungen erneut an – planen Sie ihn nach dem Workflow, der diese Tabelle lädt oder aktualisiert, und eine in den Quelldaten hinzugefügte, entfernte oder neu zugewiesene Gruppe erreicht den Zeilenzugriff bei der nächsten Ausführung, ohne dass jemand das Raster von Hand bearbeitet.

Da die Quelltabelle bestimmt, wer was sieht, können nur ein Projekt-Architect, ein Mandantenadministrator oder die eigenen Workflows des Projekts ihre Zeilen ändern oder sie löschen. Alle anderen erhalten die Meldung „This table supplies the row access grants for ‘region’, so only a project Architect can change its rows or delete it.“

### Einschränkungsvorlagen

Wenn Sie eine Einschränkungsform erstellt haben, die Sie wiederverwenden möchten – dieselbe Wertequelle, derselbe Werttyp und dieselbe Einstellung für leere Werte –, speichern Sie sie einmal und wenden Sie sie überall an, wo sie gebraucht wird, statt sie Spalte für Spalte neu aufzubauen.

- **Als Vorlage speichern…** speichert in einem geöffneten Zeilenzugriff-Bildschirm die Form der aktuellen Spalte als benannte Vorlage auf Mandantenebene. Es wird nur die Form gespeichert – es werden keine Gewährungen mitgeführt.
- **Vorlage anwenden** startet bei der Spalte eines anderen Projekts diese Spalte mit der Form der Vorlage, wobei die Gewährungen aller Gruppen leer sind und von Ihnen gefüllt werden.

Jeder Projekt-Architect kann Vorlagen speichern und anwenden. Das Umbenennen (**Umbenennen…**) und Löschen (**Löschen**) einer Vorlage erfordert einen Mandantenadministrator, da eine Vorlage mandantenweit geteilt wird. Das Löschen einer Vorlage lässt die Spalten, auf die sie angewendet wurde, so eingeschränkt, wie sie sind.

<Aside type="note">
Vorlagen sind Kopien, keine Verknüpfungen. Eine spätere Bearbeitung einer Vorlage ändert keine Spalte, die sie bereits angewendet hat – wenden Sie die Vorlage erneut an, um eine Spalte auf den Stand einer späteren Überarbeitung zu bringen.
</Aside>

### Gewährungen aus SSO-Gruppenattributen

Eine Spalte kann ihre Gewährungen auch von Ihrem Identitätsanbieter statt von PlaidCloud beziehen. Ein Projekt-Architect aktiviert dies für eine Spalte im Zeilenzugriff, indem er **Accept row-access grants from SSO group attributes** aktiviert.

Sobald dies aktiviert ist, legt das Keycloak-Attribut `row_access.<column>` einer Sicherheitsgruppe die Werte fest, die diese Gruppe über diese Spalte sehen kann – setzen Sie das Attribut für die Gruppe in Keycloak, und PlaidCloud übernimmt es automatisch für jede Gruppe, die bereits Zugriff auf das Projekt hat. Im Zeilenzugriff selbst ist nichts weiter zu konfigurieren, und die Gewährungen bleiben sowohl in den eigenen Abfragen von PlaidCloud als auch in Superset-Dashboards synchron.

<Aside type="caution">
Dies gewährt nur einer Gruppe Werte, die das Projekt bereits erreichen kann. Das Hinzufügen von `row_access.region` zu einer Gruppe ohne Projektzugriff gewährt ihr nichts, bis der Gruppe auch Zugriff auf das Projekt erteilt wird.
</Aside>

### Vorschau vor dem Speichern

Der Zeilenzugriff zeigt Ihnen, was eine Änderung bedeutet, bevor Sie sie übernehmen:

- Eine Fußzeile **Vorschau als** zeigt, wie viele der Zeilen der Tabelle eine Gruppe von der Gesamtzahl sehen würde, mit einer Stichprobe der Zeilen selbst – wählen Sie eine beliebige Gruppe im Raster aus, um sie in der Vorschau anzusehen. Die Vorschau wird nach dem Speichern aktualisiert.
- Vor dem Speichern warnt Sie der Zeilenzugriff vor allem, was einen zweiten Blick wert ist: eine Gruppe ohne Markierung, und ob das bei Ihrer Einstellung **Everyone else** bedeutet, dass sie alle Zeilen oder keine sieht; Mitglieder mit Projektzugriff, die von keiner Gewährung einer Gruppe erfasst werden; oder Zeilen, deren Wert in dieser Spalte leer (`NULL`) ist und die keiner Gruppe gewährt werden.

### Was ein eingeschränktes Mitglied sieht

Überall dort, wo ein eingeschränktes Mitglied eine Tabelle über ihren Namen liest, erhält es nur seine Zeilen – im Raster, in den Spaltenfacetten und Downloads des Tabellen-Explorers, im Dialog für den Tabellen-Download, in Apps und Tools, die als der Betrachter lesen, und in Dashboards. Der Tabellen-Explorer zeigt in seiner Symbolleiste **Zeilen durch Ihren Zugriff eingeschränkt** an, wenn das Raster, das Sie betrachten, durch Ihre Gewährungen gefiltert wurde, und beim Start eines Downloads, der gefiltert wird, erscheint „Rows limited by your access.“ Ein Architect, der jede Zeile liest, sieht keinen der beiden Hinweise.

### Zeilenzugriff und selbst geschriebene Abfragen

Wenn der Zeilenzugriff Ihre Zeilen begrenzt, können Sie auf den Abfragebildschirmen des Projekts eigene SQL-Abfragen ausführen und erhalten genau die Zeilen, die Ihre Gewährungen zulassen. Sie können die Ergebnisse als CSV, Excel oder JSON exportieren, und der Export enthält nur diese Zeilen, mit dem Hinweis **Zeilen durch Ihren Zugriff eingeschränkt**. Ein Projekt-Architect liest jede Zeile, da ein Architect sich ohnehin jeden Wert jeder eingeschränkten Spalte selbst gewähren kann, und sieht keinen Hinweis.

Ein Gewährungswert, der ein Prozentzeichen (`%`) enthält, liefert auf Abfragebildschirmen seine gewährten Zeilen, und der Download einer solchen Abfrage als CSV funktioniert.

Folgendes wird für ein Mitglied, das kein Projekt-Architect ist, weiterhin abgelehnt:

- Das Ausführen eigener freier SQL-Abfragen auf einem Snowflake- oder Databricks-Projekt-Warehouse.
- Das Exportieren der Ergebnisse Ihres eigenen SQL aus einem Warehouse der Postgres-Familie.
- Das Exportieren der Ergebnisse Ihres eigenen SQL in eine andere Datenbank.
- Das Eingeben einer Zeilenbedingung in die Vorschau „Test row 1“ eines Fan-out-Schritts.
- Das Lesen einer zugriffsgesteuerten Tabelle zum Stand eines früheren Snapshots (Time Travel).

Wer abgelehnt wird, erfährt, um welches Projekt es sich handelte, und wird auf die Leser über den Namen hingewiesen: Das Lesen einer Tabelle über ihren Namen ist der übliche Weg, auf dem Apps und Tools Daten lesen; dabei werden die Gewährungen angewendet und die Zeilen geliefert, auf die der Betrachter Anspruch hat. Eine Spaltenfacette, die als einfache Abfrage einer einzelnen Tabelle geschrieben ist, wird ebenfalls über den Namen gelesen und liefert daher die eigenen Werte des Mitglieds, statt abgelehnt zu werden. Ein Projekt-Architect kann all dies wie geschrieben ausführen.

Der Zeilenzugriff filtert eine Ansicht nach der zugriffsgesteuerten Spalte, daher muss eine Ansicht diese Spalte unter ihrem ursprünglichen Namen beibehalten. Eine Ansicht, die die zugriffsgesteuerte Spalte entfernt oder umbenennt, wird nicht gefiltert.

Der Import einer Tabellenkalkulation ist für sich genommen keine selbst geschriebene Abfrage – ein gewöhnlicher Dateiimport liest überhaupt keine eingeschränkten Daten, er erstellt nur die neue Tabelle des Projekts aus der hochgeladenen Datei und ist daher vom Zeilenzugriff nicht betroffen. Die Ausnahme ist ein Import, dessen Datenprojektion vom Aufrufer geliefert wird: ein Ausdruck pro Spalte oder eine dynamische Excel-Zuordnung. Auf dem interaktiven Importbildschirm werden diese genauso abgelehnt wie die oben genannten Oberflächen für freies SQL und erfordern einen Projekt-Architect, da eine vom Aufrufer gelieferte Projektion eine andere Tabelle lesen könnte. Ein Import, der aus einem Workflow läuft, ist in beiden Fällen nicht betroffen, da er unter der eigenen Dienstidentität des Projekts läuft.

<Aside type="caution">
Das Einschränken Ihrer ersten Spalte in einem Projekt ändert dies für alle, die es verwenden. Wenn eine Panel-App, ein Notebook oder eine Integration in diesem Projekt ihr eigenes SQL auf einem Snowflake- oder Databricks-Warehouse zusammensetzt oder ihre eigenen Abfrageergebnisse aus einem Warehouse der Postgres-Familie exportiert, stellen Sie sie vor dem Einschränken so um, dass sie die Tabelle über den Namen liest – andernfalls funktioniert sie für alle, die kein Architect sind, nicht mehr.
</Aside>

### Zeilenzugriff und Dateneditor

Der Dateneditor liest und schreibt eine Tabelle direkt, daher gilt der Zeilenzugriff für ihn auf beiden Seiten.

Das Öffnen einer eingeschränkten Tabelle im Dateneditor zeigt nur die Zeilen, die Ihrer Sicherheitsgruppe gewährt werden – derselbe Filter, der Sie in ein Dashboard begleitet, und er gilt auch dann, wenn die eingeschränkte Spalte nicht zu den im Raster angezeigten Spalten gehört.

Das Speichern Ihrer Änderungen erfordert **Architect** im Projekt. Ein Speichern ersetzt die Zeilen der Tabelle im Ganzen, statt sie zu lesen, und wird nicht zeilenweise gefiltert. Daher wird das Bearbeiten von Daten in einer eingeschränkten Tabelle als Authoring-Aktion und nicht als Lesevorgang behandelt: Wer kein Architect ist, erhält die Meldung, dass diese Rolle nötig ist. Eine Tabelle ohne eingeschränkte Spalte wird wie bisher bearbeitet, ebenso jedes Projekt, das keine Zeilen einschränkt.

### Daten in eine eingeschränkte Tabelle laden

Wenn der Zeilenzugriff die Zeilen begrenzt, die Sie sehen, wirkt das Schreiben eines DataFrames in eine eingeschränkte Tabelle oder deren Leerung mit dem Python-Client (`PlaidConnection`) bzw. das Speichern von Datensätzen darin oder deren Leerung über die REST-API nur auf Ihre eigenen Zeilen. Das Ersetzen der Daten der Tabelle ersetzt nur die Zeilen, die Sie sehen können, das Leeren leert nur diese Zeilen, und das Anhängen fügt Zeilen hinzu; jede andere Zeile bleibt, wie sie ist.

Ein Ladevorgang mit einer Zeile außerhalb Ihres Zugriffs wird abgelehnt, bevor sich etwas ändert, und der Fehler nennt jeden Wert außerhalb Ihres Zugriffs mit der Anzahl der Zeilen, die ihn tragen. Eine Zeile, die die eingeschränkte Spalte auslässt, wird in dieser Spalte als leer geprüft und daher abgelehnt, sofern Ihr Zugriff leere Zeilen nicht einschließt. Das Ersetzen der Daten auf eine Weise, die den Typ einer Spalte ändern würde, wird ebenfalls abgelehnt; bitten Sie einen Projekt-Architect, diese Änderung vorzunehmen.

Projekt-Architects, Mitglieder, deren Gewährungen jede Zeile abdecken, und Workflow-Ausführungen, die unter der Dienstidentität des Projekts laufen, schreiben die gesamte Tabelle. Eine Tabelle ohne eingeschränkte Spalte ist nicht betroffen.

Alles andere, was eine ganze eingeschränkte Tabelle ersetzt oder entfernt, wird abgelehnt, solange die Tabelle eine Zeile enthält, die Sie nicht sehen können, und es wird nichts geändert: der Import einer Datei in sie, das Kopieren einer Tabelle aus einem anderen Projekt in sie, das Wechseln oder Zusammenführen ihres Branches, das Wiederherstellen aus einem Archiv oder im Rahmen der Wiederherstellung der gehaltenen Snapshots des Projekts, das Löschen, das Zurückholen nach dem Löschen sowie jede andere Aktion, die die Tabelle leert, bevor sie sie erneut füllt. Eine Zeile, deren eingeschränkte Spalte leer ist, gilt als eine, die Sie nicht sehen können, sofern Ihr Zugriff leere Zeilen nicht einschließt. Eine Tabelle, deren Zeilen Sie alle sehen können, etwa eine, die Sie erstellt haben und die nur Ihre eigenen Zeilen enthält, kann ersetzt oder gelöscht werden.

Jeder dieser Schreibvorgänge, den eine Person in einer beliebigen Tabelle ausführt, wird im Sicherheitsprotokoll aufgezeichnet, auch die abgelehnten. Workflow-Ausführungen werden dort nicht aufgezeichnet.

### Zeilenanzahlen und Tabellengrößen

Die Zeilenanzahl und die Speichergröße einer Tabelle beschreiben die gesamte Tabelle, nicht die Zeilen, die Sie sehen dürfen, und würden einem eingeschränkten Leser daher mitteilen, wie viele Zeilen jenseits seiner Gewährung existieren. In einem Projekt, das Zeilen einschränkt, sieht jeder, dessen Lesezugriffe gefiltert werden, für keine Tabelle des Projekts eine Zeilenanzahl oder Größe – in Tabellenlisten, in der Suche, in Tabellendetails und Snapshots sowie über den KI-Assistenten und KI-Tools, die über MCP verbunden sind. Das gilt für jede Tabelle im Projekt, auch für Tabellen ohne eingeschränkte Spalte. Auch die Gesamtwerte des Projekts sind für sie ausgeblendet – die Gesamtzeilenanzahl und -größe auf der Startseite, in Projektlisten und in der Suche sowie in den Projektdetails.

Dasselbe gilt für den Verlauf der Workflow-Ausführungen. Die gelesenen und geschriebenen Zeilen, die jede Ausführung und jeder Schritt aufgezeichnet hat, beschreiben ebenfalls die gesamte Tabelle, daher bleiben diese Werte für dieselben Leser leer – im Ausführungsverlauf eines Workflows und eines Schritts sowie über den KI-Assistenten und KI-Tools, die über MCP verbunden sind. Für sie prüft [Weave](/de/guides/ai-assistant/weave-findings/) Schritte nicht auf Zeilen oder leere Werte, die sich von früheren Ausführungen unterscheiden, da ein Befund ihnen selbst mitteilen würde, dass sich die Anzahl der gesamten Tabelle verändert hat.

Projekt-Architects sehen die Werte wie bisher, ebenso alle in einem Projekt, das keine Zeilen einschränkt.

### Sehen, was ein Mitglied sehen kann

Um zu prüfen, was eine bestimmte Person sehen kann – statt dessen, was einer Gruppe gewährt wird –, öffnen Sie **Identität → Member**, wählen Sie das Mitglied aus und öffnen Sie dessen Registerkarte **Zeilenzugriff**. Die Spalte **Effektiver Zugriff** listet für jedes eingeschränkte Projekt und jede eingeschränkte Spalte die Werte auf, die dieses Mitglied über alle seine Gruppen zusammen sieht – einschließlich Gewährungen aus SSO-Gruppenattributen und leerer (`NULL`) Zeilen, wo die Gewährung einer Gruppe sie einschließt. Ein Projekt-Architect wird als **Sieht jede Zeile (Architect)** angezeigt, da ein Architect jede Zeile liest. Es ist dieselbe Antwort, die die eigenen Abfragen von PlaidCloud anwenden, daher ist sie nützlich für den Support und um zu bestätigen, dass eine Änderung das bewirkt hat, was Sie beabsichtigten, bevor jemand ein Problem meldet.

### Verständlichere Fehlermeldungen

Wo der Zeilenzugriff eine Aktion blockiert – eine selbst geschriebene Abfrage in einem eingeschränkten Projekt, eine Bearbeitung ohne Architect, eine Änderung an Automatisierung, einer Dimension oder einer Quelltabelle für Gewährungen und die anderen oben beschriebenen Fälle –, nennt die Meldung, was eingeschränkt ist und was als Nächstes zu tun ist, etwa die Architects, die Sie fragen können, statt eines allgemeinen Fehlers.

### Der Zeilenzugriff wird protokolliert

Das Einschränken oder Aufheben der Einschränkung einer Spalte sowie das Bearbeiten der Gewährungen einer Gruppe schreiben jeweils einen Eintrag in das [Projektprotokoll](/de/get-started/tutorials/collaborate-versions-and-sharing/#das-projektprotokoll-lesen) dieses Projekts – wer die Änderung wann vorgenommen hat. Öffnen Sie **Analyze → Projects → Log** im Projekt, um ihn zu sehen. Für diese Nachverfolgung muss nichts zum Zeilenzugriff aktiviert werden; sie wird genauso aufgezeichnet wie jede andere nachverfolgte Änderung an einem Projekt.

## Standard-Sicherheitsgruppen festlegen

Die Einstellung ist beim Hinzufügen einer neuen Sicherheitsgruppe verfügbar, wenn Sie unten im Fenster „Sicherheitsgruppe“ das Kontrollkästchen „Assign to New Users by Default“ aktivieren.
