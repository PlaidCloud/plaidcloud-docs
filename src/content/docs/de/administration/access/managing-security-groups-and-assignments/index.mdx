Die Sicherheits- und Zugriffsverwaltung von PlaidCloud ist unkompliziert. Einem Mitglied wird der Zugriff anhand der Gruppen gewährt oder verweigert, denen es zugeordnet ist. Die Sicherheitszuordnung eines Mitglieds lässt sich einfach hinzufügen oder ändern.

<Aside>Jeder Workspace darf eine unbegrenzte Anzahl von Sicherheitsgruppen haben, wir empfehlen jedoch, ihre Anzahl gering zu halten, um die Sicherheitsverwaltung zu erleichtern.</Aside>



## Sicherheitsgruppen verwalten


Sicherheitsgruppen können hinzugefügt, aktualisiert oder gelöscht werden.



**So verwalten Sie Sicherheitsgruppen:**


1. Öffnen Sie Identität
2. Wählen Sie in der Leiste **Sicherheitsgruppen** aus (dadurch wird eine Liste der vorhandenen Gruppen angezeigt)
3. Um eine Gruppe hinzuzufügen, klicken Sie auf **New group**
4. Um die Berechtigungen einer Gruppe zu bearbeiten, klicken Sie auf das ganz linke Symbol

**So verwalten Sie Gruppenmitglieder:**


1. Öffnen Sie Identität
2. Wählen Sie in der Leiste **Sicherheitsgruppen** aus
3. Klicken Sie auf das Symbol „Mitglied“
4. Aktivieren Sie die Mitglieder, die zur Gruppe gehören sollen, und deaktivieren Sie die übrigen. Verwenden Sie das Filterfeld, um Personen zu finden. Siehe [Zuweisen mit der Auswahl](#zuweisen-mit-der-auswahl)
5. Klicken Sie auf **Zuweisungen aktualisieren**

<Aside>Das Speichern ohne zugewiesene Personen bewirkt keine Änderung und weist Sie darauf hin. Um einer Gruppe alle Mitglieder zu entziehen, entfernen Sie ihre Berechtigungen oder löschen Sie die Gruppe, statt ihre Mitgliederliste zu leeren.</Aside>

<Aside>Wenn einer Gruppe über [Zeilenzugriff](#zeilenzugriff-verwalten) Zeilen gewährt werden, erreicht eine Änderung der Mitgliedschaft die Dashboards innerhalb von etwa einer Minute: Wer hinzugefügt wird, sieht dort die Zeilen der Gruppe, und wer entfernt wird, sieht sie nicht mehr. Das Deaktivieren oder Löschen eines Mitglieds und das Löschen einer Gruppe wirken auf dieselbe Weise.</Aside>

<Aside type="caution">Berechtigungen, die Sie selbst nicht erteilen können, bleiben beim Speichern der Berechtigungsmatrix einer Gruppe unberührt und werden darin nicht angezeigt. Wenn Sie eine davon ändern müssen, bitten Sie jemanden, der diese Berechtigung besitzt – die Matrix bearbeitet immer nur das, was Sie kontrollieren.</Aside>

<Aside type="caution">Sie können ein Mitglied einer Gruppe hinzufügen oder die Gruppen eines Mitglieds auswählen, wenn Sie jede Berechtigung besitzen, die die Gruppe gewährt. Dasselbe gilt für das Einladen einer Person als Architect. Workspace-Administratoren sind davon nicht eingeschränkt.</Aside>

## Zuweisen mit der Auswahl

Überall dort, wo Sie Personen, Gruppen oder anderen Elementen Zugriff auf etwas geben, ersetzt eine einzige Checkliste das frühere Listenpaar. Jede Zeile hat ein Kontrollkästchen, und eine aktivierte Zeile ist zugewiesen. Sie verwenden sie, um die Mitglieder einer Gruppe, die Sicherheitsgruppen eines Mitglieds, die Mitglieder, Gruppen, Agenten und Eigentümer eines Kontos, den Zugriff auf eine Verbindung, die Workspace-Mitglieder einer Verteilerliste und die Workflows in einer Weave-Bereitschaftsgruppe festzulegen.

- **Filter.** Geben Sie im Filterfeld einen Suchbegriff ein, um die Liste einzugrenzen. Der Abgleich ist teilweise und ignoriert die Groß-/Kleinschreibung, sodass `smith` jeden Namen oder jede E-Mail-Adresse findet, die es enthält, und `@example.com` alle Personen dieser Domain. Wenn Sie mehrere Wörter eingeben, bleiben nur Zeilen übrig, die zu allen passen.
- **Eine Liste von E-Mail-Adressen einfügen.** Fügen Sie mehrere E-Mail-Adressen ein, getrennt durch Leerzeichen, Kommas, Semikolons oder Zeilenumbrüche, und die Liste zeigt genau diese Personen. Sie können ganze Domains wie `@example.com` beimischen. Eine Zeile unter dem Filter gibt an, wie viele eingefügte Einträge gefunden wurden, und listet alle auf, die nicht gefunden wurden. **Zuweisen** gefolgt von der Anzahl der Treffer aktiviert mit einem Klick alle Treffer.
- **Alle, Zugewiesen und Nicht zugewiesen.** Die drei Schaltflächen über der Liste wechseln zwischen allem, nur dem Zugewiesenen und nur dem Nicht-Zugewiesenen, jeweils mit einer Anzahl. Sie lassen sich mit dem Filter kombinieren.
- **Alle angezeigten zuweisen und Zuweisung aller angezeigten aufheben.** Diese aktivieren oder deaktivieren jede Zeile, die Filter und Ansicht gerade anzeigen, und lassen ausgeblendete Zeilen unberührt. Eine Zeile über der Liste gibt an, wie viele Zeilen von der Gesamtzahl angezeigt werden.
- **Will add und Will remove.** Nichts wird gespeichert, bis Sie auf die Schaltfläche zum Speichern klicken. Eine von Ihnen aktivierte Zeile zeigt eine Anzeige **Will add**, und eine von Ihnen deaktivierte Zeile zeigt **Will remove**. Die Zusammenfassung lautet zum Beispiel `12 assigned · +3 to add · −1 to remove`. **Undo changes** stellt alles so wieder her, wie es beim Öffnen des Fensters war.
- **Nur speichern, wenn sich etwas geändert hat.** Die Schaltfläche zum Speichern, etwa **Zuweisungen aktualisieren**, **Mitglieder aktualisieren** oder **Gruppen aktualisieren**, ist nur verfügbar, wenn Sie eine Änderung vorgenommen haben.
- **Tastatur.** Die **Leertaste** aktiviert oder deaktiviert die ausgewählte Zeile. Die **Eingabetaste** im Filterfeld speichert nicht, sodass ihr Drücken während der Suche nie den Zugriff ändern kann.

Wenn Sie sehen können, wer Zugriff hat, ihn aber nicht ändern können, zum Beispiel bei einer Verbindung, deren Eigentümer Sie nicht sind, ist die Auswahl schreibgeschützt: Sie listet nur die bereits zugewiesenen Personen auf, ohne Kontrollkästchen oder Schaltflächen, die sie ändern.

## Zeilenzugriff verwalten

Der Zeilenzugriff schränkt anhand des Werts einer Spalte ein, welche Zeilen einer Tabelle eine Sicherheitsgruppe sehen kann. Beispielsweise kann eine Spalte `region` den Zugriff einschränken, wobei eine Gruppe mit den Werten `East` und `Central` auf Zeilen mit diesen Werten beschränkt ist. Alles für ein Projekt und eine Spalte – die Auswahl der Spalte, die Wahl, woher ihre Werte stammen, und die Entscheidung, welche Gruppe was sieht – geschieht in einem einzigen Bildschirm, und das Speichern wirkt sofort.

Das Einrichten und Ändern des Zeilenzugriffs erfordert einen Projekt-Architect oder einen Tenant-Administrator. Allen anderen, die die Registerkarte Sicherheit eines Projekts öffnen, wird mitgeteilt, dass der Zeilenzugriff nur Architects vorbehalten ist, und die unten genannten Einstiegspunkte erscheinen für sie nicht.

### Zeilenzugriff öffnen

Jeder Einstiegspunkt öffnet denselben Bildschirm für den Zeilenzugriff:

- **Die Symbolleiste des Tabellen-Explorers** hat eine Schaltfläche **Zeilenzugriff**, mit einem Kennzeichen, wenn die Tabelle bereits Zeilen einschränkt. Sie öffnet sich bei der ersten eingeschränkten Spalte der Tabelle, falls es eine gibt, und Sie können zu jeder anderen Spalte der Tabelle wechseln.
- **Das Facettenmenü einer Spalte** enthält **Zeilen nach dieser Spalte einschränken…**, das den Zeilenzugriff für diese Spalte öffnet. Bei einer Spalte, die bereits Zeilen einschränkt, lautet der Eintrag **Zeilen durch diese Spalte eingeschränkt – bearbeiten…**.
- **Die Registerkarte Sicherheit eines Projekts** listet jede eingeschränkte Spalte des Projekts auf, mit den Tabellen, für die sie gilt, den Gruppen mit Gewährungen und ihrem Status **Synchronisieren**. Wählen Sie eine Spalte aus, um sie zu bearbeiten, oder klicken Sie auf **Spalte einschränken…**, um eine neue zu beginnen: Wählen Sie eine Tabelle und dann eine Spalte. Spalten, die bereits Zeilen einschränken, sind mit einem Schloss gekennzeichnet.
- **Identität → Mitglied**, auf der Registerkarte **Zeilenzugriff** eines Mitglieds, und **Identität → Sicherheit → Sicherheitsgruppen**, in der Zusammenfassung zum Zeilenzugriff einer Gruppe. **Zeilenzugriff öffnen** (oder **Bearbeiten**) öffnet die ausgewählte Spalte; **Hinzufügen** schränkt eine weitere Spalte im Projekt dieser Zeile ein.

Wenn der Bildschirm für eine Spalte geöffnet wird, bleibt er bei dieser Spalte. Wird er mit **Spalte einschränken…** oder **Hinzufügen** geöffnet, können Sie eine auswählen.

### Das Raster für den Zeilenzugriff

So schränken Sie eine Tabelle nach einer Spalte ein:

1. Öffnen Sie den Zeilenzugriff über einen der oben genannten Einstiegspunkte und wählen Sie die Spalte aus, falls Sie nicht mit einer gekommen sind – die Auswahl bietet die tatsächlichen Spalten der Tabelle an, keinen freien Text.
2. Wählen Sie eine **Wertequelle** aus – **Spalte** (die eindeutigen Werte einer Tabellenspalte), **Dimension** (Knoten einer Dimension) oder **Liste** (Werte, die Sie eingeben). Der Werttyp folgt dem Datentyp der Spalte.
3. Aktivieren Sie für jede Sicherheitsgruppe die Werte, die diese Gruppe sehen darf. Das Raster listet die Gruppen mit Zugriff auf das Projekt auf sowie jede Gruppe, die bereits eine Gewährung für die Spalte besitzt.
4. Legen Sie **Everyone else** auf **sees all rows** oder **sees no rows** fest – das gilt für jede Gruppe ohne Häkchen im Raster.
5. Klicken Sie auf **Speichern**.

Das Speichern wirkt live. Die eigenen Abfragen von PlaidCloud folgen der Änderung sofort und Ihre Superset-Dashboards innerhalb von etwa einer Minute – es gibt keinen separaten Schritt zum Anwenden, und **Speichern** hält nur an, um nachzufragen, wenn eine Gewährung einen Wert enthält, den ihre Quelle nicht mehr hat (siehe unten). Der Synchronisierungsstatus des Bildschirms zeigt, wie weit die Änderung gekommen ist; siehe [Dashboards synchron halten](#dashboards-synchron-halten).

Das Raster erledigt auch die Details für Sie:

- **Viele Werte.** Die Werte sind sortiert. Wenn eine Spalte mehr Werte hat, als hineinpassen, meldet das Raster „More values than fit here — type to search.“ und das Filterfeld durchsucht die gesamte Spalte, wobei jeder Wert erhalten bleibt, den eine Gruppe bereits besitzt.
- **Werte, die die Quelle nicht mehr hat.** Ein Wert, der einer Gruppe gewährt wurde, bleibt im Raster, wenn seine Quelle ihn verliert – keine Zeile der Tabelle hat ihn mehr, die Dimension hat den Knoten nicht mehr oder die Liste hat ihn nicht mehr. Seine Spaltenüberschrift trägt ein Warnsymbol, und beim Daraufzeigen wird der Grund genannt. **Alle auswählen**, **Umkehren** und **Einfügen** lassen einen solchen Wert so, wie ihn jede Gruppe hält. Aus einer Gewährung wird nichts entfernt, es sei denn, Sie deaktivieren es: Wenn Sie auf **Speichern** klicken, während eine Gruppe noch einen solchen Wert hält, nennt der Zeilenzugriff die Gruppen und Werte unter **Values No Longer in the Source** und fragt nach. **Keep and Save** speichert sie unverändert, **Remove and Save** entfernt sie zuerst aus der Gewährung jeder Gruppe, und das Schließen der Frage speichert nichts. Würde das Entfernen dazu führen, dass bei einer Gruppe nichts mehr aktiviert ist, gibt die Frage an, ob diese Gruppe dann alle Zeilen oder keine sähe, gemäß **Everyone else**. Ein noch nicht gespeichertes Häkchen verschwindet mit seinem Wert. Wenn eine Spalte mehr Werte hat, als hineinpassen, oder ihre Tabelle noch nicht erstellt ist, kann der Zeilenzugriff nicht erkennen, welche Werte der Tabelle fehlen, und behält daher jeden gewährten Wert, ohne einen zu kennzeichnen.
- **Leere Werte.** Ein einziges Kontrollkästchen **Leere Werte – sichtbar für jede Gruppe mit einer Gewährung** entscheidet über die Zeilen ohne Wert in der Spalte. Aktivieren Sie es, und jede Gruppe mit irgendeiner Gewährung für die Spalte sieht diese Zeilen.
- **Eine noch nicht erstellte Tabelle** zeigt statt einer leeren Liste **Erstellen Sie diese Tabelle zuerst (führen Sie den Workflow aus, der sie erstellt)**.
- **Speichern wartet auf die Werte auf dem Bildschirm.** Während Werte geladen werden – nach dem Wechseln der Wertequelle, der Dimension oder der Tabelle oder nach dem Anwenden einer Vorlage – ist **Speichern** deaktiviert, mit dem Tooltip „Save is available once this source's values load.“ Schlägt ein Ladevorgang fehl, meldet das Raster dies und bittet Sie, die Quelle erneut auszuwählen; nichts wird gespeichert, bis ein Ladevorgang erfolgreich ist.

### Ein Spaltenname, jede Tabelle

Eine Einschränkung gehört zu einem Spalten*namen* im Projekt, nicht zu einer einzelnen Tabelle. Sobald `region` Zeilen einschränkt, wird jede Tabelle im Projekt mit einer Spalte namens `region` danach gefiltert, sowohl in den eigenen Abfragen von PlaidCloud als auch in Dashboards. Die Liste **Applies to** im Raster zeigt diese Tabellen. Sie ist schreibgeschützt, weil der Spaltenname sie bestimmt, und eine später hinzugefügte Tabelle mit derselben Spalte wird abgedeckt, sobald sie veröffentlicht ist.

Wenn keine Tabelle im Projekt eine Spalte mit diesem Namen hat, warnt das Fenster zusätzlich zur Anzeige **Applies to 0 tables**, dass die Einschränkung kein Dashboard filtert, bis eine Tabelle sie hat. Fügen Sie die Spalte einer Tabelle hinzu oder korrigieren Sie den Spaltennamen, und die Warnung verschwindet.

<Aside type="caution">
**Ein Spaltenname muss exakt übereinstimmen** – einschließlich Groß-/Kleinschreibung und Leerzeichen. `Region` und `region` sind verschiedene Namen, ebenso `region` und `region ` mit einem Leerzeichen am Ende. Die Auswahl bietet nur echte Spaltennamen an, daher spielt dies vor allem dann eine Rolle, wenn eine Spalte an anderer Stelle umbenannt wird – der Zeilenzugriff warnt Sie dann und nennt die ähnlichste gefundene Spalte, statt stillschweigend nichts einzuschränken.
</Aside>

<Aside type="caution">
**Das Veröffentlichen einer Tabelle, die Zeilen einschränkt, richtet im selben Schritt ihren Dashboard-Filter ein.** Dashboards lesen eine Tabelle über ihre veröffentlichte Berichtsansicht. Wenn Sie also eine Tabelle veröffentlichen oder erneut veröffentlichen, die eine eingeschränkte Spalte enthält, registriert PlaidCloud den Dashboard-Filter dieser Tabelle, bevor die Veröffentlichung abgeschlossen wird. Gelingt das nicht, wird die Veröffentlichung abgelehnt und alles, was dieser Versuch erstellt hat, wird zurückgerollt, sodass eine eingeschränkte Tabelle nie ungefiltert in Dashboards verbleibt. Eine *Ansicht* kann in einem Projekt, das Zeilen einschränkt, nicht veröffentlicht werden, da die Abfrage einer Ansicht die eingeschränkte Spalte umbenennen oder ableiten kann. Siehe [Tabellen veröffentlichen](/de/guides/data/publish/).
</Aside>

### Eine Einschränkung aufheben

**Einschränkung aufheben** im Raster entfernt die Einschränkung nach einer Bestätigung im Text – „Stop restricting rows by ‘region’? Every group's grant on it is removed and everyone sees its rows.“ Der Zeilenzugriff bestätigt dann „Rows in ‘region’ are no longer restricted.“ Das Superset-Dataset der Spalte wird damit entfernt, es sei denn, Diagramme verwenden es noch; in diesem Fall sagt der Zeilenzugriff, dass das Dataset bestehen bleibt und wie viele Diagramme es verwenden.

Eine Spalte kann nicht umbenannt oder gelöscht werden, solange sie Zeilen einschränkt. Einem Architect wird mitgeteilt, dass er die Einschränkung zuerst im Zeilenzugriff aufheben soll; allen anderen wird mitgeteilt, dass sie einen Projekt-Architect fragen sollen.

### Wer ein Projekt mit Zeileneinschränkung ändern darf

Die Workflows, Schritte und benutzerdefinierten Funktionen eines Projekts laufen unter der eigenen Dienstidentität des Projekts, die jede Zeile liest. Wer sie ändern kann, könnte einen Schritt veranlassen, Zeilen, die ihm nicht gewährt sind, in eine Tabelle zu kopieren, die er lesen kann; daher schränkt das Einschränken von Zeilen in einem Projekt auch ein, wer ändern darf, was das Projekt tut. Sobald ein Projekt mindestens eine Spalte einschränkt:

- **Automatisierung ist nur Architects vorbehalten.** Nur Projekt-Architects und Tenant-Administratoren können Workflows, Schritte, benutzerdefinierte Funktionen, Zeitpläne, Workflow- und Projektvariablen sowie Benachrichtigungs-E-Mail-Vorlagen ändern – und aus demselben Grund ein Workflow-Bundle importieren, einen Alteryx-Workflow konvertieren oder in das Projekt importieren, kopieren oder wiederherstellen oder dessen Verbindungsumgebung, Standard-Dokumentenkonto oder ERP-Buchungsmodus ändern. Alle anderen können die Workflows des Projekts weiterhin ausführen: **Start**, **Beenden**, **Fortsetzen** und **Ausgewählte(n) Schritt(e) ausführen** bleiben verfügbar. Der Schritt-Editor, die Bearbeitungssteuerelemente des Workflows, der UDF-Editor und das Zeitplanformular öffnen sich für sie schreibgeschützt, mit einem Banner, das die Architects nennt, die sie fragen können: „This project restricts rows, so only its Architects can change workflows, steps, UDFs, schedules, variables and notify templates. You can still run them.“
- **Dimensionen, die eine eingeschränkte Spalte liest, sind nur Architects vorbehalten.** Eine Dimension, die entscheidet, wer welche Zeilen sieht – die Wertequelle einer eingeschränkten Spalte –, kann nur von einem Projekt-Architect oder einem Tenant-Administrator und von den eigenen Workflows des Projekts geändert werden. Das umfasst das Hinzufügen, Verschieben, Umbenennen, Kopieren, Leeren, Laden und Wiederherstellen ihrer Knoten sowie die Dimension selbst. Allen anderen wird mitgeteilt: „This dimension decides who sees which rows of ‘region’, so only a project Architect can change it.“ Dimensionen, die keine Einschränkung liest, sind nicht betroffen.
- **Eine Quelltabelle für Gewährungen ist nur Architects vorbehalten.** Bei einer Tabelle, die als [Quelle der Gewährungen](#gewährungen-an-eine-quelltabelle-binden) einer Spalte gebunden ist, können Zeilen nur von einem Projekt-Architect, einem Tenant-Administrator oder den Workflows des Projekts geändert werden, ebenso das Löschen der Tabelle – gleichermaßen über den Dateneditor, einen Import, ein Laden über einen Connector oder die API.
- **Das Kopieren des Projekts ist nur Architects vorbehalten**, und die Kopie meldet „This copy is not row-restricted.“ – das neue Projekt trägt keine Einschränkung, bis Sie eine einrichten.
- **Das Wiederherstellen einer früheren Version ist eine Änderung wie jede andere.** Das Wiederherstellen der eigenen Einstellungen des Projekts oder einer oben genannten Dimension erfordert einen Projekt-Architect. Eine Wiederherstellung gilt immer für das Element, zu dem die Version gehört, sodass sie nicht auf ein anderes Projekt gerichtet werden kann, um dies zu umgehen – siehe [Versionsverlauf](/de/guides/projects/managing-projects/#versionsverlauf).
- **Das Bearbeiten von Daten in einer eingeschränkten Tabelle** erfordert einen Architect, wie unter [Zeilenzugriff und Dateneditor](#zeilenzugriff-und-dateneditor) beschrieben.
- **DataFrame-Schreibvorgänge, Datensatz-Speicherungen und Leerungen in eine eingeschränkte Tabelle ändern nur Ihre eigenen Zeilen**, es sei denn, Sie sehen jede Zeile, wie unter [Daten in eine eingeschränkte Tabelle laden](#daten-in-eine-eingeschränkte-tabelle-laden) beschrieben.
- **Importe, Kopien, Branch-Wechsel, Wiederherstellungen und Löschungen einer eingeschränkten Tabelle werden abgelehnt**, solange sie eine Zeile enthält, die Sie nicht sehen können, wie unter [Daten in eine eingeschränkte Tabelle laden](#daten-in-eine-eingeschränkte-tabelle-laden) beschrieben.

Bevor die erste Spalte in einem Projekt eingeschränkt wird, teilt Ihnen der Zeilenzugriff mit, wen das betrifft: „Restricting rows here means only Architects can change this project's workflows, steps, UDFs, schedules and notify templates. N members can change them today; they will still be able to run them.“

Ausführungen funktionieren genau wie bisher weiter, auch geplante, da sie unter der Dienstidentität des Projekts laufen. Was eine Ausführung erzeugt, folgt dem Entwurf, den ihre Architects ihr gegeben haben: Eine Ausgabetabelle ohne die eingeschränkte Spalte, eine Exportdatei, eine Benachrichtigungs-E-Mail oder eine Protokollzeile wird für diejenigen, die sie lesen, nicht gefiltert.

**Beim Start einer Ausführung angegebene Werte.** Jeder, der einen Workflow ausführen darf, kann ihn mit eigenen Werten für seine Variablen starten – der [App Runner](/de/guides/workflows/use-converted-alteryx-apps/#das-app-runner-frontend) tut dies mit den Antworten seines Formulars, und die API und die KI-Tools können es ebenfalls. Diese Werte gelten nur für diese Ausführung: Sie werden nie im Workflow gespeichert, und keine andere Ausführung, kein Export und kein Leser sieht sie. Da die Ausführung unter der Dienstidentität läuft, können die Werte ändern, was diese Ausführung liest und schreibt; erteilen Sie die Berechtigung zum Ausführen von Workflows daher Personen, denen Sie das anvertrauen.

**Projekte ohne Zeileneinschränkung.** Diese Regeln greifen erst, sobald ein Projekt eine Spalte einschränkt. In einem Projekt, das keine einschränkt, kann jeder, der die Automatisierung des Projekts ändern darf, einen Schritt oder eine benutzerdefinierte Funktion schreiben, die – unter der Dienstidentität des Projekts laufend – den Zugriff des Projekts ändert und ihn selbst zu einem seiner Architects macht. Das ist beabsichtigt: Ein solches Projekt verspricht keine Zeilenisolierung. Beschränken Sie die Bearbeitungsrechte dort auf Personen, denen Sie als Architects vertrauen würden, oder schränken Sie eine Spalte ein.

### Dashboards synchron halten

Der Zeilenzugriff zeigt, wo eine Änderung auf dem Weg zu Ihren Dashboards steht, im Raster und in der Spalte **Synchronisieren** der Registerkarte Sicherheit des Projekts:

| Status | Bedeutung |
|---|---|
| **Wartend** | Eine Änderung ist gespeichert und auf dem Weg zu den Dashboards. Sie verschwindet normalerweise innerhalb von etwa einer Minute. |
| **Wird wiederholt** | Ein Senden ist fehlgeschlagen und wird erneut versucht. Der Grund des Fehlschlags wird neben dem Status angezeigt, mit **Wiederholen**, um sofort erneut zu senden. |
| **Noch nicht angewendet** | Die Einschränkungen des Projekts wurden noch nicht an die Dashboards gesendet. |
| **Angewendet** | Der letzte Versuch, die Einschränkungen an die Dashboards zu senden, war erfolgreich. |
| **Mit Dashboards synchron** | Der Zeilenzugriff hat verglichen, was Dashboards durchsetzen, mit dem, was er schreiben würde, und beides stimmt überein. |
| **Dashboards weichen ab** | Dashboards setzen nicht durch, was der Zeilenzugriff schreiben würde – eine Regel wurde in Superset geändert oder gelöscht, oder die veröffentlichte Ansicht einer Tabelle kann nicht geprüft werden. |
| **Fehler** | Das Senden der Einschränkungen ist fehlgeschlagen. Der Grund wird neben dem Status angezeigt. |

Sobald eine Änderung **Angewendet** erreicht, gleicht das Raster sie mit den Dashboards ab und wechselt zu **Mit Dashboards synchron** oder **Dashboards weichen ab**. **Dashboards weichen ab** und **Fehler** bieten beide **Wiederholen**, wodurch die Einschränkungen des Projekts erneut gesendet werden. Wenn der Status überhaupt nicht gelesen werden kann, meldet das Raster „Couldn't check sync status.“

Ein **Fehler**, der durch eine Tabelle verursacht wird, nennt die Tabelle und sagt, was zu tun ist – zum Beispiel eine Tabelle, die ohne ihre eingeschränkte Spalte veröffentlicht wurde („Republish or unpublish it.“), oder eine Tabelle mit einer eingeschränkten Spalte, die nicht veröffentlicht ist und die Dashboards erst filtern können, wenn sie es ist. Der Status bleibt auf **Fehler** und nennt die unveröffentlichte Tabelle, bis Sie sie veröffentlichen oder stattdessen die Spalte in einer veröffentlichten Tabelle einschränken. Eine solche Tabelle hält den Rest des Projekts nicht auf: Jede andere Tabelle wird auf dem Laufenden gehalten.

Dashboards folgen denselben Gewährungen wie die eigenen Abfragen von PlaidCloud:

- **Jede veröffentlichte Tabelle mit der Spalte wird gefiltert**, nicht nur die Tabelle, die Sie beim Einrichten der Einschränkung angesehen haben.
- **Eine Gruppe, der nur einige Werte gewährt werden, wird gefiltert, auch wenn alle anderen jede Zeile sehen**, in jeder Tabelle, deren Dashboard-Dataset existiert.
- **Projekt-Architects sehen jede Zeile**, in Dashboards ebenso wie im Tabellen-Explorer und im Rest von PlaidCloud. Das gilt für die Architect-Gruppen des Projekts und für die Architects eines mit einzelnen Mitgliedern geteilten Projekts. Das Entziehen des Architect-Zugriffs wirkt in Dashboards sofort, ob Sie die Rolle des Mitglieds ändern, das Mitglied oder seine Gruppe aus dem Projekt entfernen, den Zugriffstyp des Projekts ändern, eine frühere Projektversion wiederherstellen oder die Gruppe löschen.
- **Änderungen der Mitgliedschaft in Sicherheitsgruppen erreichen die Dashboards von selbst.** Das Hinzufügen einer Person zu einer Gruppe oder das Entfernen in PlaidCloud, das Deaktivieren oder Löschen eines Mitglieds, das Löschen einer Gruppe oder das Hinzufügen eines neuen Mitglieds, das Ihren Standard-Sicherheitsgruppen beitritt, aktualisiert innerhalb von etwa einer Minute, was die Person in Dashboards sieht, in jedem Projekt, das dieser Gruppe Werte gewährt, ohne dass jemand den Zeilenzugriff erneut öffnet. Eine außerhalb von PlaidCloud vorgenommene Änderung der Mitgliedschaft – direkt in Keycloak oder dadurch, dass Single Sign-on jemanden bei der Anmeldung in eine Gruppe einordnet – erreicht die Dashboards innerhalb von etwa 15 Minuten, ohne dass etwas gespeichert oder wiederholt werden muss.

### Dimensionsgewährungen

Wenn **Dimension** die Wertequelle ist, aktivieren Sie einen Knoten, um alles darunter zu gewähren. Die Gewährung folgt der Dimension: Ein unter einem aktivierten Knoten hinzugefügtes Mitglied wird dieser Gruppe bei der nächsten Synchronisierung nach dem Speichern der Dimension gewährt, und ein Mitglied, das daraus verschoben oder entfernt wird, wird nicht mehr gewährt – niemand muss das Raster erneut öffnen. Wenn Sie es erneut öffnen, erscheinen die von Ihnen aktivierten Knoten wieder aktiviert.

Ein Mitglied, das Sie einzeln und nicht über einen Knoten aktiviert haben, bleibt gewährt, wenn es aus der Dimension entfernt wird, und das Raster kennzeichnet es als Wert, den die Quelle nicht mehr hat.

Das Deaktivieren eines beliebigen Elements unterhalb eines aktivierten Knotens deaktiviert den Knoten, und die Gruppe behält nur die noch aktivierten Mitglieder. Das erneute Aktivieren dieses Mitglieds aktiviert den Knoten nicht wieder – klicken Sie dafür auf das eigene Kontrollkästchen des Knotens. **Einfügen**, **Alle auswählen** und **Umkehren** aktivieren Mitglieder, nie Knoten.

Ein Dimensionsmitglied, dessen Name nicht als Zeilenzugriffswert verwendet werden kann, wird beim Speichern abgelehnt, mit Nennung des Namens. Taucht ein solches Mitglied später auf, werden seine Zeilen niemandem gewährt, und der Synchronisierungsstatus nennt es: „Dimension ‘…’ member ‘…’ cannot be used as a row access value, so its rows are not granted. Rename it in the dimension.“

### Gewährungen an eine Quelltabelle binden

Statt Werte von Hand zu aktivieren, können Sie eine eingeschränkte Spalte auf eine Quelltabelle verweisen lassen, die
die Antwort bereits enthält – eine Zeile pro Gruppe und dem Wert, den sie sehen darf. Schränken Sie die Spalte zuerst im
Raster ein und fügen Sie dann einen Workflow-Schritt [**Zeilenzugriff festlegen**](/de/reference/workflow-steps/tables/table-set-row-access/)
hinzu, der die Spalte, die Quelltabelle sowie die Gruppen- und Wertespalten der Quelltabelle nennt. Die erste Ausführung des Schritts bindet die Spalte an diese Tabelle: Die von Hand festgelegten Gewährungen der Spalte
werden gelöscht, und ihre Gewährungen werden aus den Zeilen der Tabelle gesetzt.

Nach dem Binden ist die Spalte **quellverwaltet**: Das Raster für den Zeilenzugriff zeigt sie gesperrt, mit einem Kennzeichen,
das die Quelltabelle nennt, und das manuelle Bearbeiten ihrer Gewährungen wird abgelehnt, bis Sie auf **Bindung entfernen** klicken.

Jede spätere Ausführung des Schritts liest die Quelltabelle erneut und wendet die Gewährungen erneut an – planen Sie ihn
nach dem Workflow, der diese Tabelle lädt oder aktualisiert, und eine in den Quelldaten hinzugefügte, entfernte oder neu zugeordnete Gruppe
erreicht den Zeilenzugriff bei der nächsten Ausführung, ohne dass jemand das Raster von Hand bearbeitet.

Da die Quelltabelle entscheidet, wer was sieht, können nur ein Projekt-Architect, ein Tenant-Administrator oder die
eigenen Workflows des Projekts ihre Zeilen ändern oder sie löschen. Allen anderen wird mitgeteilt: „This table
supplies the row access grants for ‘region’, so only a project Architect can change its rows or
delete it.“

### Einschränkungsvorlagen

Wenn Sie eine Einschränkungsform aufgebaut haben, die Sie wiederverwenden möchten – dieselbe Wertequelle, derselbe Werttyp und dieselbe
Einstellung für leere Werte –, speichern Sie sie einmal und wenden Sie sie überall an, wo sie gebraucht wird, statt sie
Spalte für Spalte neu aufzubauen.

- **Als Vorlage speichern…** speichert in einem geöffneten Zeilenzugriff-Bildschirm die Form der aktuellen Spalte als
  benannte Vorlage auf Tenant-Ebene. Es wird nur die Form gespeichert – es werden keine Gewährungen mitgenommen.
- **Vorlage anwenden** startet bei der Spalte eines anderen Projekts diese Spalte mit der Form der Vorlage,
  wobei die Gewährungen jeder Gruppe leer sind und von Ihnen ausgefüllt werden.

Jeder Projekt-Architect kann Vorlagen speichern und anwenden. Das Umbenennen (**Umbenennen…**) und Löschen
(**Löschen**) einer Vorlage erfordert einen Tenant-Administrator, da eine Vorlage im gesamten Tenant geteilt wird.
Das Löschen einer Vorlage lässt die Spalten, auf die sie angewendet wurde, so eingeschränkt, wie sie sind.

<Aside type="note">
Vorlagen sind Kopien, keine Verknüpfungen. Das nachträgliche Bearbeiten einer Vorlage ändert keine Spalte, die sie
bereits angewendet hat – wenden Sie die Vorlage erneut an, um eine Spalte auf den Stand einer späteren
Überarbeitung zu bringen.
</Aside>

### Gewährungen aus SSO-Gruppenattributen

Eine Spalte kann ihre Gewährungen auch von Ihrem Identitätsanbieter statt von PlaidCloud beziehen. Ein
Projekt-Architect nimmt eine Spalte im Zeilenzugriff auf, indem er **Accept row-access grants from
SSO group attributes** aktiviert.

Sobald dies aktiviert ist, legt das Keycloak-Attribut `row_access.<column>` einer Sicherheitsgruppe die Werte fest, die diese
Gruppe über diese Spalte sehen kann – setzen Sie das Attribut in Keycloak für die Gruppe, und PlaidCloud
übernimmt es automatisch für jede Gruppe, die bereits Zugriff auf das Projekt hat. Im Zeilenzugriff selbst ist nichts
weiter zu konfigurieren, und die Gewährungen bleiben sowohl in den eigenen Abfragen von PlaidCloud als auch in Superset-Dashboards synchron.

<Aside type="caution">
Dies gewährt nur Werte an eine Gruppe, die das Projekt bereits erreichen kann. Das Hinzufügen von `row_access.region`
zu einer Gruppe ohne Projektzugriff gewährt ihr nichts, bis der Gruppe auch Zugriff auf das
Projekt erteilt wird.
</Aside>

### Vorschau vor dem Speichern

Der Zeilenzugriff zeigt Ihnen, was eine Änderung bedeutet, bevor Sie sie übernehmen:

- Eine Fußzeile **Vorschau als** zeigt, wie viele der Zeilen der Tabelle eine Gruppe von der Gesamtzahl sehen würde, mit einer Stichprobe der Zeilen selbst – wählen Sie eine beliebige Gruppe im Raster aus, um sie in der Vorschau zu sehen. Die Vorschau wird nach dem Speichern aktualisiert.
- Vor dem Speichern warnt Sie der Zeilenzugriff vor allem, was einen zweiten Blick wert ist: eine Gruppe ohne aktivierte Werte, und ob das bedeutet, dass sie gemäß Ihrer Einstellung **Everyone else** alle Zeilen oder keine sieht; Mitglieder mit Projektzugriff, die von keiner Gewährung einer Gruppe abgedeckt sind; oder Zeilen, deren Wert in dieser Spalte leer (`NULL`) ist und die keiner Gruppe gewährt werden.

### Was ein eingeschränktes Mitglied sieht

Überall dort, wo ein eingeschränktes Mitglied eine Tabelle über ihren Namen liest, erhält es nur seine Zeilen – im Raster, in den Spaltenfacetten und den Downloads des Tabellen-Explorers, im Dialog zum Herunterladen von Tabellen, in Apps und Tools, die als Betrachter lesen, und in Dashboards. Der Tabellen-Explorer zeigt in seiner Symbolleiste **Zeilen durch Ihren Zugriff eingeschränkt** an, wenn das Raster, das Sie ansehen, durch Ihre Gewährungen gefiltert wurde, und das Starten eines Downloads, der gefiltert wird, meldet „Rows limited by your access.“ Ein Architect, der jede Zeile liest, sieht keine der beiden Hinweise.

### Zeilenzugriff und selbst geschriebene Abfragen

Wenn der Zeilenzugriff Ihre Zeilen einschränkt, können Sie Ihre eigenen SQL-Abfragen auf den Abfragebildschirmen des Projekts ausführen und erhalten genau die Zeilen, die Ihre Gewährungen zulassen. Sie können die Ergebnisse als CSV, Excel oder JSON exportieren, und der Export enthält nur diese Zeilen, mit dem Hinweis **Zeilen durch Ihren Zugriff eingeschränkt**. Ein Projekt-Architect liest jede Zeile, da ein Architect sich bereits jeden Wert jeder eingeschränkten Spalte selbst gewähren kann, und sieht keinen Hinweis.

Ein Gewährungswert, der ein Prozentzeichen (`%`) enthält, liefert seine gewährten Zeilen auf den Abfragebildschirmen zurück, und das Herunterladen einer solchen Abfrage als CSV funktioniert.

Für ein Mitglied, das kein Projekt-Architect ist, werden weiterhin abgelehnt:

- Das Ausführen eigener Freiform-SQL in einem Snowflake- oder Databricks-Projekt-Warehouse.
- Das Exportieren der Ergebnisse eigener SQL aus einem Warehouse der Postgres-Familie.
- Das Exportieren der Ergebnisse eigener SQL in eine andere Datenbank.
- Das Eingeben einer Zeilenbedingung in die Vorschau „Test row 1“ eines Fan-out-Schritts.
- Das Lesen einer geregelten Tabelle zu einem früheren Snapshot (Time Travel).

Wem etwas verweigert wird, dem wird mitgeteilt, um welches Projekt es sich handelte, und er wird auf die Leser nach Namen hingewiesen: Das Lesen einer Tabelle nach Namen ist der übliche Weg, auf dem Apps und Tools Daten lesen, und es wendet die Gewährungen an und liefert die Zeilen, auf die der Betrachter Anspruch hat. Eine Spaltenfacette, die als einfache Abfrage einer einzelnen Tabelle geschrieben ist, wird ebenfalls nach Namen gelesen und liefert daher die eigenen Werte des Mitglieds, statt abgelehnt zu werden. Ein Projekt-Architect kann jede davon wie geschrieben ausführen.

Der Zeilenzugriff filtert eine Ansicht nach der geregelten Spalte, daher muss eine Ansicht diese Spalte unter ihrem ursprünglichen Namen beibehalten. Eine Ansicht, die die geregelte Spalte weglässt oder umbenennt, wird nicht gefiltert.

Das Importieren einer Tabellenkalkulation ist für sich genommen keine selbst geschriebene Abfrage – ein gewöhnlicher Dateiimport liest überhaupt keine eingeschränkten Daten, sondern erstellt nur die eigene neue Tabelle des Projekts aus der hochgeladenen Datei und ist daher vom Zeilenzugriff nicht betroffen. Die Ausnahme ist ein Import, dessen Datenprojektion vom Aufrufer geliefert wird: ein Ausdruck pro Spalte oder eine dynamische Excel-Zuordnung. Auf dem interaktiven Importbildschirm werden diese genauso abgelehnt wie die oben genannten Freiform-SQL-Oberflächen und erfordern einen Projekt-Architect, da eine vom Aufrufer gelieferte Projektion eine andere Tabelle lesen könnte. Ein aus einem Workflow ausgeführter Import ist in beiden Fällen nicht betroffen, da er unter der eigenen Dienstidentität des Projekts läuft.

<Aside type="caution">
Das Einschränken Ihrer ersten Spalte in einem Projekt ändert dies für alle, die es verwenden. Wenn eine Panel-App, ein Notebook oder eine Integration in diesem Projekt eigene SQL auf einem Snowflake- oder Databricks-Warehouse zusammenstellt oder eigene Abfrageergebnisse aus einem Warehouse der Postgres-Familie exportiert, stellen Sie sie vor dem Einschränken auf das Lesen der Tabelle nach Namen um – andernfalls funktioniert sie für alle, die keine Architects sind, nicht mehr.
</Aside>

### Zeilenzugriff und Dateneditor

Der Dateneditor liest und schreibt eine Tabelle direkt, daher gilt der Zeilenzugriff für ihn auf beiden Seiten.

Das Öffnen einer eingeschränkten Tabelle im Dateneditor zeigt nur die Zeilen, die Ihrer Sicherheitsgruppe gewährt sind – derselbe Filter, der Ihnen in ein Dashboard folgt, und er gilt auch dann, wenn die eingeschränkte Spalte nicht zu den im Raster angezeigten Spalten gehört.

Das Speichern Ihrer Änderungen erfordert **Architect** im Projekt. Ein Speichern ersetzt die Zeilen der Tabelle pauschal, statt sie zu lesen, und wird nicht Zeile für Zeile gefiltert; daher gilt das Bearbeiten von Daten in einer eingeschränkten Tabelle als Authoring-Aktion statt als Lesevorgang: Allen ohne Architect wird mitgeteilt, dass sie ihn benötigen. Eine Tabelle ohne eingeschränkte Spalte wird wie bisher bearbeitet, ebenso jedes Projekt, das keine Zeilen einschränkt.

### Daten in eine eingeschränkte Tabelle laden

Wenn der Zeilenzugriff die Zeilen einschränkt, die Sie sehen, wirkt das Schreiben eines DataFrames in eine eingeschränkte Tabelle oder deren Leeren mit dem Python-Client (`PlaidConnection`) bzw. das Speichern von Datensätzen darin oder deren Leeren über die REST-API nur auf Ihre eigenen Zeilen. Das Ersetzen der Daten der Tabelle ersetzt nur die Zeilen, die Sie sehen können, das Leeren leert nur diese Zeilen, und das Anhängen fügt Zeilen hinzu; jede andere Zeile bleibt, wie sie ist.

Ein Ladevorgang, der eine Zeile außerhalb Ihres Zugriffs enthält, wird abgelehnt, bevor sich etwas ändert, und der Fehler nennt jeden Wert außerhalb Ihres Zugriffs mit der Anzahl der Zeilen, die ihn tragen. Eine Zeile, die die eingeschränkte Spalte weglässt, wird in dieser Spalte als leer geprüft und daher abgelehnt, es sei denn, Ihr Zugriff umfasst leere Zeilen. Das Ersetzen der Daten auf eine Weise, die den Typ einer Spalte ändern würde, wird ebenfalls abgelehnt; bitten Sie einen Projekt-Architect, diese Änderung vorzunehmen.

Projekt-Architects, Mitglieder, deren Gewährungen jede Zeile abdecken, und Workflow-Ausführungen, die unter der Dienstidentität des Projekts laufen, schreiben die gesamte Tabelle. Eine Tabelle ohne eingeschränkte Spalte ist nicht betroffen.

Alles andere, was eine ganze eingeschränkte Tabelle ersetzt oder entfernt, wird abgelehnt, solange die Tabelle eine Zeile enthält, die Sie nicht sehen können, und nichts wird geändert: das Importieren einer Datei in sie, das Kopieren einer Tabelle aus einem anderen Projekt in sie, das Wechseln oder Zusammenführen ihres Branches, das Wiederherstellen aus einem Archiv oder im Rahmen der Wiederherstellung der gehaltenen Snapshots des Projekts, das Löschen, das Zurückholen nach dem Löschen und jede andere Aktion, die die Tabelle leert, bevor sie sie erneut füllt. Eine Zeile, deren eingeschränkte Spalte leer ist, zählt als Zeile, die Sie nicht sehen können, es sei denn, Ihr Zugriff umfasst leere Zeilen. Eine Tabelle, deren Zeilen Sie alle sehen können, etwa eine, die Sie erstellt haben und die nur Ihre eigenen Zeilen enthält, kann ersetzt oder gelöscht werden.

Jeder dieser Schreibvorgänge, die eine Person in eine beliebige Tabelle vornimmt, wird im Sicherheitsprotokoll aufgezeichnet, auch die abgelehnten. Workflow-Ausführungen werden dort nicht aufgezeichnet.

### Zeilenanzahl und Tabellengrößen

Die Zeilenanzahl und die Speichergröße einer Tabelle beschreiben die gesamte Tabelle, nicht die Zeilen, die Sie sehen dürfen, und würden einem eingeschränkten Leser daher verraten, wie viele Zeilen jenseits seiner Gewährung existieren. In einem Projekt, das Zeilen einschränkt, sieht jeder, dessen Lesevorgänge gefiltert werden, für keine Tabelle des Projekts eine Zeilenanzahl oder Größe – in Tabellenlisten, Suche, Tabellendetails und Snapshots sowie über den KI-Assistenten und KI-Tools, die über MCP verbunden sind. Das umfasst jede Tabelle im Projekt, auch Tabellen ohne eingeschränkte Spalte. Auch die eigenen Gesamtwerte des Projekts werden vor ihnen verborgen – die Gesamtzeilenanzahl und Größe auf der Startseite, in Projektlisten und der Suche sowie in den Projektdetails.

Dasselbe gilt für den Verlauf der Workflow-Ausführungen. Auch die gelesenen und geschriebenen Zeilen, die jede Ausführung und jeder Schritt aufgezeichnet hat, beschreiben die gesamte Tabelle, sodass diese Angaben für dieselben Leser leer bleiben – im Ausführungsverlauf eines Workflows und eines Schritts sowie über den KI-Assistenten und KI-Tools, die über MCP verbunden sind. Für sie prüft [Weave](/de/guides/ai-assistant/weave-findings/) Schritte nicht auf Zeilen oder leere Werte, die von früheren Ausführungen abweichen, da ein Befund selbst verraten würde, dass sich die Anzahl der gesamten Tabelle verändert hat.

Projekt-Architects sehen die Angaben wie bisher, ebenso alle in einem Projekt, das keine Zeilen einschränkt.

### Sehen, was ein Mitglied sehen kann

Um zu prüfen, was eine bestimmte Person sehen kann, statt was einer Gruppe gewährt wird: Öffnen Sie **Identität → Mitglied**, wählen Sie das Mitglied aus und öffnen Sie dessen Registerkarte **Zeilenzugriff**. Ihre Spalte **Effektiver Zugriff** listet für jedes eingeschränkte Projekt und jede eingeschränkte Spalte die Werte auf, die dieses Mitglied über alle seine Gruppen zusammen sieht – einschließlich Gewährungen aus SSO-Gruppenattributen und leerer (`NULL`) Zeilen, wenn die Gewährung einer Gruppe sie einschließt. Ein Projekt-Architect wird als **Sieht jede Zeile (Architect)** angezeigt, da ein Architect jede Zeile liest. Es ist dieselbe Antwort, die die eigenen Abfragen von PlaidCloud anwenden; daher ist sie nützlich für den Support und um zu bestätigen, dass eine Änderung das bewirkt hat, was Sie wollten, bevor jemand ein Problem meldet.

### Verständlichere Fehler

Wo der Zeilenzugriff eine Aktion blockiert – eine selbst geschriebene Abfrage in einem eingeschränkten Projekt, eine Bearbeitung ohne Architect, eine Änderung an Automatisierung, einer Dimension oder einer Quelltabelle für Gewährungen und die anderen oben beschriebenen Fälle –, nennt die Meldung, was eingeschränkt ist und was als Nächstes zu tun ist, etwa die Architects, die zu fragen sind, statt eines generischen Fehlers.

### Zeilenzugriff wird geprüft

Das Einschränken oder Aufheben der Einschränkung einer Spalte und das Bearbeiten der Gewährungen einer Gruppe schreiben jeweils einen Eintrag in das [Projektprotokoll](/de/get-started/tutorials/collaborate-versions-and-sharing/#das-projektprotokoll-lesen) dieses Projekts – wer die Änderung wann vorgenommen hat. Öffnen Sie **Analyze → Projects → Log** im Projekt, um ihn zu sehen. Für diese Nachverfolgung muss nichts am Zeilenzugriff aktiviert werden; sie wird auf dieselbe Weise aufgezeichnet wie jede andere nachverfolgte Änderung an einem Projekt.

## Standard-Sicherheitsgruppen festlegen


Um den Aufwand beim Hinzufügen neuer Mitglieder zu verringern, legen Sie eine Reihe von Standard-Sicherheitsgruppen fest. Das bietet neuen Mitgliedern eine Grundausstattung an Sicherheitsgruppen, ohne dass jede Person manuell zugewiesen werden muss. Die Einstellung ist beim Hinzufügen einer neuen Sicherheitsgruppe verfügbar, wenn Sie das Kontrollkästchen unten im Fenster Sicherheitsgruppe aktivieren, das „Neuen Benutzern standardmäßig zuweisen“ lautet.



## Ein Sicherheitsaudit durchführen


Mit dem Sicherheitsaudit können Sie die Gruppenmitgliedschaft aller Mitglieder und Gruppen einsehen.



**So führen Sie ein Sicherheitsaudit durch:**


1. Öffnen Sie Identität
2. Wählen Sie in der Leiste unter **Sicherheit** den Eintrag **Group audit** aus

Da alle Tabellen in PlaidCloud als CSV-Datei exportiert werden können, lassen sich die Zuordnungen von Gruppenmitgliedern auch außerhalb von PlaidCloud prüfen, sei es für historische Zwecke oder einfach zum Vergnügen beim Offline-Betrachten.



**So exportieren Sie aus dem Formular „Security Group Audit“:**


1. Öffnen Sie Identität
2. Wählen Sie in der Leiste unter **Sicherheit** den Eintrag **Group audit** aus
3. Klicken Sie in der Tabelle auf das kleine Symbol ganz rechts neben „Benutzername“
4. Klicken Sie je nach Wunsch auf „CSV exportieren“ oder „Export XLXS“

## Verfügbare Berechtigungseinstellungen anzeigen


Jede im Workspace verwendete Anwendung hat spezifische verfügbare Berechtigungen. Die Berechtigungen der Sicherheitsgruppen basieren auf diesen Anwendungsberechtigungen.


Die vollständige Liste der verfügbaren Berechtigungen jeder Anwendung ist im Security Bin einsehbar.



**So rufen Sie den Security Bin auf:**

2. Wählen Sie „Sicherheit“ aus
3. Klicken Sie im Dropdown-Menü auf „Security Bins“
