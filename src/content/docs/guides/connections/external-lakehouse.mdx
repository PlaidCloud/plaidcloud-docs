A project's tables normally live in the built-in PlaidCloud Lakehouse. A workspace administrator can instead connect **your own Snowflake or Databricks warehouse** from inside PlaidCloud, with no help from PlaidCloud staff. Workflows then read and write project tables directly in your warehouse. The data stays in your account, under your governance and billing, while PlaidCloud drives the transformations, workflows, and dashboards over it.

## Connect Your Warehouse

Only a workspace administrator can connect, change, or remove a warehouse.

1. Open your user menu, choose **Manage warehouses**, and then choose **Add warehouse**. You can also choose **Connect** on the **Use your warehouse** row of the Home checklist, or choose **Use this as your warehouse instead** in a Snowflake or Databricks connection dialog.
2. Choose **Snowflake** or **Databricks**.
3. Connect in one of two ways: **Sign in with Snowflake** or **Sign in with Databricks** (the quickest, described in [Sign In With Snowflake or Databricks](#sign-in-with-snowflake-or-databricks)), or run the setup script and paste the credentials it produces (below).

### 1. Run the Setup Script First

<Aside type="caution">Run the setup script before you connect. The connection check fails until you do.</Aside>

The dialog writes a setup script from the names you choose and updates it as you type. Copy it with **Copy script** and run it in your own account. It never changes your existing warehouses.

| | Snowflake | Databricks |
|---|---|---|
| Run as | `ACCOUNTADMIN` | A workspace and metastore admin |
| Creates | A warehouse that suspends after 60 seconds idle, with a monthly credit cap that notifies at 90 percent and suspends at 100 percent; a database; a role; a service user | A service principal; a SQL warehouse that stops when idle; the catalog, unless it already exists |
| Names you can change | Warehouse, Size, Monthly credit cap, Database, Role, Service user | Service principal name, SQL warehouse name, Size, Stop after idle minutes, Catalog |
| Defaults | `PLAIDCLOUD_WH` (`XSMALL`, 100 credits a month), `PLAIDCLOUD`, `PLAIDCLOUD_ROLE`, `PLAIDCLOUD_SVC` | `plaidcloud`, `PlaidCloud` (`2X-Small`, 10 idle minutes), catalog `plaidcloud` |
| Authentication | Key pair (the script shows how to generate one) | OAuth secret for the service principal |

The script also sets up the following.

- **Network access.** The script lists the addresses PlaidCloud connects from: the control plane's, `130.211.116.97/32`, and your workspace's own when it's a different one. The Snowflake script creates a network policy that allows only those addresses for the service user. On Databricks, if your workspace already enforces IP access lists, the script includes the statement that allows them; add them to any network policy or IP access list that protects your account.
- **Policies carry over.** On Snowflake, the role is granted the privileges to apply row access, masking, projection, aggregation, and join policies and tags, so your policies survive when PlaidCloud rewrites a table. On Databricks, grant the service principal `EXECUTE` on any row-filter or column-mask function you use.
- **Run costs.** Snowflake's role receives the `SNOWFLAKE.GOVERNANCE_VIEWER` database role, which lets PlaidCloud read the credits each run was attributed and also covers [Last Read](/guides/projects/managing-tables-and-views/#last-read). Databricks receives read access to query history and warehouse sizes in the `system` catalog.
- **Last read.** On Databricks, the script also grants `USE SCHEMA` on `system.access` and `SELECT` on `system.access.table_lineage`, which the table Last Read information needs. See [Warehouse Cost per Run](#warehouse-cost-per-run).

### 2. Connect

| Field | Engine | What to enter |
|---|---|---|
| Name | Both | What PlaidCloud calls the warehouse. It follows the address, for example `Snowflake — myorg-myaccount`, until you type your own. |
| Account URL | Snowflake | Your account host, for example `myorg-myaccount.snowflakecomputing.com`. |
| Private key | Snowflake | The service user's private key (PEM). A key pair never expires. |
| Workspace URL | Databricks | Your workspace host, for example `adb-1234567890123456.7.azuredatabricks.net`. |
| SQL warehouse HTTP path | Databricks | For example `/sql/1.0/warehouses/abc123def456`. |
| Application ID | Databricks | The service principal's application (client) ID. |
| OAuth secret | Databricks | The service principal's OAuth secret. PlaidCloud renews it for you. |

Under **Advanced**, you can use a Snowflake programmatic access token or a Databricks personal access token instead. Tokens expire: PlaidCloud stops reaching your warehouse on that date until you add a new one. Fourteen days before, and after, a banner tells you the date and offers **Rotate**, which opens [Manage Warehouses](#manage-warehouses) on that warehouse and asks for the new token. A key pair or an OAuth secret avoids the expiry.

The address must be your account's public URL, ending in `.snowflakecomputing.com`, `.cloud.databricks.com`, `.azuredatabricks.net`, or `.gcp.databricks.com`. Private and custom endpoints aren't supported here; to reach your warehouse privately, [request a direct connection](#direct-connections) after you attach it.

### 3. Check, Then Use It

- **Test connection** tests the address, the sign-in, and every privilege PlaidCloud needs, and stores nothing.
- **Use as my warehouse** runs the same check and attaches the warehouse. Opened from anywhere other than **Add warehouse**, it also makes the warehouse the default and waits while the workspace switches to it. This usually takes a few minutes and you can close the window. New projects in the workspace then use your warehouse, and the window offers **Run a sample** (see [Run a Sample](#run-a-sample)). Opened from **Add warehouse**, it leaves the default unchanged; choose **Make default** in [Manage Warehouses](#manage-warehouses) when new projects should use it.

A check that fails explains the problem and the fix in plain language. Missing required privileges are listed as ready-to-run `GRANT` statements, each with a **Copy** button and a **Done** box to tick once you've run it, plus a **Copy all** button and **Show the setup script**. **Copy for support** copies the warehouse's own error text for PlaidCloud support.

The check also lists, separately, grants under **Recommended — enables Last read**, each with **Copy**. They let the table [Last Read](/guides/projects/managing-tables-and-views/#last-read) information read your warehouse's history. They never stop you from using the warehouse: without them it connects fine and Last read shows **Read history incomplete**.

- **Snowflake:** `GRANT DATABASE ROLE SNOWFLAKE.GOVERNANCE_VIEWER TO ROLE <role>;` (`IMPORTED PRIVILEGES` on the `SNOWFLAKE` database also works). Last read needs Access History, which Snowflake Standard edition doesn't have.
- **Databricks:** `USE CATALOG` on `system`, `USE SCHEMA` on `system.access`, and `SELECT` on `system.access.table_lineage` for the service principal.

| What you see | Fix |
|---|---|
| The service user can't use an object | Grant its role the privilege on that object. The setup script has every grant. |
| Your warehouse is suspended or doesn't exist | Check the warehouse name and that it can start on its own (`AUTO_RESUME` on Snowflake, a running SQL warehouse on Databricks). |
| Your warehouse has used up its credit quota | Raise the resource monitor's quota or the budget, or wait for it to reset. |
| A network policy is blocking PlaidCloud | Allow the addresses the setup script lists in the policy, as the script does. |
| The token or key has expired or is no longer valid | Create a new token, or switch to a key pair. |
| Unity Catalog denied the service principal access | Grant `USE CATALOG`, `CREATE SCHEMA`, and `USE SCHEMA` on the catalog. |
| PlaidCloud couldn't sign in | Check the user or service principal and its key, token, or secret. |
| PlaidCloud couldn't reach your warehouse | Check the URL, and allow PlaidCloud's address in any network policy or IP access list. |
| Private or custom endpoints aren't supported | Use your account's public URL. |

## Sign In With Snowflake or Databricks

Instead of pasting a key, secret, or token, an administrator can attach the warehouse by signing in. Each person then signs in with their own Snowflake or Databricks identity, so dashboards and queries run with their own permissions in your warehouse.

### What an Administrator Sets Up First

Once, in your own account, an account administrator registers PlaidCloud as a sign-in application. The connection dialog (**Use your own warehouse**, or **Add a warehouse** when opened from **Manage warehouses**) shows the exact text to use, including PlaidCloud's redirect URL.

- **Snowflake.** Run the `CREATE SECURITY INTEGRATION` statement shown in the dialog, then copy `OAUTH_CLIENT_ID` from the result of the `SELECT SYSTEM$SHOW_OAUTH_CLIENT_SECRETS` statement.
- **Databricks.** In the account console, under **Settings > App connections**, add an app named `PlaidCloud`. Give it the redirect URL shown in the dialog and access to all APIs, leave **Generate a client secret** off, and copy its client ID.

### Attach the Warehouse

1. In **Quickest: sign in with Snowflake** (or Databricks), enter the **Account URL** (or **Workspace URL**) and the **Client ID**.
2. On Snowflake, enter the **Database** and the **Data role for PlaidCloud**. **Warehouse** is optional and defaults to yours. On Databricks, enter the **SQL warehouse HTTP path**. **Catalog** is optional and defaults to yours.
3. Choose **Sign in with Snowflake** or **Sign in with Databricks**, sign in to your vendor account, and approve.

Back in PlaidCloud, the warehouse is checked once more. When the check passes, **Your warehouses** opens with the new warehouse selected. When it finds something missing, the window stays open and lists what to fix, with the missing grants to copy.

PlaidCloud creates its own service identity in your account, dedicated to this warehouse. Workflows, schedules, and anything else with no person behind them run as that identity.

- **Snowflake.** PlaidCloud creates a new service user with a key pair that holds only the data role you name. The role must be a plain data role. PlaidCloud refuses a role that is the one you signed in with, that is or inherits `ACCOUNTADMIN`, `SECURITYADMIN`, `USERADMIN`, `SYSADMIN`, or `ORGADMIN`, or that holds `CREATE USER`, `CREATE ROLE`, `MANAGE GRANTS`, `CREATE INTEGRATION`, or `CREATE NETWORK POLICY`, or owns a user. The role may hold the `APPLY ROW ACCESS POLICY`, `APPLY MASKING POLICY`, `APPLY PROJECTION POLICY`, `APPLY AGGREGATION POLICY`, `APPLY JOIN POLICY`, and `APPLY TAG` grants from the setup script, which rebuilt tables need to keep their policies. PlaidCloud also refuses to reuse an existing Snowflake user. The role you sign in with must be able to create users and grant the data role.
- **Databricks.** PlaidCloud creates a new service principal with access to the SQL warehouse and the catalog's data privileges only. Sign in as a workspace admin so PlaidCloud can create it.

If you lack a privilege the service identity needs, the warehouse still attaches for signed-in people with a warning naming it, and workflow runs are refused with the same reason until an administrator signs in again.

### Everyone Signs In

Once the workspace has a warehouse reached by sign-in, every member sees **Sign in to your warehouse** in the user menu. Choose it, then **Sign in with Snowflake** or **Sign in with Databricks**. PlaidCloud keeps you signed in. A dashboard opened without a sign-in, or after yours has expired, shows *Sign in with Snowflake to view this dashboard: in PlaidCloud, open your user menu and choose Sign in to your warehouse.* (or *Databricks*). Sign in again from that menu item.

A dashboard on such a warehouse runs with the viewer's own permissions there. A viewer who hasn't signed in is told: *Sign in with Snowflake to view this dashboard: in PlaidCloud, open your user menu and choose Sign in to your warehouse.*

## Databricks Requirements

- **A workspace at a public URL.** See the address rule under [Connect](#2-connect).
- **Unity Catalog** with a catalog PlaidCloud can create schemas in. A catalog with no managed storage refuses `CREATE SCHEMA`, and no grant fixes that. The legacy `hive_metastore` catalog has no volumes, so file imports into a project there fail, and a push to a Databricks connection there runs row by row.
- **A SQL warehouse.** We recommend a **serverless** SQL warehouse. A stopped classic SQL warehouse takes minutes to start, and the first connection check or query after it stops waits for it, while a serverless warehouse is ready much sooner.
- **A workspace and metastore admin** to run the setup script, or an account admin to add the app connection and a workspace admin to sign in.

PlaidCloud identifies itself to Databricks with the User-Agent `PlaidCloud_Lakehouse` for your warehouse and its dashboards, and `PlaidCloud_Connector` for a Databricks connection used by workflows. It never includes a tenant, organization, or user name.

## Databricks Sign-In Methods

PlaidCloud reaches Databricks in one of three ways. Each is chosen when you add the warehouse.

| Method | Use it when | Renewal |
|---|---|---|
| Sign in with Databricks (OAuth U2M) | You want each person's dashboards and queries to run with their own Databricks permissions | PlaidCloud keeps the sign-in refreshed |
| OAuth secret for a service principal (OAuth M2M) | Workflows and dashboards should run as one service principal | PlaidCloud mints a new access token before the old one expires |
| Personal access token | You can't use either OAuth method | The token expires on its date, and you add a new one |

### Sign In With Databricks

PlaidCloud signs in with the OAuth authorization-code flow and PKCE.

1. As an account admin, open **Account console > Settings > App connections** and add an app named `PlaidCloud`. Give it the redirect URL shown in the connection dialog and access to all APIs, and leave **Generate a client secret** off. Access to all APIs is required: PlaidCloud uses the admin's sign-in to create its service principal, and people who sign in later get only the `sql` scope.
2. Copy the app's client ID.
3. In PlaidCloud, open your user menu, choose **Manage warehouses**, then **Add warehouse**, and choose **Databricks**.
4. Under **Quickest: sign in with Databricks**, enter **Workspace URL**, **Client ID**, and **SQL warehouse HTTP path**. **Catalog** is optional.
5. Choose **Sign in with Databricks**, sign in as a Databricks workspace admin, and approve. PlaidCloud creates its own service principal for workflows. See [Attach the Warehouse](#attach-the-warehouse).

### OAuth Secret for a Service Principal

1. In PlaidCloud, open **Manage warehouses**, choose **Add warehouse**, and choose **Databricks**.
2. As a workspace and metastore admin, run the setup script from the dialog (see [Run the Setup Script First](#1-run-the-setup-script-first)). It creates the service principal, the SQL warehouse, and the catalog. Or create a service principal yourself, generate an OAuth secret for it in Databricks, and give it the privileges in [Databricks Minimum Privileges](#databricks-minimum-privileges).
3. Under **2. Connect**, enter **Workspace URL**, **SQL warehouse HTTP path**, **Application ID** (the service principal's application ID), and **OAuth secret**.
4. Choose **Test connection**, then **Use as my warehouse**.

PlaidCloud requests the `all-apis` scope when it mints a token.

### Personal Access Token

1. In Databricks, create a personal access token for a user or service principal that holds the privileges in [Databricks Minimum Privileges](#databricks-minimum-privileges).
2. In PlaidCloud, open **Manage warehouses**, choose **Add warehouse**, and choose **Databricks**.
3. Under **2. Connect**, enter **Workspace URL** and **SQL warehouse HTTP path**.
4. Select **Advanced: use a personal access token instead** and paste the token into **Token**. **Application ID** and **OAuth secret** aren't needed.
5. Choose **Test connection**, then **Use as my warehouse**.

A token expires on its date, and PlaidCloud stops reaching your warehouse until you add a new one. See [Connect](#2-connect) for the renewal banner.

## Databricks Minimum Privileges

Grant these to the service principal, or to the user for a personal access token. **Test connection** checks the privileges to attach the warehouse and lists any that are missing as ready-to-run `GRANT` statements. A missing volume grant shows up only when an import or push runs.

| To | Grant |
|---|---|
| Attach the warehouse | `USE CATALOG`, `CREATE SCHEMA`, and `USE SCHEMA` on the catalog, and `CAN_USE` on the SQL warehouse |
| Query and write tables | `USE SCHEMA`, `SELECT`, `MODIFY`, and `CREATE TABLE` on the project's schema, and `CAN_USE` on the SQL warehouse |
| Import files and documents (the `plaid_import` volume in the project's schema) | `CREATE VOLUME` on the schema, or `READ VOLUME` and `WRITE VOLUME` on a `plaid_import` volume an admin created |
| Push a table from a workflow to a Databricks connection (the `plaid_export` volume in the target schema) | `USE CATALOG` and `USE SCHEMA` on the target, `MODIFY` on the target table (and `CREATE TABLE` on the schema when the step creates it), and `CREATE VOLUME` on the schema, or `READ VOLUME` and `WRITE VOLUME` on a `plaid_export` volume an admin created |

A push stages each batch as a Parquet file in the volume and loads it with `COPY INTO`, with ANSI mode on, so a value that doesn't fit its column fails the step instead of becoming `NULL`. Without the volume grants, the push falls back to row-by-row `INSERT` statements, which are far slower, and the step warns and names the grants to add. On the `hive_metastore` catalog the push always runs row by row, with no warning.

## Databricks Behaviors to Know

- **Importing files and documents needs the service principal.** On a warehouse attached by sign-in with no service principal (a SQL-only attach), an import stops and says a workspace admin needs to sign in with Databricks again to add one.
- **Dashboards re-register once after the upgrade.** Each Databricks dashboard connection is registered again once with the PlaidCloud User-Agent. You don't need to do anything.
- **Removing a warehouse can't revoke a sign-in at Databricks.** Databricks documents no way to revoke the sign-in token PlaidCloud holds for a person. PlaidCloud deletes its copy and, when each is the only one, the service principal's secret and a personal access token, but a sign-in token itself stays valid at Databricks. PlaidCloud doesn't delete the service principal it created; delete it in Databricks. To end sign-ins, remove the `PlaidCloud` app connection under **Account console > Settings > App connections**.

## Manage Warehouses

A workspace administrator opens the user menu and chooses **Manage warehouses**. The **Your warehouses** window lists each warehouse's **Name**, **Engine**, **Status**, **Default**, and **Projects**. While the workspace has no Snowflake or Databricks warehouse, a card above the list says **You're running on PlaidCloud's warehouse — bring your own**.

**Add warehouse** in the toolbar opens the same flow as connecting, titled **Add a warehouse**. Your warehouse is added, and the default for new projects doesn't change.

For anything else, select a warehouse and choose from the ⋯ at the start of its row, its right-click menu, or **Actions**. Each choice appears only where it applies.

| Action | What it does |
|---|---|
| **Details** | Opens [Warehouse Details](#warehouse-details). |
| **Make default** | New projects use this warehouse once the workspace switches to it, which usually takes a few minutes. Projects already created stay on the warehouse they were created on. Only an **Active** warehouse can become the default. |
| **Rename…** | Changes the warehouse's name. |
| **Renew sign-in…** | For a warehouse attached by sign-in: signs you in to Snowflake or Databricks again. |
| **Rotate credential…** | For a key pair, a token, or an OAuth secret: paste the new one. PlaidCloud checks it against your warehouse first and replaces the current one only if the check passes. |
| **Disable…** | Pauses the warehouse. The confirmation says how many projects use it; they pause until it's enabled again and keep their data. The default warehouse can't be disabled. |
| **Enable** | Turns a disabled warehouse back on. |
| **Remove** | Disconnects the warehouse. It works only when the warehouse isn't the default and no project uses it; otherwise it tells you why. |

**Status** says where each warehouse stands.

| Status | Meaning |
|---|---|
| **Provisioning** | PlaidCloud is still setting the warehouse up. |
| **Switching…** | A change is saved and on its way to your workspace. |
| **Active** | Ready to use. |
| **Disabled** | Projects that use it are paused until it's enabled again. |
| **Attention** | Its last check failed, or its personal access token expires within 14 days. [Warehouse Details](#warehouse-details) says why. |

<Aside type="note">A change, such as a new warehouse, a new default, a new name, or disabling one, takes a few minutes to reach your workspace. Each workspace runs isolated from the others and picks up configuration changes on its own, so until the change arrives the warehouse shows **Switching…**, and a new warehouse can't be used by projects yet. The list checks again every few seconds for up to 10 minutes, then shows **Still landing — refresh later.** If the change still hasn't arrived after an hour, contact PlaidCloud support.</Aside>

When you remove a warehouse, PlaidCloud revokes its credential in your account and deletes its copy. On Snowflake that includes every sign-in and the service identity. On Databricks it includes the service principal's secret, but not people's sign-ins (see [Databricks Behaviors to Know](#databricks-behaviors-to-know)). Your data stays in your warehouse. If the credential can't be revoked, PlaidCloud tells you to revoke it in your account yourself.

### Run a Sample

When **Your warehouses** opens on a particular warehouse, as it does after a sign-in attach, and that warehouse is the default and **Active**, it says **Your warehouse is ready. Run a sample to see it work.** **Run a sample** asks **Remove sample data?** first: it permanently deletes the seeded sample project, which ran on the old warehouse, and leaves your own projects and data untouched. It then loads a fresh sample and runs it on your warehouse; follow it in Workflows. A sample project that has your own changes isn't replaced, and nothing runs.

## Warehouse Details

Choose **Details** on a warehouse to open **Warehouse details**.

| Row | What it shows |
|---|---|
| **Status** | The warehouse's status. When it isn't **Active**, **Why** explains it: for example, the problem a failed check found and its fix, or the date a token expires. |
| **Engine** | Snowflake or Databricks. |
| **Host** | The warehouse's address, partly masked. |
| **Account** | Your Snowflake or Databricks account, when PlaidCloud knows it. |
| **Authentication** | **Key pair**, **Personal access token**, **Service principal**, or **Signed in with the vendor**. |
| **Token expires** | For a personal access token: its expiry date, with **Rotate credential…**. |
| **Last check** | When the warehouse was last checked, and whether the check was **OK** or **Failed**. |
| **Projects** | How many projects use it. |
| **Connection** | How your workspace reaches it. See [Direct Connections](#direct-connections). |

**Check now** checks a Snowflake or Databricks warehouse again with the credential PlaidCloud holds, records the result as its **Last check**, and says **Everything PlaidCloud needs is in place.** or what's wrong and how to fix it. When grants are missing, it lists them as statements to run in your warehouse, each with **Copy** and **Done**, as in [Check, Then Use It](#3-check-then-use-it). Run them, then choose **Check now** again.

While a change is landing or a direct connection is being set up, the window keeps itself up to date for up to 10 minutes after you open it or request a connection. After that, refresh **Your warehouses** (F5) and choose **Details** again.

## Direct Connections

The **Connection** row in [Warehouse Details](#warehouse-details) says how your workspace reaches the warehouse. PlaidCloud reads where the warehouse runs from its address: a Snowflake account-locator address, such as `xy12345.us-east-2.aws.snowflakecomputing.com`, names its cloud and region, a Databricks address names only its cloud, and a Snowflake organization-account address names neither.

| Connection | Meaning |
|---|---|
| **Same cloud & region** | The warehouse runs in the same cloud and region as your workspace. |
| **Public internet** | The warehouse runs in another cloud or region. Queries cross the public internet, so response time and egress fees apply. |
| **Private — direct link** | Your workspace reaches the warehouse over a private link, such as AWS PrivateLink, Azure Private Link, or Google Private Service Connect, and its queries don't cross the public internet. |
| **Not detected** | PlaidCloud couldn't tell where the warehouse runs. |

A direct connection replaces the public path between your workspace and the warehouse with a private one. It's for a warehouse in the same cloud and region as your workspace.

### Request a Direct Connection

**Request direct connection** appears in **Warehouse details** when your workspace's plan includes private connectivity, the warehouse is an enabled Snowflake or Databricks warehouse, and no request for it is open. Only a workspace administrator can request one. After you choose it, the **Connection** row follows the request.

| Connection | Meaning |
|---|---|
| **Requested** | PlaidCloud received the request and will start setting it up. |
| **Setting up** | PlaidCloud is setting up the private connection. |
| **Waiting on your warehouse admin** | The connection needs a few steps in your warehouse account before it can finish. |
| **Private — direct link** | The connection is checked and in use. |
| **Needs attention** | The private connection isn't working. Check the steps, or contact PlaidCloud. |

Until the direct connection passes its check, your workspace keeps reaching the warehouse the way it did before. While PlaidCloud checks it, the row says **Checking the connection…**. If PlaidCloud returns the warehouse to the public path, the row shows how the warehouse is reached again and **Request direct connection** is offered again.

### Steps in Your Warehouse Account

While the connection is being set up, or needs attention, **view steps** beside the **Connection** row opens the steps for your warehouse administrator, numbered, with the exact text to run and **Copy** where a step has some. A step that waits on PlaidCloud says so until PlaidCloud fills it in. Let your PlaidCloud contact know once you've run them.

| Engine | What the steps ask for |
|---|---|
| Snowflake | Business Critical edition or higher. A statement, run as `ACCOUNTADMIN`, that authorizes PlaidCloud's private endpoint. A change to the network policy the setup script created, made before PlaidCloud switches over: it adds a network rule for the private endpoint and moves PlaidCloud's public addresses into a rule of their own, because a policy with network rules no longer reads its IP list. The statements are safe to run again. |
| Databricks | A workspace on the tier private connectivity needs (Enterprise on AWS, Premium on Google Cloud, Premium and VNet-injected on Azure). Registering PlaidCloud's endpoint for the workspace in your account console, or, on Azure, approving PlaidCloud's pending private endpoint connection in the workspace's Networking tab. Allowing PlaidCloud privately in your private access settings while keeping public access on for PlaidCloud's addresses. |

<Aside type="note">PlaidCloud's control plane still reaches your warehouse at its public address to sign in, set up, and disconnect. Keep public access on for the addresses from the setup script, as the steps do.</Aside>

## Warehouse Cost per Run

On your own warehouse, a converted Alteryx workflow's run history shows a **Warehouse cost** column, and the [Prove your migration](/guides/workflows/validate-converted-alteryx-workflows/#prove-your-migration) window shows the last run's cost and an estimate for the next run. Costs are in credits on Snowflake and in DBUs on Databricks.

| Label | Meaning |
|---|---|
| *attributed* | Snowflake billed these credits to the run's queries, read through the `GOVERNANCE_VIEWER` grant. Attribution appears after Snowflake's reporting delay. |
| *estimated* | Computed from query run time and the warehouse size, shown with a leading ≈. This is always the case on Databricks, and on Snowflake before attribution arrives or without the grant. |

The cost covers the steps that PlaidCloud's engine ran. A run partly priced is marked *partial*, and a run whose cost hasn't been reported yet says so.

## Your Policies and Descriptions Carry Over

Schema, table, and column descriptions set in PlaidCloud are written as comments in your warehouse's own catalog. Row access, masking, projection, aggregation, and join policies on Snowflake, and row filters and column masks on Databricks, stay attached when PlaidCloud replaces, recreates, or clones a table. If a policy can't be carried over, PlaidCloud leaves the table as it was and the message names the policy and the reason.

## Bind a Project to Your Warehouse

Once your workspace has a warehouse connected, the **New Project** dialog (**Analyze > Projects > New Project**) offers a lakehouse picker: choose **Tenant Default**, or pick a specific warehouse. **Tenant Default** is the built-in PlaidCloud Lakehouse unless a warehouse is the default, in which case new projects land there automatically. Choose **Make default** in [Manage Warehouses](#manage-warehouses), or **Use as my warehouse** in a dialog not opened from **Add warehouse**, to set the default. It affects only projects created afterward; existing projects keep the backend they were created with. From then on:

- Every table the project's workflows create, load, or transform is created and written in your lakehouse.
- Reads — in steps, views, and dashboards — run as queries against your warehouse.
- Nothing is copied into the PlaidCloud Lakehouse; the data stays in your account.

Build workflows exactly as you would on the built-in lakehouse — import, transform, join, and publish steps all work the same way. The backend is set when the project is created and applies to the whole project.

## Importing Files Into a Lakehouse-Bound Project

Importing a CSV, Parquet, XML, or Access file into a lakehouse-bound project loads it through your warehouse's own **native, parallel bulk-load path**: a Snowflake internal stage plus `COPY INTO` for Snowflake, a Databricks managed volume plus `COPY INTO` for Databricks (see [Databricks Minimum Privileges](#databricks-minimum-privileges)) — instead of staging the file through an external cloud bucket. There's no extra cloud IAM to configure, and it works the same way regardless of which cloud your warehouse runs on.

## Exporting Query and Table Results

Exporting query or table results from a lakehouse-bound project delivers straight to cloud storage rather than routing every row back through PlaidCloud:

- **Snowflake** — the export runs as a Snowflake server-side unload (`COPY INTO` a stage), so the warehouse writes the results directly to storage. Large exports are automatically split into multiple files (previously an export above Snowflake's single-file limit would fail).
- **Databricks** — the export runs as a Databricks server-side unload (`INSERT OVERWRITE DIRECTORY` into a Unity Catalog managed volume), so the warehouse writes and encodes the results itself and PlaidCloud only relays the finished files to storage. Large exports roll across multiple files automatically, and CSV can be delivered gzip-compressed.

## Dashboards Over Lakehouse Data

Dashboards work over both engines.

- **Databricks** — dashboards connect through the Databricks driver, with the service principal's OAuth credentials (or a personal access token). On a warehouse attached by [sign-in](#sign-in-with-snowflake-or-databricks), each viewer's dashboard runs with their own Databricks identity.
- **Snowflake** — dashboards connect with the warehouse's service user and key pair. On a warehouse attached by [sign-in](#sign-in-with-snowflake-or-databricks), each viewer's dashboard runs with their own Snowflake identity instead. A project's dashboard is set up when the project is created or published.

## Have PlaidCloud Register a Warehouse for You

You don't have to connect a warehouse yourself. Give your PlaidCloud contact the details below for whichever engine you're connecting, and an administrator registers it on your behalf.

### Snowflake

| Field | What to provide |
|---|---|
| Hostname | Your Snowflake account host. |
| Superuser | The Snowflake user PlaidCloud authenticates as. |
| Database | The database PlaidCloud creates and manages project schemas in. |
| Warehouse | The compute warehouse PlaidCloud runs queries under. |
| Role | The Snowflake role PlaidCloud acts as. |
| Private key | The **raw, unencrypted** PEM private key for key-pair authentication — paste the key text itself, not a base64-encoded copy. Passphrase-protected keys aren't supported yet. |

Generate a key pair and assign the public key to the Snowflake superuser before handing off the private key. The role must be able to create, read, and write tables in the target database.

### Databricks

| Field | What to provide |
|---|---|
| Hostname | Your Databricks workspace URL. |
| HTTP path | The HTTP path of the SQL warehouse PlaidCloud runs queries against. |
| Unity Catalog | The Unity Catalog catalog PlaidCloud creates and manages project schemas in. |
| Personal access token | A Databricks PAT for authentication. |

The token's identity must be able to create, read, and write tables in that catalog.

Neither registration asks for a schema — each project gets its own, derived automatically from its DSN when the project binds to the lakehouse.

The registration form has a **Test Connection** button that opens a live connection with the details entered and reports success or the reason it failed, without saving anything — so credentials can be verified before the lakehouse is registered. A Snowflake test needs the raw, unencrypted PEM private key (a passphrase-protected key is reported as unsupported); a Databricks test uses the PAT.

A registered warehouse isn't usable the moment it's saved. It shows **Switching…** in **Your warehouses** for a few minutes, for the same reason as a warehouse you add yourself (see [Manage Warehouses](#manage-warehouses)).

<Aside type="note">An Iceberg/Lakekeeper catalog connection is registered separately and is optional — it isn't required to use a Snowflake or Databricks warehouse.</Aside>
