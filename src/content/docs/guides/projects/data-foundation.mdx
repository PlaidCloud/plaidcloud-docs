**Data Foundation** is the finance data foundation for your PlaidCloud projects. Its **Common Finance Model** brings together ERP data from multiple ERP systems, and multiple instances of each, into a single model: one chart of accounts, one set of entities and one reporting currency. Reports, metrics and AI assistants built on the model all read the same numbers, whichever ERP they came from.

Your ERP connects through its PlaidCloud connection, so the general ledger, trial balance, master data and budgets arrive directly from the source, with nothing to export. Files add data a system doesn't hold, such as currency rates, allocation drivers or a budget kept outside the ERP, and can replace the ERP rows they cover. **Load** conforms every source into the model, translates it into the reporting currency and checks that it ties out, all from the **Data Foundation** group of the project's **Home** rail. When you add a second system, you answer one question per subject, such as whether it uses the same account codes as a system already connected, and a management consolidation builds the group profit and loss with the intercompany eliminated. You can add Data Foundation to any project, and solutions, such as **Enterprise Profitability**, build their reports and models on top of it.

## Get Data Foundation

You can start a project with Data Foundation, or add it to a project you already have.

- **A new project.** In Analyze, open **Projects** and click **New Project**. **Start from** lists **Blank**, **Data Foundation**, **Enterprise Profitability**, **Cost to Serve**, **Operational Transfer Pricing** and **From a template file**, with a line under the list saying what the choice gives. **Data Foundation** is the model on its own, with its reports. Each of the three solutions includes Data Foundation and adds its own models. To see a complete example before you connect anything, tick **Start with sample data**. Click **Create**. The project is private to you, and you are its only Architect, until you share it.
- **Your first sign-in.** If you can create projects, the welcome on your first sign-in offers **Connect your finance system**. It creates a Data Foundation project, names it for you and opens it while it builds.
- **A project you already have.** Open the project's **Home**. Under the **Data Foundation** heading of the rail, the **Data Foundation** row says what it is, and an Architect of the project sees **Add data foundation**. The build runs in the background and the page says **Adding Data Foundation. This takes a few minutes.** Your own workflows, tables and other work are left as they are. If the project already has a table where the model keeps one, nothing is installed and the message names the table.

**Home** is the first tab of every project. Once a project has Data Foundation, the **Data Foundation** group of its rail holds these rows, each with a link of its own:

| Row | When it shows |
|---|---|
| **Summary** | Always. A project with Data Foundation and no system yet opens on it. |
| **Systems** | When the project has two or more systems, a system waits for access, or the next step on **Summary** is to add, connect or keep a system up to date. |
| **Questions** | While a question waits for your answer, with how many as a badge. |
| **Reports** | Always. |
| **Allocations** | In a project made with a solution. |

## Connect Your ERP

Your finance system connects to Data Foundation through its PlaidCloud connection. Data Foundation reads the general ledger, trial balance, master data, exchange rates, budgets and, where the system holds them, sub-ledgers, month-end and bank balances directly from it, and only ever reads. Credentials are only ever typed in the standard connection editor. Each system has a page for the administrator who grants the access, listed in [Which Systems Can Feed the Model](/guides/projects/data-foundation-getting-started/#which-systems-can-feed-the-model), and the [Data Foundation Coverage Matrix](/reference/data-foundation-coverage-matrix/) shows which datasets each system supplies directly.

<Steps>

1. On **Summary**, click **Add your finance system**. It opens **Systems**.

2. Under **Add a system**, choose your system in **System**. What comes next depends on how the system signs in:

   - **QuickBooks Online and Xero** sign in by approving access in the system's own window. Click **Connect to** and the system's name. PlaidCloud makes the connection for the project's environment and opens the approval window. Once you approve, the system is added and starts loading. If your browser blocks the window, allow popups for the site and try again.
   - **A system you sign in to with credentials** lists under **Connection** the connections of its kind you can use, with the first one selected, and **New connection**. Pick one and click **Add system**. **New connection** opens the standard connection editor with the project's environment filled in, and the system is added when you save the connection.
   - **SAP S/4HANA, SAP ECC, Oracle E-Business Suite and Sage 100** are reached through a PlaidLink agent on your network. Set the agent up first, then choose its connection as for any system that signs in with credentials.

3. To change what is loaded before you add the system, open **Options**. **Companies** lists the system's companies: tick the ones to load, or none for all of them. A system that doesn't list its companies asks you to enter them. **Months of history** is how many months back to load, from 1 to 120. Some systems also have **System settings**, and a system with a setting it can't do without opens **Options** and asks for it. Without **Options**, every active company and 24 months of history are loaded.

4. A system added with its connection starts loading straight away. If other workflows use the same connection, PlaidCloud first asks **Load from a shared connection?** and names them, because loading reads from the connection and can slow those workflows down. Click **Load anyway** to go ahead.

</Steps>

Don't have access yet? Choose the system and click **Don't have access yet?** instead. The system is added as **Waiting for access**, and one request covering every system that waits is shown, ready to send with **Copy request** or **Email request**. When the access arrives, add the system with its connection under **Add a system**. For QuickBooks Online and Xero, click **Connect** on the system's row.

To bring in another system or another instance, add it the same way. Adding a system always leaves the others as they are, so several systems and instances feed the one consolidated model. When you add a second system, Data Foundation asks one question per subject instead of one per code. See [Map Codes Across Sources](#map-codes-across-sources).

Each load reads only what changed: open periods and the last closed period are read again, and closed periods already loaded are kept. Raising **Months of history** reads just the added months. A changed exchange rate, entity crosswalk or reporting currency reads again the months it affects.

## Systems

Every system and instance the project loads from is a source, and files you confirm are sources too. The **Systems** row of the rail, and with it the page, its buttons and its **Files** card, shows when the project has two or more systems, a system waits for access, or the next step on **Summary** is to add, connect or keep a system up to date. With one system that is loaded and kept up to date, **Summary** shows it under **Your system** instead. The **Systems** page lists every system, with **System**, **Status** and **Last load**. **Status** is one of **Waiting for access**, **Connected**, **Loading**, **Loaded** or **Failed**. **Last load** says when the system last loaded, or **Not loaded yet**, and, once the project refreshes on a schedule, when the next refresh is due, or since when it is overdue. Under a system that failed, its row says why.

Each row has the button that fits where the system stands:

| Button | When it shows |
|---|---|
| **Load** | The system is connected or loaded. It reads that system alone, and then rebuilds the model from every system's data. A failed system offers it beside its fix. |
| **Open connection** | The system failed to load. Open its connection to see why and correct it. |
| **Reconnect** | The sign-in to QuickBooks Online or Xero has expired. |
| **Connect** | QuickBooks Online or Xero is waiting for access. |
| **Request access** | A system that signs in with credentials is waiting for access. It shows the request to send again. |

Beside it, **Test connection** signs in and tries to read each dataset, then lists each as **Readable**, **Missing permission** or **Error**, and names the permissions to ask your system's administrator to add. **Remove** takes a system out of the project after you confirm **Remove this system?**. Everything loaded from it is deleted, and you can connect it again later.

Click **Edit** on a system to change how it is used, then click **Save**:

| Setting | What it does |
|---|---|
| **Name** | The label reports, questions and messages use for the system. |
| **Reporting books, separated by commas** | The accounting books to read, for a system that keeps more than one. **All reporting books** reads every book. |
| **Months this source provides** | For each **Company**, the months from **From (2026-01)** to **To (2026-12)** the system provides. Leave a month empty for no limit. Write months as the year and month, for example `2026-03`. |
| **Extra categories in this source** | For each extra category the system carries, its **Name** and where it is **Shown under**, or **Leave out**. |
| **Companies** and **Months of history** | Which companies the system loads, and how many months back. |

Adding companies, or ticking none, saves straight away. Leaving a company out asks you to confirm **Load fewer companies?** first, because saving clears everything loaded from that system at once, and the next **Load** pulls the ticked companies again.

When two systems provide the same month for the same company, the one listed higher counts until you choose which counts from when. See [Choose Which Source Counts From When](#choose-which-source-counts-from-when).

Changing sources does not read your ERP again. The bar above every page says **You have changed your sources. Press Apply changes to use them.** until you click **Apply changes**, which runs a load from the data already pulled: it conforms the sources again with your new mappings, names and files, and rebuilds the model. Click **Load** when you also want fresh data from your systems.

## Add Files for Data Outside Your ERP

Files supplement your ERP connection with data a system doesn't hold, such as currency rates, allocation drivers, a [Code map](#entity-crosswalk) of entity codes or a budget kept outside the ERP. Each file belongs to one of the datasets listed under [Common Finance Model Tables](#common-finance-model-tables).

<Steps>

1. In the **Files** card under the systems on **Systems**, choose the **Document account** to store the file in.

2. Drop a CSV or Excel file on **Drop a CSV or Excel file here**, or click **Choose a file**. The file is uploaded to the `/foundation/` folder of the document account.

   For a file that is already in the document account, open **More ways to add files** and, under **Add a file already in the document account**, enter its path, for example `/foundation/budget.csv`, and click **Add file**.

   To read a new file every month, use **Add every matching file in a folder**: enter the folder, choose whether the file names **contains**, **starts with**, **ends with**, **is exactly** or **matches (\* stands for anything)** what you enter, and click **Add files**. Files in folders inside it are not read.

3. PlaidCloud reads the file and proposes a mapping:

   - **Detected delimiter, decimal separator and dates.** The delimiter (comma, semicolon, tab or pipe), the decimal separator and the date format are detected for you.
   - **Dataset**: the Common Finance Model table the file belongs to, matched from the file name and column headings. When the match isn't clear, choose it from the list.
   - **Decimal separator**: **Period (1,234.56)** or **Comma (1.234,56)**.
   - **Date format**: shown when the file has dates. Change it if the detected format is wrong: `YYYY-MM-DD`, `DD.MM.YYYY`, `DD/MM/YYYY` or `MM/DD/YYYY`.
   - A grid of **Column in file**, **Type**, **Examples** and **Goes to**. Change **Goes to** to send a column to a different field, or to **Don't load**.

4. Answer the questions the file raises, such as **Which company is this file for?**, **Which currency are the amounts in?**, **Are these amounts year-to-date or for the month?**, **Are the amounts shown in thousands or millions?**, **Are revenues shown as negative numbers?** or, for a contracts file, **Is each row a contract term?** (see [Contract Registers](#contract-registers)). Each one is asked only when the file doesn't already say, except **Is each row a contract term?**, which every file proposed as contracts asks.

5. Check where each column goes, then click **Confirm mapping**. While it works, the note under the button says why it is waiting. In a project that still has the sample data, the first file you confirm also removes the sample, which can take a few minutes.

</Steps>

These options appear on a file when they apply:

| Option | Use it to |
|---|---|
| **Which source do these rows apply to?** | Limit a code map file to one source. **Every source** applies it to all of them. |
| **Where does this file come from?** | Say whether the file holds **This project's own codes** or comes from **Another system**, which you name, for example `SAP Germany export`. A file from another system is checked for shared codes like an ERP source. |
| **Split … into … parts at each …** (under **Advanced**) | Split one column that holds several values, such as `100-200-300`, and send each part to its own field. |
| **Which currency do you report in?** | Set the reporting currency when the project hasn't one yet. Write it as three letters, for example `USD`. |
| **These are consolidated results or your reported P&L (OneStream, Anaplan, SAP Group Reporting, FCCS)** | Load the results of your consolidation system so the group profit and loss can be [reconciled](#reconcile-to-your-consolidation-system). |

To take a file out of the project, click **Remove** next to it under **Files**, or **Remove this file** on its mapping, and confirm. Its figures leave your reports the next time you click **Apply changes**.

When PlaidCloud can't decide the dataset, the decimal separator or the date order on its own, for example a file whose dates could read as day/month or month/day, it asks you to choose before you confirm. Adding a second file for the same dataset replaces the first. If a later file's columns don't match the dataset, the load names the file and the columns and tells you to correct the file or its column names, or set the step's **Schema Mismatch** to `union`.

Accepted files are CSV, TSV and TXT text files, Excel `.xlsx` files (read from the first sheet) and Parquet files.

<Aside type="note">
A file that is missing or empty never stops a load. Adding it says there is nothing to map yet, and a load finishes with a warning that names the path. The dataset keeps the rows the file last gave it, if any. Add the file again once it exists.
</Aside>

### Contract Registers

A contracts file can be a register of contract terms or the contracts at one month end, so confirming one asks **Is each row a contract term?**. The answer proposed is **Yes, each row is a contract term** when the file has a start date and no month-end column. A file you confirmed before keeps its answer when it is added again.

- **Yes, each row is a contract term**: each row is one term of a contract, with its start date, its end date and its annual value. Every load copies each row to every month end it runs over, from its start date to its end date, or on while the end date is blank, up to the month of the load, or the last month of the entity's calendar if that is earlier. A signed contract that starts later counts from its start. Every copy is `Active` except the copy at the month of the load, which keeps the row's own status. A row with no line number is numbered within its contract.
- **No, the file is the contracts at one month end**: the file is one month end's copy of the contracts, as any other contracts file is.

A row with no start date, a row whose status says it ended but that has no end date, and a row that ends before the last day of its first month are not contract terms, so they are held back. See [Rows Held Back](#rows-held-back). A register's customer and product codes are added to the customers and products, named by the code, unless another source gives the same code a name. Its entity codes are added only when no other source names any entities.

## Load Your Data

A load reads your connected systems and your confirmed files, conforms them into the Common Finance Model, translates them into the reporting currency, runs the readiness checks and rebuilds the models. A system added with its connection starts its first load by itself. Before anything has loaded, **Load** is also the next step on **Summary**. After that, **Load** on a system's row on **Systems** reads that system alone, then conforms, rebuilds and consolidates from every system's data, so adding a system never reads the others again. While it runs, **Summary** says what is loading.

- Only one load runs for a project at a time. A second **Load** or **Apply changes** says a load is already running, and you can't change sources while one runs.
- If other workflows use the same connection, the first load lists them and asks you to confirm, because a load reads from the system and can slow those workflows down. Click **Load anyway** to go ahead.
- After PlaidCloud is upgraded, an Architect's **Load** or **Apply changes** also updates the project's generated workflows, creating any working tables they need. When a newer version of the model is available, the bar above every Data Foundation page says **Update available** and that an Architect's **Load** or **Apply changes** installs it. A Manager's **Load** warns that only an Architect can update them.
- Applying an update keeps your own edits to the generated steps. If you changed a step and the update changed it too, your edit is kept. A step you edited that the update no longer generates is kept but turned off; delete it, or turn it back on if you still need it. A step the update replaces is named, and the earlier one stays in its step versions.
- If an update stopped part way, its steps may run out of order until it finishes. Press **Load** again as an Architect to finish it. If it stops again, contact support.
- A system that fails to load shows **Failed** on **Systems**, with why and its fix. When the last load ended with a warning, **Summary** says **The last Load ended with a warning:** followed by the warning.
- If one entity and period fails to read, the rest still load. Run **Load** again to fetch only what failed.
- If one dataset of a source fails to read, the rest of the source still loads, that dataset keeps the rows it had, and the system shows **Failed** on **Systems** until a load reads it.

### Rows Held Back

When sources overlap, a load counts each figure once. Rows it doesn't count are either kept or held back.

Kept rows stay in the project, marked as not counted, so nothing a system holds is lost and nothing is counted twice. A row is kept when it is:

- in another accounting book, such as a local or tax book, that the source isn't set to read;
- outside the **From** and **To** months set for its company;
- for a company and month another source counts, for example the system an entity moved from;
- replaced by a file for that entity and month.

Held-back rows are recorded with their source, entity and the reason, and the load finishes with a warning that names the counts, for example `120 rows of NetSuite EU carrying a code another source also uses`. The reasons are:

| Reason | Meaning |
|---|---|
| Also in an earlier file of the source | An earlier file of the same source already covers the month. |
| A later opening balance | The entity's earliest opening balance and the activity since it already count. |
| Carrying a code another source also uses | The code needs your answer. See [Map Codes Across Sources](#map-codes-across-sources). |
| Carrying a code mapped to two codes | The code map gives the code two answers. |
| Carrying a code its own master does not have | The system's own list of accounts, products or customers doesn't have the code. |
| Report totals or blank lines | A file's total or blank rows. |
| With no start date, ended with no end date, or ending before the last day of its first month, so no contract term | A row of a contract register that is no contract term. See [Contract Registers](#contract-registers). |

Statistical accounts move to the allocation drivers instead of the ledger, and show as moved, not as a problem.

### ERP Data and Files Together

A file replaces only what it covers, and the other rows from your ERP stay.

- **Master files** (accounts, departments, customers, products and Segment values) replace the ERP rows with the same code.
- **Transaction files** replace the ERP rows for the same entity and month. General ledger and trial balance files also match by ledger, budget files by scenario, and statistical driver files by scenario and driver.

If a file later stops covering a month, the ERP's data for that month comes back on the next load.

## Entity Crosswalk

Each source names its entities with its own codes. A **Code map** file maps those codes to the entities in your entity master, so lines from every source land on the same entity.

To use one, add a CSV or Excel file and choose the **Code map** dataset:

| Column | Holds |
|---|---|
| `source_code` | The code as the source carries it, such as a company code. A column named `source_entity` is matched to it too. |
| `code` | The entity it belongs to, as the entity master names it. A column named `entity` is matched to it too. |

Each row maps an entity code unless the file has a `dimension` column that says otherwise. See [Map Codes Across Sources](#map-codes-across-sources).

- A code that isn't in the code map is used as it is.
- Several codes can map to one entity. Their lines are combined, and a month counts as closed once it is closed for all of them.
- The file's rows apply to every source unless you choose one in **Which source do these rows apply to?**, so limit the file to one source when two sources use the same code for different entities.
- An **Entities** file row replaces the ERP's entity with the same entity code.

The **Every entity known** check flags any line whose entity is neither in the entity master nor mapped to one by the code map. It is not applicable until an entity master is loaded.

## Map Codes Across Sources

Two systems can use the same code for different things, or different codes for the same thing. When you add a system whose codes overlap a system already connected, Data Foundation asks one question per subject instead of one per code, for example **Does SAP ECC use the same account codes as NetSuite?** It asks this for accounts, departments, profit centers, sites, products, customers and each extra category.

Each question waits on the **Questions** page with Weave's suggested answer and the evidence for it, such as how many of the shared codes have the same name, and says how many rows are held back until you answer. Answer **Same codes as** the other system or **Different codes from** it.

- Until you answer, the rows carrying the shared codes are held back, so each amount is counted once.
- Once you answer that a system uses the same codes, a code that is new to it later is taken as the other system's, with no new question.
- Mappings are kept for each system and dimension, so an answer for one system's departments never changes another system's accounts.
- An answer applies at the next **Load** or **Apply changes**, and **History** on **Summary** records who gave it, when and the value before.

You can also supply the mappings in a file. Add a file with the **Code map** dataset, and choose **Which source do these rows apply to?** to limit it to one source.

## Choose Which Source Counts From When

When an entity moves from one system to another, both systems carry it. **Questions** asks **From which month does** the new system **count for** the entity, and suggests the month after the earlier system's last ledger month. The earlier system keeps the months before.

The **Source coverage** card on **Summary** lists any other months that two sources both provide. Under **Problems**, for two sources that overlap on a company, enter the month in **That month is**, for example `2026-04`, choose the source in **From that month on, which source counts?**, click **Save choice**, then click **Apply changes** in the bar above the page. Until you choose, only the first of the two is counted, and the other source keeps the months before the one you enter. **Needs attention** explains overlaps that are counted as described, such as two sources that give different exchange rates for a company, and says whose rates are used.

## Currency Translation

Each load translates the general ledger, trial balance, sales, inventory, budget and sub-ledger amounts from their local currency into one reporting currency. Reports and models read the translated amounts, so entities in different currencies, from any system, total correctly.

### The Reporting Currency

To choose the reporting currency, set the project variable `reporting_currency` to a currency code such as `USD`. See [Managing Project Variables](/guides/projects/managing-projects/#managing-project-variables). You can instead open **Actions ▾ > Project settings…** on **Summary** and enter the code in **Reporting currency**. The template creates it blank. While it is blank, each load uses the first of these that names exactly one currency:

1. The group currency of the entities.
2. The local currency of the top-level entities, the ones with no parent.
3. The local currency of the files.

If none of them names exactly one currency, set `reporting_currency` yourself.

Amounts already in the reporting currency stay as they are, so a project whose data is all in one currency needs no rates.

Sales, inventory and budget files can carry a currency too. Map a column named `Currency` or `Local Currency` and it is picked up automatically, and the file's local amounts are translated to the reporting currency. A group or reporting amount that is already in the file is kept as it is. The product master's standard cost is already in the group currency and is not translated.

### Exchange Rates

A rate converts one unit of a currency into the reporting currency for a month: the translated amount is the local amount times the rate.

- **From your ERP**, each load reads the exchange rates the ERP holds.
- **From a file**, add a CSV or Excel file and choose the **Currency rates** dataset. A rate in the file replaces the ERP's rate for the same currencies and month. Use a file to report in a currency your ERPs don't publish rates into, or to add planned rates for budget months.

| Column | Holds |
|---|---|
| `from_currency` | The currency to translate from, for example `EUR`. |
| `to_currency` | The reporting currency, for example `USD`. |
| `period` | The month, as `YYYY-MM`. |
| `average_rate` | The average rate for the month. |
| `closing_rate` | The rate at the end of the month. |
| `historical_rate` | The historical rate, for equity and for accounts set to the historical rate. |

When a currency has no rate into the reporting currency, its rate the other way round, from the reporting currency into it, is turned around, keeping 12 decimal places. Failing that, its rate into another currency is multiplied by that currency's rate into the reporting currency.

### Which Rate Applies

Each row is translated from its own currency, so a line in a different currency from its entity is translated from the currency it is in. The first rule that fits the row applies:

| Row | Rate |
|---|---|
| Statistical and non-posting accounts | Not translated. |
| Already in the reporting currency | Not translated. |
| Account with a rate type | That rate: average, closing or historical. Historical falls back to closing when there is no historical rate. From an ERP, the rate type is the account's own rate type. In a chart of accounts file, map a rate type column to `fx_rate_type` with `average`, `closing` or `historical`. |
| Sales line | The average rate for the period. |
| Inventory balance | The closing rate for the period. |
| Supplier invoice, purchase order, payment, sales order, asset movement, deferred revenue movement, inventory movement or standard cost | The average rate for the period. |
| Open receivable or payable, a sales order's open amount, a contract's value, or a bank balance | The closing rate of the month end it is held at. |
| Budget row | By account, like the general ledger: the average rate for profit and loss accounts and the closing rate for balance sheet accounts. |
| Profit and loss account | The average rate for the period. |
| Equity account | The historical rate, or the closing rate when there is no historical rate. |
| Any other balance sheet account | The closing rate for the period. |

Translated amounts aren't rounded, so totals don't drift.

The pipeline views `cfm_rv_pipeline_month`, `cfm_rv_won_booked` and `cfm_rv_campaign_window` translate the won, lost and created amounts of opportunities at the average rate of the month the deal closed or was created. A month's open pipeline is at that month's closing rate, or at the latest closing rate loaded for the currency while the month's own isn't loaded yet.

<Aside type="note">
A foreign-currency deal's won, lost or created amount is left out when its currency has no average rate for that month, not shown at another rate. The deal is still counted. A foreign-currency win's amount stays out of `cfm_rv_pipeline_month`, `cfm_rv_won_booked` and `cfm_rv_campaign_window` until the average rate for its month is loaded, so the current month's foreign wins are missing from the won amounts until then. Add the rate to a **Currency rates** file or check that the connection can read the ERP's exchange rates, then run **Load** again.
</Aside>

<Aside type="note">
The general ledger and trial balance hold each period's movements, so their balance sheet amounts are each month's movements translated at that month's rate. The consolidated balance sheet translates balances instead, at the closing rate of the month shown, with the difference on a translation difference line under equity. See [Management Consolidation](#management-consolidation).
</Aside>

## Readiness Checks

These checks are the detail under the five assurances on **Summary**; see [Can the Numbers Be Trusted?](/guides/projects/data-foundation-proof/).

Each **Load** and **Apply changes** runs them for every entity and period, and each check counts under one of the five assurances. A check that fails is red. A caution is amber: something to look at that leaves the figures right. On the **CFM-Accounting - Close and assurance** dashboard, the **What needs fixing** tab shows **Every check, by system, month chosen**, with the number of red items each check has for each system, where zero means nothing to fix. The table of items to fix, largest first, for the month chosen, names each red item and says what to do, such as loading the chart of accounts, loading currency rates or running **Load** again. See [Dashboards, Metrics and Analysis Paths](/guides/projects/data-foundation-dashboards/).

The main checks are:

| Check | Under | What it confirms |
|---|---|---|
| **Every month loaded** | **Nothing lost on the way** | Every fiscal period has general ledger lines, and every ERP read succeeded. A closed period with no lines fails; an open period with none is a caution. |
| **Trial balance equals the ledger** | **In balance with each system** | The trial balance equals the general ledger for each entity, period and account. Where both the trial balance and the general ledger carry departments for an account, it also ties out each department. |
| **Sales equal the ledger** | **Nothing lost on the way** | Sales lines equal the general ledger revenue and COGS accounts for each period. |
| **Every product and customer of a sale known** | **Nothing lost on the way** | Every sales line names a product and customer that exist in the product and customer masters. |
| **Every account known** and **Every account typed** | **Nothing lost on the way** | Every general ledger line names an account in the chart of accounts. Lines with an unknown account are left out of the profit and loss. An account with postings but no account type also fails, and a source whose chart types Revenue accounts but no cost of goods sold account is a caution. |
| **Every amount has a rate** | **The group adds up** | Every general ledger, trial balance, sales, inventory and budget row has an amount in the reporting currency. A profit and loss or sales row with no rate fails, because the profit and loss reads translated amounts. A balance sheet, inventory or budget row with no rate is a caution, so load planned rates for budget months. See [Currency Translation](#currency-translation). |
| **Every entity known** | **Nothing lost on the way** | Every general ledger, trial balance and sales line names an entity in the entity master, directly or mapped to one in a **Code map** file. Not applicable until an entity master is loaded. See [Entity Crosswalk](#entity-crosswalk). |

These checks are raised only when they need attention, all under **Nothing lost on the way**:

| Check | What it confirms |
|---|---|
| **Reporting book chosen** | A source that carries several accounting books for an entity has had its reporting book chosen. Until you choose, only the first book counts. |
| **Codes mapped** | Every code used by more than one source has been answered. See [Map Codes Across Sources](#map-codes-across-sources). |
| **One source for each key** | No two sources provide the same months of a company unless you chose which counts. |
| **Hierarchies complete** | Every parent that a dimension names exists, and no member is its own parent or ancestor. A missing parent puts its children at the top of the hierarchy, and a loop stops that hierarchy loading. Totals are unaffected. |
| **Months placed in the fiscal calendar** | Each entity's fiscal periods are calendar months, and every month of rows can be placed in one fiscal period. It is a caution when an entity's periods are not calendar months (4-4-5, 13 periods), or when a month's rows could be in more than one fiscal period or the fiscal calendar lacks the month. |

Two setup checks are raised only when they need attention. One is raised when only one of the project variables `overhead_department` and `overhead_driver` is set, or no allocation driver matches `overhead_driver`, so the overhead allocation would do nothing: set both, or clear both to turn overhead allocation off. The other is raised when budget rows are loaded but none are in the **Budget version** of the project settings (the project variable `budget_version`), so the budget comparison would be empty.

## Management Consolidation

Each load builds a management consolidation: the profit and loss, balance sheet and cash flow of every entity in the group, in the reporting currency, with intercompany eliminated. It is for management reporting. Your consolidation system stays the record for the statutory group; reconcile to it below.

Wherever consolidated figures appear, they carry the label **Management consolidation**: beside the first line of **Summary**, in the context line at the top of each dashboard, and in the **Basis** column of the board pack, whose **Basis note** column reads "Entities combined, intercompany eliminated, translated to the reporting currency. Not a statutory consolidation." A project with one entity shows no label.

<Aside type="note">
The management consolidation is not a statutory or legal consolidation. It doesn't eliminate investments against equity, and has no goodwill or minority interest.
</Aside>

### Choose the Group

On **Summary**, **The group** card shows the reporting currency. Click **Change**, or open **Actions ▾ > Project settings…** on **Summary**, to open **Project settings**, where **Group and row access** lists the **Companies in the group**. A company you untick stays in your reports on its own, but is left out of the group total. Click **Save**. The change applies at the next **Load** or **Apply changes**. A new company is in the group until you untick it.

The group's fiscal year starts in the month set by the project variable `group_fy_start_month`. While it is blank, which it is unless you set it, the group's fiscal year starts in the month the top entity's fiscal year starts in, the one entity with no parent, or in January when the top entity has no fiscal calendar. When more than one entity has no parent, or the top entity is a hierarchy node with no fiscal calendar of its own, it starts in January and the consolidation shows amber until you set the month.

### What You Get

| Table | Holds |
|---|---|
| **Group P&L** | One row per entity, period and line (revenue, cost of goods sold, operating expenses, non-operating, intercompany difference), in the reporting currency. Revenue and costs carry their natural sign. |
| **Group P&L year to date** | The same, year to date, to the group's last fully loaded period. |
| `group_statements` | The profit and loss, balance sheet and cash flow as shown, line by line with every subtotal and total, for each entity, the eliminations and the group, in the reporting currency. Income, assets and cash in are positive. Each line has the month's amount and the group's fiscal year to that month; a balance sheet line has the month's balance. |
| `group_result` | The same three statements by entity, line, account and month, in every reporting book, in the reporting currency and, for an entity in another currency, in its own. Amounts are debit-positive, like the general ledger. |
| **Intercompany pairs** | One row per pair of entities, group and period, with each side's amount and the residual. |
| **Intercompany lines** | The ledger lines behind a group figure or a pair, with the trading partner. |
| **Reconciliation** | The group P&L year to date against your consolidation system. |

Three entity names appear in these tables:

| Entity | Meaning |
|---|---|
| **Eliminations** | The intercompany eliminations. They net to zero, so leave them in for the group figures and filter them out for the sum of the entities before elimination. |
| **Group total** | The consolidation system's total, in the reconciliation. |
| **Unmapped** | Lines with no period, and accounts or entities of your consolidation system that this project doesn't have. |

The metrics **Consolidated income**, **Consolidated result** and **IC difference** read **Group P&L**. They and an analysis path for each of the **Group P&L**, intercompany and reconciliation tables answer questions about the group. The **CFM-Finance - Statements** dashboard and the board pack show the three statements.

#### The Three Statements

- **Profit and loss**: each month at that month's average rate.
- **Balance sheet**: each account's balance is its opening balance plus its activity through the month. Balances are at the closing rate of the month shown, and equity at the historical rate, or at the account's own rate type when it has one. An equity account with no historical rate is at the closing rate. Earlier fiscal years' profit and loss is in retained earnings, and this year's in current-year earnings, each at its own months' average rates.
- The translation difference is a line under equity for each entity, worked out as its equity and earnings at the closing rate less as translated. It is what makes a translated balance sheet balance, never a balancing figure. When an entity in another currency has no closing rate for a month, its balance sheet isn't translated that month and doesn't balance, and the consolidation shows amber naming the entity and month. Load the rate, then run **Apply changes**.
- **Cash flow**: worked out from each balance sheet account's movement in the month, by its account role, at the month's average rate. An effect of exchange rates line holds the part of the change in cash, at closing rates, that comes from the rates moving. A balance sheet account with no role is on the other changes line.
- **Account roles** answered on **Questions** place accounts on their lines. **Commissions** is an operating expense line of its own. **Convertible notes and SAFEs** is a liability line, and its change is under financing in the cash flow; an equity account with that role stays in equity. An expense account named for a commission is suggested **Commissions**, a liability or equity account named for a convertible note, a SAFE or a simple agreement **Convertible notes and SAFEs**, and an account named for a shareholder loan, an owner loan or a loan from someone **Borrowings**, even when its name also says payable. An expense account named for a contractor is suggested **People**.

The balance sheet ends with a check line, assets less liabilities and equity, and the cash flow with the change in cash less the movement in the cash accounts. Both are zero when the statement is right. See [Can the Numbers Be Trusted?](/guides/projects/data-foundation-proof/) for the assurances that prove them.

### Intercompany Eliminations

Intercompany lines are matched by trading partner. The partner on the line is used; when a line has none, its customer's partner is. Both sides of a pair are eliminated, and the amount the two sides don't match by is booked to an intercompany difference line. Each pair gets a reason:

| Reason | Meaning |
|---|---|
| **Matched** | Both sides booked the same amount. |
| **Only one side booked** | One entity booked the transaction and its partner didn't. |
| **Not eliminated** | A line of the pair has no exchange rate, so neither side is eliminated. |

A pair is judged on its year to date. The intercompany check turns amber when a pair's difference is over the project variable `group_amber` (default `1`) and red over `group_red` (default `1000`), which is the **Intercompany tolerance** in **Project settings** (not shown while the group has only one company). Lines with no partner, or with a partner that isn't an entity, are not eliminated and are counted on that check. A source that carries partners beside one that doesn't shows amber.

A source's own elimination entities stay out of the group P&L, and the consolidation check says so.

In the three statements, intercompany receivables and payables are eliminated by pair as well as intercompany income and costs. What a pair's two sides don't match by is on the intercompany difference line of the profit and loss or the balance sheet, so the group balance sheet still balances, and its movement is on the change in intercompany balances line of the cash flow. Each elimination row carries both entities and the country, region and division they share, so a division, a country or a region eliminates only the pairs whose two entities are both inside it, and the group eliminates every pair.

### Reconcile to Your Consolidation System

Add the results your consolidation system reports as a file, and tick **These are consolidated results or your reported P&L (OneStream, Anaplan, SAP Group Reporting, FCCS)** when you confirm its mapping. Answer **Which version of the numbers is this?** with the system's name. The **Reconciliation** table then shows **ours**, **reported** and **diff** for each entity and line, year to date. A difference is usually explained on the **Eliminations**, **Group total** and **Unmapped** rows, or by the exchange rates the system uses. The reconciliation check lists every line over `group_amber`.

### Who Can See It

Group results follow the project's row access. When row access stops the group results, the consolidation check shows amber. A person who sees only some entities sees those entities' sums before elimination, and **Summary** tells them: "These figures cover only the entities you have access to, not the whole company." The **Eliminations** rows and the intercompany tables need access to every entity.

**Restrict rows by entity** in **Group and row access** limits a group granted entities to the rows of those entities, in every table with an entity column. Only an Architect sees it. Ticking or unticking **Restrict** applies at once, and is refused while row access is turned off for the workspace. Unticking it while groups hold entity grants asks **Remove entity grants?** first; click **Turn off** to go ahead.

If the project limits who sees which rows by a column the group tables don't carry, such as department, the group results stay off for everyone and the consolidation check says **Group views are off**. Only an Architect can then tick **Everyone on the project may see the group results** in **Group and row access** and click **Save**; others don't see the box. The change applies at the next **Load** or **Apply changes**.

## Keep It Current

Once a load is done and no question that holds rows back waits, the next step on **Summary** is **Keep this up to date** until **Refresh** in **Project settings** is **Daily**, **Weekly** or **Monthly**. There are two ways to schedule the **Load**:

- **Actions ▾ > Refresh nightly** on **Summary** runs **Load** every night at 02:00 UTC.
- Open **Actions ▾ > Project settings…** on **Summary**. Under **Refresh**, choose **Daily**, **Weekly** or **Monthly**, and set **Refresh time (UTC)**, written as hours and minutes such as `02:00`. For **Weekly**, **Refresh day** is 1 (Monday) to 7 (Sunday); for **Monthly**, it is the day of the month. Click **Save**. **On demand** removes the schedule.

A schedule can be set up once a load with a source has finished with no red checks, so a project that has only sample data can't be scheduled. If you see only some of the project's entities, an Architect sets it up. When a schedule can't be set up, the reason is shown. While **Refresh** is **Daily**, **Weekly** or **Monthly**, the **Systems** page shows when each system's next refresh is due; see [How Fresh Each System Is](/guides/projects/data-foundation-proof/#how-fresh-each-system-is). **Refresh nightly** leaves **Refresh** as it is, so no next refresh shows and **Keep this up to date** stays the next step.

The scheduled load runs as the person who set it up. If that person can no longer use a system's connection, the load is skipped with a warning that names them and the connection; set the schedule up again.

A file that is missing or empty on a scheduled load finishes with a warning that names the path, not an error, and the rest of the model still loads.

## Business Names

**Business names** give the codes in your model the names your business uses. Reports, metrics and Ask show these names, and a name you save applies at once. Later loads keep it. Open **Actions ▾ > Project settings…** on **Summary**; **Business names** is in the **Names** card of **Project settings**.

1. Click **Add a name** and choose the **Kind**: **Category**, **P&L line**, **Metric**, **Column**, **Entity** or **Account**.
2. Enter the **Code**: `segment_1` to `segment_10` for a category, the line's key for a P&L line, the metric's name, `table.column` for a column, or the code of an entity or account.
3. Enter the **Name**, at most 60 characters on one line.
4. Click **Save**. The dialog closes once everything in it is saved; a name that is refused is said under the grid, and the dialog stays open.

Saving replaces the whole list. A row with an empty name removes that name, and **Remove selected** removes the rows you tick. Naming the same code twice is refused. Business names are also written into the analysis path's description so the assistant uses your words, and that description has a length limit: if a name would make it too long, nothing is saved and you are told.

## Revenue Classes and Team Functions

Revenue classes are the kinds of revenue your company sells, such as SaaS or BPO, and a team's function says what the team's cost is for. The [CFM-Executive - Growth and efficiency](/guides/projects/data-foundation-dashboards/#growth-and-efficiency) dashboard reads both.

**Revenue classes** in **Project settings** lists the classes, each with a name and a kind: **Subscription**, **Support and maintenance**, **Managed service**, **Implementation**, **Consulting and professional services** or **Other**. The first three kinds are recurring. A project starts with one class of each kind, named after it. Open **Actions ▾ > Project settings…** on **Summary**. Click **Add** for a new class, rename a class or change its kind, or click **Remove**, then click **Save**.

- Every class needs a name, at most 60 characters, and two classes can't share one. A name can't contain a single quote, a backslash or braces, and "Shared," "Not yet classed" and "Intercompany removed" are kept for the reports.
- Renaming a class or changing its kind keeps every answer given with it. The dashboards show the change after the next **Load** or **Apply changes**.
- Removing a class asks again about each account and product answered with it.

**Questions** asks about the class and the function under **Revenue classes of accounts**, **Revenue classes of products** and **Functions of teams**:

- **Which revenue class is account …?** for each revenue and cost-of-revenue account the ledger posts to that has no class, one question per account, never one for a parent and its accounts together. A cost-of-revenue account can also be **Shared by every class**: its cost is spread over the classes by each class's share of revenue in the 12 months to each month.
- **Which revenue class is product …?** for each product on a contract that has no class. A product's class splits recurring revenue by class; every contract line counts in annual recurring revenue whatever its class.
- **Which function is department … of …?** for each department the ledger posts to, or **Which function is profit center … of …?** for each profit center when its system has no departments, such as a QuickBooks Online Class. The answer is **Cost of revenue**, **Sales and marketing**, **Research and development** or **General and administrative**, and each system's teams are asked about separately.

The suggestion comes from the name: an account or product named for subscriptions, SaaS or maintenance, for example, is suggested a class of that kind; a word after "non-" doesn't count, so "Non-recurring" suggests no recurring class. A revenue account whose name places it in no class is suggested a class of the **Other** kind, or another class that isn't recurring, and a cost-of-revenue account **Shared by every class**. A product gets a suggestion only when its name places it. A team is suggested a function from its name, such as **Sales and marketing** for a sales or marketing team, else **General and administrative**.

These questions hold nothing back: they don't turn the project amber and are never the next step on **Summary**. Until an account is answered, its revenue is "Not yet classed" and doesn't count as recurring; a product not yet answered still counts in annual recurring revenue, as "Not yet classed." The dashboard names what is not yet answered under the figures it affects.

## Explain a Number

**Explain this number** shows what makes up a figure. Once a month has loaded, **Summary** gives net income for the year to the latest complete month, with **Explain this number** beside it. It opens **Explain: Net income**, with the figure for the year to that month at the top, then what makes it up, each list largest first:

| List | What it holds |
|---|---|
| **Lines** | The statement lines that add up to the figure. |
| **Entities** | Each entity's share. In a group, the eliminations are one of them. |
| **Accounts** | Each account's share. |

Each list shows the ten largest, and the rest as one item, such as **Other accounts (12)**, so every list adds up to the figure. A name that is a link opens its own explanation, for that line, entity or account alone. **Largest documents** lists the ten largest ledger documents behind the figure with their **System**, **Entity**, **Document**, **Posted**, **Account**, **Description** and **Amount**, and **Export all documents** downloads every one. **Ask Weave why it moved** asks Weave why the figure changed in the year to that month, and which entities, accounts and documents moved it.

## Allocation Rules

Allocations spread shared costs, such as overhead, to departments, products and customers. The model has two stages: **Stage 1: overhead to departments** and **Stage 2: departments to products and customers**. In a project made with a solution, click **Allocations** in the **Data Foundation** group of the **Home** rail. It opens **Allocation rules**, where you see or change how each is done. Without changes, they work as they did before the wizard existed. A reader can open the rules but not save them.

For each stage the wizard asks four questions:

| Step | Question | Choices |
|---|---|---|
| **Pool** | Which costs do you want to spread? | The kind of account, and for stage 1 the department that holds the cost, or **All departments**. |
| **Driver** | What do you want to spread them by? | **Statistic** you loaded as allocation drivers, such as headcount or square feet, **Net sales amount**, **Sales quantity** or **Spread evenly**. Use the driver of **Same period** or **Same period last year**. |
| **Target** | Where do they land? | Stage 1: departments. Stage 2: products, customers or both. |
| **Method** | What happens when a driver is negative? | **Ignore negative values** or **Stop and tell me**. |

Under the steps, **Preview for** a month, written as year and month such as `2026-09`, shows what the rules, including ones you haven't saved, would do: `Pool 120,000 · Allocated 120,000 · Unallocated 0`. Anything unallocated is cost that had no driver to take it. The preview follows your row access.

A department or statistic name can't contain a single quote (`'`), a backslash or a line break, because the name is written into the allocation steps' filters. **Save** and a preview of stage 1 refuse one that does and name it.

Click **Save**. The rules take effect at the next **Load**, or when you click **Apply changes**. If you edited an allocation step by hand, your edit is kept, not overwritten, and the save names it. You can't save while a load is running.

## Board Pack

A board pack writes your results to a folder in a document account, ready to send. On the **Reports** page, click **Board pack settings** on the **Board pack** card, choose a **Document account** and a **Folder**, such as `/board-packs`, and click **Save**. Every **Load** then makes the pack, so the files in the folder are as current as the last load. Each run writes:

- An Excel workbook, `Board pack.xlsx`, with a **Profit and loss**, a **Balance sheet** and a **Cash flow** sheet: each month and line by entity, with the eliminations and the group total. A project with one entity has no eliminations or group rows.
- A PDF of the **CFM-Finance - Statements** dashboard.

Once that dashboard is built, **Open the board pack** on the same card opens it.

Click **Run now** to make a pack immediately; its files appear in the folder when it finishes. The dialog shows the last run and its outcome, and the next run. **Apply changes** doesn't make a pack. To make one on a schedule, schedule the **Load** (see [Keep It Current](#keep-it-current)); until then the dialog says **Not scheduled yet. A pack that can't be made in full never fails the load:

- If reporting is turned off for your workspace, the pack is the Excel workbook alone, and the run says **Reporting is turned off for this workspace, so the board pack has the Excel workbook only.**
- If a dashboard someone else made already has the address Data Foundation needs for the statements dashboard, that dashboard is left as it is and the PDF is not made. The message names the address; give the other dashboard another address in Superset, then run **Load** again.

## Restore Points

A restore point is made as each **Load** or **Apply changes** starts, whoever starts it, including a scheduled load, and before each change to mappings or sources. It holds the model's tables, the dimensions, and the settings the next load builds from: your sources, files and allocation rules. The last seven points taken for loads and the last five taken before changes are kept, so changes never push out the points taken for loads. Older points roll off.

To go back, open **Actions ▾ > Restore…** on **Summary**. Each point shows when it was made and, beneath it, how many tables restoring it brings back, for example **Puts back 12 tables.**, and in one note what it leaves as it is. Choose a point and click **Restore**. **Restore** is offered once a point exists. Restoring first records the project as it is now as a point of its own, so you can go back again. It then puts the tables, the dimensions and those settings back as they were, and the next load builds from them. Restoring to the sources you already had doesn't mark them as changed. Restoring to a point taken before a connector or file source was added removes that source's landed tables, and a warning names the source. If you undo the restore, Load pulls a connector source's tables again, and for a file source you confirm the file again. If a source's tables can't be removed, a warning says they stay in the source's folder until you delete them by hand, and the rest is still restored. A view, a dimension that can't be saved, or a table with no saved copy is named in a warning, and the rest is restored. A restore point that has rolled off is refused, and you can't restore while a load is running.

## Clone a Project

**Actions ▾ > Clone…** on **Summary** copies the project under a name you give. The copy keeps the template, your edits to the model, and your metrics and analysis paths, and loads the sample data. Its sources are not connected, so connect them in the copy before you load. You can keep working while the copy is made, and **Open project** takes you to it when it's ready.

## Save as My Template

Save a project's setup to reuse it for the next client or entity. Open **Actions ▾ > Save as my template…** on **Summary**, choose the document account, and name the file. A name ending in `.zip` is added if you leave it off. Saving over an existing file is refused, so choose another name.

The file holds the project's structure, your edits to the model, metrics and analysis paths, the business names for entities and accounts, and the rows of the template's configuration tables, such as the activity map of [Cost to Serve](/guides/projects/cost-to-serve/) or the policy ranges of [Operational Transfer Pricing](/guides/projects/operational-transfer-pricing/). It leaves out connections, files, the nightly schedule, runs, restore points, the board pack and who has access.

To use it, create a project, choose **From a template file** under **Start from**, and pick the document account and path. The new project is private to you, with every source waiting to be connected. A release of the template later merges its changes around steps you edited. If there is no file at the path, nothing is created and you are told. Anyone who can read the document account can install from the file. To use it in another workspace, download the file and upload it there.

## Resolve Open Questions With Ask

After a load, a project can still be waiting to be told three things: accounts the chart leaves without a type, codes more than one source uses, and columns in your files that matched nothing. Ask the assistant to resolve them: from an AI assistant over MCP, use the **Resolve Data Foundation residue** prompt. It reads what is waiting and proposes one answer for each item, with a reason.

The assistant writes nothing. Weave AI chat can also say what a project is waiting for (see [Weave AI Chat](/guides/ai-assistant/weave-tab/#data-foundation)), and an MCP-connected agent can read and answer the questions itself (see [Data Foundation With an MCP-Connected AI Agent](/integrations/ai-coding-agents/data-foundation/)). You apply its answers where you would have answered yourself: accounts and codes on the **Questions** page, and file columns in the file's mapping. It never proposes an entity. A question on **Questions** can already carry Weave's own suggestion; see [The Data Foundation Pages](#the-data-foundation-pages).

## Hand the Project Over

When the project is set up for someone else, such as a client, finish with these steps:

- **Keep it current.** Schedule the **Load**. See [Keep It Current](#keep-it-current).
- **Share it.** Give the team access on the project's **Access & sharing** page. See [Managing Project Access](/guides/projects/managing-projects/#managing-project-access).
- **Keep a record.** **Actions ▾ > Download evidence pack** on **Summary** downloads an Excel workbook with **Status**, **Sources**, **Coverage**, **Mappings**, **Consolidation**, **Reconcile** and **Last load** sheets: what loaded and from where, how codes were mapped, that the group ties, and how the last load went. It follows the row access of whoever downloads it, and anyone with a role on the project can download it.
- **Hand it over.** Make the owner an Architect of the project, then remove yourself from its members. Some choices are an Architect's alone, such as letting everyone see the group results or adding Data Foundation to a project.

## Build on the Model With a Template

A template builds its reports and models on the Common Finance Model, so they work the same whichever ERPs feed it. When you start a project from a template, such as **Enterprise Profitability**, it creates:

- The [Common Finance Model tables](#common-finance-model-tables), empty or filled with sample data.
- **Entity**, **Account**, **Department**, **Customer**, **Product**, **Segment 1** and **Segment 2** dimensions built from those tables. See [Hierarchies](#hierarchies).
- The **Load** workflow and the workflows it runs to read your ERP and files, conform them, check readiness and build the template's models.
- The template's own reports and models. **Enterprise Profitability** adds a profit and loss table with revenue, COGS, gross margin, direct and overhead operating expenses, contribution and operating margin, plus margin bridges year over year and against budget.
- Metrics and an analysis path for asking questions about the results.

Under **Start from**, **Data Foundation** is the model on its own, with its reports. Each of three solutions includes Data Foundation and adds its own models, and shows **Allocations** in the rail:

| Solution | Adds |
|---|---|
| **Enterprise Profitability** | The profit and loss and margin bridges. |
| **Cost to Serve** | The cost of serving each customer, and margin after it. See [Cost to Serve](/guides/projects/cost-to-serve/). |
| **Operational Transfer Pricing** | Each entity's profit level against your policy range, and the true-up. See [Operational Transfer Pricing](/guides/projects/operational-transfer-pricing/). |

**From a template file** starts from a project you saved. See [Save as My Template](#save-as-my-template).

To explore before you connect your own ERP, tick **Start with sample data** when you create the project. The project runs a first Load straight away, so **Summary** shows a complete example, including a euro entity translated into US dollars. When you connect your own ERP or add your own files, the sample is removed and your data takes its place. If the removal is interrupted, the next **Load** finishes it. A folder of your own named `sample` is never removed, but while the sample holds that folder the other tables in it are not read, so move them to a folder of another name.

## The Data Foundation Pages

The **Data Foundation** group of the project's **Home** rail is where you connect, load and check your data. Which rows show is in [Get Data Foundation](#get-data-foundation).

| Page | What it shows |
|---|---|
| **Summary** | Where Data Foundation stands, whether the numbers can be trusted, and what to do next. See below. |
| **Systems** | Every system you report from, where it stands and when it last loaded, **Add a system**, and the **Files** card. See [Connect Your ERP](#connect-your-erp), [Systems](#systems) and [Add Files for Data Outside Your ERP](#add-files-for-data-outside-your-erp). |
| **Questions** | Everything waiting for your answer. See below. |
| **Reports** | The dashboards by persona, each opening in a new tab, and the **Board pack** card. See [Dashboards, Metrics and Analysis Paths](/guides/projects/data-foundation-dashboards/) and [Board Pack](#board-pack). |
| **Allocations** | In a project made with a solution, opens **Allocation rules**. See [Allocation Rules](#allocation-rules). |

**Summary** reads from the top:

- Where the project stands in one line, with the one next step as a button, such as **Add your finance system**, **Load**, **Answer 1 question**, **Keep this up to date** or **Open the reports**, and the net income line with **Explain this number**. See [Explain a Number](#explain-a-number).
- In a project with more than one entity, **The group**: how complete the group is, its reporting currency and the month its financial year starts, with **Change** to open **Project settings**.
- **Can the numbers be trusted?**, the five assurances; with a single system, **Your system**; when there is any, **What changed**; and **Close a month**. See [Data Foundation: Can the Numbers Be Trusted?](/guides/projects/data-foundation-proof/).
- **Ask Weave**, questions to start with.
- **History**: each answer, match, close and restatement, with who made it, when and the value before. Click **Show history** to list it, **Show more** for older entries, and **Export** to download it as an Excel workbook.
- **Source coverage**, where you choose which source counts when two provide the same months. See [Choose Which Source Counts From When](#choose-which-source-counts-from-when).

If row access shows you only some entities, **Summary** says **These figures cover only the entities you have access to, not the whole company.**

**Actions ▾** at the top of **Summary** holds **Project settings…**, **Hierarchies…**, **Refresh nightly**, **Download evidence pack**, **Clone…**, **Restore…** and **Save as my template…**. See [Hierarchies](#hierarchies), [Keep It Current](#keep-it-current), [Hand the Project Over](#hand-the-project-over), [Clone a Project](#clone-a-project), [Restore Points](#restore-points) and [Save as My Template](#save-as-my-template). The **Project settings** dialog also opens from **Change** on **The group** card while the group has more than one company. Only someone who can change the project can use the ones that change it.

**Questions** lists everything waiting for your answer, grouped by subject, with how many questions each subject has. When you add a system, you answer one question per subject, such as whether it uses the same codes as a system already connected, not one per code. A question that holds rows back from the figures says how many, and their amount. **Weave suggests:** gives Weave's answer and the evidence for it: click **Use this answer**, or choose another in the list and click **Answer**. **Accept all suggested** answers every question that has a suggestion. An answer applies at the next **Load** or **Apply changes**. The **Questions** row shows only while a question waits.

A question about a revenue class or a team's function holds nothing back. See [Revenue Classes and Team Functions](#revenue-classes-and-team-functions).

When you change your sources, a bar above every page says **You have changed your sources. Press Apply changes to use them.** It has **Show what changed** and **Apply changes**, and it is the one place to apply a change. The result of a **Load** or **Apply changes** shows above whichever page is open, so you see it on every page.

While a load runs, the pages refresh on their own and keep reading even if one read fails. If the status can't be read, **The Foundation status could not be read.** appears with **Try again**, which reads it afresh; the pages also retry once by themselves before showing the message, and the message clears when the server answers.

## Common Finance Model Tables

Data Foundation conforms every source, ERP or file, into the same tables, so reports, metrics and models built on them work the same whatever the source. Each row also records its source system and when it was read. The **Dataset** column is the name you choose when you add a file.

| Dataset | Table | Holds |
|---|---|---|
| Entities | `cfm_entity` | Legal entities with parent, local and group currency, country, region and division. |
| Code map | `cfm_code_map` | The crosswalk from a code as a source carries it, such as an entity, account or department code, to the canonical code. See [Entity Crosswalk](#entity-crosswalk) and [Map Codes Across Sources](#map-codes-across-sources). |
| Currency rates | `cfm_fx_rate` | Monthly average, closing and historical rates by currency pair. See [Exchange Rates](#exchange-rates). |
| Fiscal calendar | `cfm_fiscal_calendar` | One row per entity fiscal period, with start and end dates and whether it is closed. |
| Chart of accounts | `cfm_account` | Accounts with parent, type (`Revenue`, `COGS`, `Opex`, `NonOperating`, `Asset`, `Liability`, `Equity`), statement, normal balance, rate type, account role and revenue class. The role, such as cash, receivable, payable or retained earnings, places the account on its statement and cash flow line. |
| Departments | `cfm_department` | Departments and cost centers with parent, profit center and function. |
| Profit centers | `cfm_profit_center` | Profit centers with parent and function. |
| Products | `cfm_product` | Product master with parent, family, group, unit of measure, standard cost and revenue class. |
| Customers | `cfm_customer` | Customer master with parent, group, region and country. Customer names are not masked. |
| Segment values | `cfm_segment` | Segment values with name and parent. See [Hierarchies](#hierarchies). |
| General ledger | `cfm_gl_journal` | Journal lines in transaction, local and reporting currency. |
| Trial balance | `cfm_trial_balance` | Period debits, credits and net by entity, account and department, in local and reporting currency. |
| Sales lines | `cfm_sales_line` | Invoiced sales lines with quantity, gross, discount, net and COGS amounts. |
| Pipeline | `cfm_opportunity` | Sales pipeline: one row per opportunity line, at any stage, one copy per month end. |
| Inventory balances | `cfm_inventory_balance` | Period-end inventory by product and warehouse. |
| Budget | `cfm_budget` | Budget and forecast by scenario, version, account and department. |
| CO-PA by valuation | `cfm_copa` | SAP profitability analysis (CO-PA) by entity, period, account, product and customer, one set of rows per valuation (legal, group or profit center), never added together. Revenue is positive and costs negative. Of the templates, only [Operational Transfer Pricing](/guides/projects/operational-transfer-pricing/#co-pa-margin) reads it. |
| Allocation drivers | `cfm_stat_driver` | Statistical drivers such as headcount, square feet or units. |

The model also holds the sub-ledgers and their masters, filled by the systems that carry them:

| Table | Holds |
|---|---|
| `cfm_site` | Sites: plant, warehouse location or office, each in one entity. |
| `cfm_supplier` | Supplier master. |
| `cfm_sales_rep` | Sales rep master. |
| `cfm_project` | Project master. A marketing campaign is a project. |
| `cfm_standard_cost` | Standard cost per unit by product, costing entity and period. |
| `cfm_system_balance` | Each system's own closing balance by account at each month end, read from its balance report, never from the journal lines. |
| `cfm_supplier_invoice_line` | Supplier invoice lines. |
| `cfm_purchase_order_line` | Purchase order lines, one copy per month end. |
| `cfm_open_item` | Open receivables and payables, one copy per month end. |
| `cfm_payment` | Payments received and made. |
| `cfm_order_line` | Sales order lines, one copy per month end. |
| `cfm_asset` | Fixed asset register. |
| `cfm_asset_movement` | Asset movements by book and period: addition, depreciation, disposal and transfer. |
| `cfm_contract` | Contracts and subscriptions, one copy per month end. A [contract register](#contract-registers) is copied to every month end each term runs over. |
| `cfm_deferred_revenue_movement` | Deferred revenue movements by contract and period. |
| `cfm_bank_balance` | Bank accounts and their month-end book balances. |
| `cfm_inventory_movement` | Inventory movements: receipts, issues, production, transfers, adjustments and write-offs. |

A table kept one copy per month end replaces the open month's copy at each load. The document tables carry a `counts` column: `1` for a row that counts, from the system that counts for its entity and month and from the book the project reports, and `0` for a row kept from another system or book. Reports and metrics read only the rows that count.

A Foundation project comes with [project elements](/guides/projects/data-model/) for the columns these tables share: `entity`, `account`, `department`, `profit_center`, `product`, `customer`, `period`, `site`, `supplier`, `sales_rep` and `project`. Each carries a description, and a type and dimension where one applies, so every table that has one of these columns shows the same meaning. Data Foundation adds any of them the project lacks and leaves one you have edited as it is. This holds for every ERP and file source.

Periods are written `YYYY-MM`, and transactions are placed by posting period. Budget is optional: an ERP without budgets still loads everything else.

A trial balance file can carry debit and credit columns, a net column, or both. With only debit and credit, the net is debit minus credit, and a blank side counts as zero. With only a net, a positive net becomes the debit and a negative net becomes the credit, as a positive amount. A department column is optional.

## Troubleshooting

| Symptom | What to do |
|---|---|
| **Test connection** says the ERP refused the credentials | Check the connection's credentials, and that the integration user can sign in to the ERP. |
| **Test connection** shows **Missing permission** for a dataset | Ask your ERP administrator to add the permissions it names. The [connection guide](/guides/connections/) for your ERP lists what the connection needs. |
| An ERP error message is shorter than the ERP's own | PlaidCloud removes credentials, tokens and keys from provider errors before showing them, so some detail is left out. Run **Test connection** to see which dataset is affected. |
| **Every month loaded** fails for a period | An ERP read for that period failed. Run **Load** again; periods that loaded are skipped. |
| **Every account known** fails | Add the missing accounts to the chart of accounts in the ERP or your file, and run **Load** again. |
| **Every amount has a rate** fails | An entity's currency has no rate into the reporting currency for that period, or no single reporting currency was found. Add the rates to a **Currency rates** file, check that the connection can read the ERP's exchange rates, or set the project variable `reporting_currency`. Then run **Load** again. |
| **Every amount has a rate** is a caution | Balance sheet, inventory or budget rows have no closing, historical or planned rate for the period. The profit and loss is not affected. Add the rates, including planned rates for budget months, and run **Load** again. |
| **Codes mapped** fails | Open **Questions** and answer each question. The answers apply at the next **Load** or **Apply changes**. |
| **One source for each key** fails | Under **Source coverage** on **Summary**, choose the month and the source, click **Save choice**, and click **Apply changes**. |
| The intercompany check is red or amber | Check the pairs in **Intercompany pairs**. Book the missing side, add the trading partner to the lines, or add the missing rate. |
| **Group views are off** | Ask an Architect to tick **Everyone on the project may see the group results** under **Group and row access** in **Project settings**. |
| A scheduled load was skipped | The person who set up the schedule can no longer use a system's connection. Set the schedule up again. See [Keep It Current](#keep-it-current). |
| **Every entity known** fails | Add the entity to the entity master, or map its code to an existing entity in a **Code map** file, and run **Load** again. |
