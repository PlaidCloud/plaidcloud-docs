**使用情况报告**展示工作区中谁在使用什么：成员打开了哪些屏幕、仪表板、应用和笔记本，有多少人再次回访，以及他们接下来去了哪里。可以借此了解成员采用了哪些功能、哪些仪表板和应用真正发挥了价值，以及人们在流程中的哪个环节流失。

从**身份**选项卡中打开，位于安全日志旁边。

## 谁可以查看

使用情况报告所需的权限与安全日志相同：`identity.security_log.read`。没有该权限时，不会提供此按钮；如果成员仍然设法打开报告，会看到无权访问的提示。

报告在两处按成员展示使用情况：**用户**选项卡，以及包含成员 ID 的**按成员划分的每日活动**和**首次使用**导出。其他内容均按全体成员汇总统计。请仅向需要查看个人活动的人员授予该权限。

## 统计内容

使用情况报告整合了五个来源。可以在**源**中选择其中一个，也可以保持为**所有来源**。

| 来源 | 记录内容 |
|---|---|
| PlaidCloud 应用 | 成员在应用中打开的屏幕和执行的操作。 |
| Superset | 仪表板和图表的浏览。 |
| Panel 应用 | 应用访问次数，以及成员在每个应用中花费的时间。 |
| JupyterHub | 成员在 JupyterHub 会话中花费的时间。 |
| Jupyter 笔记本 | 成员打开和保存的笔记本。 |

JupyterHub 会话和 Jupyter 笔记本是相互独立的来源，因此可以任选其一。Panel 应用算作一个来源。仅记录在默认笔记本镜像上运行的笔记本的事件，自定义镜像不会上报这些事件。

<Aside type="note">
报告中的每一天均为 UTC 日。在美洲工作到深夜的成员，其活动可能会显示在次日。
</Aside>

## 阅读报告

在窗口顶部选择来源和**日期范围**，然后选择**刷新**。可选范围为最近 7、30、90 或 180 天。每个选项卡在首次打开时加载，更改来源或范围时会再次加载。

### 概览

所选范围内的核心数据：

| 数据 | 含义 |
|---|---|
| **活跃用户** | 有任何活动的成员。 |
| **新用户** | 在该范围内首次出现的成员。 |
| **回访用户** | 在该范围之前就已出现过的活跃成员。 |
| **活跃分钟数** | 近似值：每个有活动的时间段计五分钟。 |
| **事件** | 记录的全部内容。 |
| **未归属事件** | 无法确定对应成员的事件。这些事件计入事件数，不计入用户数。 |
| **会话分钟数** | Panel 和 JupyterHub 的会话时间，与活跃分钟数分开统计。 |

**采用情况**列出每个屏幕、仪表板、图表或项目及其来源、事件、用户数、占活跃用户的比例、事件数和未归属事件数。**按月**显示每个月的活跃用户、日均用户数和用户黏性，并在该月仍在进行中、仅部分覆盖或为冻结快照时附上说明。

### 活动

按**每天**、**每周**或**每月**统计活跃用户，另有**按首周划分的留存**：针对成员首次出现的每一周，显示其后每一周有多少人回访。标有星号的时间段并未完全落在所选范围内。

### 路径

跨应用和来源，成员在屏幕之间最常走的跳转，显示为**移动自**、**移动至**和**经过次数**。路径最多涵盖最近 30 天。

### 用户

每名成员一行：姓名、用户名、活跃天数、事件数、活跃分钟数、会话分钟数，以及首次和最后一次出现的时间。

### 导出

将摘要下载为 CSV。选择**摘要**和最长 25 个月的**日期范围**，然后选择**下载 CSV**。

| 摘要 | 内容 |
|---|---|
| **每日活动** | 每天、每个来源、每个事件和每个主题的用户数和事件数。 |
| **按成员划分的每日活动** | 同上，但按每名成员统计，并包含成员 ID。 |
| **每月采用情况** | 每月、每个来源、每个事件和每个主题的用户数和事件数。 |
| **月活跃用户** | 每月、每个来源的活跃用户。 |
| **首次使用** | 每名成员首次使用每个来源的时间，并包含成员 ID。 |

导出使用的是在选项卡上方选择的来源。较大的摘要会以每批最多 50,000 行的方式下载，窗口会将它们合并为一个文件。如果文件超出窗口能够构建的大小，窗口会保存已有的内容，并提示文件不完整：请选择更短的范围以获取其余内容。

每次导出都会在安全日志中写入一条记录，记录谁导出了哪个摘要、范围以及行数。跨多个批次的摘要会为每个批次各写入一条记录。

<Aside type="caution">
每月摘要中，每个事件都有一个合计行，其主题为 `*`。该行是该事件在所有主题下去重后的用户数和事件数。不要将它与各主题行相加，否则会重复计算所有内容。
</Aside>

### 漏斗

查看有多少成员完成了一系列步骤。每个步骤是来自某个来源、针对特定主题的事件，或者是**任意主题**。

1. 选择**添加步骤**，并为每个步骤选择来源、事件和主题。一个漏斗包含 2 到 6 个步骤。
2. 选择**步骤之间允许的时间**：1、6、24、72 或 168 小时。
3. 选择 7、30 或 90 天的**日期范围**。
4. 选择**运行漏斗**。

结果会显示每个步骤有多少成员到达、占起始人数的比例、有多少人停在该步骤，以及与上一步骤之间的时间中位数。各步骤可以混用来源，因此可以追踪成员从 PlaidCloud 屏幕到 Superset 仪表板的行为。**最近的漏斗**可重新打开之前运行过的漏斗。步骤列表只提供在该范围内记录过的事件。

## 未归属的使用数据

有些事件无法关联到某个 PlaidCloud 成员。它们会计入**事件**和**未归属事件**，但绝不会计入用户数。主要情形如下：

- 在 Superset 内部而非通过 PlaidCloud 创建的 Superset 账户。
- 嵌入式仪表板的浏览，此类浏览没有 Superset 用户。
- 平台日志无法关联到某个成员的 Panel 和 JupyterHub 活动。其归属信息来自这些日志，因此只能视为尽力而为。

某个来源的未归属占比较大，意味着其用户数被低估。

## 历史记录的起点

历史记录从为工作区开启使用情况收集时开始，此前的任何一天或一个月都不会显示活动。第一个有数据的月份会标记为部分数据。

Panel 和 JupyterHub 的数据读取自平台日志，日志保留约 90 天。开始收集时，这两个来源最多补充这么长时间的更早历史。Superset 则根据其自身日志补充，最多 180 天。只有 PlaidCloud 应用在开始收集时从零开始。

使用情况报告将原始事件保留 180 天，因此最长范围为 180 天；每月摘要保留 25 个月。如果成员是在 PlaidCloud 之外被移除的，例如通过 SCIM 或 Keycloak，其原始使用数据会在 180 天后过期，首次使用记录则在 25 个月后过期。

## 清除成员的使用数据

具有 `identity.security_log.read` 权限的工作区管理员（或超级用户）可以清除某个成员的使用数据并停止收集，之后还可以撤销清除。清除和恢复都需要该权限和该角色。这两个操作仅可通过 REST API 使用。

| 操作 | 请求 |
|---|---|
| 清除 | `DELETE /rest/v1/identity/usage/users/{user_id}` |
| 恢复 | `DELETE /rest/v1/identity/usage/users/{user_id}/erasure` |

清除会删除该成员的事件和首次使用记录，并且从那一刻起，报告和导出将不再包含该成员。其使用数据不会再被收集，之后从 Panel 和 JupyterHub 日志中读取的历史记录也会被丢弃。如果无法立即完成删除，响应会予以说明，并由下一次每小时维护运行完成。

恢复会撤销清除，使新的活动重新被收集。它不会找回已清除的内容。

这两个操作都会在安全日志中写入一条记录。
