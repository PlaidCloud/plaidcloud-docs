## 新增

- **全新的启动器。** 登录后将直接进入启动器：一个由磁贴组成的页面，汇集您最近使用的项目、仪表板和 Panel 应用、您固定的内容，以及上次运行失败的所有工作流，并分为三个区域，可直接操作：打开磁贴、运行工作流、跳转到失败的运行或将其忽略。您可以在启动器中，或在平时使用的列表和文档浏览器中固定任何内容——项目、工作流、表、维度、数据编辑器、仪表板、Panel 应用，以及按文件或文件夹固定的文档。项目磁贴会汇总项目情况（工作流运行、工作流、表、记录），并带有淡化的背景图像，可在项目主页选项卡的 **启动器磁贴图像** 下为每个项目单独设置。可在磁贴视图和紧凑列表之间切换，隐藏不想看到的类型，并按 **Ctrl/Cmd-K** 在输入时即时搜索项目、工作流、表、仪表板和 Panel 应用。参见[启动器](/zh-cn/guides/launcher/)。

- **将集合或规范粘贴到 REST 请求步骤中。** Postman、OpenAPI/Swagger 和 HAR 来源在文件选择器旁各新增了 **粘贴…** 按钮，因此可以直接提供内容，而无需先将其保存到文档。参见 [REST 请求步骤](/zh-cn/guides/workflows/rest-request-step/#粘贴集合或规范而不是选取文件)。

- **为 REST 连接附加 API 定义。** 通用 REST 连接和 MuleSoft 连接现在可以携带自己的 OpenAPI 3.x 或 Swagger 2.0 定义——可以是已发布的地址，也可以是保存在文档中的规范文件。在连接的 **API 定义** 下设置一次后，任何使用该连接的 REST 请求步骤都可以将 **端点来源** 设为 **来自连接的 API 定义**，并列出该 API 的端点，方法、参数和请求体均已填好，无需在每个步骤中重复声明定义。参见[通用 REST 连接](/zh-cn/reference/connectors/rest/generic-rest/#api-定义)和 [REST 请求步骤](/zh-cn/guides/workflows/rest-request-step/#复用连接的-api-定义)。

- **MuleSoft 现已可作为连接类型使用。** 从 **新建连接** 菜单中添加 MuleSoft Anypoint 网关，并像配置其他 REST 连接一样进行配置——填写您自己的网关地址以及它所要求的任意身份验证方式。参见 [MuleSoft REST 连接器](/zh-cn/reference/connectors/rest/mulesoft/)。

- **PlaidCloud Git 连接。** 通过简化的表单连接到工作区自己的托管 Git 服务器——只需填写账户名称、备注、仓库路径、默认分支和可选的起始路径——无需输入服务器 URL、用户名、令牌或 SSH 密钥，因为 Git 服务器及您对它的访问权限均来自您平时的 PlaidCloud 登录。将 Server Panel 应用的构建指向 PlaidCloud Git 连接，即可完全在工作区内自动化构建，无需外部 GitHub 账户或访问令牌。外部 Git 提供商（GitHub、GitLab、Bitbucket、Forgejo、Gitea）仍使用完整的连接表单。参见 [PlaidCloud Git 连接](/zh-cn/guides/connections/plaidcloud-git/)。

- **Currency——专为金额设计的列数据类型。** 所有列数据类型列表——步骤的输出列映射、数据映射器网格、表的 **列属性**，以及 MCP/AI 工具——现在都提供 **货币**：一种精确的定点类型，具有 18 位精度和 4 位小数（范围约为 ±100 万亿，精确到 1/10,000）。它存储金额时占用的内存宽度只有 Numeric 的一半，因此金额密集的仪表板和工作流步骤扫描的数据量约减少一半，运行也更快；Numeric 仍是高精度的默认类型（38 位精度，10 位小数）。Currency 始终由您明确选择——导入、类型检测、SQL 结果和派生列仍默认使用 Numeric——一旦为某列设置，该类型会在读取、下游步骤和表重建过程中保持不变。Currency 的聚合结果为 Numeric。该选项将在平台更新在您的工作区上线后出现。参见 [Currency 数据类型](/zh-cn/guides/data/currency-data-type/)。

- **跳过重新导入未更改的源文件**——文件导入步骤（CSV、Excel、固定宽度、JSON、Avro、Parquet、Alteryx yxdb、dbf、XML、Access）新增了 **源文件未更改时跳过重新导入** 选项。启用后，如果自上次成功运行以来源文件和步骤设置均未更改，工作流运行将跳过整个下载、转换和表重建过程，因此计划的重新加载不再重复执行这些工作。**默认启用**——在步骤上取消勾选该选项即可始终重新导入；更改依据每个文件的大小和修改时间来检测，如果数据源提供内容哈希，则同时使用内容哈希。手动的一次性导入始终会运行。参见[导入 CSV](/zh-cn/reference/workflow-steps/import/import-csv/) 步骤。

- **工作流中的机器学习——ML：训练模型 和 ML：评分 步骤。** 可以在任意表上训练模型——从线性回归、逻辑回归、决策树、随机森林和梯度提升等七种算法中选择——并使用该模型对数据评分、追加预测列，整个过程都在工作流内完成。训练好的模型像其他表一样在工作流中流转，其算法、设置、特征和训练指标会一并记录，而拼写错误的算法或设置会在保存步骤时被捕获。参见 [ML：训练模型](/zh-cn/reference/workflow-steps/machine-learning/ml-train/)和 [ML：评分](/zh-cn/reference/workflow-steps/machine-learning/ml-score/)。

- **PlaidCloud 托管存储桶文档账户。** 只需一步即可为文档添加全托管的文件存储——无需设置或调整云项目、凭据、区域或存储层级。适用于 Business 和 Enterprise 套餐。参见[添加 PlaidCloud 托管存储桶账户](/zh-cn/guides/documents/adding-accounts/add-managed-bucket-account/)。

- **以最小权限连接 OneDrive 或 SharePoint 站点。** 将 OneDrive for Business 或 SharePoint 站点添加为文档账户，该账户只能访问 Microsoft 管理员明确授权的站点——即 Microsoft 的 Sites.Selected 模型——而不是整个 Microsoft 365 租户。将 OneDrive 选为账户的服务，输入应用注册的客户端 ID、密钥和租户 ID，粘贴已授权站点的 URL，然后选择其中一个文档库作为起始文件夹。未授权的站点——例如薪资、人力资源等——将完全无法访问。参见[添加 OneDrive / SharePoint 账户](/zh-cn/guides/documents/adding-accounts/add-onedrive-account/)。

- **功能更强的 REST 请求步骤。** REST 请求现在可以针对驱动表的各行扇出调用——每行一次请求，并可选用行筛选器——将键列带入结果，同时支持并发限制、请求速率上限、用于安全重新运行的可选幂等键、出错后继续的选项，以及清晰的逐行失败报告。新的编写辅助功能让请求更易于构建和验证：从 curl 命令导入、插入并高亮变量标记（包括驱动表的列）、测试第一个扇出行、在运行前预览解析后的请求及其分页、恢复未保存的草稿、就地编辑所选连接，以及在保存尚未成功测试的请求之前进行确认。参见 [REST 请求步骤](/zh-cn/guides/workflows/rest-request-step/)。

- **更完善的帮助与支持体验。** 可以为工单和回复附加屏幕截图和文件（图像内联显示）；在可排序、可筛选的支持控制台中处理工单（回复、添加内部备注、认领、设置优先级并升级给 PlaidCloud）；将新工单提醒发送到 Slack、Teams 或电子邮件渠道；在工单收到回复时向工单所有者发送电子邮件；并对长时间未回复的工单自动升级。参见[获取帮助](/zh-cn/guides/support/getting-help/)、[支持控制台](/zh-cn/guides/support/support-console/)和[管理支持](/zh-cn/guides/support/managing-support/)。

- **用于 AI 提问的分析路径。** 为最常分析的表起一个易记的名称，并将其中一个设为默认，这样您和 AI 助手就可以询问“运营结果”，或者直接问“上个季度有什么变化？”，而无需每次都指明项目和表。适用于 Microsoft 365 Copilot 和任何连接了 MCP 的代理。参见[分析路径](/zh-cn/integrations/ai-coding-agents/analysis-paths/)。

- **更智能、更诚实的 AI 分摊成本追溯。** 当您询问连接了 MCP 的 AI 代理某个分摊结果为何发生变化时，答案现在会附带通俗易懂的置信度和注意事项——指出原因是否为多个重叠因素的混合、是否取决于当前的层次结构或动因权重，或者部分变化是否可能只是数据加载尚未完成——并且即使后续代理对答案进行总结，这些可信度信号也会随答案一起传递。管理员还可以启用一项可选检查：当答案所依据的成本池或动因数据近期未重新加载时，降低置信度并标记该答案。对于由多个分摊分支构成的结果，置信度现在会按各分支对变化的贡献比例加权，因此一个很小且不可靠的分支不会拖累原本清晰的答案。您还可以提出动因重新加权的假设性问题（“如果这个成本中心的人数翻倍会怎样？”），并且完整的根本原因分析现在也可以通过 REST API 驱动，而不仅限于通过 AI 代理。参见[使用连接了 MCP 的 AI 代理追溯分摊](/zh-cn/integrations/ai-coding-agents/tracing-allocations/)。

- **值得信赖、且 AI 可自行核查的书面追溯摘要。** 当您询问连接了 MCP 的 AI 代理某个分摊结果为何发生变化时，它现在可以返回**直接根据分析生成的通俗摘要**：其中说明置信度、列出每一条注意事项，并且不会引用任何并非来自真实查询的数字。配套的**忠实性检查**让代理能够确认其改写后的版本保留了置信度和每一条注意事项，且没有编造任何内容——因此叙述不仅流畅，而且*可证明*忠实。每份摘要还会建议自然的下一个问题——限定到单个成员、按某个维度拆解变化，或者在结果表由多个步骤构建时指向特定的生成步骤——让您无需知道确切措辞即可深入查看。参见[值得信赖的答案](/zh-cn/integrations/ai-coding-agents/honest-answers/)。

- **在可视化工作流设计器中预览步骤数据。** 无需打开新窗口，即可就地查看步骤的输出——在画布底部停靠一个预览，显示前 100 行、带类型的列、行数和列数，并为多输出步骤提供选择器。点击另一个步骤会切换预览目标，运行结束时预览会刷新，一键即可打开完整的表资源管理器。参见[预览步骤数据](/zh-cn/guides/workflows/preview-step-data/)。

- **锁定 Panel 应用以防意外更改。** 在 我的 Panel 应用 的每一行上都有一个锁形图标，其保护方式与现有的工作流锁和步骤锁相同：锁定后，编辑、移除和重建该应用的操作都将拒绝执行——向 Server 应用的分支推送 git 也不再触发重建——而打开应用、查看其日志和使用指标仍可正常使用。这只是防止意外的措施，而非安全控制：任何可以编辑 Panel 应用的人都可以将其解锁。参见[锁定应用](/zh-cn/guides/panel-apps/using/#锁定应用)。

- **工作流步骤自动编号。** 现在每个步骤都带有一个编号——可视化画布上的徽章、步骤网格的首列，以及运行日志、工作流文档报告和 AI 助手列表中同样的“步骤 7”——因此在杂乱的导入工作流中，您可以让同事或 AI 代理查看“步骤 7”，而无需用名称来描述某个步骤。编号遵循数据流（步骤的编号始终排在为其提供数据的步骤之后），画布位置按从左到右、再从上到下的顺序决定先后，并且随着工作流被编辑，所有人的画布都会实时重新编号，编号发生变化的步骤会短暂高亮。右键点击步骤（或点击其徽章）即可复制可直接粘贴的引用，例如“步骤 7 — Clean Customer Names”。参见[步骤编号](/zh-cn/guides/workflows/step-numbers/)。

- **两个新的工作流步骤——目录列表 和 行数断言。** 目录列表会写出一张文档目录中文件的表（可选文件模式和子目录选项），以便下游步骤对现有的任何文件进行处理。行数断言是一道数据质量关卡，当两张表的行数不同时会使工作流失败。参见[目录列表](/zh-cn/reference/workflow-steps/document/directory-listing/)和[行数断言](/zh-cn/reference/workflow-steps/workflow-control/row-count-assert/)。

- **从可视化工作流设计器跳转到工作流的日志。** 画布工具栏上的 **查看日志** 按钮会打开项目日志视图，并已按您当前打开的工作流筛选——与您原本从项目区域进入的完整运行日志相同。参见[高级工作流](/zh-cn/guides/workflows/advanced-workflows/#查看日志)。

## 变更

- **Table Update 步骤写入目标表，而不是更改其源表。** 原先名为 **Table In-Place Update** 的步骤现在是 **Table Update**，并且重新出现在 **新建步骤** 菜单中。它读取源表，更新符合筛选条件的行，并将所有行——无论是否更改——写入您选择的目标表，同时保留源表不变以便比对。目标表的列始终与源表一致，包括步骤上次打开之后在上游新增的任何列。由于更新不再就地进行，它可以在所有仓库上运行，包括那些不允许就地更改表的仓库。视图是有效的目标。在此更改之前保存的步骤需要先选择目标表才能运行，并且任何原本读取源表并期望得到已更新行的步骤，都必须改为指向新的目标表。参见 [Table Update](/zh-cn/reference/workflow-steps/tables/table-update/)。

- **多表联接接受动态的源表和目标表。** 在表选择器上勾选 **动态**，然后输入表名或项目路径，而不是从列表中选择——两者都可以带有在工作流运行时解析的 `{variable}` 标记，因此联接可以写入 `/03 Results/FACT_GL_{year}`，并在每个期间读取不同的表。如果目标不存在，则会创建。其他所有步骤的表原本就是这样工作的；多表联接此前要求从列表中选择表，否则无法保存。动态源表的列在设计时无法读取，因此需要在侧边面板中手动输入。参见[多表联接步骤](/zh-cn/guides/workflows/multi-table-join-step/)。

- **多表联接的输出列可以包含表达式或常量。** 输出列的值现在恰好来自三种来源之一——源列（以及拥有该列的画布别名）、**常量** 或 **表达式**。**添加表达式列** 会追加一行并打开完整的表达式编辑器，其列浏览器中包含画布上的所有表，因此一个值可以跨越多个联接的表。**联接后筛选器** 也是同一个编辑器，而不再是普通文本框，并列出可作为 `result.column_name` 引用的输出列。编辑器缩减为三个选项卡：仅供内部使用的 **高级（服务器设置）** 选项卡已移除，其设置在保存时仍会保留。参见[多表联接步骤](/zh-cn/guides/workflows/multi-table-join-step/)。

- **文件导入可处理大文件并保留源数据类型。** Excel、JSON、Parquet、Alteryx yxdb、dBASE 和固定宽度文件的导入不再将整个文件加载到内存中，因此此前因内存不足而失败的大文件现在可以导入——实际限制是磁盘空间，而不是内存。源数据的类型——小数、日期和时间戳——现在会原样传递到目标表，而不再经过文本转换，并且 Parquet 时间戳列保留完整的时分秒精度（此前被截断为日期）。刻意保持不变的是：空白数值单元格仍加载为 0，文件名、路径、工作表名称、行号和最后修改时间列的行为与之前完全一致，行号按每个源文件计数。参见[导入 Excel](/zh-cn/reference/workflow-steps/import/import-excel/)、[导入 JSON](/zh-cn/reference/workflow-steps/import/import-json/) 和[导入 Parquet](/zh-cn/reference/workflow-steps/import/import-parquet/)。

- **JSON 导入接受换行分隔的文件，并生成标准 JSON 文本。** 导入 JSON 步骤现在除 JSON 数组外，还接受换行分隔的 JSON（NDJSON）——每行一个对象——并且嵌套的对象和数组现在以标准的紧凑 JSON 文本而不是 Python 风格的表示法进入表中，因此下游步骤可以使用任何 JSON 工具对其进行解析。参见[导入 JSON](/zh-cn/reference/workflow-steps/import/import-json/)。

- **为 Git 连接选取仓库、分支和文件夹。** Git 连接表单不再要求您输入仓库路径、分支名称或起始路径——而是从实时列表中选择。输入服务器和凭据（PlaidCloud Git 连接无需输入任何内容），点击“刷新”列出该连接可访问的仓库，选择其中一个以加载其分支，然后浏览其文件夹以设置可选的起始路径——这样拼写错误的名称就不会悄悄破坏连接。编辑现有连接时无需重新输入已存储的密码即可浏览。适用于 PlaidCloud Git 以及所有外部提供商（GitHub、GitLab、Bitbucket、Forgejo、Gitea）。参见 [PlaidCloud Git 连接](/zh-cn/guides/connections/plaidcloud-git/)。

- **AI 成本追溯更准确，也更不易被误导。** 假设性估算现在是真实的按目标计算的数值，能够在扇出之间累加，而不再是上限值，并且可以限定到单个目标——如果指向的是动因表或基准表而不是输入成本池，代理会拒绝估算并说明原因。动因重新加权的假设分析是精确的：它们只移动动因实际拆分的金额，不触及任何直通成本。代理现在能够识别并降低对具有误导性形态的置信度——例如总额中大幅上下波动相互抵消、净变化很小，或者变化主要是直通成本而非由动因决定——会指出由动因控制的金额实际变动了多少，并且在拆分不可靠时不再夸大单一“主导因素”。它还会解释维度层次结构分摊，而不是将其归为无法归因。数据新鲜度检查现在涵盖动因表和基准表，由多个分摊步骤生成的结果可以通过选择步骤来追溯——或者在筛选器将范围缩小到仅由一个步骤生成的行时自动追溯——并且在没有上一年数据的情况下进行同比比较时，现在会如实说明，而不是称这一变化“正常”。参见[使用连接了 MCP 的 AI 代理追溯分摊](/zh-cn/integrations/ai-coding-agents/tracing-allocations/)。

- **外部表：从源刷新单个表的列。** 在导入外部表和导出外部表步骤中，每个表的 **检查源** 按钮现在会直接从已连接的数据库读取所选表的当前列，并就地仅更新该表的映射——当源表的列在您构建步骤之后发生变化时非常方便，无需对整个连接重新运行发现。参见[导入外部数据库表](/zh-cn/reference/workflow-steps/import/import-external-database-tables/)。
- **可视化工作流设计器中的在线状态现在显示真实头像。** 当多人同时打开同一个高级工作流时，工具栏的在线状态行现在会用 gravatar 头像（若没有则用姓名首字母）显示每个人，并且无论某人在多少个浏览器选项卡中打开，都只显示一次。参见[高级工作流](/zh-cn/guides/workflows/advanced-workflows/#当前在线的用户)。

- **打开 Server Panel 应用时现在会显示真实进度。** 唤醒屏幕过去在整个启动过程中只显示一条消息，然后给出笼统的超时提示，因此完全无法启动的应用与只是启动缓慢的应用看起来毫无区别。现在它会报告实际阶段——启动中、准备中、加载中——在几秒内报告真正的失败及其根本原因，并在应用已经就绪时直接进入。启动后在加载时失败的应用（例如缺少软件包）会被报告为失败并附带错误，而不是提供空白页面。参见[创建 Panel 应用](/zh-cn/guides/panel-apps/creating/)。

## 修复

- **Table Update 在保存时不再丢弃“设为 Null”。** 它的列映射器在 **源列** 标题下列出您要更新的列，**目标列** 为空，并且根本没有提供 **设为 Null** 控件——保存步骤时会悄悄丢弃所有设置了“设为 Null”的列的该设置，导致步骤不再清除这些值。映射器现在在常量、表达式和设为 Null 旁显示 **更新列** 标题，并保留这四项。如果您的某个步骤之前会清除某一列，请检查“设为 Null”是否仍处于勾选状态。参见 [Table Update](/zh-cn/reference/workflow-steps/tables/table-update/)。

- **Table Upsert 现在可在 StarRocks 工作区上通过 API 使用。** 这些工作区使用的合并操作可以从工作流引擎调用，但无法从 REST API 调用，而后者仍要求该路径并不使用的语句，因此在那里根本无法通过 API 驱动 upsert。参见 [Table Upsert](/zh-cn/reference/workflow-steps/tables/table-upsert/)。

- **宏内的 Table Upsert 现在会停止，而不是写入错误的表。** 在 StarRocks 工作区上，它会悄悄合并到项目自己的表，而不是宏的副本。现在它会报告明确的错误，在底层限制解除之前，这些工作区上的宏 upsert 仍不可用。参见 [Table Upsert](/zh-cn/reference/workflow-steps/tables/table-upsert/)。

- **保存多表联接步骤时会报告需要修复的内容。** 只要有任何待解决的问题，保存就会因内部错误而失败，而不会告诉您哪里出了问题。现在它会切换到包含第一个问题的选项卡并列出所有问题，每个选项卡上也会显示问题数量的徽章。**从画布选取…** 选择器不再在步骤表单后面打开而无法操作。参见[多表联接步骤](/zh-cn/guides/workflows/multi-table-join-step/)。

- **动态 Excel 导入再次可用。** 配置为从工作表发现列、而不是使用已保存的列映射的 Excel 导入，每次运行都会失败。现在它会按配置正常导入。参见[导入 Excel](/zh-cn/reference/workflow-steps/import/import-excel/)。

- **空工作表不再导致多工作表 Excel 导入失败。** 当一次 Excel 导入涵盖多个工作表而其中一个为空时，导入现在会从该工作表加载零行并继续执行，而不是使整个步骤失败。参见[导入 Excel](/zh-cn/reference/workflow-steps/import/import-excel/)。

- **JSON 导入不再丢弃大型文档中较晚出现的列。** 某一列的首个值出现在大型 JSON 文件的较深位置时，可能会在导入的表中被悄悄遗漏。现在文档中的每一列都会被包含。参见[导入 JSON](/zh-cn/reference/workflow-steps/import/import-json/)。
- **AI 助手不再批准运行时会失败的表达式。** 少数表达式函数与 Python 关键字同名——`IF`、`AND`、`OR`、`NOT`——并且写成带尾部下划线的形式，如 `func.if_(...)`。助手之前把这一点弄反了：它批准了 `func._if(...)`，而这并不是真正的函数，会在运行时失败，同时拒绝了正确的 `func.if_(...)`。现在它接受有效的写法，拒绝无效的写法，并在您写错时指出正确的拼写。它在起草时参考的函数参考也已更正，与此保持一致。参见 [IF](/zh-cn/reference/expressions/lakehouse-v2/06-condition-functions/if/)。

- **使用 Basic、API 密钥或持有者令牌身份验证的 REST 连接现在会真正进行身份验证。** 过去只有 OAuth 2.0 凭据会被发送，因此配置了其他三种方式中任意一种的连接，在检查身份验证的 API 上都会失败。现在这四种都会按配置工作。如果您曾通过手动把凭据放入 **默认标头** 来绕过此问题，连接自身的身份验证现在优先生效，可以删除该行。参见[通用 REST 连接](/zh-cn/reference/connectors/rest/generic-rest/#身份验证)。

- **从 Postman 集合或 API 规范列出端点再次可用。** 在 REST 请求步骤中，**加载目录** 对每个来源都报告错误——无论是 Postman 集合还是 OpenAPI/Swagger 规范，无论是从文档中选取还是从地址获取。现在它可以再次列出端点，并且如果您尚未选择，会提示您先选择文件或地址。参见 [REST 请求步骤](/zh-cn/guides/workflows/rest-request-step/)。

- **REST 连接的默认标头现在会真正发送。** 在 REST 连接的 **默认标头** 下设置的标头会显示在步骤的请求预览中，却不会出现在实际请求里。现在它们会随通过该连接发出的每个请求一起发送，包括分页读取中的每一页以及逐行扇出中的每个请求。在单个步骤上设置的标头，仍优先于连接上同名的标头。如果您的某个连接配置了默认标头，请检查它们是否正是您想发送的内容。参见[通用 REST 连接](/zh-cn/reference/connectors/rest/generic-rest/#默认标头)。

- **向 Server Panel 应用的仓库推送现在会重建该应用。** 从 PlaidCloud Git 或 GitHub 连接发布 Server Panel 应用一直可以正常工作，但之后对该连接分支的推送不会被识别——应用会一直提供其最初构建的版本，直到有人手动重新发布。现在推送会自动触发重建和重新部署，详见[从 Git 部署 Panel 应用](/zh-cn/guides/panel-apps/deploy-from-git/)。已锁定的应用仍会跳过重建，直到解锁。现有应用或连接无需任何更改。

- **重命名步骤的运行条件再次可用。** 设置步骤运行前必须满足的条件时，现在可以重命名每个条件——在配置面板中编辑新的 **名称** 字段，或双击列表中的条件。右键点击条件还可以进行 **重命名** 和 **删除**。参见[步骤的运行条件](/zh-cn/guides/workflows/step-conditions/)。

- **导入无法读取任何列时给出更清晰的错误。** 当您设置或自动创建 CSV 或文本导入，而 PlaidCloud 无法从源文件读取任何列时——例如某些 Microsoft Access 文本导出，或分隔符、引号与实际不符的文件——现在会在您保存或创建导入时立即告知，而不是让步骤运行后再以令人困惑的消息失败。请调整分隔符、引号和转义设置或修复文件，然后重试。参见[导入 CSV](/zh-cn/reference/workflow-steps/import/import-csv/)。

- **托管存储桶名称冲突现在会给出解释。** 以已被占用的存储桶名称创建 PlaidCloud 托管存储桶文档账户时，此前会以笼统的“Internal server error”失败。现在 **存储桶名称** 字段会直接标出冲突，并说明存储桶名称是全局唯一的，同时指导如何选择更具体的名称——例如加上公司名作为前缀。参见[添加 PlaidCloud 托管存储桶账户](/zh-cn/guides/documents/adding-accounts/add-managed-bucket-account/)。

- **OneDrive 和 SharePoint 文档账户——浏览与下载修复。** 打开已配置的 OneDrive 或 SharePoint 文档账户时，现在可以可靠地列出其文件夹和文件，而不是出错失败；并且即使 Microsoft 管理员已关闭该站点的链接共享，下载文件也能正常进行。下载不再依赖创建可共享链接，因此锁定站点中的文件仍可打开，而不会报错。参见[添加 OneDrive / SharePoint 账户](/zh-cn/guides/documents/adding-accounts/add-onedrive-account/)。

- **删除被导入读取的表时现在会发出警告。** 删除 **导入：外部项目表** 步骤所读取的表时，PlaidCloud 现在会将其识别为正在使用，并要求您确认强制删除——勾选 **是否强制删除该表？** ——而不是提供普通删除，这样其他项目所依赖的表就不会被意外移除。这包括来自共享本项目数据的*另一个*项目中的步骤的引用；这些引用会显示在确认信息中，但不包含另一个项目的步骤详情（您可能无权访问该项目）。参见[导入项目表](/zh-cn/reference/workflow-steps/import/import-project-table/)。

- **联接步骤——输出列修复。** 对于内联接、外联接、反联接和交叉联接，输出列选项卡现在只列出您从两个源映射的列，并在您移除已映射的源列时删除过期的行；列映射器工具栏和多行选择已恢复；并且“汇总”现在是默认关闭的开关，因此联接不再强制对其输出分组——开启后，新列会根据其数据类型默认使用聚合，您可以按列覆盖。多表联接的输出列现在会跟随联接图设计器中的重命名和移除。参见 [Table Inner Join](/zh-cn/reference/workflow-steps/tables/table-inner-join/) 和[多表联接步骤](/zh-cn/guides/workflows/multi-table-join-step/)。

- **REST 请求可靠性修复。** 变量现在可以在 JSON 请求体中可靠地替换，每个请求的超时和重试设置会被遵守（仅对幂等方法重试，因此 POST/PUT/PATCH 绝不会被重新发送），被限流的响应会以退避方式重试，并且请求凭据在任何捕获的原始 JSON 中都会被屏蔽。测试请求现在即使成功也会显示响应状态码，单对象响应会作为一行导入。由传感器和 Webhook 触发的工作流还可以将触发器的元数据和入站有效负载作为变量读取。参见 [REST 请求步骤](/zh-cn/guides/workflows/rest-request-step/)。

- **AI 成本追溯修复。** 成本追溯现在可以处理包含空格或符号的模型列名，可以解析按友好名称给出的表，适用于模型运行步骤和项目副本的结果，并可在所有工作区类型中使用。异常检测现在会标记异常大的波动，并在跨年度边界时让以季度标注的期间保持真实的时间顺序；另外还更正了两个误标问题——加权基准为空时出现的“从零开始”跳变，以及前值为负时百分比变化符号错误。

- **导入/导出项目表在源为空时发出警告。** 当导入项目表或导出项目表步骤从没有任何行的源表复制时，现在会在完成时给出警告，说明源为空——这样意外的空结果很容易被发现，而不是步骤看似悄然成功。这通常意味着步骤运行时，源项目的数据尚未构建。参见[导入项目表](/zh-cn/reference/workflow-steps/import/import-project-table/)和[导出到外部项目表](/zh-cn/reference/workflow-steps/export/export-project-table/)。

- **表包现在会携带每列的维度、备注和格式。** 先前将表导出为包再导入到另一个项目时，导入后的表中每一列的维度关联都为空，列的备注和显示格式也是如此。由于后续步骤的列设置取自其读取的表，导入的表可能会把这一缺失传递给基于它构建的所有内容。这些设置现在随包一起传递，并在导入时恢复。如果某列指向目标项目中不存在的维度，则只会丢弃这一项关联，并在导入日志中列出，而不是恢复成损坏的链接——请在创建该维度后重新关联。在此更改之前导出的包，其导入方式与之前完全相同。

- **“创建并打开”现在会为 DAG 工作流打开正确的视图。** 对新的高级（DAG）工作流使用 **创建并打开配置** 时，会打开经典步骤网格，而不是可视化工作流设计器画布。现在它会打开画布，与双击该工作流时的效果一致。参见[高级工作流](/zh-cn/guides/workflows/advanced-workflows/)。

- **Panel 应用的依赖项可以放在应用旁边。** 从 Git 仓库构建的服务器端 Panel 应用，现在不仅会安装仓库根目录下的 `requirements.txt`，也会安装与其入口点放在一起的同名文件——因此存放在共享仓库子文件夹中的应用可以声明自己的软件包（例如 `plotly`、`holoviews` 或 `hvplot`），不会再因缺少库而渲染为空白。参见[创建 Panel 应用](/zh-cn/guides/panel-apps/creating/#添加依赖项)。

- **在文件夹之间移动大量或大型文档。** 同时移动多个文件——或单个大文件——从一个文档文件夹到另一个现在可以可靠地完成。移动逐个执行以保持文件列表一致，大型移动会获得所需的完成时间，而不会在中途被切断。

- **AI 助手不再拒绝引用以下划线命名的列的表达式。** 引用名称以下划线开头的列（例如 `_MajorAccountFlag`）的表达式现在会被接受。并且当表达式使用 `is`、`is not` 或 `not` 来测试某一列时——在列上这永远不会匹配任何行，或者会出错，而不是实现看起来的效果——助手会引导您使用有效的运算符（`is_(None)` 用于空值测试，`!=`，`~`），而不是直接拒绝。

- **AI 助手不再拒绝有效的函数。** 表达式选择器列表中没有的真实函数——`rtrim`、`ltrim`、`to_char`、`substring` 等许多函数——之前被当作未知函数拒绝，而将任何函数名写成大写（`func.SUM`）即使小写形式被接受也会被拒绝。现在助手会对照您工作区自己的函数列表以及选择器的列表检查名称，并且不区分大小写。

- **Panel 应用不再渲染出看不见的文字。** 平台范围的主题默认设置曾应用于每个 Panel 应用，包括那些不使用匹配页面模板的应用。在这些应用上，它会把文字画成白色、页面也是白色——应用看起来一片空白，日志里也没有任何解释。现在应用会保持自己的外观，除非它们选择使用主题模板。现有应用将在下次重建或重新发布时获得此修复。

- **唤醒屏幕不再改变 Panel 应用的外观。** 当 Server Panel 应用启动时，其背后的屏幕会设置自己的背景和浅色/深色配色，而应用会继承它们且无法覆盖——因此应用可能会在错误的画布颜色上渲染，并遵循操作系统的浅色/深色偏好而不是它自己的设置。现在应用启动后，该屏幕会被完全移除。它也不会再丢弃您所打开地址中的任何内容：应用读取的查询参数，包括 `?theme=dark`，现在都会传递给应用。

- **展开归档会保留其文件夹结构。** 将 `.zip` 或 `.tar.gz` 解压到文档中时，所有内容会被展平到目标文件夹——包含 `data/master/accounts.csv` 的归档只会生成一个孤零零的 `accounts.csv`，因此位于不同文件夹中的同名文件会发生冲突。现在嵌套的归档解压时会保留其文件夹。平面归档以及单文件 `.gz`/`.bz2` 保持不变。在 SFTP 文档账户上，目标文件夹必须已经存在，因此请将嵌套归档展开到您已在那里创建的路径。

- **错误的计划不再破坏事件调度器。** 一个重复规则无法使用的计划事件——例如不可能的日期（如 30 天的月份中的 31 日）或格式错误的条目——会导致整个工作区的事件调度器列表和计划日历因内部服务器错误而失败，并可能导致项目无法打开。现在无法读取的计划只会显示空白的下次运行时间，屏幕上的其他内容均可正常加载。参见[事件调度器](/zh-cn/administration/scheduled-events/event-scheduler/)。

- **工作流失败现在会说明实际出了什么问题。** 当工作流步骤在后台作业中失败时，运行日志和通知电子邮件只显示该操作的笼统消息——“Exception importing directly from remote sql”——而真正的原因，例如源系统上的密码过期，在您能看到的任何地方都没有出现。现在底层失败原因会传递到日志和电子邮件中。当许多表因同一个共同原因失败时，只会报告一次，而不是每个表各报告一次，并且消息中的凭据会被移除。

- **发往其他主机的 REST 请求不再发送连接的凭据。** 当 REST 请求步骤使用完整地址而不是路径时——包括许多 API 返回的分页链接——会出现两个问题：该地址被拼接到连接的主机上，导致请求彻底失败；并且无论请求发往何处，连接的身份验证和默认标头都会被附加。现在完整地址按原样使用，并且除非地址指回连接自己的主机，否则凭据和默认标头不会发送——因此分页仍然有效，而第三方地址绝不会收到您的凭据。参见 [REST 请求步骤](/zh-cn/guides/workflows/rest-request-step/)。

- **编辑 Basic 身份验证的 REST 连接不再丢失其密码。** 保存使用 Basic 身份验证的 REST 连接的更改而不重新输入密码时，会丢弃已存储的密钥。现在所有四种身份验证类型的已存储密码都会被保留。还修复了两处请求预览不一致的问题：在步骤上以不同大小写设置的标头，现在按与真实请求相同的方式合并，空的标头值现在以空值发送，而不是字面文本“None”。参见[通用 REST 连接](/zh-cn/reference/connectors/rest/generic-rest/#身份验证)。

- **合并表时会保留每列的维度和格式。** 当 Union、Union All、分摊或多表联接将多个源合并为一个输出列时，该列的维度、备注和格式设置取自碰巧排在最后的源。未声明维度的源可能会压过指明维度的源，因此一列在重建后一直没有关联，而类似的列却能恢复。现在，指明了维度的源优先于沉默的源，直通列优先于重命名列，而各源之间真正的分歧会在步骤日志中报告，而不是被悄悄解决。将聚合列重命名——`SUM(amount)` 变为 `total_amount`——也不再把源列的维度复制到总计上，因为总计从来不能标识该维度的某个成员。参见 [Table Union All](/zh-cn/reference/workflow-steps/tables/table-union-all/) 和 [Table Union Distinct](/zh-cn/reference/workflow-steps/tables/table-union-distinct/)。

- **Table Melt 遵循您编写的列映射。** 您有意从 melt 映射中排除的列会在后台被重新加入步骤，这在聚合步骤上会使整个步骤失败。现在，指明了其值列的映射将严格按所写内容使用。参见 [Table Melt](/zh-cn/reference/workflow-steps/tables/table-melt/)。

- **从另一个项目复制表再次可用。** 在项目之间复制表的步骤调用了一个已不存在的操作，因此每次运行都在服务器上失败。现在它使用与导入项目表步骤相同的机制，并且在源为空时报告警告而不是失败。参见[导入项目表](/zh-cn/reference/workflow-steps/import/import-project-table/)。

- **行数断言可在宏内使用。** 嵌套在 Macro Run 或 Macro Concurrent 步骤中的行数断言步骤会因服务器端错误而失败；只有顶层运行可以正常工作，这也是此问题一直没被发现的原因。现在它可以在任何嵌套层级正确运行。参见[行数断言](/zh-cn/reference/workflow-steps/workflow-control/row-count-assert/)。
- **当上游成本池尚未构建时，成本追溯不再中断。** 询问某个分摊结果为何发生变化时，如果为该分摊提供数据的某张表尚未生成——通常是因为模型的这一部分尚未运行——过去会直接失败。现在追溯可以完成：它仍会报告该阶段的实测总额，将上游拆解标记为无法归因而不是猜测，并告诉您在重新追溯之前需要重建哪个输入。总额没有变化的阶段会报告为未变，而不会暗示对缺失的成本池做过任何测量。

- **表详情现在显示实时行数。** 打开表的详情时，行数会从仓库读取，因此在通过 SQL 写入数据之后仍然正确——此前在刷新表的结构之前，它可能显示过时的数字。对于只能估算行数的数据存储，现在会将其标记为近似值，而不是显示为精确值。

## 移除

- **停用的旧版导入和导出步骤**——SAS7BDAT 导入、HTML 导入和 HTML 导出步骤已被移除。请改用当前的导入和导出步骤来处理这些格式。

- **停用 X12 EDI 导入步骤**——该步骤类型已被移除。它从未正常工作：每次 X12 EDI 导入在运行时都会失败。如果需要在 PlaidCloud 中使用 EDI 数据，请先将其转换为 CSV 或 JSON 等受支持的格式，然后导入。

- **停用应用内的 重置密码 选项**——账户（头像）菜单中的 **重置密码** 项已被移除。要重置密码，请使用登录页面上的 **Forgot Password?** 链接。

## 安全

- **安全分配的更改现在立即生效。** 编辑安全组的范围或成员、删除安全组、更改成员所属的安全组，以及激活和停用成员，过去都会延迟生效——大多数权限最多延迟半分钟，而对工作区 Git 服务器的访问要等到该用户下次登录才生效，对于被撤销访问权限的人来说，这可能永远不会发生。现在，所有这些更改都会在保存的瞬间应用到整个平台。无需任何配置；请检查您之前授予或撤销的任何访问权限，现在应当是准确的。参见[管理安全组和分配](/zh-cn/administration/access/managing-security-groups-and-assignments/)。
