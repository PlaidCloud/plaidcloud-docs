## Dodano

- **Nowy Launcher.** Po zalogowaniu otwiera się teraz Launcher: jedna strona kafelków zbierająca ostatnie projekty, pulpity i aplikacje Panel, wszystko, co przypięto, oraz każdy przepływ pracy, którego ostatnie uruchomienie zakończyło się błędem — ułożone w trzy pasy, na których można działać bezpośrednio: otworzyć kafelek, uruchomić przepływ pracy, przejść do uruchomienia z błędem lub go odrzucić. Przypinaj dowolne elementy z Launchera albo z list i przeglądarki dokumentów, w których już pracujesz — projekty, przepływy pracy, tabele, wymiary, edytory danych, pulpity, aplikacje Panel oraz dokumenty (pliki lub foldery). Kafelki projektów podsumowują projekt (uruchomienia przepływów pracy, przepływy pracy, tabele, rekordy) i mają wyblakły obraz tła, który można ustawić dla każdego projektu w polu **Obraz kafelka programu uruchamiającego** na karcie Home projektu. Przełączaj się między kafelkami a gęstą listą, ukrywaj typy, których nie chcesz widzieć, i naciśnij **Ctrl/Cmd-K**, aby w trakcie pisania wyszukiwać projekty, przepływy pracy, tabele, pulpity i aplikacje Panel. Zobacz [Launcher](/pl/guides/launcher/).

- **Wklej kolekcję lub specyfikację do kroku Żądanie REST.** Źródła Postman, OpenAPI/Swagger i HAR mają teraz przycisk **Wklej…** obok selektora plików, dzięki czemu można podać zawartość bezpośrednio, zamiast najpierw zapisywać ją w Document. Zobacz [Krok Żądanie REST](/pl/guides/workflows/rest-request-step/#wklejanie-kolekcji-lub-specyfikacji-zamiast-wybierania-pliku).

- **Dołącz definicję API do połączenia REST.** Ogólne połączenia REST i MuleSoft mogą teraz zawierać własną definicję OpenAPI 3.x lub Swagger 2.0 — opublikowany adres albo plik specyfikacji przechowywany w Document. Ustaw ją raz w połączeniu w polu **Definicja API**, a każdy krok Żądanie REST używający tego połączenia może ustawić **Źródło punktów końcowych** na **Z definicji API połączenia** i wyświetlić listę punktów końcowych interfejsu API wraz z wypełnionymi metodami, parametrami i treściami żądań, bez ponownego podawania definicji w każdym kroku. Zobacz [Ogólne połączenie REST](/pl/reference/connectors/rest/generic-rest/#definicja-api) oraz [Krok Żądanie REST](/pl/guides/workflows/rest-request-step/#ponowne-użycie-definicji-api-połączenia).

- **MuleSoft jest dostępny jako typ połączenia.** Dodaj bramę MuleSoft Anypoint z menu **Nowe połączenie** i skonfiguruj ją jak każde inne połączenie REST — podając adres własnej bramy i oczekiwany sposób uwierzytelniania. Zobacz [Konektor MuleSoft REST](/pl/reference/connectors/rest/mulesoft/).

- **Połączenia PlaidCloud Git.** Połącz się z zarządzanym serwerem Git własnego obszaru roboczego za pomocą uproszczonego formularza — wystarczy nazwa konta, notatka, ścieżka repozytorium, domyślna gałąź i opcjonalna ścieżka początkowa — bez adresu URL serwera, nazwy użytkownika, tokenu ani klucza SSH, ponieważ serwer Git i dostęp do niego wynikają ze zwykłego logowania do PlaidCloud. Skieruj kompilację serwerowej aplikacji Panel na połączenie PlaidCloud Git, aby zautomatyzować kompilacje w całości wewnątrz obszaru roboczego, bez zewnętrznego konta GitHub ani tokenu dostępu. Zewnętrzni dostawcy Git (GitHub, GitLab, Bitbucket, Forgejo, Gitea) zachowują pełny formularz połączenia. Zobacz [Połączenie PlaidCloud Git](/pl/guides/connections/plaidcloud-git/).

- **Waluta — typ danych kolumny stworzony dla wartości pieniężnych.** Każda lista typów danych kolumn — mapowania kolumn wyjściowych kroków, siatka Data Mapper, **Właściwości kolumny** tabeli oraz narzędzia MCP/AI — oferuje teraz typ **Waluta**: dokładny typ stałoprzecinkowy z 18 cyframi precyzji i 4 miejscami dziesiętnymi (w przybliżeniu ±100 bilionów, z dokładnością do 1/10 000). Przechowuje kwoty w pamięci w połowie szerokości typu Numeric, więc pulpity i kroki przepływów pracy intensywnie operujące na kwotach skanują około połowy danych i działają szybciej; Numeric pozostaje domyślnym typem wysokiej precyzji (38 cyfr, 10 miejsc dziesiętnych). Waluta jest zawsze Twoim jawnym wyborem — importy, wykrywanie typów, wyniki SQL i kolumny pochodne nadal domyślnie używają typu Numeric — a po ustawieniu w kolumnie jest zapamiętywana przy odczytach, w kolejnych krokach i podczas odbudowy tabel. Agregacje typu Waluta zwracają typ Numeric. Opcja pojawia się, gdy aktualizacja platformy zostanie uruchomiona w Twoim obszarze roboczym. Zobacz [Typ danych Waluta](/pl/guides/data/currency-data-type/).

- **Pomijanie ponownego importu niezmienionych plików źródłowych** — kroki importu plików (CSV, Excel, plik o stałej szerokości, JSON, Avro, Parquet, Alteryx yxdb, dbf, XML, Access) mają nową opcję **Pomiń ponowny import, jeśli pliki źródłowe nie uległy zmianie**. Po jej włączeniu uruchomienie przepływu pracy pomija całe pobieranie, konwersję i odbudowę tabeli, jeśli pliki źródłowe i ustawienia kroku nie zmieniły się od ostatniego udanego uruchomienia — dzięki temu zaplanowane ponowne ładowanie nie powtarza już tej samej pracy. **Domyślnie włączone** — odznacz opcję w kroku, aby zawsze importować ponownie; zmiana jest wykrywana na podstawie rozmiaru i czasu modyfikacji każdego pliku oraz skrótu zawartości, jeśli źródło go udostępnia. Ręczne, jednorazowe importy zawsze się wykonują. Zobacz [Importuj CSV](/pl/reference/workflow-steps/import/import-csv/).

- **Uczenie maszynowe w przepływach pracy — kroki ML: trenuj model i ML: oceniaj.** Wytrenuj model na dowolnej tabeli — do wyboru siedem algorytmów, w tym regresja liniowa i logistyczna, drzewa decyzyjne, lasy losowe i wzmacnianie gradientowe — i oceniaj nim dane, dopisując kolumnę predykcji, w całości wewnątrz przepływu pracy. Wytrenowany model przepływa przez przepływ pracy jak każda inna tabela, a jego algorytm, ustawienia, cechy i metryki treningowe są zapisane obok; błędnie wpisane algorytmy lub ustawienia są wychwytywane przy zapisie kroku. Zobacz [ML: trenuj model](/pl/reference/workflow-steps/machine-learning/ml-train/) oraz [ML: oceniaj](/pl/reference/workflow-steps/machine-learning/ml-score/).

- **Konta dokumentów typu Zasobnik zarządzany przez PlaidCloud.** Dodaj w pełni zarządzane przechowywanie plików do Document jednym krokiem — bez konfigurowania i dostrajania projektu w chmurze, poświadczeń, regionu ani poziomu przechowywania. Dostępne w planach Business i Enterprise. Zobacz [Dodawanie konta Zasobnik zarządzany przez PlaidCloud](/pl/guides/documents/adding-accounts/add-managed-bucket-account/).

- **Połącz witrynę OneDrive lub SharePoint z dostępem o minimalnych uprawnieniach.** Dodaj witrynę OneDrive for Business lub SharePoint jako konto Document, które ma dostęp wyłącznie do witryn, do których administrator Microsoft wyraźnie przyznał uprawnienia — zgodnie z modelem Sites.Selected firmy Microsoft — a nie do całej dzierżawy Microsoft 365. Wybierz OneDrive jako usługę konta, wpisz identyfikator klienta, sekret i identyfikator dzierżawy rejestracji aplikacji, wklej adres URL witryny z przyznanym dostępem i wybierz jedną z jej bibliotek dokumentów jako folder początkowy. Witryny, do których nie przyznano dostępu — płace, kadry i podobne — pozostają całkowicie poza zasięgiem. Zobacz [Dodawanie konta OneDrive / SharePoint](/pl/guides/documents/adding-accounts/add-onedrive-account/).

- **Bardziej rozbudowany krok Żądanie REST.** Żądanie REST może teraz rozgałęziać wywołanie na wiersze tabeli sterującej — jedno żądanie na wiersz, z opcjonalnym filtrem wierszy — przenosząc kolumny kluczowe do wyników, z limitem współbieżności, ograniczeniem częstotliwości żądań, opcjonalnym kluczem idempotentności dla bezpiecznych ponownych uruchomień, opcją kontynuowania po błędzie i czytelnym raportowaniem błędów dla poszczególnych wierszy. Nowe pomoce autorskie ułatwiają tworzenie i weryfikowanie żądań: import z polecenia curl, wstawianie i wyróżnianie tokenów zmiennych (także kolumn tabeli sterującej), testowanie pierwszego wiersza rozgałęzienia, podgląd rozwiązanego żądania i jego stronicowania przed uruchomieniem, przywracanie niezapisanych wersji roboczych, edycja wybranego połączenia w miejscu oraz potwierdzenie przed zapisaniem żądania, które nie zostało pomyślnie przetestowane. Zobacz [Krok Żądanie REST](/pl/guides/workflows/rest-request-step/).

- **Rozszerzona obsługa Pomoc i wsparcie.** Dołączaj zrzuty ekranu i pliki do zgłoszeń i odpowiedzi (obrazy wyświetlają się w treści), obsługuj zgłoszenia z posortowanej i filtrowalnej konsoli wsparcia (odpowiadaj, dodawaj notatki wewnętrzne, przejmuj, ustawiaj priorytet i eskaluj do PlaidCloud), kieruj alerty o nowych zgłoszeniach na kanał Slack, Teams lub e-mail, wysyłaj e-mail do właściciela zgłoszenia, gdy otrzyma odpowiedź, oraz automatycznie eskaluj zgłoszenia pozostawione zbyt długo bez odpowiedzi. Zobacz [Uzyskiwanie pomocy](/pl/guides/support/getting-help/), [Konsola wsparcia](/pl/guides/support/support-console/) oraz [Zarządzanie wsparciem](/pl/guides/support/managing-support/).

- **Ścieżki analizy dla pytań do AI.** Nadaj tabelom, które analizujesz najczęściej, przyjazną nazwę i ustaw jedną jako domyślną, aby Ty i Twój asystent AI mogli pytać o „Operations Results” — albo po prostu „co zmieniło się w ostatnim kwartale?” — bez każdorazowego podawania projektu i tabeli. Działa w Microsoft 365 Copilot i w każdym agencie połączonym przez MCP. Zobacz [Ścieżki analizy](/pl/integrations/ai-coding-agents/analysis-paths/).

- **Mądrzejsze i rzetelniejsze śledzenie kosztów alokacji przez AI.** Gdy pytasz agenta AI połączonego przez MCP, dlaczego wynik alokacji się zmienił, odpowiedź zawiera teraz poziom pewności i zastrzeżenia w prostym języku — wskazuje, gdy przyczyną jest mieszanka nakładających się czynników, gdy zależy ona od bieżącej hierarchii lub wag kluczy alokacji albo gdy część zmiany może wynikać z niedokończonego ładowania danych — a te sygnały wiarygodności towarzyszą odpowiedzi nawet wtedy, gdy podsumowuje ją kolejny agent. Administratorzy mogą też włączyć opcjonalne sprawdzenie, które obniża pewność i oznacza odpowiedź, gdy dane puli lub klucza alokacji, na których się opiera, nie były ostatnio przeładowywane. Dla wyniku zbudowanego z kilku gałęzi alokacji pewność waży teraz każdą gałąź według tego, jaką część zmiany wyjaśnia, więc jedna mała, niepewna gałąź nie obniża skądinąd czystej odpowiedzi. Można też zadawać pytania what-if dotyczące zmiany wag kluczy alokacji („co by było, gdyby liczba pracowników tego centrum kosztów się podwoiła?”), a pełną analizę przyczyn można teraz prowadzić także przez interfejs API REST, nie tylko przez agenta AI. Zobacz [Śledzenie alokacji za pomocą agenta AI połączonego przez MCP](/pl/integrations/ai-coding-agents/tracing-allocations/).

- **Pisemne podsumowanie śledzenia, któremu można zaufać — i które AI może zweryfikować.** Gdy pytasz agenta AI połączonego przez MCP, dlaczego wynik alokacji się zmienił, może on teraz zwrócić **podsumowanie w prostym języku zbudowane bezpośrednio na podstawie analizy**: podaje poziom pewności, zawiera każde zastrzeżenie i nie przytacza żadnej liczby, która nie pochodzi z rzeczywistego zapytania. Towarzyszące **sprawdzenie wierności** pozwala agentowi potwierdzić, że jego przeformułowana wersja zachowała pewność i każde zastrzeżenie oraz niczego nie wymyśliła — dzięki temu narracja jest *dowodliwie* wierna, a nie tylko płynna. Każde podsumowanie sugeruje też naturalne kolejne pytanie — zawężenie do pojedynczego elementu, rozbicie zmiany według wymiaru lub wskazanie konkretnego kroku tworzącego wynik, gdy tabelę wynikową buduje więcej niż jeden — abyś mógł zagłębić się w temat, nie znając dokładnego sformułowania. Zobacz [Odpowiedzi, którym można zaufać](/pl/integrations/ai-coding-agents/honest-answers/).

- **Podgląd danych kroku w Wizualnym projektancie przepływów pracy.** Zobacz wynik kroku na miejscu, bez otwierania nowego okna — zadokuj na dole kanwy podgląd pierwszych 100 wierszy z typowanymi kolumnami, liczbą wierszy i kolumn oraz selektorem dla kroków z wieloma wyjściami. Kliknięcie innego kroku zmienia cel podglądu, odświeża się on po zakończeniu uruchomienia, a pełny Eksplorator tabel otworzysz jednym kliknięciem. Zobacz [Podgląd danych kroku](/pl/guides/workflows/preview-step-data/).

- **Zablokuj aplikację Panel przed przypadkowymi zmianami.** Ikona kłódki w każdym wierszu listy Moje aplikacje Panel chroni aplikację tak jak istniejące blokady przepływów pracy i kroków: dopóki jest zablokowana, edycja, usuwanie i przebudowa odmawiają wykonania — a wypchnięcie zmian git do gałęzi aplikacji serwerowej nie przebudowuje jej — natomiast otwieranie aplikacji, jej dzienników i metryk użycia nadal działa. To zabezpieczenie przed wypadkami, a nie mechanizm bezpieczeństwa: każdy, kto może edytować aplikacje Panel, może je odblokować. Zobacz [Blokowanie aplikacji](/pl/guides/panel-apps/using/#blokowanie-aplikacji).

- **Kroki przepływu pracy są numerowane automatycznie.** Każdy krok ma teraz numer — plakietkę na wizualnej kanwie, pierwszą kolumnę siatki kroków oraz to samo „Krok 7” w dziennikach uruchomień, raportach dokumentacji przepływu pracy i listach asystenta AI — dzięki czemu można wskazać współpracownikowi lub agentowi AI „krok 7”, zamiast opisywać krok po nazwie w zagmatwanym zaimportowanym przepływie pracy. Numery podążają za przepływem (krok zawsze otrzymuje numer po krokach, z których czerpie dane), a pozycja na kanwie rozstrzyga remisy od lewej do prawej, a następnie od góry do dołu; kanwa każdego użytkownika numeruje się na nowo na żywo podczas edycji przepływu pracy, z krótkim wyróżnieniem kroków, których numer się zmienił. Kliknij krok prawym przyciskiem myszy (lub kliknij jego plakietkę), aby skopiować gotowe do wklejenia odwołanie, np. „Krok 7 — Clean Customer Names”. Zobacz [Numery kroków](/pl/guides/workflows/step-numbers/).

- **Dwa nowe kroki przepływu pracy — Lista katalogu i Asercja liczby wierszy.** Lista katalogu zapisuje tabelę z plikami w katalogu dokumentów (z opcjonalnym wzorcem plików i opcją podkatalogów), aby kolejne kroki mogły działać na dowolnych obecnych plikach. Asercja liczby wierszy to bramka jakości danych, która przerywa przepływ pracy, gdy dwie tabele mają różną liczbę wierszy. Zobacz [Lista katalogu](/pl/reference/workflow-steps/document/directory-listing/) oraz [Asercja liczby wierszy](/pl/reference/workflow-steps/workflow-control/row-count-assert/).

- **Przejście do dzienników przepływu pracy z Wizualnego projektanta przepływów pracy.** Przycisk **Wyświetl dzienniki** na pasku narzędzi kanwy otwiera widok Dziennik projektu już przefiltrowany do otwartego przepływu pracy — jest to ten sam pełny dziennik uruchomień, do którego w inny sposób docierasz z obszaru projektu. Zobacz [Zaawansowane przepływy pracy](/pl/guides/workflows/advanced-workflows/#wyświetlanie-dzienników).

## Zmieniono

- **Table Update zapisuje do tabeli docelowej zamiast zmieniać źródło.** Krok dawniej nazywany **Table In-Place Update** nazywa się teraz **Table Update** i wrócił do menu Nowy krok. Odczytuje źródło, aktualizuje wiersze pasujące do filtra i zapisuje każdy wiersz — zmieniony i niezmieniony — do wybranej tabeli docelowej, pozostawiając źródło nietknięte do porównania. Kolumny tabeli docelowej zawsze odzwierciedlają kolumny źródła, w tym kolumnę dodaną wyżej w przepływie po ostatnim otwarciu kroku. Ponieważ aktualizacja nie odbywa się już w miejscu, działa w każdym magazynie danych, także w tych, które nie pozwalają zmieniać tabeli w miejscu. Widok jest prawidłową tabelą docelową. Kroki zapisane przed tą zmianą wymagają wybrania tabeli docelowej, zanim zostaną uruchomione, a każdy krok, który odczytywał źródło, oczekując zaktualizowanych wierszy, trzeba skierować na nową tabelę docelową. Zobacz [Table Update](/pl/reference/workflow-steps/tables/table-update/).

- **Złączenie wielu tabel akceptuje dynamiczne tabele źródłowe i docelowe.** Zaznacz **Dynamiczny** w selektorze tabeli i podaj nazwę tabeli lub ścieżkę projektu zamiast wybierać z listy — każda z nich może zawierać tokeny `{variable}` rozwiązywane podczas uruchomienia przepływu pracy, dzięki czemu złączenie może zapisywać do `/03 Results/FACT_GL_{year}` i w każdym okresie pobierać inną tabelę. Tabela docelowa jest tworzona, jeśli nie istnieje. W ten sposób działały już tabele we wszystkich innych krokach; Złączenie wielu tabel wcześniej wymagało tabeli wybranej z listy i nie dawało się zapisać inaczej. Kolumn dynamicznego źródła nie można odczytać podczas projektowania, więc wpisuje się je ręcznie w panelu bocznym. Zobacz [Krok Złączenie wielu tabel](/pl/guides/workflows/multi-table-join-step/).

- **Kolumny wyjściowe Złączenia wielu tabel mogą zawierać wyrażenie lub stałą.** Kolumna wyjściowa pobiera teraz wartość z dokładnie jednego z trzech miejsc — kolumny źródłowej (wraz z aliasem kanwy, do którego należy), **Stałej** lub **Wyrażenia**. **Dodaj kolumnę wyrażenia** dołącza wiersz i otwiera pełny edytor wyrażeń z każdą tabelą z kanwy w przeglądarce kolumn, dzięki czemu wartość może obejmować kilka złączonych tabel. **Post-Join Filter** to ten sam edytor, a nie zwykłe pole tekstowe, i wyświetla kolumny wyjściowe, do których można się odwoływać jako `result.column_name`. Edytor ma teraz trzy karty: wewnętrzna karta **Advanced (server-set)** zniknęła, a jej ustawienia nadal są zachowywane przy zapisie. Zobacz [Krok Złączenie wielu tabel](/pl/guides/workflows/multi-table-join-step/).

- **Importy plików obsługują duże pliki i zachowują typy danych źródła.** Importy plików Excel, JSON, Parquet, Alteryx yxdb, dBASE i o stałej szerokości nie ładują już całego pliku do pamięci, więc duże pliki, które wcześniej kończyły się błędami braku pamięci, są teraz importowane — praktycznym ograniczeniem jest miejsce na dysku, a nie pamięć. Typy danych źródła — liczby dziesiętne, daty i znaczniki czasu — są teraz przenoszone do tabeli docelowej, zamiast przechodzić przez tekst, a kolumny znaczników czasu Parquet zachowują pełną precyzję pory dnia (wcześniej obcinaną do daty). Celowo bez zmian: puste komórki liczbowe nadal ładują się jako 0, a kolumny nazwy pliku, ścieżki, nazwy arkusza, numeru wiersza i czasu ostatniej modyfikacji zachowują się dokładnie jak dotąd, z numerami wierszy liczonymi dla każdego pliku źródłowego. Zobacz [Importuj Excel](/pl/reference/workflow-steps/import/import-excel/), [Importuj JSON](/pl/reference/workflow-steps/import/import-json/) oraz [Importuj Parquet](/pl/reference/workflow-steps/import/import-parquet/).

- **Importy JSON akceptują pliki rozdzielane znakami nowego wiersza i tworzą standardowy tekst JSON.** Krok Importuj JSON akceptuje teraz JSON rozdzielany znakami nowego wiersza (NDJSON) — jeden obiekt na wiersz — oprócz tablic JSON, a zagnieżdżone obiekty i tablice trafiają do tabeli jako standardowy zwarty tekst JSON zamiast notacji w stylu Pythona, więc kolejne kroki mogą je analizować dowolnymi narzędziami JSON. Zobacz [Importuj JSON](/pl/reference/workflow-steps/import/import-json/).

- **Wybierz repozytorium, gałąź i folder dla połączenia Git.** Formularz połączenia Git nie wymaga już wpisywania ścieżki repozytorium, nazwy gałęzi ani ścieżki początkowej — wybiera się je z list na żywo. Wpisz serwer i poświadczenia (dla połączenia PlaidCloud Git nie ma nic do wpisania), kliknij Odśwież, aby wyświetlić repozytoria dostępne dla połączenia, wybierz jedno, aby załadować jego gałęzie, a następnie przeglądaj jego foldery, aby ustawić opcjonalną ścieżkę początkową — dzięki temu błędnie wpisana nazwa nie zepsuje po cichu połączenia. Edycja istniejącego połączenia umożliwia przeglądanie bez ponownego wpisywania zapisanego hasła. Dotyczy PlaidCloud Git i każdego zewnętrznego dostawcy (GitHub, GitLab, Bitbucket, Forgejo, Gitea). Zobacz [Połączenie PlaidCloud Git](/pl/guides/connections/plaidcloud-git/).

- **Śledzenie kosztów przez AI jest dokładniejsze i trudniejsze do zmylenia.** Szacunki what-if to teraz rzeczywiste liczby dla poszczególnych celów, które sumują się przy rozgałęzieniu, a nie górne ograniczenia, i można je zawęzić do pojedynczego celu — a gdy wskazuje się tabelę klucza alokacji lub podstawy zamiast puli wejściowej, agent odmawia oszacowania i wyjaśnia dlaczego. Szacunki what-if dla zmiany wag klucza alokacji są dokładne: przesuwają tylko kwotę, którą klucz faktycznie dzieli, a każdy koszt przechodni pozostaje nietknięty. Agent rozpoznaje teraz mylące układy i obniża w nich pewność — sumę, w której duże wzrosty i spadki znoszą się do niewielkiej zmiany netto, lub zmianę będącą głównie kosztem przechodnim, a nie sterowanym kluczem — podając, o ile faktycznie zmieniła się kwota sterowana kluczem, i nie przeceniając pojedynczego „dominującego czynnika”, gdy podział jest niewiarygodny. Wyjaśnia też alokacje po hierarchii wymiarów, zamiast pozostawiać je bez przypisania. Sprawdzenia aktualności danych obejmują teraz tabele klucza i podstawy, wyniki wytwarzane przez więcej niż jeden krok alokacji można prześledzić, wybierając krok — lub automatycznie, gdy filtr zawęża się do wierszy wytworzonych tylko przez jeden krok — a porównanie rok do roku bez danych z poprzedniego roku mówi o tym wprost, zamiast nazywać zmianę „normalną”. Zobacz [Śledzenie alokacji za pomocą agenta AI połączonego przez MCP](/pl/integrations/ai-coding-agents/tracing-allocations/).

- **Tabele zewnętrzne: odśwież kolumny pojedynczej tabeli ze źródła.** W krokach Import and Export External Tables przycisk **Sprawdź źródło** przy każdej tabeli odczytuje teraz bieżące kolumny wybranej tabeli bezpośrednio z połączonej bazy danych i aktualizuje w miejscu tylko mapowanie tej tabeli — przydatne, gdy kolumny tabeli źródłowej zmieniły się od zbudowania kroku, bez ponownego uruchamiania wykrywania dla całego połączenia. Zobacz [Importuj zewnętrzne tabele bazy danych](/pl/reference/workflow-steps/import/import-external-database-tables/).
- **Obecność w Wizualnym projektancie przepływów pracy pokazuje prawdziwe awatary.** Gdy kilka osób ma otwarty ten sam zaawansowany przepływ pracy, wiersz obecności na pasku narzędzi pokazuje każdą osobę za pomocą jej gravatara (lub inicjałów, jeśli go nie ma), a osoba pojawia się tylko raz, niezależnie od liczby kart przeglądarki, w których go otworzyła. Zobacz [Zaawansowane przepływy pracy](/pl/guides/workflows/advanced-workflows/#kto-tu-jest).

- **Otwieranie serwerowej aplikacji Panel pokazuje teraz rzeczywisty postęp.** Ekran budzenia pokazywał dawniej jeden komunikat przez cały czas uruchamiania, a następnie ogólny limit czasu, więc aplikacja, która w ogóle nie mogła się uruchomić, wyglądała tak samo jak ta, która po prostu działała wolno. Teraz zgłasza faktyczny etap — uruchamianie, przygotowywanie, ładowanie — zgłasza rzeczywistą awarię w ciągu kilku sekund wraz z jej przyczyną i przekierowuje od razu, gdy aplikacja jest już rozgrzana. Aplikacja, która się uruchamia, ale zawodzi podczas ładowania (na przykład z powodu brakującego pakietu), jest zgłaszana jako nieudana wraz z błędem, zamiast wyświetlać pustą stronę. Zobacz [Tworzenie aplikacji Panel](/pl/guides/panel-apps/creating/).

## Naprawiono

- **Table Update nie odrzuca już Ustaw NULL przy zapisie.** Jego mapper kolumn wyświetlał aktualizowane kolumny pod nagłówkiem **Kolumna źródłowa**, pozostawiał **Kolumnę docelową** pustą i w ogóle nie oferował kontrolki **Ustaw NULL** — a zapis kroku po cichu usuwał Ustaw NULL z każdej kolumny, która go miała, przez co krok przestawał czyścić te wartości. Mapper pokazuje teraz nagłówek **Kolumna aktualizacji** obok Stała, Wyrażenie i Ustaw NULL i zachowuje wszystkie cztery. Jeśli Twój krok wcześniej czyścił kolumnę, sprawdź, czy Ustaw NULL nadal jest zaznaczone. Zobacz [Table Update](/pl/reference/workflow-steps/tables/table-update/).

- **Table Upsert działa przez API w obszarach roboczych StarRocks.** Scalanie używane w tych obszarach roboczych było dostępne z silnika przepływów pracy, ale nie z interfejsu API REST, który nadal wymagał instrukcji, których ta ścieżka nie używa, więc upsertu nie dało się tam w ogóle wykonać przez API. Zobacz [Table Upsert](/pl/reference/workflow-steps/tables/table-upsert/).

- **Table Upsert wewnątrz makra zatrzymuje się teraz, zamiast zapisywać do niewłaściwej tabeli.** W obszarach roboczych StarRocks po cichu scalał dane do tabeli samego projektu, a nie do kopii makra. Teraz zgłasza czytelny błąd, a upserty makr w tych obszarach roboczych pozostają niedostępne, dopóki nie zostanie usunięte podstawowe ograniczenie. Zobacz [Table Upsert](/pl/reference/workflow-steps/tables/table-upsert/).

- **Zapis kroku Złączenie wielu tabel zgłasza, co trzeba poprawić.** Zapis z czymkolwiek do rozwiązania kończył się błędem wewnętrznym zamiast informacji, co jest nie tak. Teraz przełącza na kartę z pierwszym problemem i wyświetla wszystkie problemy, a każda karta ma plakietkę z ich liczbą. Selektor **Wybierz z obszaru roboczego…** nie otwiera się już za formularzem kroku, gdzie nie dało się go osiągnąć. Zobacz [Krok Złączenie wielu tabel](/pl/guides/workflows/multi-table-join-step/).

- **Dynamiczne importy Excela znów działają.** Import z Excela skonfigurowany tak, aby wykrywać kolumny z arkusza, a nie z zapisanego mapowania kolumn, kończył się błędem przy każdym uruchomieniu. Teraz importuje zgodnie z konfiguracją. Zobacz [Importuj Excel](/pl/reference/workflow-steps/import/import-excel/).

- **Pusty arkusz nie powoduje już błędu importu Excela z wieloma arkuszami.** Gdy import z Excela obejmuje kilka arkuszy, a jeden z nich jest pusty, import ładuje teraz z tego arkusza zero wierszy i działa dalej, zamiast przerywać cały krok. Zobacz [Importuj Excel](/pl/reference/workflow-steps/import/import-excel/).

- **Importy JSON nie pomijają już kolumn pojawiających się późno w dużym dokumencie.** Kolumna, której pierwsza wartość pojawiała się głęboko w dużym pliku JSON, mogła po cichu zniknąć z zaimportowanej tabeli. Teraz uwzględniana jest każda kolumna dokumentu. Zobacz [Importuj JSON](/pl/reference/workflow-steps/import/import-json/).
- **Asystent AI nie zatwierdza już wyrażenia, które zawodzi przy uruchomieniu.** Kilka funkcji wyrażeń ma nazwę zgodną ze słowem kluczowym Pythona — `IF`, `AND`, `OR`, `NOT` — i zapisuje się je z podkreślnikiem na końcu, jako `func.if_(...)`. Asystent robił to na odwrót: zatwierdzał `func._if(...)`, które nie jest prawdziwą funkcją i zawodzi w czasie wykonania, a odrzucał poprawne `func.if_(...)`. Teraz akceptuje formę, która działa, odrzuca tę, która nie działa, i podaje właściwy zapis, gdy się pomylisz. Przywoływana przy redagowaniu dokumentacja funkcji została poprawiona. Zobacz [IF](/pl/reference/expressions/lakehouse-v2/06-condition-functions/if/).

- **Połączenia REST z uwierzytelnianiem Basic, Klucz API lub Token okaziciela faktycznie się uwierzytelniają.** Wysyłane były wyłącznie poświadczenia OAuth 2.0, więc połączenie skonfigurowane z którymkolwiek z pozostałych trzech typów zawodziło wobec interfejsów API sprawdzających uwierzytelnienie. Wszystkie cztery działają teraz zgodnie z konfiguracją. Jeśli obchodzono to, wpisując poświadczenia ręcznie w **Domyślne nagłówki**, własne uwierzytelnianie połączenia ma teraz pierwszeństwo i ten wiersz można usunąć. Zobacz [Ogólne połączenie REST](/pl/reference/connectors/rest/generic-rest/#uwierzytelnianie).

- **Wyświetlanie punktów końcowych z kolekcji Postman lub specyfikacji API znów działa.** W kroku Żądanie REST przycisk **Załaduj katalog** zgłaszał błąd dla każdego źródła — kolekcji Postman i specyfikacji OpenAPI/Swagger, zarówno wybranych z dokumentów, jak i pobranych z adresu. Znów wyświetla punkty końcowe, a jeśli nie wybrano jeszcze pliku ani adresu, informuje, aby to zrobić. Zobacz [Krok Żądanie REST](/pl/guides/workflows/rest-request-step/).

- **Domyślne nagłówki połączenia REST są teraz faktycznie wysyłane.** Nagłówki ustawione w **Domyślne nagłówki** w połączeniu REST były widoczne w podglądzie żądania kroku, ale pomijane w rzeczywistym żądaniu. Teraz są wysyłane z każdym żądaniem przez to połączenie, w tym z każdą stroną odczytu ze stronicowaniem i każdym żądaniem rozgałęzienia na wiersze. Nagłówek ustawiony w pojedynczym kroku nadal ma pierwszeństwo przed nagłówkiem o tej samej nazwie w połączeniu. Jeśli masz połączenie ze skonfigurowanymi nagłówkami domyślnymi, sprawdź, czy są to nagłówki, które chcesz wysyłać. Zobacz [Ogólne połączenie REST](/pl/reference/connectors/rest/generic-rest/#domyślne-nagłówki).

- **Wypchnięcie zmian do repozytorium serwerowej aplikacji Panel przebudowuje teraz aplikację.** Publikowanie serwerowej aplikacji Panel z połączenia PlaidCloud Git lub GitHub zawsze działało, ale późniejsze wypchnięcia do gałęzi połączenia nie były wychwytywane — aplikacja nadal serwowała wersję, z której została pierwotnie zbudowana, dopóki ktoś nie opublikował jej ponownie ręcznie. Wypchnięcia automatycznie przebudowują i wdrażają aplikację, jak opisano w [Wdrażanie aplikacji Panel z Git](/pl/guides/panel-apps/deploy-from-git/). Zablokowana aplikacja nadal pomija przebudowę, dopóki jej nie odblokujesz. Istniejące aplikacje i połączenia nie wymagają żadnych zmian.

- **Zmiana nazwy warunków uruchomienia kroku znów działa.** Podczas ustawiania warunków, które muszą być spełnione przed uruchomieniem kroku, można teraz zmienić nazwę każdego warunku — edytując nowe pole **Nazwa** w panelu Konfiguracja lub klikając dwukrotnie warunek na liście. Kliknij warunek prawym przyciskiem myszy, aby uzyskać także **Zmień nazwę** i **Usuń**. Zobacz [Warunki uruchomienia kroku](/pl/guides/workflows/step-conditions/).

- **Czytelniejszy błąd, gdy import nie może odczytać żadnych kolumn.** Gdy konfigurujesz lub automatycznie tworzysz import CSV albo tekstowy, a PlaidCloud nie może odczytać żadnych kolumn z pliku źródłowego — na przykład w niektórych eksportach tekstowych Microsoft Access lub w pliku, którego separator albo cudzysłowy nie pasują — informuje o tym od razu, przy zapisie lub tworzeniu importu, zamiast pozwalać krokowi się uruchomić i później zakończyć mylącym komunikatem. Dostosuj ustawienia separatora, cudzysłowu i znaku ucieczki lub napraw plik, a następnie spróbuj ponownie. Zobacz [Importuj CSV](/pl/reference/workflow-steps/import/import-csv/).

- **Kolizje nazw zasobników zarządzanych same się tłumaczą.** Utworzenie konta dokumentów typu Zasobnik zarządzany przez PlaidCloud z nazwą zasobnika, która jest już używana, kończyło się wcześniej ogólnym komunikatem „Internal server error”. Pole **Nazwa zasobnika** wskazuje teraz kolizję bezpośrednio i wyjaśnia, że nazwy zasobników są unikatowe globalnie, wraz ze wskazówką, jak wybrać nazwę bardziej szczegółową — na przykład dodając nazwę firmy jako prefiks. Zobacz [Dodawanie konta Zasobnik zarządzany przez PlaidCloud](/pl/guides/documents/adding-accounts/add-managed-bucket-account/).

- **Konta dokumentów OneDrive i SharePoint — poprawki przeglądania i pobierania.** Otwarcie skonfigurowanego konta dokumentów OneDrive lub SharePoint niezawodnie wyświetla teraz jego foldery i pliki, zamiast kończyć się błędem, a pobieranie pliku działa nawet wtedy, gdy administrator Microsoft wyłączył udostępnianie linków dla witryny. Pobieranie nie zależy już od utworzenia łącza do udostępniania, więc plik w mocno zabezpieczonej witrynie nadal się otwiera zamiast zgłaszać błąd. Zobacz [Dodawanie konta OneDrive / SharePoint](/pl/guides/documents/adding-accounts/add-onedrive-account/).

- **Usunięcie tabeli, z której odczytuje import, wyświetla teraz ostrzeżenie.** Gdy usuwasz tabelę, z której odczytuje krok **Import: zewnętrzna tabela projektu**, PlaidCloud rozpoznaje ją jako używaną i wymaga potwierdzenia wymuszonego usunięcia — zaznaczenia **Wymusić usunięcie tabeli?** — zamiast oferować zwykłe usunięcie, aby tabeli, od której zależy inny projekt, nie dało się usunąć przypadkowo. Dotyczy to także odwołań z kroku w *innym* projekcie współdzielącym dane tego projektu; są one pokazywane w potwierdzeniu bez szczegółów kroku innego projektu (możesz nie mieć do niego dostępu). Zobacz [Importuj tabelę projektu](/pl/reference/workflow-steps/import/import-project-table/).

- **Kroki złączeń — poprawki Kolumn wyjściowych.** W krokach Złączenie wewnętrzne, zewnętrzne, anty i krzyżowe karta Kolumny wyjściowe wyświetla teraz tylko kolumny zmapowane z dwóch źródeł i usuwa nieaktualne wiersze po usunięciu zmapowanej kolumny źródłowej; pasek narzędzi mappera kolumn i zaznaczanie wielu wierszy wróciły; a Summarize jest teraz przełącznikiem domyślnie wyłączonym, więc złączenie nie wymusza już grupowania wyniku — a po jego włączeniu nowe kolumny domyślnie dostają agregację zależną od typu danych, którą można zmienić dla każdej kolumny. Kolumny wyjściowe Złączenia wielu tabel podążają teraz za zmianami nazw i usunięciami w projektancie grafu złączeń. Zobacz [Table Inner Join](/pl/reference/workflow-steps/tables/table-inner-join/) oraz [Krok Złączenie wielu tabel](/pl/guides/workflows/multi-table-join-step/).

- **Poprawki niezawodności Żądania REST.** Zmienne są niezawodnie podstawiane w treściach żądań JSON, ustawienia limitu czasu i ponawiania dla pojedynczego żądania są respektowane (ponawianie ograniczone do metod idempotentnych, więc POST/PUT/PATCH nigdy nie jest wysyłany ponownie), odpowiedzi z ograniczeniem częstotliwości są ponawiane z wycofywaniem, a poświadczenia żądania są maskowane w każdym przechwyconym surowym JSON. Żądanie testowe pokazuje teraz kod statusu odpowiedzi także po sukcesie, a odpowiedź z pojedynczym obiektem jest importowana jako jeden wiersz. Przepływy pracy wyzwalane czujnikiem lub webhookiem mogą też odczytywać metadane wyzwalacza i przychodzący ładunek jako zmienne. Zobacz [Krok Żądanie REST](/pl/guides/workflows/rest-request-step/).

- **Poprawki śledzenia kosztów przez AI.** Śledzenie kosztów obsługuje teraz nazwy kolumn modelu zawierające spacje lub symbole, rozwiązuje tabele podane przez przyjazną nazwę, działa na wynikach kroków uruchomienia modelu i kopiach projektów oraz we wszystkich typach obszarów roboczych. Wykrywanie anomalii oznacza teraz nietypowo duże wahania i zachowuje okresy oznaczone kwartałami w rzeczywistej kolejności czasowej na granicy roku, a dwa błędy w opisach — skok „od zera”, gdy podstawa ważenia była początkowo pusta, oraz zmiana procentowa z błędnym znakiem, gdy wartość poprzednia była ujemna — zostały poprawione.

- **Import/Eksport tabeli projektu ostrzega o pustym źródle.** Gdy krok Import Project Table lub Export Project Table kopiuje z tabeli źródłowej bez wierszy, kończy się teraz ostrzeżeniem, że źródło było puste — dzięki temu nieoczekiwanie pusty wynik łatwo zauważyć, zamiast pozornie cichego sukcesu kroku. Najczęściej oznacza to, że dane projektu źródłowego nie zostały jeszcze zbudowane w chwili uruchomienia kroku. Zobacz [Importuj tabelę projektu](/pl/reference/workflow-steps/import/import-project-table/) oraz [Eksport do zewnętrznej tabeli projektu](/pl/reference/workflow-steps/export/export-project-table/).

- **Pakiety tabel przenoszą teraz wymiar, notatkę i format każdej kolumny.** Eksport tabel do pakietu i import do innego projektu pozostawiał wcześniej puste powiązanie każdej kolumny z wymiarem w zaimportowanej tabeli, a także notatkę i format wyświetlania kolumny. Ponieważ kolejne kroki przejmują ustawienia kolumn z odczytywanych tabel, zaimportowana tabela mogła przenosić tę lukę na wszystko, co z niej zbudowano. Te ustawienia podróżują teraz z pakietem i są przywracane przy imporcie. Gdy kolumna wskazywała wymiar, którego projekt docelowy nie ma, to jedno powiązanie jest pomijane i wymienione w dzienniku importu, zamiast przywracać zepsute łącze — powiąż je ponownie po utworzeniu wymiaru. Pakiety wyeksportowane przed tą zmianą importują się dokładnie tak jak wcześniej.

- **Utwórz i otwórz otwiera teraz właściwy widok dla przepływu pracy DAG.** Użycie **Utwórz i otwórz konfigurację** na nowym zaawansowanym przepływie pracy (DAG) otwierało klasyczną siatkę kroków zamiast kanwy Wizualnego projektanta przepływów pracy. Teraz otwiera kanwę, tak samo jak dwukrotne kliknięcie przepływu pracy. Zobacz [Zaawansowane przepływy pracy](/pl/guides/workflows/advanced-workflows/).

- **Zależności aplikacji Panel mogą znajdować się obok aplikacji.** Serwerowa aplikacja Panel zbudowana z repozytorium Git instaluje teraz plik `requirements.txt` przechowywany obok jej punktu wejścia, a nie tylko ten w katalogu głównym repozytorium — dzięki temu aplikacja przechowywana w podfolderze wspólnego repozytorium może zadeklarować własne pakiety (na przykład `plotly`, `holoviews` lub `hvplot`) i nie wyświetla już pustej strony z powodu brakującej biblioteki. Zobacz [Tworzenie aplikacji Panel](/pl/guides/panel-apps/creating/#dodawanie-zależności).

- **Przenoszenie dużych lub licznych dokumentów między folderami.** Przenoszenie kilku plików naraz — lub jednego dużego pliku — z jednego folderu Document do drugiego działa teraz niezawodnie. Przenoszenie odbywa się pojedynczo, aby lista plików pozostała spójna, a duże przeniesienie dostaje czas potrzebny na zakończenie, zamiast być przerywane w połowie.

- **Asystent AI nie odrzuca już wyrażeń odwołujących się do kolumn z nazwami zaczynającymi się od podkreślnika.** Wyrażenie odwołujące się do kolumny, której nazwa zaczyna się od podkreślnika (na przykład `_MajorAccountFlag`), jest teraz akceptowane. A gdy wyrażenie testuje kolumnę za pomocą `is`, `is not` lub `not` — co w przypadku kolumny nigdy nie pasuje do żadnego wiersza albo powoduje błąd, zamiast robić to, na co wygląda — asystent kieruje do działającego operatora (`is_(None)` dla testu null, `!=`, `~`) zamiast po prostu odrzucać.

- **Asystent AI nie odrzuca już prawidłowych funkcji.** Prawdziwe funkcje, których nie było na liście selektora wyrażeń — `rtrim`, `ltrim`, `to_char`, `substring` i wiele innych — były odrzucane jako nieznane, a zapis dowolnej nazwy funkcji wielkimi literami (`func.SUM`) był odrzucany, nawet gdy wersja małymi literami była akceptowana. Asystent sprawdza teraz nazwy w liście funkcji własnego obszaru roboczego, a nie tylko selektora, i robi to bez rozróżniania wielkości liter.

- **Aplikacje Panel nie renderują się już z niewidocznym tekstem.** Domyślny motyw całej platformy był stosowany do każdej aplikacji Panel, także tych, które nie używają pasującego szablonu strony. W takich aplikacjach malował tekst na biało na białej stronie — aplikacja wyglądała na pustą, a nic w dziennikach tego nie wyjaśniało. Aplikacje zachowują teraz własny wygląd, chyba że zdecydują się na szablon z motywem. Istniejące aplikacje zyskają tę poprawkę przy następnej przebudowie lub ponownej publikacji.

- **Ekran budzenia nie zmienia już wyglądu aplikacji Panel.** Podczas uruchamiania serwerowej aplikacji Panel ekran za nią ustawiał własne tło i kolory jasne/ciemne, a aplikacja je dziedziczyła bez możliwości zastąpienia — przez co mogła renderować się na niewłaściwym kolorze płótna i podążać za preferencją jasnego/ciemnego systemu operacyjnego zamiast własnej. Ekran jest teraz całkowicie usuwany po uruchomieniu aplikacji. Nie gubi też niczego z otwartego adresu: parametry zapytania odczytywane przez aplikację, w tym `?theme=dark`, docierają teraz do aplikacji.

- **Rozpakowanie archiwum zachowuje jego strukturę folderów.** Rozpakowanie `.zip` lub `.tar.gz` do Document spłaszczało wszystko do folderu docelowego — archiwum zawierające `data/master/accounts.csv` dawało sam `accounts.csv`, więc pliki o tej samej nazwie w różnych folderach kolidowały. Zagnieżdżone archiwa rozpakowują się teraz z nienaruszonymi folderami. Archiwa płaskie i pojedyncze pliki `.gz`/`.bz2` pozostają bez zmian. Na kontach dokumentów SFTP foldery docelowe muszą już istnieć, więc rozpakuj zagnieżdżone archiwum do ścieżki, którą już tam utworzono.

- **Błędny harmonogram nie psuje już Harmonogramu zdarzeń.** Jedno zaplanowane zdarzenie z nieużywalną cyklicznością — niemożliwą datą, jak 31. dzień 30-dniowego miesiąca, lub nieprawidłowym wpisem — powodowało, że lista Harmonogramu zdarzeń całego obszaru roboczego i kalendarz harmonogramu kończyły się wewnętrznym błędem serwera, a mogło też uniemożliwić otwarcie projektu. Harmonogram, którego nie da się odczytać, pokazuje teraz po prostu puste następne uruchomienie, a reszta ekranu ładuje się normalnie. Zobacz [Harmonogram zdarzeń](/pl/administration/scheduled-events/event-scheduler/).

- **Błędy przepływów pracy teraz mówią, co faktycznie poszło nie tak.** Gdy krok przepływu pracy zawodził w zadaniu w tle, dziennik uruchomienia i e-mail z powiadomieniem pokazywały tylko ogólny komunikat operacji — „Exception importing directly from remote sql” — podczas gdy rzeczywista przyczyna, na przykład wygasłe hasło w systemie źródłowym, nie pojawiała się nigdzie, gdzie można było ją zobaczyć. Podstawowa przyczyna awarii jest teraz przekazywana do dziennika i e-maila. Gdy wiele tabel zawodzi z jednej wspólnej przyczyny, jest ona zgłaszana raz, a nie dla każdej tabeli, a poświadczenia są usuwane z komunikatu.

- **Żądania REST do innego hosta nie wysyłają już poświadczeń połączenia.** Gdy krok Żądanie REST używał pełnego adresu zamiast ścieżki — w tym linków stronicowania zwracanych przez wiele interfejsów API — działo się coś złego na dwa sposoby: adres był doklejany do hosta połączenia i żądanie kończyło się błędem, a uwierzytelnianie i domyślne nagłówki połączenia były dołączane niezależnie od tego, dokąd szło żądanie. Pełne adresy są teraz używane tak, jak podano, a poświadczenia i domyślne nagłówki są wstrzymywane, chyba że adres wskazuje z powrotem na własny host połączenia — dzięki temu stronicowanie nadal działa, a adres strony trzeciej nigdy nie otrzymuje Twoich poświadczeń. Zobacz [Krok Żądanie REST](/pl/guides/workflows/rest-request-step/).

- **Edycja połączenia REST z uwierzytelnianiem Basic nie gubi już hasła.** Zapis zmiany w połączeniu REST używającym uwierzytelniania Basic, bez ponownego wpisania hasła, odrzucał zapisany sekret. Zapisane hasła są teraz zachowywane dla wszystkich czterech typów uwierzytelniania. Naprawiono też dwie rozbieżności podglądu żądania: nagłówek ustawiony w kroku różnymi wielkościami liter jest łączony tak samo jak w rzeczywistym żądaniu, a pusta wartość nagłówka jest wysyłana jako pusta, a nie jako dosłowny tekst „None”. Zobacz [Ogólne połączenie REST](/pl/reference/connectors/rest/generic-rest/#uwierzytelnianie).

- **Łączenie tabel zachowuje wymiar i formatowanie każdej kolumny.** Gdy Union, Union All, Alokacja lub wielotabelowe Złączenie scala kilka źródeł w jedną kolumnę wyjściową, ustawienia wymiaru, notatki i formatu kolumny były ustalane z tego źródła, które akurat sortowało się ostatnie. Źródło, które nic nie mówiło o wymiarze, mogło zdominować to, które go wskazywało, więc kolumna pozostawała niepowiązana po odbudowach, podczas gdy podobna kolumna odzyskiwała powiązanie. Teraz źródło wskazujące wymiar ma pierwszeństwo przed milczącym, kolumna przekazana bez zmian ma pierwszeństwo przed przemianowaną, a rzeczywista niezgodność źródeł jest zgłaszana w dzienniku kroku, zamiast być rozstrzygana po cichu. Zmiana nazwy kolumny zagregowanej — `SUM(amount)` na `total_amount` — nie kopiuje już wymiaru kolumny źródłowej na sumę, która nigdy nie identyfikowała jego elementu. Zobacz [Table Union All](/pl/reference/workflow-steps/tables/table-union-all/) oraz [Table Union Distinct](/pl/reference/workflow-steps/tables/table-union-distinct/).

- **Table Melt respektuje mapowanie kolumn, które utworzyłeś.** Kolumny celowo pominięte w mapowaniu melt były po cichu dodawane z powrotem do kroku, co w kroku agregującym powodowało błąd całego kroku. Mapowanie, które wymienia swoje kolumny wartości, jest teraz używane dokładnie tak, jak zostało zapisane. Zobacz [Table Melt](/pl/reference/workflow-steps/tables/table-melt/).

- **Kopiowanie tabeli z innego projektu znów działa.** Krok kopiujący tabelę między projektami wywoływał operację, która już nie istnieje, więc każde uruchomienie kończyło się błędem po stronie serwera. Teraz używa tego samego mechanizmu co krok Import Project Table i zgłasza ostrzeżenie zamiast błędu, gdy źródło jest puste. Zobacz [Importuj tabelę projektu](/pl/reference/workflow-steps/import/import-project-table/).

- **Asercja liczby wierszy działa wewnątrz makra.** Krok Asercja liczby wierszy zagnieżdżony w kroku Macro Run lub Macro Concurrent kończył się błędem po stronie serwera; działały tylko uruchomienia najwyższego poziomu, dlatego nie zauważono tego wcześniej. Teraz działa poprawnie na każdym poziomie zagnieżdżenia. Zobacz [Asercja liczby wierszy](/pl/reference/workflow-steps/workflow-control/row-count-assert/).
- **Śledzenie kosztów nie przerywa się już, gdy nadrzędna pula kosztów nie została jeszcze zbudowana.** Pytanie, dlaczego wynik alokacji się zmienił, kończyło się wcześniej niepowodzeniem, jeśli tabela zasilająca alokację nie została wygenerowana — zazwyczaj dlatego, że ta część modelu nie była uruchomiona. Śledzenie kończy się teraz powodzeniem: nadal raportuje zmierzone sumy dla etapu, oznacza rozbicie nadrzędne jako niemożliwe do przypisania zamiast je zgadywać i mówi, które wejście przebudować przed ponownym śledzeniem. Etap, którego suma się nie zmieniła, jest raportowany jako niezmieniony, bez sugerowania, że cokolwiek zmierzono w brakującej puli.

- **Szczegóły tabeli pokazują teraz bieżącą liczbę wierszy.** Otwarcie szczegółów tabeli odczytuje liczbę wierszy z magazynu danych, więc pozostaje poprawna po zapisaniu danych przez SQL — wcześniej mogła pokazywać nieaktualną wartość do czasu odświeżenia kształtu tabeli. Tam, gdzie magazyn danych potrafi tylko oszacować liczbę, jest ona teraz oznaczona jako przybliżona, zamiast być pokazywana jako dokładna.

## Usunięto

- **Wycofane starsze kroki importu i eksportu** — kroki importu SAS7BDAT, importu HTML i eksportu HTML zostały usunięte. Dla tych formatów użyj bieżących kroków importu i eksportu.

- **Wycofano krok importu X12 EDI** — typ kroku został usunięty. Nigdy nie działał: każdy import X12 EDI kończył się błędem przy uruchomieniu. Jeśli potrzebujesz danych EDI w PlaidCloud, przekonwertuj je do obsługiwanego formatu, takiego jak CSV lub JSON, i zaimportuj ten plik.

- **Wycofano opcję Resetuj hasło w aplikacji** — pozycja **Resetuj hasło** została usunięta z menu konta (awatara). Aby zresetować hasło, użyj łącza **Forgot Password?** na stronie logowania.

## Bezpieczeństwo

- **Zmiany przypisań zabezpieczeń zaczynają obowiązywać natychmiast.** Edycja zakresów lub członków grupy zabezpieczeń, usunięcie grupy, zmiana grup zabezpieczeń członka oraz aktywacja i dezaktywacja członka były stosowane z opóźnieniem — do pół minuty dla większości uprawnień, a dla dostępu do serwera Git Twojego obszaru roboczego dopiero przy następnym logowaniu tej osoby, co w przypadku osoby z odebranym dostępem mogło nigdy nie nastąpić. Każda z tych zmian jest teraz stosowana w chwili zapisu, w całej platformie. Nie ma nic do skonfigurowania; przejrzyj dostęp, który wcześniej przyznano lub odebrano, i oczekuj, że jest teraz dokładny. Zobacz [Zarządzanie grupami zabezpieczeń i przypisaniami](/pl/administration/access/managing-security-groups-and-assignments/).
