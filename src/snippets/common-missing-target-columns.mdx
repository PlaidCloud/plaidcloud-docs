#### Target Columns the Target Table Lacks

This step writes into its target table as the table stands, and never adds a column to it, so a run fails on a **Target Column** the table doesn't have. When the step opens, and again whenever you choose another target table, the form reads the target table's columns, filling in any variable in its name from the workflow's variables. Each **Target Column** the table doesn't have is shown in red behind a ⚠ warning sign, and hovering over it says *Column "discount" is not in the target table.* Names are compared without regard to case, so `Discount` matches `discount`. This mark sits alongside the one on a **Source Column** the source columns no longer list, which says *Column "discount" is not in the source columns.*

Nothing is marked while the target table doesn't exist yet, because the run creates it from the mapping, or while its columns can't be read.

When you save a step with a row marked this way, the **Stale Columns Found** dialog lists the marked rows under **Columns**, below *These rows name a column the step can't use:*, and ends with *The step can't be saved until the columns the target table lacks are added to it, or their rows are removed.* It offers two choices:

- **Remove All and Save** — remove every marked row, so those columns are no longer loaded, then save.
- **Cancel** — go back to the step without saving.

There is no **Save Anyway**, because the server refuses to save a mapping that names a column the existing target table doesn't have. To keep a row, add its column to the target table, then save the step again. The exception is a target table named with a variable, such as `{year}/Sales`: the server leaves that check to the run, so the dialog still offers **Save Anyway**.

When rows are marked only for their **Source Column**, the dialog offers **Remove All and Save**, **Save Anyway** and **Cancel**, as described above.
